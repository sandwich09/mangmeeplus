## 1. เป้าหมายและขอบเขต

ผู้ประกอบการเปิดร้านครั้งแรก เข้าใช้ร้านเดิม หรือขอความช่วยเหลือได้โดยไม่เกิดคำขอที่ไม่มีใครเห็น ไม่ได้ร้านใหม่โดยไม่ตั้งใจ และไม่ถูกข้อความรอหลอกว่าระบบยังทำงานอยู่ ทุกสถานะมีทางทำต่อที่ตรวจสอบสิทธิ์แล้ว ไม่ใช่เพียงข้อความ error หรือเบอร์โทรเป็นทางออกเดียว

คงสมัครผ่าน LINE โดยกรอกชื่อร้าน เบอร์มือถือ และอีเมลที่รูปแบบถูกต้อง ไม่บังคับ password/การส่งเมล ใช้ trial preset15 เดิมสำหรับสิทธิ์ทดลองที่ได้รับอนุญาต การใช้งานบิลแรกไม่ผูกกับการกรอกข้อมูลเสริมในตั้งค่า

รอบนี้แก้ G01–G05 และผลกระทบเรื่องสถานะ/สิทธิ์/งานค้าง/การช่วยลูกค้า ไม่ทำ mail provider, เก็บเงิน subscription, eKYC, เปลี่ยนสิทธิ์ OWNER จากข้อมูลที่พิมพ์มา หรือรวมบริษัท/บิล งาน mail provider และ flow จ่ายเงิน subscriber เป็นงานถัดไปหลังส่งเข้า develop/main

## 2. กฎการตัดสินใจและหลักฐาน

1. **คำขอเดิมก่อน:** ตรวจ token/channel/บัญชีและคำขอเดิมก่อนสร้างรายการใหม่ ใช้ submission identity เดิมเมื่อกดซ้ำ/response หาย/เปิดใหม่ เพื่อ resume หรืออ่านผลเดิม คนละคนใช้ key เดียวกันไม่มีสิทธิ์เห็นคำขอกัน
2. **การเปิดร้านเพิ่มต้องเลือกเอง:** หลังสำเร็จแสดงเข้าร้านเดิมเป็นทางหลัก เปิดร้านเพิ่มเป็น action แยก เมื่อเลือกแล้วใช้ submission ใหม่ ไม่ให้การ refresh/retry แปลว่าเปิดร้านเพิ่ม
3. **คงขอบเขตบัญชี:** current LINE proof, active identity/user และ membership/role จริงเป็นหลักฐานทางเทคนิคสำหรับเข้าร้านเดิม ชื่อร้าน เบอร์ อีเมล และรายการย้อนหลังเป็นข้อมูลช่วยตรวจ ไม่ใช่สิทธิ์ย้าย OWNER หรือ merge
4. **คงข้อห้าม:** user/identity suspension และ explicit security hold ไม่ถูก bypass ด้วย unlink, retry, email correction, historical-request exception หรือ admin resolution ของงานสมัคร
5. **อีเมลซ้ำตนเอง:** ยกเว้นการชนกับบัญชีที่ LINE ปัจจุบันพิสูจน์ได้และ contact ของร้านที่มีสิทธิ์จริง แต่ไม่ยกเว้น repeat-trial หรือการชนกับบัญชีบุคคลอื่น อีเมลไม่ใช่ตัวระบุร้าน
6. **ประวัติคำขอเก่า:** คำขอที่ EXPIRED/REJECTED โดยไม่มี company และไม่มี explicit security hold ไม่จองอีเมลตลอดไป คำขอเปิดค้าง/ที่สร้างบริษัทแล้ว/SUSPENDED ยังเป็นเหตุให้ตรวจ; เก็บ audit เดิม ห้ามลบประวัติเพื่อเปิดสิทธิ์ ข้อห้ามที่อิงบัญชีเดิมยังตรวจแยก
7. **อีเมลคนอื่น/คำขอชนกัน:** ไม่ auto ทั้งคู่และไม่ยึดบัญชี เก็บคำขอ ให้แก้ข้อมูล ขอความช่วยเหลือ หรือกลับไปพิสูจน์บัญชีเดิม ผู้ยังไม่มีสิทธิ์ไม่เห็นชื่อบัญชี/ร้านอื่นเพราะกรอก email ตรง
8. **shared contact:** เจ้าหน้าที่เลือกและบันทึกว่าเปิดร้านใหม่ให้คนละคนที่ใช้ข้อมูลติดต่อร่วมกันได้เมื่อคลี่คลายแล้ว ไม่ทำให้ email login ของอีกบัญชีย้ายมา ต้องบอกผู้สมัครว่าเข้าใช้ด้วย LINE และแสดงสถานะ email บัญชีตามจริง
9. **การเปิดร้านกับสิทธิ์ทดลอง:** admin ต้องเลือกผลว่าเปิดร้านใหม่โดยชัดเจน กรณีเคยมี trial ต้องยืนยันอนุญาต trial เพิ่มพร้อมเหตุผลแยกจากการอนุมัติร้าน หากไม่อนุญาตและยังไม่มีการจัดแพ็กเกจ ให้เป็นงานรอจัดแพ็กเกจที่มองเห็น/มีผู้รับผิดชอบ ห้ามสร้างร้านที่ใช้งานไม่ได้หรือสร้าง paid subscription โดยไม่ขอ การขาย/ชำระเงินจริงอยู่ task ถัดไป
10. **กลับร้านเดิม:** admin ชี้ได้เฉพาะร้านที่เจ้าของคำขอมีสิทธิ์ปัจจุบันจาก LINE proof ข้างต้น ปิดคำขอด้วยผลว่าใช้ร้านเดิม ไม่สร้างบริษัท/member/plan/trial ใหม่ ไม่ใช้ email match อนุมาน target และไม่ทำให้การ suspend/retry ของ signup กระทบร้านเดิม
11. **กู้ไม่ได้เพราะไม่มีหลักฐานเดิม:** เปิด/ผูกเคส support พร้อมข้อมูลที่ต้องขอทั้งหมดและผู้รับผิดชอบ ใช้เครื่องมือกู้เดิมเฉพาะเมื่อผ่านกระบวนการยืนยันที่มีอำนาจ ห้ามมีปุ่มข้าม proof; ข้อมูลอ่อนไหวไม่ใส่ใน audit/message โดยไม่จำเป็น กรณีนี้ไม่อ้างว่ากู้อัตโนมัติได้แล้ว
12. **งานไม่หายเพราะเงียบ:** request ที่ส่งแล้วเปิดดู/ทำต่อได้ ข้อมูลที่ยังไม่ส่งจะไม่อ้างว่าบันทึกบน server แล้ว การหมดเวลาหยุด AI ไม่เท่ากับแก้ปัญหาให้ลูกค้าสำเร็จ เคสที่ยังรอมนุษย์ไม่ถูกปิดอัตโนมัติเพียงลูกค้าเงียบ

## 3. Intake และ recovery

- `RECEIVED`/`VALIDATED` ที่ commit แล้วต้อง resume ได้ ไม่สร้างคำขอใหม่ต่อเนื่องเพื่อหลบ unique fence ตรวจ validation/identity/legal/cap ที่จำเป็นก่อน provision ทุกครั้ง
- คำขอ intake ค้างต้องขึ้นแท็บปัญหาและมี retry ที่ปลอดภัย เจ้าหน้าที่ไม่ต้องแก้ DB ตรง ไม่เปิด APPROVE ให้ข้าม validation
- CAS/transaction และ advisory lock เดิมป้องกันสอง browser/สอง admin/ตัว retry กับงานเดิมกำลังทำ ห้าม provision สองบริษัทหรือ claim daily slot ซ้ำ การเปลี่ยนอีเมลระหว่างคิว/approve ต้องตรวจรุ่นหรือ lock เดียวกัน
- บันทึกก้าวที่ทำไปแล้วและผลการตัดสินใจให้กู้ต่อได้โดยไม่รับ trial เพิ่มหรือทิ้งการอนุญาตที่จำเป็น audit/outbox ต้องตามการตัดสินใจจริง เมื่อแจ้งไม่สำเร็จยังอ่านผลจริงและ retry การแจ้งได้
- โค้ด/หน้าเก่าที่ยังไม่ส่ง field ใหม่ต้องได้ผลที่ปลอดภัยและ error ภาษาไทยที่มีทางต่อ ไม่อนุมัติ repeat trial เงียบ ๆ เพื่อความเข้ากันได้
- consent เดิมเป็นหลักฐานที่แก้ย้อนหลังไม่ได้ หากต้องยอมรับ release ใหม่ให้แสดงข้อกำหนดปัจจุบันและเก็บหลักฐานใหม่อย่างชัดเจน ไม่ให้ retry ปลอม consent แทนผู้ใช้

## 4. หน้า LIFF และคิวแอดมิน

ใช้ renderer จากสถานะ server ร่วมกันสำหรับเปิดหน้า, POST สำเร็จ, conflict และ network recovery

| สถานะ/ผลจริง | ข้อความและการกระทำที่ต้องมี |
| --- | --- |
| ยังไม่มีคำขอ | ฟอร์มช่องจำเป็น ตรวจและบอกช่องที่ขาดทั้งหมดให้แก้ครั้งเดียว มีทางกลับร้านเดิม/ขอช่วยที่หาเจอ |
| รับแล้ว/validate ค้าง | ระบุว่าเก็บคำขอแล้ว พร้อม reference และปุ่มทำต่อที่ใช้ request เดิม |
| รอ review | ชื่อร้านตนเอง reference สาเหตุแบบไม่เปิดเผยข้อมูลคนอื่น ขั้นถัดไป และช่องทางคุยเจ้าหน้าที่ |
| ขอข้อมูลเพิ่ม | ข้อมูลที่ขาดทั้งหมด ข้อความของเจ้าหน้าที่ และการแก้ข้อมูลที่ backend อนุญาต ไม่มี approve เพราะหมดเวลา |
| กำลัง provision | บอกกำลังทำ ไม่บอกว่าสำเร็จ ปุ่มอ่านสถานะใหม่ ไม่สร้างงานใหม่ |
| ล้มเหลว/READY ยังปิดงานไม่จบ | บอกสิ่งที่บันทึกแล้วและทาง retry/เจ้าหน้าที่ มี reference ไม่ใช้ข้อความ manual review กลบ system fault |
| COMPLETED/กลับร้านเดิม | บอกผลจริง เข้าร้านผ่าน permission-checked LIFF start; เปิดร้านเพิ่มเป็นทางเลือกแยก |
| ถูกปฏิเสธ/ระงับ/สิทธิ์ไม่พอ | คำอธิบายภาษาไทยและ action ที่ทำได้จริง ไม่สร้างร้านใหม่เพื่อหลบข้อห้าม |
| response หาย/อ่านผลไม่ได้ | บอกว่ายังยืนยันผลไม่ได้ เก็บ submission เดิม อ่านผล/ส่งเดิมซ้ำได้ ไม่บอกว่าส่งใหม่แน่นอน |

ปุ่มใหญ่เห็นชัด ลำดับสำคัญชัด มี loading/disabled ที่ปลดได้เมื่อ error เก็บ input ที่แก้ได้ ข้อความสั้นตรงผลจริง รายละเอียดเทคนิคไม่ใช่คำแนะนำหลัก

คิวแอดมินใช้การตัดสินใจที่ระบุผลชัด: เปิดร้านใหม่, กลับร้านที่มีสิทธิ์เดิม, ขอข้อมูลทั้งหมด, รอจัดแพ็กเกจ, ปฏิเสธ/ระงับตามสิทธิ์เดิม มี preview ว่าจะสร้างร้าน/ให้ trial หรือไม่ การอนุญาตกับ proof ตรวจซ้ำที่ backend ขณะ commit

## 5. Support ที่เดินจบได้

- ใช้ inbox/LINE sender เดิม ตอบด้วย supportRequestId ที่ server หา LINE ผู้ขอเอง ทั้งมีบริษัท, มีเพียงคำขอสมัคร, หรือไม่มีทั้งคู่ ใช้สิทธิ์ system.partner_company.update เดิม ห้ามเปิด endpoint ส่งหา raw LINE ID ตามใจ
- มีทางเปิดเคสจากผู้สมัครจริง ใช้คำสั่งติดต่อเจ้าหน้าที่ใน LINE ที่มีอยู่ได้ หากการส่งคำสั่งไม่สำเร็จต้องบอกความจริงและทาง fallback ห้ามบอกว่ามีคนรับเคสแล้วโดยไม่มี request
- ผูกเคสสมัครกับ signupRequestId เมื่อมี; ส่งแอดมินกลับแถวที่ตรงคำขอ/ค้นหาได้ ไม่ให้ไล่หาจากทั้งระบบ
- ผู้รับผิดชอบเคสต้องมองเห็นได้และ claim/ส่งต่อได้ตามสิทธิ์ การตอบเป็นข้อความรวมสิ่งที่ต้องขอ ตรวจข้อความ/URL/ขนาดตาม sender เดิม
- ส่ง LINE ไม่สำเร็จหรือผลไม่แน่นอนต้องแจ้งและ retry โดยไม่ปิดเคสว่าเรียบร้อย การเปลี่ยนผู้ส่ง/สถานะระหว่างส่งไม่ทับข้อความใหม่ของลูกค้า
- แยกส่งคำตอบ, ลูกค้าตอบกลับ, ทำเรื่องเสร็จ, ให้ AI กลับมาคุย และปิดเคส มี explicit resolution พร้อมเหตุผล/audit ไม่ใช้ answeredAt เป็นหลักฐานว่าเข้าใช้ร้านได้
- คิวมี pagination แบบต่อจากลำดับเดิมได้ งานเก่าไม่หายเมื่อเกิน200หรือมีข้อความใหม่ count ต้องตรง database; ข้อผิดพลาดโหลดคิวไม่แสดงเป็นคิวว่าง
- คง retention ของเคสที่จบตามเดิม ข้อมูลติดต่อ/ข้อความจำกัดเท่าที่จำเป็น ไม่เก็บสำเนาบัตร/รายการธุรกิจเพิ่มในรอบนี้ และไม่ประกาศ SLA ที่ยังไม่มีทีมรองรับ

## 6. Acceptance ที่ต้องมีหลักฐาน

1. Fault หลัง receive/rate counter/validate/decision และตอบกลับหาย → ทำงานเดิมต่อได้ ไม่มี invisible intake
2. Duplicate submit พร้อมกัน/ต่าง tab/reopen completed/add-shop ชัดเจน → จำนวน request/company/trial ตรงเจตนา
3. AUTO ใหม่15 ไม่มี password/mail gate; บิลแรกและ existing preset ไม่ถอยหลัง
4. ทุกสถานะ LIFF ใน audit รวม 409→COMPLETED แสดงผลและ action จริง; browser มือถือเห็นปุ่มและข้อความ ไม่เพียง string test
5. Own email, other user email, own/company shared email, expired/rejected no-company history, suspended/history with company, parallel other LINE: ตรง decision table และไม่ข้าม repeat trial
6. แก้ email ใน pending/needs-info ชน admin approve → ไม่มีการอนุมัติโดยใช้ proof/decision เก่า
7. Admin เลือกกลับร้านเดิม → recheck membership/status/role; wrong target ปฏิเสธ; ไม่สร้างหรือ reset plan; replay ไม่เปลี่ยนสิทธิ์
8. Admin เปิดร้านใหม่/ให้ trial ซ้ำ → explicit authorization; ไม่ยืนยัน trial → คิวงานแพ็กเกจที่มองเห็น
9. คนไม่มีบริษัทขอ help และ admin ตอบถึงผู้ขอจริง; wrong permission/closed case/wrong tenant ปฏิเสธ
10. Send failure, double tap, ลูกค้าตอบระหว่างส่ง และ reload หลังส่ง → ไม่อ้างสำเร็จผิด ไม่ทับงานรอใหม่
11. Support เกิน200, claim/reassign, answered vs resolved, เงียบเกิน24h → งานรอยังหาได้
12. Existing-company reply, web signup/claim, account merge, package change, receipt quota/first receipt tests ที่เกี่ยวข้องยังผ่าน

ใช้ PostgreSQL จริงสำหรับ state/fence/concurrency และ migration acceptance ที่สำคัญ รวม focused tests/typecheck และเส้นทาง browser ที่มีอยู่ ไม่ยิงข้อความจริง ไม่ deploy ระหว่าง validation รอบนี้
