## 2. Goal

A LINE message that corrects a field of a record the assistant itself just captured must end in exactly one honest outcome, and never in a new record:

1. the correction is applied to the intended draft (phase 2) — atomically, ALL requested fields or NONE — with provenance and a confirmation reply naming old → new values; or
2. ONE bounded reply that names the record and hands the user the web edit deep link (phase 1, and the permanent fallback whenever the correction cannot be applied safely); or
3. ONE bounded clarify naming concrete candidate records when the target is ambiguous.

Corrections are never silently dropped, never guessed onto the wrong record, and never turned into a new capture.

## 5. Non-goals

- No final business mutations from LINE (unchanged): no confirm, approve, pay, post, void, export, period close. Correction applies only to editable draft statuses.
- No correction of records not captured via LINE by this same user (web-created expenses stay web-edited).
- No re-attach/replace of the evidence file via correction text; a re-sent image stays on the existing media path, which already carries the shipped duplicate-detection lifecycle (RECEIPT-10 — no work needed).
- No CRM booking reschedule implementation (CUST-12 containment only; full fix is its own spec).
- No new user-facing permission keys; reuse `expense.update`/`expense.review` semantics exactly as `UpdateExpenseDraftUseCase` enforces them today.
- No new tables or columns. The ONLY schema change is the additive `AiTurnIntent.CORRECTION` enum value (phase 1); chat isolation and provenance ride existing JSON columns, and the durable idempotency/consumption markers (§8) reuse `OutboxEvent`. Marker identity includes `companyId` plus only hashed chat/message identity (never a raw LINE/group id); marker event types are a permanent retention exclusion. If the owner rejects marker rows in outbox, the alternative is a small dedicated table and this decision reopens.
- No partial multi-field apply (v1): if ANY requested field fails its guard, the turn mutates nothing and falls back to clarify/guidance.
- No category or source-document-type correction from LINE (v1): line/tax reconciliation semantics for those fields are undefined for a blind chat edit — deferred until specified (guidance reply meanwhile).
- Phase 1 adds no model-driven CORRECTION mutation: its correction branch never creates or updates an expense. It still hardens existing intake mutations so `chatKeyHash` and consumed-clarification markers commit with the capture/signature outcome; other writes are the enum migration, `AiTurn`/event-log rows, Redis cleanup, and audits.

## 6. User Roles

- Staff/accountant who captured the draft (record creator, has `expense.receipt.line_upload` or `expense.create` + `expense.update`): full journey — correction applied (phase 2) on non-finance fields.
- Finance/reviewer (`expense.review`): same v1 field set as the creator (category/source-type corrections are deferred for ALL roles, §5); their extra powers stay in web.
- A different user in the same chat (group OA): never gets the creator's record auto-targeted; receives the guidance reply with the expenses list link.
- Unlinked/opted-out/forbidden users: unchanged existing refusals.

## 7. Business Journey

Phase 1 (guidance, no correction mutation):

1. Within a short window after a capture, user sends a correction ("วันที่ผิด ต้องเป็น 20 ก.ค. 2569", "ยอดจริงๆ 590", "ร้านชื่อ ABC ไม่ใช่ XYZ").
2. Intake router classifies `EXPENSE_CAPTURE_CORRECTION` (new intent; correction of a recent capture is NEVER `EXPENSE_DOCUMENT_CAPTURE`).
3. API resolves candidates deterministically (server-side DB lookup, §8 rules; the model never picks the record in phase 1) and replies by the target matrix: 0 candidates → expenses-list link; exactly 1 → that record's summary (doc type, amount, current date) + web deep link `/companies/{companyId}/expenses/{expenseId}`; more than 1 → expenses-list link naming the top candidates briefly — never silently presenting the newest as "the" record.
4. Reply copy is permission-aware: a user who can actually edit the target in web (record owner with `expense.update`, or `expense.review`) gets "แก้ไขได้ที่ลิงก์นี้"; a capture-only role (e.g. ACCOUNTANT/MARKETING hold `expense.receipt.line_upload` without `expense.update`) gets "เปิดตรวจสอบ/ส่งต่อผู้มีสิทธิ์แก้ไข" copy — the link must never promise an edit the role cannot perform. No record is created or modified either way.
5. `waiting_user` clarifications consumed by this turn — and only those, only for this user — are acked (RECEIPT-08 fix applies to ALL intake terminal branches).

Phase 2 (applied correction):

1. Same routing; router now also emits bounded `correctionHints` (target selected ONLY from server-provided `recentCapturedExpenses` candidates + corrected fields selected from `valueCandidates` under the same membership guards as capture hints).
2. API resolves the target by the SAME matrix — 0 candidates → guidance (list link); exactly 1 → that candidate; more than 1 → requires a valid `correctionHints.targetExpenseId` from the candidate list, and without one (or with an id outside the list) asks ONE clarify naming the candidate records. An invalid model target NEVER silently retargets to the newest record.
3. Field guards: corrected values pass the same deterministic guards as capture (`applyCaptureHintValueGuards` reuse). All-or-nothing: if ANY requested field is ambiguous or fails its guard, the turn applies nothing (clarify for value ambiguity per ADR 0011; guidance otherwise).
4. API applies inside ONE transaction (§8 atomic apply unit) through the `UpdateExpenseDraftUseCase` rules (owner-or-reviewer permission, editable-status gate, VAT/tax rules), appending provenance `corrections[]` and writing the correction audit row in the same unit.
5. Reply confirms: "แก้วันที่เอกสาร 17 มิ.ย. 2569 → 20 ก.ค. 2569 แล้ว" + same web link. Any guard failure → phase-1 guidance reply (permission-aware copy), never a create, never a silent drop.

Phase 3 (CUST-12 containment, CRM customer OA):

1. `bookingReminderText` stops inviting chat reschedule; new copy points to phone/staff contact until reschedule exists.
2. A reschedule/cancel message is detected against the ACTUAL booking table — an upcoming `CrmBooking` with `status = 'BOOKED'` for this conversation/customer (`sourceConversationId`/`customerId`, `startAt` in the future) — NOT against the latest proposal's status (a proposal can be CANCELLED/CONFLICTED while a real booking exists, or BOOKED while staff already cancelled the booking; both false signals are unacceptable).
2.5 Final TOCTOU guard (r4, moved to the COMMIT turn r5): the booking does NOT commit on the turn that carried the reschedule wording — it commits on a LATER explicit-confirm turn (`tryResolveBookingProposal`; "Booking commits ONLY from an explicit confirm"), so a guard keyed to "reschedule-flagged turns" would never run at commit time. Instead, at proposal commit the origin intent is RE-DERIVED deterministically: load the origin message via `proposal.sourceMessageId` (persisted on the proposal) and run the same reschedule/cancel detector over its text. When it fires, the commit's `assertWithinTx` hook COMPOSES the upcoming-`BOOKED` re-check (inside the booking transaction, after the canonical customer lock) with the existing `assertAutonomyEnabledWithinTx` — never replaces it. Found → the hook throws a TYPED error (e.g. `BookingSupersededByRescheduleError`), the booking rolls back, and the handler routes it into the FULL idempotent handoff (flag + outbox + notification + reply policy), never the generic `HANDED_TO_STAFF` shortcut. Required two-turn concurrent test: reschedule-like request → proposal → rival booking commits → user confirms → rollback + full handoff.
3. Precedence matrix (r3) — the booking check runs BEFORE proposal resolution, and the active proposal is transitioned explicitly, never left dangling:
   - actual upcoming BOOKED booking + proposal `PROPOSED`/`AWAITING_CONFIRMATION` → handoff, and the pending proposal is CANCELLED with audited reason `superseded_by_reschedule_handoff`.
   - actual upcoming BOOKED booking + proposal `CONFIRMED`/`COMMITTING` at PRE-CHECK time → handoff; the in-flight proposal is NOT touched (its commit may genuinely be mid-flight and unknowable from here); its id rides in the staff-flag payload so staff reconcile both.
   - the SAME proposal reaching handoff through the confirm-turn TOCTOU guard (§7.2.5) is a different case (r6): the booking transaction has already ROLLED BACK, so nothing is in flight — the proposal must CAS `COMMITTING` → `HANDED_TO_STAFF` in the handoff transaction rather than being left dangling. "Untouched" applies only to the pre-check path.
   - no actual upcoming BOOKED booking → today's behavior unchanged (proposal resolution, then autonomy evaluation).
4. On detection: honest deterministic reply ("รับเรื่องส่งต่อเจ้าหน้าที่แล้ว...") + a concrete staff flag — conversation reopened/priority raised for the inbox views + audit `crm.booking.reschedule_handoff` + outbox `crm.booking.reschedule_requested` (exact conversation fields confirmed in plan phase 3 discovery) — and the turn SKIPS autonomous booking evaluation entirely.
5. Handoff hardening (r3, made concrete r4, ordering + send-policy r5): ONE transaction under the conversation/customer lock performs — proposal CAS (per the matrix), `CrmConversation.status → OPEN` + `priority → HIGH` (fields exist on the model), an audit-existence check for this message's handoff, and an outbox append whose `eventKey` idempotencyPart is the inbound `CrmMessage.id` (the outbox unique `eventKey` is the exactly-once backstop; the append must use a NON-swallowing path — the current helper's silent catch is not acceptable here). Fixed ORDER (r5): handoff transaction → ensure notification → reply. The notification (outside the tx by nature of the notification center) is an IDEMPOTENT "ensure" step: an autonomy-job retry must still ensure it even when the audit/outbox rows already exist AND even when a newer outbound message exists (the retry path's newer-outbound short-circuit must not skip notification ensure for a committed handoff). Staff notification reuses the SLA-breach pattern: `CreateOrUpdateNotificationEventUseCase` (item 06 notification center) to the assignee + inbox managers — the new-conversation scanner does NOT cover reschedules on existing conversations, and inbox list ordering ignores priority, so the notification event is the visibility mechanism. Reply policy (r5 — the current send helper cannot express it: `deterministic=true` still consumes the AI cap, while `holdingReason` is cap-exempt but bypasses the kill-switch recheck): the send helper gains THREE INDEPENDENT options (r6 adds the third): `capExempt`, `respectSendBlocks`, and `preserveAttentionState`. The third is REQUIRED because a successful send today resets the conversation's `unreadCount` to 0 and advances status via `statusAfterStaffReply(...)` → `WAITING_CUSTOMER` — which would immediately undo the `OPEN`/`HIGH` staff flag the handoff transaction just set, i.e. the reply would erase its own escalation. The handoff reply sends with `capExempt: true, respectSendBlocks: true, preserveAttentionState: true` (message row + `lastMessageAt`/`lastOutboundAt`/preview still update; status, priority, and unread are left as the handoff set them). When sends are blocked, the flag + audit + notification still happen and the reply is skipped.
   Notification "ensure" must genuinely reconcile (r6 — `CreateOrUpdateNotificationEventUseCase` is NOT idempotent as-is): it returns early on cooldown before touching recipients, and when a recipient row already exists it never repairs missing per-channel `NotificationDelivery` rows (`NotificationRecipient` has `@@unique([eventId, userId])`, but `NotificationDelivery` has only an index on `(recipientId, channel)` — no unique). The handoff's safety-trigger ensure therefore takes a company+dedup-key advisory lock and uses ONE notification transaction to reconcile event → current assignee/manager recipients → exactly one web + one LINE delivery per recipient; cooldown cannot short-circuit that reconciliation. With no new unique constraint, every caller of this ensure must use the same lock. If the owner prefers a DB-level guarantee instead, a `@@unique([recipientId, channel])` migration is the alternative and the schema-minimal decision reopens (§5). Release dependency: the CRM LINE webhook surface sits at `BLOCKED_OWNERSHIP` in the launch-gate catalog — there is no gate to ride yet, so phase 3 is NOT independently releasable until that ownership is resolved (supersedes §17.6's earlier default).

## 8. Business Rules

- Candidate scope (deterministic, API-side):
  - candidates = expenses with `captureSource = 'LINE_UPLOAD'`, `createdByUserId = caller`, same company, **branch in the caller's current ABAC scope**, **same chat** (bounded `chatKeyHash` stored in `sourceChannelMetadataJson` at capture time matches this turn's chat; raw LINE/group ids never reach the model), status ∈ {DRAFT, NEEDS_REVIEW, READY_FOR_CONFIRMATION} — `EXTRACTING` is EXCLUDED in v1 (web blocks edits during extraction; LINE must not race the OCR pipeline), `createdAt >= now − 24h`, newest first, ≤ 5. Rows captured before `chatKeyHash` existed are excluded (transitional gap ≤ 24h after deploy, accepted). `chatKeyHash` is written on ALL THREE capture paths: text note, direct media, and the pending-media clarify resolution (`createReceiptDraftFromPendingMedia`).
  - Branch scope is applied IN the candidate query, not only at the mutation gate — a user whose branch scope was revoked must not even see the record summary/link.
- Target matrix (single source of truth for BOTH phases; no other selection rule exists):
  - **0 candidates** → guidance reply with the expenses-list link (`/companies/{companyId}/expenses`); no create, no clarify loop.
  - **exactly 1 candidate** → phase 1: that record's summary + link; phase 2: it is the apply target when every field guard passes.
  - **more than 1 candidate** → phase 1: expenses-list link naming top candidates; phase 2: apply requires a valid `correctionHints.targetExpenseId` ∈ candidate list (membership guard — identical pattern to `expenseCategoryId` ∈ `activeCategories`); absent or invalid → ONE clarify naming the candidate records.
  - A model-referenced target outside the candidate list NEVER silently retargets to the newest (or any other) record — that path is clarify/guidance only.
- Routing rules (gateway prompt + parse guards):
  - A message that corrects/repairs a field of an already-captured record (explicitly: mentions a wrong value, "ผิด", "แก้", "ที่จริง", or answers a clarify whose ORIGINAL request was such a correction) routes `EXPENSE_CAPTURE_CORRECTION`, never `EXPENSE_DOCUMENT_CAPTURE`.
  - A spend note still requires what it always required (amount + purpose); a bare value with no purpose in a chat that just captured a record is correction context, not a new note.
  - Clarify inheritance is DETERMINISTIC, not prompt-hoped: an intake CLARIFY raised on a correction turn stores `clarifyForIntent: 'EXPENSE_CAPTURE_CORRECTION'` (plus the shortlisted candidate ids, when the clarify was a target disambiguation) on the ledger `sub_request` entry. The next turn passes it through `openClarifications`, and the dispatcher treats an answer to such an entry as a correction turn regardless of how the model re-reads the original text. The prompt rule ("classify for the ORIGINAL request") remains as belt-and-braces only.
  - Wire contract for inheritance (r3): `LineAiOpenClarification` gains optional `clarifyForIntent` and `candidateExpenseIds` (≤ 5 ids), parsed and bounds-checked by the gateway. `resolvedClarificationIds` is membership-guarded (⊆ the ids sent in this request's `openClarifications`). The candidate snapshot is NEVER authorization: when the user answers, the dispatcher re-runs the candidate query fresh (permission, status, branch, chat scope re-checked) and intersects with the stored shortlist.
  - Ledger isolation per user: `openWaitingUser` filters entries by the turn's `userId` (entries already store it) — in a group chat, user B never receives, resolves, or acks user A's clarification.
  - The route plan returns `resolvedClarificationIds` (ids of `openClarifications` entries the model judged answered by this message); the dispatcher acks ONLY those ids, and only when the entry's `userId` matches the turn user. No blanket ack of everything carried.
  - Low confidence (< 0.6) on the new intent downgrades to CLARIFY exactly like capture/signature today — clearing `correctionHints`, and using a correction-specific clarify template (never the generic receipt-vs-signature copy).
- Field allowlist for applied corrections (phase 2 v1), mapped onto `UpdateExpenseDraftInput`:
  - `expenseDate`, `vendorNameSnapshot`, `vendorDocumentNumber`, note/description — header-only writes; the lines array is NOT touched for these. These stay ONE step (no preview card): they are what this lane has always applied directly, they change no money, and the reply already names old → new per field.
  - **`note` is APPEND-ONLY (amendment 2026-09-05, `line-ai-draft-control-spec-th.md` §5.3).** The header note carries capture provenance — `'LINE receipt upload'` is how anyone later knows the draft came from a photo in this chat — and a correction used to replace it with whatever sentence the user typed (UAT 2026-09-03). `appendUserNote` keeps the existing note and adds `ผู้ใช้แจ้ง: <text>` after a ` · ` separator, capped at 500 characters total and idempotent on redelivery. The audit row carries `noteAppend: true`, because `fields.note.to` records what the user asked for, not what the column now holds.
  - amount — **AMENDED 2026-09-05 by the draft-control spec §5.4 (S-4), and gated on `LINE_AI_DRAFT_EDIT_ENABLED`.**
    - With the flag ON, money leaves this lane entirely: it routes to the `draft_update` tools, which PREVIEW the resulting totals and write only on a `ยืนยัน` postback. An `amount` hint becomes `expense.draft.set_line` with no `lineNumber`; the use case fills it with the record's ONLY line, or refuses `ambiguous_line`, which renders as the existing "บรรทัดไหน" clarify.
    - With the flag OFF this lane behaves exactly as before S-4 — the original rule stands: amount applies ONLY when the target is `sourceDocumentType = 'EXPENSE_NOTE_TEXT'` with at most one simple line and no VAT/WHT/tax-code selection (the shape `CaptureLineExpenseNoteUseCase` writes). Anything richer → guidance reply, because a blind single-line replacement would destroy OCR lines and tax data: `UpdateExpenseDraftUseCase` replaces the whole lines set. A flag has to be a rollback, not a one-way door.
    - `canCorrectAmount` is therefore LIVE, not vestigial: it is what the flag-off path asks. Slice B additionally made it refuse a record whose single line is itself an additional charge, since rewriting that as a product row would silently reclassify a service charge as goods.
  - `expenseCategoryId` and `sourceDocumentType` — DEFERRED (non-goal §5): header-vs-line category propagation and `taxEvidenceStatus` recomputation semantics are undefined for a chat edit. Guidance reply until a follow-up spec defines them.
  - Everything else (VAT/WHT amounts, tax codes, branch, attachments, status) → guidance reply.
- **Reply honesty (amendment 2026-09-05, §5.3).** The confirmation states exactly what was written and nothing more:
  - each changed field reads `เปลี่ยน<ฟิลด์> จาก <เก่า> เป็น <ใหม่>`; a note reads `บันทึกหมายเหตุไว้: <text>`;
  - a turn that changed ONLY the note never says `แก้ไขรายการเดิมให้แล้ว` — its header is `📝 บันทึกหมายเหตุไว้ให้แล้วค่ะ (ยังไม่ได้แก้ตัวเลขในรายการ)`;
  - when the user's message mentions money this lane cannot change (ค่าบริการ / service charge / VAT / ภาษี / ค่าส่ง / ทิป / ส่วนลด / ยอด / ราคา / บาท) and no `amount` was in fact applied, the reply says so plainly and links to the record in the web app. This is the interim answer until the draft-edit tools (S-4) land, at which point the same turn is expected to offer the edit instead.
  - Duplicate RECONCILIATION runs INSIDE the atomic apply unit (r4 — a committed correction with failed reconciliation would be unrepairable behind idempotency): recompute matches, close stale OPEN candidates that no longer match (both directions of the relationship), upsert new ones through the now tx-aware/status-preserving `createDuplicateCandidate`, and recompute `duplicateStatus` from the surviving OPEN set. `DISMISSED`/`CONFIRMED_DUPLICATE`/`OVERRIDDEN` resolutions remain untouched.
- Duplicate-writer LOCK HIERARCHY (r5 — sorted-set locking alone still deadlocks, because the write path takes the TARGET's advisory lock first: Tx-A holds A, Tx-B holds B, both then wait on the sorted pair). The hierarchy binds EVERY flow that writes duplicate candidates or `duplicateStatus` — the complete inventory (r6; the r5 list of three was incomplete): (a) LINE correction reconciliation, (b) web/LINE upload completion scan (`CompleteReceiptUploadUseCase`), (c) OCR apply follow-up, (d) manual rescan (`DuplicateCheckUseCase`), (e) human resolve (`ResolveDuplicateUseCase`, after its EXP-SEC-01 fix) — and (f) the pending-media clarify completion path, which creates a draft and runs the same scan. A writer outside the hierarchy can reopen or overwrite a reconciliation that a correction just committed. Each acquires in this fixed order, never interleaved:
  1. message-scoped advisory lock `companyId:lineMessageIdHash:line-correction` (LINE correction only, BEFORE target resolution) — serializes two deliveries of the same message even when the model picked different targets, making the in-lock idempotency check sound;
  2. company-scoped advisory lock `companyId:duplicate-reconciliation` — taken BEFORE any expense advisory lock by every duplicate writer; two duplicate writers can therefore never hold disjoint expense locks while waiting on each other (ponytail: company-wide serialization of duplicate writes; upgrade to computed lock-sets only if throughput demands);
  3. expense advisory lock(s) (existing `substitute-receipt` key) via the tx-aware write path.
  Required concurrent tests: A↔B simultaneous corrections; same `lineMessageIdHash` two deliveries with DIFFERENT model-chosen targets → exactly one apply; correction × manual rescan, correction × human resolve, and correction × pending-media completion → the committed reconciliation is never reopened or overwritten.
- Atomic apply unit (phase 2): one DB transaction that (1) takes the message-scoped lock, then the company reconciliation lock (hierarchy above), (2) checks idempotency by exact company-scoped marker key `expense.line_correction.applied:line_message:<companyId>:<lineMessageIdHash>`—never by target-local `corrections[]`; a hit returns the marker's bounded confirmation payload, (3) locks and re-reads the target (status, creator, branch scope re-checked inside the lock), (4) applies header/lines through the `UpdateExpenseDraftUseCase` rules, (5) runs duplicate reconciliation (above) when a matched field changed, (6) appends the `corrections[]` provenance entry, (7) writes the correction audit row via `audit.log(entry, tx)`, and (8) inserts the marker through the SAME `Prisma.TransactionClient`. The marker payload contains target expense id + applied field old→new pairs, enough to rebuild the confirmation reply. The existing `OutboxAppendService` is forbidden for markers because it uses the root client and swallows append errors; use the established direct `tx.outboxEvent.create` pattern. The message lock normally makes the exact-key pre-check decisive; the global unique constraint is the backstop, and a rare `P2002` is handled OUTSIDE the aborted transaction by re-reading the same company-scoped marker and returning its confirmation. Audit/marker failure rolls back the mutation. Two concurrent webhook deliveries (distinct event ids, same `lineMessageId`) produce exactly one applied correction. The correction path suppresses the use case's internal generic audit (`expense.review.update`, today a `void` fire-and-forget outside any tx) — the correction audit row is THE record; no false-positive review audit may escape the transaction.
- Tx-aware plumbing is REQUIRED for that unit (r3): `UpdateExpenseDraftUseCase` and the repository write methods it uses (`updateExpense`, `upsertLines`) currently each open their OWN `$transaction` holding the same `substitute-receipt` advisory lock — wrapping them naively self-deadlocks. They must accept an injected `Prisma.TransactionClient` (threading it into `ExpenseTransactionTaxService.resolveLines(..., db)`, which already takes one), while preserving the existing advisory-lock key, signed-substitute-evidence guards, and material-field checks unchanged. This changes plumbing, never mutation semantics.
- OCR staleness guard (r3, scope r4, structural r5): "caller skips on stale" is NOT enough — today the apply transaction closes after header/lines, and the duplicate scan/status plus the extraction use case's summary write run AFTER it, so a correction landing between the passed CAS and those follow-ups would still be overwritten. Therefore the ENTIRE OCR write set — header, lines, duplicate reconciliation + `duplicateStatus`, and the summary/`aiVerifiedFieldsJson`/`missingFields` update the extraction flow performs — moves into ONE transaction guarded by ONE `updatedAt` CAS (token captured by `RequestReceiptExtractionUseCase` before the external call), taking the company reconciliation lock per the hierarchy. Mismatch → nothing in the set is written, `stale_skipped` returned + audited `expense.ocr.apply_skipped_stale`. The `not_expense_document` branch (writes a summary after the external call) gets the SAME CAS treatment. Note (r5): the `EXTRACTING` candidate exclusion is web-parity only, NOT a concurrency defense — extraction never moves the record into `EXTRACTING` before calling the external service. Both interleavings (correction-then-OCR-apply, OCR-apply-then-correction) are tested.
- Provenance durability: the audit log is the durable source of truth for corrections. `aiVerificationSummaryJson.corrections[]` is a convenience mirror, and every summary writer (receipt OCR apply, extraction, classification override) must merge-preserve `corrections[]` instead of replacing the whole JSON — an OCR re-run must never erase correction history.
- Grounding evidence set (r4): hints are grounded against the CURRENT turn's text/candidates PLUS the original text of exactly the clarifications this turn resolves (`resolvedClarificationIds` only — never a union of everything open). The resolved entry's original candidates are recomputed deterministically from its stored `text` with `todayIso` derived from its `askedAt` date (so a clarify answered across midnight cannot shift relative-date readings). This covers the two-turn shape "แก้ยอดเป็น 590" → clarify target → "รายการที่ 2": the 590 grounds from turn 1's evidence, the target from turn 2.
- Value grounding: corrected amount/date must be selected from the evidence set's `valueCandidates` (ambiguous/future dates → ONE clarify, ADR 0011 unchanged). The model never converts numbers/calendars. For CORRECTION hints the guard is mandatory-evidence (r4): an amount/date hint with NO matching candidate anywhere in the evidence set is stripped to `missingFields` — the capture-path legacy of skipping the check when the candidate array is empty does NOT apply to corrections.
- String grounding (v1): `vendorName`, `documentNumber`, and note hint values must be exact substrings of one of the evidence set's normalized texts (deterministic API-side span check; leading/trailing whitespace tolerated). A hint failing the span check is stripped to `missingFields` — the model never authors string values, and paraphrased notes are not accepted in v1.
- Replacement direction guard (r4): `correctionHints` fields carry `{ to, from? }`. `to` must pass the grounding above; when `from` is present it must equal the target's CURRENT field value (normalized) or the hint is stripped. When the evidence contains multiple plausible spans for the same field (e.g. "เลขเดิม 123 แก้เป็น 456") and `from`/ordering cannot prove direction deterministically, the turn asks ONE clarify — never a guessed write of the old value.
- Ledger hygiene (RECEIPT-08, ack timing corrected r5): every intake terminal branch (capture done, signature ticket created, correction applied, correction guidance sent) acks exactly the `waiting_user` entries this turn consumed (`resolvedClarificationIds` ∩ same `userId`), never a blanket sweep — and the ack fires AT THE TERMINAL OUTCOME, decoupled from confirmation delivery: for mutating turns immediately after the business commit (BEFORE the reply attempt), for guidance turns once the terminal reply is composed. Rationale: capture/correction commit before `deliverReply`; an ack gated on delivery would leave the entry open on a failed reply, and the NEXT message would inherit the old request and re-apply/re-create under a fresh `lineMessageId` — the original incident class. Delivery failure is recorded separately (`delivery_pending`, relaxed policy).
- Durable clarification consumption (r6 — the Redis ack alone cannot carry this guarantee): `LineAiLedgerService.ack()` returns `void`, returns silently when Redis is absent, and swallows an `XACK` error into a warn log. So no crash is needed for the incident to recur — a swallowed ack after a committed mutation is enough, and the earlier "`from`-guard backstop" argument does NOT hold (`from` is optional, and capture clarifications have no correction guard at all). Each consumed entry gets a company/stream-scoped marker whose exact key is `ai.line.clarification.consumed:line_clarification:<companyId>:<ledgerKeyHash>:<entryId>`; Redis entry ids alone are NOT globally unique across streams. `ledgerKeyHash = hashMessagePreview(entry.key)` keeps the raw chat/user/group id out of Postgres. For mutating outcomes, marker insertion and the business mutation share the owning transaction; this requires tx-aware terminal finalizers for text capture, receipt/pending-media completion, signature-asset creation, and correction apply — an after-commit dispatcher append is explicitly insufficient. Guidance writes its marker in a short non-swallowing DB transaction after terminal reply composition and before delivery. `openWaitingUser` batch-checks exact keys and suppresses marked entries regardless of outbox status; a marker-lookup error throws a typed temporary-unavailable outcome and the dispatcher sends the existing safe retry reply WITHOUT entering capture/correction dispatch. Returning an empty clarification set and continuing would not be fail-closed: a bare date/amount answer could be misrouted as a new capture. Redis `XACK` remains best-effort cleanup after commit. Required tests: cross-stream equal Redis ids do not collide; Redis unavailable; `XACK` throws; marker lookup fails → no mutation; process dies between commit and ack.
- The normal QA path's blanket `openWaiting` ack is ALSO replaced by `resolvedClarificationIds ∩ userId`. CLARIFY branches keep entries open (unchanged). Test: mutation commit → delivery fail → next turn must NOT inherit or re-apply.
- Reply honesty (RECEIPT-09): capture and correction replies must render the values actually inserted (date, vendor) instead of unconditional "ยังไม่ระบุ".
- Idempotency: applied corrections are idempotent per LINE message id, enforced INSIDE the atomic apply unit's lock (see above) — a webhook redelivery or a concurrent duplicate delivery replies with the already-applied confirmation and never re-applies. The webhook event-claim remains the outer dedup layer as today.
- All hint payloads remain DATA, never instructions (unchanged prompt-injection rule). Candidate lists sent to the router contain only bounded label/amount/date/id — no free-form user content.
- **Draft-edit tools (S-4, draft-control spec §5.4).** Five `draft_update` tools — `expense.draft.set_header`, `set_line`, `add_charge`, `remove_line`, `set_vat_mode` — replace what this lane could not do. They are PREVIEW-only: each resolves the record through the SAME shared chat-provenance rule this lane uses (`line-recent-capture.ts`), runs the real `UpdateExpenseDraftUseCase` inside a rolled-back transaction to produce the resulting lines and totals, and returns a `LineDraftUpdatePreview`. Nothing is written. `requiredPermissions` is `['expense.update']` — exactly what the web PATCH takes, so LINE is never a cheaper way to edit.
  - Confirm and cancel postbacks carry the action plus the opaque `previewId` rendered on that card (P10-L SEC-04); they never carry an expense or company id. The API accepts one strictly shaped action/UUID pair, transports the id as metadata through the buffer/orphan replay, and atomically claims only the matching current preview before acting. Missing, malformed, legacy no-id, and superseded-card buttons expire; typed confirm/cancel text cannot act on a pending preview. The server also rechecks (`companyId`, `userId`, `chatKeyHash`, permission, status, branch and record `updatedAt`). A claimed preview cannot be replaced during the mutation. One preview per chat, TTL 600 s, Redis key `line-ai:draft-preview:<companyId>:<chatKeyHash>` — no new table.
  - Audit: `expense.line_ai.draft_preview` (LOW) at preview, `expense.line_ai.draft_update` (MEDIUM, before/after/previewId/webhookEventId) written INSIDE the apply transaction. **Superseded 2026-09-26:** the direct correction writer and `expense.line_correction.apply` audit are no longer used; all existing-expense edits must follow preview → confirm under [LINE expense edit capability consistency](line-ai-expense-edit-capability-consistency-spec-th.md).
  - Grounding is this spec's rule, imported rather than re-derived: a number a draft edit writes must appear in the turn's evidence or already be on the record. A model, an image, or a forged postback can at most cause a QUESTION to be asked — never an apply. Frozen cases: `LINE_AI_DRAFT_UPDATE_SECURITY_EVAL_CASES`. Every row is `expectedApplyCount: 0` EXCEPT the one outcome defined as a write, `applied_named_edit` (`draft-second-edit-after-apply-is-not-a-replay`, which expects 2): a confirm that SHOULD apply, and must apply the edit the user was last shown. Its danger is the mirror of the others — not an unwanted write, but a wanted write silently swallowed and answered with somebody else's numbers.
  - Edits never consume `RECEIPT_QUOTA`: the quota counts new captures, and no capture use case is on this path.

## 9. Boundary and Ownership

- Expenses module owns the mutation: the ONLY business-mutation path is the existing `UpdateExpenseDraftUseCase`; LINE side adds a thin use case that resolves target + maps allowlisted fields and calls it. No new MUTATION SEMANTICS — the narrowly-scoped repository additions this spec itself requires (tx-aware overloads, the status-preserving duplicate-reconciliation upsert) are plumbing, not new business writes (aligned r5; supersedes the earlier "no new repository write methods" absolute).
- LINE AI module (apps/api) owns routing dispatch, target candidate lookup, marker key/read policy, Redis cleanup, replies, and correction-turn audit; each business module owns inserting consumed markers through its mutation transaction.
- AI Gateway stays a router: emits intent + bounded hints only; still creates no records and calls no ERP tools.
- CRM containment (phase 3) is owned by the CRM/crm-inbox modules; this spec only pins the two deterministic behaviors (reminder copy, post-commit reschedule handoff reply + flag).

### R1 — short replies to read questions (2026-10-05)

- `openClarifications` is original user data, not instructions or mutation authority. A compact `read`, `general` or `help` clause may quote the original `text` of an entry named in `resolvedClarificationIds`, or the sole open entry when ids were omitted. Unknown ids never select another entry. Such a quote becomes a whole reference to the selected live reply part; an entity from the same original text is retained. `write`, `file`, `public` and mutation-route normalization keep live-only evidence and entities.
- The shared semantic parser revalidates a historical entity against selected open-question context at subsequent hops. The API carries `resolvedClarificationIds` into the turn and uses the context-preserving path for general/help with open questions; AgentCore carries both fields. The clause's evidence text remains the live reply, while its goal and open-question context carry the original request. This does not make an old question authority for a write.
- Read filter grounding may use selected original text and deterministic periods recomputed at `askedAt` (Bangkok date), offered as same-id `readClarificationCandidates`, never all open questions. Existing tool, permission, filter and prepared-plan gates still apply; open questions remain ineligible for prepared execution.
- A delivered semantic `needs_user` item with reason `READ_FILTER_NOT_UNDERSTOOD` and same-index `kind=read` writes that exact reason on its waiting ledger entry. It survives append/read/API mapping as `LineAiOpenClarification.reasonCode`. Legacy prose reasons cannot mint it; existing entries without the marker remain model-routed. Group entries remain isolated to their original asker.
- With exactly one marked plain question (no `clarifyForIntent`, `pendingMedia` or `candidateExpenseIds`), one live evidence part, no attachment or retained write, and only unambiguous supplied period spans plus whitespace, punctuation and the closed filler list below, intake builds an ordinary compact `BUSINESS_READ_QUESTION` decision without calling a model. It uses one read clause per period, a whole live-part source, the exact candidate date pair, the offered question id, and an at-most-800-character original-plus-reply goal. The same decoder and route builder validate it. Original text cannot change the kind.
- Filler: ของ, ช่วง, เอา, ขอ, เป็น, แทน, ครับ, ค่ะ, คะ, นะ, จ้า, หน่อย, ก็ได้, แล้วกัน, ละ, ล่ะ, please. `ถึง`, `และ`, `กับ` and hyphens are not filler: ranges/lists must already be covered by candidate spans. Unread words, ambiguous candidates, multiple questions/parts, attachments or unmarked questions take the model path. The shortcut serves evidenced bound turns; legacy requests without evidence retain model routing.
- API budget admission still precedes routing and the following turn keeps its narrowed grant even when intake spends zero model calls. No new provider call or authority bypass is introduced.
- Every compact/route rejection has a closed reason and an actionable repair hint; both decoder and terminal logs include the attempt number and no user/model text. Deterministic decoding is attempt 0. A second period ask by the semantic turn remains outside R1: the turn receives the selected ids, the original question/reason, live evidence and goal needed for the next round to distinguish a reply.

## 14. Edge Cases

- Multiple recent captures, correction referencing "บิลกาแฟ" → candidate labels carry structured fields only (no vendor text, r4), so a semantic reference the labels cannot disambiguate → ONE clarify listing the structured labels; the user picks. Model target selection is valid only from the candidate list; wrong/absent selection → same clarify. Never a write to the newest by fallback.
- Correction after the target was confirmed/posted in web → status gate fails → guidance reply stating it must be edited by review flow in web.
- Correction from a different user in a group chat → zero candidates (creator-scoped) → list-link guidance; user B's turn never carries or acks user A's clarifications (per-user ledger isolation §8).
- Same user corrects from a DIFFERENT chat (private vs group) → zero candidates (chatKeyHash mismatch) → list-link guidance; a correction never targets a record captured in another chat.
- Caller's branch scope revoked after capture → candidate query excludes the record → list-link guidance; no summary/link leak of an out-of-scope record.
- Correction arriving > 24h later → zero candidates → list-link guidance.
- "แก้เป็นวันที่ 32 ก.ค." / future date → value guard rejects → ONE clarify (ADR 0011) naming valid readings.
- Duplicate webhook redelivery AND two concurrent deliveries with the same `lineMessageId` — even when the model chose DIFFERENT targets per delivery → message-scoped lock serializes them, in-lock idempotency yields exactly one apply; the other delivery replies with the already-applied confirmation, no second audit/apply.
- LINE delivery fails AFTER the transaction committed → correction stays applied (audit is truth); no rollback, no re-apply — and the consumed clarification marker already committed with the mutation, so the next message cannot inherit the old request even if Redis cleanup fails. Delivery guarantee is RELAXED in v1 (r3 decision): the expired-token → push fallback inside `deliverReply` is the only automatic retry; if that also fails, the event log records `delivery_pending` for ops and the user sees the corrected state in web / on their next turn. Intake branches have no durable ledger-turn replay today (the drain re-runs QA turns only) — a durable intake-replay is an explicitly recorded fast-follow (§17.10), made safe by in-lock idempotency.
- OCR re-run / classification override after a correction → `corrections[]` preserved (merge-preserve rule §8); audit unaffected.
- Redis down, or `XACK` throws, after a committed correction → the durable consumption marker still suppresses the entry; the next turn does not inherit (§8). Same for a process death between commit and ack.
- A redelivery whose model picks a DIFFERENT target than the original apply → the message-keyed durable marker is found regardless of target; the original confirmation is replayed from the marker payload; no second apply.
- A human resolve / manual rescan / pending-media completion racing a correction → serialized by the company reconciliation lock; the later writer sees the committed reconciliation and never reopens a resolved candidate.
- Router UNAVAILABLE → existing fallback (normal turn path) — corrections then get the assistant's normal answer, still never a create because capture requires a routed plan.
- User corrects two fields in one message ("วันที่ 20 ก.ค. ยอด 590") → all-or-nothing: both applied only when BOTH pass guards; any failure → nothing applied, reply names the failing field (clarify for value ambiguity, guidance otherwise).

## 15. Acceptance Criteria

1. The incident transcript, replayed, ends with zero new records: correction turn produces a guidance reply naming the original draft (phase 1) or updates its `expenseDate` to 2026-07-20 (phase 2).
2. No path exists from `EXPENSE_CAPTURE_CORRECTION` to `CaptureLineExpenseNoteUseCase` or `CreateExpenseDraftUseCase`.
3. Applied corrections appear in the target record's audit trail + `aiVerificationSummaryJson.corrections`, with old→new values.
4. `waiting_user` entries carried into a terminal intake turn are logically consumed exactly once: durable markers suppress only `resolvedClarificationIds ∩ same userId`; Redis `XACK` is best-effort cleanup and unrelated entries survive.
