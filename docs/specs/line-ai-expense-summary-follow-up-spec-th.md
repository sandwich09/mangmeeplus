## 2. ปัญหาและผลลัพธ์ที่ต้องการ

คำตอบสรุปยอดค่าใช้จ่ายระบุว่าไม่รวมเอกสารที่ปฏิเสธหรือยกเลิกแล้ว ผู้ใช้ถามต่อว่า `เอาแบบไม่รวมยอดยกเลิกและปฏิเสธ` แต่ระบบตอบว่า LINE ยังไม่รองรับการกรองสถานะและส่งไปเว็บ ผู้ใช้จึงไม่รู้ว่าเงื่อนไขที่ขอถูกใช้ในยอดก่อนหน้าอยู่แล้วหรือไม่

ผู้ใช้ที่มีสิทธิ์ควรถามย้ำเกณฑ์ของผลที่เพิ่งได้รับแล้วได้คำตอบตรงประเด็นใน LINE หากต้องการยอดปัจจุบันหรือเปลี่ยนช่วงเวลา ระบบต้องอ่านข้อมูลจาก ERP ตามสิทธิ์ปัจจุบันและตอบเฉพาะช่วงที่ตรวจครบ

ภาพเป็นหลักฐานของข้อความที่ผู้ใช้เห็น ไม่ใช่หลักฐานว่า Gateway เข้า branch ใดหรือยอดทุกเดือนผ่าน tool จริง การตรวจ Production คนละ turn ใน [บันทึกยอดสองเดือน](../agent-memory/prod-mangmee-two-month-expense-answer-2026-09-25.md) พบกรณีขอสองเดือนแต่ tool ถูกเรียกเพียงเดือนเดียว จึงห้ามใช้ข้อความคำตอบเดิมเป็นหลักฐานความครบ

## 3. ความหมายของยอดและความสามารถที่มี

| ความหมาย/คำขอ | สัญญาปัจจุบัน |
| --- | --- |
| ยอดปกติจาก `expense.list_recent` | รวม `grandTotalAmount` และจำนวนของเอกสารทุกสถานะยกเว้น `REJECTED` กับ `VOIDED`; รวมรายการรอตรวจสอบด้วย; ช่วงอ้างอิง `expenseDate` |
| `ไม่รวมยกเลิกและปฏิเสธ` | เป็นเกณฑ์เดิมของยอดปกติ ไม่ใช่คำขอ status filter ใหม่ |
| เดือน/ช่วงวันที่/สาขา | `expense.list_recent` รับ `fromDate`, `toDate`, `branchId` และต้องตรวจสิทธิ์/ABAC ที่ ERP tool |
| `เฉพาะยืนยันแล้ว`, `เฉพาะจ่ายแล้ว`, `รวมรายการยกเลิก`, สถานะอื่น | เป็นการเปลี่ยนฐานข้อมูลที่ถาม; LINE summary tool ยังไม่มี input/filter และ aggregate ที่ยืนยันความหมายนี้ |
| `expense.get_breakdown` | จัดกลุ่มยอดตามหมวด/สาขาในฐานที่ตัด `REJECTED`/`VOIDED`; ไม่ใช่ตัวกรองสถานะหรือหมวดเดียว |
| Web expense list API | รับ `status` หนึ่งค่า, `paymentStatus`, `expenseCategoryId`, วันที่, สาขา และแบ่งหน้า; ไม่ใช่ผลรวม LINE สำหรับทุกชุด filter โดยอัตโนมัติ |

สถานะจริงของค่าใช้จ่ายคือ `VOIDED` ไม่ใช่ `CANCELLED` แม้ข้อความภาษาไทยจะแสดงว่า “ยกเลิก” คำตอบที่อ้างว่า “ใช้ไปแล้ว” ต้องไม่สื่อว่าเป็นยอดจ่ายจริงหรือยอดยืนยันแล้ว หากยังรวมรายการรอตรวจสอบ

## 4. ขอบเขต

### ทำในงานแก้นี้

1. จำแนกการถามต่อสรุปยอดค่าใช้จ่ายเป็น **ยืนยันเกณฑ์เดิม**, **ขอยอดเดิมอีกครั้ง/ยอดปัจจุบัน**, **เปลี่ยนช่วงเวลาหรือสาขาที่ tool รองรับ**, **ขอ filter ใหม่ที่ LINE tool ยังไม่รองรับ**, หรือ **อ้างอิงกำกวม** โดยใช้ความหมายของทั้งข้อความและหลักฐาน turn ก่อนหน้า ไม่ใช้ keyword `ยกเลิก`/`ปฏิเสธ` เพียงอย่างเดียว
2. ยืนยันว่าเกณฑ์เดิมตัด `REJECTED`/`VOIDED` เฉพาะเมื่อระบุได้ว่าผลก่อนหน้าที่ผู้ใช้อ้างถึงเป็นผล `expense.list_recent` ที่สำเร็จ ครบ และส่งถึง LINE แล้ว
3. เมื่อจะบอกตัวเลขอีกครั้งหรือเปลี่ยนช่วง/สาขา ให้อ่าน ERP tool ใหม่ตามสิทธิ์ปัจจุบัน พร้อมตรวจความครบของทุกช่วงที่ขอ
4. เมื่อหลักฐานไม่พอ ให้ตอบกติกาทั่วไปหรือถามหนึ่งคำถามเพื่อกำหนดผล/ช่วงที่ต้องการ ห้ามยืนยันว่า *ยอดก่อนหน้า* ถูกต้องจากถ้อยคำของโมเดล

### ไม่ทำในงานแก้นี้

- เพิ่มการกรอง `status`, `paymentStatus`, หมวด หรือ exclusion list ให้ LINE tool
- สร้าง query-patch engine ใช้ได้ทุกโมดูล หรือฐานข้อมูลบทสนทนาชุดที่สอง
- เปลี่ยนนิยามยอดค่าใช้จ่าย สถานะ การนับ การลงบัญชี สิทธิ์/ABAC หรือ API รายการบนเว็บ
- ใช้คำตอบเก่า/ตัวเลขใน chat history เป็น business source หรือข้าม AI credit, entitlement, audit และ delivery gate เดิม

## 5. สัญญาการอ้างอิงผลก่อนหน้า

การกล่าวว่า “ยอดที่แสดงก่อนหน้านี้…” ต้องอาศัย **หลักฐานจากระบบ** ไม่ใช่การอ่านข้อความตอบก่อนหน้าแล้วเชื่อว่าเป็นผลจริง หลักฐานที่ใช้ตัดสินใจต้องระบุได้อย่างน้อย:

- turn ต้นทางและผลส่งถึง LINE ที่ยืนยันแล้ว; บริษัท, ผู้ใช้, membership และแชตเดียวกับข้อความปัจจุบัน; อยู่ในหน้าต่างต่อเนื่อง 15 นาที; หากมีหลายผลที่อาจถูกอ้างถึงให้ถามกลับ
- ชื่อ tool, input ที่ผ่าน allowlist, ช่วงวันที่ตาม `expenseDate`, สาขา/ขอบเขตที่มีผลจริง, เกณฑ์สถานะ, `asOf`, สถานะผล, และตัวบ่งชี้ว่าผลไม่ถูกตัดเพราะ page cap หรือขาดบางช่วง
- สำหรับคำขอหลายเดือน ต้องจับคู่ **ทุกช่วงที่ผู้ใช้ขอ** กับ tool result ที่สำเร็จและถูกใช้ในคำตอบเดียวกัน; เรียกได้เพียงเดือนเดียวห้ามยืนยันว่าคำตอบสองเดือนครบ
- current identity, selected company, entitlement, `line.ai.query`, สิทธิ์อ่านค่าใช้จ่าย และ ABAC ต้องผ่านอีกครั้งก่อนอ้างผลเดิมหรือเรียก tool ใหม่; การย้ายบริษัท/สาขา การถอนสิทธิ์ หรือคนละแชตต้องไม่ใช้ reference เก่า

อาจใช้ turn/ledger และ `LineReadEvidence` ที่มีอยู่เป็นฐานของหลักฐาน แต่ `resultHash`, reply preview หรือ tool name เดี่ยว ๆ ไม่เพียงพอจะยืนยันตัวเลข ความครบ และ delivery ด้วยตัวเอง แผน implementation ต้องกำหนด bounded descriptor และอายุข้อมูลโดยไม่เก็บผลธุรกิจซ้ำเป็นแหล่งความจริงอีกชุด

descriptor สำหรับการยืนยันเกณฑ์เดิมโดยไม่ query ซ้ำต้องผูก turn ต้นทางกับ request/evidence ของ **ทุกช่วงที่ตอบ**, แชต, input ที่ใช้จริง, สถานะความครบ และ `LineTurnOutcome.deliveredAt` ให้ตรวจสอบได้ และแยกการตรวจสิทธิ์ปัจจุบันออกจากการพิสูจน์ว่าครั้งก่อนเคยใช้เกณฑ์ใด `LineReadEvidence.verify()` ปัจจุบัน re-query และเทียบ hash จึงใช้เป็นขั้นตอนของคำตอบแบบ “ไม่เรียก ERP tool ซ้ำ” โดยตรงไม่ได้

## 6. กติกาคำตอบและการเรียก tool

| สถานการณ์ | พฤติกรรมที่ต้องได้ |
| --- | --- |
| ผลก่อนหน้าครบและผู้ใช้ถามย้ำเกณฑ์เดิม โดยไม่ขอตัวเลขใหม่ | ตอบว่า **ผลก่อนหน้าที่อ้างถึง** ใช้เกณฑ์ไม่รวมปฏิเสธ/ยกเลิกอยู่แล้ว ระบุว่าเป็นเกณฑ์ ณ เวลาที่แสดงผล ไม่เรียก ERP tool ซ้ำ และไม่ทวนตัวเลข |
| ผู้ใช้ขอ “ยอดเท่าไร”, “แสดงยอดอีก”, “ตอนนี้”, หรือขอเปลี่ยนช่วง/สาขา | เรียก `expense.list_recent` ใหม่ตามช่วง/สาขาที่ระบุหรือ resolve ได้อย่างปลอดภัย; ตอบยอด จำนวน ช่วง `asOf` และฐานสถานะจากผลใหม่เท่านั้น |
| ผู้ใช้เปลี่ยนเฉพาะสาขาหลังผลหลายช่วง เช่น `ดูเฉพาะสาขา A` | คง **ทุกช่วงเดิมที่พิสูจน์ได้** และ re-query เฉพาะ A แยกตามช่วง; หากไม่ทราบช่วงเดิมครบให้ถามกลับ ไม่ default ไปเดือนปัจจุบัน |
| ผู้ใช้พูด `เดือนก่อนหน้าล่ะ` หรือช่วงสัมพัทธ์อื่น | ใช้เดือนของผลก่อนหน้าเป็น anchor เฉพาะเมื่อมีช่วงอ้างอิงเดียวที่ตรวจแล้ว; เมื่อมีหลายช่วงหรือไม่มี reference ให้ถามว่าเทียบกับช่วงไหน ไม่แปลเทียบกับวันนี้โดยเงียบ |
| ระบุชื่อสาขาที่ซ้ำกัน, สาขาหาไม่พบ หรือเกินขีดจำกัด lookup | แจ้งเป็นภาษาเข้าใจง่ายว่าระบุสาขาไม่ได้ และให้เลือกสาขาจากหน้าเว็บ; ห้ามขอรหัส/UUID, แสดงรหัสภายใน, เลือกชื่อแรก หรือแปลเป็นยอดศูนย์ |
| ผลก่อนหน้าไม่ครบ, ถูกตัด, ส่งไม่สำเร็จ, หมดอายุ หรือระบุผลที่อ้างไม่ชัด | ไม่ยืนยันว่า *ยอดก่อนหน้า* ครบ; หากช่วงเดิมพิสูจน์ได้และ tool ทำได้ ให้ตรวจใหม่; มิฉะนั้นถามหนึ่งคำถามเฉพาะจุด |
| ไม่มีผลก่อนหน้า แต่ถามว่าไม่รวมยกเลิก/ปฏิเสธไหม | อธิบายกติกาทั่วไปของยอด LINE ได้เมื่อผ่าน gate สิทธิ์; ไม่กล่าวว่าเคยแสดงยอดนั้นแล้ว; ถ้าต้องการยอดให้ถามช่วงเวลา |
| ขอ `เฉพาะยืนยันแล้ว`, `เฉพาะจ่ายแล้ว`, `รวมรายการยกเลิก` หรือ filter ที่ tool ไม่มี | แจ้งอย่างตรงว่า LINE ยังตอบยอดตามเงื่อนไขนั้นไม่ได้; ห้ามใช้ยอดปกติหรือ `paidAmount` แทน; ลิงก์เว็บได้เฉพาะเมื่อปลายทางและสิทธิ์ตรวจแล้ว และไม่อ้างว่าจะเห็นยอดตรงกับ LINE ทันที |
| ระบุ filter สถานะไม่ชัดหรือสะกดคลาด เช่น `ไม่รวมปฎิเสธ` | ถามว่าต้องการรวมหรือตัดสถานะใด; ห้ามอ่านหรือแสดงยอดสรุปแบบไม่กรอง |
| เปลี่ยนสิทธิ์/บริษัท/แชต หรือ source/ERP ไม่พร้อม | ใช้ refusal/unavailable/clarification ตามสาเหตุจริง ไม่แสดงตัวเลขเก่าหรือบอกว่าไม่มีรายการ |

ข้อความตัวอย่างสำหรับกรณีภาพ เมื่อหลักฐานผลก่อนหน้าครบ:

> ยอดค่าใช้จ่ายที่แสดงก่อนหน้านี้ไม่รวมรายการที่ “ปฏิเสธ” และ “ยกเลิก” อยู่แล้วค่ะ ยอดนั้นยังรวมรายการที่อยู่ระหว่างตรวจสอบด้วย หากต้องการยอดล่าสุด เดี๋ยวตรวจให้อีกครั้งค่ะ

ห้ามทวน 25,147.80 หรือ 214,899.57 บาทจากข้อความสนทนาหรือ cache ของคำตอบเดิมโดยไม่มีการอ่านปัจจุบันที่ผ่านสิทธิ์ครบ การตอบยืนยันเกณฑ์โดยไม่เรียก tool ไม่ใช่ข้อยกเว้นของ gate สิทธิ์หรือการบันทึก turn/delivery

## 7. ขอบเขตระบบและ failure handling

- API เป็นเจ้าของตัวตน LINE, company/chat binding, สิทธิ์, entitlement, ประวัติ turn, หลักฐานผล และ delivery outcome; AI Gateway ตีความ follow-up แต่ต้องรับเฉพาะ descriptor ที่ API ตรวจแล้ว ไม่เลือกบริษัท/สิทธิ์จาก chat
- ERP source module เป็นเจ้าของยอดและสถานะ; ทุกคำตอบตัวเลขใหม่ผ่าน internal permission-checked tool เดิม AI Gateway ไม่เข้าฐานข้อมูลโดยตรง
- ตัว normalize ช่วงเวลาต้องส่ง candidate ผ่าน API → Gateway → AgentCore ครบ หากช่วงจากข้อความก่อนหน้าหรือคำขอปัจจุบันไม่มี candidate ที่ยืนยันได้ ห้ามปล่อยให้ model คำนวณวันที่เอง; ถามกลับหรือใช้ input ที่บันทึกจาก tool ซึ่งตรวจแล้วตามสัญญา follow-up
- ทุก execution lane ที่เปิดใช้ รวม prepared/simple-read, JSON tool loop และ native loop ต้องรักษาช่วงและสาขาที่ระบุจริง; ถ้า lane ส่งสาขาไม่ได้ต้องตกไปเส้นทางที่ตรวจสาขาได้หรือถามกลับ ห้ามเรียก `{}` แล้วตอบยอดรวมแทนยอดสาขา; การเรียก tool ซ้ำสำหรับหลายช่วงต้องไม่ถูกตัดเพราะชื่อ tool เคยถูกเรียกแล้ว
- เมื่อ deterministic fallback ทำงานโดยปิด orchestration ให้ยืนยันเกณฑ์ด้วย fixed read-free reply หลังตรวจสิทธิ์และ entitlement; คำถามยอดทั่วไปหรือเดือนปัจจุบันอ่านผ่าน `expense.list_recent` เดิมได้ ส่วนช่วงอื่น, สาขา, filter ที่ไม่รองรับ และ follow-up ที่กำกวมต้องถามกลับ/ส่งไปเว็บ; คำถามเลขที่/สถานะ/รายละเอียดและคำถามหลายหัวข้อห้ามถูกแปลงเป็นยอดค่าใช้จ่ายรายเดือน
- การระบุสาขาด้วยชื่อให้ตรวจความเป็นเอกลักษณ์ภายในสิทธิ์ปัจจุบันก่อนอ่านยอด เพราะรหัสสาขาเท่านั้นที่ unique ในบริษัท; สาขา `branchId=null` ต้องแยกความหมายจากสาขาที่ระบุชัด และกรณีมีสาขามากกว่า lookup cap ต้องไม่สรุปว่าไม่มีสาขานั้น
- คำตอบใหม่ต้องตรวจว่าทุกช่วงที่ขอมีผลจริง รวมกรณีสองเดือน การสะกดชื่อเดือนผิด และ output ที่ `truncated`; ขาดช่วงใดต้องระบุส่วนที่ขาด ไม่ตอบเหมือนครบ
- หลัง tool error/timeout/permission denied ห้าม fallback เป็นยอดเก่า ห้ามแปลงเป็น “ไม่พบรายการ” และห้ามแนะนำเว็บว่าได้ยอดเดียวกันโดยไม่มีตัวกรองวันที่/สถานะเดียวกัน
- เมื่อถามหลายหัวข้อพร้อมกัน ให้ตอบหัวข้ออื่นที่ route และมีสิทธิ์ได้ แม้ส่วน expense ต้อง clarify หรือยังไม่รองรับ; คำถามยอดขายล้วนห้ามถูกตีความเป็นการยืนยันเกณฑ์ค่าใช้จ่าย และ read-free criterion proof ต้องปฏิเสธข้อความหลายหัวข้อ
- ใช้ flow idempotency, serialization, credit, usage/audit และ LINE delivery เดิม; log เฉพาะชนิด follow-up, prior-turn reference, เหตุผลที่ reuse/refresh/clarify และ tool outcome โดยไม่บันทึกข้อความหรือยอดเกินนโยบายเดิม

## 8. เกณฑ์รับงานและหลักฐานทดสอบก่อน release

1. จำลองบทสนทนา `สรุป ก.ค. และ ส.ค.` → ได้ผลทั้งสองช่วง → `เอาแบบไม่รวมยอดยกเลิกและปฏิเสธ`: ตอบยืนยันเกณฑ์ใน LINE ไม่เรียก ERP tool ซ้ำ ไม่ทวนตัวเลข ไม่ส่งไปเว็บ และแสดงฐานที่รวมรายการรอตรวจสอบอย่างไม่กำกวม
2. เมื่อคำขอสองเดือนมีหลักฐาน tool เพียงเดือนเดียว ระบบไม่กล่าวว่าผลสองเดือนครบ; ตรวจใหม่ครบสองช่วงหรือถามกลับตามช่วงที่ resolve ได้
3. คำถาม `อันนี้ไม่รวมรายการยกเลิกใช่ไหม` และ `เอาแบบไม่รวมรายการที่ถูกปฏิเสธและยกเลิก` ตีความเป็นการยืนยันเกณฑ์เดิมได้โดยไม่ขึ้นกับลำดับคำหรือมีคำว่า `สถานะ`
4. `ยอดล่าสุดเท่าไร`, `เอาเฉพาะสิงหาคม`, และ status/branch เปลี่ยนระหว่าง turn เรียก tool ใหม่ตามสิทธิ์; ไม่ใช้ผลเก่า ไม่ default ไปเดือนปัจจุบันโดยเงียบหากหมายถึงช่วงเดิม
5. `เฉพาะยืนยันแล้ว`, `จ่ายแล้วกี่ใบ`, `เฉพาะหมวดเดินทาง`, `รวมยกเลิก` ไม่ได้ยอดจาก `expense.list_recent` แบบไม่กรอง และไม่อ้างว่า `expense.get_breakdown` เป็น status filter
6. เปลี่ยนบริษัท, chat, membership, branch scope, สิทธิ์ หรือ entitlement ระหว่างสอง turn แล้ว reference เดิมใช้ไม่ได้; ไม่มีข้อมูลข้าม scope ใน reply, model input หรือ link
7. ผลเก่าที่ failed, undelivered, truncated, หมด 15 นาที, ไม่พบ `asOf`/ช่วง, หรือมีหลาย candidate กำกวม ต้อง refresh/clarify/decline ตามสาเหตุ ไม่ยืนยันจาก reply preview
8. ทดสอบ API → Gateway → AgentCore และ ERP result → composer → LINE card/text ครบทั้ง answer, clarification, forbidden, unavailable, delivery failure และ retry; บันทึก verification commands/results ใน task memory
9. `ดูเฉพาะสาขา A` หลังผล ก.ค.+ส.ค. ใช้ทั้งสองช่วงและ branch ID ของ A ไม่ใช่เดือนปัจจุบันหรือยอดทุกสาขา; ชื่อซ้ำต้องบอกว่าแยกสาขาไม่ได้และให้เลือกจากเว็บโดยไม่แสดงหรือขอรหัส/UUID, branch ที่อยู่นอก 100 รายการแรกต้องไม่ถูกตีเป็นไม่มี, รายการส่วนกลางไม่ถูกรวมในยอด A
10. `แล้วเดือนก่อนหน้าล่ะ` หลังผล ส.ค. ใช้ ก.ค.; หลังผล ก.ค.+ส.ค. ถาม anchor; typo เดือนที่ให้ candidate ไม่ครบต้องไม่ตอบราวกับได้ครบทุกเดือน
11. การตอบคำถามสาขาใน prepared lane ต้องไม่ทิ้ง branch; JSON/native lane ต้องครอบคลุมผลหลายช่วงและรายงานช่วงที่ tool ไม่สำเร็จ; test assert tool input/output และ delivery outcome ไม่ตรวจเพียง reply text
12. คำถามรวมยอดขายกับค่าใช้จ่ายต้องตอบส่วนยอดขายที่ตรวจได้และแจ้งข้อจำกัดของ filter ค่าใช้จ่าย โดยไม่อ่านยอดค่าใช้จ่ายแบบไม่กรอง; คำถามยอดขายที่ไม่มีบริบทค่าใช้จ่ายต้องไม่ถูกตอบด้วย fixed expense criterion หรือข้อความข้อจำกัดของค่าใช้จ่าย

งาน implementation ต้องมีแผน scoped change และทดสอบจุดต่อระหว่างโมดูลตาม `AGENTS.md` ก่อนรับ handoff; spec นี้เพียงอย่างเดียวไม่ใช่หลักฐานว่าแก้ Production แล้ว
