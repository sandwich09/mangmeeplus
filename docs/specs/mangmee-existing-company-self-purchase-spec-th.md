# Spec: บริษัทเดิมซื้อแพ็กเกจ catalog เองได้

วันที่ 2026-09-21 · สถานะ **implement ในเครื่องแล้ว / ยังไม่ deploy** · แผน [mangmee-existing-company-self-purchase-plan-th.md](../plans/mangmee-existing-company-self-purchase-plan-th.md) · memory [legacy-company-self-purchase.md](../agent-memory/legacy-company-self-purchase.md)

## 1. เป้าหมายและมติ

OWNER ของบริษัทเดิมที่ไม่มี `CompanyPlanTerm` หรือมี term ที่ Admin กำหนดเอง ต้องเลือกแพ็กเกจ catalog ที่เปิดขายและชำระเงินด้วย flow ปกติได้ โดยไม่ต้องให้ทีมงานสร้าง paid history เทียมหรือตรวจแพ็กเกจเดิมก่อนทุกครั้ง ภาพ UAT วันที่ 2026-09-16 แสดงช่องว่างนี้: หน้าเว็บให้เลือก แต่ `quote` ตอบ `BILLING_LEGACY_REVIEW_REQUIRED` ก่อนติดต่อ Stripe ([หลักฐาน](../research/uat-billing-native-2026-09-16.md)). **ยังไม่มีการสำรวจจำนวนบริษัท Production** จึงไม่สรุปว่าทุกบริษัท Production ถูกบล็อก

มติ Owner ในบทสนทนานี้: **แพ็กเกจที่ซื้อใหม่เริ่มทันทีเมื่อชำระสำเร็จ; วันคงเหลือของแพ็กเกจที่ Admin ให้ไม่ทบและไม่เป็นส่วนลด**. ก่อนมี verified paid invoice และ apply สำเร็จ สิทธิ์เดิมยังอยู่ตามสถานะปัจจุบัน; การกด quote, Checkout, กลับจาก Stripe หรืออีเมลแจ้งเตือนไม่เปลี่ยนสิทธิ์เอง

มติ Owner เพิ่มเติม 2026-09-21: ถ้าบริษัทเดิมใช้เมนูมากกว่าแพ็กเกจ catalog ที่เลือก **แสดงเมนูที่จะหยุดใช้ก่อนชำระ** และหลังชำระสำเร็จปรับสิทธิ์ทั่วไปเหลือชุดของแพ็กเกจที่ซื้อ; สิทธิ์พิเศษที่ Admin ตัดสินให้เฉพาะรายยังคงอยู่. ห้ามถือ legacy fail-open หรือ `grantOrigin=null` เพียงอย่างเดียวเป็นสิทธิ์พิเศษของ Admin

Spec นี้แก้เฉพาะ catalog self-purchase ของบริษัทเดิม และเป็นมติใหม่สำหรับข้อ `B09` ใน [แผน Stripe หลัก](../plans/mangmee-stripe-billing-implementation-and-test-plan-th.md) ส่วน legacy/manual; การ implement ในเครื่องแทนกฎ `BILLING_LEGACY_REVIEW_REQUIRED` ของ [UI spec § legacy recovery](mangmee-line-web-billing-ui-spec-th.md), [UI plan § Native UAT legacy-company recovery](../plans/mangmee-line-web-billing-ui-plan-th.md) สำหรับบริษัทที่ผ่าน preflight. ไม่เปลี่ยนราคาที่อนุมัติ, gate เปิดขาย, Enterprise lock, การเก็บเงิน subscription เดิม, ข้อห้ามซื้อเมื่อมีหนี้/refund ค้าง หรือสิทธิ์ Admin/security hold

## 2. ผู้ใช้และเส้นทางหลัก

1. OWNER เลือกบริษัท → หน้าแพ็กเกจอ่านสถานะบริษัทและ offer รายเดือน/รายปีที่เปิดขาย; พนักงานไม่มีปุ่มซื้อ. บริษัทไม่มี term แสดง “ยังไม่มีแพ็กเกจที่ตั้งค่า” ไม่แสดง “ไม่จำกัด” เป็นสิทธิ์ซื้อ
2. OWNER เลือก tier/interval → server ตรวจ policy/cohort/gate, อีเมลที่ยืนยันแล้ว, บริษัท/hold, ราคา Stripe, term+feature+capacity snapshot, รายการชำระ/คืนเงินค้าง แล้วออก quote อายุสั้น. ถ้าสาขาหรือสมาชิกเกิน limit ให้เลือกสิ่งที่คงไว้ก่อน quote ที่ชำระได้
3. Quote แสดงยอดวันนี้, ภาษี, การต่ออายุอัตโนมัติ, วันที่คาดว่าเริ่ม/สิ้นสุด, โควตาใหม่, สิทธิ์ฟีเจอร์และ capacity ที่เปลี่ยน, และข้อความตรง source: `NO_TERM`, `TRIAL`, `ADMIN_MANUAL` หรือ `DEAL`. สำหรับ `ADMIN_MANUAL` ต้องระบุวันสิ้นสุดเดิมและ “วันคงเหลือไม่ทบ/ไม่ลดราคา” ก่อน consent
4. Checkout ใช้ quote snapshot และ idempotency key เดิม, ตรวจ source/version/capacity/สิทธิ์/consent ซ้ำภายใต้ lock. มีหนึ่ง active attempt ต่อบริษัท; provider timeout/UNKNOWN ให้ติดตาม attempt เดิม ไม่ชวนซื้อใหม่
5. Worker ตรวจ invoice ที่จ่ายจริงกับ account/mode/customer/subscription/offer/period/snapshot ก่อน apply. การเปลี่ยน term, capacity, package-owned feature entitlements, receipt grants, audit/outbox และ `APPLIED` marker ต้องสำเร็จเป็นธุรกรรมเดียว. หน้า return รอ `APPLIED` และ protected action จึงบอกว่าใช้งานแพ็กเกจแล้ว

### ตาราง source ที่ต้องแยกก่อน quote

| Source ปัจจุบัน | การซื้อ catalog ครั้งนี้ | หลัง verified paid apply |
|---|---|---|
| ไม่มี term (`NO_TERM`) | `INITIAL`; ไม่มีวันเดิมให้ทบ; ตรวจ legacy usage/feature ที่ใช้อยู่ | สร้าง term จาก paid period, สร้าง paid receipt source และ entitlements ที่ถูกต้อง |
| `FREE_TRIAL_15` | ใช้ first-purchase flow เดิม | paid ทันที, วัน trial ที่เหลือไม่ทบ |
| term Admin/manual ไม่มี paid provenance (`ADMIN_MANUAL`) | `INITIAL` แม้มี `BillingAccount` ว่างจาก attempt เก่า; แจ้งวัน/สิทธิ์เดิมที่จะสิ้นสุด | paid ทันที, วัน Admin เดิมไม่ทบ/ไม่คืนเงิน, เก็บ audit ประวัติเดิม |
| active catalog subscription ใน Stripe account+mode ปัจจุบัน (`PAID_CURRENT_MODE`) | ใช้ repeat/upgrade/plan change เดิม; **ห้าม**ตีเป็น `INITIAL` | ยึดสัญญา paid เดิมและกติกา credit/renewal เดิม |
| catalog subscription เดิมใน mode ปัจจุบันสิ้นสุดแล้ว (`PAID_EXPIRED_CURRENT_MODE`) | ใช้ restart/recovery เดิม, ตรวจหนี้/คืนเงิน/collection และเลือก capacity ถ้าจำเป็น | เริ่มสัญญาใหม่จาก verified paid period; ไม่ฟื้น quota ที่หมดอายุ |
| term ผูก paid account คนละ account/mode (`PAID_OTHER_MODE`) | ตรวจ mapping และ active collection ก่อน; ถ้ายังมี payable subscription ให้หยุดพร้อมเหตุเฉพาะ ไม่สร้าง subscription ซ้อน | ไม่แทน paid source ข้าม mode จากชื่อ tier หรือแถว account ว่าง |
| term/account/invoice ขัดกัน (`SOURCE_INCONSISTENT`) | หยุดก่อนสร้าง collectible Checkout พร้อม reference ให้ operator ตรวจหลักฐานจริง | ห้ามเดาว่าเป็น manual หรือ paid จาก tier/account row อย่างเดียว |
| ดีลที่จ่ายแล้ว (`DEAL_APPLIED`) | ต้องใช้กติกา conversion ของดีลที่กำลังตกลงแยก; ยืนยันราคา/credit ก่อนเปิด Checkout | ห้ามทำให้เงินค่าดีลคงเหลือหายไปโดยไม่เปิดเผย |
| Admin/security hold, disputed/refund/debt, active/UNKNOWN attempt | ใช้ hold/recovery ของกรณีนั้น; ไม่เปิด Checkout ใหม่ | เก็บ paid+HELD/issue ถ้าจ่ายแล้วชน hold; ไม่ปลด hold ด้วยเงิน |

`BillingAccount` ที่มีเพียง customer หรือ attempt **ไม่ใช่หลักฐานว่าเคยซื้อ**. Source paid ต้องอิง invoice/subscription/grant ที่ verify และ mapping mode ปัจจุบัน; tier name อย่างเดียวไม่ใช่หลักฐาน. `COMPANY_SALES_CLOSED`, gate `new_sales`, unsupported offer, verified email, company identity/OWNER และ platform launch gates ยังมีผลตามเดิม

## 3. กติกาการแทนที่ term และสิทธิ์

- สำหรับ Admin/manual: ไม่ยืด term จาก `termEndsAt` เดิม ไม่เอาวันเหลือไปคูณเป็น credit; service period ใหม่อ้าง base invoice line ของ subscription ที่จ่ายแล้วตาม [package spec §5](mangmee-package-entitlements-spec-th.md). Quote ต้องบอกเวลาเริ่ม/สิ้นสุดเป็นเวลาคาดหมาย; หลังชำระให้แสดงเวลาจริงจาก provider และไม่อ้างว่าเริ่มใช้ก่อนยืนยันเงิน. หาก payment method ที่จ่ายล่าช้าทำให้ provider period เริ่มก่อน paid confirmation ต้องแก้ provider/activation contract หรือไม่เปิดวิธีนั้นใน flow นี้จนยืนยันจำนวนวันได้รับจริงได้
- Failed/cancelled/expired Checkout ไม่ลบ term/สิทธิ์ Admin เดิมและไม่สร้าง paid receipt grant. `UNKNOWN` คง reservation จนตรวจ provider เป็น terminal. `PAID` แต่ apply ค้างต้องมี issue, owner-facing pending/reference และ operator retry invoice เดิม; ห้ามยิง Checkout ใหม่เพื่อแก้
- `Company.status=DISABLED` ที่มี `termDisabledAt` เพราะ term หมดอายุ/ยังไม่มีแพ็กเกจ อาจเข้า owner billing recovery และเปิด ACTIVE หลัง paid apply; hold จาก Admin/security, suspended/archived และ membership ที่ถูกถอนห้ามปลด. ต้องใช้ lifecycle reason/provenance ที่อ่านย้อนหลังได้ ไม่ใช้ `termDisabledAt` เพียงตัวเดียวตัดสินหากมี hold อื่น
- การเปลี่ยนจาก no-term fail-open หรือ manual entitlement ไป paid ต้องได้ feature set ตาม **approved versioned offer snapshot**. STARTER/BASIC/PRO ปัจจุบันใช้ starter 17 explicit keys ตาม [package spec §2–3](mangmee-package-entitlements-spec-th.md); future catalog version อาจต่างกัน. ห้ามสร้างสิทธิ์จากชื่อ tier หรือเปิด feature ที่ launch gate ปิด. สิทธิ์ Admin ที่มี provenance ชัดต้องคงเป็น independent override; legacy fail-open ที่ไม่มี row ไม่เท่ากับ Admin override. ก่อน Checkout ต้องคำนวณ feature impact และงานค้างที่ต้อง runoff; เมื่อปิด feature ใหม่ต้องใช้ transition/epoch/runoff ที่ [entitlement command](../../apps/api/src/modules/system-partner-management/application/use-cases/set-partner-features.use-case.ts) ใช้อยู่ ไม่ update boolean ตรง. ถ้าแยก package-owned กับ Admin override ไม่ได้จากข้อมูลปัจจุบัน ให้ทำ provenance/migration หรือ targeted preflight ที่แก้ได้ก่อนเปิดขาย cohort นั้น ไม่รับเงินแล้วปล่อยสิทธิ์ไม่ตรง
- สาขาและสมาชิกเกิน limit ต้องเลือกเก็บผ่าน `capacityOptions`/`capacityValid` และแสดงผลกระทบก่อน consent; apply อาจ suspend ส่วนเกินพร้อม audit แต่ไม่ลบข้อมูล, ห้าม suspend OWNER หรือทรัพยากรที่ผูกคำขอเบิกค้าง. ถ้า source เปลี่ยนหลัง quote ให้ stale/requote ก่อนจ่าย; ถ้าเปลี่ยนหลังจ่ายให้ paid+HELD พร้อม repair ของ invoice เดิม
- Receipt OCR ก่อนซื้อของ manual/no-term ใช้ `LEGACY_MONTH`; หลังจ่ายใช้ paid grants ของ account ปัจจุบันร่วมกับ Admin gift grant ที่ยังมีผล. ไม่ยกยอดเดือนเดิมเป็น paid grant, ไม่คืน usage ที่ใช้แล้ว, ไม่รีเซ็ต counter หรือสร้าง grant ซ้ำ. Web/LINE OCR และ `BillingStatus.usage` ต้องอ่าน source เดียวกัน. งบ AI ที่ Admin ตั้งและ abuse brake ยังมีผล; paid package ไม่ reset spend หรือเปิด cost-bearing route อื่น
- `PackageChangeRequest` ที่ OPEN ต้องไม่ถูก Admin approve manual หลัง paid conversion; request ที่ตรง tier และไม่มีหลักฐาน payment อื่นอาจ fulfill จาก invoice ที่ APPLIED ตามกติกาเดิม. Request ไม่ตรง tier ต้องปิดเป็น superseded หรือแสดงว่าไม่เกี่ยวพร้อม audit/ข้อความ ไม่ค้างเป็นคำขอให้ Admin เปลี่ยน paid term. Deal ที่ APPROVED/checkout ค้างต้องระบุ precedence และ payment fence ใน §7

## 4. Backend / frontend contract

ใช้ `GET status`, `GET catalog`, `POST quote`, `POST checkout`, `GET attempt/return` เดิม ไม่ต้องสร้าง purchase endpoint ใหม่. เพิ่มข้อมูลเฉพาะที่ลูกค้าต้องตัดสินใจ:

- `BillingStatus`: source/eligibility reason ที่ derive จากกฎเดียวกับ quote สำหรับ route ปัจจุบัน; `allowedActions.new_sales` สื่อว่าเริ่ม quote ได้จริง (ยกเว้นข้อมูลที่ quote ต้องตรวจแบบสด เช่น provider ราคา/อีเมล). `NO_TERM` และ `ADMIN_MANUAL` ต้องซื้อได้เมื่อผ่าน gate; บอก pending/refund/hold ด้วยเหตุเฉพาะ; no-term usage `limit:null` ห้ามแปลเป็น “แพ็กเกจไม่จำกัด”
- `BillingQuote`/persisted `BillingSnapshot`: `previousSource`, old term end, กฎเริ่มทันทีและไม่ทบวันสำหรับ manual/trial ที่สื่อจาก source/quote, feature snapshot version/hash, entitlement/capacity impact และข้อความ consent revision ที่ตรงผล. ไม่รับ source/price/feature/old days จาก client. `termVersion`/`termProjectionHash` อย่างเดียวไม่ครอบคลุมการเปลี่ยน entitlements/deal/hold; snapshot ต้อง pin source revisions ที่เกี่ยวข้องและ recheck ตอน checkout/paid apply
- Web + LINE entry ใช้ shared billing page: แสดง loading, stale/retry, quote errors ที่ตรงสาเหตุ, บริษัทที่เลือก, source และคำเตือนวันเดิมก่อนกดจ่าย; เด้งกลับ/เปลี่ยนบริษัทต้องไม่ใช้ quote เก่าหรือสร้าง charge ซ้ำ. `INITIAL` copy ปัจจุบันที่กล่าวถึง “วันทดลอง” ทุกกรณีต้องแยก manual/no-term. เจ้าของที่ term หมดอายุใช้ recovery route; พนักงาน/บริษัทอื่น/role revoked ไม่มี checkout
- Public catalog/marketing แสดงเพียงราคาที่เปิดขายและ availability; eligibility ของบริษัทเป็นข้อมูล authenticated และไม่ฝังไว้ใน public route. Admin directory/timeline ต้องแสดง source ก่อน/หลัง, invoice/attempt reference, manual term เดิมและ reason ที่ถูกแทน, paid+HELD, ไม่แสดงว่าบัญชีว่างคือจ่ายแล้ว. Notification ส่งหลัง apply; ส่งล้มเหลวไม่ย้อนสิทธิ์

## 5. ความสอดคล้องกับดีลและบัญชีขาย

[Sales/deals spec](mangmee-sales-deals-and-locked-signup-spec-th.md) ยังเป็น DRAFT และมี R9/S14 เดิมขัดกับมติ D5 ภายหลังเรื่อง catalog subscription → deal; ให้ยึดมติ D5 เป็นแนวทางของทิศนั้น. ทิศ **deal ที่จ่ายแล้ว → catalog** ยังต้องกำหนด credit ของมูลค่าดีลที่เหลือก่อนเปิด Checkout; มติไม่ทบวันของ term ที่ Admin ให้ **ไม่ใช่**คำตอบแทนดีลที่ลูกค้าจ่ายแล้ว. ระหว่างรอมติ ให้ catalog แสดงข้อเสนอได้ แต่ปิดการสร้าง collectible quote สำหรับ `DEAL_APPLIED` ด้วย reason เฉพาะและทางเลือกตรวจดีลเดิม; ห้ามใช้ `BILLING_LEGACY_REVIEW_REQUIRED` กว้าง ๆ

ถ้าบริษัทมีดีล APPROVED ที่ยังไม่จ่าย เจ้าของเลือก catalog เองได้; ใน quote ต้องบอกว่าเป็นราคา catalog และไม่ได้ใช้ราคาดีล. เมื่อลูกค้าชำระ catalog สำเร็จ ให้ยกเลิก/mark superseded ข้อเสนอที่ยังไม่จ่ายอย่างมี audit เพื่อไม่ให้สอง Checkout active พร้อมกัน. ดีลที่มี payment pending/UNKNOWN ต้อง reconcile เดิมก่อนเปิด catalog ใหม่. รายงานฝ่ายขายใช้ verified paid source/attribution ตาม Sales spec; ห้ามนับการซื้อ catalog เป็นยอดดีลเพราะบริษัทเคยมีดีล

## 6. ตรวจ impact / bug / gap ตาม module

สถานะ `OBSERVED` คือพบจาก source ปัจจุบัน; `REQUIRED` คือสิ่งที่ต้องปิดก่อนเปิดขาย; `DEPENDENCY` คือร่างงานอื่นที่อาจเปลี่ยน source. ลำดับ P0 = เสี่ยงรับเงินแต่สิทธิ์ผิด/เก็บซ้ำ, P1 = flow ขาดหรือสิทธิ์ผิด, P2 = UX/ops/history

| Module / source | ผลตรวจและงานที่ต้องทำ | สถานะ |

## 8. Implementation checkpoint 2026-09-21

- Source classifier ใช้ร่วมกันที่ status/quote/checkout; บัญชีว่างไม่เป็นหลักฐาน paid. `NO_TERM`/`ADMIN_MANUAL` ผ่าน quote ได้เมื่อ preflight ผ่าน; source ขัดกันและ normalization ไม่พร้อมให้เหตุผลเฉพาะ
- Quote แสดงวันเดิมและเมนูที่หาย; snapshot pin feature source/target. Verified initial invoice เขียน term, feature transition/epoch/runoff, paid receipt grant, audit และ APPLIED ใน transaction เดียว. สิทธิ์ Admin เฉพาะรายอ่านจาก transition log; no-row fail-open ถูก materialize เป็น cohort `EXPLICIT` ของ package ที่ซื้อ
- Admin set/renew term หยุดเมื่อ paid pointer หรือ Checkout ค้าง; LINE package request ที่ยังไม่จ่ายและ tier ไม่ตรงถูก supersede เมื่อ initial catalog purchase สำเร็จ. Request ที่มีหลักฐานจ่าย/สลิปยังให้ทีมงานตรวจ ไม่ปิดเอง. หน้าปัญหาใบแจ้งหนี้ของ operator แสดงเหตุสิทธิ์เมนูเปลี่ยนและให้ตรวจ invoice เดิมก่อนเปิดสิทธิ์หรือคืนเงิน
- Local unit 34 cases ผ่าน (รวม snapshot เสียต้องไม่เขียนสิทธิ์); PostgreSQL จริงพิสูจน์ rollback/rights/Admin override/no-op `updatedAt`/request supersede 2 cases; billing renewal/grace regression 13 cases ผ่าน; contracts/API/web typecheck ผ่าน. ดูคำสั่งและผลใน [memory](../agent-memory/legacy-company-self-purchase.md)

ก่อนปล่อย Production ต้องมี read-only inventory แบบนับจำนวนตาม source/term/feature provenance/overcapacity/deal/active attempt/holds/TEST-LIVE mapping โดยไม่เก็บ PII ในรายงาน; HTTP/auth, browser/E2E, UAT Stripe native paid/fail/retry และ release protocol ตาม [runbook](../runbooks/uat-production-v2-deployment.md). Paid-deal→catalog ยังไม่มีมติและไม่มี runtime deal apply. หลักฐาน UAT 2026-09-16 พิสูจน์ trial→paid และ legacy quote refusal เท่านั้น ไม่ใช่หลักฐานว่าการแปลงบริษัท manual/no-term สำเร็จ. โค้ดรอบนี้ยังไม่เปลี่ยน UAT/Production
