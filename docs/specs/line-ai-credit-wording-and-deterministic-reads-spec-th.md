# Spec: LINE AI — คำว่า "เครดิต AI", ข้อความปฏิเสธการอ่านเอกสาร และคำตอบธุรกิจแบบ deterministic (wave 2)

> ส่วนเพิ่มจาก [สเปกซื้อเครดิต AI และจำนวนอ่านรูปใบเสร็จเพิ่ม](chat-credit-and-receipt-addons-spec-th.md) (2026-09-29): W-01 ยังมีผล — “เครดิต AI” เป็นชื่อเดียวของเงิน AI ที่ลูกค้าเห็น และยอดของลูกค้าทั้งจากแพ็กเกจและที่ซื้อเพิ่มคือ “เครดิต AI”; จุดที่คอนโซลแสดงเพดานใช้จ่ายรายเดือนของแอดมินใช้ **“เพดานเครดิต AI ต่อเดือน”** เพื่อไม่ชนกับยอดของลูกค้า (มติ T-06, add-on §17.1). สำหรับร้านที่ย้ายไปกติกา add-on แล้ว: วลี “ของเดือนนี้/เดือนหน้าเริ่มใหม่” เปลี่ยนเป็นวลีตามรอบของแพ็กเกจ, ไม่ใช้ “เครดิต AI ส่วนแชต”, ข้อความขีดจำกัดของร้านบอก “ติดต่อทีมงาน” ไม่ใช่ผู้ดูแลของร้าน (T-05), ยอดทีมงานกับยอดซื้อรวมเป็น “ยอดเพิ่มเติม” และไม่แสดงยอดกันไว้ (§17), ยอดรูปชื่อ “จำนวนอ่านรูปใบเสร็จ” ส่วนประโยค “เครดิตสำหรับการอ่านเอกสารไม่พอ” คงไว้กับร้านที่ยังไม่ย้าย (คำถาม Q6 รอ Owner). ร้าน legacy ใช้ §3–§5 เดิม. Operator holds/สิทธิ์/audit คงเดิม; deterministic business reads อยู่นอกการเปลี่ยนนี้. หมายเหตุนี้ไม่ยืนยันว่า runtime เปลี่ยนแล้ว

## 3. คำศัพท์ (ใช้ทุก surface)

| เดิม | ใหม่ | หมายเหตุ |
| --- | --- | --- |
| งบ AI | **เครดิต AI** | ใช้ "เครดิต AI" ไม่ใช่ "เครดิต" ลอย ๆ เพราะระบบบัญชีใช้คำว่าเครดิต (เดบิต/เครดิต, บัตรเครดิต, เครดิตภาษี) อยู่แล้ว |
| งบ AI ส่วนแชต / เพดานแชต | **เครดิต AI ส่วนแชต** | |
| งบ AI สำหรับ/ส่วนอ่านเอกสาร, สิทธิ์อ่านเอกสารด้วย AI (จำนวนครั้ง) | **เครดิตสำหรับการอ่านเอกสาร** | ครอบทั้งเงินส่วน OCR และจำนวนใบ (§4) |
| โควตา AI ของแพ็กเกจเดือนนี้ครบแล้ว | **เครดิต AI ของเดือนนี้หมดแล้ว** | |
| ใช้งบ AI ครบแล้ว / งบเต็ม | **เครดิต AI หมดแล้ว** (exceeded) — ห้ามใช้ "หมด/ครบ/เต็ม" กับกรณี insufficient (§9.1 เดิม) | |
| งบ AI ที่เหลือไม่พอ… | **เครดิต AI ที่เหลือไม่พอ…** | insufficient |
| ยังตรวจสอบงบ AI ไม่ได้ | **ยังตรวจสอบเครดิต AI ไม่ได้** | unavailable |
| กันไว้ระหว่างเรียก AI (reserved) | **เครดิตที่กันไว้ระหว่างเรียก AI** | |

กติกา: จำนวนเงินยังแสดงเป็นบาทที่เดิม; ไม่มี surface ใดได้ตัวเลขเงินเพิ่มจากที่เคยแสดง; ชื่อ field/enum/error code/telemetry ไม่เปลี่ยน (เปลี่ยนเฉพาะข้อความที่คนอ่าน); คำภาษาอังกฤษใน UI ที่มีอยู่ ("AI budget") เปลี่ยนเป็น "AI credit" แบบเดียวกัน

## 4. ข้อความปฏิเสธการอ่านเอกสาร (LINE และเว็บ)

ข้อเท็จจริงสามอย่างต้องอยู่ครบและตรงจริงเสมอ: (1) เหตุ (2) สถานะไฟล์ — เก็บไว้แล้ว / เก็บไม่สำเร็จ / ไม่ได้เก็บ (3) ยังไม่ได้บันทึกรายการ และห้ามสัญญาว่าจะลองใหม่เอง ห้ามมีตัวเลขเงิน

| เหตุ (code) | ข้อความเหตุ (ส่วนแรกของ reply) |
| --- | --- |
| เงินส่วนอ่านเอกสารหมด (`AI_MONTHLY_BUDGET_EXCEEDED` scope OCR หรือ TOTAL บนเส้นทางรูป), เงินเหลือไม่พอเริ่มอ่าน (`AI_BUDGET_INSUFFICIENT`), จำนวนใบครบ (`OCR_MONTHLY_LIMIT_EXCEEDED`) | **เครดิตสำหรับการอ่านเอกสารไม่พอ** |
| ตรวจเครดิตไม่ได้ (`AI_BUDGET_UNAVAILABLE`, `OCR_QUOTA_UNAVAILABLE`) | ตอนนี้ยังตรวจสอบเครดิต AI ของร้านไม่ได้ |
| ระบบกำลังทำงานก่อนหน้า (`AI_BUDGET_BUSY`) | ระบบกำลังประมวลผลงานก่อนหน้าอยู่ |
| ผู้ดูแลปิดการอ่านเอกสาร (`OCR_FEATURE_DISABLED`) | บริษัทปิดการอ่านเอกสารด้วย AI ไว้ค่ะ (คงเดิม) |

ตัวอย่างประกอบ (รูปเก็บไว้แล้ว): `💚 รับรูปไว้แล้วค่ะ แต่เครดิตสำหรับการอ่านเอกสารไม่พอ จึงยังไม่ได้อ่านและยังไม่ได้บันทึกรายการค่าใช้จ่ายนะคะ` + ตัวเลือกเดิม (บันทึกเป็นใบเสร็จ/เก็บไว้เฉย ๆ/…) ตามที่ `MEDIA_CLARIFY_REPLY` มีอยู่; กรณีเก็บรูปไม่สำเร็จ/มีรูปรอคำตอบ/ไม่มีสิทธิ์ ใช้ tail เดิมของ `formatBudgetMediaNotStoredReply` แต่เปลี่ยนเหตุตามตารางนี้

สิ่งที่ยังแยกจากกันภายใน: code, scope, terminal class, การคืน/ไม่คืนจำนวนใบ (R-05) และเงินที่จอง — spec นี้รวมเฉพาะ **คำที่ลูกค้าอ่าน** ไม่รวม semantics

เว็บ (อัปโหลดเอกสาร/สเตทเมนต์/CRM): key ใน `workspace-dictionary.ts`, `banking.logic.ts`, `InboxAiPanel.tsx` และ error map ใช้คำตาม §3 และประโยคเหตุตาม §4 โดยคงข้อเท็จจริงว่าไฟล์ยังอยู่และยังไม่ได้อ่าน

## 5. ข้อความฝั่งแชต, แอดมิน และ billing

### 5.1 แชต (Flex card + drain notice)

| กรณี | หัวการ์ด | ข้อความ |
| --- | --- | --- |
| TOTAL หมด | เครดิต AI เดือนนี้หมดแล้ว | เครดิต AI ของเดือนนี้หมดแล้วค่ะ (ร้านทดลอง: ช่วงทดลองมีเครดิต AI จำกัดต่อเดือน) เดือนหน้าเริ่มใหม่ หรือขอเปลี่ยนแพ็กเกจเพื่อใช้ต่อได้เลยนะคะ |
| CHAT หมด | เครดิต AI ส่วนแชตเดือนนี้หมดแล้ว | เครดิต AI ส่วนแชตของเดือนนี้หมดแล้วค่ะ … (ส่วนอ่านเอกสารยังใช้ได้ถ้ามีเครดิต — ไม่ต้องอ้าง เพราะยังพิสูจน์จากการ์ดไม่ได้) |
| insufficient | เครดิต AI เดือนนี้เหลือไม่พอ | เครดิต AI (ส่วนแชต) ที่เหลือของเดือนนี้ไม่พอเริ่มงานนี้ค่ะ … |
| drain notice (reclaimed turn) | — | ข้อความ text เดิมโดยแทนคำตาม §3; integrity check ต้องอัปเดตให้ตรง exact string ใหม่ |

ปุ่ม "ดูแพ็กเกจ" / "ขอเปลี่ยนแพ็กเกจ" คงเดิม

### 5.2 System Admin console (partner detail → AI และโควตา) และ support timeline

เปลี่ยนคำตาม §3 ทุก label/heading/notice/toast/confirm/ประวัติการปรับ (`PartnerAiAdjustmentHistory`) รวม browser smoke `admin-ai-adjustments-smoke.ts` ที่ยึดข้อความ exact; ความหมายและตัวเลขไม่เปลี่ยน; หัวข้อ "แยกเพดานงบ AI ของบริษัทนี้" → "แยกเพดานเครดิต AI ของบริษัทนี้"; timeline "ใช้งบ AI ของเดือนนี้ครบแล้ว" → "เครดิต AI ของเดือนนี้หมดแล้ว" และประโยคส่วนแชต/อ่านเอกสารตาม §3

### 5.3 Billing admin (owner decision 5)

- `readWarnings` ใบเสร็จ: `AI_BUDGET_REACHED` → "ร้านนี้ใช้เครดิต AI ของเดือนนี้หมดแล้ว"; `AI_OCR_BUDGET_REACHED` → "เดือนนี้ร้านนี้ไม่มีเครดิตสำหรับการอ่านเอกสารเหลือแล้ว (ใช้หมดหรือตั้งเพดานไว้ 0 บาท) เครดิตส่วนอื่นที่เหลืออยู่ใช้อ่านเอกสารไม่ได้"
- เพิ่ม warning คำล้วน (member ใหม่ของ `BillingReceiptReadWarning`, additive): `AI_CREDIT_HOLDS_PENDING` → "มีงาน AI ที่กำลังทำอยู่หรือยังไม่ทราบผล ระบบกันเครดิตไว้ชั่วคราว เครดิตที่ใช้ได้จริงอาจต่ำกว่าที่แสดง ตรวจได้ที่หมวด AI และโควตา" เมื่อ `readAiBudgetReadiness` รายงาน reserved > 0 หรือ `unresolvedHolds` > 0 ในเดือนนี้ (ไม่มีตัวเลขเงิน)
- หน้าปรับแพ็กเกจ (`BillingPlanAdjustmentUnchanged`, แสดงเงินอยู่แล้ว): เพิ่ม field additive `aiReservedSatang` และ `aiUnresolvedHolds` และบรรทัด "เครดิต AI เดือนนี้ X บาท · ใช้แล้ว Y บาท · กันไว้ระหว่างเรียก AI Z บาท" + เมื่อ unresolved > 0: "มี N รายการที่ยังไม่ทราบผลจากผู้ให้บริการ AI เครดิตส่วนนั้นยังถูกกันไว้"
- SHARED และ SPLIT ให้ warning นี้เหมือนกัน; บริษัทที่ไม่มี hold ต้องได้ผลเดิมทุกตัวอักษร (นอกจากคำตาม §3)

### 6.1 หลักการ

- คำถามอ่านข้อมูลธุรกิจแบบ "ค่าเดียว/รายการเดียว" ตอบด้วย formatter ที่ compile ไว้ (เลน prepared simple-read) — 1 model call (intake) เท่านั้น
- คำถามแบบ "แยก" (แยกหมวด/สาขา/ช่วงเวลา, อธิบายรายการ และการเปรียบเทียบที่ไม่เข้าเกณฑ์ §6.1.1) ใช้เส้นทางปกติ: tool คืนข้อเท็จจริง → `compose()` deterministic → โมเดล "ขัดเกลาภาษา" และเพิ่มคำแนะนำได้ **แต่ตัวเลขทุกตัวต้องมาจาก tool data หรือการคำนวณในโค้ด** — numeric guard เดิมของ composer เป็นกลไกบังคับ (ตัวเลขที่ไม่มีใน tool data/คำถาม/บริบท ⇒ fallback เป็นข้อความ grounded) และต้องมี test ที่พิสูจน์ว่า "ตัวเลขที่โมเดลคำนวณเอง" (ผลต่าง/เปอร์เซ็นต์/ผลรวมที่ tool ไม่ได้ให้) ถูกปฏิเสธ ถ้าผลิตภัณฑ์ต้องการผลต่าง/เปอร์เซ็นต์ ให้โค้ดคำนวณแล้วใส่เป็น fact ก่อน
- Production เปิดเลนนี้ (owner): ยืนยันว่า deploy default ปัจจุบันเปิดอยู่จริงทั้ง UAT/Production; แก้ comment ล้าสมัยใน `deploy.sh`; family ใหม่ทุกตัวเข้า allowlist default
- ข้อจำกัดที่พบตอน implement (2026-09-18) และ **ไม่แก้**: guard ที่ปฏิเสธคำแนะนำจริง ๆ ไม่ใช่ numeric guard แต่เป็น vocabulary guard `preservesSemanticGrounding` — ทุกคำในคำตอบต้องอยู่ใน tool data / คำถาม / `SAFE_REPLY_WORDS` ฉะนั้นประโยคแนะนำที่ใช้คำอย่าง "ควร", "ราคา", "ผู้ขาย" หรือแม้แต่ "นะคะ" จะ fallback เป็น grounded text; และคำใน `SAFE_REPLY_WORDS` ที่เป็นคำประสม (เช่น `ตรวจสอบ`) ไม่เคย match เพราะ `Intl.Segmenter` ตัดเป็น `ตรวจ`+`สอบ` (`response-composer.agent.ts` `SAFE_REPLY_WORDS`/`wordTokens`). การขยายรายการคำ = ขยายสิ่งที่โมเดลพูดได้ ต้องเป็น owner decision แยก ไม่ใช่ผลพลอยได้ของ wave นี้

### 6.1.1 สรุปเปรียบเทียบค่าใช้จ่ายหลายเดือน (2026-10-05)

- เมื่อคำขออ่านตั้งแต่สองข้อขึ้นไปใช้ `expense.list_recent` หรือ `expense.get_breakdown` ตัวเดียวกัน อ่านช่วงต่างกันสำเร็จครบ และใช้ฐาน/ตัวกรอง/สิทธิ์/การจัดกลุ่มเดียวกัน ให้โค้ดตอบเป็นสรุปเดียวที่คำขอแรก ไม่เรียกโมเดลแต่งคำตอบเปรียบเทียบ ข้ออื่นยังมีสถานะและแหล่งข้อมูลครบแต่ไม่มีข้อความซ้ำหรือข้อ numbered เพิ่ม
- รองรับสูงสุด **8 ช่วง** ต่อ turn ตามเพดาน 8 tool calls ของ planner; ไม่ตัดช่วงที่สามเป็นต้นไป ช่วงซ้ำจากผลเดียวกันแสดงครั้งเดียว; ผลต่างของช่วงซ้ำที่ขัดกันไม่รวมเป็นสรุป
- เรียงเก่าสุดก่อน แสดงยอดรวมและจำนวนของทุกช่วงคนละบรรทัด แล้วแสดงผลต่างเทียบกับช่วงก่อนหน้าที่อยู่ติดกันในสรุป คำนวณเปอร์เซ็นต์ `(ยอดหลัง − ยอดก่อน) / |ยอดก่อน| × 100` ในโค้ด ปัดหนึ่งตำแหน่ง ถ้ายอดก่อนเป็นศูนย์ไม่แสดงเปอร์เซ็นต์
- เพิ่มขึ้นตั้งแต่ 100% และยอดก่อนเป็นบวก แสดงทั้งเปอร์เซ็นต์และจำนวนเท่า `ยอดหลัง / ยอดก่อน` ปัดหนึ่งตำแหน่ง; ต่ำกว่า 100% แสดงเฉพาะเปอร์เซ็นต์; ลดลงไม่แสดงจำนวนเท่า; ยอดเท่ากันระบุว่าเท่ากับช่วงก่อน
- หัวเรื่องระบุช่วงที่อ่านจริง ไม่ใช้คำว่า “ช่วง” นำหน้าชื่อเดือน รายเดือนเต็มใช้ชื่อเดือน; ช่วงไม่เต็มเดือนคงวันที่จริง; มีทั้งเดือนเต็มกับช่วงไม่ครบเดือนให้ระบุข้อจำกัดในหนึ่งบรรทัด ปีในแต่ละบรรทัดไม่กำกวมเมื่อข้ามปี ภาษาอังกฤษใช้โครงสร้างเดียวกัน
- `expense.get_breakdown` คงผลต่างกลุ่มที่ทั้งสองช่วงอ่านได้ (สูงสุด 8 กลุ่มต่อคู่) และอันดับสูงสุด 3 กลุ่มของแต่ละช่วงต่อคู่; ไม่สมมติกลุ่มที่ขาดเป็นศูนย์ ขอบเขตเฉพาะรายการของผู้ใช้ยังต้องบอกตามผลอ่านจริง
- คนละ tool, คนละตัวกรอง/ฐาน/สิทธิ์/กลุ่ม, ช่วงทับกัน, หลายผลคนละด้านในคำขอเดียว, ผลอ่านไม่ครบ/ล้มเหลว/ไม่มีสิทธิ์, สกุลเงินปะปนหรือยอดที่ไม่ใช่เงินบาท: ไม่ฝืนรวมเป็นสรุปเปรียบเทียบ ใช้คำตอบแยกตามแหล่งข้อมูลของแต่ละข้อ; ผลล้มเหลวหรือไม่มีสิทธิ์ระบุเดือนที่อ่านไม่ได้โดยไม่แสดงตัวเลข; ผลรวมไม่ครบระบุว่าไม่สรุปยอด ห้ามแทนด้วยศูนย์หรือยอดบางส่วน
- ข้อเท็จจริงสำหรับ grounding ใช้การคำนวณชุดเดียวกับข้อความสรุป รวมจำนวนเท่า ผลต่าง เปอร์เซ็นต์ และอันดับ ข้ออื่นใน turn ตอบตามเดิม แม้โมเดลแต่งคำตอบข้ออื่นก็เปลี่ยนหรือทิ้งตัวเลขในสรุปไม่ได้

ตัวอย่างข้อมูล ก.ค. 25,147.80 → ส.ค. 214,899.57 → ก.ย. 98,000.00 บาท:

```text
เปรียบเทียบค่าใช้จ่าย ก.ค. – ก.ย. 2569
• ก.ค. 2569: 25,147.80 บาท (7 รายการ)
• ส.ค. 2569: 214,899.57 บาท (25 รายการ)
• ก.ย. 2569: 98,000.00 บาท (12 รายการ)
ส.ค. มากกว่า ก.ค. 189,751.77 บาท
ก.ย. น้อยกว่า ส.ค. 116,899.57 บาท
```

**แก้ไขรอบเย็น 2026-10-05 (เจ้าของดูคำตอบจริงบน LINE UAT: "เอา % ออกเถอะ งง ไม่สวยด้วย", "อันดับ 1 อะไรไม่ต้อง บอกประมาณว่า เดือนไหนเทียบกับเดือนไหน อะไรมากกว่า น้อยกว่าเท่าไหร่ แล้วสรุปค่าใช้จ่ายที่น่าสนใจว่าเป็นค่าอะไร") — ข้อนี้แทนที่กติกาเรื่องเปอร์เซ็นต์ จำนวนเท่า ผลต่างรายกลุ่ม และอันดับ ในรายการด้านบน:**

- คำตอบมีสามส่วนเท่านั้น: ยอดรวมและจำนวนรายการของทุกช่วง, ประโยคเทียบช่วงหลังกับช่วงก่อนหน้าที่อยู่ติดกัน ("ส.ค. มากกว่า ก.ค. 189,751.77 บาท", ยอดเท่ากันใช้ "เท่ากับ"), และเมื่ออ่านแบบแยกกลุ่ม (`expense.get_breakdown`) หัวข้อ "ค่าใช้จ่ายที่น่าสนใจ" บอกกลุ่มที่แต่ละช่วงจ่ายมากที่สุดช่วงละหนึ่งบรรทัด ("ส.ค. จ่ายมากที่สุด: ไม่ระบุหมวด 9,884.00 บาท") โดยดูจากทุกกลุ่มที่ tool คืนของช่วงนั้น ช่วงที่ไม่มีกลุ่มไม่มีบรรทัด
- ไม่แสดงเปอร์เซ็นต์และจำนวนเท่า เว้นแต่ผู้ใช้ถามถึงเอง (ข้อความมี "เปอร์เซ็นต์", "%", "กี่เท่า" หรือ percent) จึงต่อท้ายประโยคเทียบด้วยวงเล็บแบบเดิม "(เพิ่มขึ้น 754.5% หรือราว 8.5 เท่าของ ก.ค.)"
- ไม่มีบรรทัด "อันดับ" และไม่มีตารางผลต่างของทุกกลุ่มอีกต่อไป ข้อเท็จจริงสำหรับ grounding (ผลต่าง เปอร์เซ็นต์ จำนวนเท่า ผลต่างรายกลุ่ม) ยังคำนวณชุดเดิมให้ข้ออื่นใน turn อ้างได้
- เมื่อทั้ง turn คือการเปรียบเทียบชุดเดียว คำตอบเป็นการ์ดแบบแถวของดีไซน์ที่ล็อกไว้ (หัว "เปรียบเทียบค่าใช้จ่าย" กับช่วงที่อ่าน): แถวละช่วง (ยอดอย่างเดียว เพราะยอดที่มีจำนวนรายการต่อท้ายจะตกบรรทัดในแถว), แถวละคู่เทียบ ("ส.ค. มากกว่า ก.ค. : 189,751.77 บาท"), แถวละช่วงสำหรับกลุ่มที่จ่ายมากที่สุด; หมายเหตุคือประโยคช่วงไม่ครบเดือนและขอบเขตข้อมูล เกิน 16 แถว (ตั้งแต่ 6 ช่วงแบบแยกกลุ่ม) หรือชื่อยาวเกินแถว การ์ดเป็นข้อความแทนโดยไม่ตัดอะไร ภาษาอังกฤษไม่มีการ์ดแบบแถว

**ถอนออกแล้ว 2026-10-05 22:50 — หัวข้อ "อ่านคำถามเปรียบเทียบที่ชัดเจนโดยไม่เรียกโมเดล" ด้านล่างนี้ไม่ได้ใช้งาน:** เส้นทางนี้ route ได้ถูกต้องใน 3–7 ms แต่ API ไปต่อไม่ได้ เพราะ budget authority ยอมลดขอบเขต grant (`narrow`) เฉพาะหลังขั้น intake ใช้ model call ไปแล้วหนึ่งครั้ง (`nextOrdinal` ต้องเป็น 1 หรือ 2) ทุก turn จึงจบด้วย `AI_BUDGET_UNAVAILABLE` ("ยังตรวจสอบเครดิต AI ของร้านไม่ได้") — เห็นบน LINE UAT 22:33 และ 22:35 หลังขึ้นได้ 80 นาทีโดยไม่มีใครลองถาม เส้นทางตอบช่วงเวลาอย่างเดียวของรอบ 2b สร้างแบบเดียวกันและถูกถอนพร้อมกัน ทุกข้อความกลับไปให้โมเดล route ตามเดิม ชุดทดสอบของเส้นทางนี้เรียก router โดยตรงและไม่เคยผ่าน authority จริง บรรทัดจับเวลาและการจำคำตอบ runtime พร้อม (ด้านล่าง) ยังอยู่ การนำกลับมาต้องแก้สัญญา budget ก่อน ซึ่งเป็นการตัดสินใจของเจ้าของ

**อ่านคำถามเปรียบเทียบที่ชัดเจนโดยไม่เรียกโมเดล (2026-10-05 รอบค่ำ; เจ้าของบน LINE UAT: "เปรียบเทียบค่าใช้จ่าย อ่านช้ามาก")** — วัดจากรอบจริง 20:36: ทั้ง turn 11.1 วินาที เป็นขั้น router เรียกโมเดล 4.6 วินาที ทั้งที่ตัวอ่านช่วงเวลาอ่านประโยคได้ครบแล้ว

- ข้อความที่มี **เฉพาะ** คำกริยาเปรียบเทียบ (เทียบ/เปรียบเทียบ/compare), คำว่า ค่าใช้จ่าย/รายจ่าย/expenses, ช่วงเวลา 2–8 ช่วงที่ตัวอ่านช่วงเวลาอ่านได้ ไม่กำกวม และไม่ทับกัน กับคำเชื่อม/คำสุภาพในรายการปิด (`COMPARISON_WORDS`) ถูก route เป็น `BUSINESS_READ_QUESTION` ทันที: หนึ่งคำขออ่านต่อช่วง เรียงเก่าสุดก่อน, `toolHint` = `expense.get_breakdown`, ตัวกรองมีแต่วันเริ่มและวันสิ้นสุด — รูปเดียวกับที่โมเดลเคยตอบ จึงใช้เส้นทางเดิมทั้งหมดหลังจากนั้น (planner ถูกข้ามด้วย hint, คำตอบคือสรุปเปรียบเทียบข้างบน)
- มีคำอื่นแม้คำเดียว (ชื่อร้าน/หมวด, "แยกตาม…", "ทำไม", "กี่เปอร์เซ็นต์", จำนวนเงิน, "ถึง" ซึ่งเป็นช่วงเดียว), มีคำถามค้างในแชต, มีไฟล์แนบ, เป็นหลายข้อความที่ส่งติดกัน, เหลือช่วงเดียว หรือ tool นี้ไม่ได้ถูกเสนอให้ผู้ใช้คนนี้ (สิทธิ์/แพ็กเกจ) → ส่งให้โมเดลอ่านตามเดิม
- ไม่ได้ตัดสินสิทธิ์: tool ต้องอยู่ในชุดที่ API เสนอให้ผู้ใช้คนนี้ และ API ตรวจสิทธิ์อีกครั้งตอน tool ทำงาน ไม่มีการเรียกโมเดลจึงไม่มีค่า AI ของขั้นนี้
- เพิ่มบรรทัดจับเวลา (มีแต่ตัวเลข ไม่มีข้อความผู้ใช้): API `line.ai.intake_timing` (`grantMs`, `contextMs`, `categoriesMs`, `gatewayMs`) และ gateway `LINE intake routed` มี `routeMs`, `handlerMs` เพื่อหาเวลาราว 2 วินาทีก่อนเรียกโมเดลที่ยังไม่รู้ที่มา

**จำคำตอบ "runtime พร้อม" ไว้ชั่วคราว (2026-10-05 22:00)** — บรรทัดจับเวลาใหม่ของรอบแรกบน UAT (21:57) บอกว่าขั้น route ใช้ `grantMs` 1,505 ms ก่อนเรียกโมเดล: ทุกข้อความ API ขอ `/internal/ai/line-reliability-capabilities` และ gateway ตอบโดย **invoke AgentCore runtime หนึ่งรอบ** (capability probe) เพื่อยืนยันเวอร์ชันสัญญาและ identity ของ artifact

- คำตอบ "พร้อม" เป็นข้อเท็จจริงของ artifact หลัง qualifier ที่ process นี้ถูก pin ไว้ ซึ่ง release ไม่เปลี่ยนใต้ process ที่ยังให้บริการ (release ถัดไป pin process ใหม่ไปอีก qualifier) และทุก invoke จริงยังตรวจ identity ของ runtime เองแบบ fail closed อยู่แล้ว gateway process จึงจำคำตอบ **ใช่** ไว้ 5 นาที (`BUDGET_V2_CAPABILITY_TTL_MS`)
- คำตอบ **ไม่** หรือ probe ที่ล้มเหลว ไม่ถูกจำ: ข้อความถัดไปถามใหม่ทันที จึงกลับมาใช้งานได้ทันทีที่ runtime พร้อม
- ผลที่ยอมรับ: ถ้า runtime เสียภายใน 5 นาทีหลังตอบว่าพร้อม turn จะล้มเหลวที่ invoke จริงแทนที่จะถูกปฏิเสธตั้งแต่ขั้นออก grant ซึ่งเป็นผลเดียวกับ runtime เสียหลัง probe ผ่านในแบบเดิม

## 7. ตัวเลขตั้งต้นของร้านทดลอง (owner decision 6)

- เครดิต AI ส่วนแชต: **80 บาท/เดือน**
- เครดิตสำหรับการอ่านเอกสาร: **15 ใบ/เดือน** (จำนวนใบ = โควตาใบเสร็จของแพ็กเกจทดลองที่มีอยู่แล้ว) — เพดานเงินส่วน OCR เป็น guard ภายในที่ต้อง **ไม่** สะดุดก่อนจำนวนใบ: 15 ใบ × p90 ≈ 3.05 บาท (ก่อนงาน C; หลังงาน C ≈ 2.8) × เผื่ออ่านซ้ำ/หลายหน้า 1.3 ≈ **60 บาท**
- เพดานรวม (T) = 80 + 60 = **140 บาท/เดือน**
- การนำไปใช้: ตั้งต่อบริษัทได้ที่หน้าแอดมินหลัง deploy (flag เปิดแล้วตาม PR #622/#623); ค่า default ต่อแพ็กเกจ (ทดลอง/Starter/Basic/Pro) ยังไม่มี — เป็นส่วนหนึ่งของ concept เครดิต (owner decision 3) ไม่ใช่ spec นี้
- ห้าม auto-allocate ให้บริษัทจริงจาก spec นี้; การตั้งค่าจริงเป็นการกระทำของแอดมินและต้องมี reason/audit เดิม
