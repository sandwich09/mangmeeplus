### Byte integrity and failure handling

**Owner decision, 2026-11-07: keep every original file** ("เก็บครบทุกไฟล์"). The owner was shown the part cost: a 300-expense month is about 15–16 parts with originals plus packets, against about 10 today and about 5 with originals kept only when a packet cannot hold them. Every original stays in its folder; the packets are additional copies.

Keep originals byte-for-byte in today's six folders, and add `ใบเบิก/` and `ชุดเอกสารรายการ/`. Deduplicate by source attachment/document version within a packet and by claim ID for the standalone claim file. Preserve existing public-name collision suffixes (`expense-evidence.use-case.ts:537-540`). Current substitute copies are used in packets. Historical copies retain the existing folder and supersession references (`:611-619`).

The proposed `appendRecordFile` must inspect PDF structure before copying pages. A signature field/dictionary, `/ByteRange`, document permission signature, byte-bound embedded payload or unresolved integrity state makes the file original-only. Parse errors, encryption and unsupported structures also take the reference path. Do not use filename, MIME or a raw byte search as proof that a PDF is unsigned. No signature verification claim is made. Detection and conservative fallback are engineering gates to prove with real signed and malformed fixtures. There is no existing protected-PDF classification in the opened bundle/renderer paths.

For a byte-sensitive original, add `เปิดไฟล์ต้นฉบับเพื่อคงลายเซ็นอิเล็กทรอนิกส์` only when signature evidence exists. For an uncertain file use `ไฟล์นี้แยกไว้ในโฟลเดอร์ต้นฉบับ`. The packet reference includes its relative path and part. A file successfully preserved separately is an intentional reference, with a reason in the appendix and file index. An original that cannot be read or included produces a follow-up problem as well. These cases must stay distinguishable.

If one appendix fails, retain the packet and mark that appendix unavailable. If the packet itself cannot be constructed, retain originals and expose a skipped packet entry. Convert `addDocument`'s current silent Forbidden/NotFound return (`expense-evidence.use-case.ts:570-572`) into a safe status result for an already-visible selected record. Denied aggregate documents expose only a generic reason on that record. They never expose an unselected document number, filename, line, amount or signature. Reuse existing safe failure labels at `:648-654`.

### Limits and performance envelope

`EVIDENCE_BUNDLE_MAX_FILES` is 60 and `EVIDENCE_BUNDLE_MAX_BYTES` is 60,000,000 file bytes. A single oversized file currently travels alone (`expense-evidence.use-case.ts:30-32`, `:603-609`). Retain that meaning, including workbook/text overhead outside the file-byte count. Every new claim and packet counts as a file. Never divide a filing packet across PDFs to meet a part boundary.

Measure generated documents sequentially, discard each measured buffer, and keep only metadata/loaders during planning, matching `addDocument` at `expense-evidence.use-case.ts:567-581`. During download hold one destination packet and one current source at a time, then release their PDF/raster objects. Current ZIP generation retains a single part's entries and allocates the final ZIP buffer (`:638-660`, `apps/api/src/common/export/xlsx.logic.ts:77-120`). The rule therefore means one document under construction plus one bounded part, rather than constant memory independent of part bytes. Apply existing PDF/page/raster safety bounds to pathological inputs and reference excess appendices with reasons instead of producing an unreadable or unbounded packet.

The expected ordinary fixture is 300 direct-paid expenses, each with a 500 KB receipt, 250 KB proof and an assembled PDF at most 750 KB. That is 900 counted files and about 450 MB, hence 15 parts when no consecutive 60-file block exceeds 60 MB. Thirty readable claims averaging 250 KB add 30 standalone files and their repeated packet pages. With packets still at most 750 KB this is 930 files, about 457.5 MB and 16 parts. Actual sizes determine the real count. Large vouchers and originals can change it.

Proposed acceptance budgets on the controller's local production-equivalent runtime are a plan at most 30 seconds, each ordinary part at most 30 seconds, and all 16 parts sequentially at most 8.5 minutes. Expected incremental peak RSS is at most 256 MiB above a warmed idle API worker, including the part and one ordinary packet. These are unmeasured budgets. Record machine/resources, cold/warm timings, largest packet and measured RSS. `bundleContents` rerenders generated files when planning every download today (`:629-645`), so repeated sizing can dominate. Avoid rendering packets for standalone XLSX. Failure of these budgets blocks acceptance and requires a scoped follow-up design. It does not justify a new job, cache, dependency, switch or stored export marker in this round.

## 12. Owner question and controller gates

**Q1 — multi-line signed claim with a partial expense selection. Decided by the controller, 2026-11-07.** The export includes the complete signed claim only when every expense it represents is selected and loaded. Otherwise each affected selected record carries `ใบเบิกรวมรายการนอกชุดที่เลือก จึงไม่ได้รวมใบนี้`. This is the same rule the owner accepted for co-vouchers (RC-F2), so no unselected line, amount or signature leaves the shop.
