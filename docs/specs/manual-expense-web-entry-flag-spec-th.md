## 1. Product decision และข้อตัดสินใจ D1–D8

### 1.1 สิ่งที่เจ้าของตัดสินแล้ว (2026-10-01)

Owner ยืนยัน “ปิดแค่ทางเข้าการ manual บน web”, “ยังไม่แก้นะ ทำ spec มาก่อน” และ **“เอา flag ย่อย ภายใต้ feature บันทึกด้วยมือ ซ่อน ทางเข้า menu นี้ไป เปิดปิดได้ เบื้องหลังทำงานเหมือนเดิม”**

จากคำตัดสินนี้ สิ่งที่ตายตัวแล้วคือ

1. ผู้ดูแลระบบเห็นสวิตช์ย่อยใต้ฟีเจอร์ “บันทึกด้วยมือ” ในหน้าแพ็กเกจและฟีเจอร์ของร้าน เปิดและปิดได้
2. ปิดแล้วเมนู ปุ่ม และลิงก์ที่พาไปหน้าบันทึกด้วยมือบนเว็บหายไป ไม่ครอบการกรอกด้วยมือภายใน OCR และ wizard ใบรับรองแทนใบเสร็จ
3. เบื้องหลังเหมือนเดิม: ไม่เปลี่ยน guard ของ POST/PATCH/DELETE, สิทธิ์ของบทบาท, LINE, OCR, wizard, การเบิกจ่าย หรือพฤติกรรมด้านเงิน
4. `expenses.manual` คง `permissionKeys: ['expense.create', 'expense.update']` และความหมายเดิมทุกประการ ร้านที่ปิด `expenses.manual` อยู่ยังถูกตัดสิทธิ์ตามเดิม ไม่มีการคืนสิทธิ์อัตโนมัติ

### 1.2 ข้อตัดสินใจ D1–D8 — ตัดสินแล้ว 2 ต.ค. 2569 (เจ้าของ: ตามที่แนะนำ)

เมื่อ 2 ต.ค. 2569 เจ้าของตอบคำถามแปดข้อจาก[รีวิวอิสระ](../research/manual-expense-web-entry-flag-review-2026-10-01-th.md)ว่า “ตามที่แนะนำทั้งหมด” เอกสารฉบับนี้เขียนตามคำตอบที่แนะนำอยู่แล้ว ทุกจุดที่ใช้คำตอบมีป้าย **(ตัดสินแล้ว 2 ต.ค. 2569 (เจ้าของ: ตามที่แนะนำ) — Dn)** ทางเลือกที่ไม่ได้เลือกและต้นทุนของแต่ละข้อเก็บไว้ในตารางเป็นบันทึก และคอลัมน์สุดท้ายบอกหัวข้อที่ใช้คำตอบนั้น

**เจ้าของเปลี่ยนครึ่งแรกของ D2 ในวันเดียวกัน (2 ต.ค. 2569 เวลาประมาณ 23:08):** “สวิตช์ซ่อนเมนู ให้เป็น default ปิดไปเลยนะ” ผู้ควบคุมงานอ่านคำสั่งนี้ว่า เมนูบันทึกด้วยมือ**ไม่แสดงเป็นค่าเริ่มต้น** ร้านที่ไม่มีแถวค่าตั้งอ่านได้ว่าไม่แสดง ทั้งร้านที่มีอยู่วันนี้และร้านใหม่ และผู้ดูแลระบบเปิดให้ทีละร้าน **เจ้าของยืนยันการอ่านนี้เมื่อ 3 ต.ค. 2569:** “ปิดเป็นค่าเริ่มต้นทุกร้าน รวมร้านเก่าด้วย” ทางเลือกที่ให้ร้านเดิมคงเมนูไว้จึงไม่เอา ครึ่งหลังของ D2 คงเดิม: การซื้อ อัปเกรด ดีล และชุดสำเร็จรูปไม่อ่านและไม่เขียนค่านี้

## 2. Goal, ผู้ใช้ และ acceptance outcome

จุดประสงค์ **(ตัดสินแล้ว 2 ต.ค. 2569 (เจ้าของ: ตามที่แนะนำ) — D3 และ D2 ฉบับที่เจ้าของเปลี่ยน)**: เมนูบันทึกด้วยมือไม่แสดงเป็นค่าเริ่มต้น เพื่อให้หน้าจอของพนักงานพาไปที่การอัปโหลดใบเสร็จเป็นหลัก และผู้ดูแลระบบเปิดเมนูนี้ให้ร้านที่ต้องการได้ทีละร้าน สวิตช์นี้ **ไม่ใช่การห้าม** และ **ไม่ใช่ขอบเขตความปลอดภัย** ผู้มี `expense.create` ยังสร้างรายจ่ายได้ผ่าน API, wizard ใบรับรองแทนใบเสร็จ และ LINE ตามสิทธิ์เดิม

| --- | --- |

## 5. Data model และ permission contract

### 5.1 ที่เก็บ **(ตัดสินแล้ว 2 ต.ค. 2569 (เจ้าของ: ตามที่แนะนำ) — D1 และ D2 ฉบับที่เจ้าของเปลี่ยน)**

สวิตช์นี้ **ไม่ใช่ entitlement key** ไม่เพิ่มอะไรใน `FEATURE_CATALOG`, `ALL_FEATURE_ENTITLEMENT_KEYS`, `MENU_ENTITLEMENT_BINDINGS`, `STARTER_FEATURE_KEYS`, `TIER_FEATURE_PRESETS` หรือ `SALES_DEAL_ALLOWED_FEATURE_KEYS` และไม่เขียนแถวใน `CompanyFeatureEntitlement`

- เก็บเป็นค่าตั้งรายร้านแบบเดียวกับ `CompanyAiConfiguration.ocrEnabled` คือ boolean มี version ของตัวเองสำหรับ CAS และแถวถูกสร้างเมื่อผู้ดูแลเปลี่ยนค่าครั้งแรกเท่านั้น (หรือเมื่อ seed ของร้านตัวอย่างเขียนให้)
- รูปที่สร้าง: model `CompanyWebEntrySetting` มี `companyId` (unique, ลบตามบริษัท), `manualExpenseEntryEnabled Boolean` (**ไม่มีค่าเริ่มต้นในฐานข้อมูล** แถวทุกแถวบอกค่าของตัวเองเสมอ จึงเก็บได้ทั้ง “แสดง” และ “ไม่แสดง”), `version Int @default(0)`, `updatedBySystemAdminUserId`, `createdAt`, `updatedAt`
- **ไม่มีแถว = ไม่แสดงเมนู** (เจ้าของสั่ง 2 ต.ค. 2569) ร้านเดิมทุกร้านและร้านใหม่จึงไม่เห็นเมนูจนกว่าผู้ดูแลระบบจะเปิดให้ร้านนั้น ไม่มี backfill และร้านใหม่ไม่ต้องมีขั้นตอนใดใน onboarding
- **ความหมายของ “ไม่มีแถว” ตัดสินที่จุดเดียวฝั่ง API** คือค่าคงที่ `MANUAL_EXPENSE_WEB_ENTRY_WITHOUT_ROW` กับฟังก์ชัน `manualExpenseWebEntryState` ใน `apps/api/src/modules/system-partner-management/domain/logic/manual-expense-web-entry.logic.ts` ทั้ง `/auth/me` รายละเอียดร้าน และ command อ่านผ่านฟังก์ชันนี้ ถ้าวันหน้าต้องเปลี่ยนค่าเริ่มต้น ให้แก้บรรทัดนี้กับ test ที่ตรึงค่าไว้ ห้ามเขียนค่าเริ่มต้นซ้ำที่อื่น
- ทางเลือกที่**เจ้าของไม่เอา** (ยืนยัน 3 ต.ค. 2569: “ปิดเป็นค่าเริ่มต้นทุกร้าน รวมร้านเก่าด้วย”) และไม่ได้สร้าง: ร้านที่มีอยู่ ณ วันปล่อยได้แถว “แสดง” ครั้งเดียว ส่วนร้านใหม่เริ่มที่ไม่แสดง
- migration แบบ additive หนึ่งรายการ `20261002230000_company_web_entry_setting` (สร้างตารางใหม่พร้อม unique index และ foreign key ของตารางนั้นเอง ไม่แตะตารางเดิม ไม่มีการย้ายข้อมูล) จึงต้องปล่อยผ่านเส้นทาง release ปกติที่รองรับ migration ตาม [deployment protocol](../runbooks/uat-production-v2-deployment.md)
- ไม่เพิ่ม environment switch, SKU, permission หรือ pack

### 5.2 Authority invariance

ห้ามแก้ `expenses.manual.permissionKeys`, `pack.expense.self`, HTTP expense guards, `SetPartnerFeaturesUseCase`, `evaluateEntitledFeatureKeys`, `filterPermissionsByEntitlement` หรือ source-state conditions ในงานนี้ ค่าตั้งใหม่ถูกอ่านเพียงสามจุด คือ `GET /v1/auth/me`, `GET` รายละเอียดร้านของผู้ดูแล และ command ใน §5.3 ไม่มี guard, use case, repository, LINE tool หรือ billing ใดอ่านค่านี้

เมื่อ roles, scopes และสิทธิ์แพ็กเกจเท่าเดิม ต้องได้

```text
permissions(แสดง) == permissions(ซ่อน) == permissions(แสดงอีกครั้ง)
entitledFeatureKeys(แสดง) == entitledFeatureKeys(ซ่อน)
CompanyEntitlementSet.setVersion ไม่เปลี่ยนเมื่อสลับค่าตั้งนี้
```

ต้องเทียบ permission ทั้งชุดของทุกบทบาทใน `ROLE_GRANTS` และทุกเทมเพลตใน `ROLE_TEMPLATES` ไม่ใช่ดูแค่ `expense.create`

### 5.3 Command ของผู้ดูแล

ใช้รูปแบบเดียวกับ `SetPartnerOcrConfigUseCase` (`apps/api/src/modules/system-partner-management/application/use-cases/set-partner-ocr-config.use-case.ts`)

- endpoint `PUT /v1/system/partners/:partnerCompanyId/manual-expense-web-entry` guard ด้วย `system.partner_feature.manage` ซึ่งเป็นสิทธิ์เดียวกับการแก้ฟีเจอร์ของร้าน ไม่เพิ่ม permission
- body เป็นค่าที่ต้องการแบบสัมบูรณ์: `enabled` และ `expectedVersion` ไม่บังคับกรอกเหตุผล (ต่างจาก OCR config) เพราะไม่ใช่การปรับโควตาหรือสิทธิ์ และหน้าจอมีขั้นยืนยันก่อนซ่อนอยู่แล้ว
- ค่าที่ขอเท่ากับค่าปัจจุบัน: คืนค่าปัจจุบัน ไม่เขียน ไม่ audit ไม่เพิ่ม version การกดซ้ำหรือ retry หลัง response หายจึงปลอดภัย
- ค่าต่างและ `expectedVersion` ไม่ตรง: 409 รหัส `manual_expense_web_entry_version_conflict` หน้าผู้ดูแลแสดงข้อความใน §8 แล้วโหลดรายละเอียดร้านใหม่ให้
- ร้านสถานะ `DISABLED` หรือ `ARCHIVED`: ปฏิเสธด้วยกติกา `partnerMetadataLockError` เดิม
- ทำใน transaction เดียวกับ audit โดยล็อกแถวบริษัทก่อนอ่าน (ตัวเดียวกับที่ lifecycle ของบริษัทใช้ จึงเรียงลำดับผู้ดูแลสองคนที่กดพร้อมกันได้) ไม่เรียก `invalidateLineConversationState` ไม่สร้าง `EntitlementTransition`, `RunoffSnapshot` หรือ `EntitlementCommand` และไม่แตะ `CompanyEntitlementSet`
- `GET` รายละเอียดร้านคืนค่าปัจจุบันและ version เสมอ (`manualExpenseWebEntry: { enabled, version }`) รวมร้านที่ยังไม่มีแถว (ค่า = ไม่แสดง, version = 0) และร้านที่ชุดสิทธิ์ยังรอการเตรียม

## 6. Session contract: API → web

### 6.1 ค่าเดียว **(ตัดสินแล้ว 2 ต.ค. 2569 (เจ้าของ: ตามที่แนะนำ) — D5)**

`GET /v1/auth/me` เพิ่ม field เดียวแบบ additive ที่ server คำนวณ: `manualExpenseWebEntry: boolean` (true เมื่อร้านมีแถวที่ระบุว่าแสดง, false เมื่อแถวระบุว่าไม่แสดงหรือ**ร้านไม่มีแถว** ตามจุดตัดสินเดียวใน §5.1) อ่านใน `auth.controller.ts` พร้อมข้อมูลอื่นของ response เดิม ไม่ผ่าน `ResolvedAccess`, `RequestContext` หรือ resolver เพื่อไม่ให้ค่านี้ไปถึง LINE หรือ fingerprint ของ LINE

```json
{
  "companyId": "company-A",
  "permissions": ["expense.create", "expense.update", "expense.receipt.upload"],
  "manualExpenseWebEntry": false
}
```

เว็บไม่รับรายการ feature ทั้งชุด เพราะเมื่อ `expenses` หรือ `expenses.manual` ปิด `expense.create` ถูกตัดอยู่แล้ว ข้อมูลที่เว็บต้องรู้เพิ่มจึงมีเพียงค่านี้ ตัวอย่างข้างบนคือร้านที่ยังไม่ได้เปิดเมนู

| ค่าที่เว็บได้รับ | ความหมาย |
| --- | --- |
| `true` | แสดงทางเข้าตามสิทธิ์ |
| `false` | ร้านไม่แสดงเมนู (ค่าเริ่มต้น หรือผู้ดูแลปิด) |
| field หายหรืออ่านไม่ได้ | ถือว่าแสดง: ความขัดข้องชั่วคราวหรือ API รุ่นเก่าต้องไม่เอาหน้านี้ไปจากร้านที่ผู้ดูแลเปิดให้แล้ว และ API เป็นผู้ตัดสินสิทธิ์จริงอยู่แล้ว (เหตุผลเดิม “เพราะค่าเริ่มต้นคือแสดง” ไม่จริงแล้ว) ผลที่ยอมรับ: ระหว่างที่ field หาย ร้านที่ยังไม่ได้เปิดก็เห็นทางเข้าด้วย |

ห้ามให้ browser ส่งค่านี้กลับมาเพื่อเปลี่ยนสิทธิ์ และไม่เก็บใน localStorage หรือ JWT

### 6.2 Predicate เดียวสำหรับทางเข้า

เพิ่ม helper เล็กใน web expense feature (ชื่อเสนอ `manual-expense-entry.logic.ts`) ใช้ร่วมกันทุกจุดใน §9

```text
canOpenManualWeb = session เป็นของบริษัทที่เปิดอยู่
  AND permissions มี expense.create
  AND manualExpenseWebEntry !== false
```

ไม่เปลี่ยนความหมาย `expenseCapabilities.canCreate` เพราะ wizard และ flow อื่นยังต้องใช้ authority เดิม ให้ส่งผลของ predicate แยกจาก capabilities

### 6.3 Revalidation และ company switching

- เพิ่มเฉพาะ boolean นี้ใน `accessContextFingerprint` ไม่ใส่รายการ feature เพื่อไม่ให้การเปลี่ยนสิทธิ์ที่ไม่เกี่ยวสั่ง `router.refresh()` ทุกแท็บของร้าน
- ใช้ focus/visibility/`ACCESS_CONTEXT_STALE_EVENT`/poll **60 วินาที** เดิม ไม่เพิ่ม timer หรือ websocket
- การเปลี่ยนค่านี้ต้องอัปเดตเมนูแม้ permission array ไม่เปลี่ยน และต้องไม่ทำให้ใครหลุดจากระบบ
- ไม่มีคำรับรองว่าสลับแล้วเปลี่ยนทุกแท็บทันที ทั้งตอนเปิดและตอนปิด: หน้าที่โหลดใหม่ใช้ค่าล่าสุด แท็บที่เปิดอยู่ปรับเมื่อ revalidate สำเร็จ แท็บที่ซ่อนอยู่ปรับเมื่อกลับมาแสดง
- company switch เป็นการเปลี่ยน route จึงประเมินใหม่เสมอ ห้ามนำค่าของบริษัท A ไปใช้กับบริษัท B

## 7. Admission ของหน้า manual และการรักษางานค้าง

### 7.1 Admission คืออะไร และอยู่ที่ไหน

Admission คือการตัดสินว่า “หน้านี้เปิดฟอร์มให้หรือไม่” ในเบราว์เซอร์ **เป็นสถานะหน้าจอ ไม่ใช่การปฏิเสธของ server และไม่ใช่ขอบเขตความปลอดภัย**

- server route `/expenses/manual` โหลด session ด้วย `fetchServerSession` แบบ no-store เดิม แล้ว **render gate และฟอร์มเสมอ** โดยส่งผลของ `canOpenManualWeb` เป็น prop server ไม่ตอบ 403 และไม่ redirect เพราะค่านี้
- gate อยู่ในหน้าฝั่ง client ของแท็บบันทึกด้วยมือ และครอบเฉพาะส่วนฟอร์มของแท็บนั้น (ช่องเลือกสาขากับ `ManualExpensePanel`) ไม่ครอบ module shell หรือแท็บอื่น ตัดสินจาก prop: เมื่อ prop เป็นแสดง ให้รับเข้า เปิดฟอร์ม และจำผลไว้ โดยไม่ถอนเมื่อ prop เปลี่ยนเป็นไม่แสดงภายหลัง เมื่อ prop เป็นไม่แสดงและยังไม่เคยรับเข้า ให้แสดงสถานะ “หน้าบันทึกด้วยมือไม่ได้เปิดใช้สำหรับร้านของคุณ” (§8) และถ้า prop เปลี่ยนเป็นแสดงระหว่างที่ผู้ใช้อยู่ในสถานะนั้น ให้รับเข้าได้โดยไม่ต้องโหลดหน้าใหม่ สถานะนี้แสดงนอกกรอบเลือกสาขาของฟอร์ม เพื่อไม่ให้ข้อความ “เลือกสาขาก่อน” ของฟอร์มไปขึ้นกับปุ่มของสถานะนี้
- ผลรับเข้าเก็บใน state ของ gate เท่านั้น ไม่เก็บลง storage, cookie หรือ server
- alias `/expenses?tab=manual`, deep link ผ่านหน้า login และลิงก์กลับจากหน้าตั้งค่ารหัสภาษี ลงที่ route เดียวกันจึงผ่าน gate เดียวกัน
- generic `canAccessWorkspacePath` เป็น permission gate ของโมดูลตามเดิม ห้ามใช้ค่านี้ปิด module shell หรือไล่ผู้ใช้ไป dashboard
- ไม่ต้องใส่ `prefetch={false}` ที่ลิงก์ เพราะหน้า dynamic ไม่ถูก prefetch เต็มอยู่แล้ว
- ข้อจำกัดที่ยอมรับ: การกด Back/Forward กลับมาหน้าที่เบราว์เซอร์จำไว้ก่อนผู้ดูแลปิดเมนู อาจยังเห็นฟอร์มจนกว่าจะโหลดหน้าใหม่ ไม่สร้างกลไกเพิ่มเพื่อปิดกรณีนี้ เพราะ API รับการบันทึกตามสิทธิ์เดิมอยู่แล้ว ถ้าภายหลังเปิดใช้ `cacheComponents` ของ Next ต้องทบทวนข้อนี้ใหม่

### 7.2 ฟอร์มที่เปิดอยู่แล้ว **(ตัดสินแล้ว 2 ต.ค. 2569 (เจ้าของ: ตามที่แนะนำ) — D6)**

- เมื่อ gate รับเข้าแล้ว การปิดเมนูภายหลังไม่ unmount ฟอร์ม ไม่เคลียร์ `items`, ค่าบริการ, ภาษี, ไฟล์ที่เลือก, `savedExpenseId` และไม่สร้าง idempotency key ใหม่ (state ของ `ManualExpensePanel` ใน `ExpensesPages.tsx`)
- ผู้ใช้บันทึกรายการที่กำลังกรอกได้ตาม API permission เดิม และแนบไฟล์หลังสร้างต่อได้
- แสดงข้อความ “หน้านี้ถูกปิดสำหรับร้านของคุณแล้ว คุณยังบันทึกรายการที่กำลังกรอกได้” เหนือฟอร์ม เฉพาะขณะที่ยังไม่ได้บันทึกรายการ (เมื่อรายการถูกบันทึกแล้วแต่แนบไฟล์ไม่สำเร็จ ไม่มีรายการที่กำลังกรอกเหลืออยู่ ข้อความนี้จึงไม่แสดง)
- เมื่อออกจากหน้า, โหลดหน้าใหม่, เปลี่ยนบริษัทหรือผู้ใช้ หรือเปิดแท็บใหม่ ต้องประเมินใหม่
- ข้อจำกัดที่ยอมรับ: ถ้าเบราว์เซอร์โหลดหน้าใหม่เอง (มือถือสลับแอป, LINE in-app browser) ถือเป็นการเข้าใหม่และไม่เปิดฟอร์มเมื่อร้านไม่แสดงเมนู ข้อมูลที่ยังไม่บันทึกหายตามพฤติกรรมเดิมของเบราว์เซอร์
- permission, company หรือ session ที่ถูกถอนจริงยังมีผลตามเดิม ห้ามใช้ admission ข้าม API authorization
- server ต้องไม่สลับ subtree ของหน้าเพราะค่านี้เปลี่ยน มิฉะนั้น `router.refresh()` จะทำให้ฟอร์มหายซ้ำอาการ F08
- ไม่เพิ่ม persistent draft store และไม่ส่งข้อมูลไป server อัตโนมัติ

Acceptance ต้องทดสอบ: ร้านที่ผู้ดูแลเปิดเมนูให้ → กรอกข้อมูลและเลือกไฟล์ → ผู้ดูแลปิดเมนูจากอีก session → focus/poll → ฟอร์มอยู่ → บันทึกครั้งเดียวสำเร็จ → โหลดหน้าใหม่แล้วไม่เปิดฟอร์ม

## 8. Admin UI และข้อความ

แสดงโครงสร้างดังนี้ในหน้าแพ็กเกจและฟีเจอร์ของร้าน โดยสวิตช์หลักคง label และความหมายเดิม

```text
ค่าใช้จ่ายและใบเสร็จ
  บันทึกด้วยมือ                         [สวิตช์เดิม อยู่ในชุดสิทธิ์]
    แสดงเมนูบันทึกด้วยมือบนเว็บ          [สวิตช์ใหม่ บันทึกแยก]
```

- สวิตช์ใหม่ **ไม่อยู่ในรายการเปลี่ยนแปลงของชุดสิทธิ์** ไม่ผ่านปุ่ม “ตรวจสอบและบันทึก”, ชุดสำเร็จรูป, เปิดปิดทั้งกลุ่ม หรือ `toggleSubmenu` การเปิด (ไม่แสดง → แสดง) บันทึกผ่าน command ใน §5.3 ทันที ไม่ต้องยืนยัน การปิด (แสดง → ไม่แสดง) บันทึกทันทีหลังยืนยัน
- ใช้ได้กับทุกร้านที่ใช้งานอยู่ รวมร้านเดิมที่ยังไม่มีแถว และร้านที่ชุดสิทธิ์ยังรอการเตรียม เพราะไม่ขึ้นกับชุดสิทธิ์ ปุ่มกาง “เมนูย่อย” ของการ์ดจึงกดได้เสมอ (เดิมกดไม่ได้ขณะที่สวิตช์ของชุดสิทธิ์ถูกล็อก ทำให้เข้าถึงแถวนี้ไม่ได้) ร้านที่ปิดใช้งานหรือเก็บถาวรสลับไม่ได้ตามกติกา `partnerMetadataLockError` เดิม และหน้าร้านมีแถบบอกเหตุผลอยู่แล้ว
- เมื่อ `expenses` หรือ `expenses.manual` ที่บันทึกแล้วของร้านปิดอยู่: สวิตช์กดไม่ได้ และสถานะข้างสวิตช์บอก**สิ่งที่ร้านเห็น**คือ “ไม่แสดง” (สวิตช์อยู่ตำแหน่งปิด) เพราะร้านไม่เห็นเมนูไม่ว่าค่าที่เก็บเป็นอะไร ไม่แก้ค่าที่เก็บ และค่าที่เก็บกลับมามีผลเมื่อฟีเจอร์เปิดอีกครั้ง บริษัทที่ปิดใช้งานหรือเก็บถาวรก็แสดงแบบเดียวกัน กติกานี้อ่านค่าที่**บันทึกแล้ว** ไม่ใช่ค่าที่ผู้ดูแลกดไว้แต่ยังไม่ได้บันทึก (แก้ 3 ต.ค. 2569: เดิมแสดงค่าที่เก็บ ซึ่งอาจขึ้นว่า “แสดง” ทั้งที่ร้านไม่เห็นเมนู)
- การบันทึกสวิตช์นี้ไม่ทำให้รายการเปลี่ยนแปลงของชุดสิทธิ์ที่ผู้ดูแลยังไม่ได้บันทึกหายไป: เมื่อบันทึกสำเร็จ หน้าเก็บค่าและ version ที่ command คืนมาโดยไม่โหลดรายละเอียดร้านใหม่ และเมื่อได้ 409 หน้าอ่านรายละเอียดร้านใหม่แล้วนำมาใช้เฉพาะค่าของสวิตช์นี้
- เมื่อการบันทึกล้มเหลวด้วยเหตุอื่น หน้าแสดงข้อความไทยกลางของระบบ สวิตช์คงค่าเดิมและกดได้อีก
- ไม่เพิ่ม navigation item, route หรือแถวเมนูใหม่ในรายการเมนูของร้าน

| ฟอร์มที่เปิดค้างหลังผู้ดูแลปิด | ฟอร์มที่รับเข้าแล้ว ร้านเปลี่ยนเป็นไม่แสดง และยังไม่ได้บันทึกรายการ | หน้านี้ถูกปิดสำหรับร้านของคุณแล้ว คุณยังบันทึกรายการที่กำลังกรอกได้ |
| หมายเหตุในคู่มือ | คู่มือค่าใช้จ่าย หัวข้อ “บันทึกด้วยมือ” ขณะร้านไม่แสดงเมนู (ประโยคแรกเป็นหัวเรื่องของกล่องหมายเหตุ ประโยคหลังเป็นบรรทัดใต้หัวเรื่อง เพื่อไม่ซ้ำชื่อหัวข้อที่อยู่เหนือกล่อง) | เมนูนี้ไม่ได้เปิดใช้สำหรับร้านของคุณ ขั้นตอนในหัวข้อนี้จึงยังใช้ไม่ได้ในขณะนี้ |

- เว็บรู้เพียงว่าร้าน “แสดง” หรือ “ไม่แสดง” (boolean ค่าเดียวใน §6.1) จึงแยกไม่ได้ว่าร้านไม่เคยเปิด หรือเคยเปิดแล้วถูกปิด ข้อความฝั่งพนักงานจึงต้องจริงทั้งสองกรณี และใช้คำว่า “ไม่ได้เปิดใช้” ไม่ใช่ “ยังไม่เปิดใช้”
- ร้านเปิดเมนูเองไม่ได้ มีเพียงผู้ดูแลระบบของแพลตฟอร์มที่เปิดได้ ข้อความฝั่งพนักงานจึงไม่บอกว่า “ร้านซ่อน” ผู้ที่เห็นบรรทัด “กรุณาติดต่อเจ้าของกิจการ” ขาดสิทธิ์อัปโหลดใบเสร็จและสิทธิ์ดูรายการ และมีเพียงเจ้าของกิจการที่ให้สิทธิ์ได้ทุกอย่าง จึงให้ติดต่อเจ้าของกิจการ ชื่อบทบาทมาจากรายการกลาง `THAI_SYSTEM_ROLE_NAMES` (“ผู้ดูแลร้าน” ไม่ใช่ชื่อบทบาทใดในระบบ แก้ 3 ต.ค. 2569) ส่วนผู้อ่านที่เป็นเจ้าของกิจการเองถือทุกสิทธิ์ที่แพ็กเกจให้อยู่แล้ว ประโยคนั้นจะส่งเขาไปหาตัวเอง และมีเพียงผู้ดูแลระบบของแพลตฟอร์มที่เปิดหน้านี้ให้ร้านได้ จึงได้ “กรุณาติดต่อทีมงานเพื่อเปิดหน้านี้ให้ร้านของคุณ” ซึ่งใช้คำว่า “ติดต่อทีมงาน” แบบเดียวกับข้อความเรื่องแพ็กเกจและเมนูที่ระบบใช้กับเจ้าของกิจการอยู่แล้ว
- สถานะที่พนักงานเห็นต้องไม่ใช้ข้อความ “ไม่มีสิทธิ์” เพราะไม่ใช่เรื่องสิทธิ์ และต้องไม่เสนอปุ่มที่ผู้ใช้เปิดไม่ได้
- ห้ามมีข้อความใดบอกว่าระบบหลังบ้านถูกปิด หรือบอกว่าพนักงานบันทึกด้วยมือไม่ได้
- Switch มี accessible name, focus และ aria-checked ปุ่มที่ถูกซ่อนไม่เหลือ keyboard focus target

### 9.3 คู่มือและคำตอบของผู้ช่วย **(ตัดสินแล้ว 2 ต.ค. 2569 (เจ้าของ: ตามที่แนะนำ) — D4)**

- คู่มือบนเว็บ: เมื่อร้านไม่แสดงเมนู ไม่แสดงปุ่ม “เปิดหน้าบันทึกด้วยมือ” และแสดงหมายเหตุตาม §8 ที่ต้นหัวข้อ “บันทึกด้วยมือ” ไม่ลบหัวข้อ เพราะคู่มืออ้างเลขหัวข้อและจำนวนเมนูย่อย
- หมายเหตุและการตัดปุ่มของหัวข้อ “บันทึกด้วยมือ” ทำในไฟล์แปลงผลลัพธ์ `expenses-guide-manual-entry.ts` ซึ่งเรียกจาก `user-guide/expenses/page.tsx`
- **แก้ 3 ต.ค. 2569 (รอบแก้ถ้อยคำ):** เมื่อทุกร้านเริ่มที่ไม่แสดงเมนู ประโยคใน `expenses-guide.content.ts` ที่เสนอการบันทึกด้วยมือเหมือนทุกร้านมี เป็นข้อบกพร่อง จึงแก้ในไฟล์คู่มือเองให้จริงทั้งร้านที่แสดงและไม่แสดงเมนู: ภาพรวม (“เมนูนี้ใช้ทำอะไร” และขั้น “นำเข้าระบบ”) สรุปของหัวข้อเมนูย่อย สรุปของหัวข้อ “บันทึกด้วยมือ” (เงื่อนไขอยู่ต้นประโยคเพราะหัวข้อที่พับอยู่ตัดสรุปเหลือสองบรรทัด) ลิงก์กรณีไม่มีใบเสร็จ และคำตอบ “ไม่พบเมนูย่อยบางรายการ” (หลังรวมงานชื่อบทบาท: ประโยคกลาง `GUIDE_MISSING_MENU_HELP` ตามด้วยเงื่อนไขของเมนูบันทึกด้วยมือ) ส่วนแถวที่เป็นชื่อเมนูย่อย ป้ายช่องทางของรายการที่บันทึกแล้ว และตารางสิทธิ์ จริงทั้งสองแบบอยู่แล้ว (เหตุผลเขียนไว้ใน test) hash ใน `sources` ของ `approved-product-help.ts` ย้ายตามไฟล์ที่ commit และการ์ดทุกใบที่อ้างคู่มือนี้ตรวจแล้ว (plan §5.1)
- คำตอบของผู้ช่วยใน LINE (การ์ด `expense.start`): **แก้ 3 ต.ค. 2569** เดิม “…นำใบเสร็จเข้าระบบหรือบันทึกด้วยมือ ระบบเก็บเป็นฉบับร่าง…” ไม่จริงกับร้านที่ไม่แสดงเมนูและกับผู้อ่านที่ไม่มีสิทธิ์บันทึก (การ์ดแสดงกับผู้มี `expense.read` หรือ `expense.read_own` ซึ่งรวมผู้ตรวจสอบแบบอ่านอย่างเดียว) เป็น “…นำใบเสร็จเข้าระบบหรือบันทึกด้วยมือตามช่องทางที่เปิดใช้สำหรับร้านของคุณและสิทธิ์ที่คุณมี ระบบเก็บเป็นฉบับร่าง…” ส่วนอื่นของการ์ดไม่เปลี่ยน การเปลี่ยนนี้อยู่ใน `apps/ai-gateway` จึงต้องปล่อยผู้ช่วยในรอบเดียวกัน

## 14. State, concurrency, audit และข้อจำกัดที่ตั้งใจ

- ไม่มี ExpenseRecord state transition จากการสลับค่า ไม่มี archive/delete/reclassify/re-number/backfill
- CAS ของค่านี้เป็นของตัวเอง (`expectedVersion`): ผู้ดูแลที่ถือค่าเก่าได้ 409, ค่าเท่าเดิมเป็น no-op
- ไม่ใช้และไม่ bump `CompanyEntitlementSet.setVersion` จึงไม่ชนกับการแก้ชุดสิทธิ์ที่ทำพร้อมกัน และไม่ทำให้การชำระเงินที่ค้างอยู่ถูกพัก
- ไม่เพิ่ม transaction lock หรือ backend fence ให้การสร้างรายจ่าย เพราะขอบเขตนี้ควบคุมทางเข้าเว็บ ไม่ได้ห้าม backend creation
- ปิดเมนูแข่งกับ request ที่ส่งไปแล้ว: API ทำตาม permission เดิม ถือว่า expected ไม่สัญญา “ไม่มีรายจ่ายใหม่หลังเวลาที่ปิด”
- การปิดฟีเจอร์แม่หรือ revoke role เป็นคนละ authority ต้องไม่ถูก admission ยกเว้นให้
- audit ตาม §5.4 การแสดงหรือซ่อนเมนูให้ผู้ใช้ไม่สร้าง audit

## 15. Compatibility, rollout และ rollback

มี migration แบบ additive หนึ่งรายการ ไม่มี permission migration และไม่เปลี่ยน semantics ของ key ใด

**ผลของวันปล่อย (ต้องแจ้งใน release handoff):** ทันทีที่รุ่นนี้ขึ้น เมนู ปุ่ม และลิงก์ที่พาไปหน้าบันทึกด้วยมือบนเว็บ**หายสำหรับทุกร้านที่มีอยู่** เพราะไม่มีร้านใดมีแถว จนกว่าผู้ดูแลระบบจะเปิดให้ร้านนั้น พนักงานยังอัปโหลดใบเสร็จ ใช้ใบรับรองแทนใบเสร็จ พิมพ์ใน LINE และแก้รายการเดิมได้ตามสิทธิ์เดิม ร้านที่ปิดอัปโหลดใบเสร็จอยู่จะเหลือปุ่มสร้างรายจ่ายบนเว็บเฉพาะผู้มีสิทธิ์ตรวจสอบค่าใช้จ่าย (ผ่านใบรับรองแทนใบเสร็จ) ผู้ดูแลควรเปิดให้ร้านที่ต้องใช้ก่อนแจ้งลูกค้า

1. web และ API ออกเป็น image เดียว (`infra/api-web/Dockerfile.api-web`) จึงขึ้นและถอยพร้อมกัน ช่วงสลับรุ่นสั้น ๆ: เว็บใหม่กับ API เก่าได้ field หายและถือว่าแสดง เว็บเก่ากับ API ใหม่ไม่อ่าน field และแสดงเมนูตามเดิม ทั้งสองกรณีทุกร้านเห็นเมนูชั่วคราว ไม่มีกรณีใดที่ร้านซึ่งเปิดไว้แล้วเสียหน้านี้ไป
2. ลำดับ: migration → API (command, รายละเอียดร้าน, `/auth/me`) → web (helper, gate, ทางเข้า, หน้าผู้ดูแล) ใน release เดียวกัน
3. ข้อมูลเดิมของร้าน สิทธิ์ รายจ่าย และภาษี ไม่ถูกเปลี่ยนจาก deployment
4. Rollback: ถอย image แล้ว**ทุกร้านกลับมาเห็นเมนู** ทั้งร้านที่เปิดไว้และร้านที่ไม่เคยเปิด เพราะโค้ดเก่าไม่อ่านค่านี้ ตารางใหม่ถูกปล่อยไว้ ไม่มีโค้ดเก่าใดอ่านตารางนี้ ไม่กระทบ billing, LINE หรือ normalizer ค่าที่ผู้ดูแลตั้งไว้ยังอยู่และมีผลอีกครั้งเมื่อขึ้นรุ่นใหม่ ให้บันทึกข้อจำกัดนี้ใน release handoff
5. ไม่มีขั้นตอน “เปิดให้ใช้ทีหลัง” ด้วย environment switch สวิตช์ใช้ได้ทันทีที่ release ขึ้น และค่าเริ่มต้น “ไม่แสดง” มีผลกับทุกร้านทันทีเช่นกัน
6. ร้านตัวอย่างของ seed (local, e2e) มีแถว “แสดง” ที่ `apps/api/prisma/seed.ts` เขียนให้ seed นี้ถูกเรียกเฉพาะในเครื่องและใน workflow ทดสอบ (`extended-tests.yml`) ไม่อยู่ในขั้นตอน deploy ใดใน `infra/` หรือ workflow ปล่อย จึงไม่มีร้านใดได้แถวจากการปล่อย (ตรวจจากโค้ดใน repo ไม่ได้ตรวจฐานข้อมูลจริง)

ก่อน cloud inspection อ่าน [cloud operations](../runbooks/cloud-environment-operations.md); ก่อน deploy/promotion/customer-gate change/retry อ่าน [mandatory deployment protocol](../runbooks/uat-production-v2-deployment.md) งานนี้ไม่อนุญาต deploy หรือเปลี่ยนค่าของลูกค้า

## 17. Out of scope และ definition of done

ไม่สร้าง global kill switch, ไม่หยุด LINE หรือ manual API, ไม่ปิด wizard, ไม่เพิ่ม permission, SKU หรือ entitlement key, ไม่ปรับเงินหรือภาษี, ไม่เปลี่ยน parent launch หรือ runoff policy, ไม่แก้ชุดคำตอบ LINE, ไม่สร้างที่เก็บร่างฟอร์ม และไม่แก้บั๊กใน[เอกสารบั๊กแยก](../research/manual-expense-current-code-bugs-2026-10-01-th.md)

เจ้าของตัดสิน D1–D8 แล้วเมื่อ 2 ต.ค. 2569 สั่งเริ่ม implement ในวันเดียวกัน และเปลี่ยนครึ่งแรกของ D2 เป็นค่าเริ่มต้นไม่แสดง ซึ่งเจ้าของยืนยันเมื่อ 3 ต.ค. 2569 ว่ารวมร้านเดิมด้วย (§1.2) ข้อค้นพบถูกตรวจซ้ำที่ commit เริ่มงานตาม plan P0 แล้ว Implementation complete เมื่อ AC01–AC20 มีหลักฐานตาม plan, spec/plan/memory อัปเดตสถานะจริง และระบุ live evidence ที่ยังค้างอย่างตรงไปตรงมา การสร้างเสร็จยังไม่ใช่การปล่อย: การปล่อยต้องผ่าน deployment protocol และคำสั่งของเจ้าของ
