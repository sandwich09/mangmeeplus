## 4. ความจำในบทสนทนา

ปัญหา: รอบถัดไปโมเดลเห็นเฉพาะข้อความที่ลูกค้าพิมพ์ ไม่รู้ว่ารอบก่อนอ่านอะไร กรองอะไร และแสดงรายการใดไป คำถามต่อเนื่องจึงตีความไม่ได้

- **R-M1 เก็บสิ่งที่อ่านไปแล้ว:** ทุกครั้งที่ API รันเครื่องมืออ่านรายจ่ายหรือใบเบิกสำเร็จ ให้เก็บใน `LineReadEvidence.inputJson` (เป็น JSON อยู่แล้ว ไม่ต้อง migration): ชื่อเครื่องมือ, input ที่ใช้จริงแบบ canonical (ช่วงวันที่ สถานะ สถานะจ่าย หมวด ร้าน สาขา), answerShape, รายการที่แสดง `shownItems` ไม่เกิน 10 รายการตามลำดับที่แสดง (ลำดับ, id, วันที่, ชื่อร้าน), `asOf`, `chatKeyHash`
- **R-M2 ส่งต่อให้รอบถัดไป:** `loadConversationContext` เพิ่มฟิลด์ `recentReads` (สูงสุด 3 รายการล่าสุด) เฉพาะแชตเดียวกัน สิทธิ์เดียวกัน ภายใน 15 นาที และส่งคำตอบถึงลูกค้าแล้ว ฟิลด์เดิม `deliveredExpenseSummary` คงไว้
- **R-M3 ให้โมเดลเห็น:** router แสดง `recentReads` แบบย่อในข้อความผู้ใช้ พร้อม id ที่คัดลอกได้ ไม่มียอดเงิน
- **R-M4 กติกาการต่อบริบท:**
  - คำถามต่อที่ไม่ระบุช่วงหรือตัวกรอง ให้ใช้ช่วงและตัวกรองของการอ่านล่าสุด
  - ค่าที่ลูกค้าพิมพ์ในข้อความปัจจุบันชนะเสมอ
  - "รวม X ด้วย" ให้เอาตัวกรองที่กัน X ออก ส่วน "เฉพาะ Y" หรือ "ไม่เอา X" ให้เพิ่มตัวกรอง
  - "แยกตาม…" ให้ใช้ breakdown ในขอบเขตเดิม
  - คำอ้างลำดับ เช่น "รายการแรก" หรือ "อันที่สอง" ให้ใช้ id จาก `shownItems` ของรายการล่าสุดที่แสดง
  - ถ้าลูกค้าเปลี่ยนเรื่อง ไม่ต้องสืบบริบท
- **R-M5 ตัวตรวจ:** ค่าที่สืบมาถือว่ามีหลักฐาน เมื่อเท่ากับค่าใน `recentReads` ซึ่ง API พิสูจน์แล้ว ใช้คู่กับค่าที่พบในข้อความปัจจุบัน id ที่อ้างต้องอยู่ใน `shownItems` เท่านั้น
- **R-M6 ห้ามใช้ตัวเลขเก่า:** ตัวเลขในคำตอบต้องมาจากการอ่านในรอบนี้เท่านั้น ความจำใช้เพื่อเข้าใจคำถามเท่านั้น
- **R-M7:** แชตกลุ่มไม่มีความจำข้อมูลบริษัท ตามกติกาเดิม

## 5. เส้นทางตอบ และการไม่ตัน

- **R-L1 ตรวจก่อนล็อกทางลัด:** gateway เสนอแผนทางลัด (`preparedPlan.complexity = simple`) เฉพาะเมื่อผ่านการตรวจชุดเดียวกับที่ orchestrator ใช้ก่อนเรียกเครื่องมือ (ใช้ฟังก์ชันร่วมกัน) API จึงล็อกงบแบบทางลัด 2 ช่องได้เฉพาะแผนที่ทำได้จริง นอกนั้นให้ไปทางปกติ
- **R-L2 พลาดแบบซื่อตรง:** ถ้าทางลัดยังล้มก่อนเรียกเครื่องมือ เช่น สิทธิ์เปลี่ยนระหว่างทาง ให้จบแบบ `unsupported` พร้อมข้อความ §8 ห้ามตั้งเป็น `needs_user` API ต้องปิดงานเป็น `completed` ไม่สร้างงานค้าง ใช้กฎเดียวกันกับ `READ_SOURCE_UNAVAILABLE`
- **R-L3:** `needs_user` ใช้เฉพาะเมื่อขาดค่าจากลูกค้าจริงและมีคำถามจริง
- **R-L4 ครอบครัวทางลัด:** ค่าเริ่มต้นในโค้ดและค่าใน Kamal ของ UAT และ production ใช้รายการเดียวกัน:
  - `expense.list_recent::single_metric`, `expense.list_recent::list`
  - `expense.get_breakdown::list`, `expense.get_daily_closing::single_metric`
  - `reimbursement.list_pending_approvals::list`, `reimbursement.get_summary::single_metric`
  - คงครอบครัวเดิมที่ production เปิดอยู่ไว้ด้วย
  - ค่าใน Kamal มีผลเมื่อ deploy ตาม runbook เท่านั้น
- **R-L5 เทียบช่วง:** ทางปกติต้องเรียกเครื่องมือเดิมซ้ำด้วยช่วงต่างกันได้ภายในงบ 4 ช่อง
- **R-L6 การอ้างงานค้าง:** คำสั่งแบบย่อของ router ต้องบอกรูปแบบ `taskRef {taskId, taskRevision, subrequestIndex}` พร้อมตัวอย่าง และแสดง ref ที่คัดลอกได้สำหรับงานที่ต่อได้ ถ้าโมเดลตอบผิดรูปแบบ การลองซ้ำต้องบอกว่าผิดที่ช่องไหน ตัวอ่านต้องคืนเหตุผลที่ปฏิเสธ คำถามอ่านข้อมูลใหม่ต้องไม่ผูกกับงานค้าง

## 6. รูปแบบคำตอบ

- **R-A1 ตัวเลขรวม:** บอกหัวข้อ, ช่วงวันที่แบบไทย, ตัวกรองที่ใช้ (สถานะเอกสาร สถานะจ่าย หมวด ร้าน สาขา), จำนวนรายการ, ยอดรวม, บรรทัด "ข้อมูล ณ" และลิงก์ แสดงบรรทัด "ฐานยอด" (รอดำเนินการ ร่าง ยืนยันแล้ว) เฉพาะเมื่อไม่ได้กรองสถานะ ห้ามแสดงยอดร่างเป็นศูนย์เมื่อร่างถูกกรองออก
- **R-A2 การแยกยอด:** เรียงกลุ่มจากมากไปน้อย แสดงยอดและจำนวนรายการ สูงสุด 8 กลุ่ม ที่เหลือรวมเป็น "อื่นๆ" แล้วบอกยอดรวม (เจ้าของ 2026-10-05: ไม่แสดงสัดส่วนร้อยละ — "เอา % ออกเถอะ งง ไม่สวยด้วย"; บนการ์ดแบบแถวแสดงยอดของกลุ่มอย่างเดียว)
- **R-A3 รายการ:** มีเลขลำดับ วันที่ ร้าน ยอด และสถานะ ไม่เกิน 10 รายการ พร้อมลิงก์ดูทั้งหมด เลขลำดับนี้คือเลขเดียวกับ `shownItems` ใน §4
- **R-A4 คำตอบที่โมเดลเรียบเรียง:** ต้องผ่านการตรวจตัวเลขเดิม (numeric grounding)
- **R-A5 บุคลิก:** น้องมั่งมีพูดสุภาพ ลงท้าย "ค่ะ" กระชับ ไม่ใช้ศัพท์ระบบ ไม่แสดงรหัสภายใน (ตามกติกา owner เรื่องไม่แสดงรหัสเครื่องในหน้าลูกค้า)

## 7. ความเข้าใจภาษา

- **R-U1 สถานะไม่ใช่สาขา:** คำหลัง "เฉพาะ" "เอาเฉพาะ" "ดูเฉพาะ" ที่เป็นเกณฑ์สถานะ ไม่ถือเป็นชื่อสาขา ทั้งแบบมีและไม่มี "ที่" หรือ "รายการที่" นำหน้า ได้แก่ ยืนยัน อนุมัติ จ่ายแล้ว ยังไม่จ่าย ค้างจ่าย ร่าง รอตรวจ ปฏิเสธ ยกเลิก ต้องแก้ทั้งใน gateway (`expenseBranchScopeRequested`) และตัวเดียวกันใน API (`line-read-evidence.service.ts`)
- **R-U2 ข้อความสำเร็จรูปว่า "ไม่รองรับ":** เดิม `UNSUPPORTED_EXPENSE_FILTER` และ `LINE_AI_EXPENSE_CRITERION_REPLIES` ตอบว่ากรองสถานะ แยกหมวด และ "จ่ายจริง" ไม่ได้ ตอนนี้เครื่องมือรองรับแล้ว ให้คงข้อความสำเร็จรูปไว้เฉพาะเกณฑ์ที่ยังทำไม่ได้จริง เช่น นับรวมรายการที่ถูกปฏิเสธหรือยกเลิกเข้าไปในยอดรวม
- **R-U3 ภาษาธรรมชาติ:** ต้องรองรับคำพิมพ์ผิด เช่น "ค่าไช้จ่าย" "เดือนนิ", ภาษาพูด, ไทยปนอังกฤษ, ปี พ.ศ., ชื่อเดือนย่อ และช่วงสัมพัทธ์ เช่น เดือนที่แล้ว สัปดาห์นี้ ปีนี้ ไตรมาสนี้ สามเดือนที่ผ่านมา การแปลงช่วงเวลาใช้ตัวแปลงค่าที่มีอยู่แล้ว ถ้ารองรับไม่ครบให้เติม
- **R-U4 หลายคำถามในข้อความเดียว:** ต้องตอบครบทุกคำถาม หรือบอกชัดว่าคำถามไหนยังตอบไม่ได้

## 9. ความเร็ว

- **เป้า:** ตาม A7 เร็วกว่านี้ได้ยิ่งดี แต่ห้ามแลกกับความถูกต้อง
- **ตัวช่วยหลักรอบนี้:** ขยายทางลัด (R-L4), ตรวจก่อนล็อกทางลัด (R-L1), ลดข้อความที่โมเดล router ต้องเขียนออกมา เช่น ตัด `reason` แบบข้อความยาวออก หากไม่มีส่วนใดใช้ ให้วัดก่อนและหลังตัด, และเติมค่า `lane`, `fallbackReason`, `costSatang` ใน `turn_summary` ที่ปัจจุบันเป็นค่าว่าง
- **ไม่ทำรอบนี้:** เปลี่ยนโมเดล router เป็นรุ่นที่เร็วกว่า เพราะต้องผ่านการตัดสินใจเรื่องผู้ให้บริการและความเป็นส่วนตัวของ owner ก่อน

## 10. ชุดทดสอบและเกณฑ์รับงาน

- **Runtime:** ใช้ `scripts/line-ai-reliability-runtime.ts` ที่มีอยู่ API แบบ compiled รันในโปรเซส gateway แยกโปรเซส Postgres และ Redis แยกเฉพาะ LINE เป็น sink จำลอง Bedrock เป็นของจริงผ่านโปรไฟล์ `watchdog-bedrock`
- **สิทธิ์:** คำนวณจาก `TIER_FEATURE_PRESETS` และ `ROLE_GRANTS` ของจริง ห้ามเขียนสิทธิ์รวมเอง
- **ข้อมูลตั้งต้น:** "วันนี้" คือ 2026-09-27 เวลาไทย
  - บริษัท A: STARTER_249 หนึ่งสาขา
  - บริษัท B: PRO_999 สองสาขา
  - บทบาท: OWNER, MANAGER, STAFF, ACCOUNTANT, AUDITOR_READONLY
  - รายจ่ายเดือนสิงหาคมและกันยายน 2026 อย่างน้อย 30 รายการ ห้าหมวด หกร้าน (มีสองร้านที่ชื่อคล้ายกัน) ทุกสถานะเอกสาร และสถานะจ่ายทั้งสามแบบ
  - ใบเบิกอย่างน้อยหกใบ: ร่าง รออนุมัติ อนุมัติ จ่ายแล้ว ปฏิเสธ
- **ชุดจูน:** อย่างน้อย 200 ข้อ ในอย่างน้อย 60 บทสนทนา
  - ครอบคลุมทุกแถวของ §3
  - ภาษา: คำพิมพ์ผิด ภาษาพูด อังกฤษปน ปี พ.ศ.
  - รูปแบบต่อเนื่อง: เปลี่ยนตัวกรอง เปลี่ยนช่วง เปลี่ยนการจัดกลุ่ม อ้างลำดับ แก้คำ เปลี่ยนเรื่องแล้วกลับมา หลายคำถามในข้อความเดียว
  - ทุกบทบาท
- **ชุดเก็บไว้ทดสอบ (held-out):** อย่างน้อย 60 ข้อ เขียนแยกโดยผู้เขียนอีกคน ห้ามใช้ปรับแต่งระหว่างทำงาน
- **เฉลย:**
  - ข้อที่ถามข้อมูลมีเครื่องมือและ input แบบ canonical ที่ถูก (รับคำตอบทางเลือกที่เทียบเท่าได้)
  - ตัวเลขที่คาดหวังได้จากการรันเครื่องมือเฉลยกับข้อมูลตั้งต้นตอนตรวจ ห้ามพิมพ์ตัวเลขเอง
  - ข้อที่ไม่ใช่ข้อมูลใช้ป้ายกำกับ: `no_tool`, `must_answer`, `must_not_refuse`, `must_mention_any`, `must_not_claim`
- **ผลตรวจ:**
  - ผ่านหรือไม่ผ่านรายข้อ พร้อมเหตุผล
  - สรุปตาม A1–A8 เวลาแยกตามทาง และค่าใช้จ่าย
  - บทสนทนาเต็มสำหรับให้คนอ่านทวน
- **เกณฑ์ผ่าน:** ชุดจูนและชุดเก็บไว้ทดสอบผ่าน A1–A8 ครบ ในการรันกับโมเดลจริงรอบสุดท้าย บน commit เดียวกับที่จะ merge

## 11. กติกาที่ห้ามละเมิด

- **สิทธิ์ข้อมูล:** gateway เรียกเฉพาะเครื่องมือของ API ที่ตรวจสิทธิ์แล้ว ห้ามอ่านฐานข้อมูลเอง ต้องรักษาขอบเขตสิทธิ์ บริษัท และสาขาไว้ทุกจุด แชตกลุ่มต้องไม่เห็นข้อมูลบริษัท
- **ความถูกต้องของข้อมูล:** ห้ามสร้างตัวเลขหรือแหล่งอ้างอิงขึ้นเอง ทุกการเขียนต้องผ่านขั้น preview แล้ว confirm ห้ามส่ง อนุมัติ หรือจ่ายแทนผู้ใช้เอง
- **การปล่อยงาน:** ห้ามเพิ่ม flag, env หรือ dependency ใหม่ ให้ rollback ด้วยการย้อนเวอร์ชัน ห้ามแก้ `package.json` เว้นแต่เป็นการเปลี่ยน dependency
- **การทดสอบ:** spec ใหม่ต้องลงทะเบียนใน `scripts/line-ai-whole-chain-acceptance.catalog.mjs` หรือ workflow ที่เกี่ยวข้อง ถ้าแตะไฟล์ที่ถูก pin ต้อง sync pin ด้วย

## 12. การปล่อยใช้งาน

- **merge:** เข้า develop และ main หลังผ่าน §10 (owner อนุมัติไว้แล้ว) main ต้องมาจาก branch ที่แตกจาก main
- **deploy:** แยกจากการ merge ต้องทำตาม runbook UAT และ production ร่วมกับ owner
- **ข้อควรระวัง:** main มีงาน v2.4 ที่ตั้งให้เปิดเองอยู่แล้ว (merge 2026-09-27) ไม่ควร deploy main จนกว่างานนี้จะ merge

  - ชุดทดสอบส่งข้อความติดกันจึงเห็นแค่ครั้งแรก
  - ค่าเฉลี่ยจริงจึงขึ้นกับความถี่ของข้อความในแต่ละร้าน
- **ชื่อย่อหรือชื่อเรียกสั้นของร้าน:** ระบบจับคู่ชื่อหมวด ร้าน และสาขาที่สะกดต่างกันหนึ่งตัวอักษรได้แล้ว (เมื่อชื่อยาวอย่างน้อยสี่ตัวอักษร) แต่ "ปั๊ม ปตท." ยังไม่จับคู่กับ "ปั๊มน้ำมัน ปตท." จึงได้ "ไม่พบ"
- **ชื่อร้านที่พิมพ์ไม่เต็ม:** เช่น "สมใจ" ตามหลังคำถามเรื่อง "ร้านสมใจ" บางครั้งโมเดลตีความเป็นร้านเดิมแทนการถามว่าหมายถึงร้านไหน
- **ลำดับที่อ้างถึงหลังตารางแยกกลุ่ม:** เมื่อผู้ใช้ขอ "5 อันดับแรก" หลังดูยอดแยกตามร้าน โมเดลแสดงอันดับร้านแทนรายการล่าสุด 5 รายการ
  - คำถามต่อมา "อันแรกจ่ายหรือยัง" จึงตอบว่ายังดึงข้อมูลไม่ได้ เพราะสิ่งที่แสดงเป็นกลุ่มร้าน ไม่ใช่รายการ (นับเป็นทางตันหนึ่งครั้ง)
  - ควรถามกลับ หรือเปิดรายการของร้านนั้นแทน
  - ในชุดจูนพบคล้ายกันหนึ่งครั้ง: "อันแรกที่รอตรวจ" ถูกอ่านเป็นรายการเก่าที่สุด
- **ตัวกรองค้างในคำขอที่ครบในตัว:** "ขอดูรายการล่าสุด 5 รายการ" หลังคุยเรื่องรายการที่ยืนยันแล้ว ยังคงตัวกรอง "ยืนยันแล้ว" ไว้
- **"จ่ายไปทั้งหมดเท่าไหร่" หลังคุยเรื่องสถานะการจ่าย:** ถูกตีความเป็นเฉพาะรายการที่จ่ายแล้ว แทนยอดค่าใช้จ่ายทั้งหมด คำนี้กำกวม ควรบอกฐานยอดให้ชัด
- **คำถามวิธีใช้ฟีเจอร์นอกแพ็กเกจ:** "สั่งซื้อของจากซัพพลายเออร์ยังไง" ถูกส่งไปทางคำถามวิธีใช้ จึงตอบแบบคู่มือทั่วไป ไม่ได้บอกว่าอยู่นอกแพ็กเกจ
- **คำถาม "ทำไม" บางแบบ:** "ทำไมยังไม่จ่ายเยอะ" ตอบโดยแยกตามร้านแทนแยกตามหมวด และ "ทำไมจ่ายร้าน X เยอะ" ไม่ได้บอกยอดของร้านอื่นให้เทียบ
- **ตัวเลขเล็ก 1–20 ที่ผู้ใช้พิมพ์เอง** (เช่น "รายการที่ 3") ถือว่าอ้างอิงได้ เพราะเป็นเลขลำดับ ไม่ใช่ยอดเงิน
