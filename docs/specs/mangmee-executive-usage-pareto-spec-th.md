## 1. มติและขอบเขต

Owner ขอกราฟแยกสี คลิกเจาะข้อมูลได้ เรียงตามการใช้งาน ตัวอย่างหลังตัดบริษัททดสอบ 72 บริษัท เคยเพิ่มใบเสร็จ40 (55.6%) / ยังไม่เคย32 (44.4%) และนำ 80/20 Top spender มาใช้
ตัวเลข72/40/32 เป็น fixture สำหรับออกแบบ ไม่ใช่การตรวจข้อมูลลูกค้าจริง
คง B6 เซลล์หรือช่องทาง, paid-not-started กลุ่มเดียว, ธีม shared fields และการซ่อน deletion ตามมติล่าสุด
Owner ยืนยันนิยาม Top spender: เงินที่บริษัทจ่ายให้มั่งมีหักคืนเงินตามช่วงรายงาน; แยกจากค่าใช้จ่ายในใบเสร็จของบริษัทลูกค้าและต้นทุน AI/OCR
ช่วงรายงานของกลุ่มนี้คือเดือนที่เลือก และทุกหัวข้อของแท็บต้องมีคำว่า “ในเดือน” พร้อมชื่อเดือน (**ตัดสินแล้ว 2 ต.ค. 2569 (เจ้าของ: ตามที่แนะนำ) — Q24**; ทางเลือกที่ไม่ได้เลือกคือนับ 12 เดือนล่าสุด ซึ่งข้อมูลเงินเริ่มกันยายน 2026 จึงครบ 12 เดือนได้เร็วที่สุดกันยายน 2027)
การจัดอันดับทั้งหมดใช้แค่ข้อมูลวิเคราะห์ที่ executive มีสิทธิ์อ่าน ไม่มีลิงก์เปิดไฟล์ใบเสร็จลูกค้าจากกราฟนี้

## 2. ฐานบริษัทและเวลา

- ใช้ eligible population เดียวกับ BE§12: distinct companyId, CUSTOMER, สมัครก่อน effectiveEnd; ตัด TEST/INTERNAL ก่อน aggregate/rank/denominator
- ใช้เดือนและ shared industry/discovery/referrer filters เดียวกัน และชุดข้อมูล (`build`) เดียวกับหน้าที่เปิดอยู่
- กราฟแสดงฐาน N หลังกรองเสมอ; N=0 แสดง empty และเปอร์เซ็นต์เป็น null ไม่ทำ 0/0
- “เคยเพิ่ม” = ตั้งแต่สมัครจนถึง cutoff; “จำนวนใบเสร็จในเดือน” = ช่วงรายงาน half-open เวลา Bangkok
- ไม่ใช้ population เฉพาะหน้าตารางหรือเฉพาะบริษัทที่มีรายรับเป็น denominator โดยไม่เปลี่ยนชื่อฐาน
- คำว่า snapshot ที่เหลืออยู่ในเอกสารนี้หมายถึงชุดข้อมูลของรายงานตามสเปกหลังบ้าน §12.3 (ตารางสรุปที่สร้างตามเวลา ไม่มีอายุ 15 นาที) กราฟ รายชื่อ และไฟล์ส่งออกที่เปิดต่อกันต้องมาจากชุดข้อมูลเดียวกัน และถ้าชุดข้อมูลเปลี่ยนระหว่างทางต้องบอกผู้ใช้ตามสเปกหน้าจอ §4.1
- ไม่รวมบริษัท test จากการค้นชื่อเอง; classification unknown ต้องแจ้ง coverage ไม่เดาเป็นลูกค้าจริง
- เดโมใหม่78แถว =72 CUSTOMER +4 TEST +2 INTERNAL; รายงานทุกหน้าตัด6แถวก่อนสรุป ยอดในเดโมเดิม12บริษัทเป็น historical baseline

## 3. ใบเสร็จและ coverage

metric นี้หมายถึง **ใบเสร็จค่าใช้จ่ายที่ลูกค้าเพิ่มเข้าสู่ระบบ** ไม่ใช่ `companiesWithReceipts` ที่หมายถึงบริษัทที่จ่ายเงินให้มั่งมี
ใช้ชื่อ `expenseReceiptAdoption` และ `expenseReceiptCountInPeriod` เพื่อไม่ชน billing receipts (N08, N09 ของสเปกหน้าจอ §4.2)
กติกาข้อมูลของหัวข้อนี้อยู่ที่สเปกหลังบ้าน §13.4 และ §13.5 ซึ่งแทนข้อเสนอ Q03 เดิมของเอกสารนี้ สรุปสิ่งที่หน้าจอต้องรู้:

- หนึ่งรายจ่ายที่เพิ่มด้วยการส่งใบเสร็จ (ทางเว็บหรือทาง LINE) นับหนึ่งใบ ภาพหลายหน้า ไฟล์แนบเสริม และการเปลี่ยนไฟล์ไม่นับเพิ่ม รายจ่ายที่กรอกมือโดยไม่มีใบเสร็จไม่นับ
- จำนวนรายเดือนเก็บในตารางสรุปและไม่ลดลงเมื่อมีการลบภายหลัง “ใบเสร็จสะสม” คือผลรวมของจำนวนรายเดือนที่เก็บไว้
- หลักฐานว่า “เคยส่งใบเสร็จเข้าอ่าน” ไม่ใช่หลักฐานว่า “อ่านสำเร็จ” รุ่นแรกไม่มีตัวเลขอ่านใบเสร็จสำเร็จ

สถานะของแต่ละบริษัทตัดสินตามลำดับในตาราง ข้อแรกที่ตรงเป็นคำตอบ บริษัทหนึ่งอยู่ได้สถานะเดียว (ลำดับเดียวกับสเปกหลังบ้าน §13.4):

| สถานะ | เกณฑ์ตามสเปกหลังบ้าน §13.4–§13.5 | ชื่อบนจอ | สีตามบทบาท (สเปกหน้าจอ §10.5) |
|---|---|---|---|
| EVER | พบหลักฐานอย่างน้อยหนึ่งอย่างว่าเคยเพิ่มใบเสร็จ หรือตารางสรุปเคยบันทึกว่าเคยเพิ่ม | เคยเพิ่มใบเสร็จ | สีหลัก เขียวเข้ม |
| NOT_ENTITLED | ไม่เคยมีหลักฐาน และร้านไม่มีสิทธิ์ใช้ฟีเจอร์รายจ่ายตามแพ็กเกจ ณ เวลาที่สร้างชุดข้อมูล | ไม่มีในแพ็กเกจ | เทาอ่อนมีขอบ |
| UNKNOWN | ไม่พบหลักฐาน ร้านมีสิทธิ์ใช้ฟีเจอร์รายจ่าย และร้านสร้างก่อน 2026-08-27 ซึ่งเป็นวันที่ระบบเริ่มเก็บหลักฐานชนิดหนึ่ง | ยังประเมินไม่ได้ | เทามีลายขีด |
| NEVER | ไม่พบหลักฐาน ร้านสร้างตั้งแต่ 2026-08-27 และมีสิทธิ์ใช้ฟีเจอร์รายจ่าย | ยังไม่พบการเพิ่มใบเสร็จ | สีเตือน ทองเข้มหรือทองมีขอบสีเข้ม |

- สมการ EVER + NEVER + UNKNOWN + NOT_ENTITLED = N; `% = count/N*100` หลังบ้านคืนค่าที่ปัดแล้วหนึ่งตำแหน่งตามกติกาปัดเศษของสเปกหน้าจอ §4.3
  40/72=55.555…→55.6%; 32/72=44.444…→44.4%; ห้ามเอาค่าที่ปัดแล้วไปคำนวณเงินหรืออันดับ
- ร้านที่เข้าเกณฑ์ทั้ง “ไม่มีในแพ็กเกจ” และ “ยังประเมินไม่ได้” (สร้างก่อนวันดังกล่าวและไม่มีสิทธิ์) อยู่ในแถว “ไม่มีในแพ็กเกจ” สเปกหลังบ้าน §13.4 เขียนลำดับนี้ไว้แล้ว: “ไม่มีในแพ็กเกจ” เป็นข้อเท็จจริงปัจจุบันที่รู้แน่ และร้านที่ใช้ฟีเจอร์ไม่ได้ไม่ใช่ร้านที่ต้องตามเรื่องใบเสร็จ “ยังประเมินไม่ได้” จึงเหลือเฉพาะร้านที่ใช้ฟีเจอร์ได้แต่ประวัติย้อนไปไม่ถึง ร้านที่มีหลักฐานเป็น “เคยเพิ่มใบเสร็จ” เสมอ แม้วันนี้ไม่มีสิทธิ์แล้ว
- ร้านที่เคยเพิ่มใบเสร็จแล้วลบทิ้งทั้งหมดยังเป็น “เคยเพิ่มใบเสร็จ” (**ตัดสินแล้ว 2 ต.ค. 2569 (เจ้าของ: ตามที่แนะนำ) — Q20**; ทางเลือกที่ไม่ได้เลือกคือนับจากรายการที่เหลืออยู่ ซึ่งทำให้ตัวเลขของเดือนเก่าลดลงเองเมื่อมีการลบ)
- UNKNOWN เป็นสถานะ coverage ของ metric ไม่ใช่ paid usage business cohort ใหม่
- ชื่อบนจอของ NEVER คือ “ยังไม่พบการเพิ่มใบเสร็จ” ตามป้ายที่สเปกหลังบ้านเสนอ แทนคำเดิม “ยังไม่เคยเพิ่มใบเสร็จ” เพราะระบบบอกได้เพียงว่าไม่พบหลักฐาน (เอกสารคำบนหน้าจอ แถว N08)
- ข้อมูลตัวอย่าง 72 บริษัทยังเป็น 40 / 32 / 0 / 0 ตามเกณฑ์นี้ และยังไม่มีบริษัทตัวอย่างของสถานะ “ยังประเมินไม่ได้” กับ “ไม่มีในแพ็กเกจ” ให้ตรวจบนหน้าจอ

## 4. การกด สี และอันดับ

- แถบกราฟและคำอธิบายทุกกลุ่มกดได้ ทั้งแตะ คลิก Enter และ Space มี label+จำนวน+% ไม่สื่อด้วยสีอย่างเดียว ส่วนของแถบที่แคบกว่า 44 px ให้กดผ่านรายการคำอธิบายใต้กราฟ ซึ่งแต่ละรายการสูงอย่างน้อย 44 px
- สีกำหนดตามบทบาท และบทบาทหนึ่งมีความหมายเดียวทั้งชุดหน้าและในไฟล์ Excel: **สีหลัก เขียวเข้ม** = กลุ่มที่เป็นประเด็นของกราฟ (เคยเพิ่มใบเสร็จ; กลุ่มที่จ่ายสูงสุด), **สีเตือน ทอง** = กลุ่มที่ต้องตามต่อ (ยังไม่พบการเพิ่มใบเสร็จ), **เทามีลายขีด** = ข้อมูลไม่พอ (ยังประเมินไม่ได้) เท่านั้น, **เทาอ่อนมีขอบ** = อยู่นอกประเด็น (ลูกค้านอกกลุ่ม; ไม่มีในแพ็กเกจ) ไม่ใช้สีน้ำเงินกับส่วนที่กดได้ ใช้ tokens ของแอป
- ส่วนของกราฟที่อยู่ติดกันต้องต่างกันด้านความสว่างอย่างน้อย 3:1 และทุกสีต่างจากพื้นอย่างน้อย 3:1 กราฟต้องอ่านได้เมื่อมองเป็นขาวดำ (สเปกหน้าจอ §10.5)
- กลุ่มธุรกิจ/ช่องทาง/เซลล์มีแถบจำนวนบริษัทที่กดได้ ใช้สีเดียว (สีหลัก) ทุกแถว ไม่ใช้สีแยกหมวด เพราะจำนวนหมวดไม่จำกัดและแต่ละแถวมีชื่อกำกับอยู่แล้ว
- เปิดรายชื่อด้วยตัวกรองร่วมและชุดข้อมูลเดิม บวกเงื่อนไขของกลุ่มที่กด; ตัวกรองเฉพาะรายชื่ออื่นเริ่มจากค่าเริ่มต้น (แก้สาเหตุ G22) และ **ไม่เขียนทับตัวกรองของหน้าต้นทาง** กติกาครบอยู่ในสเปกหน้าจอ §3.3
- แสดง chip/ข้อความฐาน cohort และ sort ชัด; เปลี่ยน shared filter หลังเลือก cohort ให้คำนวณสมาชิกกลุ่มใหม่จากคำขอใหม่
- ค่าเริ่มต้นอันดับการใช้ = ใบเสร็จในเดือนมาก→น้อย; เลือกวันใช้งานหรือใช้ผู้ช่วยได้ ไม่สร้างคะแนนรวมข้ามหน่วย
- ค่าที่ไม่มีข้อมูลเรียงท้าย ไม่ถือเป็น 0 และไม่มีเลขอันดับ; ค่าเท่ากันได้เลขอันดับเดียวกัน (1, 1, 3) และเรียงภายในด้วยวันที่สมัครก่อน แล้วจึงรหัสภายในซึ่งไม่แสดงบนจอ; จำนวนที่แสดงเป็น known count หาก coverage ไม่ครบ
- กราฟแสดง 10 อันดับแรกพร้อมเลขอันดับที่หลังบ้านคืนมา และปุ่ม “ดูอันดับทั้งหมด” ซึ่งเปิดรายชื่อที่เรียงตามตัวชี้วัดเดียวกัน; หน่วยเขียนติดกับตัวเลข; การแบ่งหน้าของรายชื่อไม่เปลี่ยนค่า total/denominator/rank
- กราฟตัดที่ 10 รายการเสมอ ไม่ขยายเมื่อมีบริษัทที่ค่าเท่ากัน แต่ต้องบอกใต้กราฟทุกครั้งที่มีบริษัทค่าเท่ากับรายการสุดท้ายที่แสดงแต่ไม่ได้อยู่ในกราฟ: “มีอีก N บริษัทที่ค่าเท่ากับอันดับสุดท้ายที่แสดง (V <หน่วย>)” เช่น “มีอีก 3 บริษัทที่ค่าเท่ากับอันดับสุดท้ายที่แสดง (12 ใบ)” โดย N กับ V มาจาก `usageRanking.boundaryTie { count, value }` ที่หลังบ้านคืน (สเปกหลังบ้าน §13.6) หน้าเว็บไม่นับเอง ประโยคเขียน “อันดับสุดท้ายที่แสดง” ไม่เขียน “อันดับที่ 10” เพราะค่าเท่ากันได้เลขอันดับเดียวกัน รายการที่สิบจึงอาจมีเลขอันดับน้อยกว่า 10 ไม่มีตัวกรองเพิ่มสำหรับประโยคนี้ ผู้ใช้กด “ดูอันดับทั้งหมด” แล้วเห็นบริษัทเหล่านั้นด้วยเลขอันดับเดียวกัน `count` เป็น 0 หรือหลังบ้านไม่คืนช่องนี้ ไม่แสดงประโยค (กติกาเดียวกับขอบกลุ่มใน §5 — **ตัดสินแล้ว 2 ต.ค. 2569 (เจ้าของ: ตามที่แนะนำ) — Q25**)
- บนมือถือ อันดับเป็นรายการทีละบริษัท (ชื่อ แถบ และตัวเลขพร้อมหน่วย) แบบที่ต้นแบบทำอยู่ ซึ่งอ่านครบที่ 390 px
- กลับจากรายละเอียดคงกลุ่ม การเรียง และเลขหน้า; เปลี่ยนตัวกรอง การเรียง หรือกลุ่มแล้วกลับไปหน้า 1; เลขหน้าที่เกินให้แสดงหน้าสุดท้าย; “ล้างตัวกรอง” ล้างกลุ่ม การเรียง และเลขหน้าโดยคงเดือน (การแบ่งหน้าใช้เลขหน้าตามสเปกหน้าจอ §3.2)

## 5. Top spender / Pareto

ชื่อบนจอ: “ลูกค้าที่จ่ายสูงสุด 20% แรก”, “บริษัทที่รวมยอดรับถึง 80%”, “จ่ายมากกว่ายอดคืนในเดือน” และ “ยอดที่ใช้คำนวณสัดส่วน” (N12) หัวข้อของแท็บมีชื่อเดือนกำกับ เช่น “รายรับในเดือน ก.ย. 2569 มาจากลูกค้ากลุ่มใด” และเมื่อเดือนยังไม่จบมีป้าย “เดือนนี้ยังไม่จบ” ตามสเปกหน้าจอ §4.1

นิยามเงินที่ Owner ยืนยัน: `net_i = verified receipts_i − actual refunds_i` ในช่วงที่เลือก ตาม BE§14
ให้ดูยอดรับสุทธิจริงในตารางเสมอ; ข้อเสนอทางคำนวณสำหรับกรณีค่าติดลบคือส่วนกราฟ concentration ใช้ `w_i = max(net_i,0)` เพราะส่วนแบ่งสะสมต้องไม่ลดลง
`positiveNetTotal = sum(w_i)` ต้องมีชื่อฐานชัดว่า “ยอดรับสุทธิที่เป็นบวก” ไม่อ้างว่าเท่ากับยอดรับสุทธิทั้งแพลตฟอร์ม
แสดงยอดติดลบรวม/จำนวนบริษัทที่ net≤0 แยก เมื่อมี; platform net ยังคงรวมค่าติดลบตามจริง

- N = บริษัทจริงทั้งหมดหลัง shared filters แม้ไม่มีการจ่าย; K=ceil(N*0.2); สมาชิกของกลุ่มคิดจากประชากรหลังตัวกรองร่วมเท่านั้น ตัวกรองเฉพาะรายชื่อและคำค้นไม่เปลี่ยนสมาชิกของกลุ่ม
- เรียงเฉพาะ w_i>0 มาก→น้อย ค่าเท่ากันเรียงตามวันที่สมัครก่อน แล้วจึงรหัสภายในซึ่งไม่แสดงบนจอ; topCount=min(K,positiveCount)
- Top20 share = sum(w ของ topCount)/positiveNetTotal; แสดงจำนวนจริงและ topCount/N เสมอ เพราะการปัดขึ้นอาจเกิน20%
- ถ้าผู้จ่ายบวกน้อยกว่า K ให้บอกว่ามีผู้จ่ายบวกไม่ถึง20%; ไม่เติมบริษัท0บาทแล้วเรียก spender
- กลุ่มถึง80% = minimal prefix ที่ cumulative >= 80% ของ positiveNetTotal; ใช้ integer satang เปรียบเทียบ `cumulative*100 >= total*80` ก่อนปัด
- ขอบกลุ่มไม่ขยายเมื่อมีบริษัทที่จ่ายเท่ากัน แต่ต้องบอกบนจอทุกครั้งที่เกิด ทั้งกลุ่ม 20% และกลุ่ม 80%: “มีอีก N บริษัทที่จ่ายเท่ากับลำดับสุดท้ายของกลุ่ม (X บาท) แต่อยู่นอกกลุ่ม” ประโยคอยู่ใต้กลุ่มที่เกิด และกดเปิดรายชื่อบริษัททุกรายที่จ่ายเท่ายอดนั้น ทั้งในและนอกกลุ่ม บริษัทที่จ่ายเท่ากันได้เลขอันดับเดียวกันตาม §4 (**ตัดสินแล้ว 2 ต.ค. 2569 (เจ้าของ: ตามที่แนะนำ) — Q25**; ทางเลือกที่ไม่ได้เลือกคือรวมทุกบริษัทที่จ่ายเท่ากันเข้ากลุ่ม ซึ่งทำให้กลุ่มใหญ่กว่า 20% — ข้อมูลตัวอย่างจะเป็น 22 จาก 72 บริษัท หรือ 30.6% — และต้องเปลี่ยนชื่อกลุ่ม)
  - กลุ่ม 20%: N กับ X มาจาก `boundaryTie { count, netSatang }` และรายชื่อเปิดด้วย `spendCohort=BOUNDARY_TIE`
  - กลุ่ม 80%: N กับ X มาจาก `prefix80BoundaryTie { count, netSatang }` และรายชื่อเปิดด้วย `spendCohort=TO80_BOUNDARY_TIE`
  - `count` เป็น 0 ไม่แสดงประโยค; เมื่อไม่มีกลุ่ม (เหตุผล `TOO_FEW_COMPANIES`, `NO_POSITIVE_NET` หรือ `BILLING_SCAN_NOT_COMPLETE`) หลังบ้านไม่คืนสองช่องนี้และไม่มีประโยค; หน้าเว็บไม่นับเอง
  - รายชื่อที่เปิดจากประโยคมีบรรทัดสรุปตามสเปกหน้าจอ §6: จำนวนบริษัท และยอดรับสุทธิในเดือนรวมของบริษัทในรายชื่อนั้น
- รายชื่อที่เรียงตามยอดรับสุทธิในเดือน (รวมรายชื่อของกลุ่ม 20% และกลุ่ม 80%) มีบรรทัดอธิบายลำดับ “ถ้ายอดเท่ากัน บริษัทที่สมัครก่อนอยู่ก่อน” ใต้รายชื่อเสมอ บรรทัดนี้อธิบายลำดับภายในยอดที่เท่ากัน ไม่ได้ใช้แทนประโยคบอกจำนวนข้างบน
- ตัวอย่างจากข้อมูลตัวอย่าง: 14 บริษัทจ่าย 2,990.00 บาทเท่ากัน กลุ่ม 20% (15 บริษัท) มี 7 บริษัทอยู่ในกลุ่มและ 7 บริษัทอยู่นอกกลุ่ม หน้าจอต้องแสดง “มีอีก 7 บริษัทที่จ่ายเท่ากับลำดับสุดท้ายของกลุ่ม (2,990.00 บาท) แต่อยู่นอกกลุ่ม” ใต้กลุ่ม 20% ส่วนกลุ่ม 80% (13 บริษัท) มี 5 ในกลุ่มและ 9 นอกกลุ่ม หน้าจอต้องแสดง “มีอีก 9 บริษัทที่จ่ายเท่ากับลำดับสุดท้ายของกลุ่ม (2,990.00 บาท) แต่อยู่นอกกลุ่ม” ใต้กลุ่ม 80% รายชื่อที่เปิดจากประโยคทั้งสองมี 14 บริษัทเท่ากัน และบรรทัดสรุปของรายชื่อนั้นคือ “พบ 14 บริษัท · ยอดรับสุทธิในเดือน 41,860.00 บาท” (14 × 2,990.00 บาท; จำนวน 7, 9 และ 14 ตรงกับตัวอย่างของสเปกหลังบ้าน §13.6)
- กลุ่มที่จ่ายสูงสุดใช้สีหลัก (เขียวเข้ม) กลุ่มนอกใช้เทาอ่อนมีขอบ ตามบทบาทสีใน §4; กดแถบหรือจำนวนไปยังสมาชิกกลุ่มเดียวกัน โดยรายชื่อเรียงตามยอดรับสุทธิในเดือนมาก→น้อย และการกดไม่เขียนทับตัวกรองของหน้าต้นทาง (สเปกหน้าจอ §3.3)
- “นอกTop20” ใช้ N ลบสมาชิกTop20 จึงรวมผู้ไม่มี net บวกด้วย; รายการระบุยอด0/ติดลบตามจริง
- กด “บริษัทที่รวมยอดรับถึง 80%” เปิด exact prefix; อย่าใช้ top20 แทน prefix80 เพราะจำนวนอาจต่างกัน
- เมื่อรายชื่อเรียงตามยอดรับสุทธิในเดือน ให้แสดงสัดส่วนสะสมของ “ยอดที่ใช้คำนวณสัดส่วน” ต่อบริษัท (ทศนิยม 1 ตำแหน่ง) เพื่อให้ตรวจขอบกลุ่ม 80% จากหน้าจอได้ บริษัทที่ยอดเป็น 0 หรือติดลบแสดง “ไม่นับในสัดส่วน”
- ยอดรวมเป็น 0 (หลังบ้านคืนเหตุผล `NO_POSITIVE_NET`): ไม่มีกลุ่ม ไม่มีสัดส่วน แสดง “ไม่มีบริษัทที่จ่ายมากกว่ายอดคืนเงินในเดือน จึงยังคำนวณสัดส่วนรายรับไม่ได้” ไม่วาดกราฟปลอม
- กลุ่มเล็ก: เมื่อบริษัทที่นำมาคำนวณน้อยกว่า 10 ราย (หลังบ้านคืนเหตุผล `TOO_FEW_COMPANIES`) ไม่แบ่งกลุ่ม ไม่ใช้คำว่า “20% แรก” ไม่วาดแถบสองกลุ่ม และไม่มีกลุ่ม 80% เพราะ K จะเป็น 1 หรือ 2 บริษัท ซึ่งคิดเป็น 22–100% ของฐาน ให้แสดงอันดับบริษัทตามยอดรับสุทธิในเดือน และข้อความ “บริษัทน้อยเกินไปสำหรับการแบ่งกลุ่ม”; ตัวกรอง “กลุ่มลูกค้าตามยอดจ่าย” ของรายชื่อใช้ไม่ได้และบอกเหตุผลเดียวกัน
- จำนวน “จ่ายมากกว่ายอดคืนในเดือน” ต่างจาก “ชำระในเดือน” (N03) และ “เคยชำระเงิน” (N04) ได้โดยชอบ (ข้อมูลตัวอย่าง: 58 / 59 / 61) และต้องมีบรรทัดอธิบายที่มองเห็นเสมอตามสเปกหน้าจอ §4.2
- ข้อมูลเงินของเดือนยังอ่านไม่ครบ (หลังบ้านคืนเหตุผล `BILLING_SCAN_NOT_COMPLETE`): แสดง “ข้อมูลการรับเงินยังไม่ครบ จึงยังจัดอันดับทั้งหมดไม่ได้” ไม่มีกลุ่มและไม่มีอันดับที่อาจเปลี่ยน
- การต่ออายุ/ส่วนเสริมรวมตาม net cash; sales credit และต้นทุนไม่ใช่ยอดจ่าย ไม่รวม currency ต่างกันโดยไม่กำหนด policy

## 6. สัญญาข้อมูล

เอกสารนี้ไม่เขียนรายการ parameter หรือชื่อช่องของตัวเอง สัญญาชุดเดียวอยู่ที่สเปกหลังบ้าน §12.4 และ §16 และกติกาข้อมูลอยู่ที่ §13.4–§13.6 ข้อเสนอ API ของฉบับก่อน (รวมค่า `sort=RECEIPTS_DESC` และ cursor) ถูกแทนด้วยสัญญานั้นแล้ว
ตารางนี้บอกเพียงว่าสิ่งที่หน้าจอแสดงตาม §3–§5 มาจากส่วนใดของสัญญา:

| สิ่งที่หน้าจอแสดง | มาจาก |
|---|---|
