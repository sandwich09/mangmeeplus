## 1. เป้าหมายและขอบเขตที่ผู้ใช้ยืนยัน

ผู้บริหารของ **แพลตฟอร์มมั่งมี** ต้องดูภาพรวมธุรกิจ ดูบริษัทลูกค้าแยกเป็นรายบริษัท
และเปรียบเทียบกลุ่มบริษัทได้ โดยต้องเห็นทั้ง **รู้จักมั่งมีจากไหน** และ **เซลล์ผู้แนะนำ**
ฟีเจอร์คำขอลบข้อมูลพักไว้และซ่อนทั้งหมดตามมติล่าสุด

เส้นทางหลัก: ภาพรวม → เลือกกลุ่มธุรกิจ/ช่องทาง/เซลล์ → รายชื่อบริษัท → รายละเอียดบริษัท
→ ประวัติบริษัท โดยกลับมาที่ตัวกรองเดิมได้

ข้อกำหนดเพิ่มเติมจากผู้ใช้: **ใช้ธีมเดิมทั้งหน้า โดยเฉพาะ dropdown และ input ทุกชนิดห้ามหลุดธีม**
รอบนี้ส่งมอบเอกสารและเดโม v2 โดย reuse controls/theme ของ repo ไม่เปลี่ยน application code
ผู้ใช้ปัจจุบันคือ Owner และผู้บริหารรวม 4 คน ต้องมีหน้าสร้างบัญชีใน admin console
จำนวน 4 คนไม่ใช่เพดานบัญชี และไม่ใช่การให้สิทธิ์ System Admin แก่ทุกคน

## 2. Source of truth และลำดับการอ้างอิง

1. สเปกนี้: โครงหน้าจอ ข้อมูลที่ต้องสื่อ พฤติกรรมการใช้งาน และเกณฑ์ตรวจรับหน้าจอ
2. [Mangmee System UI Alignment](mangmee-system-ui-alignment-spec.md),
   [Web Frontend Code Style](../guidelines/web-frontend-code-style.md) และ shared components ปัจจุบัน:
   สี ฟอนต์ shell controls และ responsive behavior
3. [Admin company onboarding](admin-company-onboarding-spec.md): ขอบเขตข้อมูลระดับแพลตฟอร์ม
4. [Company data lifecycle P31](mangmee-company-data-lifecycle-deletion-spec-th.md)
   และ [Data rights runbook](../runbooks/user-company-data-rights.md): นโยบายและการดำเนินการกับข้อมูล
5. เดโมในแชต: ตัวอย่างโครงข้อมูลและ journey เท่านั้น ดูที่อยู่ไฟล์และหลักฐานทดสอบใน task memory

**ธีมระบบจริงมีลำดับเหนือเดโม** v2 bundle shared fields/cards/buttons, CSS tokens และฟอนต์จริง
มีเฉพาะ shell geometry แบบ preview; ไม่คัดลอก shell แทน `SystemHeader` เมื่อ implement application
เดโม v1 ที่ใช้ sidebar เขียวเข้ม/Noto Sans Thai/native select/dark appearance ถูกแทนที่แล้ว
จำนวนบริษัท แพ็กเกจ ชื่อเซลล์ ยอดเงิน และสูตร/ค่ารายงานในเดโมเป็นข้อมูลสมมติ
ส่วน **คงข้อมูลทั้งหมด 14 วันก่อนลบจริง** เป็นมติ Owner รอบหลังตาม backend draft B8
เดโม v2 ไม่ใช้เกณฑ์ไม่ใช้งาน 14 วันของ v1 แล้ว แต่แสดงกลุ่ม paid usage ตาม B3

## 4. โครงสร้างร่วมและตัวกรอง

ลำดับหน้า: breadcrumb/ชื่อหน้า → คำอธิบายสั้น → ตัวกรอง → เวลาของข้อมูล → เนื้อหา
ใช้ `MangmeePage` และให้มี primary action เฉพาะเมื่อมีงานหลักของหน้านั้น

| ตัวควบคุม | การแสดงผล | Shared component |
|---|---|---|
| เดือนรายงาน | ชื่อเดือน/ปีตาม locale; ค่าเดือนภายในไม่ใช้ข้อความแสดงผลเป็นรหัส | `ThemedDate` `mode="month"` |
| ประเภทธุรกิจ | ทุกธุรกิจ + กลุ่มที่เลือกได้ + ยังไม่ระบุ | `SelectField` |
| รู้จักมั่งมีจากไหน | ทุกช่องทาง + ช่องทางที่มีข้อมูล + ยังไม่ระบุ | `SelectField` |
| เซลล์ผู้แนะนำ | ทั้งหมด + ชื่อพร้อมรหัสเซลล์ + ไม่มีเซลล์ผู้แนะนำ + ยังไม่ระบุ | `SelectField` `searchable` |
| รูปแบบกิจการ | ทั้งหมด / บริษัทจำกัด / ห้างหุ้นส่วน / บุคคลธรรมดา / อื่น ๆ ตามข้อมูลจริง | `SelectField` |
| ค้นหาบริษัท | ชื่อบริษัท/ชื่อร้าน รหัสบริษัท หรือจังหวัด | `TextField` `type="search"` |
| บริษัทในคำร้อง (DEFERRED) | ชื่อ + รหัส เพื่อแยกชื่อซ้ำ; ค้นหาได้ | `SelectField` `searchable` |
| อ้างอิงคำร้อง/ผู้ติดต่อ (DEFERRED) | label, hint และ error ใต้ช่อง | `TextField` |
| เหตุผล/ขอบเขตคำร้อง (DEFERRED) | ข้อความหลายบรรทัด | `TextareaField` |

- EX-01/02/03 ใช้เดือน ประเภทธุรกิจ ช่องทางที่รู้จัก และเซลล์ร่วมกัน
- รูปแบบกิจการและคำค้นเป็นตัวกรองใน EX-02; แสดงเงื่อนไขที่ใช้อยู่ให้ชัด
- EX-04 แสดงเดือนรายงานและบริษัทที่กำลังดู; ไม่ทิ้งตัวกรองรวมที่ไม่ส่งผลกับรายละเอียดไว้บนหน้า
- การเลือกตัวกรองเปลี่ยนข้อมูลในบริบทเดียวกัน; แสดง pending ระหว่างอ่านข้อมูล ไม่แสดงยอดเก่าภายใต้ label ใหม่
- เปลี่ยนตัวกรองแล้วกลับหน้าแรกของรายการ; กดกลับจากบริษัทหรือ browser Back ต้องได้ตัวกรอง/คำค้น/ตำแหน่งรายการเดิม
- มี “ล้างตัวกรอง” เมื่อมีเงื่อนไขเพิ่มเติม; เก็บเดือนที่เลือกไว้ และล้างกลุ่ม/ช่องทาง/เซลล์/ชนิดกิจการ/คำค้น
- หัวตาราง กราฟ KPI และจำนวนรายการต้องสื่อขอบเขตเดียวกัน จำนวนรวมไม่ใช่จำนวนเฉพาะหน้าของ pagination
- แสดง “ข้อมูลถึง …” หรือ “ปรับปรุงล่าสุด …” ตามความหมายจริง; วันที่สมัคร/ข้อมูลบริษัทปัจจุบันต้องแยกจาก metric ตามเดือน

## 5. EX-01 — ภาพรวมธุรกิจ

1. ชื่อ “ภาพรวมธุรกิจมั่งมี” และทางไป “ดูบริษัท”
2. ตัวกรองร่วมตาม §4
3. KPI: บริษัทในระบบ, บริษัทที่ใช้งาน, บริษัทที่ชำระเงิน, ยอดรับสุทธิ
4. กราฟแนวโน้มยอดรับของมั่งมี พร้อมหน่วย บาท ช่วงเวลา และชื่อกลุ่มที่กำลังดู
5. จำนวนบริษัทแยกประเภทธุรกิจ กดกลุ่มเพื่อไป EX-02 พร้อมเงื่อนไขนั้น
6. “บริษัทที่ควรติดตาม” แสดงบริษัท สถานะบริการ เหตุผล และทางไปบริษัท
7. กล่อง “ชำระเงินแล้ว ใช้งานเป็นอย่างไร” แยกจ่ายแล้ว ยังไม่เริ่มใช้ / เคยใช้แต่ไม่ใช้ในช่วงนี้ /
   ใช้งานในช่วงนี้ และกดดูรายชื่อแต่ละกลุ่มได้ ไม่แยกกลุ่มรอเปิดบริการ
   ถ้าข้อมูลไม่พอ ให้หมายเหตุ “ยังประเมินการใช้งานไม่ได้ … บริษัท” แยกจากกลุ่มธุรกิจ

KPI ต้องมีคำอธิบายสั้นว่าเป็นจำนวนสะสมหรือกิจกรรมในช่วงรายงาน สูตรและขอบเขตของแต่ละ metric
ใช้มติ B2–B4: รวมบริษัทจริงทุกสถานะ แยกกรองได้ ไม่รวมทดสอบ/ภายใน; หนึ่งพื้นที่บริษัทนับหนึ่งบริษัท
การใช้งานนับฟีเจอร์จริง แยกจาก login; ยอดรับคือเงินรับจากแพ็กเกจ ต่ออายุ และส่วนเสริมหักคืนเงิน
ค่าธรรมเนียม/ต้นทุนแสดงแยก ไม่ใช้ยอดขาย/กำไรของบริษัทลูกค้ามาแสดงเป็นรายได้ของมั่งมี
รายละเอียด event, cutoff, refund และแหล่งยืนยัน test/internal ยังรอ backend contract
รายการติดตามแสดงเหตุผลจากข้อมูลจริง; ไม่สร้างคะแนนสุขภาพหรือเกณฑ์น้อย/กลาง/มากขึ้นเอง

## 6. EX-02 — บริษัทลูกค้า

ตารางตั้งต้นเรียงข้อมูลดังนี้:

| คอลัมน์ | ข้อมูล |
|---|---|
| บริษัท / จังหวัด | ชื่อร้านหรือชื่อบริษัท, รหัสบริษัท, จังหวัด; ชื่อเป็นลิงก์เปิด EX-04 |
| ธุรกิจ / รูปแบบกิจการ | ประเภทธุรกิจและรูปแบบนิติบุคคลเป็นคนละค่า |
| รู้จักจาก / เซลล์ผู้แนะนำ | ช่องทางที่รู้จัก, ชื่อเซลล์หรือสถานะไม่มี/ยังไม่ระบุ |
| แพ็กเกจ | ชื่อแพ็กเกจจริงที่อ่านได้ ไม่ตีความข้อมูลที่ขาดเป็นแพ็กเกจฟรี |
| สถานะบริการ | badge พร้อมข้อความ; ไม่ใช้สีอย่างเดียว |
| ชำระเงิน / การใช้งาน | แสดงแยกสองมิติ เช่น ชำระแล้ว · ยังไม่เริ่มใช้; ข้อมูลไม่ครบต้องไม่กลายเป็นไม่ใช้ |
| ปริมาณใช้งานในช่วง | วันใช้งาน, ผู้ใช้ที่ใช้งาน, เอกสาร/AI ที่นับได้; detail แสดงรายการเต็ม |
| ใช้งานล่าสุด | วันที่/เวลา พร้อมบริบท as-of; ไม่เรียกวันสิ้นเดือนเก่าว่า “วันนี้” |
| ยอดรับสุทธิในเดือน | จัดชิดขวา หน่วยบาท และทศนิยมตาม formatter กลาง |

- แสดงจำนวนที่ตรงเงื่อนไขและ pagination ตาม pattern เดิม รายงานรวมต้องไม่เปลี่ยนเพียงเพราะเปลี่ยนหน้า
- แยกสถานะบริการออกจากกิจกรรมใช้งาน เช่น หมดอายุแต่เคยมีการใช้งานในเดือนนั้น
- มีตัวกรองสถานะบริษัทและกลุ่ม paid usage; ไม่แทนการเคยชำระด้วยยอดรับเฉพาะเดือน
- ไม่เพิ่มปุ่มลบข้อมูลในแต่ละแถวหรือ bulk delete
- Mobile เก็บชื่อบริษัท รหัส และลิงก์เข้า detail ให้อ่านได้; ตารางเลื่อนเฉพาะภายใน `mangmee-table-scroll`
  หรือใช้รูปแบบรายการมือถือเดิมเมื่อเหมาะสม ห้ามทำทั้งหน้าเลื่อนแนวนอน

## 8. EX-04 — รายละเอียดบริษัท

ส่วนหัวแสดงชื่อ รหัส ประเภทธุรกิจ จังหวัด และปุ่มกลับรายการ; KPI ตามเดือน
ประกอบด้วยยอดรับสุทธิ เอกสาร การใช้ AI และจำนวนสมาชิก โดยแต่ละค่าระบุช่วงเวลา/ปัจจุบันให้ตรงความหมาย

### 8.1 แท็บข้อมูลบริษัท

เรียงกล่องตามนี้:

1. **รู้จักมั่งมีได้อย่างไร**: ช่องทางที่รู้จัก, รายละเอียดช่องทาง/แคมเปญเมื่อมี,
   เซลล์ผู้แนะนำชื่อ+รหัส, หลักฐานหรืออ้างอิงการแนะนำที่มีสิทธิ์ดู
   และเซลล์ที่ได้เครดิตยอดเปิดบริษัทแยกอีกช่องตามข้อมูลจริง
2. **ข้อมูลบริษัท**: รหัส, รูปแบบกิจการ, ประเภทธุรกิจ, จังหวัด, สาขา, สมาชิก,
   ผู้ติดต่อหลักตามสิทธิ์, วันที่สมัคร
3. **การใช้บริการมั่งมี**: แพ็กเกจ, วันสิ้นสุดบริการ, วิธีสมัคร, ใช้งานล่าสุด,
   จำนวนคำร้องที่เกี่ยวข้อง และทีมดูแลปัจจุบัน
4. ข้อมูลที่ควรติดตามและทางไปแท็บการใช้งาน ถ้ามีเหตุผลจากข้อมูลจริง

ความหมายที่ต้องแยกชัดเจน:

- **รู้จักจากไหน**: ใช้ตัวเลือก/label จาก `SIGNUP_DISCOVERY_SOURCE_OPTIONS` เดิม:
  Website, IG, TikTok, Facebook, เซลล์ของมั่งมี, อื่น ๆ; ค่าที่ขาดแสดงยังไม่ระบุ
  รายละเอียดเช่น Google/LINE/อีเวนต์/ลูกค้าแนะนำแสดงใต้ “อื่น ๆ” เมื่อมีข้อมูลจริง
  ไม่เพิ่มเป็น enum ช่องทางใหม่หรือเดาจากวิธีสมัคร
- **เซลล์ผู้แนะนำ**: บุคคลที่ระบบรับรองว่าแนะนำบริษัทนี้; ชื่อซ้ำต้องแยกด้วยรหัส
- **วิธีสมัคร**: สมัครเองหรือผ่านกระบวนการอื่น ไม่ใช่คำตอบแทนช่องทางที่รู้จัก
- **ผู้ดูแลปัจจุบัน**: อาจเป็นคนละคนกับผู้แนะนำเดิม ห้าม UI ใช้แทนกัน
- **ไม่มีเซลล์ผู้แนะนำ**: มีข้อมูลยืนยันว่าไม่มี; **ยังไม่ระบุ**: ข้อมูลขาด/ยังไม่ทราบ

ตามมติ B6 แสดงที่มาตาม flow เดิม เช่น “เซลล์ของมั่งมี / คุณฟ้า · S003” หรือ “Facebook”
ไม่เพิ่มการกรอกรหัสเซลล์คู่กับช่องทางอื่น; “อื่น ๆ” ยังระบุรายละเอียดได้ตามเดิม
ชื่อผู้ได้เครดิตยอดเปิดบริษัทเป็นอีกความหมายตาม B5 ไม่ใช้เปลี่ยนที่มาของลูกค้า
เดโม v2 แก้ตัวอย่าง Facebook คู่กับเซลล์ของ v1 แล้ว; ไม่ใช้การแก้ fixture นี้เป็นคำสั่งแก้ข้อมูลลูกค้าเก่า
หน้านี้เป็นการอ่าน ไม่เพิ่มแบบฟอร์มแก้ attribution หรือเลือกเซลล์ย้อนหลังในรอบ UI นี้

### 8.2 แท็บการใช้งานและรายรับ

แสดงแนวโน้มยอดรับ จำนวนเอกสาร การใช้ AI ต้นทุนบริการที่วัดได้ ยอดรับ ยอดคืนเงิน
และใช้งานล่าสุดในช่วงที่เลือก ไม่เปิดเอกสาร/บทสนทนา/ข้อมูลธุรกรรมของ tenant ผ่านรายงานนี้
แสดงวันชำระ วันพร้อมใช้บริการ วันที่ใช้ฟีเจอร์ครั้งแรก/ล่าสุดเท่าที่มี และ login ล่าสุดแยกกัน
ปริมาณใช้แสดงจำนวนวัน จำนวนผู้ใช้ เอกสาร และ AI พร้อมหน่วย; แยกเคยจ่าย/จ่ายในช่วง/สิทธิ์ปัจจุบัน
ถ้าไม่มีข้อมูลกิจกรรมย้อนหลังเพียงพอ ให้บอกว่า “ยังประเมินการใช้งานไม่ได้” ไม่จัดเป็น “จ่ายแล้วไม่ใช้”
เดือนก่อนวันที่สมัครแสดง “บริษัทนี้ยังไม่สมัครในช่วงรายงานนี้” ไม่สร้างกิจกรรมเป็นศูนย์ที่ชวนให้เข้าใจผิด

### 8.3 แท็บประวัติบริษัท

แสดง timeline การสมัครและเหตุการณ์บริการที่ได้รับอนุญาต
ซ่อนรายการคำร้อง เลขเคส ลิงก์รายละเอียด และปุ่มสร้างคำขอ; ไม่ query ข้อมูลคำร้องในรุ่นนี้
การเปิดแท็บหรือดูประวัติต้องไม่สร้าง mutation ใด ๆ

## 9. EX-05/06 — คำขอเกี่ยวกับข้อมูล (DEFERRED ถึงก่อน §9.2)

- ใช้เคสเดิมของ `system-data-rights` ไม่สร้างทะเบียนคำร้องคู่ขนาน
- แสดงบริษัทด้วยชื่อ+รหัส ขอบเขตที่ขอ วันที่รับ ผู้รับผิดชอบถ้ามี และสถานะที่มาจากระบบจริง
- การรับคำร้องทางอีเมลต้องมีผู้ร้อง/อ้างอิง เป้าหมาย ขอบเขต และข้อมูลที่ contract เดิมกำหนด
  ฟอร์มสั้นในเดโมไม่ใช่การอนุมัติให้ตัด required fields หรือ validation เดิม
- ถ้ามีบริษัทจากหน้าต้นทาง ให้แสดงบริบทและตรวจเป้าหมายอีกครั้งก่อนส่ง; ไม่ใช้ URL เป็นหลักฐานสิทธิ์
- แยก “บันทึกคำร้อง”, “อนุมัติคำร้อง” และ “ดำเนินการลบ” เป็นคนละขั้น ห้ามแสดงว่าลบแล้วหลังรับคำร้อง
- หน้ารายงานไม่ให้สิทธิ์ `system.data_rights.manage`; แสดง action เฉพาะเมื่อมีสิทธิ์และสถานะรองรับจริง
- ยึดมติใหม่ B8 และ P31 ฉบับปรับปรุง: สร้างคำขอ → อนุมัติ → คงข้อมูลทั้งหมด 14 วัน → ลบจริง
  หลังลบเหลือเฉพาะข้อมูลที่มีฐานเก็บรักษาตามกฎหมายที่ผ่านการพิจารณา

### 9.1 โครงรายการและรายละเอียดคำขอลบ (DEFERRED)

- รายการแสดงเลขคำร้อง บริษัท ผู้ร้อง วันที่รับ สถานะ วันที่อนุมัติ และกำหนดครบช่วงรอเมื่อคำนวณได้
- รายละเอียดเรียง: บริษัท/ผู้ร้อง → ขอบเขต → ผลตรวจสอบ/อนุมัติ → ช่วงคงข้อมูล → ผลดำเนินการ/หลักฐาน
- ช่วงคงข้อมูลแสดงข้อความ “ข้อมูลทั้งหมดอยู่ระหว่างคงไว้ 14 วันก่อนลบจริง” พร้อมวันที่เริ่ม/ครบกำหนด
  และเวลาคงเหลือจาก server; ถ้ายังไม่มีกฎหรือ timestamp ที่ยืนยัน ให้แสดง “ยังไม่กำหนด” ไม่เริ่มนับจาก browser
- ครบกำหนดแสดง “ครบช่วงรอ” แยกจาก “ลบสำเร็จ”; action ดำเนินการต้องผ่านสิทธิ์และเงื่อนไขหลังบ้าน
- ผลลัพธ์แยกข้อมูลที่ลบ / ข้อมูลที่เก็บต่อพร้อมเหตุผลและกำหนด / งานที่ยังไม่สำเร็จ
  ห้ามขึ้น “ลบทั้งหมดแล้ว” หากยังมีข้อยกเว้นหรือหลักฐานไม่ครบ
- ไม่มีปุ่มลบทันทีข้าม 14 วันในโครงใหม่; การยกเลิกคำร้อง การระงับการใช้งาน และ auto/manual execution
  รอคุยรายละเอียด ไม่กำหนดจากชื่อสถานะหน้าจอ
- เก็บข้อเสนอไว้ในเอกสาร แต่ซ่อน mock states และทุกทางเข้าบนเดโม; ไม่เชื่อม executor

### 9.2 EX-07/08 — บัญชีผู้บริหารใน admin console

**EX-07 รายการ:** ชื่อหน้า “บัญชีผู้บริหาร” → ค้นหาชื่อ/อีเมลและกรองสถานะ → ปุ่ม “เพิ่มผู้บริหาร”
→ ตารางชื่อ อีเมล บทบาท/สิทธิ์ สถานะ และเข้าใช้ล่าสุด → เปิดรายละเอียดบัญชี
ใช้สถานะบัญชีที่ระบบรองรับจริง ไม่สร้างตัวเลขผู้ใช้ 4 คนเป็น fixture ใน application

**EX-08 สร้าง:** breadcrumb → ชื่อและอีเมล (`TextField`) → บทบาท/ชุดสิทธิ์ (`SelectField`)
→ สรุปสิทธิ์ที่จะได้รับ → บันทึก/ยกเลิก; ตั้งต้นเป็นอ่านรายงานผู้บริหาร โดยผู้สร้างให้ได้เฉพาะสิทธิ์ที่ตนจัดการได้
วิธีเปิดใช้งาน/เชิญ/ตั้ง credential รอข้อสรุปจากระบบ identity เดิม ไม่สร้างช่องรหัสผ่านหรือส่งอีเมลโดยเดา

**EX-08 รายละเอียด:** ข้อมูลบัญชีและสิทธิ์ → สถานะ/ประวัติการเปลี่ยนที่มีสิทธิ์ดู → action แก้ไขหรือระงับ
ตาม contract ที่ตกลง; ข้อจำกัดการแก้สิทธิ์ตัวเอง/บัญชีผู้ดูแลคนสุดท้ายและ session revocation รอหลังบ้าน

- ผู้ดูรายงานทั่วไปไม่เห็น action จัดการบัญชี; API ต้องตรวจสิทธิ์ซ้ำเมื่อเชื่อมจริง
- ไม่เพิ่มสมาชิกในบริษัทลูกค้าทุกแห่ง และไม่ให้สิทธิ์อนุมัติ/ลบข้อมูลติดมากับบทบาทผู้บริหาร
- ฟอร์มต้องรองรับอีเมลผิดรูปแบบ/บัญชีซ้ำ/สิทธิ์ไม่พอ/pending/error พร้อมรักษาค่าที่กรอก
  กรณีอีเมลเป็นบัญชีเดิมต้องตกลงว่าจะเพิ่มสิทธิ์ให้ตัวตนเดิมอย่างไร ไม่สร้าง user ซ้ำเงียบ ๆ
- ฟิลด์ ปุ่ม dropdown รวมรายการสิทธิ์ ใช้ theme contract §10 เช่นเดียวกับรายงาน

| Dropdown | `SelectField` ซึ่งใช้ `ThemedSelect`; ใช้ `ThemedSelect` โดยตรงเมื่อ wrapper ไม่เหมาะกับโครงเดิม |
| เดือน / วันที่ | `ThemedDate` โดยมี label และ ARIA; ฟอร์มที่ต้องใช้เวลาให้ reuse pattern ที่รองรับเวลาจริง |
| ตาราง | `mangmee-table`, `mangmee-table-scroll`, pagination เดิม |
| Popover / modal | `PopoverPanel`, shared `Modal` และ hook ปิดเมนูเดิม |
| Loading / empty / error / denied | `CoverLoader`, `LoadingState`, `EmptyState`, `ErrorState`, `ForbiddenState` |

ใช้ธีม light ตามระบบปัจจุบัน แม้อุปกรณ์ตั้ง dark mode; ไม่มี dark theme ใหม่ใน scope นี้
สีตัวเลข กราฟ และ legend ใช้ design tokens; ไม่เพิ่ม blue/indigo/sky เป็นสีหลักของ interaction
feature CSS ใช้เฉพาะ layout และ token ไม่ประกาศ palette/font/reset สำหรับหน้าเอง

### 10.2 Dropdown ต้องเข้าธีมทั้งปิดและเปิด

- **ห้าม rendered native `<select>` ใหม่ในหน้าชุดนี้**; การตกแต่งกรอบ select อย่างเดียวไม่ทำให้ popup ของ OS เข้าธีม
- ใช้ `SelectField`/`ThemedSelect` ทั้ง filter toolbar, search form, company picker และฟอร์มคำร้อง
- ชุดเมนูที่เปิดต้องคุมพื้นหลัง ขอบ shadow สีข้อความ hover focus selected checkmark และ disabled option
  รวมถึงช่องค้นหาภายในเมนู ไม่มีส่วนใดกลับไปใช้ฟอนต์หรือสี browser default
- ใช้ portal ของ `PopoverPanel` เดิม ไม่แก้ด้วย z-index สูงเฉพาะหน้า หรือย้าย popover กลับเข้า container ที่ clip
- เมนูไม่ถูก table/card/modal ตัด ไม่ล้นขอบจอ เลื่อนตาม anchor ถูก และวางเหนือ/ใต้ตามพื้นที่
- คลิกเลือกแล้วปิด, กด trigger ซ้ำแล้วปิด, กดนอกเมนูแล้วปิด, Escape แล้วปิด
  กดอีก dropdown ต้องใช้งานต่อได้โดยไม่ต้องกดซ้ำ
- Keyboard ใช้งานได้: เปิดด้วยคีย์บอร์ด เลื่อนตัวเลือก เลือก กลับ focus ที่ trigger;
  ค้นหาแล้วไม่พบแสดงข้อความในเมนู และรายการ disabled เลือกไม่ได้
- label ยาวไม่ชน chevron; ชื่อเซลล์/บริษัทยาวต้องยังตรวจตัวตนได้ในรายการที่เปิด

### 10.3 Text input และ textarea ทุกตำแหน่ง

- ห้าม visible `<input>`/`<textarea>` ที่เขียน style เฉพาะหน้าแทน shared fields;
  hidden inputs และ internal search ของ shared components ใช้ implementation กลางต่อได้
- default, hover, focus, filled, placeholder, disabled, readonly, error และ browser autofill ต้องยังอ่านได้และใช้ธีมระบบ
- label อยู่เหนือช่อง; hint/error ผูก `aria-describedby`; error มีข้อความและ `aria-invalid` ไม่พึ่งสีอย่างเดียว
- readonly ยังเลือก/คัดลอกได้เมื่อเหมาะสม; disabled ต้องดูและทำงานเป็น disabled ไม่สว่างเหมือนคลิกได้
- ป้องกันข้อความชนไอคอนโดยใช้ spacing ของ component; กรณี raw shared `.mangmee-input`
  ที่มีไอคอนท้ายใช้ `.mangmee-input-icon-end` ตาม implementation เดิม
- ใช้ขนาดจาก shared fields: controls หลักอย่างน้อย 44px บน mobile, 40px desktop ตาม breakpoint เดิม;
  ข้อความกรอกบนมือถืออย่างน้อย 16px ตาม global rule เพื่อไม่ให้ iOS ซูมเมื่อ focus
- ไม่ใช้ inline hex/font/ring override เพื่อแก้เพียงบางช่อง ไม่ใช้ native date/month popup เป็นทางลัด
- ถ้า component กลางมีปัญหา ให้แก้ที่ common layer แบบ scoped พร้อม check ไม่ทำสำเนา component เฉพาะรายงาน

### 10.4 ข้อสังเกตจาก code audit ณ วันที่เขียน

`SelectField` มี `ThemedSelect` และ searchable menu อยู่แล้ว; `ThemedDate` รองรับเดือน
จึงไม่ต้องสร้าง dropdown/date picker ใหม่หรือเพิ่ม dependency
`TextField`/`TextareaField` และ `.mangmee-input` มีรายละเอียด CSS คนละทางบางส่วน
ต้องเลือก wrapper ให้สอดคล้องใน form เดียวกัน และตรวจ computed style จริง โดยไม่เติม class ทับแบบเดา

หน้า `DataRightsNewPage.tsx` เดิมยังมี local `inputClass`, native datetime และสีบางค่าที่กำหนดเอง
การ reuse flow นี้ **ไม่ได้แปลว่ารับรอง style เดิมทั้งหมด**; หากปรับหน้าคำร้องในงานนี้ต้องนำ controls ที่แตะ
เข้าสู่ theme contract ข้างต้น โดยรักษา field semantics/validation/permission เดิม
ไม่ขยายงานเป็นการเปลี่ยนธีมทั้งระบบ

## 11. สถานะและ responsive behavior

| สถานะ | สิ่งที่ผู้ใช้ต้องเห็น |
|---|---|
| Initial loading | loading ของ shell/page ที่เกี่ยวข้อง ไม่มีเลข 0 ชั่วคราว |
| เปลี่ยน filter / หน้า / refresh | `CoverLoader` คลุม scope ที่อ่านใหม่; ป้องกันกดซ้ำและข้อมูล response เก่าทับตัวกรองใหม่ |
| ไม่มีข้อมูลจริง | empty state ของช่วง/กลุ่มนั้น; จำนวนศูนย์ใช้ได้เฉพาะที่ทราบว่าศูนย์ |
| ไม่พบจากตัวกรอง | แสดงเงื่อนไขและทางล้างตัวกรอง |
| ข้อมูลขาด | `—` พร้อมคำอธิบาย “ยังไม่มีข้อมูล”/“ยังไม่ระบุ”; ไม่แทนด้วย 0 |
| Partial error | แจ้งส่วนที่อ่านไม่ได้ ไม่ทำให้ส่วนที่สำเร็จกลายเป็นศูนย์; ข้อมูลเก่าที่คงไว้ต้องติดเวลา/สถานะ |
| ไม่มีสิทธิ์ / สิทธิ์ถูกถอน | shared forbidden state และล้างข้อมูลที่ไม่ควรเห็น; ไม่ใช้ข้อมูลเก่าค้าง |
| บริษัทไม่พบ | not-found state พร้อมกลับรายชื่อ; ไม่เผยข้อมูลบริษัทอื่น |
| เดือนก่อนสมัคร | ข้อความเฉพาะเหตุผล ไม่แสดงกิจกรรมที่แต่งขึ้น |
| ส่งคำร้อง | pending บนฟอร์ม ป้องกันส่งซ้ำ; error แล้วข้อมูลที่กรอกยังอยู่; success หลังผลยืนยันจริง |

ทดสอบที่ 1440, 1024, 768, 390 และ 320px; ตัวกรอง wrap/stack ได้ ไม่มี horizontal overflow ของหน้า
ตารางอาจเลื่อนภายในพื้นที่ของตัวเอง KPI ลดคอลัมน์ตามพื้นที่ modal/popover ไม่ซ่อน action
ทดสอบ browser zoom 200%, label ไทยยาว, keyboard-only และอุปกรณ์ที่ตั้ง dark mode
ข้อความผู้ใช้มีภาษาไทยและอังกฤษผ่าน dictionary เดิม ไม่ฝัง string ใหม่กระจายใน JSX

- [ ] ไม่มี fake data/success ใน production; สิทธิ์อ่านรายงานไม่กลายเป็นสิทธิ์แก้บริษัท/ลบข้อมูล
