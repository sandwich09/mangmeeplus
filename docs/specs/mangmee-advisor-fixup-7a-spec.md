# Advisor fix-up 7A

Goal: a LINE expense owner can choose evidence on the first ask, read a multi-page PDF without retrying ordinary intermediate pages, receive a failed-read result, and confirm/pay with fewer presses. Existing tenant, branch, permission, source revision, evidence and final-mutation guards remain authoritative.

## Required sequences and acceptance

- Z1: resolve the active draft → interrupt/park it (which commits a new expense revision) → call gateway tools → prepare evidence/category/action choices against that revision → persist the turn → validate and deliver the choices/card. Never interrupt after a tool has prepared a revision-bound card. A later content edit must still invalidate it.
  Previously: `expense.action.preview` stored choices at R0 → `interruptExpenseDraft` → `interruptOpen` / `persist` committed R1 → `evidenceChoice` compared R0 to R1 → `repairChoices` returned null. Now interruption commits R1 before the gateway calls `expense.action.preview`; preparation and delivery both observe R1. A subsequent web/content edit to R2 still fails the unchanged revision check.
- Z2: provider `max_tokens` / `output_limit`, an incomplete JSON envelope, or actual local text clipping can mark output truncated. A model's narrative `partial` reason alone cannot. Missing totals on an intermediate PDF page are normal; totals must be transcribed only where printed. The supplied `trace-g.jsonl` records gateway turns, not raw capture-read provider outputs; the owner-recorded reason `cut off; no totals block` is replayed explicitly in the registered capture route spec, with a normal provider stop and a later page containing totals.
- Z3: each claimed read attempt has a distinct finished-event dedupe identity. A previously published PARTIAL result cannot swallow a later FAILED/attempts_exhausted event. LINE delivery rechecks the source owner, channel, membership, branch and permissions, then pushes one short failure sentence with a web button. Retries of the same event reuse its delivery identity; a new result gets a new identity.
  Root cause: the runner used `requestId = jobId` on every finish; OutboxAppendService keys on event type + aggregate + requestId, so the initial PARTIAL row swallowed later FAILED appends. The requestId is now `jobId:attempts`, while jobId/expenseId remain the unchanged source identifiers. Legacy push retry identity also uses this result requestId instead of the expense/group alone.
- Z4: a prepared expense confirmation/payment is one Flex message with altText. Payment previews show payment status (including partial payments), rather than repeating expense confirmation status. When category is the only structured missing source field, selection dry-runs the existing category edit and all confirmation validators, then presents one signed confirmation card containing that category. No committed edit precedes the signed press. That press applies the category through UpdateExpenseDraftUseCase, then MarkExpenseReadyUseCase when needed, the existing evidence review save when needed, and ConfirmExpenseUseCase, carrying each committed revision forward. A stale/archived category or changed source/permission blocks the chain. Other incomplete repairs retain the existing edit flow.

## Implementation plan

1. Move interruption before gateway execution; cover the exact first-ask sequence and single-card delivery in the registered webhook spec.
2. Separate narrative partial reasons from output truncation and cover provider limits, incomplete JSON, and ordinary intermediate pages in the registered gateway capture routes spec.
3. Give finished results attempt-scoped event/delivery identities and reuse the existing text-card builder for failure notices; cover PARTIAL → FAILED and delivery retries in registered runner/notifier specs.
4. Compose category preview and confirmation using the existing category projection and rolled-back web update pattern. Extend registered security specs for ordered use-case calls, replay and stale/permission rejection. No dependencies or feature switches.
5. Build contracts; run API/gateway typecheck scripts, full gateway/contracts registered suites, and all registered API specs importing changed implementations. Record results in task memory and last-message.md.
