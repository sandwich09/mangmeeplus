## มติล่าสุด: ใช้ไฟล์ Dashboard v4 เป็นแม่แบบ

Owner ระบุ `company-receipts-dashboard-v4.xlsx` (ไฟล์อ้างอิงในเครื่องของ Owner; ไม่แนบข้อมูลบริษัทจริงเข้า repository) เป็นรูปแบบ Export ที่ต้องการ
มตินี้แทนตัวเลือก summary-only/optional company sheet และข้อเสนอ values-only ในฉบับก่อน: ค่าเริ่มต้นเป็น **Excel Dashboard พร้อมกราฟจริง สูตร และข้อมูลต้นทาง**
สองชีตหลัก **ภาพรวม** และ **รายบริษัท** ตามแม่แบบ; ตารางคำนวณอยู่ใต้ Dashboard และเงื่อนไขอยู่ในหัวข้อมูลต้นทาง ไม่เพิ่มชีตเทคนิคหลายแท็บ
แม่แบบกำหนด layout/สี/โครงสูตร ไม่ใช่แหล่งตัวเลขสำหรับเดือนใหม่; ไม่แก้หรือเขียนทับไฟล์อ้างอิง
แม่แบบที่เก็บใน repository ต้องสร้างใหม่จากข้อมูลสมมติ ไม่ใช่ไฟล์ของ Owner ที่ตัดแถวออก ตาม §8 (RB-27)

## 1. เป้าหมายและขอบเขต

ผู้บริหารนำสิ่งที่กำลังวิเคราะห์ไปประชุมหรือวิเคราะห์ต่อได้ โดยจำนวนบริษัท ยอดเงิน สูตร ฐาน และเงื่อนไขตรงหน้าจอ
เพิ่มปุ่ม **ส่งออก Excel** ที่หัวของหน้ารายงานและรายละเอียดบริษัท สำหรับผู้มีสิทธิ์ตาม §6 ไม่เพิ่มเมนูหลักหรือหน้าตั้งค่ารายงานอีกชุด
ไม่ใส่ในหน้าบัญชีผู้บริหาร ไม่ส่งออกเอกสาร/รูปใบเสร็จ/บทสนทนา/ข้อมูลคำร้องลบ และไม่เพิ่มการส่งอีเมลหรือการตั้งเวลา
รุ่นแรกใช้ `.xlsx`, Dashboard สีเขียว–ทอง, KPI และ native editable Excel charts ผูกกับสูตร/ตารางคำนวณและข้อมูล ณ snapshot; ไม่มี macro/external link/pivot หรือสูตรที่ผู้ใช้ส่งเข้ามา
ส่งออกกราฟเป็น chart object ไม่ใช่ภาพกราฟแปะ; มีตารางตัวเลขที่ใช้วิเคราะห์ต่อได้; การส่งออกรายงานสรุปนี้เข้าขอบเขตใหม่ ส่วนเอกสารธุรกรรมลูกค้าโดยละเอียดยังอยู่นอกขอบเขต

## 2. เส้นทางผู้ใช้

1. เลือกหน้า แท็บ เดือน ตัวกรอง หรือกลุ่มจากกราฟตามปกติ
2. กด “ส่งออก Excel” → เปิดแผงเตรียมไฟล์ในพื้นที่รายงานแทนเนื้อหาเดิม; คงเมนู/ชื่อหน้า ไม่ต่อแผงท้ายหน้าให้ยาวขึ้น; แผงเป็นสถานะใน URL (`export=1` ตามสเปกหน้าจอ §3.2) ปุ่ม Back ของเบราว์เซอร์และปุ่ม “← กลับ<ชื่อรายงาน>” ปิดแผงและคืนรายงานเดิม ไม่ออกจากหน้า
3. แผงแสดงชื่อรายงาน/แท็บ เดือนแบบ “ก.ย. 2569” ข้อมูลถึงเวลาใด เงื่อนไขที่เลือกทั้งหมดด้วยคำเดียวกับหน้าจอ จำนวนบริษัท และข้อความ “ไม่รวมบริษัททดสอบและบริษัทของมั่งมี”
4. ใช้รูปแบบเดียว **Excel Dashboard พร้อมข้อมูลต้นทาง**; ไม่ต้องเลือกระหว่างสรุปกับข้อมูลรายบริษัทอีก เพราะกราฟต้องมีข้อมูลรองรับ
5. ปุ่ม **สร้างไฟล์ Excel** อยู่ถัดจากบรรทัดสรุปของข้อ 3 และต้องเห็นในจอแรกที่ 390×844 โดยไม่ต้องเลื่อน เมื่อปุ่มใช้ไม่ได้ต้องมีเหตุผลเป็นข้อความใกล้ปุ่ม เช่น “ยังไม่มีข้อมูลของเดือนนี้”, “ไม่มีบริษัทตามเงื่อนไข”, “เลือกคนละกลุ่มก่อนส่งออก”
6. ใต้ปุ่มแสดงรายการชีต (ภาพรวม และรายบริษัท) กับรายการหัวคอลัมน์ของชีตรายบริษัทเป็นข้อความที่ตัดบรรทัดได้; **ไม่วาดตัวอย่างไฟล์ด้วยสีของตัวเอง และไม่คำนวณตัวเลขซ้ำบนแผง** เพราะจะเป็นจุดที่สามที่ต้องให้ตัวเลขตรงกับหน้าจอและไฟล์ และขัดกับ theme contract ของสเปกหน้าจอ §10.1 (RU-17)
7. เฉพาะการส่งออกจากรายชื่อบริษัทและรายละเอียดบริษัท และเฉพาะผู้ใช้ที่มีสิทธิ์ดูข้อมูลติดต่อ: มีช่องติ๊ก “รวมข้อมูลติดต่อเจ้าของบัญชี” ค่าเริ่มต้นไม่ติ๊ก พร้อมคำอธิบาย “ไฟล์จะมีอีเมลและเบอร์โทรของเจ้าของร้าน ซึ่งเป็นข้อมูลส่วนบุคคล” (**ข้อเสนอ รอเจ้าของยืนยัน — Q33** ดู §9)
8. กด **สร้างไฟล์ Excel** → preparing → download เมื่อได้ไฟล์สมบูรณ์; กันกดซ้ำ และแสดง “ดาวน์โหลดไฟล์ไม่สำเร็จ กรุณาลองใหม่” หากเบราว์เซอร์ดาวน์โหลดไม่สำเร็จ
9. กลับรายงานแล้วยังคงแท็บ/ตัวกรอง/หน้าเดิม; การเปลี่ยนหน้า/เดือน/สิทธิ์ระหว่างเตรียมยกเลิกผลเก่า ไม่ดาวน์โหลดไฟล์ผิดบริบท

เดโมใช้ปุ่ม **จำลองสร้าง Excel** และระบุชัดว่าไม่ได้สร้างหรือดาวน์โหลดไฟล์จริง; มี ready/error/snapshot-expired ให้ตรวจ flow
ไม่แสดงปุ่มดาวน์โหลดที่ไม่มีไฟล์ ไม่สร้าง CSV แล้วตั้งนามสกุลเป็น xlsx
ใช้ Button/SelectField/theme เดิมทั้งหมด; แผงไม่มีตารางกว้าง มือถือแผงเต็มความกว้าง ไม่มีการเลื่อนแนวนอนทั้งระดับหน้าและภายในแผง
การดาวน์โหลดใช้แบบแผนเดิมของหน้าเว็บ: ดึงไฟล์ด้วย `authedFetch` แล้วตั้งชื่อไฟล์ที่หน้าเว็บ (แบบ `apps/web/src/features/expenses/expenses.api.ts` และ `apps/web/src/common/files/download-artifact.ts`) และต้องตรวจการดาวน์โหลดกับการเปิดไฟล์บน iPhone Safari และ Android Chrome เพราะผู้ใช้ทำงานบนมือถือเป็นหลัก (EXL-18)

## 3. แต่ละหน้าได้อะไร

## 4. โครงสร้างไฟล์และข้อมูล

- ชื่อไฟล์ที่ผู้ใช้ได้เป็นภาษาไทย: `รายงานผู้บริหารมั่งมี-<ชื่อรายงาน>-<เดือน>-ส่งออก-<วันที่>-<เวลา>.xlsx` เช่น “รายงานผู้บริหารมั่งมี-รายรับ-ก.ย.2569-ส่งออก-1ต.ค.2569-0930.xlsx” ตั้งที่หน้าเว็บตอนดาวน์โหลด; ไม่ใส่รหัสคำขอ รหัสบริษัท ชื่อบริษัท คำค้น หรือข้อมูลส่วนบุคคลในชื่อไฟล์ (การส่งออกรายละเอียดบริษัทใช้ชื่อรายงานว่า “รายละเอียดบริษัท”); หัวข้อ `Content-Disposition` ของคำตอบใช้ชื่อสำรองแบบ ASCII ที่ไม่มีข้อมูลใด ๆ
- ชีตภาษาไทยชื่อคงที่ ปลอดภัย ไม่เอาชื่อบริษัท/ตัวกรองมาตั้งชื่อชีตโดยตรง
- หัวตาราง freeze, filter, ความกว้างอ่านได้, wrap headers, เงินชิดขวา; data sheets ไม่มี merged cells
- เงินเก็บตัวเลขหน่วยบาท 2 ตำแหน่งจากจำนวนสตางค์; counts เป็น integer, rates เป็น numeric fraction พร้อม percent format; จุดเปอร์เซ็นต์เป็น numeric difference ×100 พร้อมหน่วยแยก
- ไม่มีคอลัมน์รหัสภายในของบริษัท ผู้ใช้ หรือเซลล์ (**ข้อเสนอ รอเจ้าของยืนยัน — Q29**; ถ้าเจ้าของเลือกให้มีรหัสลูกค้าแบบสั้น ให้เพิ่มคอลัมน์ “รหัสลูกค้า” ต่อจากคอลัมน์ “บริษัท”); รหัสเซลล์ที่พนักงานใช้เรียกกัน (`salesCode`) แสดงต่อท้ายชื่อเซลล์และเป็น text รักษา leading zeros
- เดือนแสดงแบบเดียวกับหน้าจอ เช่น “ก.ย. 2569” ไม่ใช้ 2026-09
- วันที่และเวลาแปลงเป็นเวลาไทยก่อนเขียน และแสดงเป็น พ.ศ. แบบเดียวกับหน้าจอ เช่น “30 ก.ย. 2569” และ “30 ก.ย. 2569 12:00 น.” ค่าเริ่มต้นคือเขียนเป็นค่าวันที่จริงพร้อมรูปแบบ พ.ศ. เพื่อให้เรียงและกรองในไฟล์ได้ ขั้นประเมินตัวเขียนไฟล์ (§6) ต้องเปิดไฟล์ด้วยตัวอ่านทั้งหมดของ EXL-18 ถ้าตัวอ่านใดแสดงเป็น ค.ศ. หรือเป็นตัวเลข ให้เปลี่ยนคอลัมน์วันที่ทั้งหมดเป็นข้อความไทยผ่าน `formatThaiExportDate` เดิม (`apps/api/src/common/export/thai-date.logic.ts`) ซึ่งเป็นแบบที่ไฟล์ส่งออกอื่นของระบบใช้อยู่ และบันทึกผลการเลือกไว้ในเอกสารนี้ก่อนเริ่มสร้าง
- unknown ไม่แปลงเป็น 0 หรือ string ใน numeric column: เว้นค่าว่างและมี status/coverage กำกับ; zero ใช้เมื่อ source ครบและไม่มีจริงเท่านั้น
- ข้อมูลต้นทางเป็น typed snapshot values; สูตรที่ template กำหนดเท่านั้นคำนวณสรุป/อัตรา/คำอธิบายและเป็นแหล่งของ chart objects. ทุก user text ใช้ explicit string cell แม้ขึ้นต้นด้วย =,+,-,@,tab หรือ CR
- สูตรใช้ bounded ranges ที่ปรับตามจำนวนแถวจริงหรือ Excel Table; ไม่คงช่วง72แถวจากแม่แบบ. Coverage/blankต้องตรวจแยกก่อน COUNTIFS/SUMIFS; unknownไม่ถูกนับเป็นNEVERหรือ0 และ rateฐาน0ใช้ unavailable
- ค่าเมื่อเปิดครั้งแรกต้องตรง server snapshot ทั้งค่าตัวเลข/สูตร cached values/chart cache. การแก้ข้อมูลในExcelคำนวณใหม่ในไฟล์เท่านั้น ไม่ส่งกลับระบบ; filteringตารางเฉยๆไม่เปลี่ยนฐานDashboardโดยปริยาย
- สูตร/กราฟอ้างชีตในไฟล์เดียว ไม่ใช้ TODAY/NOW ทำให้lookbackเลื่อนเมื่อเปิดภายหลัง. Snapshot/date/definitionคงที่; lookback7/30วันอิง cutoffเดียวกันและไม่บวกกลุ่มซ้อนทับ
- Escape XML/control characters และ validate finite number, sheet name, row/byte limits; ห้าม truncation เงียบหรือ return ไฟล์เสีย
- คำอธิบายในไฟล์เขียนเป็นภาษาคน เรียงตามนี้: รายงาน; เดือน; ข้อมูลถึง (วันเวลาไทย และเวลาของแหล่งที่ช้ากว่าเมื่อมี); เงื่อนไขที่เลือก (ชื่อและค่าตามที่แสดงบนจอ หรือ “ไม่มี”); เรียงตาม; จำนวนบริษัท; “ไม่รวมบริษัททดสอบและบริษัทของมั่งมี”; หน่วยและนิยามของตัวเลขที่ใช้; “ส่งออกโดย <ชื่อที่แสดงของผู้ส่งออก> เมื่อ <วันเวลาไทย>”; “เลขอ้างอิงการส่งออก” หนึ่งบรรทัด; และเมื่อมีคอลัมน์ข้อมูลติดต่อเพิ่ม “มีข้อมูลส่วนบุคคล ใช้ภายในเท่านั้น” กับ “ข้อมูลบัญชี ณ <วันเวลา>” (ตรงกับสเปกหลังบ้าน §16.4)
- รหัสทางเทคนิค (`buildId`, `definitionVersion`, รุ่นของแม่แบบ, วิธีเรียงค่าที่เท่ากัน) ไม่ใส่ในไฟล์ ให้เก็บในบันทึกการส่งออกและค้นได้จากเลขอ้างอิงการส่งออก (RU-10)
- หัวคอลัมน์ ลำดับ และค่าของชีตรายบริษัทอยู่ใน §4.1 ช่องของระบบที่เป็นแหล่งของแต่ละคอลัมน์ (เช่น `usageGroup`, `contactStatus`, `paidEver`) เป็นเรื่องของสัญญาข้อมูล ไม่ใช่ข้อความในไฟล์
- อีเมลและเบอร์โทรล่าสุดของบัญชีเจ้าของที่ผูกกับบริษัทลูกค้าอยู่ในไฟล์ตามเงื่อนไขของ §9; ไม่รวม tax ID, ที่อยู่เต็ม, bank data, invoice lines, customer documents, access tokens หรือรายชื่อ/ข้อมูลติดต่อพนักงานและลูกค้าปลายทางของบริษัท
- ชีตรายบริษัทไม่มีแถวผลรวม เพื่อไม่ให้การกรองหรือการรวมในไฟล์นับซ้ำ ค่ารวมอยู่ในชีตภาพรวม
- ค่าสรุปที่ข้อมูลไม่ครบ: ช่องตัวเลขเก็บจำนวนที่ยืนยันได้ และช่องข้อความที่ติดกันเขียน “อย่างน้อย” ให้ตรงกับการ์ดบนหน้าจอ (สเปกหน้าจอ §4.2) กราฟอ้างช่องตัวเลข
- ตัวเลขที่มีเฉพาะในไฟล์ คือช่วง 0 / 1–5 / 6 รายการขึ้นไปของใบเสร็จสะสม ต้องมีบรรทัดในคำอธิบายของไฟล์ว่า “ตัวเลขนี้ไม่มีบนหน้าจอ” พร้อมนิยาม
- ค่าเฉลี่ย เปอร์เซ็นต์ อันดับ และสัดส่วนสะสม เป็นค่าที่หลังบ้านคำนวณและปัดแล้ว ตัวเขียนไฟล์ไม่ปัดเอง (สเปกหลังบ้าน §13.1)
- สมาชิกที่อยู่หลายกลุ่มในอนาคตต้องมี distinct company count แยก row count; รุ่นแรก single-value dimensions ทำให้ A/B คนละกลุ่มไม่ overlap

### 4.2 ข้อความที่คนพิมพ์เอง และเครื่องหมายสูตร

ช่องที่ลูกค้าหรือบุคคลภายนอกพิมพ์เองได้: ชื่อบริษัท ชื่อจดทะเบียน ประเภทกิจการที่พิมพ์เอง จังหวัด รายละเอียด “อื่น ๆ” ของแบบสมัครสาธารณะ (ยาวได้ 200 ตัวอักษร — `SIGNUP_DISCOVERY_OTHER_MAX` ใน `packages/contracts/src/external-signup.ts`) อีเมลและเบอร์โทรเจ้าของบัญชี ช่องที่พนักงานของมั่งมีพิมพ์: ชื่อเซลล์ และคำค้นที่ผู้ส่งออกพิมพ์ซึ่งอยู่ในคำอธิบายของไฟล์ (RU-18)

- ทุกช่องข้างบนเขียนเป็นเซลล์ข้อความเสมอ ห้ามผ่านทางเขียนสูตร แม้ข้อความขึ้นต้นด้วย `=`, `+`, `-`, `@`, แท็บ หรือขึ้นบรรทัดใหม่ ข้อความในไฟล์ต้องตรงกับที่พิมพ์ ไม่เติมอักขระนำหน้า
- ห้ามใช้ข้อความเหล่านี้เป็นเงื่อนไขของสูตรนับ รวม หรือค้นหา เงื่อนไขของสูตรอ้างได้เฉพาะคอลัมน์ที่ค่ามาจากรายการปิดของระบบ (สถานะ กลุ่มธุรกิจ ช่องทาง กลุ่มการชำระและใช้งาน) ถ้าต้องสรุปตามมิติที่คนพิมพ์ได้ เช่น เซลล์ ให้สูตรเทียบค่าตรงตัวแบบที่ไม่ตีความ `*`, `?`, `~` เป็นอักขระแทน หรือให้ server เขียนค่าที่สรุปแล้วสำหรับมิตินั้น
- ก่อนเขียน ให้ตัดอักขระควบคุมที่ XML ไม่รับ และแทนแท็บกับการขึ้นบรรทัดใหม่ในช่องบรรทัดเดียวด้วยช่องว่าง ตัวเขียนไฟล์เดิมแปลงเฉพาะ `&`, `<`, `>`, `"` (`apps/api/src/common/export/xlsx.logic.ts`) จึงต้องเพิ่มส่วนนี้
- ชุดตรวจต้องมีบริษัทตัวอย่างที่ชื่อ ชื่อจดทะเบียน และช่อง “อื่น ๆ” ขึ้นต้นด้วย `=`, `+`, `-`, `@`, แท็บ และขึ้นบรรทัดใหม่ และมี `*`, `?`, `~`, `>` อยู่ในข้อความ แล้วยืนยันว่าเปิดไฟล์แล้วเห็นข้อความเดิม (แท็บและการขึ้นบรรทัดใหม่กลายเป็นช่องว่างตามข้อก่อนหน้า) ไม่มีสูตรทำงาน และตัวเลขในชีตภาพรวมไม่เปลี่ยน (EXL-16)
- ความเสี่ยงที่เหลือ: ถ้าผู้ใช้บันทึกไฟล์เป็น CSV แล้วเปิดใหม่ โปรแกรมตารางอาจตีความข้อความเหล่านี้เป็นสูตร รุ่นแรกไม่เติมอักขระกันไว้ในไฟล์ xlsx เพราะทำให้ข้อความไม่ตรงกับหน้าจอ (ฝั่งไฟล์ CSV ของระบบมี `safeCsvCell` ใน `apps/api/src/common/export/csv.logic.ts` อยู่แล้ว แต่การส่งออกนี้ไม่สร้าง CSV)

## 5. สัญญา FE → BE (ข้อเสนอ)

Reuse executive report projections/definitions ของ API02–05; ห้ามใช้ DOM หรือ client paginated rows เป็นแหล่งข้อมูลจริง
เสนอ `POST /v1/system/executive/exports` (API13) คืน binary xlsx ใน request เดียวสำหรับขอบเขตที่ bounded
body เป็นไปตามสเปกหลังบ้าน §16.4: `{ buildId, reportKey, subview?, month, filters, sortBy?, sortDir?, comparison?, targetCompanyId?, includeContacts, format: "xlsx" }` เอกสารนี้ไม่กำหนด field เพิ่ม
`includeContacts` มีผลเฉพาะ `reportKey` ของรายชื่อบริษัทและรายละเอียดบริษัท และเฉพาะผู้มีสิทธิ์ดูข้อมูลติดต่อ (§6, §9); เงื่อนไขที่กดเจาะมา (สเปกหน้าจอ §3.3) ส่งอยู่ใน `filters` แบบเดียวกับคำขอของรายชื่อ; บริษัทของการส่งออกรายละเอียดส่งเป็น `targetCompanyId`; หน้าเว็บไม่ส่งแม่แบบ
คำว่า snapshot ที่เหลืออยู่ในเอกสารนี้หมายถึงชุดข้อมูลของรายงาน ซึ่งสัญญาใช้ `buildId` (สเปกหลังบ้าน §12.3) ไม่มีอายุ 15 นาทีแล้ว
ไม่รับ arbitrary SQL/field names/member IDs/client totals/page/cursor; unknown keys/enum และ field ที่ไม่ใช้กับ report นั้นต้อง reject
FE canonicalize context ก่อนส่ง; BE normalize/validate กับ immutable snapshot + definition version + actor scope เสมอ
BE query ทั้งผลลัพธ์ของ snapshot, derive cohort/Pareto/comparison ที่ server; ตรง membership/count/sum/order กับหน้าจอ
Detail context ใช้ `targetCompanyId` และเดือน ไม่รับ shared segment/list filters; compare context ใช้ A/B ของตน ไม่รับ dormant report filters
Serverเลือก templateVersion/hashที่อนุมัติ ไม่รับtemplate/formula/font/chart configจากclient; บันทึกtemplateVersionคู่definitionVersionในบันทึกการส่งออก ไม่ใส่ในไฟล์
Response: XLSX MIME + safe Content-Disposition (ชื่อสำรองแบบ ASCII; ชื่อไฟล์ภาษาไทยตั้งที่หน้าเว็บตาม §4) + requestId/rowCount/บริษัทที่ไม่ซ้ำ + no-store; headers/errors ไม่มี PII
คืน 200 เมื่อสร้างครบเท่านั้น; failure คืน JSON error ก่อนเริ่มส่ง binary ไม่มี partial success

บันทึกการตัดสินใจ (RU-17): ระบบมีโมดูลรายงานของบริษัทลูกค้าที่ส่งออกได้อยู่แล้ว (`apps/api/src/modules/reports/application/report.use-cases.ts`: เก็บไฟล์ ตรวจ sha256 หมดอายุ 7 วัน บันทึก `report.export.request` และ `report.export.download`; เพดาน 5,000 แถวใน `apps/api/src/modules/reports/domain/report-query-validator.logic.ts`) โมดูลนั้นผูกกับบริษัทลูกค้าทีละรายและรับเฉพาะ CSV
การส่งออกของผู้บริหาร **ไม่ใช้วงจรเก็บไฟล์ 7 วันนั้น** เพราะไฟล์มีข้อมูลของทุกบริษัทและอาจมีข้อมูลส่วนบุคคล จึงไม่ควรมีสำเนาค้างที่ server แต่ใช้ส่วนที่ใช้ร่วมได้ คือแบบแผนบันทึกการส่งออก แบบแผนเพดานแถว และแบบแผนดาวน์โหลดฝั่งหน้าเว็บ (§2)

รุ่นแรกไม่สร้าง queue/storage/export history เพิ่มเพื่อข้อมูลหลักสิบ/หลักร้อยบริษัท:

- ไฟล์ต้องมาจากชุดข้อมูลเดียวกับที่ผู้ใช้เห็นบนหน้าจอ: API13 ต้องส่ง `buildId` และตรวจสิทธิ์ซ้ำก่อนส่งไฟล์ ถ้า `buildId` ไม่ใช่ชุดปัจจุบัน หลังบ้านคืน 409 `EXECUTIVE_SNAPSHOT_EXPIRED` ไม่สร้างไฟล์จากชุดใหม่เงียบ ๆ หน้าเว็บแสดง “ข้อมูลรายงานเก่าแล้ว กรุณาโหลดใหม่ก่อนสร้างไฟล์” และผู้ใช้กลับไปดูรายงานที่โหลดใหม่ก่อน (สเปกหน้าจอ §4.1) รหัสนี้คงชื่อเดิมแต่คืนเฉพาะการส่งออก การอ่านรายงานไม่มีวันหมดอายุ
- เพดานตามสเปกหลังบ้าน §16.4: จำนวนแถวข้อมูลไม่เกิน 10,000, ขนาดไฟล์ไม่เกิน 20 MiB คิดจากไฟล์ที่บีบอัดแล้ว, สร้างไม่เกิน 30 วินาที และหนึ่งงานต่อผู้ใช้ในเวลาเดียวกัน; ตัวเลขทั้งหมดต้องยืนยันด้วย capacity test ไม่ใช่ SLA ที่พิสูจน์แล้ว
- เพดานแถวต้องไม่ต่ำกว่าสองเท่าของจำนวนบริษัทที่ใช้ตรวจรับ (รอบแรก 1,000 บริษัทตามสเปกหลังบ้าน §20.2) และเมื่อจำนวนบริษัทจริงเกินครึ่งของเพดานแถว ต้องทบทวนเพดานหรือออกแบบแบบ async ก่อน เพื่อไม่ให้หน้าที่รวมทุกบริษัทส่งออกไม่ได้ (RU-17)
- ตัวเขียนไฟล์ต้องบีบอัด ตัวเขียนเดิม (`apps/api/src/common/export/xlsx.logic.ts`) เก็บแบบไม่บีบอัด ผู้ตรวจทานประมาณว่าไฟล์ 10,000 แถวที่ประมาณ 40 คอลัมน์จะมีขนาด 20–30 MB ถ้าไม่บีบอัด (ค่าประมาณ ยังไม่ได้วัดจากไฟล์จริง ต้องวัดในขั้นประเมินตัวเขียนไฟล์ของ §6)
- เกินเพดานคืน 422 `EXECUTIVE_EXPORT_LIMIT_EXCEEDED` ก่อนเริ่มส่งไฟล์ หน้าเว็บแสดง “ไฟล์ใหญ่เกินไป กรุณาเลือกกลุ่มธุรกิจหรือช่องทางก่อนส่งออก” ห้ามแอบแบ่ง/ตัดข้อมูล; ไม่มีบริษัทในขอบเขตคืน 422 `EXECUTIVE_EXPORT_EMPTY` หน้าเว็บแสดง “ไม่มีบริษัทตามเงื่อนไข จึงไม่มีไฟล์ให้สร้าง”; หาก scale จริงเกินขอบเขตค่อยออกแบบ async และ storage lifecycle แยก
- รหัสข้อผิดพลาดทั้งชุดอยู่ในสเปกหลังบ้าน §16.3: 403 ไม่มีสิทธิ์อ่านหรือส่งออก, 409 ชุดข้อมูลเปลี่ยน, 422 เกินเพดานหรือไม่มีบริษัท, 429 เรียกถี่เกินไปหรือมีงานส่งออกค้างอยู่, 503 แหล่งข้อมูลไม่พร้อม; ทุกรหัสต้องมีข้อความไทยตามเอกสารคำบนหน้าจอและลงทะเบียนใน `apps/web/src/common/api/api-error-message.ts` ก่อนใช้ 429 ต้องบอกเวลาที่ต้องรอ
- ทำงานอ่านอย่างเดียว; retry ไม่เปลี่ยน billing/usage/sales state. กัน duplicate click/active build และบันทึก audit ต่อ attempt/requestId โดยไม่เพิ่ม generic command/job system

2. ใช้ distinct userId: พบหนึ่งบัญชีจึงคืน contactUserId และ `User.email`/`User.phoneNumber` จาก user เดียวกัน; ตรวจ email/phone แยก field. null/ว่าง/ค่าที่ใช้ไม่ได้ทำให้เฉพาะ field นั้นว่างพร้อม coverage ตามจริง; ไม่ล้างอีก field ที่ยังมีข้อมูล

4. สถานะ User เป็นข้อมูลอีกมิติ: SUSPENDED/DISABLED ไม่เปลี่ยนตัวตนเจ้าของที่ยังมี active membership หรือทำให้เลือกคนอื่น; ส่ง accountStatus เพื่ออธิบายสถานะบัญชีในรายละเอียด. หาก membership ถูกระงับ/ปิดหรือ OWNER ถูกถอด จะไม่อยู่ในชุดเจ้าของปัจจุบัน. รายงานนี้ไม่ให้สิทธิ์ login/เปลี่ยนบัญชี/ส่งข้อความ (สัญญาหลังบ้านฉบับแก้ไม่ส่งสถานะบัญชีของเจ้าของร้านมาที่หน้าจอ จึงไม่แสดง)
