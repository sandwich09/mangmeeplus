## 1. เป้าหมาย

Owner (2026-09-29): "ด้วยเป้าหมายเราอยากให้เป็น advisor ai แปลว่าต้องตอบเกี่ยวกับร้านและระบบได้หมด เท่าที่จะอนุญาต … ความรู้ทั่วไป + ความรู้ในระบบ จะทำให้มั่งมีดูฉลาดขึ้น"

แปลงเป็นข้อกำหนด:

1. **ข้อมูลของร้าน:** ตอบได้ทุกเรื่องที่ **แพ็กเกจเปิด ∩ โมดูลที่พัฒนาเสร็จและเปิดใช้แล้ว ∩ สิทธิ์ของผู้ถาม ∩ ขอบเขตสาขาและเจ้าของรายการ** ผ่านเครื่องมืออ่านของ API ที่ตรวจสิทธิ์ (ความพร้อมของแต่ละโมดูลอยู่ใน §2.2)
2. **ความรู้ระบบ** (วิธีใช้ กติกาแพ็กเกจ ความหมายของสถานะ): ตอบจากคู่มือที่อนุมัติ ความสามารถจริงของผู้ถาม และคำตอบนโยบายสาธารณะที่มีอยู่
3. **ความรู้ธุรกิจทั่วไป:** ตอบเต็มทุกแพ็กเกจ
4. **งานขั้นสุดท้ายอยู่บนเว็บเสมอ**

### 2.3 สิทธิ์และขอบเขต "ของฉัน" กับ "ทั้งร้าน"

- **ขอบเขตมาจากสิทธิ์จริงเท่านั้น** (`PermissionResolverService.resolveAccess`):
  - `company` อ่านได้ทั้งร้าน
  - `related` อ่านได้เฉพาะรายการที่เกี่ยวกับผู้ถาม
  - `own` อ่านได้เฉพาะของผู้ถาม

  เครื่องมือใหม่ทุกตัวต้องคืน `queryApplied.accessScope` เหมือนเครื่องมือรายจ่าย
- **คำตอบจากขอบเขต `own`/`related`** ต้องบอกชัดว่าเป็นเฉพาะรายการของผู้ถาม (กฎเดิมใน `ANSWER_PROMPT`)
- **คิว "ของฉัน"** (ใบที่ฉันต้องเซ็น ใบที่ฉันต้องอนุมัติ) เป็นขอบเขตของผู้ถามตามนิยาม ไม่ใช่ทั้งร้าน แม้ผู้ถามจะเป็นเจ้าของร้าน
- **แพ็กเกจ โควตาใบเสร็จ และเครดิต AI** (มติ Owner 2026-09-30 §10 ข้อ 2): ตอบเฉพาะผู้มีสิทธิ์จัดการแพ็กเกจ (`company.plan.manage`) ตามบทบาทที่ร้านมอบ รวมเจ้าของร้าน
  - ใช้สิทธิ์เดิมของระบบแพ็กเกจ ไม่ตั้งกติกาใหม่: `resolveAccess` เก็บเฉพาะบทบาทที่ใช้งานอยู่ เหมือน `canManagePlan` (`plan-manager.logic.ts:28-32`) ที่ `BillingService.assertOwner` ใช้
  - คนอื่นได้ข้อความไม่มีสิทธิ์มาตรฐาน P8 (ให้ถามเจ้าของร้านหรือผู้มีสิทธิ์จัดการแพ็กเกจ) ไม่เห็นตัวเลขใด ๆ
- **ใบเบิกค้างที่ใคร** (มติ Owner 2026-09-30 §10 ข้อ 10): เห็นทั้งร้านเฉพาะผู้ที่เห็นใบเบิกทั้งร้านบนเว็บตามสิทธิ์ที่ได้รับ (รวมเจ้าของร้าน) พนักงานทั่วไปเห็นเฉพาะว่าใบของตัวเองค้างที่ใคร
- **ร้านสร้างบทบาทเองได้** ตาราง §4 จึงระบุ **สิทธิ์** เป็นหลัก ชื่อบทบาทเป็นเพียงตัวอย่างจาก `ROLE_GRANTS` (`apps/api/src/modules/auth/permission-registry.ts`)

### 2.4 สาขา

- **ใช้ตัวกรองสาขาเดิม** (`branchScopeWhere`, `resolveExpenseBranchFilter`) การเลือกสาขา A หมายถึงเฉพาะ A ไม่รวมส่วนกลาง (core contract §5)
- **ข้อมูลระดับบริษัทที่ไม่มีสาขา** ได้แก่ แพ็กเกจและเครดิต ทะเบียนคู่ค้า และรายชื่อสมาชิก ให้ผลเท่ากับหน้าเว็บของสิทธิ์เดียวกัน (หน้าเว็บของทั้งสามส่วนไม่กรองตามสาขา) รอ Owner ยืนยันใน §10 ข้อ 7
- **ใบเบิก:** หน้ารายการบนเว็บไม่มีตัวกรองสาขา ใช้เฉพาะขอบเขตสาขาของสมาชิก ซึ่งรวมใบที่ไม่มีสาขา (`branchScopeWhere`, `branch.logic.ts:80-83`)
- **ยอดเงินที่ผูกกับคู่ค้า** (จ่ายร้านไหนเท่าไหร่) ยังมาจาก `expense.get_breakdown` ซึ่งกรองสาขาและขอบเขตแล้ว

### 2.5 ความเป็นส่วนตัว

- **ห้ามอ่านออกมาในแชต:** เบอร์โทร อีเมล เลขบัตรประชาชน เลขผู้เสียภาษีของบุคคล ที่อยู่ เลขบัญชีธนาคาร ลายมือชื่อ วันเกิด
- **เครื่องมือต้องไม่ส่งค่าเหล่านี้ให้ gateway เลย** การสั่งโมเดลว่าอย่าพูดไม่พอ
  - เหตุผล: ตัวตรวจตัวเลข `allowedAnswerNumbers` (`semantic-turn-v2.ts`) อนุญาตทุกตัวเลขที่อยู่ใน `data` ของผลเครื่องมือ ถ้าเบอร์โทรอยู่ใน `data` ตัวตรวจจะปล่อยผ่าน
  - ให้ส่งเป็นค่าจริง/เท็จแทน เช่น `hasPhone`, `hasEmail`, `lineLinked`, `hasTaxId`, `hasAddress`
- **รายชื่อคนบอกได้:** ชื่อที่แสดงและบทบาทเป็นข้อมูลภายในร้านที่ผู้ถามเห็นบนเว็บอยู่แล้ว
  - ชื่อผู้อนุมัติที่ใบเบิกรออยู่ เห็นได้เท่ากับหน้าเว็บ (`currentDesk` ใน `apps/api/src/modules/reimbursements/domain/logic/reimbursement.logic.ts:378`)
  - `getUserDisplayNames` ไม่กรองคนที่ออกไปแล้ว (`prisma-reimbursement.repository.ts:207`) ต้องกรองด้วยผู้อนุมัติที่ยังใช้งานอยู่ก่อนบอกชื่อ (§5.3)
- **ผู้รับเงินในใบรับรองแทนใบเสร็จ** อาจเป็นบุคคลธรรมดา บอกชื่อผู้รับเงินได้เพราะพิมพ์อยู่ในเอกสาร แต่ไม่บอกเลขผู้เสียภาษีและที่อยู่
- **แชตกลุ่มและห้อง** ไม่อ่านข้อมูลร้านเลย เส้นทางเดิมส่งข้อความกลุ่มไป `executePublicGeneral` เครื่องมือใหม่ทั้งหมดจึงใช้ได้เฉพาะแชตส่วนตัว
- **บันทึกการอ่าน:** เครื่องมือที่คืนชื่อคนหรือข้อมูลการค้าตั้ง `sensitiveAudit: true` เพื่อใช้บันทึก `AI_TOOL_INVOKE` เดิม
- **ข้อยกเว้นเดิมที่ต้องตัดสิน:** `company.get_employee_detail` คืนเบอร์และอีเมลของคนที่ถามชื่อ (มติ 2026-07-05, `erp-business-tools.use-case.ts:334-340`) ซึ่งขัดกับกฎ "บอกชื่อเท่านั้น" ของเอกสารนี้ ดู §10 ข้อ 6
  - อีเมลที่เครื่องมือนี้คืนคืออีเมลเข้าระบบ ส่วนหน้าเว็บแสดงอีเมลติดต่อก่อน (`employee-access.mapper.ts:74`) และเครื่องมือนี้ไม่กรองสถานะสมาชิก

### 2.6 งานขั้นสุดท้ายอยู่บนเว็บ

- **LINE ทำได้:** อ่าน อธิบาย เทียบ จัดอันดับ ชี้จุดที่ควรตรวจ และเตรียมร่างใน flow ที่มีอยู่แล้ว
  - ร่างรายจ่ายจากรูป
  - แก้ร่างแบบ preview แล้วยืนยัน
  - ร่างใบเบิก
  - สองข้อหลังผูกกับค่าตั้งเดิม (`LINE_AI_DRAFT_EDIT_ENABLED`, `LINE_AI_REIMBURSEMENT_DRAFT_WRITE_ENABLED`) ซึ่งค่าเริ่มต้นในโค้ดเปิด แต่เปิดอยู่จริงบน production หรือไม่ต้องอ่าน env ที่ deploy — **ต้องตรวจสอบ** เอกสารนี้ไม่พึ่งสองข้อนี้
- **LINE ทำไม่ได้:**
  - อนุมัติหรือปฏิเสธ จ่าย ยืนยัน ยกเลิก
  - ลงลายมือชื่อ รับรอง หรืออนุมัติใบรับรองแทนใบเสร็จ
  - ซื้อแพ็กเกจหรือเครดิต
  - เปลี่ยนสิทธิ์ เพิ่มหรือปิดพนักงาน
- **ตอบคำสั่งเหล่านี้ด้วยเหตุผลตรง ๆ** พร้อมลิงก์หน้าเว็บที่ทำได้ ตามรูปแบบข้อ 2 ของ `scopePolicyOverride`
  - ข้อเท็จจริงในโค้ด: ข้อความของข้อ 2 วันนี้บอกชื่อหน้าเป็นคำไทย ไม่มีลิงก์ที่กดได้ (`line-ai-scope-policy.logic.ts:154-169`) ลิงก์ที่กดได้มาจาก `sourceRefs` ของเครื่องมือเท่านั้น (§2.7)
  - ปัจจุบันกฎนี้ครอบคลุมใบเบิก (อนุมัติ ปฏิเสธ จ่าย) และรายจ่าย (ยืนยัน ยกเลิก) แต่ยังไม่ครอบคลุม "เซ็น ลงนาม หรืออนุมัติใบรับรอง" จึงเพิ่มใน slice S1 (#910 merge แล้ว ไม่ต้องรอ)
- **ลายเซ็นและการรับรองบนเว็บยังบังคับ `assertWeb` เหมือนเดิม** เครื่องมือใหม่อ่านคิวเท่านั้น ห้ามลดทอน guard นี้

## 4. แคตตาล็อกคำถาม

## 5. เครื่องมืออ่านใหม่ (สัญญาระดับสเปก)

ไฟล์ ตำแหน่ง และ `ToolMeta` แบบเต็มอยู่ในแผน §3 ส่วนนี้ล็อกพฤติกรรม

### 5.0 กติการ่วมของเครื่องมือใหม่ทุกตัว

- **ที่อยู่ของเครื่องมือ:** อยู่ใน API (`apps/api/src/modules/line-ai/application/use-cases/erp-*-tools.use-case.ts`)
  - เรียก use case หรือ repository ของโมดูลเจ้าของข้อมูล และตรวจสิทธิ์เองอีกชั้น
  - Gateway เห็นแค่ `ToolResult` ห้ามอ่านฐานข้อมูลเอง (AGENTS.md)
- **ผลต้องอ่านซ้ำได้ค่าเดิม:** ตอนส่งคำตอบ API อ่านซ้ำด้วย input เดิมแล้วเทียบ hash (`LineReadEvidenceService.verifyDelivery` → `verify` → `lineReadResultHash`)
  - ห้ามใส่ค่าที่เปลี่ยนตามเวลาละเอียดกว่าวันใน `data` เช่น ชั่วโมงที่รอ "กี่นาทีที่แล้ว" หรือเวลาปัจจุบัน
  - ให้ใช้วันที่และจำนวนวันตามวันไทย (`Asia/Bangkok`)
  - `sourceRefs[].asOf` ไม่ถูกนำมาคิด hash อยู่แล้ว
- **ตัวเลขทุกตัวที่คำตอบอาจพูดถึงต้องอยู่ใน `data` หรือ `facts`** รวมถึงผลคำนวณ เช่น คาดการณ์ ส่วนต่าง อัตรา และจำนวนวัน เพราะตัวตรวจตัวเลขปฏิเสธตัวเลขที่โมเดลคิดเอง
- **เงินใช้ Decimal เป็นสตริง** ห้ามใช้ `Number()` ในการรวมยอด (core contract §5) และไม่รวมยอดต่างสกุลเงิน
- **ต้องมี** `queryApplied` (ถ้าเกี่ยวกับช่วงหรือสาขา) พร้อม `accessScope`, `completeness` และ `sourceRefs` ที่มี `webPath`
  - เครื่องมือที่รับช่วงเวลาต้องคืน `queryApplied.period.startDate/endDate` เพื่อให้หมายเหตุ "ไม่ได้ระบุปี" ของ #912 ทำงาน (`readPeriod`, `semantic-turn-v2.ts:233`)
  - `sourceRefs` ตัวแรกคือลิงก์ที่ลูกค้าเห็น (§2.7) จึงต้องชี้หน้ารายการที่ถูกต้อง
- **ไม่รับ id ที่โมเดลคิดเอง** ยกเว้นค่าที่ API เคยส่งให้ผ่าน `shownItems` และชื่อที่ใช้กรอง (`search`) ต้องปรากฏในข้อความผู้ใช้ (`nameFilterGroundedInText`, `read-tool-input.ts:58`)
- **ขนาด:** รายการไม่เกินที่ระบุต่อเครื่องมือ และไม่เกินขอบเขตรายการของ core contract §5 (รายการสูงสุด 50 แถว)

  - สิทธิ์นี้มาจาก `resolveAccess` ซึ่งเก็บเฉพาะบทบาทที่ใช้งานอยู่ ตรงกับ `canManagePlan` (`plan-manager.logic.ts:28-32`) ที่ `BillingService.assertOwner` ใช้ (`billing.service.ts:149`) และตัดสิทธิ์นี้ตามแพ็กเกจไม่ได้

- **การตรวจสิทธิ์และคำตอบ P8:**
  - ถ้าผูก `company.plan.manage` ไว้ใน registry เครื่องมือจะไม่ถูกเสนอให้คนที่ไม่มีสิทธิ์เลย (`lineIntakeOfferedToolNames`, `process-line-webhook.use-case.ts:449-461`) ข้อความ P8 จึงไม่มีทางเกิด และ `ANSWER_PROMPT` หลัง #910 จะตอบว่าแพ็กเกจยังไม่มีข้อมูลนี้ ซึ่งผิดเหตุผล
  - จึงเสนอเครื่องมือให้ทุกคนที่ใช้ผู้ช่วยได้ (`requiredPermissions: ['ai.tool.invoke']` แบบ `public.lookup`, `ai-tools.ts:995-1000`) แล้วตรวจ `company.plan.manage` ในเครื่องมือ
  - คนที่ไม่มีสิทธิ์ได้ `forbidden` พร้อม `errorCode: 'PACKAGE_MANAGER_REQUIRED'` แล้ว gateway ตอบข้อความคงที่ P8 แบบเดียวกับ `REIMBURSEMENT_APPROVAL_NOT_PERMITTED`
- **อ่านจาก:**
  - แพ็กเกจ: `CompanyPlanTerm.tierKey` ตั้งชื่อด้วย `billingPlanLabel` เหมือนหน้าเว็บ ไม่ใช้ tier ของของขวัญชั่วคราว และ `termEndsAt` สำหรับวันที่ใช้ได้ถึง

  - จำนวนสาขาและสมาชิกที่ใช้อยู่: นับแบบเดียวกับ `plan-term-limit.ts:38`, `:52-54` (สาขา ACTIVE และสมาชิก ACTIVE ไม่นับที่นั่ง SYSTEM_ADMIN)
    - วันนี้การนับนี้มีสำเนาอยู่หลายที่ ให้แยกเป็น helper เดียว
    - ห้ามเรียก `BillingService.capacity()` เพราะล็อกแถวบริษัทและเรียก `assertOwner`
  - ใบเสร็จ: `BillingService.usage(companyId)` (`billing.service.ts:213-219`) ซึ่งอ่าน DB อย่างเดียว ไม่ตรวจเจ้าของ และให้ตัวเลขเดียวกับ "ใบเสร็จคงเหลือ" บนหน้าแพ็กเกจ (ภายในเรียก `receiptQuotaSnapshot`)
  - รูปแบบต่ออายุ: ใช้ค่าที่หน้าเว็บคำนวณ (`billing.service.ts:876`, `:1000`) ไม่ใช้ `renewalMode` ดิบ
  - (S2b) ตัวคำนวณยอดเครดิต AI **ตัวเดียวกับ** `BillingStatus.addOns.quotaSummary` ของงาน E9 แผน add-on (ยังไม่มี — แผน §4 D2)
- **ห้ามเรียก `BillingService.status()`** เพราะเรียก Stripe ในบางโหมด และจะ throw เมื่อผู้ถามไม่ใช่ผู้จัดการแพ็กเกจ
- **`data`:**
  - `package { label, termEndsOn, renewal: 'auto'|'one_time'|'none' }`
  - `capacity { branches { used, limit }, members { used, limit } }`
  - `receipts { used, limit, remaining, cadence, periodStartOn, periodEndsOn, additional { remaining, expiresOn } | null, pace | null }`
    - `used` นับทุกการอ่านรูปที่ระบบรับ ไม่ใช่เฉพาะใบเสร็จ (§11 ข้อ 1) คำตอบใช้คำเดียวกับหน้าแพ็กเกจ
    - `additional` มีเฉพาะยอดแถมของแบบรายเดือนเดิม (`monthlyAllowance`) แบบ `PAID_GRANTS` รวมยอดแถมไว้ใน limit และ used แล้ว
  - (S2b) `aiCredit { totalRemaining, fromPackage, additional, unlimited, nextRefillOn | null }` หน่วย "เครดิต AI" ทศนิยมไม่เกิน 2 ตำแหน่ง (`unitScale` 100)
- **คาดการณ์ (`pace`, formula `package-pace-v1`, มติ Owner 2026-09-30 §10 ข้อ 4 ข):**
  - `projectedUsed = ceil(used × daysInPeriod / daysElapsed)` และ `projectedShortfall = max(0, projectedUsed − limit)`
  - รอบของแบบรายเดือนเดิม (`LEGACY_MONTH`) คือเดือนปฏิทินตามเวลาไทย (`billingMonth`)
  - รอบของแบบ `PAID_GRANTS` คือ `serviceStart`/`serviceEnd` ของ lot ที่กำลังใช้ (`BillingReceiptGrant`, `schema.prisma:10040-10041`) ซึ่งโค้ดวันนี้ยังไม่ select ต้องเพิ่ม
  - คืน `null` พร้อมเหตุผลเมื่อรอบผ่านไปไม่ถึง 7 วัน เมื่อเพดานไม่จำกัด หรือเมื่อหารอบที่ชัดเจนไม่ได้ (เช่น มีหลาย lot ซ้อนกัน)
  - คำตอบต้องบอกว่าเป็นการคาดการณ์จากอัตราการใช้รอบนี้ และบอกได้เพียง "น่าจะพอ" หรือ "ขาดประมาณ N ใบ"
- **ไม่มี:** ราคา ยอดกันไว้ (RESERVED/HELD) ต้นทุน เพดานเงินรายเดือน รหัสแพ็กเกจ หรือชื่อแพ็กเกจอื่น (มติ §10 ข้อ 4)

### 5.2 `expense.list_substitute_receipts_to_sign` (slice S1)

- **input:** `role?: 'payer'|'approver'`, `limit?: 1..10`
- **สถานะของใบรับรอง** มีแค่ `PREPARED`, `PAYER_CERTIFIED`, `ISSUED`, `SUPERSEDED` (`schema.prisma:2444`) และ `signatureMode` เป็น `DIGITAL` หรือ `PAPER`
- **`asPayer`:** สถานะ `PREPARED` และ `payerUserId` ตรงกับผู้ถาม (มี index `[companyId, payerUserId, status]`)
  - ฉบับกระดาษที่ทำบนเว็บตั้ง `payerUserId` เป็นค่าว่าง (`substitute-receipt.use-case.ts:569-570`) จึงไม่อยู่ในคิวผู้จ่ายของใคร
  - ใบที่สร้างจาก LINE เป็น `PREPARED`/`DIGITAL` และผู้ส่งเป็นผู้จ่าย (`line-substitute-receipt-continuation.use-case.ts:417`) จึงอยู่ในคิวนี้ และเป็นทางเดียวที่ผู้จ่ายจะเห็นใบนี้ เพราะระบบไม่แจ้งเตือนผู้เตรียมที่เป็นผู้จ่ายเอง
- **`asApprover`:** ผู้ถามมี `expense.confirm` และอยู่ในสาขาที่ผู้ถามเห็น ต้องผ่านกติกาเดียวกับการอนุมัติบนเว็บ (`ApproveSubstituteReceiptUseCase`, `substitute-receipt.use-case.ts:1134`)
  - รวมสองแบบ: สถานะ `PAYER_CERTIFIED` และฉบับกระดาษที่ส่งเข้าระบบแล้วรอรับ (`PREPARED` + `PAPER` + มี `paperSubmissionJson`) ซึ่งรับด้วยกติกาเดียวกัน (`:1639-1643`) และหน้าเว็บนับเป็นรออนุมัติอยู่แล้ว (`substitute-receipt-hub.model.ts:28-31`)
  - `isEligibleSubstituteReceiptApprover` ตามโหมด `OWNER_SELF`/`DESIGNATED_APPROVERS` ของนโยบายระดับบริษัท (`getSubstituteReceiptPolicy`) และ `listEligibleSubstituteReceiptApprovers` ต่อสาขา
  - อนุมัติของตัวเองไม่ได้ เว้นแต่ `selfApprovalPermitted` ซึ่งต้องเป็นโหมด `OWNER_SELF` และมีบทบาท OWNER, ADMIN หรือ MANAGER (`:1173-1176`) เครื่องมือจึงต้องได้บทบาทจริงของผู้ถาม
  - กติกา "ผู้อนุมัติเดิม" ใช้เฉพาะใบแก้ไขของใบที่ออกแล้ว (`correctionOfEvidenceId`, `:1162-1164`) ไม่ใช่ทุกฉบับแก้ไข และต้องอ่าน `approverUserId` ของใบเดิม
- **`data`:** `asPayer { count, items[] }`, `asApprover { count, items[] }` และ `accessScope: 'own'`
  - item = `documentNumber, payeeName, amount, currency, expenseDate, preparedOn, stepLabel` ไม่เกิน 10 รายการต่อขั้น
  - ไม่มี `payeeTaxId`, `payeeAddress`, ลายเซ็น หรือไฟล์
- **ไม่ใช้ `ListCompanySubstituteReceiptsUseCase`** (`:424`) เพราะมี `assertWeb` และเป็นมุมมองทั้งร้าน ให้เพิ่ม use case อ่านอย่างเดียวตัวใหม่ในโมดูล expenses แทน โดยไม่แก้ `assertWeb` ของการ certify และ approve
- **ความสัมพันธ์กับงานใบรับรองบน LINE (#926):**
  - `substituteAwaitsCaptionlessPhoto` (`line-substitute-receipt-continuation.use-case.ts:803`) ให้งานใบรับรองรับรูปที่ไม่มีข้อความได้เฉพาะภายใน 30 นาทีหลังคำขอที่ชัดเจนในแชตนั้น (พิมพ์ฟอร์ม ขอลายเซ็น หรือขอใบเสร็จฉบับจริง) และไม่แตะข้อความตัวอักษร
  - เครื่องมือนี้อ่านอย่างเดียว ห้ามสร้างหรือแก้สถานะงานต่อเนื่องใน `sourceChannelMetadataJson.lineSubstituteReceiptContinuation`
  - คำตอบของ S1 ไม่ใช่คำขอรูป จึงห้ามบอกให้ส่งรูปใบที่เซ็นแล้วมาทาง LINE ให้บอกว่าเซ็นบนเว็บ

### 5.3 `reimbursement.get_approval_backlog` (slice S3)

- **ขอบเขต (มติ Owner 2026-09-30 §10 ข้อ 10):** เหมือน `GetReimbursementAiSummaryUseCase` (`reimbursement-summary.use-case.ts:13`) บวกสาขาที่เห็น
  - `reimbursement.read` เห็นทั้งร้าน (ผู้ที่เห็นใบเบิกทั้งร้านบนเว็บ รวมเจ้าของร้าน)
  - `read_related` เห็นที่เกี่ยวข้อง
    - เงื่อนไข "เกี่ยวข้อง" วันนี้ไม่ดูรายชื่อผู้อนุมัติที่ถูกตรึง บทบาทที่ร้านสร้างเองซึ่งมีแค่ `read_related` จึงไม่เห็นใบที่รอตัวเองผ่านบทบาท (บทบาทมาตรฐาน ADMIN และ MANAGER มี `read`)
  - `read_own` เห็นของตัวเอง (พนักงานทั่วไปเห็นว่าใบของตัวเองค้างที่ใคร)
- **ใบเบิกรอใครอยู่:**
  - `currentDesk` (`reimbursement.logic.ts:378`) คืน kind `REQUESTER`/`APPROVER`/`FINANCE`/`PAYMENT` (`packages/contracts/src/reimbursements.ts:290`) ไม่มี kind ของกลุ่มตามบทบาท
  - ตอนส่ง ระบบตรึงผู้อนุมัติของขั้นไว้ใน `assignedApproverUserIdsJson` เป็นทุกคนที่ถือบทบาทที่เลือก หรือคนเดียวที่ระบุชื่อ (`reimbursement-request.use-case.ts:572`)
    - กลุ่มตามบทบาทหรือเจ้าของเหลือเป็นทางสำรองเมื่อทุกคนที่ถูกตรึงไม่ active แล้ว (`frozenApprovalAuthority`, `reimbursement.logic.ts:630`)
  - กรองด้วยผู้อนุมัติที่ยังใช้งานอยู่ต่อสาขา (`findActiveApproverUserIds`, `prisma-reimbursement.repository.ts:228`) ก่อนนับและก่อนบอกชื่อ
- **กลุ่มของคำตอบ (มติ Owner 2026-09-30 §10 ข้อ 9 "แยกเป็นกองกลาง"):**
  - ใบที่มีผู้อนุมัติที่ใช้งานได้คนเดียว → นับให้คนนั้น
  - ใบที่อนุมัติได้หลายคน → **กองกลาง** แยกต่างหาก ไม่นับให้คนใดคนหนึ่ง
    - ร้านที่ตั้งผู้อนุมัติเป็นบทบาทที่มีหลายคน ใบส่วนใหญ่จะอยู่ในกองกลาง
  - ไม่มีผู้อนุมัติที่ใช้งานได้ → กลุ่มของตัวเอง
  - `PENDING_APPROVAL` ที่ขั้นอนุมัติผ่านแล้วแต่สถานะยังไม่ขยับ (ไม่มีขั้นที่ค้าง) → กลุ่ม "รอระบบปรับสถานะ" ไม่ใช่ของคน
  - รอการเงินตรวจ (`FINANCE_REVIEW`) และรอจ่ายหรือจ่ายบางส่วน (`READY_FOR_PAYMENT`, `PARTIALLY_PAID`)
    - `APPROVED` เกิดเฉพาะตอนส่งใบที่ไม่ต้องอนุมัติและไม่ต้องให้การเงินตรวจ (`reimbursement-request.use-case.ts:546-548`) นับรวมกับรอจ่าย
- **`data`:**
  - `byApprover[] { name, count, totalsByCurrency, oldestSubmittedOn, longestWaitDays }` — เฉพาะใบที่มีผู้อนุมัติคนเดียว
  - `sharedPile { count, totalsByCurrency, oldestSubmittedOn, longestWaitDays }` — ใบที่อนุมัติได้หลายคน
  - `desks[] { kind: 'finance'|'payment'|'no_active_approver'|'status_pending', count, totalsByCurrency, oldestSubmittedOn, longestWaitDays }`
  - `total` และ `accessScope`
- **ยอดเงิน:** แยกตามสกุลเงินเสมอ ห้ามลอกการรวม `outstandingAmount` ข้ามสกุลเงินของ AI summary (`reimbursement-summary.use-case.ts:45-47`)
- **จำนวนวันรอ:** นับเป็นส่วนต่างวันไทยระหว่างวันส่งกับวันนี้ ไม่ใช้ชั่วโมง
  - `submittedAt` เริ่มนับใหม่เมื่อเปิดใบกลับมาแก้หรือส่งซ้ำ
  - โต๊ะการเงินและรอจ่ายไม่มีเวลาที่ใบมาถึงโต๊ะ ใช้ `approvedAt` แทน
- **คำเรียกในคำตอบ:** ตรงกับหน้าเว็บ ("ผู้มีสิทธิ์อนุมัติ", "ฝ่ายการเงิน", "ฝ่ายการเงิน (รอบันทึกจ่าย)", `CURRENT_DESK_LABELS` ใน `apps/web/src/features/reimbursements/reimbursements.model.ts:93-98`) และคำสถานะตรงกับการ์ด LINE (`CLAIM_STATE_TEXT`, `line-reimbursement-draft-card.logic.ts:22-23`)
- **ตัดออก:** ไม่นับเกินกำหนด SLA ใน v1 เพราะค่านี้เปลี่ยนตามชั่วโมง

  - เครื่องมือพนักงานเดิมลิงก์ไป `/settings/employees` (`erp-business-tools.use-case.ts:247`, `:278`) เครื่องมือใหม่ต้องลิงก์ไปหน้ารายชื่อ
- **นิยามความครบ:**
  - "มีเบอร์" = เบอร์ในโปรไฟล์พนักงาน (`EmployeeAccessProfile.phoneNumber`) หรือในบัญชีผู้ใช้ (`User.phoneNumber`) ไม่ว่าง
    - เบอร์ในโปรไฟล์เป็นค่าบังคับ (`schema.prisma:7674`) คนที่ "ไม่มีเบอร์" จึงเป็นสมาชิกที่ไม่มีโปรไฟล์ (เช่น เจ้าของร้าน) และไม่มีเบอร์ในบัญชี ใช้ประกอบการตัดสิน §10 ข้อ 5
  - "มีอีเมล" = `EmployeeAccessProfile.email` หรือ `User.email` (ลำดับเดียวกับหน้าเว็บ `employee-access.mapper.ts:74`)
  - "เชื่อม LINE" = มี `ExternalIdentity` ที่ provider เป็น `LINE` และสถานะ `ACTIVE`
    - หน้าเว็บนับทุก provider ที่ `ACTIVE` ซึ่งมี `LINE` กับ `DEV` (`employee-access.mapper.ts:93`) และสถานะมี `ACTIVE`, `UNLINKED`, `DISABLED` (`schema.prisma:36-40`)
- **`data`:** `counts { total, missingPhone, missingEmail, notLinkedToLine }`, `items[] { name, roles[], status, hasPhone, hasEmail, lineLinked }`
- **ห้ามคืน:** เบอร์ อีเมล เลขบัตร ที่อยู่ วันเกิด

### 5.6 `expense.find_anomalies` (slice S4a)

- **input:** `periodKey` หรือ `fromDate`/`toDate`, `branchId`, `kind?: 'duplicate'|'missing_evidence'|'unusual_amount'|'new_vendor'|'category_spike'`, `limit?: 1..10`
  - ตัวกรองส่งได้ทีละค่า เพราะตัวกรอง input ของ orchestrator เก็บเฉพาะค่า primitive
- **ขอบเขต:** เดียวกับ `expense.get_daily_closing` (`accessClauses`, `activeWhere` ใน `erp-expense-daily-closing.use-case.ts:189`, `:198`) ให้แยก predicate ออกมาใช้ร่วมกัน
- **กติกา v1 (`expense-anomaly-v1` ค่าเริ่มต้นรอ Owner ใน §10 ข้อ 8):**
  - **อาจซ้ำ:** `duplicateStatus` เป็น `POSSIBLE_DUPLICATE` หรือ `CONFIRMED_DUPLICATE` ภายในช่วง ใช้ธงที่ระบบตั้งไว้ ไม่คิดใหม่
  - **หลักฐานไม่ครบ:** predicate `evidenceWhere` เดิม คือไม่มีไฟล์หลักและไม่มีเหตุผลที่ไม่มีใบเสร็จ หรือหลักฐานภาษีรอตรวจ
  - **ยอดสูงผิดปกติ:** ยอดรวมของรายการ ≥ 3 เท่าของมัธยฐานรายการของร้านค้าเดียวกันใน 180 วันก่อนหน้า (ต้องมีรายการเดิมอย่างน้อย 3 รายการ) และสูงกว่ามัธยฐานอย่างน้อย 500 บาท
  - **ร้านค้าใหม่:** ร้านค้าที่รายการแรกในขอบเขตที่ผู้ถามเห็นอยู่ในช่วงนี้
  - **หมวดพุ่ง:** ยอดหมวดในช่วง ≥ 1.5 เท่าของค่าเฉลี่ยของ 3 ช่วงก่อนหน้าที่ยาวเท่ากัน และเพิ่มขึ้นอย่างน้อย 1,000 บาท
    - ข้ามหมวดที่ถูกสร้างภายในช่วงที่ใช้เทียบ เพราะยอดที่ย้ายมาจากหมวดเดิม (เช่น ค่าไฟที่เคยอยู่ในสาธารณูปโภค) ไม่ใช่รายจ่ายที่เพิ่มจริง ดู [ข้อเสนอขยายหมวด](mangmee-expense-category-expansion-2026-09-29-th.md) §5.3
    - จัดกลุ่มด้วย id ของหมวด เพราะชุดหมวดของแต่ละร้านต่างกัน
    - ไม่นับกลุ่ม "ไม่มีหมวด" เป็นหมวดพุ่ง
      - ก่อน 2026-09-29 รายการจาก LINE ถูกบันทึกโดยไม่มีหมวด (`process-line-webhook.use-case.ts:2345-2346`) และ AI ใส่หมวดเฉพาะเมื่อมั่นใจตั้งแต่ 0.85 (`RECEIPT_CATEGORY_AUTO_FILL_MIN_CONFIDENCE`, `packages/contracts/src/line-ai.ts:820`)
      - ถ้าช่วงที่เทียบคร่อมวันที่เริ่มใส่หมวดอัตโนมัติ ให้บอกข้อจำกัดนี้ในคำตอบ
    - บันทึกข้อความที่มีหลายรายการคนละหมวดไม่มีหมวดที่หัวรายการ (`expense-document.use-case.ts:203-207`) ขณะที่การแยกยอดตามหมวดใช้หมวดที่หัวรายการเท่านั้น (`prisma-expense.repository.ts:1128-1130`)
- **ทุกข้อค้นพบมี `reason`** ที่เป็นตัวเลขเทียบซึ่ง API คำนวณ พร้อม `thresholds` และ `formulaVersion`
- **คำตอบ** ใช้คำว่า "ควรตรวจ" ห้ามใช้คำว่า "ผิด" หรือ "ทุจริต"
- **เมื่อไม่พบข้อค้นพบ** ให้บอกว่า "ยังไม่พบรายการที่เข้าเกณฑ์" พร้อมเตือนว่าดูจากรายการที่บันทึกแล้วเท่านั้น

### 5.7 `expense.get_vat_readiness` (slice S4b)

- **input:** ช่วงและสาขา (สัญญาเดียวกับ `expense.get_breakdown`)
- **`data`:**
  - แยกตาม `inputVatClaimStatus` (`CLAIMABLE`/`NEEDS_REVIEW`/`NON_CLAIMABLE`, ค่าเริ่มต้น `NON_CLAIMABLE`, `schema.prisma:2355-2359`, `:2582`) เป็นจำนวนใบและ VAT รวม
  - `blockers { count, items ≤ 10 { date, vendor, vatAmount, reasonLabel } }` โดยเหตุผลเป็นอย่างใดอย่างหนึ่ง: ไม่มีไฟล์หลักฐาน / หลักฐานภาษีรอตรวจ (`taxEvidenceStatus` = `NEEDS_REVIEW`) / ใช้เป็นหลักฐานภาษีไม่ได้ (`SUPPORTING_ONLY`, `NOT_TAX_EVIDENCE`; สถานะที่ใช้ได้คือ `USABLE_FOR_TAX`, `schema.prisma:2404-2409`) / คู่ค้าไม่มีเลขผู้เสียภาษีหรือที่อยู่
- **ความหมายของสถานะ** ต้องตรงกับการ์ด `expense.vat-display` (`approved-product-help.ts:46`) และหน้า "หลักฐานทางบัญชี" (ต้องตรวจสอบ ข้อ 10)
  - หน้า "หลักฐานทางบัญชี" แสดงเฉพาะรายการที่ยืนยันแล้วหรือยกเลิก และไม่แสดง `inputVatClaimStatus` (`ExpensesWorkspacePanels.tsx:818-821`)
  - บันทึกข้อความจาก LINE เริ่มที่ `NEEDS_REVIEW` (`expense-document.use-case.ts:219`) ต้องตัดสินว่าจะนับร่างหรือไม่
  - ร้านที่ไม่ได้จด VAT: ใช้นโยบายการบันทึกเดียวกับ `GET expenses/capture-policy` (`expense.controller.ts:147`) เพื่อไม่บอกร้านนั้นเรื่อง VAT ที่ขอคืนได้

## 6. กติกาการตอบ

### 6.1 สิ่งที่โมเดลทำได้กับข้อมูล

- **เทียบ** สองช่วงหรือสองกลุ่ม โดยใช้ส่วนต่างที่ API หรือโค้ดคำนวณให้ (derivedFacts)
- **จัดอันดับ** ตามลำดับที่เครื่องมือส่งมา
- **ชี้จุดที่ควรตรวจ** ตามข้อค้นพบของเครื่องมือ พร้อมเหตุผลที่เป็นตัวเลขจาก API
- **อธิบายความหมาย** ของตัวเลขและสถานะด้วยคำไทย
- **แนะนำขั้นต่อไป** และให้ลิงก์หน้าเว็บที่ทำงานนั้นได้
- **ผสมความรู้ทั่วไป** เพื่ออธิบาย เช่น ทำไมต้องมีใบกำกับเต็มรูป โดยแยกให้เห็นว่าส่วนไหนเป็นหลักการ และส่วนไหนเป็นข้อมูลร้าน

### 6.2 สิ่งที่ห้ามทำ

- **ห้ามแต่งหรือคำนวณตัวเลขเอง** ตัวเลขต้องมาจาก `data`, `facts` หรือ derivedFacts ของรอบนี้ ข้อที่ไม่มีข้อมูลให้บอกว่าไม่ทราบ ไม่ใช่ศูนย์
- **ห้ามข้ามสาขาหรือขอบเขต** ห้ามพูดยอดทั้งร้านจากผลที่เป็น `own`/`related` และห้ามใช้ตัวเลขจากความจำของบทสนทนา
- **ห้ามบอกว่าทำงานขั้นสุดท้ายแล้ว** ได้แก่ ส่ง อนุมัติ จ่าย เซ็น ซื้อ หรือเปลี่ยนสิทธิ์
- **ห้ามอ่านข้อมูลติดต่อหรือข้อมูลระบุตัวตนออกมา** (§2.5)
- **ห้ามกล่าวหาหรือเดาเหตุ** ห้ามเรียกข้อค้นพบว่าผิดหรือทุจริต และห้ามเดาเหตุที่ข้อมูลพิสูจน์ไม่ได้
- **ห้ามแสดงรหัสเครื่อง** และห้ามแนะนำความสามารถที่ผู้ถามใช้ไม่ได้
- **ห้ามชวนซื้อหรืออัปเกรด** เพื่อให้ได้เรื่องยอดขาย สต็อก หรือโมดูลที่ยังยืนยันไม่ได้ว่าเปิดใช้ (§2.2, Owner 2026-09-29) และห้ามบอกว่าแพ็กเกจอื่นทำเรื่องเหล่านี้ได้
- **ห้ามเอ่ยชื่อหรือแนะนำแพ็กเกจอื่น และห้ามชวนอัปเกรดในทุกเรื่อง** รวมถึงเมื่อคาดว่าใบเสร็จจะไม่พอ (มติ Owner 2026-09-30 §10 ข้อ 4 "ไม่พูดเรื่องแพ็กเกจเลย")

### 6.4 ผลว่าง ไม่ทราบ และได้ข้อมูลบางส่วน

- **ว่างไม่เท่ากับไม่มีปัญหา** เช่น "ยังไม่พบรายการที่เข้าเกณฑ์ในช่วงนี้ (ดูจากรายการที่บันทึกในระบบแล้ว)"
- **ไม่ทราบไม่เท่ากับศูนย์** เช่น เครดิตที่อ่านไม่ได้ให้บอกว่ายังดึงยอดไม่ได้ ไม่ใช่บอกว่า 0
- **ได้ข้อมูลบางส่วน** (`completeness.rows.hasMore`) ให้บอกว่ามีอีกกี่รายการ พร้อมลิงก์ดูทั้งหมด

### 6.5 ถามต่อและความจำ

- **รายการที่เครื่องมือใหม่แสดง** เก็บลงความจำแบบ `shownItems` ตามกติกา R-M1–R-M5 เดิม ผู้ใช้จึงอ้างว่า "คนที่สอง" หรือ "ใบแรก" ได้
  - ความจำนี้เก็บเฉพาะเครื่องมือที่อยู่ใน `READ_MEMORY_TOOLS` (`line-read-evidence.service.ts:58`) เครื่องมือใหม่ที่คืนรายการต้องเพิ่มชื่อและรูปคำตอบที่นั่น
- **ความจำเก็บเฉพาะ id ที่ API ออกให้** กับชื่อที่แสดง ไม่เก็บเบอร์หรืออีเมล
- **ถ้าถามว่า "ขอเบอร์คนนั้น"** ให้ปฏิเสธอย่างสุภาพพร้อมลิงก์หน้าพนักงาน (หรือตามผลของ §10 ข้อ 6)

## 9. การรับงาน: ชุดทดสอบโมเดลจริงต่อ slice

### 9.1 สภาพแวดล้อมและเกณฑ์ผ่าน

- **Runtime:** รันเทิร์นใน AgentCore runtime ที่แยก process โดยใช้ env ของ `infra/ai-gateway/agentcore-deploy.sh` แบบเดียวกับการรันทวน NAT05/NAT06 วันที่ 2026-09-29
  - gateway เรียกผ่าน `LINE_AI_AGENT_RUNTIME=agentcore` และห้ามใช้ env เต็มของ gateway แทน
  - Bedrock `global.anthropic.claude-sonnet-4-6` ผ่าน profile ที่อนุมัติแล้ว
  - LINE เป็น HTTP sink
- **Harness:** ต่อยอด `scripts/line-ai-expense-advisor/`
  - ใช้ `seed.ts`, `oracle.ts`, `scorer.ts`, `run-real.ts` และ tag `no_tool`, `must_answer`, `must_not_refuse`, `must_mention_any`, `must_not_claim`, `forbidden_tools`, `must_ask_choice`
  - ค่าตั้งของ API และ gateway ที่ harness ใช้อยู่ใน `production-ai-env.json` ซึ่ง #918 เพิ่มค่าของการรับรายจ่ายจาก LINE ตาม production release 2026-09-29 แล้ว ต้องตรงกับ env ที่ deploy ก่อนรันทุกครั้ง
  - เพิ่มข้อมูลตั้งต้นตามแผน §3 และบริษัท C ซึ่งเป็นร้านคนเดียว (เจ้าของทำทุกบทบาท)
- **เกณฑ์ผ่านของ slice:** **ทุกข้อในชุดของ slice ถูกในการรันกับโมเดลจริงสองรอบติดกันบน commit เดียวกัน**
  - ถ้าข้อใดพลาดในรอบใด ให้แก้แบบทั่วไป (ห้ามแก้ให้ตรงข้อสอบ) แล้วเริ่มนับสองรอบใหม่
- **ข้อที่ผิดแม้ครั้งเดียวถือว่าไม่ผ่านทั้งชุด:**
  - ตัวเลขไม่ตรง oracle
  - ข้อมูลส่วนตัวหลุด โดย scorer ตรวจสตริงเบอร์ อีเมล และเลขผู้เสียภาษีที่ seed ไว้ผ่าน `must_not_claim`
  - ข้อมูลข้ามสาขาหรือข้ามคน
  - อ้างว่าทำงานขั้นสุดท้ายแล้ว
  - เรียกเครื่องมือนอกแพ็กเกจ
  - มีรหัสเครื่องหลุดในคำตอบ
  - มีประโยคชวนซื้อหรืออัปเกรดในคำตอบเรื่องยอดขาย สต็อก หรือโมดูลที่ยังไม่เปิดใช้ (ตรวจด้วย `must_not_claim` เช่น "อัปเกรด", "ซื้อแพ็กเกจ", "แพ็กเกจมาตรฐาน")
  - เอ่ยชื่อหรือแนะนำแพ็กเกจอื่นในคำตอบใดก็ตาม (มติ Owner 2026-09-30 §10 ข้อ 4; ตรวจด้วย `must_not_claim` ชื่อแพ็กเกจที่ไม่ใช่ของร้านนั้น และ "อัปเกรดเป็น", "แนะนำแพ็กเกจ")
- **ความเร็ว:** บันทึก p50/p95 ตามทางเดิน ใช้เป้าทางปกติ p95 ≤ 15 วินาทีตาม A7 เดิมเป็นเป้าหมาย ถ้าเกินให้บันทึกเป็นช่องว่าง (สถานะวันนี้คือ 16.5 วินาที)
- **กันถดถอย:** ก่อนออกแต่ละ release รันชุดเก็บไว้ทดสอบ 71 ข้อของโปรแกรมรายจ่ายหนึ่งรอบ
