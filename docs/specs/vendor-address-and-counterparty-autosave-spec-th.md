## 2. เป้าหมาย

- ทุกใบที่ตรวจในระบบมีช่อง "ที่อยู่ผู้ขายตามใบ" และเมื่อเคยซื้อร้านนี้แล้ว ช่องเติมให้เองโดยไม่ต้องพิมพ์ซ้ำ
- ทะเบียนคู่ค้าโตเองจากการทำงานปกติ ไม่ต้องมีคนมานั่งกรอกทะเบียนก่อน
- หนังสือรับรอง 50 ทวิ และรายงาน WHT ได้ที่อยู่ผู้ถูกหักจากทะเบียนหรือจากใบ ไม่ใช่ค่าว่าง
- ไม่มีขั้นตอนใดของงานนี้หยุดผู้ใช้ไว้กลางทาง และไม่มีอะไรถูกเก็บหรือถูกตัดออกโดยไม่บอก

## 3. ขอบเขต

อยู่ในงานนี้ (Slice 1 และ 2):

- ช่อง `vendorAddressSnapshot` บนรายจ่าย + หน้าตรวจ + ส่งออก + tax event + prefill ใบทดแทนและ 50 ทวิ
- ทะเบียนคู่ค้า: หน้ารายการและหน้ารายละเอียด/แก้ไข (ลูกค้า ผู้ขาย ทั้งคู่) พร้อมที่อยู่ ที่มาของที่อยู่ และที่อยู่อื่นที่พบบนใบ
- ออโต้จับคู่และออโต้บันทึกคู่ค้าจากรายจ่าย ทั้งจากเว็บและจาก LINE
- OCR อ่านที่อยู่ผู้ขาย และผู้ซื้อตามที่พิมพ์ (Slice 2 ใช้ค่า)
- บั๊กและช่องว่างใน §9 ที่ระบุว่า "แก้ในงานนี้"

นอกงานนี้:

- พิมพ์ที่อยู่ลูกค้า/ที่อยู่เรา บนเอกสารที่เราออก และหน้ากรอกที่อยู่ลูกค้า (งานถัดไปตาม D1)
- ตัวพิมพ์หนังสือรับรอง 50 ทวิ ในระบบ (ยังเป็น handoff ภายนอกตาม gate เดิม งานนี้ทำให้ข้อมูลที่ส่งต่อครบ)
- เครื่องมือรวมคู่ค้าซ้ำ (merge) ระบุไว้เป็นงานถัดไป
- ที่อยู่แบบโครงสร้าง (ตำบล/อำเภอ/จังหวัด) สำหรับคู่ค้า ใช้เฉพาะเมื่อดึงจากกรมสรรพากรได้ ไม่บังคับกรอกเป็นช่อง
- ข้อมูลธนาคารของคู่ค้า

สิ่งที่เห็นใน FlowAccount (โครงเท่านั้น): สมุดรายชื่อเก็บ ประเภทผู้ติดต่อ (นิติบุคคล/บุคคลธรรมดา), ประเภท (ลูกค้า/ผู้จำหน่าย เลือกได้ทั้งคู่), เลขภาษี, สำนักงานใหญ่/สาขา, ที่อยู่เป็น textarea เดียว, รหัสไปรษณีย์แยก, ที่อยู่จัดส่ง, ปุ่ม "ค้นหาจากฐานข้อมูลกรมสรรพากร" เติมชื่อ/ที่อยู่จากเลขภาษี; เอกสารรายจ่ายมีสำเนาที่อยู่ของตัวเองที่แก้ได้; หัก ณ ที่จ่าย ดึงชื่อ ที่อยู่ เลขภาษี สาขา ของผู้ถูกหักมาจากเอกสารรายจ่าย

## 6. โมเดลข้อมูล

**ExpenseRecord** เพิ่ม `vendorAddressSnapshot String?` (≤ 500) ข้อความตามใบ ไม่ backfill แก้ได้ภายใต้กฎเดิมของหน้าตรวจทุกประการ คือสถานะอยู่ใน DRAFT / NEEDS_REVIEW / READY_FOR_CONFIRMATION และรายการยังไม่ถูกใบเบิกอ้างสิทธิ์ ไม่สร้างข้อยกเว้นใหม่ (CON-11); `vendorSnapshotJson` ที่เขียนใหม่มี `{id, name, taxId, branchCode, addressText}`;

`vendorBranchCodeSnapshot` (คอลัมน์เดิม) ได้กฎที่ยังไม่เคยมี: รับเฉพาะตัวเลข 5 หลัก เก็บ `null` เมื่อว่าง ห้ามเขียนสตริง `'00000'` ลงฐานข้อมูล และตัวจับคู่คู่ค้าถือ `null` เท่ากับ `'00000'` (สำนักงานใหญ่) ตามสัญญาเดิมของฝั่งขาย (CON-8)

`vendorEntityKindSnapshot` (คอลัมน์เดิม) ใช้ enum เดียวกับ `AccountingCounterparty.entityKind` จึงส่งค่ากันได้ตรงๆ ทั้งสองทาง (CON-7) Slice 2 เพิ่ม `buyerAsPrintedJson Json?` โครง `{name, taxId, branchCode, addressText, matchStatus: 'MATCH'|'MISMATCH'|'UNCHECKED'|'NOT_PRINTED', checkedAt, overrideReason?}` (implement 21 ก.ย. 2569 เพิ่มแบบ additive: `reasons` = TAX_ID/BRANCH/NAME/POSTAL_CODE, `differences` = ค่าบนใบกับค่าทะเบียนที่ใช้เทียบต่อเหตุผล ณ `checkedAt`, `overriddenByUserId`, `overriddenAt`, `claimStatusBeforeMark` (สถานะสิทธิ์ภาษีซื้อก่อนคนกดทำเครื่องหมาย ใช้คืนค่าเมื่อกดยกเลิก); contract `ExpenseBuyerAsPrinted`, detail DTO ส่งเป็น `buyerAsPrinted`)

**AccountingCounterparty.billingAddressJson** กำหนดโครง v2 แบบ additive ทุกผู้อ่านเลือก `addressText` ก่อนเมื่อมี คีย์เดิมคงไว้:

```ts
type CounterpartyAddressV2 = {
  addressText: string;            // ที่พิมพ์ลงเอกสาร
  postalCode?: string | null;     // 5 หลัก เมื่อแยกได้
  structured?: CompanyLegalAddress | null; // เฉพาะเมื่อดึงจากกรมสรรพากรหรือกรอกแบบโครง
  provenance: { source: 'MANUAL' | 'EXPENSE_AUTO' | 'RD_LOOKUP' | 'OCR' | 'PROCUREMENT'; expenseId?: string; userId: string; at: string };
  seenOnDocuments?: Array<{ addressText: string; expenseId: string; at: string }>; // ที่อยู่อื่นที่พบบนใบ สูงสุด 5 รายการล่าสุด
};
```

ที่อยู่ที่ "พิมพ์ลงเอกสาร" ของคู่ค้ามีแหล่งเดียวคือ `billingAddressJson.addressText` ฝั่งจัดซื้อ (`SupplierProfile.addressJson`) และลูกค้า CRM เป็นข้อมูลปฏิบัติการของโมดูลนั้น งานนี้ไม่ซิงก์ย้อน แต่หน้าคู่ค้าแสดงลิงก์ไปโปรไฟล์ซัพพลายเออร์เมื่อมี

ไม่มีตารางใหม่ ไม่มี permission key ใหม่ ไม่มี enum ใหม่

## 7. การได้ที่อยู่มา และการบันทึกทะเบียนคู่ค้าอัตโนมัติ

ลำดับการเติมช่องในหน้าตรวจ: ค่าที่ผู้ใช้พิมพ์ > ค่าที่ OCR อ่านได้ (ติดป้าย AI ให้ยืนยันเหมือนช่องอื่น) > ค่าจากทะเบียนคู่ค้าเมื่อจับคู่ได้ (ติดป้าย "จากทะเบียน") > ว่าง

ออโต้บันทึกทะเบียน (D4) ทำงานทุกครั้งที่บันทึกรายจ่ายที่มีชื่อผู้ขาย ทั้งจากเว็บ (บันทึกร่าง บันทึกการตรวจ ยืนยัน) และจาก LINE (หลัง OCR apply) ด้วยกติกาสี่กรณี:

ข้ามออโต้บันทึกทั้งหมดเมื่อรายจ่ายนั้นเป็นรายการที่ระบบสร้างเอง (`captureSource='API_INTERNAL'` หรือมี `sourceReimbursementRequestId`) เพราะชื่อผู้ขายของมันคือ "เบิกคืนพนักงาน: …" ไม่ใช่ร้านค้าจริง (CON-4)

| กรณี | ระบบทำ | ผู้ใช้เห็น |
|---|---|---|
| a ไม่พบคู่ค้าที่ตรงกุญแจ A2 | สร้างคู่ค้า VENDOR ใหม่ {ชื่อ, เลขภาษี, รหัสสาขา, ประเภทนิติบุคคล, ที่อยู่ตามใบเป็นที่อยู่หลัก, provenance EXPENSE_AUTO} แล้วผูก `vendorCounterpartyId` | toast "เพิ่ม [ร้าน] ลงทะเบียนคู่ค้าแล้ว · ดู" |
| b พบคู่ค้า แต่ทะเบียนไม่มีที่อยู่ | เติมที่อยู่ตามใบเป็นที่อยู่หลัก provenance EXPENSE_AUTO เฉพาะเมื่อใบมีที่อยู่ ถ้าทั้งสองฝั่งว่างเป็น NOOP | toast "บันทึกที่อยู่ของ [ร้าน] ลงทะเบียนแล้ว · ดู" เฉพาะการบันทึกที่เติมที่อยู่สำเร็จครั้งนั้น การบันทึกถัดไปไม่แจ้งซ้ำ |
| c พบคู่ค้า ทะเบียนมีที่อยู่ และต่างจากใบหลัง normalize | ไม่ล็อก: ที่อยู่ของใบนี้กลายเป็นที่อยู่หลัก ที่อยู่เดิมเข้าประวัติ `seenOnDocuments` · ล็อกอยู่: ที่อยู่หลักคงเดิม ที่อยู่ของใบเข้าประวัติ ใบยังเก็บของตัวเองเสมอ | บรรทัดข้อมูลบรรทัดเดียวใต้ช่อง ไม่มีปุ่ม: "ที่อยู่ต่างจากใบครั้งก่อน ระบบจำอันล่าสุดนี้ไว้เติมให้ครั้งหน้า ดูประวัติที่หน้าคู่ค้า" (หรือ "…ทะเบียนล็อกไว้ จึงเก็บเฉพาะใบนี้") |
| d พบคู่ค้าและที่อยู่เท่ากัน | ผูก `vendorCounterpartyId` ถ้ายังไม่ผูก | ไม่มีข้อความ |

กติกาเพิ่มเติม:

- ผู้ขายที่ไม่มีเลขภาษีและชื่อไม่ตรงทั้งคำกับทะเบียน ถือเป็นกรณี a (สร้างใหม่) ยกเว้นชื่อว่างเปล่าซึ่งข้ามการจับคู่ทั้งหมด
- การค้นหาคู่ค้าเพื่อจับคู่ **ไม่กรองตาม `type`** จึงเจอแถวที่ CRM หรือจัดซื้อสร้างไว้ก่อน และไม่สร้างซ้ำ (CON-12) เมื่อจับคู่เจอแถวที่เป็น CUSTOMER ให้เลื่อนเป็น BOTH ใน transaction เดียวกัน
- เมื่อจับคู่ได้และช่อง `vendorEntityKindSnapshot` ของใบยังว่าง ให้เติมจาก `entityKind` ของทะเบียน และเมื่อผู้ตรวจเลือกค่านี้เองให้บันทึกกลับทะเบียนด้วยกติกาเดียวกับที่อยู่ (CON-7) ค่านี้จำเป็นต่อการยืนยันรายจ่ายที่มีหัก ณ ที่จ่าย
- การ normalize ที่อยู่: ตัดช่องว่างซ้ำ แปลง ถ./ถนน ซ./ซอย ต./ตำบล อ./อำเภอ จ./จังหวัด แขวง/เขต ให้เป็นรูปเดียวกัน ตัดเครื่องหมายวรรคตอน เทียบไม่สนตัวพิมพ์
- ทุกการเขียนทะเบียนอัตโนมัติมี audit `accounting.counterparty.create` หรือ `.update` พร้อม `metadataJson.source = 'expense_auto_link'` และ `expenseId` **ห้ามส่งค่าที่อยู่เข้า metadata ตั้งแต่ต้น** ส่งเพียง `addressChanged: true` เพราะตัวกรองข้อมูลอ่อนไหวของ audit จับเฉพาะคีย์กลุ่ม token/password/body/content จึงไม่ช่วยปิดบังที่อยู่ให้ และห้ามแก้ตัวกรองนั้นเพราะจะไปลบคีย์ชื่อคล้ายกันของสเปคตัวตนภาษี (CON-10)
- การเขียนทะเบียนอยู่ใน transaction เดียวกับรายจ่ายเมื่อทำได้ แต่ถ้าล้มเหลว (เช่น ชนกันพร้อมกัน) รายจ่ายต้องบันทึกสำเร็จเสมอ และแสดง "ยังไม่ได้บันทึกลงทะเบียนคู่ค้า ลองใหม่ได้จากหน้าคู่ค้า" ไม่ล้มรายจ่ายเพราะทะเบียน
- **ไม่เพิ่ม launch gate ใดทั้งสิ้น** การสร้างคู่ค้าฝั่งผู้ขายขี่สิทธิ์และ entitlement ของการเขียนรายจ่ายที่ผ่านมาแล้ว ต่างจากตัวสร้างฝั่งลูกค้าซึ่งผูกกับ gate ของเอกสารขาย การลอกมาทั้งก้อนจะทำให้บริษัทที่ยังไม่เปิดเอกสารขายบันทึกรายจ่ายไม่ได้ (CON-3)
- LINE: ทำงานเงียบฝั่งเซิร์ฟเวอร์ ข้อความสรุปการบันทึกที่มีอยู่แล้วเพิ่มบรรทัดเดียวเฉพาะกรณี a "บันทึกร้านนี้ลงทะเบียนคู่ค้าแล้ว" ไม่ถามซ้ำ
- หน้าคู่ค้าเท่านั้นที่มีปุ่ม "ใช้อันนี้เป็นหลัก" บนรายการประวัติ (สิทธิ์ `accounting.counterparty.manage`) และสวิตช์ "ล็อกที่อยู่หลัก" หน้าตรวจไม่มีการตัดสินใจเรื่องทะเบียนเลย
- รหัสสาขาบนหน้าตรวจ: สำนักงานใหญ่/สาขา + ช่องรหัส 5 หลัก (`vendorBranchCodeSnapshot` เดิม) ไม่บังคับ OCR เติมได้ ว่าง = 00000 รหัสใหม่ที่ยังไม่มีในทะเบียน = สร้างคู่ค้าแถวใหม่ตามกรณี a พร้อม toast ที่บอกว่าเป็นสาขา

OCR (D3 ก้าวที่สอง): เพิ่มช่อง `vendorAddress` และกลุ่ม `buyerAsPrinted {name, taxId, branchCode, addressText}` ใน `ReceiptOcrFieldResult` และ prompt ต้องแยกผู้ขายกับผู้ซื้ออย่างเด็ดขาดตามกฎเดิมของสเปคความถูกต้องภาษี (ห้ามเอาตัวตนผู้ซื้อไปใส่ช่องผู้ขาย) ค่าที่อ่านได้เข้าช่องพร้อมป้าย AI ค่าที่อ่านไม่ได้ปล่อยว่างพร้อม hint ไม่เดา และ `vendorAddressSnapshot` ต้องถูกเพิ่มเข้ารายการฟิลด์ที่ห้ามทับเมื่อผู้ตรวจบันทึกการตรวจไปแล้ว ชุดเดียวกับชื่อผู้ขาย เลขภาษี รหัสสาขา เลขที่เอกสาร และวันที่ มิฉะนั้นการอ่านใบซ้ำจะลบที่อยู่ที่คนพิมพ์ทิ้ง (CON-5)

ดึงจากกรมสรรพากร: หน้าคู่ค้ามีปุ่ม "ดึงชื่อ/ที่อยู่จากกรมสรรพากร" เมื่อเลขภาษีครบ 13 หลัก ใช้ `RdVatDetailAdapter` ของสเปคตั้งค่าตัวตนภาษีเมื่อ adapter นั้นพร้อม ก่อนหน้านั้นปุ่มไม่แสดง ผลลัพธ์เป็น suggestion ที่ต้องยืนยันก่อนเขียน (กติกาเดียวกับสเปคนั้น)

## 8. ตารางไม่บล็อก (D5)

ทุกเคสที่ระบบอาจหยุดผู้ใช้ และทางผ่านที่ต้องมี:

| เคส | ระบบทำ | ทางไปต่อที่ผู้ใช้เห็น |
|---|---|---|
| บันทึกร่าง/ตรวจ/ยืนยัน โดยที่อยู่ว่าง | บันทึกได้ทุกสถานะ | ไม่มีข้อความ ยกเว้นใบกำกับเต็มรูป: คำเตือนสีเหลืองใต้ช่อง "ใบกำกับเต็มรูปควรมีที่อยู่ผู้ขาย เติมจากใบหรือปล่อยไว้ก็ได้" |
| ใบกำกับเต็มรูปที่จะใช้ภาษีซื้อ แต่ที่อยู่ว่าง (D2) | ไม่แตะ `taxEvidenceStatus` และ `inputVatClaimStatus` (E11) ใบยังเป็น CLAIMABLE ตามเดิม | คำเตือนเดียวกัน + ใบเข้ารายการกรอง "ใบกำกับที่ยังไม่มีที่อยู่ผู้ขาย" ในหน้ารายจ่ายและใน checklist ของ workpaper ภ.พ.30 ว่ามีกี่ใบ ให้คนตัดสินก่อนยื่น |
| ที่อยู่ยาวเกิน 500 | ไม่ตัดเอง | ข้อความใต้ช่อง "ยาวเกิน 500 ตัวอักษร ตัดให้สั้นลง" บันทึกได้เมื่อแก้ ไม่มีอย่างอื่นค้าง |
| OCR อ่านที่อยู่ไม่ได้ / อ่านผิด | ช่องว่างหรือค่าติดป้าย AI | hint "AI อ่านที่อยู่ไม่ได้ พิมพ์เอง เลือกจากทะเบียน หรือปล่อยว่าง" |
| สร้าง/เติมทะเบียนคู่ค้าไม่สำเร็จ | รายจ่ายบันทึกสำเร็จเสมอ | แถบ "ยังไม่ได้บันทึกลงทะเบียนคู่ค้า ลองใหม่ได้จากหน้าคู่ค้า" |
| ที่อยู่บนใบต่างจากทะเบียน (กรณี c) | ล่าสุดเป็นหลักโดยอัตโนมัติ (หรือเก็บเฉพาะใบเมื่อล็อก) | บรรทัดข้อมูลเดียว ไม่มีปุ่ม ไม่มีอะไรต้องตัดสินใจ |

## 10. หนังสือรับรอง 50 ทวิ และ tax event

- `payeeSnapshot.address` ของ VAT_INPUT และ WHT จากรายจ่าย = `vendorAddressSnapshot` ถ้าว่างใช้ `billingAddressJson.addressText` ของคู่ค้าที่ผูกไว้ ถ้ายังว่างเป็น null ตามจริง
- `payerSnapshot.address` = ข้อความจาก `formatCompanyLegalAddress(company.addressJson)` เมื่อมี (แก้ BUG-1) รูปแบบ "เลขที่ ถนน แขวง/ตำบล เขต/อำเภอ จังหวัด รหัสไปรษณีย์" หนึ่งบรรทัด
- handoff prefill ส่งค่าเหล่านี้ต่อ หน้าตรวจก่อน handoff มีช่องที่อยู่ผู้ถูกหักให้พิมพ์ในที่ เมื่อพิมพ์แล้วบันทึกกลับทะเบียนคู่ค้าตามกติกา §7 (กรณี b หรือ c)
- รายงาน WHT แสดงคอลัมน์ที่อยู่ผู้ถูกหักเมื่อมี ไม่บังคับ
- ที่อยู่เป็นข้อมูลระบุตัวบุคคลสำหรับผู้ขายบุคคลธรรมดา คง redaction เดิมของ log และ audit

## 11. หน้าจอ

### 11.1 หน้าคู่ค้า (ใหม่)

- เส้นทาง `/companies/:companyId/counterparties` (รายการ) และ `/counterparties/:counterpartyId` (รายละเอียด/แก้ไข) เมนู "คู่ค้า" ใต้ การเงินและบัญชี สิทธิ์อ่าน `accounting.counterparty.read` แก้ `accounting.counterparty.manage` (ทั้งคู่มีอยู่แล้ว) และคนที่เพิ่มคู่ค้ารายนั้นเปิดและแก้แถวของตัวเองได้แม้ไม่ถือคีย์ (D8) API ส่ง `canEdit` มาให้หน้าจอ ไม่ให้หน้าจอคิดกติกาเอง ผู้ที่เปิดได้เพราะเป็นคนเพิ่มอย่างเดียวไม่เห็นป้ายการใช้งานและใบล่าสุด 5 ใบ เพราะเป็นข้อมูลรายจ่ายของทั้งบริษัท
- รายการ: ค้นหา ชิป ทั้งหมด/เคยซื้อ/เคยขาย/ยังไม่มีที่อยู่ แถวแสดง ชื่อ เลขภาษี สำนักงานใหญ่/สาขา ที่อยู่หนึ่งบรรทัด ป้ายการใช้งาน และป้าย "ยังไม่มีที่อยู่" ปุ่ม "เพิ่มคู่ค้า"
- รายละเอียด: ส่วน ตัวตน (ป้ายการใช้งาน "เคยซื้อ N ใบ / เคยขาย N ใบ" แทนตัวเลือกประเภท, ร้านนี้เป็น นิติบุคคล/บุคคลธรรมดา พร้อมคำอธิบายว่าใช้เลือกแบบ ภ.ง.ด.3/53, ชื่อที่แสดง, ชื่อตามทะเบียน, เลขภาษี, สำนักงานใหญ่/สาขา + รหัสสาขา (ถ้ามี) จัดแนวเดียวกันสูง 44 px, สถานะ VAT) · ที่อยู่ (textarea "ที่อยู่ตามเอกสาร", รหัสไปรษณีย์, ปุ่มดึงจากกรมสรรพากรเมื่อพร้อม, บรรทัดที่มา "อัปเดตอัตโนมัติจากใบล่าสุด EXP-… เมื่อ … โดย …") · ประวัติที่อยู่จากใบ (รายการ `seenOnDocuments` เรียงล่าสุดก่อน แถวแรกติดป้าย "ล่าสุด = ที่อยู่หลัก" แถวก่อนหน้ามีปุ่ม "ใช้อันนี้เป็นหลัก" + สวิตช์ "ล็อกที่อยู่หลัก" ที่หัวการ์ด) · ที่อยู่จัดส่ง (ไม่บังคับ) · ติดต่อ (ชื่อผู้ติดต่อ อีเมล เบอร์) · ใบล่าสุด 5 ใบ · ลิงก์ไปโปรไฟล์ซัพพลายเออร์/ลูกค้า CRM เมื่อมี
- สถานะที่ต้องมี: โหลด ผิดพลาด ไม่มีสิทธิ์ ว่าง อ่านอย่างเดียวสำหรับผู้ที่ไม่มีสิทธิ์แก้ บันทึกสำเร็จ และ conflict เมื่อมีคนแก้พร้อมกัน (ใช้ `expectedUpdatedAt`)
- ออกแบบที่ 390 px ก่อน เดสก์ท็อปสองคอลัมน์

### 11.2 หน้าตรวจรายจ่าย

- ช่อง "ที่อยู่ผู้ขายตามใบ" ใต้เลขประจำตัวผู้เสียภาษี textarea 2 ถึง 3 บรรทัด ป้าย AI เมื่อ OCR อ่านได้ ป้าย "จากทะเบียน" เมื่อเติมจากคู่ค้า
- ใต้ช่องเมื่อว่างและจับคู่ทะเบียนได้: "ทะเบียนมีที่อยู่: … [ใช้ที่อยู่นี้]"
- สำนักงานใหญ่/สาขา + รหัสสาขา (ถ้ามี) เป็นตัวควบคุมเดียวกับหน้าคู่ค้า ไม่ใช่ dropdown จากทะเบียน
- หลังบันทึก: toast ตามกรณี a/b ของ §7 และบรรทัดข้อมูลกรณี c ไม่มีปุ่มตัดสินใจ
- คำเตือนสีเหลืองสำหรับใบกำกับเต็มรูปที่ที่อยู่ว่าง ไม่ใช่ error ไม่ปิดปุ่มใด

### 11.3 LINE

- หลัง OCR ใบกำกับเต็มรูปที่อ่านที่อยู่ไม่ได้: ข้อความเดียว "อ่านที่อยู่ร้านจากใบไม่ได้ พิมพ์ที่อยู่ตามใบได้เลย หรือพิมพ์ ข้าม" คำตอบเข้าช่องเดียวกัน ข้ามหรือเงียบไม่ถามซ้ำ
- ข้อความสรุปหลังบันทึกเพิ่มบรรทัด "บันทึกร้านนี้ลงทะเบียนคู่ค้าแล้ว" เฉพาะกรณี a
- ไม่มีการเขียนฐานข้อมูลจาก AI โดยตรงตามเดิม

### 11.4 จุดอื่นที่แตะ

- หน้ารายการรายจ่าย: ตัวกรอง "ใบกำกับที่ยังไม่มีที่อยู่ผู้ขาย"
- workpaper ภ.พ.30: บรรทัด "ใบกำกับเต็มรูปในงวดนี้ที่ยังไม่มีที่อยู่ผู้ขาย N ใบ" พร้อมลิงก์ "ดูรายการ" ไปตัวกรองรายจ่ายที่ส่ง `fromDate`/`toDate` ของงวด (ตามวันที่เอกสาร) หน้ารายจ่ายกรองตามช่วงนั้นและแสดงช่วงวันที่ N นับจากตัวกรองเดียวกัน จึงตรงกับรายการที่เปิดเห็น แสดงเมื่อ N > 0 ไม่ตัดยอด ชิป "ยังไม่มีที่อยู่" ในหน้ารายจ่ายยังแสดงทุกงวด
- ใบทดแทน: prefill `payeeAddress`
- ส่งออก CSV: คอลัมน์ `vendor_address`
- ส่วน "ลูกค้าและคู่ค้า" เดิมในหน้าบัญชี: เหลือรายการล่าสุดและลิงก์ "จัดการคู่ค้า"

## 12. สัญญา API และสิทธิ์

- รายจ่าย: `vendorAddressSnapshot` ใน detail/summary/list, create/update input, และ review-fields input; list รับ `vendorAddressMissing`
- OCR: `ReceiptOcrFieldResult` เพิ่ม `vendorAddress?`, `buyerAsPrinted?`; `missingFields` เพิ่มค่า `vendorAddress` เฉพาะใบกำกับเต็มรูป
- คู่ค้า: `AccountingCounterpartyDetail.billingAddressJson` ตามโครง v2 บวก `locked?: boolean`; list รับ `usage` (bought/sold), `addressMissing`, `search` และไม่กรองตาม `type`; detail มี `recentExpenses[]`, `usageCounts`; PATCH ใช้ `expectedUpdatedAt`; endpoint `POST /counterparties/:id/promote-seen-address` (สิทธิ์ manage) ใช้จากหน้าคู่ค้าเท่านั้น รับ `expectedUpdatedAt` และตอบ `counterparty_conflict` เมื่อแถวถูกแก้ไปแล้ว (การบันทึกอัตโนมัติจากรายจ่ายก็ compare-and-set และลองใหม่สูงสุดสองครั้งโดยไม่ทำให้รายจ่ายล้มเหลว); ทุกแถวของ list มี `usageCounts`; `type` ถูกตั้งโดยระบบ (VENDOR เมื่อสร้างจากใบซื้อ, เลื่อนเป็น BOTH เมื่อถูกใช้ฝั่งขาย) ไม่รับจาก client อีกต่อไป
- ใช้ use case ใหม่ `EnsureVendorCounterpartyFromExpenseUseCase` ที่ทั้ง expense draft/review/confirm และ receipt-ocr-apply เรียก ไม่เรียก `CreateCounterpartyUseCase` ตรง (สิทธิ์ต่างกันตาม A3)
- tax: `payeeSnapshot.address` และ `payerSnapshot.address` มีค่าตาม §10; ที่อยู่ผู้ถูกหักที่พิมพ์บนหน้า handoff เก็บในคอลัมน์ `WhtCertificateHandoff.payeeAddress` (พร้อม `payeeAddressByUserId`, `payeeAddressAt`) ข้าง snapshot ไม่เขียนลง `prefillSnapshotJson` ที่ถูกล็อกด้วย hash; `POST /companies/:companyId/wht/payment-handoffs/:handoffId/payee-address` แก้ได้เฉพาะสถานะ `REQUIRED`
- error code ใหม่มีเพียง `counterparty_address_too_long`, `counterparty_branch_code_invalid`, `counterparty_conflict`, `EXPENSE_VENDOR_BRANCH_CODE_INVALID`, `EXPENSE_VENDOR_ADDRESS_TOO_LONG`, `wht_handoff_payee_address_required`, `wht_handoff_address_not_editable`, `expense_buyer_match_not_mismatch` และ `expense_buyer_match_reason_required` ทุกตัวมีข้อความไทย
- Slice 2: `POST /companies/:companyId/expenses/:expenseId/buyer-match/confirm` `{ reason }` (สิทธิ์ `expense.confirm`, เหตุผล 1–500 ตัวอักษร, ใช้ได้เฉพาะเมื่อผลเทียบเป็น MISMATCH, audit ไม่เก็บค่าที่พิมพ์บนใบ); detail ส่ง `buyerAsPrinted`

- การสร้างและเติมทะเบียนอัตโนมัติไม่ผูกกับ `accounting.counterparty.manage` ตาม A3 การทับที่อยู่หลักด้วยมือ การกด "ใช้อันนี้เป็นหลัก" และสวิตช์ล็อก ยังต้องถือคีย์นี้ หรือเป็นคนที่เพิ่มคู่ค้ารายนั้น (D8)
- ผู้ที่ไม่มีสิทธิ์อ่านคู่ค้า ยังพิมพ์ที่อยู่บนใบได้ตามปกติ toast ตัดลิงก์ "ดู" ออก ยกเว้นเมื่อการบันทึกครั้งนั้นเพิ่งสร้างคู่ค้า ผู้บันทึกคือคนเพิ่มจึงเปิดได้ (D8)
- ตัวกรองสิทธิ์ตามแพ็กเกจเก็บ `accounting.counterparty.*` ไว้เมื่อบริษัทเปิดค่าใช้จ่ายหรือเอกสารขายอย่างใดอย่างหนึ่ง ตรงกับเมนู "คู่ค้า" ที่ผูกทั้งสองฟีเจอร์ (แก้ 25 ก.ย. 2569: เดิมคีย์ manage อยู่ในชุดสิทธิ์ `pack.billing.operate` ของเอกสารขายเท่านั้น ร้านที่มีแต่ค่าใช้จ่าย ซึ่งคือทุกแพ็กเกจที่ขายอยู่ จึงแก้คู่ค้าไม่ได้แม้เป็นเจ้าของ)
- ทางของคนเพิ่มผ่านด่านเส้นทางด้วยคีย์ `expense.read_related` / `accounting.document.read_related` ที่สมาชิกทุกคนถือสำหรับเอกสารของตัวเอง แต่ละคีย์ผูกแพ็กเกจของฟีเจอร์ตัวเอง แล้ว use case ตัดสินจากคีย์คู่ค้าหรือ `createdByUserId` เท่านั้น
- ผู้ที่อัปโหลดไฟล์ใบเสร็จหลักซึ่งทำให้ระบบสร้างคู่ค้าอัตโนมัติ เปิดและแก้ได้เฉพาะคู่ค้ารายนั้น แม้ผู้ตรวจรายจ่ายเป็นคนกดบันทึก; เก็บผู้ใช้จากไฟล์ใบเสร็จที่ยังใช้งานอยู่ ณ เวลาสร้างคู่ค้า ไม่เปลี่ยนเมื่อรายจ่ายอื่นมาใช้คู่ค้าเดิม
- สิทธิ์เฉพาะแถวไม่เปิดรายการคู่ค้า ยอดใช้งาน หรือใบล่าสุด; API ตรวจบริษัท ผู้สร้าง และผู้ที่อัปโหลดใบต้นทางอีกครั้งก่อนอ่านหรือเขียน และส่งลิงก์กลับเฉพาะเมื่อยืนยันสิทธิ์แถวนั้นได้
- การแก้ทะเบียนคู่ค้าด้วยมือใช้สิทธิ์ทะเบียน ไม่ถูกบล็อกด้วยด่านเปิดเอกสารขายใหม่; การสร้างเอกสารขายยังใช้ด่านเดิม
- `vatStatus` ของคู่ค้าเป็นข้อมูลของฝั่งขาย ฝั่งผู้ขายแสดงเป็นป้ายเท่านั้น ห้ามนำมาเป็นเงื่อนไขของสิทธิภาษีซื้อในงานนี้ (CON-13)

## 15. การทดสอบ

- Unit API: matcher กุญแจ A2 และ normalize ที่อยู่, สี่กรณี a–d, failure isolation, `formatCompanyLegalAddress`, payeeSnapshot address precedence, export column, OCR apply ใส่ `vendorAddressSnapshot`, deriveTaxEvidence ไม่เปลี่ยนเพราะที่อยู่
- Unit web: validation ความยาว, ลำดับเติมช่อง (พิมพ์ > AI > ทะเบียน), การแสดงคำเตือน/แถบ/toast, ทะเบียนคีย์ AI
- Integration (Postgres จริง): ซื้อร้านใหม่สองครั้งพร้อมกัน → ได้คู่ค้าไม่เกินสองแถวและรายจ่ายทั้งสองสำเร็จ; ทะเบียนถูก update พร้อมกัน → conflict ไม่ทับกัน
- OCR: fixture ใหม่ 3 ใบ (ใบกำกับเต็มรูปมีสองที่อยู่, ใบกำกับอย่างย่อไม่มีที่อยู่ผู้ซื้อ, บิลเงินสดที่อยู่สั้น) ผ่านชุดทดสอบเดิมของสเปคความถูกต้องภาษี
- E2E: เว็บ ตรวจใบ → toast → เปิดหน้าคู่ค้า → เห็นที่มา; LINE fake harness ส่งใบกำกับ → ร่างมีที่อยู่ → คู่ค้าถูกสร้าง
- Permission: บทบาทที่ไม่มี counterparty.manage ยังพิมพ์ที่อยู่บนใบและเกิดออโต้บันทึกได้ แต่กดสลับที่อยู่หลักไม่ได้; ADMIN และผู้ถือ `pack.expense.review` เปิดหน้าคู่ค้าได้ (CON-2); ร้านที่มีแต่ค่าใช้จ่ายยังถือ `accounting.counterparty.manage` หลังกรองตามแพ็กเกจ; คนที่เพิ่มคู่ค้าแก้และสลับที่อยู่หลักของแถวตัวเองได้ แต่แก้แถวของคนอื่นไม่ได้ (D8)
- ความสอดคล้อง (หนึ่งเทสต์ต่อหนึ่งข้อ): รายจ่ายจากใบเบิกไม่สร้างคู่ค้า (CON-4) · บริษัทที่ปิดเอกสารขายยังบันทึกรายจ่ายและสร้างคู่ค้าได้ (CON-3) · อ่านใบซ้ำหลังบันทึกการตรวจไม่ทับที่อยู่ (CON-5) · คู่ค้า VENDOR ที่รับเงินฝั่งขายถูกเลื่อนเป็น BOTH และเครื่องมือสรุปรายรับเห็น (CON-1) · รหัสสาขาว่างเก็บ null และ 4 หลักถูกปฏิเสธ (CON-8) · เติม `vendorEntityKindSnapshot` จากทะเบียนแล้วยืนยันรายจ่ายที่มี WHT ได้ (CON-7) · audit ไม่มีค่าที่อยู่ (CON-10) · จับคู่เจอแถวที่ CRM สร้างไว้โดยไม่สร้างซ้ำ (CON-12) · จัดซื้อเขียนที่อยู่แล้วหน้าคู่ค้าอ่านได้ (CON-9)
