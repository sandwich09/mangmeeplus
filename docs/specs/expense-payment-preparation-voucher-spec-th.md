## 0. สรุปสำหรับเจ้าของ

1. **ใบเตรียมจ่าย/ใบสำคัญจ่าย เป็นเอกสารใบเดียว เลขเดียว**: รวมรายจ่ายที่ยืนยันแล้วของผู้รับเงินรายเดียว ให้ผู้มีอำนาจอนุมัติ แล้วบันทึกว่าจ่ายแล้วครั้งเดียวทั้งใบ จ่ายแล้วใบเดิมเลขเดิมคือใบสำคัญจ่าย เจ้าของร้านที่ทำเองคนเดียวกด 3 ครั้ง: สร้าง → ส่งและอนุมัติ → บันทึกว่าจ่ายแล้ว
2. **การจ่ายตรงปุ่มเดียวของวันนี้ไม่เปลี่ยน** ถ้าต้องการใบสำคัญจ่ายของการจ่ายตรง กดออกได้ และใบนั้นจะอยู่ในหน้ารายการเดียวกัน
3. **สวิตช์ตัวเดียว แบบเดียวกับบันทึกด้วยมือ**: ผู้ดูแลระบบเปิด–ปิดการแสดงเมนูรายร้าน ปิดแล้วเมนู ปุ่ม และลิงก์หาย เบื้องหลังทำงานเหมือนเดิม ข้อมูลอยู่ครบ ค่าเริ่มต้นคือ **ไม่แสดง** จนกว่าจะเปิดให้ร้านนั้น
4. **ไม่แตะรายการสิทธิ์ของแพ็กเกจ** จึงไม่มีผลต่อการซื้อ ต่ออายุ หรือดีลของร้านเดิม ใช้ได้ทุกแพ็กเกจที่มีรายจ่าย
5. **สิทธิ์ติ๊กเพิ่มได้ 5 ชุด**: ดู / จัดทำ / อนุมัติ / บันทึกจ่ายตามใบ / ออกใบสำคัญจ่ายจากการจ่ายตรง เจ้าของร้านติ๊กให้ตำแหน่งใดก็ได้ การให้พนักงานคนเดียวทำโดยสร้างตำแหน่งใหม่แล้วย้ายคนนั้นไป (ระบบให้หนึ่งคนหนึ่งตำแหน่ง)
6. **50 ทวิ**: ไม่เปลี่ยนวิธีออกและจุดนับภาษี เพิ่มหน้ารายการสำหรับร้านที่ออกในระบบได้ และช่องบันทึกว่าออกหนังสือรับรองเองแล้วบนหน้ารายจ่ายสำหรับทุกแพ็กเกจ
7. **รายจ่ายที่ออก 50 ทวิไปแล้วแต่ข้อมูลผิด**: เปิดกลับมาแก้หรือยกเลิกได้ ระบบยกเลิกใบเดิมให้เองพร้อมเหตุผลและประวัติ แก้เสร็จแล้วออกใบใหม่เลขใหม่ ทำไม่ได้กรณีเดียวคือภาษีงวดนั้นยื่นไปแล้ว
8. **หน้าจอ** ทำตามสิ่งที่ทำให้ FlowAccount ใช้ง่าย แต่จัดสำหรับมือถือ: เริ่มจากผู้รับเงิน ป้ายสถานะสี ปุ่มหลักหนึ่งปุ่มต่อการ์ด ฟอร์มจ่ายที่เติมให้ครบ
9. **ไม่ทำในรุ่นแรก**: ใบเบิกและบิลเจ้าหนี้ในใบเตรียมจ่าย, การย้ายจุดนับภาษี, การเตือนวันครบกำหนด, การทำรายการจาก LINE
10. **ตรวจกับโค้ดจริงแล้ว**: แบบนี้ทำได้ ไม่มีข้อใดต้องตัดสินใหม่ มีแปดจุดที่ปรับให้ตรงกับโค้ด (ตารางถัดไป) และพบบั๊กของเดิมห้าจุดที่กระทบร้านวันนี้ เสนอให้แก้ไปพร้อมกัน รอคำยืนยัน (§16.1)

## 1. มติเจ้าของ

### 1.1 มติตั้งต้น (11 ต.ค. 2569)

1. เป็นเมนูย่อยฝั่ง **รายจ่าย** เชื่อมของเดิมและเพิ่มส่วนที่ขาด ไม่สร้างระบบรายจ่ายชุดที่สอง
2. ใบเตรียมจ่ายและใบสำคัญจ่ายใช้ได้ตั้งแต่ STARTER_249 รวม BASIC_499, PRO_999 และ ENTERPRISE_1999
3. มีสวิตช์เปิด–ปิดแยกแต่ละฟีเจอร์ เปิดกลับแล้วใช้ข้อมูลเดิมต่อได้
4. แพ็กเกจ 249 เก็บข้อมูลที่จำเป็นต่อ 50 ทวิได้ แต่ไม่แสดงเมนูออก 50 ทวิและออกในระบบไม่ได้ เมื่ออัปเกรดเป็น 1999 ให้เห็นเมนูและใช้ข้อมูลเดิมกดออกได้
5. ทำ spec ก่อน

| D13 | รายจ่ายที่มี 50 ทวิแล้ว | "ถ้าเป็นเคสที่ลูกค้าให้ข้อมูลผิดแล้วอยากให้ออกใหม่ ควรออกได้ เพราะเคสนี้มีอยู่เยอะ แต่เราก็ทำประวัติ และยกเลิกใบเดิมอัตโนมัติ แล้วค่อยออกใบใหม่" → §10.6 |

### 1.3 สิ่งที่ยืนยันแล้ว และสิ่งที่ผู้เขียนกำหนดตามมา

ยืนยันแล้วทุกข้อของแบบ: D1–D18 เหลือคำยืนยันหนึ่งข้อที่ไม่ใช่เรื่องของแบบ: ให้แก้บั๊กของเดิมห้าจุดไปพร้อมงานนี้หรือไม่ (§16.1)

**ผลที่ตามมาจากการรวมเป็นเอกสารใบเดียว (D17) ซึ่งผู้เขียนกำหนดและแจ้งไว้ให้ทราบ:**

1. ชื่อที่ผู้ใช้เห็นคือ **"ใบเตรียมจ่าย/ใบสำคัญจ่าย"** ทั้งในเมนู หน้ารายการ และหัวหน้าเอกสาร
2. สิทธิ์เหลือ 5 ตัว และชุดที่ติ๊กได้เหลือ 5 ชุด เพราะ "ดูใบเตรียมจ่าย" กับ "ดูใบสำคัญจ่าย" เป็นการดูเอกสารใบเดียวกัน ตารางสิทธิ์ตามตำแหน่งที่ยืนยันแล้ว (D10) มีผลเท่าเดิม
3. เลขชุดเดียว ออกครั้งแรกตอนส่งอนุมัติ และใช้เลขนั้นจนเป็นใบสำคัญจ่าย ใบสำคัญจ่ายที่กดออกจากการจ่ายตรงได้เลขจากชุดเดียวกันตอนกดออก
4. ใบที่จ่ายแล้วซึ่งการจ่ายถูกยกเลิกภายหลัง มีสถานะ "ยกเลิก" พร้อมเหตุผล ไม่ย้อนกลับเป็นรอจ่าย

**ผลที่ตามมาจากการตรวจกับโค้ดจริง (D18) ซึ่งผู้เขียนกำหนดและแจ้งไว้ให้ทราบ:**

1. การรวมรายจ่ายเป็นผู้รับเงินรายเดียวกันโดยอัตโนมัติ ใช้ได้เฉพาะเมื่อเลขประจำตัวผู้เสียภาษีตรงกัน กรณีอื่นผู้จัดทำต้องติ๊กยืนยัน (ตาม D15) ระบบไม่เชื่อการผูกคู่ค้าที่มีอยู่บนรายจ่าย
2. การยกเลิกรายจ่ายที่มีภาษีหัก ณ ที่จ่าย ทำให้รายการรอออกหนังสือรับรองเป็นยกเลิกเสมอ แม้ยังไม่เคยออกใบ รายจ่ายที่ถูกยกเลิกจึงไม่ค้างเป็นงานรอออกในหน้ารายการ 50 ทวิ
3. หน้าต่างยืนยันของ "แก้ไขเอกสาร" และ "ยกเลิก" บนหน้ารายจ่าย เปลี่ยนเฉพาะเมื่อรายจ่ายมีหนังสือรับรอง รายจ่ายอื่นเห็นหน้าจอเหมือนเดิม
4. เมื่อสองคำสั่งชนกัน (เช่น ยกเลิกรายจ่ายขณะมีคนส่งอนุมัติหรือออกหนังสือรับรอง) ผู้ใช้ฝั่งที่แพ้ได้ข้อความให้ลองใหม่ ไม่ใช่ข้อผิดพลาดของระบบ

## 2. เป้าหมายและผู้ใช้

| ผู้ใช้ | ต้องการอะไร | ผลที่ต้องได้ |
|---|---|---|
| เจ้าของร้านทำเองคนเดียว (ส่วนใหญ่ใช้มือถือ) | บันทึกว่าจ่ายแล้วให้เร็วที่สุด และพิมพ์ใบสำคัญจ่ายเมื่อต้องใช้ | ทางจ่ายตรงปุ่มเดียวเหมือนเดิม เพิ่มปุ่ม "ออกใบสำคัญจ่าย" |
| ร้านที่แยกคนเตรียมกับคนอนุมัติ | รวมบิลของผู้ขายรายเดียวเป็นชุด ให้ผู้มีอำนาจดูก่อนโอน | ใบเตรียมจ่ายหนึ่งใบ อนุมัติ แล้วบันทึกจ่ายครั้งเดียว ได้ใบสำคัญจ่ายเอง |
| พนักงานที่ได้รับสิทธิ์เพิ่ม | จัดทำใบ หรือบันทึกจ่ายตามใบที่อนุมัติแล้ว | ทำได้เฉพาะงานที่ถูกติ๊ก และเฉพาะรายจ่ายที่ตนอ่านได้ |
| นักบัญชี/การเงิน | เอกสารภายในที่มีเลข ย้อนถึงรายจ่ายและการจ่ายจริงได้ | หน้ารายการใบเตรียมจ่าย/ใบสำคัญจ่าย ไฟล์ของใบที่จ่ายแล้วตรึงไว้ ไม่เปลี่ยนตามข้อมูลปัจจุบัน |
| ร้าน 1999 | หาและออก 50 ทวิได้จากที่เดียว | หน้ารายการ 50 ทวิ ลิงก์ไปปุ่มออก/แก้/ใบแทนที่มีอยู่ |
| ร้านต่ำกว่า 1999 ที่หักภาษี | เก็บว่าออกหนังสือรับรองให้ผู้รับแล้ว | การ์ดบนหน้ารายจ่ายสำหรับบันทึกฉบับที่ออกเอง |

ผลรวมที่ต้องได้: ไม่มียอดจ่ายซ้ำ ไม่มีภาษีหรือการลงบัญชีเกิดซ้ำจากเอกสารใหม่ ซ่อนเมนูแล้วข้อมูลและงานค้างไม่หายและทำต่อจนจบได้

## 3. แต่ละใบคืออะไร

ทุกหน้าจอที่แสดงชื่อเอกสารต้องมีคำอธิบายหนึ่งบรรทัดใต้ชื่อตามตารางนี้

| เอกสาร | คำอธิบายหนึ่งบรรทัด | สถานะในระบบ |
|---|---|---|
| ใบเตรียมจ่าย/ใบสำคัญจ่าย | ใบเดียว เลขเดียว: ก่อนจ่ายคือรายการที่จะจ่ายให้ผู้รับเงินรายหนึ่งและรออนุมัติ จ่ายแล้วคือเอกสารภายในที่สรุปว่าจ่ายเงินครั้งนี้เพื่อชำระอะไร | **ใหม่** |
| ใบรับรองแทนใบเสร็จ | ใช้แทนใบเสร็จเมื่อผู้ขายไม่ออกให้ | มีแล้ว ไม่เปลี่ยน |
| ใบสำคัญรับเงิน | ให้ผู้รับเงินลงชื่อว่าได้รับเงิน ใช้คู่ใบรับรองแทนใบเสร็จ | มีแล้ว ไม่เปลี่ยนชื่อ ไม่เปลี่ยน route ในโค้ดเอกสารนี้ชื่อ payment voucher เอกสารใหม่จึงใช้ชื่อในโค้ดว่า disbursement voucher (K01) |
| หนังสือรับรองหัก ณ ที่จ่าย (50 ทวิ) | หนังสือที่ต้องให้ผู้รับเงินเมื่อหักภาษีไว้ | มีแล้ว ไม่เปลี่ยนวิธีออก |

## 5. ขอบเขตรุ่นแรก

**รวม**

- ใบเตรียมจ่าย/ใบสำคัญจ่ายสำหรับรายจ่าย: หน้ารายการเดียว สร้าง/แก้ ส่งอนุมัติ อนุมัติ/ตีกลับ ยกเลิก บันทึกจ่าย แบบพิมพ์ก่อนจ่ายและหลังจ่าย
- ออกใบสำคัญจ่ายจากการจ่ายตรงที่มีอยู่ เมื่อกด
- ค่าตั้งหน้าจอ 1 ตัว สิทธิ์ใหม่ 5 ตัวในรูปชุดที่ติ๊กได้ 5 ชุด และการแจ้งเตือน 6 แบบ
- หน้ารายการ 50 ทวิสำหรับผู้มีสิทธิ์ออก และการ์ดบันทึกว่าออกหนังสือรับรองเองแล้วบนหน้ารายจ่าย
- รายจ่ายที่มีหนังสือรับรองแล้ว: เปิดกลับมาแก้หรือยกเลิกได้ โดยยกเลิกใบเดิมอัตโนมัติพร้อมประวัติ (§10.6)
- แบ่งหน้าและขอบเขตของรายการรอออก (§10.5) ซึ่งต้องเสร็จก่อนเปิดหน้ารายการ 50 ทวิ

**ไม่รวม** (รายละเอียดใน §16): ใบเบิกและบิลเจ้าหนี้ในใบเตรียมจ่าย, ใบสำคัญจ่ายของใบเบิก, การย้ายจุดรับรู้ภาษี, หนังสือรับรองหลายบรรทัด, การจองงานจ่ายกันโอนซ้ำนอกระบบ, การสั่งโอนเงินจริง, การเตือนวันครบกำหนด, การทำรายการจาก LINE, สกุลเงินอื่นนอกจากบาท, การติ๊กสิทธิ์รายคนโดยไม่สร้างตำแหน่ง, การบันทึกยอดจ่ายที่ต่างจากยอดอนุมัติ

## 6. เมนูและหน้าจอ

เมนูหลักไม่เปลี่ยน "การเบิกจ่าย" คงเป็นเมนูหลัก ไม่เพิ่มเมนูเจ้าหนี้ ไม่เพิ่ม "ลายเซ็นของฉัน" (การไม่แสดงมี test ล็อกไว้)

| ลูกใหม่ใต้ "รายจ่าย" | ปลายทาง (เติม `/companies/:companyId`) | เห็นเมื่อ |
|---|---|---|
| ใบเตรียมจ่าย/ใบสำคัญจ่าย | `/expenses/disbursement-vouchers`, `/new`, `/:id` | มี `expense.disbursement.read` **และ** ร้านถูกตั้งให้แสดง |
| หัก ณ ที่จ่าย (50 ทวิ) | `/expenses/wht-certificates` | มี `wht.certificate.issue` |

**คำสถานะที่ผู้ใช้เห็น (D17)** กำหนดที่เดียวใน contracts ตามกติกา one-source words ใช้เหมือนกันบนป้าย ตัวกรอง การแจ้งเตือน และใบพิมพ์

| สถานะในระบบ | คำที่ผู้ใช้เห็น | สีป้าย |
|---|---|---|
| DRAFT | ฉบับร่าง | เทา |
| PENDING_APPROVAL | รออนุมัติ | เหลือง |
| APPROVED | อนุมัติแล้ว รอจ่าย | ฟ้า |
| PAID | จ่ายแล้ว | เขียว |
| CANCELLED | ยกเลิก | แดงอ่อน |

**หน้ารายการ** (หน้าเดียวสำหรับทุกขั้น)

- ตัวกรองสถานะเป็นปุ่มเรียงแถวเดียว: ทั้งหมด, ฉบับร่าง, รออนุมัติ, รอจ่าย, จ่ายแล้ว, ยกเลิก ค่าเริ่มต้นคือทั้งหมด เรียงตามกำหนดจ่าย เน้นใบที่เลยกำหนด
- บนมือถือเป็นการ์ด: เลขที่ (ฉบับร่างแสดงว่ายังไม่มีเลข), ผู้รับเงิน, กำหนดจ่ายหรือวันที่จ่าย, ยอดจ่าย, ป้ายสถานะ, ปุ่มหลักหนึ่งปุ่มตามสิทธิ์ของผู้ดู (ส่งอนุมัติ / อนุมัติ / บันทึกว่าจ่ายแล้ว / ดูใบสำคัญจ่าย)
- ใบที่เกิดจากการกดออกจากการจ่ายตรง แสดงคำว่า "บันทึกจ่ายโดยตรง" ใต้เลขที่
- ปุ่มสร้างใหม่อยู่บนสุดของหน้า

**อื่น ๆ**

- เจ้าของร้าน 249 วันนี้เห็นลูกใต้รายจ่าย 6 รายการ เมื่อผู้ดูแลเปิดเมนูให้จะเป็น 7 รายการ ร้าน 1999 เพิ่มอีก 1
- เพิ่ม route rule เฉพาะของสองเส้นทางนี้ มิฉะนั้นจะถูกกติกา `/expenses` ตัดสินแทน ไม่แก้รายการสิทธิ์สามชุดของกลุ่มรายจ่ายที่ test บังคับให้เท่ากัน (route rule, module gate, menu binding) สิทธิ์ใหม่จึงไม่ทำให้กลุ่มรายจ่ายปรากฏด้วยตัวเอง ผู้ใช้ต้องมีสิทธิ์รายจ่ายอย่างน้อยหนึ่งตัวอยู่แล้ว ซึ่งทุกตำแหน่งมี
- กติกา route ฝั่งเว็บเป็นการบังหน้าจอ ตัวบังคับจริงคือ API ทุกคำสั่ง
- หน้ารายละเอียดรายจ่ายเพิ่ม: ป้าย "อยู่ในใบเตรียมจ่ายเลขที่ … จัดทำโดย …" พร้อมลิงก์, ปุ่ม "เพิ่มเข้าใบเตรียมจ่าย", ปุ่ม "ออกใบสำคัญจ่าย" และ "ดูใบสำคัญจ่าย" บนแถวการจ่าย, การ์ดหนังสือรับรองตาม §10.3 ทำเป็นไฟล์ component แยก ไม่ขยาย `ExpenseReviewPage.tsx` (2,245 บรรทัด) ตำแหน่งวางและข้อจำกัดอยู่ใน §6.1 ข้อ 12
- ปุ่มที่ spec นี้เรียกว่า "เปิดรายจ่ายกลับมาแก้" มีชื่อบนหน้าจอจริงว่า **"แก้ไขเอกสาร"** ชื่อปุ่มไม่เปลี่ยน
- เส้นทาง API ของเอกสารนี้อยู่ที่ controller ของตัวเอง (`companies/:companyId/disbursement-vouchers`) ตามแบบ `substitute-receipts` ไม่วางใต้ `…/expenses/` ซึ่งมี `:expenseId` รับอยู่
- หน้าเอกสารเป็น **หน้าเดียวแบบขั้นตอน**: รายการ → อนุมัติ → จ่าย → เอกสาร ใช้ `ThemedSteps` ที่เป็นของกลาง และเขียนตัวสร้างขั้นของตัวเอง ไม่ import ตัวสร้างของใบเบิก ฟอร์มจ่ายอยู่ในการ์ดของขั้น ไม่เป็น dialog
- ออกแบบที่ความกว้าง 390px ก่อน ปุ่มหลักเต็มความกว้าง ไม่ใช้ `h-screen`/`100vh`
- ข้อความภาษาไทยล้วน ป้ายใหม่ลงใน `workspace-dictionary.ts` ใต้ `expenses.*` ซึ่งถูกตรวจว่าไม่มีอักษรละติน (ยกเว้นคำที่อนุญาต) ไม่แสดงชื่อสถานะในระบบ รหัส หรือ id
- ลิงก์จาก LINE ที่มีอยู่ไม่เปลี่ยน

### 6.1 ข้อกำหนดหน้าจอจากผลศึกษา FlowAccount (D16)

ที่มาและเหตุผลรายข้ออยู่ใน [ผลศึกษา](../research/flowaccount-expense-payment-ux-study-2026-10-11-th.md) §5.1 ข้อเหล่านี้ไม่เปลี่ยนคำตัดสินใด

1. **เริ่มจากผู้รับเงิน**: ขั้นแรกของการสร้างใบเตรียมจ่ายคือเลือกผู้รับเงิน แล้วระบบแสดงรายจ่ายค้างของผู้รับเงินนั้นให้ติ๊ก พร้อมจำนวนรายการและยอดรวมที่ขยับตามทันที การเข้าจากปุ่มบนรายจ่ายถือว่าเลือกผู้รับเงินของรายจ่ายนั้นแล้ว
2. **ป้ายสถานะสี** บนทุกการ์ดและหัวหน้าเอกสาร และ **ปุ่มหลักหนึ่งปุ่มของขั้นถัดไป** ต่อการ์ด งานรองอยู่ในเมนูเพิ่มเติม
3. **ฟอร์มจ่ายเติมให้ครบ**: บนสุดเป็นข้อความอ่านอย่างเดียวว่าใบเลขใด จ่ายให้ใคร ยอดเท่าไร ตามด้วยวันที่ วิธีจ่าย แล้วช่องไม่บังคับ กรณีปกติกดบันทึกครั้งเดียว
4. **สรุปสามบรรทัด** บนใบและบนฟอร์มจ่าย: รวมเป็นเงิน, ภาษีหัก ณ ที่จ่ายของเอกสาร, ยอดจ่าย
5. **หน้าว่างมีประโยคเดียวบอกขั้นถัดไป** หรือบอกว่าทำไมจึงว่าง
6. **ออกจากหน้าที่ยังไม่บันทึก** มีคำถามพร้อมสามปุ่มที่ชื่อบอกผล: อยู่ต่อ, ไม่บันทึกและออก, บันทึกและออก
7. **ประวัติจัดกลุ่มตามวัน**: เวลา ผู้ทำ สิ่งที่เกิด และลิงก์ไปเอกสารที่เกี่ยว ใช้กับรุ่นของใบเตรียมจ่ายและประวัติหนังสือรับรอง บนมือถือเปิดเป็นแผ่นจากด้านล่าง
8. **สรุปการชำระแสดงใต้ยอดเงิน** ไม่ซ่อนหลังไอคอนหรือการชี้
9. **หลังบันทึกจ่ายรายจ่ายที่มีภาษีหัก ณ ที่จ่าย** หน้าจอเสนอขั้นถัดไปของหนังสือรับรองทันที: ผู้ที่ออกในระบบได้เห็นปุ่มออก 50 ทวิ ผู้ที่ออกไม่ได้เห็นทางบันทึกว่าออกเองแล้ว ระบบไม่ออกเอกสารภาษีเอง
10. **ปุ่มหลักอยู่ที่เดิมเสมอ** ไม่มีแผงหรือข้อความที่เปิดแล้วดันปุ่มหลักไปจากตำแหน่ง
11. ไม่แสดงรหัสบัญชีหรือคำของนักบัญชีในหน้าของงานนี้ ใช้ชื่อหมวดภาษาคน

ข้อ 12–19 มาจาก[ผลตรวจความเข้ากับโค้ดจริง](../research/expense-payment-voucher-code-fit-check-2026-10-11-th.md) §4

12. **หน้ารายละเอียดรายจ่าย**: ของใหม่ทุกชิ้นเป็น component ลูกที่ถือ state ของตัวเอง ไม่เพิ่ม hook ที่ถือ state ในระดับหน้า ไม่แก้ข้อความที่ test ล็อก ปุ่ม "เพิ่มเข้าใบเตรียมจ่าย" อยู่ในการ์ดการจ่าย ไม่อยู่ในแถบล่าง ปุ่มใบสำคัญจ่ายอยู่บนแถวการจ่ายเฉพาะในการ์ดการจ่าย ไม่ปรากฏในหน้าต่างปฏิเสธซึ่งแสดงแถวเดียวกัน
13. **หน้าต่างยืนยันบนหน้ารายจ่ายเปลี่ยนเฉพาะเมื่อมีหนังสือรับรอง**: "แก้ไขเอกสาร" ใช้หน้าต่างเดิมและเพิ่มเลขที่ใบกับช่องติ๊ก ส่วน "ยกเลิก" เปิดหน้าต่างแทนกล่องเหตุผลในแถบล่าง รายจ่ายที่ไม่มีหนังสือรับรองเห็นทั้งสองทางเหมือนเดิม
14. **หน้าต่างที่มีช่องกรอก** (เหตุผล ช่องติ๊ก ยอด) ไม่ปิดเมื่อแตะพื้นหลัง ปุ่มของหน้าต่างมีระยะเผื่อแถบล่างของเครื่อง บนจอแคบกว่า 640px เป็นแผ่นจากด้านล่างตาม `Modal` กลาง
15. **ตัวเลือกผู้รับเงินเป็นรายการเต็มหน้าที่ค้นจาก server** ไม่ใช้ช่องเลือกแบบหล่นลง (ซึ่งกรองได้เฉพาะตัวเลือกที่โหลดแล้ว และอาจถูกแป้นพิมพ์บัง) รายการรายจ่ายที่ติ๊กมีแถบยอดรวมติดขอบล่างพร้อมระยะเผื่อ
16. **ป้ายสถานะอยู่บรรทัดเดียว** รวม "อนุมัติแล้ว รอจ่าย" ตัวกรองสถานะเป็นตารางสองคอลัมน์ มีจำนวน ปุ่มสูงอย่างน้อย 44px
17. **ปุ่มบันทึกของฟอร์มจ่ายเต็มความกว้างและอยู่ตำแหน่งเดียวกับปุ่มหลักของการ์ด** ไม่คัดลอกการจัดวางของฟอร์มจ่ายใบเบิกซึ่งทำให้ปุ่มหลักหายและปุ่มบันทึกชิดขวา
18. **คำถามก่อนออกจากหน้า** สร้างบน `Modal` กลางสำหรับการไปหน้าอื่นในแอป และคงการเตือนของเบราว์เซอร์สำหรับการปิดแท็บ ประโยคบอกขั้นถัดไปของหน้าว่างใช้หัวเรื่องของ `EmptyState` ไม่ใช้คำอธิบายสีจาง
19. **ใช้ของกลางก่อนสร้างใหม่**: `MangmeeBadge`, `ThemedSteps`, ชุดสถานะสี่แบบ (ไม่ส่งรหัสคำขอให้หน้าข้อผิดพลาด), `useToast`, `ThemedFile`, `MoneyRow`, `baht()` และ `formatThaiDate` แบบเดียวทั้งฟีเจอร์ รายการการ์ดมี `data-testid` ลงท้าย `-card-list` เพื่อให้ชุดตรวจจอมือถือครอบได้ เมนูเพิ่มเติมแยกจาก `ReceiptActions` เป็นของกลาง

## 7. แพ็กเกจ สวิตช์ และสิทธิ์

### 7.1 ใครใช้ได้

| ความสามารถ | เงื่อนไข |
|---|---|
| ใบเตรียมจ่าย/ใบสำคัญจ่าย | ร้านมี "รายจ่าย" (ทุกแพ็กเกจที่ขายและทุกดีลมี) + ผู้ดูแลระบบตั้งให้แสดง + ผู้ใช้มีสิทธิ์ |
| เก็บข้อมูลภาษีหัก ณ ที่จ่าย และบันทึกว่าออกหนังสือรับรองเองแล้ว | ทุกแพ็กเกจ ตามสิทธิ์เดิม |
| เมนู 50 ทวิ และออกในระบบ | ร้านมี `wht_50bis` (1999 หรือดีลที่ขายสิทธิ์นี้) + ผู้ใช้มี `wht.certificate.issue` |

- **`FEATURE_CATALOG`, `STARTER_FEATURE_KEYS`, `TIER_FEATURE_PRESETS`, ดีล และระบบชำระเงินไม่เปลี่ยน** จำนวน key ยังเป็น 62
- สิทธิ์ใหม่ทั้งห้าอยู่ในชุดที่ผูก `expenses` ปิด "รายจ่าย" ทั้งหมดแล้วสิทธิ์ใหม่ถูกตัดตามกติกาเดิม
- ไม่มีราคา SKU หรือโควตาใหม่ ข้อความบนการ์ดแพ็กเกจและแคตตาล็อกใน LINE ไม่เปลี่ยน

### 7.2 ค่าตั้งหน้าจอหนึ่งตัว

| ค่าตั้ง | ป้ายบนหน้าผู้ดูแล | ไม่มีการตั้งค่า |
|---|---|---|
| `disbursementVoucherEntryEnabled` | แสดงเมนูใบเตรียมจ่าย/ใบสำคัญจ่ายบนเว็บ | ไม่แสดง |

**ที่เก็บและคำสั่ง** ตามแบบบันทึกด้วยมือทุกข้อ

- หนึ่งช่องใหม่ (ว่างได้) บนแถว `CompanyWebEntrySetting` เดิม ใช้ `version` ร่วมกับสวิตช์บันทึกด้วยมือ ช่องเดิมของบันทึกด้วยมือไม่ถูกแก้โครงสร้าง แถวที่ถูกสร้างขึ้นเพราะค่าตั้งใหม่เขียนช่องบันทึกด้วยมือเป็นค่าเริ่มต้นปัจจุบัน (ไม่แสดง) ร้านจึงเห็นเหมือนเดิม
- คำสั่งของผู้ดูแลระบบหนึ่งเส้นทาง รับ `{ enabled, expectedVersion }` ใช้สิทธิ์ `system.partner_feature.manage` เดิม มี audit และ 409 เมื่อ version ไม่ตรง
- ค่าเริ่มต้นอยู่ที่ค่าคงที่จุดเดียว ไม่มี default ในฐานข้อมูล
- `/auth/me` ส่งค่า boolean หนึ่งตัว เว็บถือว่า **ค่าที่หายไปคือไม่แสดง** (ต่างจากบันทึกด้วยมือที่ค่าหายคือแสดง เพราะเมนูใหม่ต้องไม่โผล่ให้ทุกร้านระหว่างที่ API กับเว็บเป็นคนละรุ่น)
- **ไม่มี guard, ตัวกรองสิทธิ์, ระบบชำระเงิน, LINE หรือ use case ทางธุรกิจใดอ่านค่านี้** เหมือนบันทึกด้วยมือ

**ซ่อนอะไร**

- ลูกเมนูใต้รายจ่าย
- ปุ่ม "เพิ่มเข้าใบเตรียมจ่าย", ปุ่ม "ออกใบสำคัญจ่าย" และลิงก์ไปเอกสารนี้บนหน้าอื่น
- หน้ารายการและหน้าสร้าง: เปิดด้วยลิงก์ตรงจะเห็นการ์ด "หน้านี้ไม่ได้เปิดใช้สำหรับร้านของคุณ" พร้อมปุ่มกลับ ไม่ redirect ไม่ขึ้นหน้าไม่มีสิทธิ์
- หน้าที่เปิดไว้ก่อนถูกซ่อนยังทำงานต่อได้จนออกจากหน้านั้น พร้อมบรรทัดแจ้ง

**ไม่ซ่อน และไม่เปลี่ยน**

- **หน้าของใบที่มีอยู่แล้ว** เปิดได้ตามสิทธิ์เสมอ จากป้ายบนรายจ่ายที่ถูกจองหรือจากการแจ้งเตือน งานค้างจึงทำต่อจนจบหรือยกเลิกได้ ไม่มีหนี้ค้างตายเพราะซ่อนเมนู
- คำสั่งทุกคำสั่งที่ API, ยอดจอง, การแจ้งเตือน, ข้อมูลและไฟล์ทั้งหมด
- เปิดแสดงกลับ: ทุกอย่างอยู่ตามเดิม ไม่มีการทำซ้ำอัตโนมัติ

**หน้าผู้ดูแล**

- หนึ่งแถวใต้การ์ด "ค่าใช้จ่าย+ใบเสร็จ" ของหน้ารายละเอียดร้าน ต่อจากแถวเมนูย่อย สถานะ "แสดง / ไม่แสดง"
- ล็อกเมื่อร้านปิด "รายจ่าย" หรือร้านถูกปิดใช้งาน และแสดงสิ่งที่ร้านเห็นจริง
- ถามยืนยันเฉพาะตอนซ่อน พร้อมข้อความว่าใบที่ค้างอยู่ยังเปิดจากหน้ารายจ่ายและทำต่อได้
- บันทึกแล้วไม่โหลดหน้าใหม่ สองสวิตช์ (รวมบันทึกด้วยมือ) ถือ `version` ร่วมกัน
- เมื่อเปิดแสดง หน้าผู้ดูแลบอกแบบอ่านอย่างเดียวว่าตำแหน่งใดของร้านมีสิทธิ์ของฟีเจอร์นี้แล้ว และเตือนเมื่อมีเพียงเจ้าของร้านที่ใช้ได้ (G14)

### 7.3 สิทธิ์และชุดที่ติ๊กได้

| สิทธิ์ใหม่ | ทำอะไรได้ |
|---|---|
| `expense.disbursement.read` | ดูหน้ารายการ รายละเอียด และไฟล์ของใบที่ครอบรายจ่ายที่ตนอ่านได้ ในสาขาที่เข้าถึงได้ |
| `expense.disbursement.prepare` | สร้าง แก้ ส่งอนุมัติ พากลับไปแก้ และยกเลิกใบที่ยังไม่จ่าย เลือกได้เฉพาะรายจ่ายที่ตนอ่านได้ |
| `expense.disbursement.approve` | อนุมัติหรือตีกลับ และยกเลิกใบที่ยังไม่จ่าย |
| `expense.disbursement.pay` | บันทึกว่าจ่ายแล้วจากใบที่อนุมัติ ไม่ต้องมี `expense.payment.record` |
| `expense.disbursement.issue` | กดออกใบสำคัญจ่ายจากการจ่ายตรงที่มีอยู่ ไม่มีสิทธิ์แก้ยอดหรือวันที่ของการจ่าย |

ชุดที่ติ๊กได้ (หมวด "ค่าใช้จ่าย" ในหน้าสร้างตำแหน่ง, ผูก `expenses`, ชื่อและคำอธิบายภาษาไทยล้วน):

| ชุด | สิทธิ์ในชุด |
|---|---|
| ดูใบเตรียมจ่าย/ใบสำคัญจ่าย | read |
| จัดทำใบเตรียมจ่าย | read + prepare |
| อนุมัติใบเตรียมจ่าย | read + approve |
| บันทึกจ่ายตามใบเตรียมจ่าย | read + pay |
| ออกใบสำคัญจ่ายจากการจ่ายตรง | read + issue |

- **ห้ามใส่สิทธิ์ใหม่ลงในชุดเดิม** โดยเฉพาะ "อนุมัติ/จ่ายค่าใช้จ่าย" (`pack.expense.finance`): จะทำให้ติ๊กชุดเดิมแล้วได้สิทธิ์ใหม่โดยไม่รู้ตัว และทำให้ชุดเดิมหลุดติ๊กในตำแหน่งเก่าทุกตำแหน่ง
- ชื่อชุดใช้ `pack.expense.disbursement.*`; `pack.payment.*` เป็นของการรับชำระจากลูกค้าอยู่แล้ว
- ทุกสิทธิ์ต้องอยู่ในชุดที่ผูกแพ็กเกจและไม่อยู่ในชุดที่ไม่ผูก มิฉะนั้นจะไม่ถูกตัดเมื่อปิดรายจ่าย เพิ่ม test ยืนยันข้อนี้

ค่าเริ่มต้นของตำแหน่งมาตรฐาน (ยืนยันแล้ว D10):

| ตำแหน่ง | สิทธิ์ |
|---|---|
| เจ้าของ, ผู้ดูแล, การเงิน | ดู จัดทำ อนุมัติ บันทึกจ่ายตามใบ ออกใบสำคัญจ่ายจากการจ่ายตรง |
| ผู้จัดการ | ดู อนุมัติ |
| นักบัญชี | ดู ออกใบสำคัญจ่ายจากการจ่ายตรง |
| พนักงาน | ไม่มี |

แม่แบบตำแหน่งในหน้าสร้างตำแหน่ง (การเงิน, ผู้จัดการ, บัญชี) เพิ่มชุดใหม่ให้ตรงกับตารางนี้

**การให้สิทธิ์เพิ่ม**

- เจ้าของร้าน (ผู้มี `access.role.manage`) สร้างตำแหน่งใหม่ที่ `/settings/permissions` โดยติ๊กชุด แล้วเปลี่ยนตำแหน่งของพนักงานคนนั้นที่ `/settings/access-overview` หรือแก้ตำแหน่งเดิมซึ่งมีผลกับทุกคนในตำแหน่งนั้น
- ไม่มี backfill ให้ตำแหน่งที่ร้านสร้างเองและสำเนาของตำแหน่งมาตรฐานที่ร้านเคยแก้: กลไก backfill เดิมบังคับ (ด้วย test) ว่าชุดที่มีสิทธิ์หลักต้องมีสิทธิ์ที่จะเติมด้วย ซึ่งขัดกับการแยกชุดให้ติ๊ก ฟีเจอร์นี้เป็นของใหม่ จึงไม่มีงานเดิมที่จะค้างเพราะไม่ได้สิทธิ์
- ผู้ให้สิทธิ์ให้ได้ไม่เกินสิทธิ์ที่ตนมี ตามกติกาเดิม
- ขอบเขตสาขาเป็นไปตามสมาชิกภาพของแต่ละคนตามเดิม
- พนักงานที่ได้ "จัดทำใบเตรียมจ่าย" อย่างเดียวจะเลือกได้เฉพาะรายจ่ายที่ตนสร้างหรือเกี่ยวข้อง เพราะสิทธิ์ใหม่ไม่ให้สิทธิ์อ่านรายจ่ายเพิ่ม
- หน้าสร้างตำแหน่งของร้านแสดงบรรทัดแนะนำชุดใหม่เมื่อเมนูของร้านเปิดอยู่ (G14) และบอกว่าชุดใหม่ใช้กับรายจ่ายที่ตำแหน่งนั้นดูได้อยู่แล้ว ตำแหน่งที่ไม่มีสิทธิ์รายจ่ายใดเลยจะไม่เห็นกลุ่มเมนูรายจ่ายและไม่มีใบให้ดู (ไม่เพิ่มสิทธิ์ใหม่เข้ารายการที่เปิดกลุ่มเมนู เพราะอยู่ในไฟล์ที่ผู้ช่วยใน LINE ตรึง hash)

### 7.4 งานที่ต้องเสร็จก่อนขึ้นระบบ

1. migration เพิ่มหนึ่งช่องบน `CompanyWebEntrySetting` และโครงสร้างใน §11.1 (เพิ่มอย่างเดียว)
2. ลงทะเบียนสิทธิ์ ชุด ตำแหน่งมาตรฐาน และแม่แบบตำแหน่ง แล้วตรวจกับ test ของ registry ทุกชุด
3. ลงทะเบียนการแจ้งเตือนครบสี่จุดต่อชนิด พร้อมกิ่งใหม่ในตัวอ่านสถานะเอกสารและตัวบอกรอบ (§8.6) ไม่มีการ sync แม่แบบ
4. ข้อความไทยของ error code ใหม่ทุกตัว และคำสถานะใน contracts
5. เพิ่ม amendment ลง `mangmee-package-entitlements-spec-th.md` และ `permission-matrix.md` บน main ว่ามีฟีเจอร์นี้ในทุกแพ็กเกจที่มีรายจ่าย โดยไม่แตะ amendment 23 ก.ย. เรื่อง 50 ทวิ

หลังขึ้นระบบไม่มีร้านใดเห็นเมนูใหม่จนกว่าผู้ดูแลจะเปิดให้ร้านนั้น

## 8. ก่อนจ่าย: ใบเตรียมจ่าย

### 8.1 รายการที่เลือกได้

รายจ่ายหนึ่งรายการเลือกเข้าใบได้เมื่อครบทุกข้อ และระบบบอกเหตุผลเป็นภาษาไทยเมื่อเลือกไม่ได้

- ผ่านกติกาบันทึกจ่ายเดิมทั้งหมด: ยืนยันแล้ว มีสาขา มียอดค้าง ไม่ผูกใบเบิกที่ยังเดินอยู่ ไม่ใช่รายการที่เกิดจากใบเบิก ไม่ใช่เงินสำรองจ่ายส่วนตัว
- สกุลเงินบาท
- ไม่อยู่ในใบอื่นที่ยังจองยอดอยู่ (หนึ่งรายจ่ายอยู่ได้ทีละใบ)
- ผู้ใช้อ่านรายจ่ายนั้นได้ตามสิทธิ์และสาขาของตน

หนึ่งใบ: บริษัทเดียว สาขาเดียว ผู้รับเงินรายเดียว **ไม่เกิน 30 รายการ** (เจ้าของสั่ง 5 พ.ย. 2569: เดิม 20; หนึ่งรายการคือหนึ่งบิล รายการในบิลยังครบทุกรายการ) ในไลน์ ตัวช่วยยังเสนอได้ครั้งละ 20 บิลจนกว่าจะวัดค่า AI ของตัวรับข้อความใหม่แบบคู่จริง (paired live calibration, `docs/specs/line-ai-credit-levers-20261019.md`) การ์ดในไลน์บอก "บิลในใบนี้ N ใบ · ขอไว้ M ใบ" และถ้าไม่ครบให้กดไม่ทำแล้วทำต่อในเว็บ ระบบถือว่าเป็นผู้รับเงินรายเดียวกันเมื่อข้อใดข้อหนึ่งเป็นจริง

1. เลขประจำตัวผู้เสียภาษีของผู้ขายตรงกันทุกรายการและไม่ว่าง เทียบหลังตัดอักขระที่ไม่ใช่ตัวเลข เพราะระบบเก็บเลขตามที่พิมพ์
2. **ไม่มีรายการใดมีเลขประจำตัวผู้เสียภาษี และชื่อผู้ขายตรงกันทุกตัวอักษร (D21)**: รวมได้โดยไม่ต้องติ๊ก และหน้าจอแสดงคำเตือนเล็ก ๆ ว่า "รายการเหล่านี้ไม่มีเลขผู้เสียภาษี ระบบรวมให้เพราะชื่อร้านตรงกัน โปรดตรวจว่าเป็นร้านเดียวกัน" การเทียบชื่อใช้ตัวปรับเดียวกับการจัดกลุ่มในตัวเลือกผู้รับเงิน คือไม่นับช่องว่าง เครื่องหมาย และตัวพิมพ์เล็กใหญ่ หน้าของใบและใบพิมพ์ระบุว่า "รวมจากชื่อร้านที่ตรงกัน (ไม่มีเลขผู้เสียภาษี)" ให้ผู้อนุมัติเห็น
3. ผู้จัดทำติ๊กยืนยันว่า "รายการเหล่านี้จ่ายให้ผู้รับเงินรายเดียวกัน" (D15, G12) ช่องติ๊กปรากฏเมื่อข้อ 1 และ 2 ไม่เป็นจริง เช่น ชื่อต่างกัน เลขภาษีต่างกัน หรือบางรายการมีเลขภาษีแต่บางรายการไม่มี

**ไม่ใช้การผูกคู่ค้า (`vendorCounterpartyId`) เป็นฐาน** (K02): การผูกเกิดตอนอ่านใบเสร็จครั้งแรกและไม่ถูกเปลี่ยนเมื่อผู้ใช้แก้ชื่อร้านเป็นอีกร้าน รายจ่ายที่พิมพ์ชื่อร้านหนึ่งจึงอาจยังผูกอีกร้าน ใบนี้ยึดข้อมูลผู้ขายปัจจุบันบนรายจ่ายเท่านั้น

**ข้อมูลของหน้าสร้างใบ** (K03) มาจากตัวอ่านสองตัวของเอกสารนี้ ทั้งคู่คืนเฉพาะรายจ่ายที่ผู้ใช้อ่านได้ตามสิทธิ์และสาขา

- **กลุ่มผู้รับเงินที่มีรายจ่ายค้าง**: จัดกลุ่มรายจ่ายที่ยืนยันแล้วและมียอดค้าง ตามเลขประจำตัวผู้เสียภาษี (หลังตัดอักขระที่ไม่ใช่ตัวเลข) ถ้าไม่มีเลข จัดตามชื่อผู้ขายที่ปรับรูปแบบด้วยตัวปรับเดียวกับการจับคู่คู่ค้า แต่ละกลุ่มแสดงชื่อล่าสุด จำนวนรายการ และยอดค้างรวม ค้นด้วยชื่อหรือเลขภาษีได้ แบ่งหน้า กลุ่มที่จัดตามชื่อ (ไม่มีเลขภาษี) รวมในใบเดียวได้โดยไม่ต้องติ๊กตามข้อ 2
- **รายจ่ายค้างของกลุ่มที่เลือก หรือของคำค้น**: แต่ละแถวมียอดค้าง สถานะว่าเลือกได้หรือไม่ และเหตุผลเป็นภาษาไทยเมื่อเลือกไม่ได้
- ปุ่ม **"เพิ่มรายจ่ายของชื่ออื่น"** เปิดการค้นรายจ่ายค้างด้วยชื่อหรือเลขภาษี สำหรับร้านเดียวกันที่ถูกบันทึกไว้หลายชื่อ รายการที่เพิ่มทางนี้ทำให้ต้องติ๊กยืนยันตามข้อ 3 เว้นแต่เลขภาษีตรงกัน
- ไม่ใช้ตัวค้นคู่ค้า (ต้องมีสิทธิ์อ่านคู่ค้าซึ่งพนักงานและชุดการเงินไม่มี) และไม่ใช้รายการรายจ่ายเดิมซึ่งตัดที่ 200 แถว

การยืนยันตามข้อ 3 ถูกบันทึกพร้อมชื่อผู้ยืนยัน หน้าอนุมัติและใบพิมพ์แสดงชื่อผู้ขายของแต่ละรายการและข้อความว่ารวมด้วยการยืนยันของผู้จัดทำ ชื่อผู้รับเงินของใบเติมจากรายการแรกและผู้จัดทำแก้ได้ รายจ่ายรายการเดียวทำใบได้เสมอ

ยอดต่อรายการ: ค่าเริ่มต้นคือยอดค้างทั้งหมด ลดได้ (จ่ายบางส่วน) หน่วยเดียวกับ `ExpensePayment.amount`

ระบบไม่เสนอรายการเข้าใบเอง (D6) การสร้างเริ่มจากการเลือกผู้รับเงิน (§6.1 ข้อ 1) หรือจากปุ่ม "เพิ่มเข้าใบเตรียมจ่าย" บนรายจ่าย ซึ่งถือว่าเลือกผู้รับเงินของรายจ่ายนั้นแล้ว

### 8.2 ขั้นตอน

| ขั้น | ผู้ทำ | สิ่งที่กรอก | ผล |
|---|---|---|---|
| 1 สร้าง | ผู้มี `prepare` | ผู้รับเงิน, รายการและยอด, กำหนดจ่าย, วิธีจ่ายที่ตั้งใจ, บัญชีผู้รับ (ไม่บังคับ), หมายเหตุ | ฉบับร่าง ยังไม่จองยอด ยังไม่มีเลข |
| 2 ส่งอนุมัติ | ผู้มี `prepare` | เลือกผู้อนุมัติ (เติมให้เมื่อมีคนเดียว) | ตรวจต้นทางใหม่ จองยอดทั้งใบ ได้เลข พิมพ์เป็นใบเตรียมจ่ายได้ พร้อมข้อความ "ยังไม่ได้จ่ายเงิน" |
| 3 อนุมัติ | ผู้มี `approve` | — หรือเหตุผลเมื่อตีกลับ | อนุมัติแล้ว รอจ่าย หรือกลับเป็นฉบับร่าง |
| 4 บันทึกว่าจ่ายแล้ว | ผู้มี `pay` | วันที่จ่ายจริง (วันนี้), วิธีจ่าย (ตามที่ตั้งใจ), จ่ายจาก (ไม่บังคับ), สลิป (ไม่บังคับ) | สร้างการจ่ายของทุกรายการในคราวเดียว ปล่อยยอดจอง ใบเดิมเป็นใบสำคัญจ่าย (§9) |

- ผู้ที่ถือทั้ง `prepare` และ `approve` เห็นปุ่มเดียว **"ส่งและอนุมัติ"** เจ้าของคนเดียวจึงทำ 3 ครั้ง หลังอนุมัติ หน้าเปิดฟอร์มจ่ายต่อทันทีเมื่อผู้ดูจ่ายได้
- **ยอดที่บันทึกจ่ายต้องเท่ายอดที่อนุมัติทุกรายการ (D17)** จะจ่ายต่างจากนั้นต้อง "กลับไปแก้" ก่อน ซึ่งคงรายการเดิมไว้ให้ ผู้ที่อนุมัติเองได้ทำต่อจนจ่ายได้ในสองครั้ง
- สลิปและบัญชีไม่บังคับ (D9)
- ระบบไม่โอนเงินและไม่ยืนยันกับธนาคาร การบันทึกคือการบอกว่าจ่ายภายนอกแล้ว ระบบกันได้เฉพาะการบันทึกซ้ำ ไม่ได้กันคนสองคนโอนซ้ำนอกระบบ
- การจ่ายตรงจากหน้ารายจ่ายยังอยู่เหมือนเดิมทุกประการสำหรับรายจ่ายที่ไม่อยู่ในใบ

### 8.3 สถานะ

| สถานะที่ผู้ใช้เห็น | ทำอะไรได้ | ยอดจอง |
|---|---|---|
| ฉบับร่าง | แก้ ลบ ส่งอนุมัติ | ไม่จอง |
| รออนุมัติ | อนุมัติ ตีกลับ ยกเลิก พิมพ์ใบเตรียมจ่าย ส่งเตือนอีกครั้ง | จอง |
| อนุมัติแล้ว รอจ่าย | บันทึกว่าจ่ายแล้ว กลับไปแก้ ยกเลิก พิมพ์ใบเตรียมจ่าย | จอง |
| จ่ายแล้ว | ดู ดาวน์โหลดใบสำคัญจ่าย | ปล่อยแล้ว |
| ยกเลิก | ดูประวัติ | ปล่อยแล้ว |

- ตีกลับและ "กลับไปแก้" พาใบกลับเป็นฉบับร่างพร้อมเหตุผล ปล่อยยอดจอง ส่งใหม่ใช้เลขเดิมและเพิ่มรุ่น เก็บรุ่นเก่าและผลอนุมัติเก่าไว้
- ลบได้เฉพาะฉบับร่างที่ยังไม่เคยมีเลข ใบที่มีเลขแล้วใช้ยกเลิก เลขไม่ถูกใช้ซ้ำ
- ยกเลิกหรือพากลับไปแก้ใบที่ยังไม่จ่าย ทำได้โดยผู้มีสิทธิ์จัดทำหรือสิทธิ์อนุมัติคนใดก็ได้ของสาขานั้น ไม่จำกัดที่ผู้จัดทำ ยอดจองจึงไม่ค้างเมื่อผู้จัดทำไม่อยู่หรือถูกถอนสิทธิ์ (G16)
- ก่อนอนุมัติและก่อนจ่าย ระบบตรวจต้นทางซ้ำทุกรายการ (§8.1, ยอดค้างไม่น้อยกว่ายอดในใบ, hash ของข้อมูลสำคัญตรงกับตอนส่ง) ไม่ผ่านแล้วปฏิเสธพร้อมเหตุผล ทำได้อย่างเดียวคือกลับไปแก้หรือยกเลิก เป็นการตรวจกันพลาด เพราะยอดจองกันทางที่แก้รายจ่ายไว้แล้ว
- ไม่มีสถานะ "กำลังจ่าย": การบันทึกจ่ายเป็นคำสั่งเดียวที่สำเร็จหรือไม่สำเร็จทั้งใบ
- ใบที่จ่ายแล้วไม่ย้อนกลับเป็นรอจ่าย ถ้าการจ่ายถูกยกเลิกภายหลัง ใบเป็น "ยกเลิก" ตาม §9.4

### 8.4 การอนุมัติ

- ผู้อนุมัติคือผู้ใดก็ได้ที่มี `expense.disbursement.approve` และเข้าถึงสาขานั้น ผู้ที่ถูกเลือกตอนส่งเป็นเพียงผู้รับแจ้งเตือน
- ผู้ส่งอนุมัติใบของตนเองได้เมื่อมีสิทธิ์อนุมัติ (D8) ระบบบันทึกว่า "อนุมัติเอง" ใน audit และบนใบพิมพ์ ร้านที่ต้องการสองคนให้ติ๊กสิทธิ์จัดทำกับสิทธิ์อนุมัติให้คนละตำแหน่ง
- กติกานี้ไม่ใช้กับใบเบิก และไม่เปลี่ยนสวิตช์อนุมัติตนเองของใบเบิก (เจ้าของ 4 ต.ค. 2569)
- การอนุมัติใบนี้ไม่แทนการยืนยันรายจ่าย
- ไม่มี workflow หลายชั้น ไม่มีวงเงินอนุมัติในรุ่นแรก

### 8.5 ยอดจองและทางเข้าที่ต้องเชื่อม

ยอดจอง = ช่อง `reservedByDisbursementVoucherId` บนแถวรายจ่าย เขียนตอนส่งอนุมัติ ล้างเมื่อตีกลับ กลับไปแก้ ยกเลิก หรือจ่ายแล้ว เขียนภายใต้ล็อกวงจรชีวิตของรายจ่ายและไม่เปลี่ยน `updatedAt` (ตามแบบที่ repository ทำอยู่แล้ว) เหตุที่อยู่บนแถวรายจ่าย: การยกเลิกรายจ่ายทำงานแบบ Serializable และเริ่มอ่านข้อมูลก่อนได้ล็อก ยอดจองที่อยู่บนแถวเดียวกับที่มันจะเขียนจึงเป็นทางเดียวที่มันมองไม่พลาด: เมื่อการส่งอนุมัติ commit ระหว่างที่การยกเลิกรอ การเขียนแถวรายจ่ายของการยกเลิกจะชนและล้ม **ข้อผิดพลาดชนิดนี้ต้องถูกแปลงเป็นข้อความไทยให้ลองใหม่** วันนี้กลุ่มรายจ่ายยังไม่มีการแปลงนี้ การชนกับการจ่ายจึงออกมาเป็นข้อผิดพลาดดิบ (K07) ช่องนี้เป็นตัวชี้ธรรมดา ไม่มี foreign key ตามข้อกำหนดของตารางรายจ่าย

ตัวค้นยอดจองมีตัวเดียว เรียกจากทุกทางในตารางนี้ พร้อมเหตุผลใหม่หนึ่งค่า ข้อความ: "รายการนี้อยู่ในใบเตรียมจ่ายเลขที่ … จัดทำโดย …" มีลิงก์เมื่อผู้ใช้ดูใบได้ ผู้ที่ดูใบไม่ได้ยังเห็นเลขที่และชื่อผู้จัดทำเพื่อรู้ว่าต้องติดต่อใคร (G15)

| ทางเข้าที่มีอยู่ | จุดที่ต้องเพิ่มการตรวจ | เมื่อรายจ่ายถูกจอง |
|---|---|---|
| บันทึกจ่ายตรง | การตรวจของ `recordPaymentAtomic` และ `recordPaymentBlocker` ที่หน้ารายละเอียดใช้ | ปฏิเสธ |
| เปิดรายจ่ายกลับมาแก้ | `readExpenseCorrectionCapabilities` (รายการ reopen) | ปฏิเสธ |
| ยกเลิกรายจ่าย | การตรวจของ `voidExpenseTrueReversal` เอง | ปฏิเสธ; การชนกันขณะทำงานต้องได้ข้อความให้ลองใหม่ ไม่ใช่ข้อผิดพลาดระบบ |
| อนุมัติใบรับรองแทนใบเสร็จแบบบริษัทจ่าย | ก่อนสร้างการจ่ายใน `issueSubstituteEvidence` (ทางนี้สร้างการจ่ายเองโดยไม่ผ่าน `recordPaymentAtomic` จึงต้องตรวจตรงนี้) | ปฏิเสธ |
| ยกเลิกการจ่ายรายการเก่าของรายจ่ายนั้น | ไม่ต้องเพิ่ม | ทำได้ (ยอดค้างเพิ่ม ไม่กระทบยอดจอง) |
| ปฏิเสธรายจ่าย | ไม่ต้องเพิ่ม | ทำไม่ได้อยู่แล้ว รายจ่ายที่ยืนยันแล้วไม่มีทางไปสถานะปฏิเสธ |
| ใบเบิกที่อ้างรายจ่ายหรือใช้ไฟล์ร่วม | ไม่ต้องเพิ่ม | ถูกปฏิเสธด้วยกติกาเดิม เพราะรายจ่ายที่ยืนยันแล้วเป็นต้นทางใบเบิกไม่ได้ |
| จ่ายใบเบิก (ปรับรายการเงาเป็นจ่ายแล้ว) | ไม่ต้องเพิ่ม | รายการเงาเลือกเข้าใบไม่ได้ตั้งแต่ต้น |
| LINE | ไม่ต้องเพิ่ม | ไม่มีคำสั่งจ่ายจาก LINE |

ทิศกลับ: การส่งอนุมัติเรียก `lockFundingEvidence` ครั้งเดียวสำหรับรายจ่ายทุกรายการ แล้ว `assertFundingMutation('payment')` ต่อรายการ จึงเห็นใบเบิกที่เดินอยู่ด้วยกติกาเดียวกับการจ่ายตรง

### 8.6 การแจ้งเตือน

ใช้ **การแจ้งตรง** แบบเดียวกับใบรับรองแทนใบเสร็จในกลุ่มรายจ่าย (เรียกตัวสร้างการแจ้งเตือนพร้อมรายชื่อผู้รับ) ไม่ใช้แม่แบบ workflow และไม่ต้องรัน sync แม่แบบ (K04) ยึดหลัก "แจ้งเฉพาะคนที่เกี่ยว" ผู้กระทำไม่ได้รับแจ้งเตือนของตัวเอง

| เหตุการณ์ | ผู้รับ |
|---|---|
| ส่งอนุมัติ (ไม่ใช่อนุมัติเอง) | ผู้อนุมัติที่ถูกเลือกตอนส่ง |
| อนุมัติแล้ว | ผู้จัดทำ; ถ้าผู้จัดทำบันทึกจ่ายไม่ได้ ให้ผู้อนุมัติที่จ่ายได้; ถ้ายังไม่มี จึงแจ้งผู้มีสิทธิ์บันทึกจ่ายตามใบ |
| ตีกลับ | ผู้จัดทำ |
| บันทึกจ่ายแล้ว | ผู้จัดทำ |
| ยกเลิก | ผู้จัดทำ |
| กด "ส่งเตือนอีกครั้ง" บนใบที่รออนุมัติ | ผู้อนุมัติที่ผู้กดเลือก จะเป็นคนเดิมหรือคนอื่นก็ได้ |

- "ส่งเตือนอีกครั้ง" (G13): ผู้มีสิทธิ์จัดทำกดได้บนใบที่รออนุมัติ ใช้การแจ้งเตือนชนิดเดียวกับการส่งอนุมัติ จำกัดไม่เกินหนึ่งครั้งต่อผู้รับต่อชั่วโมง และบันทึกผู้รับคนล่าสุดกับเวลาบนใบ
- ลิงก์ในการแจ้งเตือนพาไปหน้าของใบ ซึ่งเปิดได้แม้เมนูถูกซ่อน
- แต่ละชนิดต้องลงทะเบียนสี่จุด มิฉะนั้นจะไม่ส่งหรือค้างโดยไม่มีข้อผิดพลาดให้เห็น: (1) รายการ trigger ที่ระบบรู้จัก (2) รายการที่ส่ง LINE เสมอ เพื่อให้สมาชิกที่เคยบันทึกการตั้งค่าการแจ้งเตือนไว้ก่อนมีชนิดใหม่ยังได้ LINE (3) แผนที่ว่า trigger เป็นของฟีเจอร์ใด (`expenses`) (4) ตัวอ่านสถานะเอกสาร พร้อมกิ่งใหม่สำหรับเอกสารชนิดนี้ เพื่อให้การแจ้ง "รออนุมัติ" หายเองเมื่อใบพ้นสถานะนั้น ถ้าลงทะเบียนโดยไม่เพิ่มกิ่ง ตัวอ่านจะถือว่างานเสร็จแล้วทันที
- **ทุกการส่งมีตัวบอกรอบ** (`periodKey`): การส่งอนุมัติและผลของมันใช้เลขรุ่นของใบ การส่งเตือนอีกครั้งใช้เลขรุ่นกับลำดับการเตือน ถ้าไม่มี การส่งใหม่หลังตีกลับหรือการเตือนซ้ำจะถูกรวมเข้ากับเหตุการณ์เดิมและไม่ส่งอะไรออกไป
- หัวเรื่องและข้อความเป็นภาษาไทยล้วน มีเลขที่ใบ ไม่มีรหัสหรือ id
- ไม่มีการเตือนวันครบกำหนดในรุ่นแรก

### 8.7 สิ่งที่ปรับระหว่างลงมือทำ (ถือตามข้อนี้เมื่อขัดกับ §8–§9 และ §12)

1. **เหตุผล**: "กลับไปแก้" ไม่บังคับเหตุผล เพื่อให้คนที่ทำคนเดียวแก้ยอดได้เร็ว "ตีกลับ" และ "ยกเลิกใบ" บังคับอย่างน้อย 3 ตัวอักษร ฉบับร่างที่มีเลขแล้วใช้ยกเลิก ไม่ใช่ลบ
2. **ประวัติของรุ่น**: รุ่นที่อนุมัติแล้วเก็บผลอนุมัติไว้ และบันทึกแยกว่าต่อมาถูกนำกลับไปแก้หรือยกเลิกโดยใคร เมื่อไร ด้วยเหตุผลใด แต่ละรุ่นเก็บผู้อนุมัติที่ถูกขอของรุ่นนั้นเอง ชื่อแสดงเฉพาะสมาชิกของร้าน คนที่ออกจากร้านแล้วแสดงเป็น "ผู้ใช้ที่ไม่อยู่ในร้านแล้ว"
3. **ข้อความให้ลองใหม่เป็นของใบเอง**: บันทึกจ่ายที่ชนหรือหมดเวลา "บันทึกไม่สำเร็จ ยังไม่มีการบันทึกจ่ายรายการใด กรุณาลองอีกครั้ง" คำสั่งอื่นของใบ "มีการทำรายการกับใบนี้หรือรายจ่ายในใบพร้อมกัน ระบบยังไม่ได้บันทึกสิ่งที่คุณเพิ่งทำ กรุณาเปิดหน้านี้ใหม่แล้วลองอีกครั้ง" ไม่ใช้ประโยคของการยกเลิกเอกสาร
4. **ประโยคที่บอกให้กดปุ่มใด บอกเฉพาะกับคนที่มีปุ่มนั้น** เช่น ผู้ที่มีแต่สิทธิ์บันทึกจ่าย เมื่อรายจ่ายถูกเปลี่ยนหลังอนุมัติ ได้ประโยคว่าให้ผู้จัดทำหรือผู้อนุมัติกด "กลับไปแก้"
5. **บันทึกจ่ายทั้งใบ**: ใบ 20 รายการใช้เวลา 0.16 วินาทีบน PostgreSQL จริง (เวลาที่ตั้งไว้ 20 วินาที) จึงคงเพดาน 20 รายการ ต่อมาเจ้าของสั่งเพิ่มเป็น 30 (5 พ.ย. 2569) และวัดใบ 30 รายการบน PostgreSQL จริงอีกครั้งตามข้อ 12
6. **ออกใบจากการจ่ายตรง และออกใบใหม่แทนใบที่ถูกยกเลิก** รับ `commandId` โดยไม่มี `expectedVersion` เพราะยังไม่มีใบให้เทียบรุ่น กดซ้ำได้ใบเดิม
7. **ไฟล์พิมพ์** ส่งเป็นไฟล์จาก endpoint ของใบโดยตรงภายใต้กติกาอ่านของใบ ไม่ออก URL อายุสั้น (สลิปยังใช้ URL อายุสั้น) ฉบับร่างที่ยังไม่เคยส่งพิมพ์ไม่ได้และบอกว่าต้องส่งอนุมัติก่อน รุ่นที่ส่งก่อนงานนี้เสร็จไม่มีข้อมูลบริษัทและสาขาใน snapshot ช่องนั้นจึงพิมพ์เป็น "-"
8. **สลิป**: หนึ่งสลิปต่อใบ เปลี่ยนได้ ไม่มีคำสั่งเอาออก แนบได้เมื่อใบอนุมัติแล้วหรือจ่ายแล้ว โดยผู้มีสิทธิ์บันทึกจ่าย การบันทึกจ่ายทำได้แม้อัปโหลดสลิปไม่สำเร็จ
9. **บัญชีผู้รับเงิน**: เลขบัญชี 6–20 หลัก ต้องระบุธนาคาร เปิดดูเลขเต็มได้เฉพาะผู้ที่ดูใบได้และมีสิทธิ์อนุมัติหรือบันทึกจ่าย หรือผู้ที่แก้ไขใบร่างนั้นได้ (เจ้าของสั่ง 2026-10-15) เมื่อนำบัญชีจากใบเดิมมาใช้ ผู้มีสิทธิ์จัดทำที่เปิดใบเดิมได้เปิดดูเลขเต็มได้ ระบบเขียน audit ก่อนถอดรหัสทุกครั้ง บันทึกไม่ได้ก็ไม่เปิดเลข
10. **การแจ้งเตือน**: ห้าชนิดของใบอยู่ในรายการที่ส่งถึง LINE เสมอ (รายการนั้นจึงมี 15 รายการ รวมการแจ้งว่าหนังสือรับรองถูกยกเลิก) ผู้กระทำไม่ได้รับแจ้งของตนเอง "อนุมัติเอง" ไม่มีการแจ้งรออนุมัติ การกลับไปแก้โดยคนอื่นแจ้งผู้จัดทำด้วยการแจ้งชนิดตีกลับ การยกเลิกหลังจ่ายแจ้งผู้จัดทำพร้อมบอกว่าการจ่ายใดยังอยู่
11. **รายจ่ายที่ถูกจอง**: ทางจ่ายตรง แก้ไขเอกสาร ยกเลิกเอกสาร และอนุมัติใบรับรองแทนใบเสร็จ ปฏิเสธด้วยประโยคของแต่ละทางซึ่งบอกเลขที่ใบ ชื่อผู้จัดทำ และสิ่งที่ต้องทำก่อน ผู้ที่เปิดใบนั้นไม่ได้ยังเห็นเลขที่และชื่อ
12. **บั๊กของเดิม E4–E5** แก้แล้ว: ตัวกันอ่านเฉพาะใบรับรองแทนใบเสร็จที่ยังไม่ถูกแทน (สถานะในระบบคือ SUPERSEDED) และการส่งคำสั่งจ่ายตรงซ้ำของการจ่ายที่ถูกยกเลิกแล้วได้ข้อความว่าถูกยกเลิก ไม่ตอบว่าบันทึกแล้ว
13. **ไฟล์ของใบ** (สลิปและไฟล์ใบสำคัญจ่าย) เปิดได้จากใบเท่านั้น แนบกับเอกสารอื่นไม่ได้ ทางดาวน์โหลดและทางลบไฟล์แนบทั่วไปปฏิเสธทั้งสองชนิด
14. **ใบที่ยกเลิกแล้วพิมพ์พร้อมแถบ "ยกเลิกแล้ว"** ทุกหน้า บอกวันที่และเหตุผล ใบสำคัญจ่ายที่ถูกยกเลิกหลังจ่ายบอกว่าการจ่ายของรายการใดถูกยกเลิก เหตุผลที่ผู้ใช้พิมพ์ตอนยกเลิกการจ่ายหรือยกเลิกเอกสาร และเลขที่ใบที่ออกแทน ไฟล์ต้นฉบับของใบสำคัญจ่ายที่เก็บไว้ไม่ถูกแก้ ปุ่มบนหน้าจอเรียกว่า "พิมพ์ใบ (ยกเลิกแล้ว)" และ "ดาวน์โหลดใบ (ยกเลิกแล้ว)"
15. **ใบพิมพ์อ่านเหมือนหน้าจอ**: ยอดเงินมีจุลภาคและชิดขวา วันที่แบบ "12 ต.ค. 2569" ใช้คำว่า "กำหนดจ่าย" เอกสารหน้าเดียวไม่มีข้อความท้ายกระดาษ เอกสารหลายหน้าแสดงเฉพาะ "หน้า x/y" มุมขวาล่าง ไม่พิมพ์รหัสตรวจสอบเอกสาร แต่ยังเก็บรหัสตรวจสอบไว้ในระบบ (เจ้าของสั่ง 2026-10-15) ข้อมูลที่ไม่มีถูกละไว้ทั้งป้าย ไม่พิมพ์ขีด มีบรรทัดอธิบายเมื่อสามบรรทัดสรุปไม่ลงตัวเพราะจ่ายบางส่วน และใบสำคัญจ่ายมีบรรทัดหลักฐานการจ่าย ณ ตอนจ่าย
16. **บันทึกจ่ายต้องมีวิธีจ่าย**: ถ้าใบไม่ได้ตั้งวิธีจ่ายไว้ ผู้บันทึกต้องเลือกก่อน
17. **ใบที่มีอยู่แล้วยังเปิดได้เมื่อเมนูถูกซ่อน**: การซ่อนเมนูซ่อนสิ่งที่เริ่มงานใหม่ (ลูกเมนู ปุ่มสร้าง ปุ่มเพิ่มเข้าใบ ปุ่มออกใบสำคัญจ่าย) ลิงก์ไปใบที่มีอยู่ ("เปิดใบ" "ดูใบสำคัญจ่าย") ยังอยู่สำหรับผู้ที่เปิดใบนั้นได้
18. **รายจ่ายที่ถูกจอง**: ประโยคเลือกตามสิ่งที่ผู้ดูทำกับใบนั้นได้ ทำได้เอง / เปิดได้แต่ทำไม่ได้ / เปิดไม่ได้ และคำว่า "บันทึกจ่ายจากใบนั้น" ใช้กับผู้ที่มีสิทธิ์บันทึกจ่ายตามใบเท่านั้น
19. **การแจ้งเตือน**: ยอดเงินมีจุลภาค การเตือนซ้ำขึ้นหัวเรื่อง "เตือนอีกครั้ง" และเป็นของรอบที่ส่งนั้น ผู้ที่ต้องบันทึกจ่าย (เมื่อผู้จัดทำและผู้อนุมัติจ่ายไม่ได้) ได้การแจ้งแบบงานที่ปิดเองเมื่อจ่าย กลับไปแก้ หรือยกเลิก ผู้จัดทำได้รับแจ้งทุกครั้งที่ผู้อนุมัติไม่ใช่ตนเอง รวมกรณีคนอื่นกดส่งและอนุมัติใบของตน ตัวเลขนับการแจ้งเตือนบนจอลดทันทีหลังคำสั่งของใบ
20. **หน้าจอ** (จากการเดินจอจริง 390px สองรอบ): แถวตอนเลือกรายจ่ายมีรายละเอียด เลขที่เอกสารของผู้ขาย และสาขาเมื่อจำเป็น ไม่เกินสี่บรรทัด; ปุ่มที่ยังกดไม่ได้บอกเหตุ; ใบที่ถูกตีกลับแสดงผู้ตีกลับและเหตุผลบนหน้า; การยกเลิกการจ่ายหรือยกเลิกเอกสารที่อยู่ในใบสำคัญจ่ายเตือนก่อนว่าใบจะถูกยกเลิกตาม; การออกใบใหม่แทนถามยืนยัน; ใบจากการจ่ายตรงไม่แสดงขั้นอนุมัติ
21. **ใบที่จ่ายแล้วบอกความจริงเรื่องหนังสือรับรองของแต่ละรายการ** (จากการตรวจรอบสุดท้าย): คำตอบรายละเอียดของใบมีสถานะหนังสือรับรองต่อรายการ (ไม่มีภาษีหัก / ยังไม่ออก / ออกในระบบแล้วพร้อมเลขที่ / ร้านบันทึกว่าออกเองแล้วพร้อมเลขที่) อ่านจากรายการรอออกของรายจ่ายนั้นในคำสั่งเดียว ผู้อ่านใบเห็นได้โดยไม่ต้องมีสิทธิ์หนังสือรับรอง หน้าจอแสดง "ไปออกหนังสือรับรอง" เฉพาะรายการที่ยังไม่ออก รายการที่ออกแล้วแสดงเลขที่และ "ดูหนังสือรับรอง"
22. **ใบที่ออกใหม่แทนใบที่ถูกยกเลิกไม่ถือสลิปของใบเดิม**: ไฟล์พิมพ์และหน้าจอบอกตรงกันว่ายังไม่มีสลิป และแนบใหม่ได้
23. **ไฟล์พิมพ์**: รายการที่การจ่ายถูกยกเลิกพิมพ์ "ยกเลิกการจ่ายแล้ว" แทนยอดค้างหลังจ่าย และไม่นับในยอดที่จ่าย; หัวคอลัมน์ "ยอดที่จะจ่าย" อยู่ชิดขวาเหนือตัวเลข; บรรทัดสาขาตามทะเบียนภาษีพิมพ์เฉพาะเมื่อร้านมีเลขผู้เสียภาษี; วันที่ในการแจ้งเตือน "จ่ายแล้ว" ใช้รูปย่อเหมือนที่อื่น
24. **หน้าใบบอกว่ารอใคร**: ผู้ที่อนุมัติได้แต่ไม่ใช่คนที่ใบถูกส่งถึง อ่านว่า "รอ {ชื่อ} อนุมัติ คุณมีสิทธิ์อนุมัติด้วย จะอนุมัติหรือตีกลับเองก็ได้"; ฉบับร่างที่ถูกคนอื่นตีกลับ ปุ่มหลักคือ "ส่งให้คนอื่นอนุมัติ" โดยเลือกผู้ที่ตีกลับไว้ให้ก่อน และ "ส่งและอนุมัติ" เป็นปุ่มรอง
25. **ถ้อยคำและการจัดวาง**: ยอดภาษีหักในแถวเลือกรายการขึ้นบรรทัดของตัวเอง ไม่ถูกตัด; ใบที่ถูกยกเลิกบอกเหตุครั้งเดียวตามลำดับของไฟล์พิมพ์ (เหตุ → เหตุผลที่พิมพ์ → ใบที่ออกแทน); หน้าคู่ค้าของผู้ดูแลระบบระบุชื่อสวิตช์เมนูทุกตัวที่ยังใช้ได้; หัวข้อในกระดิ่งแจ้งเตือนแสดงได้สองบรรทัด เลขเอกสารจึงไม่ถูกตัด (มีผลกับการแจ้งเตือนทุกชนิด)
26. **จากการเดินตามขั้นตอนทดลองของเจ้าของ (12 ต.ค.)**: หน้าใบที่เปิดค้างอ่านข้อมูลใหม่เองเมื่อแท็บหรือหน้าต่างกลับมา และเมื่อเปิดใบเดิมซ้ำจากลิงก์หรือการแจ้งเตือน โดยไม่อ่านทับระหว่างมีหน้าต่างเปิดอยู่หรือมีคำสั่งกำลังทำ และอ่านไม่ถี่กว่าห้าวินาทีต่อครั้ง; หน้าต่าง "แก้ไขเอกสาร" ของรายจ่ายที่จ่ายผ่านใบแล้ว บอกเลขใบและบอกว่าใบกับรายการจ่ายยังอยู่ ไม่เปลี่ยนตามสิ่งที่แก้; รายชื่อ "ส่งให้คนอื่นอนุมัติ" ไม่มีชื่อผู้ส่งเอง; ไฟล์พิมพ์ของใบที่ถูกยกเลิกหลังจ่ายบอกว่า "ยอดนี้ไม่รวมรายการที่การจ่ายถูกยกเลิก" แทนประโยคเรื่องจ่ายบางส่วน (ซึ่งยังใช้เมื่อมีการจ่ายบางส่วนจริง)
27. **ยังเปิดอยู่**: ประวัติของใบไม่แสดงการเตือนของรอบก่อนหลังส่งใหม่ (ข้อมูลยังอยู่ในบันทึกคำสั่ง ต้องเพิ่มตัวอ่านประวัติและหน้าจอ); แถวที่เลือกไม่ได้เพราะอยู่คนละสาขาสูงห้าบรรทัดบนโทรศัพท์
28. **หน้ารายจ่ายพากลับไปใบที่ถูกยกเลิกพร้อมการจ่าย (D25)**: คำตอบของรายจ่ายคงตัวชี้ของใบที่ยังมีผลไว้ตามเดิม และเพิ่มตัวชี้ของใบที่ถูกยกเลิกล่าสุดซึ่งเคยครอบการจ่ายนั้น เฉพาะเมื่อไม่มีใบที่ยังมีผลครอบอยู่ ใช้กติกาสิทธิ์เปิดใบเดียวกัน การ์ดการชำระเงินบอกว่า "ใบสำคัญจ่ายเลขที่ … ถูกยกเลิกพร้อมการจ่ายนี้" สำหรับการจ่ายที่ถูกยกเลิก และ "ใบสำคัญจ่ายเลขที่ … ของการจ่ายนี้ถูกยกเลิกแล้ว ออกใบใหม่สำหรับการจ่ายที่ยังมีผลได้ที่หน้าของใบนั้น" สำหรับการจ่ายที่ยังมีผล พร้อมลิงก์ "เปิดใบ" เมื่อออกใบใหม่แล้ว บรรทัดนี้ถูกแทนด้วยลิงก์ของใบใหม่
29. **จากการเดินรอบสอง**: ไฟล์พิมพ์เรียงที่อยู่ของร้านตามลำดับที่อยู่ด้วยตัวจัดรูปกลาง และเขียนสาขาตามทะเบียนภาษีเป็น "สำนักงานใหญ่" หรือ "สาขาที่ {รหัส}"; ใบที่จ่ายแล้วซึ่งรายการยังไม่ได้ออกหนังสือรับรอง บอกว่า "ยังไม่ได้ออกหนังสือรับรอง (50 ทวิ) ให้ผู้รับเงิน" โดยไม่บอกว่าออก "ได้เลย" เพราะอาจยังขาดที่อยู่ผู้รับเงินหรือข้อมูลของร้าน
30. **ใบที่ถูกยกเลิกเพราะยกเลิกการจ่าย แสดงยอดเดียวกับกระดาษ (D27)**: หน้าของใบใช้กติกาเดียวกับไฟล์พิมพ์ คือยอดของการจ่ายที่ยังมีผล พร้อมบรรทัด "ยอดนี้ไม่รวมรายการที่การจ่ายถูกยกเลิก" การ์ดในหน้ารวมยังแสดงยอดเดิมของใบพร้อมป้ายยกเลิก เพราะแถวในรายการไม่มีข้อมูลการจ่ายรายบรรทัด
31. **ทางออกอยู่ตรงที่ข้อความเอ่ยถึง (D27)**: ข้อความล็อกบนหน้ารายจ่ายและข้อความปฏิเสธตอนยกเลิกเอกสารมีลิงก์ "เปิดใบ"; ใบที่ถูกตีกลับมีปุ่ม "แก้ไข" ในกล่องข้อความ; ฟอร์มจ่ายมีปุ่ม "ยอดจ่ายไม่ตรง? กลับไปแก้" เปิดหน้าต่างเดิม; ลิงก์ไปหนังสือรับรองพาไปลงที่การ์ด 50 ทวิ (ลิงก์มีทั้งจุดยึดและพารามิเตอร์สำรอง และการ์ดเลื่อนตัวเองเข้ามาเมื่อโหลดเสร็จ)
32. **ขั้นเลือกผู้รับเงิน (D27)**: เลือกแล้วไปขั้นเลือกรายการทันที ถ้ามีรายการค้างจ่ายที่เลือกได้รายการเดียว ระบบติ๊กให้ กด "กลับ" แล้วคำค้นและตัวเลือกเดิมยังอยู่
33. **ใครอนุมัติ (D27)**: หน้าของใบบอก "อนุมัติโดย {ชื่อ} เมื่อ {วันเวลา}" และคงคำว่า "อนุมัติเอง" เมื่อผู้อนุมัติคือผู้ส่ง
34. **คำถามยืนยันก่อนเรื่องเงิน (D28 ข้อ 2)**: ปุ่มบันทึกจ่ายเปิดหน้าต่างที่มีแต่ข้อมูล (จ่ายเท่าไร ให้ใคร วันที่ วิธีจ่าย และ "ยังไม่ได้แนบหลักฐาน" เมื่อไม่มีไฟล์) ปุ่มคือ "ยืนยัน จ่ายแล้ว ฿…" กับ "กลับไปตรวจ"; ปุ่มอนุมัติถาม "อนุมัติจ่าย ฿… ให้ … ใช่ไหม"; หลังหน้าต่างของหน้านี้ทำงานสำเร็จ ปุ่มหลักที่ตรึงอยู่ด้านล่างไม่รับการกดชั่วครู่
35. **หนึ่งชื่อสำหรับไฟล์ประกอบการจ่าย (D27)**: หน้าจอของใบใช้ "หลักฐานการจ่าย" ตรงกับไฟล์พิมพ์ แทน "สลิป" ซึ่งไม่จริงเมื่อจ่ายเงินสดหรือเช็ค
36. **คำแนะนำเรื่องหนังสือรับรองอยู่ในการ์ดของรายการ (D27)**: ประโยคและปุ่ม "ไปออกหนังสือรับรอง / ดูหนังสือรับรอง" อยู่ในการ์ดของรายจ่ายรายการนั้น ไม่แยกเป็นกล่องที่ซ้ำเลขรายจ่าย
37. **ถ้อยคำสั้นลงตามงบถ้อยคำ (D29)**: คำนำของหน้ารวม คำใบ้ใต้ช่อง คำเตือนตอนยกเลิกการจ่าย และข้อความแจ้งหลังยกเลิกการจ่ายที่ทำให้ใบถูกยกเลิก เหลือบรรทัดเดียว; ทุกหน้าต่างปิดด้วย "ปิด"; หน้าต่างประวัติชื่อ "ประวัติของใบ"; ตัวเลือกว่างของธนาคารและวิธีที่จะจ่ายคือ "ยังไม่ระบุ"; ช่องกำหนดจ่ายใช้ปฏิทินไทย; เลขที่เอกสารไม่ถูกตัดขึ้นบรรทัดใหม่ ทั้งบนหน้าจอและในข้อความแจ้ง
38. **ไฟล์พิมพ์บอกว่าจ่ายค่าอะไร (D27)**: รายละเอียดของรายจ่ายถูกจำไว้ตอนส่งอนุมัติและพิมพ์แทนคอลัมน์ชื่อผู้ขายที่ซ้ำกันทุกแถว (ชื่อที่ต่างจากหัวใบพิมพ์ใต้รายละเอียด; ใบเก่าที่ไม่มีข้อมูลนี้พิมพ์ช่องว่าง) เลขที่และวันที่ไม่ถูกตัดกลางคำ หัวคอลัมน์ภาษีคือ "ภาษีที่หักไว้" และคอลัมน์ยอดที่เท่ากันทุกแถวพิมพ์คอลัมน์เดียว (ข้อนี้แทนถ้อยคำของ §9.3 เดิมในส่วนที่ต่างกัน)
39. **ค้นหาในหน้ารวมใบ (D27)**: คำขอรายการรับคำค้น (ชื่อผู้รับเงินหรือเลขที่ใบ) และค้นก่อนแบ่งหน้า ตัวเลขบนแท็บสถานะนับตามคำค้นเดียวกัน
40. **แจ้งเตือน "อนุมัติแล้ว รอจ่าย" (D27)**: เป็นงานที่ต้องทำสำหรับผู้จัดทำที่บันทึกจ่ายได้ และปิดเองเมื่อใบถูกจ่าย ถูกนำกลับมาแก้ หรือถูกยกเลิก ผู้รับรายอื่นยังได้เป็นการแจ้งเพื่อทราบ ผู้รับและข้อความในไลน์ไม่เปลี่ยน
41. **แถบขั้นตอนชุดเดียวตลอดอายุของใบ (D27)**: หน้าสร้างและหน้าของใบใช้แถบเดียวกัน "เลือกรายการ → อนุมัติ → จ่าย → ใบสำคัญจ่าย" สามขั้นย่อยของการสร้างแสดงเป็นข้อความ ("ขั้น 2 จาก 3: เลือกรายการ") ขั้นสุดท้ายของการสร้างมีปุ่มหลักเป็นงานถัดไปจริง: "ส่งและอนุมัติ" สำหรับผู้ที่อนุมัติใบของตนเองได้ หรือ "ส่งให้ผู้อนุมัติ" สำหรับคนอื่น และ "บันทึกฉบับร่าง" เป็นปุ่มรอง ระบบบันทึกฉบับร่างก่อนแล้วเปิดคำถามยืนยันเดิม ถ้าส่งไม่สำเร็จ ฉบับร่างยังอยู่
42. **หน้ารออนุมัติของผู้ส่ง (D27)**: บอกว่าส่งให้ใครเมื่อไร มีปุ่ม "ส่งเตือนอีกครั้ง" และ "กลับไปแก้" ให้เห็น และเมื่อผู้ส่งมีสิทธิ์อนุมัติด้วย "อนุมัติเอง" เป็นปุ่มรอง ส่วนหน้าของผู้อนุมัติที่ถูกระบุชื่อไม่เปลี่ยน
43. **กันพลาดบนหน้าของใบ (D28 ข้อ 2)**: ปุ่มยืนยันในหน้าต่างบันทึกจ่ายและหน้าต่างอนุมัติไม่รับการกดใน 600 มิลลิวินาทีแรก (ปุ่มปิดกดได้ทันที); เมื่อระบบแจ้งว่าสถานะของใบเปลี่ยนไปแล้วและผู้ใช้กดโหลดข้อมูลล่าสุด หน้าต่างปิดและหน้าแสดงสถานะใหม่; ประโยคของใบสำคัญจ่ายในหน้าต่างแก้ไขรายจ่ายเหลือ "ใบสำคัญจ่ายเลขที่ … และรายการจ่ายจะไม่เปลี่ยนตาม"
44. **บรรทัดของใบและการค้นหา (D27)**: การ์ดของแต่ละบรรทัดบอกรายละเอียดของรายจ่ายและมี "ดูใบเสร็จ" สำหรับผู้ที่เปิดรายจ่ายได้; หน้ารวมใบมีช่อง "ค้นชื่อผู้รับเงินหรือเลขที่ใบ" ซึ่งถามระบบ (ไม่ใช่กรองเฉพาะหน้าที่โหลด) เก็บคำค้นไว้ในที่อยู่ของหน้า และบอกเมื่อพบในแท็บอื่น
45. **หน้าจอแพ็กเกจของผู้ดูแลระบบ (ต่อจากข้อเดิมเรื่องชุด 1999)**: ชุดที่ตรงกับสวิตช์ที่บันทึกไว้ของร้านมีเครื่องหมายว่าใช้อยู่ (หรือบอกว่า "ปรับเอง" และต่างจากชุดที่ใกล้ที่สุดกี่รายการ) แต่ละชุดมีคำอธิบายหนึ่งบรรทัดของตัวเอง ชุดที่จะปิดสิทธิ์ที่ร้านบันทึกไว้ถามก่อนพร้อมรายชื่อ ชุดที่มีแต่เพิ่มใช้ทันที หัวแถวของชุดคือ "ชุดเมนูสำเร็จรูป" สวิตช์ 50 ทวิ อยู่ใต้ ภ.ง.ด.53 และบอกสิ่งที่ร้านได้ และหน้าต่างตรวจก่อนบันทึกมีชื่อร้าน

## 9. หลังจ่าย: ใบสำคัญจ่าย

### 9.1 ใบกลายเป็นใบสำคัญจ่ายเมื่อไร

- **จ่ายจากใบที่อนุมัติแล้ว**: คำสั่งบันทึกว่าจ่ายแล้วทำให้ใบเดิม เลขเดิม เป็นใบสำคัญจ่าย ไม่มีขั้น "ออกใบ" แยก ผู้บันทึกจ่ายไม่ต้องมีสิทธิ์อื่นเพิ่ม และไม่ขึ้นกับค่าตั้งหน้าจอ
- **กดออกจากการจ่ายตรง (D4)**: ปุ่ม "ออกใบสำคัญจ่าย" บนแถวการจ่ายในหน้ารายจ่าย สำหรับการจ่ายที่บันทึกแล้วและยังไม่อยู่ในใบใด ต้องมี `expense.disbursement.issue` ระบบสร้างใบสถานะจ่ายแล้วหนึ่งใบ ครอบการจ่ายนั้นรายการเดียว ได้เลขจากชุดเดียวกันตอนกด และระบุว่า "บันทึกจ่ายโดยตรง" เงื่อนไข: รายจ่ายอยู่ในสถานะยืนยันแล้ว และการจ่ายมีแถวการจ่ายที่ยังมีผล รายจ่ายที่จ่ายผ่านใบเบิก (ไม่มีแถวการจ่ายของรายจ่าย) และยอดจ่ายเก่าที่ไม่มีแถว จึงออกใบทางนี้ไม่ได้ และปุ่มไม่แสดง
- การจ่ายตรงปุ่มเดียวไม่สร้างใบเอง จึงไม่มีเลขและไฟล์เกิดขึ้นต่อใบเสร็จเงินสดทุกใบ
- การจ่ายที่เกิดจากการอนุมัติใบรับรองแทนใบเสร็จนับเป็นการจ่ายตรง ออกใบได้เมื่อกด (ทางนี้ไม่ส่ง event จึงไม่อาศัย event)

### 9.2 หนึ่งใบครอบอะไร

- หลังจ่าย แต่ละรายการของใบผูกกับ `ExpensePayment` หนึ่งรายการ
- การจ่ายหนึ่งรายการอยู่ในใบที่ยังไม่ถูกยกเลิกได้ใบเดียว บังคับด้วย unique แบบมีเงื่อนไข กดออกซ้ำจึงได้ใบเดิม

### 9.3 เนื้อหาและไฟล์

- **เลขเดียวตลอด**: เลขออกใน transaction ผ่าน `reserveNumberInTransaction` ตอนส่งอนุมัติครั้งแรก หรือตอนกดออกจากการจ่ายตรง ชนิดเลขใหม่หนึ่งชนิด แยกจากใบสำคัญรับเงินและ 50 ทวิ ดูตัวอย่างก่อนส่งไม่กินเลข
- **ก่อนจ่าย** พิมพ์หัวกระดาษ "ใบเตรียมจ่าย" พร้อมข้อความ "ยังไม่ได้จ่ายเงิน" และรุ่นของใบ สร้างจาก snapshot ของรุ่นที่ส่งอนุมัติ ไม่เก็บเป็นไฟล์ถาวร
- **หลังจ่าย** พิมพ์หัวกระดาษ "ใบสำคัญจ่าย" จาก snapshot ที่ตรึงตอนจ่าย: บริษัทและสาขา, ผู้รับเงิน (ชื่อ เลขประจำตัวผู้เสียภาษี สาขา), แต่ละรายจ่าย (เลขเอกสาร วันที่ ชื่อผู้ขาย ยอดรวม ภาษีหัก ณ ที่จ่ายของเอกสาร ยอดสุทธิที่ต้องจ่าย ยอดที่จ่ายครั้งนี้ ยอดค้างหลังจ่าย), สรุปสามบรรทัด, วันที่จ่ายจริง, วิธีจ่าย, จ่ายจาก, บัญชีผู้รับแบบปิดเลข, ผู้จัดทำ ผู้อนุมัติ ผู้บันทึกจ่าย, รายการหลักฐานการจ่ายที่มีขณะนั้น
- ใบจากการจ่ายตรงพิมพ์ว่า "บันทึกจ่ายโดยตรง" ไม่แต่งชื่อผู้อนุมัติย้อนหลัง
- ภาษีหัก ณ ที่จ่ายแสดงเป็นข้อมูลของเอกสารต้นทาง ไม่ปันส่วนตามการจ่ายบางส่วน และไม่อ้างว่าเป็นหนังสือรับรอง
- ช่องลงชื่อ: ผู้จัดทำ ผู้อนุมัติ ผู้จ่าย พิมพ์ชื่อและวันเวลาจากเหตุการณ์จริง ช่องผู้รับเงินเว้นว่าง ไม่ใช้รูปลายเซ็นในรุ่นแรก
- ไฟล์ใบสำคัญจ่ายสร้างด้วยตัวทำ PDF เดิมของ expenses หลัง transaction แล้ว **เก็บตัวไฟล์พร้อม checksum** (ตัวทำ PDF ไม่รับประกันว่าได้ไฟล์เหมือนเดิมทุกครั้ง) ใช้แบบเดียวกับไฟล์ใบรับรองแทนใบเสร็จที่ระบบสร้างเอง ถ้าเก็บไฟล์ไม่สำเร็จ การจ่ายและเลขยังอยู่ การดาวน์โหลดครั้งถัดไปสร้างจาก snapshot เดิมแล้วเก็บ ไม่ออกเลขใหม่
- หน้าของใบแสดงบรรทัดเตือนเมื่อรายจ่ายต้นทางถูกแก้หลังจ่าย ไฟล์เดิมไม่ถูกเขียนทับ

### 9.4 ยกเลิกหลังจ่าย

- ใบที่จ่ายแล้วยกเลิกเองไม่ได้ สถานะตามการจ่าย: เมื่อการจ่ายรายการใดในใบถูกยกเลิก หรือรายจ่ายถูกยกเลิก ใบนั้นเป็น "ยกเลิก" ใน transaction เดียวกัน พร้อมเหตุผลและเครื่องหมายว่ายกเลิกหลังจ่าย ไฟล์และเลขเก็บไว้
- จุดวาง: หลังการจ่ายถูกทำให้เป็นโมฆะในทางยกเลิกการจ่าย และในลูปยกเลิกการจ่ายของการยกเลิกรายจ่าย ทั้งสองทางต้องไม่ขอล็อกของใบ
- การจ่ายที่เหลือและยังมีผลของใบที่ถูกยกเลิก: หน้าของใบนั้นมีปุ่ม "ออกใบใหม่สำหรับการจ่ายที่เหลือ" (ต้องมี `issue`) ได้ใบสถานะจ่ายแล้วเลขใหม่ที่อ้างถึงใบเดิม

### 9.5 สิทธิ์เข้าถึง

- หน้ารายการ หน้าของใบ และไฟล์ ใช้ขอบเขตเดียวกับการอ่านรายจ่ายต้นทาง (อ่านทั้งหมด / เฉพาะที่เกี่ยวข้อง / เฉพาะของตน) และขอบเขตสาขา
- ดาวน์โหลดผ่าน endpoint ของเอกสารนี้เอง ซึ่งตรวจสิทธิ์ดูใบและการอ่านรายจ่ายต้นทางก่อนออก URL อายุสั้น ทางดาวน์โหลดไฟล์แนบทั่วไปต้องปฏิเสธไฟล์ชนิดนี้ (ทางทั่วไปตรวจแค่สิทธิ์อ่านไฟล์แนบและสาขา)
- เลขบัญชีเต็มไม่อยู่ในหน้ารายการ ในไฟล์ หรือใน log

## 10. ภาษีหัก ณ ที่จ่ายและ 50 ทวิ

### 10.1 สิ่งที่ไม่เปลี่ยน

- จุดรับรู้: ตอนยืนยันรายจ่าย หนึ่งรายจ่ายหนึ่งรายการรอออกหนังสือรับรอง วันที่บนรายการคือวันที่ของรายจ่าย
- วิธีออก ปุ่ม "แก้ไขหนังสือรับรอง" และการออกใบแทน; แบบฟอร์ม; ลายเซ็น; สิทธิ์และการผูกแพ็กเกจ; สถานะบริการ (เปิดตามมติ 22 ก.ย. 2569) สิ่งที่เปลี่ยนมีเรื่องเดียวคือ §10.6
- ใบเตรียมจ่าย การบันทึกจ่าย และใบสำคัญจ่าย **ไม่สร้าง** รายการภาษี รายการรอออกหนังสือรับรอง หรือการลงบัญชีภาษีใด ๆ
- ภ.ง.ด.53 ไม่เปลี่ยน

### 10.2 หน้ารายการ 50 ทวิ (ผู้มี `wht.certificate.issue`)

- แสดงรายการรอออกและที่ออกแล้ว จาก `wht/payment-handoffs` เดิม กรองได้: ยังไม่ออก, ออกในระบบแล้ว, บันทึกฉบับที่ออกเองแล้ว, ยกเลิก พร้อมผู้รับเงิน วันที่ ยอด และลิงก์ไปรายจ่าย
- ปุ่มทุกปุ่มเรียก action ที่มีอยู่: ออกในระบบ, ดาวน์โหลด, แก้ไขหนังสือรับรอง, ออกใบแทน, บันทึกฉบับที่ออกเอง ไม่มี endpoint ออกเอกสารใหม่
- เขียน component ฝั่ง expenses ใหม่ ใช้ฟังก์ชัน api/logic/model ที่มี ไม่ย้าย component ของหน้าเจ้าหนี้ (ไม่ได้ export และมี test ล็อกข้อความในไฟล์)
- ป้ายปุ่มพิมพ์ใช้ key `wht.print_certificate` เดิม
- endpoint เดิม `POST tax/wht-certificates` ไม่ถูกใช้และไม่ถูกเปิดเพิ่ม
- รายการที่ข้อมูลไม่ครบจนออกไม่ได้ (ไม่ทราบประเภทผู้รับเงิน, ไม่มีหมวดเงินได้หรืออัตรา) แสดงสถานะ "ข้อมูลไม่ครบ" พร้อมบอกช่องที่ขาด และลิงก์ไปเปิดรายจ่ายกลับมาแก้ ไม่ปล่อยให้ผู้ใช้เจอข้อผิดพลาดตอนกดออก (G26)
- หน้านี้ไม่มีสวิตช์ซ่อน เห็นตามสิทธิ์ออกซึ่งผูกแพ็กเกจอยู่แล้ว
- ไม่แสดงรายการของรายจ่ายที่ไม่ได้อยู่ในสถานะยืนยันแล้วเป็นงาน "ยังไม่ออก" (K06) รายจ่ายที่ถูกยกเลิกปรากฏเฉพาะในตัวกรอง "ยกเลิก"

### 10.3 การ์ดบนหน้ารายจ่าย (ทุกแพ็กเกจ)

วันนี้รายจ่ายที่ยังไม่ออกหรือบันทึกฉบับที่ออกเองแล้ว ไม่แสดงอะไรเลยสำหรับผู้ที่ออกในระบบไม่ได้ ให้เพิ่มการ์ดสถานะหนังสือรับรองสำหรับผู้มี `wht.certificate.read`

- ผู้มี `wht.external_certificate.link`: บันทึกที่อยู่ผู้รับเงิน และ "บันทึกว่าออกหนังสือรับรองเองแล้ว" (เลข วันที่ หลักฐานอ้างอิง) ผ่าน endpoint เดิม ซึ่งวันนี้มีหน้าจอเฉพาะในหน้าเจ้าหนี้
- ผู้มี `wht.certificate.issue`: ปุ่มออกในระบบที่มีอยู่เดิม
- ร้านที่ออกในระบบไม่ได้ไม่เห็นปุ่มออก และไม่เห็นข้อความชวนซื้อบนการ์ดนี้
- ถ้อยคำ (G25): ระบบรับเลข วันที่ และข้อความอ้างอิงของฉบับที่ร้านออกเอง **ไม่มีการอัปโหลดไฟล์** จึงใช้คำว่า "บันทึกว่าออกหนังสือรับรองเองแล้ว" ทุกที่ ไม่ใช้คำว่า "แนบ" การแนบไฟล์จริงอยู่ใน §16

### 10.4 อัปเกรด 249 → 1999

- ไม่มีการคัดลอกหรือสร้างข้อมูล: รายการรอออกถูกเขียนตั้งแต่ยืนยันรายจ่ายในทุกแพ็กเกจ เมื่อสิทธิ์ `wht_50bis` มีผล ผู้มีสิทธิ์ออกเห็นเมนูและรายการเดิมทั้งหมด
- รายการที่บันทึกฉบับที่ออกเองแล้วออกในระบบซ้ำไม่ได้
- เมนูปรากฏเมื่อ access context ถูกอ่านใหม่: หน้ากลับจากการชำระเงินโหลดใหม่อยู่แล้ว และ shell อ่านใหม่เมื่อ focus หรือทุก 60 วินาที ไม่ต้องออกจากระบบ
- อัปเกรดไม่ออกหนังสือรับรองเอง ไม่ย้ายงวด ไม่แก้วันที่

### 10.5 งานแก้ที่ต้องเสร็จก่อนเปิดหน้ารายการ

**รายการรอออกต้องมีขอบเขตและแบ่งหน้า**: วันนี้ list ตรวจแค่บริษัท ใช้สาขาเป็นตัวกรอง และตัดที่ 200 รายการ ให้เพิ่มขอบเขตสาขา (`branchScopeWhere`) และกติกาอ่านรายจ่ายต้นทางสำหรับรายการที่มาจากรายจ่าย พร้อมแบ่งหน้าแบบ `page`/`pageSize` ใช้กติกาเดียวกันทั้ง list, get, บันทึกฉบับที่ออกเอง, ที่อยู่, ออก, ดาวน์โหลด, **แก้ไขหนังสือรับรอง และออกใบแทน** ผ่านตัวโหลดรายการรอออกตัวเดียวที่ตรวจขอบเขตสาขา วันนี้ทุกทางที่รับ id ตรวจแค่บริษัท ผู้ใช้ที่ถูกจำกัดสาขาจึงเข้าถึงใบของสาขาอื่นได้

### 10.6 รายจ่ายที่มีหนังสือรับรองแล้ว: แก้หรือยกเลิกได้ ระบบยกเลิกใบเดิมเองและเก็บประวัติ

หลัก (D13): ข้อมูลผิดแล้วต้องออกใหม่เป็นกรณีที่เกิดบ่อย ต้องทำได้ โดยเก็บประวัติ ยกเลิกใบเดิมอัตโนมัติ แล้วจึงออกใบใหม่

**วันนี้ระบบทำได้แค่ไหน**

- "แก้ไขหนังสือรับรอง" ทำตามหลักนี้อยู่แล้วสำหรับตัวเอกสาร แต่ **แก้เฉพาะตัวเอกสาร**: ข้อมูลของรายจ่ายและรายการภาษีที่ใช้ทำ ภ.ง.ด.53 ไม่เปลี่ยน เอกสารกับรายงานจึงไม่ตรงกันได้ และหน้าจอไม่ได้บอกผู้ใช้
- ถ้าต้องแก้ที่รายจ่าย: เปิดกลับมาแก้ถูกกัน และไม่มีทางยกเลิกหนังสือรับรองแบบเดี่ยว ผู้ใช้จึงไปต่อไม่ได้
- ถ้ายกเลิกรายจ่าย: ทำได้โดยไม่มีอะไรกัน หนังสือรับรองค้างเป็น "ออกแล้ว" ทั้งที่รายจ่ายถูกยกเลิก

**สามทางหลังงานนี้**

| ผู้ใช้ต้องการ | ทางที่ใช้ | ระบบทำอะไร |
|---|---|---|
| แก้เฉพาะตัวหนังสือ เช่น ตัวสะกดชื่อ ที่อยู่ | "แก้ไขหนังสือรับรอง" (เดิม) | ไม่เปลี่ยนพฤติกรรม เพิ่มข้อความว่าการแก้นี้มีผลกับตัวเอกสารเท่านั้น และถ้ายอด อัตรา หรือเลขประจำตัวผู้เสียภาษีผิด ให้เปิดรายจ่ายกลับมาแก้เพื่อให้รายงานภาษีตรงกัน |
| ข้อมูลในรายจ่ายผิด: ผู้รับเงิน ยอด อัตรา หมวดเงินได้ วันที่ | "เปิดรายจ่ายกลับมาแก้" | ถามยืนยันโดยระบุเลขที่ใบที่จะถูกยกเลิก (เหตุผลบังคับอยู่แล้ว) → ใน transaction เดียว: ใบเดิมเป็นยกเลิกพร้อมเหตุผล, รายการรอออกเป็นยกเลิกและล้างตัวชี้หลังเขียนประวัติ, รายการภาษีของรายจ่ายถูกถอนตามทางเดิม → ผู้ใช้แก้และยืนยันใหม่ ซึ่งนำรายการรอออกแถวเดิมกลับมาเป็นยังไม่ออกด้วยข้อมูลใหม่ → กดออกใบใหม่ ได้เลขใหม่ที่อ้างถึงใบเดิม |
| ยกเลิกรายจ่ายทั้งรายการ | "ยกเลิกรายจ่าย" | ถามยืนยันโดยระบุเลขที่ใบที่จะถูกยกเลิก → ใน transaction เดียว: รายจ่ายถูกยกเลิก, ใบเป็นยกเลิกพร้อมเหตุผล, รายการรอออกเป็นยกเลิก |

**ข้อกำหนด**

- ใบเดิมไม่ถูกลบ: สถานะยกเลิก เวลา ผู้ทำ เหตุผล และเหตุที่ยกเลิก (ต้นทางถูกเปิดแก้ / ต้นทางถูกยกเลิก / ถูกแทนด้วยใบแก้ไข) เลขไม่ถูกใช้ซ้ำ มี audit ทุกครั้ง
- ใบใหม่ที่ออกหลังยืนยันรายจ่ายใหม่อ้างถึงใบเดิมด้วยสายเดียวกับการแก้ไขหนังสือรับรอง (`supersedesCertificateId` / `supersededByCertificateId`) โดยหาใบเดิมจากประวัติของรายจ่ายนั้น การออกครั้งใหม่ต้องใช้ **key กันส่งซ้ำและ key ออกเลขตัวใหม่ต่อรอบ** วันนี้ทั้งสอง key ผูกกับรายการรอออก ออกรอบสองจึงได้เลขของรอบแรกกลับมา หรือชนเมื่อข้ามเดือน (G02, K05)
- **เมื่อใบถูกยกเลิกตามต้นทาง แถวรายการรอออกเป็นสถานะยกเลิก และตัวชี้ถึงใบกับข้อมูลของฉบับที่ร้านออกเองถูกล้าง หลังเขียนลงประวัติแล้ว** (K05) เหตุผล: ตอนยืนยันรายจ่ายใหม่ ระบบนำแถวเดิมกลับมาใช้เฉพาะแถวสถานะยกเลิก มิฉะนั้นจะสร้างแถวใหม่ซึ่งชน unique และถ้าตัวชี้ค้าง ทุกจุดที่ดูตัวชี้จะนับว่าออกแล้วตลอดไป จุดที่ค้นใบจากรายการภาษี (ตัวกัน `certificate_issued`) ต้องนับเฉพาะใบสถานะออกแล้ว (G03)
- **การยกเลิกรายจ่ายทำให้รายการรอออกเป็นยกเลิกทุกกรณี** รวมรายจ่ายที่ยังไม่เคยออกใบ (K06) วันนี้การยกเลิกรายจ่ายที่ยืนยันแล้วไม่แตะรายการรอออก รายการภาษีของรายจ่ายยังไปตามทางเดิม ไม่เปลี่ยน
- **"แก้ไขหนังสือรับรอง" การออกในระบบ และการออกใบแทน** ทั้งสามคำสั่ง: ตรวจว่ารายจ่ายต้นทางยังอยู่ในสถานะยืนยันแล้ว, ตรวจว่าใบยังมีสถานะออกแล้ว (สำหรับแก้ไขและใบแทน), และเขียนแถวรายจ่ายใน transaction เดียวกันโดยมีเงื่อนไขสถานะ ถ้าไม่มีแถวถูกเขียนให้ปฏิเสธ เหตุผล: การยกเลิกรายจ่ายอ่านข้อมูลก่อนได้ล็อก การเขียนแถวเดียวกันทำให้สองคำสั่งชนกันและมีฝั่งเดียวที่สำเร็จ (G04, K07) เป็นการเพิ่มการป้องกัน ไม่เปลี่ยนสิ่งที่ผู้ใช้ทำได้ ใบที่ถูกยกเลิกแล้วออกใบแทนไม่ได้
- การชนกันทุกแบบในข้อนี้ถูกแปลงเป็นข้อความไทยให้ลองใหม่ ไม่ใช่ข้อผิดพลาดของระบบ
- ข้อมูลรายการรอออกที่ส่งให้หน้าจอเพิ่มเลขที่ของใบ เพื่อให้หน้าต่างยืนยันและประวัติแสดงเลขที่ได้ วันนี้มีแต่ id
- **ช่องติ๊กบังคับ** ในหน้าต่างยืนยันของทั้งสองทาง: "ยังไม่ได้ยื่นภาษีงวดนี้ หรือจะยื่นเพิ่มเติมเอง" ระบบรู้ว่างวดยื่นแล้วเฉพาะร้านที่ใช้หน้า ภ.ง.ด.53 ร้านที่ยื่นนอกระบบจึงต้องรับรองเอง การติ๊กถูกบันทึกในประวัติพร้อมผู้ติ๊ก (D15, G06)
- เมื่อใบถูกยกเลิกโดยคนอื่นที่ไม่ใช่ผู้ออกใบ ระบบแจ้งผู้ออกใบเดิมว่าใบเลขที่ใดถูกยกเลิก เพราะอะไร และต้องออกใหม่หรือไม่ (G08)
- **ประวัติ** แสดงบนการ์ดหนังสือรับรองของหน้ารายจ่ายและในหน้ารายการ 50 ทวิ: ทุกเหตุการณ์ของรายจ่ายนั้น (ออก, แก้ไข, ยกเลิกตามต้นทาง, บันทึกฉบับที่ออกเอง, ยกเลิกการบันทึก) พร้อมเลขที่ สถานะ วันเวลา ผู้ทำ เหตุผล และใบที่มาแทน อ่านจากตารางประวัติแบบเพิ่มอย่างเดียว เพราะข้อมูลของฉบับที่ร้านออกเองอยู่บนแถวรายการรอออกซึ่งถูกนำกลับมาใช้ตอนยืนยันใหม่ (G05) วันนี้ระบบไม่เก็บไฟล์ของหนังสือรับรอง จึงดาวน์โหลดใบที่ถูกยกเลิกย้อนหลังไม่ได้ ประวัติแสดงเป็นข้อมูล
- **งวดภาษีหัก ณ ที่จ่ายของรายจ่ายที่ยื่น ชำระ หรือปิดแล้ว**: ปฏิเสธทั้งเปิดกลับมาแก้ (ตัวกัน `tax_period_filed` เดิม) และยกเลิก (เพิ่มให้เท่ากัน) ข้อความบอกสิ่งที่ยังทำได้ ไม่ใช่ "ติดต่อผู้ทำบัญชี" อย่างเดียว
- ตัวกันอื่นของสองทางนี้คงเดิม: ลงบัญชีแล้ว, ใบเบิกที่เดินอยู่, ยอดจองของใบเตรียมจ่าย (§8.5)
- ผู้ทำต้องมีสิทธิ์ของทางนั้นตามเดิม (`expense.confirm` สำหรับเปิดกลับมาแก้, `expense.void` สำหรับยกเลิก) **และ** `wht.certificate.correct` เมื่อมีใบที่ออกในระบบ หรือ `wht.external_certificate.link` เมื่อเป็นใบที่ร้านบันทึกเอง ไม่มีแล้วถูกปฏิเสธพร้อมบอกสิทธิ์ที่ขาด
- **ใบที่ร้านออกเองแล้วบันทึกไว้**: ระบบยกเลิกการบันทึกและเก็บประวัติ ข้อความยืนยันบอกว่าระบบยกเลิกเอกสารที่ร้านออกเองให้ไม่ได้ ร้านต้องยกเลิกเอง แล้วบันทึกฉบับใหม่หลังยืนยันรายจ่าย
- ข้อความยืนยันทุกทางบอกให้เรียกคืนหรือแจ้งยกเลิกฉบับที่มอบให้ผู้รับเงินไปแล้ว ระบบไม่ส่งอะไรถึงผู้รับเงิน
- **ใบเบิกที่รายจ่ายมีหนังสือรับรอง (D20)**: รายจ่ายของใบเบิกแก้หรือยกเลิกจากหน้ารายจ่ายไม่ได้ ทางออกจึงอยู่ที่การยกเลิกใบเบิก: ยกเลิกได้เมื่อผู้ยกเลิกมีสิทธิ์จัดการหนังสือรับรองชนิดนั้นและติ๊กรับรองเรื่องการยื่นภาษีในหน้าต่างยืนยันของใบเบิก ระบบยกเลิกหนังสือรับรองใน transaction เดียวกับการยกเลิกรายจ่ายของใบเบิก เขียนประวัติ และแจ้งผู้ออกใบ จากนั้นผู้ใช้ทำใบเบิกใหม่ด้วยข้อมูลที่ถูก และออกหนังสือรับรองใบใหม่ งวดที่ยื่นแล้วยังปฏิเสธ พร้อมบอกสิ่งที่ทำได้ ผู้ที่ไม่มีสิทธิ์ได้ข้อความบอกว่าใครทำได้ การตัดสินนี้ถูกเก็บไว้กับการยกเลิกที่เริ่มแล้ว ผู้ที่มาทำต่อหรือระบบที่ทำต่อให้จึงไม่ต้องถามซ้ำ และใบเบิกไม่ค้างครึ่งทาง
- ไม่เปลี่ยน: จุดรับรู้ภาษี, เนื้อหาและแบบของหนังสือรับรอง, ปุ่มออกใบแทน, เงื่อนไขของ "แก้ไขหนังสือรับรอง"
- ต้องแก้เอกสารบน main ให้ตรง: `expense-confirmed-return-for-correction-spec.md` (กติกา 4 ต.ค.) และคำถามค้างข้อ 3 ของ `wht-certificate-correction-replacement-spec.md`
- **ใบที่ค้างจากก่อนมีงานนี้** (G01, D19): เจ้าของยืนยัน 11 ต.ค. 2569 ว่ายังไม่มีร้านใดเปิดใช้ 50 ทวิบนระบบจริง จึง **ไม่นับและไม่เก็บกวาด** ไม่มีคำสั่งเก็บกวาดในงานนี้ สิ่งที่กันไว้มีอย่างเดียว: หน้ารายการ 50 ทวิไม่แสดงรายการของรายจ่ายที่ไม่ได้อยู่ในสถานะยืนยันแล้วเป็นงานรอออก (§10.2) รายการรอออกที่ค้างบนรายจ่ายที่ถูกยกเลิกไปก่อนหน้านี้จึงไม่กลายเป็นงานค้างของใคร

### 10.7 สิ่งที่ปรับระหว่างลงมือทำ (ถือตามข้อนี้เมื่อขัดกับ §10.6)

1. **ชื่อบนหน้าจอ**: หน้ารายจ่ายเรียกสองทางนี้ว่า "แก้ไขเอกสาร" และ "ยกเลิกเอกสาร" ข้อความใหม่ทุกข้อความบนหน้ารายจ่ายใช้สองคำนี้ ไม่ใช้ "เปิดรายจ่ายกลับมาแก้" หรือ "ยกเลิกรายจ่าย" ปุ่มออกหนังสือรับรองมีชื่อจริงว่า "พิมพ์เอกสาร 50 ทวิ" ประโยคที่บอกให้ออกใบใหม่จึงอ้างชื่อปุ่มนี้ ข้อความของใบเบิกใช้ "ยกเลิกคำขอเบิก"
2. **การกันคำสั่งชนกัน (K07)**: ไม่ได้เพิ่มการเขียนแถวรายจ่ายแยกในคำสั่งออก แก้ไขหนังสือรับรอง และออกใบแทน การยกเลิกตามต้นทางเขียนแถวรายการรอออกและแถวหนังสือรับรอง ซึ่งสามคำสั่งนั้นเขียนอยู่แล้ว ฐานข้อมูลจึงทำให้ชนกันเองและมีฝั่งเดียวที่สำเร็จ ทั้งสามคำสั่งตรวจว่ารายจ่ายต้นทางยังยืนยันแล้วภายใต้ล็อกวงจรชีวิตของรายจ่าย พิสูจน์ด้วย test แข่งกันบน PostgreSQL จริง ผู้ใช้ได้ข้อความไทยให้ลองใหม่
3. **หนังสือรับรองที่ออกจากหน้าภาษี** (ผูกผ่านรายการภาษี และอาจครอบหลายเอกสาร): ยังกันทั้ง "แก้ไขเอกสาร" และ "ยกเลิกเอกสาร" ระบบยกเลิกให้เองเฉพาะใบที่ออกจากรายการรอออกของรายจ่ายนั้นเอง ข้อความบอกว่าต้องจัดการใบนั้นที่หน้าภาษีก่อน
4. **ข้อปฏิเสธใหม่ของ "ยกเลิกเอกสาร"** (สิทธิ์จัดการหนังสือรับรอง ช่องติ๊กเรื่องการยื่นภาษี งวดที่ยื่นแล้ว) ใช้เฉพาะเมื่อรายจ่ายมีหนังสือรับรอง การยกเลิกเอกสารอื่นทำงานเหมือนเดิมทุกประการ
5. **เลขรอบ**: key ออกเลขและ key กันส่งซ้ำของการออกหนังสือรับรองมีเลขรอบของรายการรอออก รอบเพิ่มทุกครั้งที่ใบถูกยกเลิกตามต้นทาง
6. **"แก้ไขหนังสือรับรอง"** (พบจากการเดินหน้าจอจริง): ช่องที่คำขอไม่ได้ส่งมาต้องคงค่าเดิม เดิมถูกล้าง ทำให้การแก้ครั้งที่สองล้มและเสียเลข ชื่อผู้รับเงินว่างถูกปฏิเสธพร้อมข้อความ ครั้งที่ล้มหลังจองเลขแล้วจะยกเลิกการจองเลขนั้น เลขไม่ถูกนำกลับมาใช้ จึงมีเลขที่ข้ามได้ โดยมีบันทึกว่าเลขนั้นถูกยกเลิก
7. **หน้าจอรู้ล่วงหน้าว่าผู้ดูยกเลิกหนังสือรับรองได้หรือไม่** จากข้อมูลความสามารถของรายจ่าย ผู้ไม่มีสิทธิ์จึงเห็นข้อความบอกสิทธิ์ที่ขาดแทนฟอร์ม ไม่ต้องกรอกก่อนแล้วจึงถูกปฏิเสธ
8. **ข้อปฏิเสธทุกข้อที่ผู้ใช้เจอได้จากสองทางนี้มีรหัสและข้อความไทย** รวมกรณีที่สถานะของเอกสารเปลี่ยนไประหว่างเปิดหน้าค้างไว้ ซึ่งบอกให้เปิดหน้านี้ใหม่
9. **ประวัติของฉบับที่ร้านออกเอง** เก็บเลขอ้างอิงและหมายเหตุที่ร้านพิมพ์ไว้ด้วย เมื่อการบันทึกถูกยกเลิกข้อมูลนี้ยังอยู่ในประวัติ
10. **บั๊กของเดิม E1–E3** (ฐานเงินได้บนหนังสือรับรอง การแก้ครั้งที่สองทับครั้งแรก วันที่ออกเพี้ยนข้ามวัน) แก้ในส่งมอบนี้แล้ว E4–E5 อยู่ในส่งมอบ ข
11. **ใบเบิก (D20)** สร้างตามข้อสุดท้ายของ §10.6: การตัดสินของผู้เริ่มยกเลิกเก็บในช่องใหม่หนึ่งช่องบนคำขอเบิก
12. **เลขหนังสือรับรองนับรายปี (บั๊กของเดิม พบจากการเดินหน้าจอจริงรอบสอง)**: เลขพิมพ์เป็น `WHT-{ปี}-{ลำดับ}` แต่ตัวนับเดิมแยกรายเดือน เดือนที่สองของปีจึงได้เลขซ้ำและออกไม่ได้ ตอนนี้มีตัวนับเดียวต่อร้านต่อปี migration รวมตัวนับรายเดือนเดิมให้ตัวนับรายปีต่อจากเลขสูงสุดที่เคยใช้ เลขที่เคยออก ยกเลิก หรือจองไว้ไม่ถูกใช้ซ้ำ ถ้าเลขยังซ้ำได้อีก ผู้ใช้ได้ข้อความที่บอกให้ลองใหม่และแจ้งทีม ไม่ใช่ "กำลังออกเอกสารนี้อยู่"
13. **คำตอบของการแก้ไขเอกสาร ยกเลิกเอกสาร และยกเลิกคำขอเบิก** ระบุหนังสือรับรองที่ระบบยกเลิกจริง ข้อความแจ้งสำเร็จจึงถูกแม้มีคนแก้ไขหนังสือรับรองระหว่างที่หน้าต่างเปิดค้าง
14. **งวดที่ยื่นแล้ว**: ข้อความปฏิเสธใช้คำทั่วไป เดือนแบบ "ก.ย. 2569" ระบุชื่อแบบในวงเล็บ และบอกสิ่งที่ทำได้ (ผิดเฉพาะตัวสะกดหรือที่อยู่ใช้ "แก้ไขหนังสือรับรอง" ได้ ถ้ายอด อัตรา หรือเลขผู้เสียภาษีผิดต้องยื่นแบบเพิ่มเติม) ระบบไม่มีทางเปิดงวดที่ยื่นแล้วกลับมาแก้ หน้าต่างยกเลิกเอกสารบอกเรื่องนี้ก่อนให้กรอก
15. **การแก้ไขหนังสือรับรองที่ไม่เปลี่ยนอะไร** ถูกปฏิเสธก่อนใช้เลข การส่งคำขอเดิมซ้ำหลังสัญญาณหลุดจึงไม่ออกใบที่สาม
16. **ใบเบิกหักภาษี ณ ที่จ่ายไม่ได้ในระบบวันนี้**: รายจ่ายที่เกิดจากใบเบิกถูกสร้างด้วยยอดหักเป็นศูนย์และไม่มีช่องหักภาษีในฟอร์มใบเบิก ทางออกตาม D20 (ยกเลิกใบเบิกพร้อมหนังสือรับรอง) จึงยังไม่มีทางถูกใช้ โค้ดและ test ของทางนั้นคงไว้ **เจ้าของตัดสินแล้ว (D22): ใบเบิกไม่หักภาษี ณ ที่จ่ายในรุ่นนี้** รายการที่ต้องหักให้บันทึกเป็นรายจ่ายปกติ ซึ่งหักและออกหนังสือรับรองได้อยู่แล้ว ถ้าจะเปิดให้ใบเบิกหักได้ต้องมี spec ของตัวเอง (ใครรับภาระภาษีเมื่อพนักงานจ่ายร้านเต็มจำนวนไปแล้ว และหนังสือรับรองออกในชื่อร้าน)
17. **สิทธิ์ของการ์ดหนังสือรับรอง (§10.3)**: ผู้มีสิทธิ์ออกในระบบบันทึกที่อยู่ผู้รับเงินได้ด้วย ผู้มีสิทธิ์บันทึกใบที่ออกเองอ่านรายการรอออก ประวัติ และไฟล์ของใบที่ออกในระบบได้ เลขอ้างอิงของใบที่ออกเองไม่บังคับ ทุกทางยังอยู่ใต้ขอบเขตสาขาและกติกาอ่านรายจ่ายต้นทาง
18. **ถ้อยคำ**: ประวัติใช้คำว่า "เอกสาร" (เช่น "ยกเลิก เพราะเอกสารถูกแก้ไข") ช่องติ๊กใช้ "…ของรายการนี้…" ไม่ใช่ "ของเดือนนี้" ข้อความเรื่องสิทธิ์ระบุเลขที่ใบเมื่อทราบ
19. **แก้ไขการบันทึกใบที่ร้านออกเอง** ทำได้จากการ์ดโดยผู้มีสิทธิ์บันทึกใบที่ออกเอง ไม่ต้องแก้ไขเอกสาร ค่าเดิมเก็บในประวัติ งวดที่ยื่นแล้วยังแก้ไม่ได้ คำขอที่ไม่เปลี่ยนอะไรถูกปฏิเสธ
20. **แถวที่กลับมาเป็นยังไม่ออก** แสดงว่าใบเดิมเลขที่ใดถูกยกเลิกเมื่อไร ทั้งบนการ์ดและในหน้ารายการ และไม่ส่งเลขกับวันที่ของใบที่ถูกยกเลิกมาเป็นของแถวนั้น
21. **ที่อยู่ผู้รับเงิน**: หน้ารายการและการ์ดเตือนเมื่อยังไม่มีที่อยู่ พร้อมทางเพิ่ม **เจ้าของตัดสินแล้ว (D22): ออกไม่ได้จนกว่าจะมีที่อยู่** รายละเอียดอยู่ในข้อ 25
22. **ฟอร์ม "แก้ไขหนังสือรับรอง"**: คำอธิบายบอกว่าแก้ที่นี่เปลี่ยนเฉพาะตัวหนังสือรับรอง ถ้ารายจ่ายผิดด้วยให้ใช้ "แก้ไขเอกสาร"; ป้ายใช้ "ประเภทผู้รับเงิน" และ "รหัสสาขาของผู้รับเงิน"; แสดงชื่อหมวดเงินได้ ไม่แสดงรหัส; ฟอร์มยังแก้ได้ทุกช่องเหมือนเดิม
23. **ข้อความมุมจอทั้งระบบ** ไม่ตัดเลขเอกสารขึ้นบรรทัดใหม่ และข้อความปฏิเสธของการบันทึกใบที่ออกเองไม่ใช้คำว่า "แนบ" (หน้าเจ้าหนี้ซึ่งไม่อยู่ในแพ็กเกจที่ขายยังใช้คำเดิม)
24. **ยังเปิดอยู่**: เจ้าของร้านแพ็กเกจที่ออกในระบบไม่ได้ ถ้าเปิดหน้ารายการ 50 ทวิจากลิงก์ตรง จะเห็นข้อความ "คุณไม่มีสิทธิ์" ของตัวกันกลาง ซึ่งไม่ตรงเหตุ; ประวัติอยู่บนการ์ดของหน้ารายจ่าย ไม่ได้อยู่ในหน้ารายการ (หน้ารายการมีบรรทัดใบเดิมและลิงก์ไปรายจ่าย)
25. **ออกหนังสือรับรองไม่ได้ถ้ายังไม่มีที่อยู่ผู้รับเงิน (D22)**: ที่อยู่ที่ใช้พิมพ์คือที่อยู่ที่ผู้ใช้พิมพ์บนรายการรอออก ถ้าไม่มีจึงใช้ที่อยู่ที่ติดมากับรายจ่าย ถ้าว่างทั้งสองที่ ระบบปฏิเสธก่อนใช้เลขและก่อนเขียนประวัติ ด้วยข้อความ "ยังไม่มีที่อยู่ผู้รับเงิน กรุณาเพิ่มที่อยู่ผู้รับเงินก่อน แล้วกดออกหนังสือรับรองอีกครั้ง" บนการ์ด ลำดับการกดคือเพิ่มที่อยู่ก่อนแล้วจึงออก: เมื่อยังไม่มีที่อยู่ การ์ดไม่แสดงปุ่มออก แสดงบรรทัด "ยังไม่มีที่อยู่ผู้รับเงิน เพิ่มที่อยู่ก่อนจึงจะออกหนังสือรับรองได้" และปุ่มหลักคือ "เพิ่มที่อยู่" ผู้ที่ออกในระบบได้ทุกคนบันทึกที่อยู่ได้ (ข้อ 17) ที่อยู่ที่บันทึกถูกจำในทะเบียนคู่ค้าตามของเดิม ทางออกหนังสือรับรองโดยตรงของหน้าภาษี (ยังไม่มีหน้าจอเรียกใช้) ปฏิเสธแบบเดียวกัน การแก้ไขหนังสือรับรองต้องจบด้วยที่อยู่ที่ไม่ว่าง โดยบอกให้พิมพ์ที่อยู่ในฟอร์มนั้น หน้าเจ้าหนี้การค้าใช้ลำดับเดียวกันและให้ผู้ออกในระบบบันทึกที่อยู่ได้ ใบแทนเป็นสำเนาของใบที่ออกแล้วจึงไม่เปลี่ยน "บันทึกว่าออกหนังสือรับรองเองแล้ว" ไม่ต้องมีที่อยู่ เพราะเป็นการจดว่าร้านทำกระดาษเองแล้ว
26. **จากการตรวจหน้าจอรอบสุดท้าย (12 ต.ค.)**: บนใบที่พิมพ์ ที่อยู่ของผู้จ่ายและผู้รับเงินอยู่เหนือเส้นประ และเลขผู้เสียภาษีทุกหลักอยู่ในช่อง; บนการ์ด เลขอ้างอิงและหมายเหตุของใบที่ร้านออกเองแสดงก่อนประวัติ ไม่ซ้ำใต้รายการประวัติ **ยังเปิดอยู่**: ระบบรับหมวดเงินได้ของนิติบุคคลบนผู้รับเงินที่เป็นบุคคลธรรมดา (เป็นเรื่องของการบันทึกรายจ่าย นอกสามจุดของ D24)
27. **ออกหนังสือรับรองไม่ได้ถ้าร้านยังไม่มีเลขผู้เสียภาษีหรือที่อยู่ของร้านเอง (D23)**: ข้อมูลผู้จ่ายบนหนังสือรับรองถูกจำไว้ตั้งแต่ยืนยันรายจ่าย ดังนั้นตอนกดออก ช่องที่ว่างหรือพิมพ์ไม่ได้ (รวมเลขที่ไม่ครบ 13 หลัก) จะเติมจากข้อมูลกิจการล่าสุด ค่าที่จำไว้และพิมพ์ได้คงเดิม ข้อมูลที่จำไว้บนรายการรอออกและค่าตรวจสอบของมันไม่ถูกแก้ ถ้ายังขาด ระบบปฏิเสธก่อนใช้เลขและก่อนเขียนประวัติ ด้วยข้อความที่ระบุสิ่งที่ขาด (เลขผู้เสียภาษี ที่อยู่ หรือทั้งสอง) ลำดับคือข้อมูลของร้านก่อน แล้วจึงที่อยู่ผู้รับเงิน (ข้อ 25) คำตอบของรายการรอออกบอกสิ่งที่ขาดล่วงหน้า การ์ด หน้ารายการ และหน้าเจ้าหนี้การค้าจึงไม่เสนอปุ่มออก แสดงบรรทัด "ยังไม่มี…ของกิจการ กรอกข้อมูลกิจการก่อนจึงจะออกหนังสือรับรองได้" ผู้มีสิทธิ์แก้ข้อมูลกิจการได้ปุ่ม "ไปกรอกข้อมูลกิจการ" คนอื่นอ่านว่าให้ผู้ที่แก้ข้อมูลกิจการได้กรอกก่อน ทางออกโดยตรงและการแก้ไขหนังสือรับรองใช้กติกาเดียวกัน ใบแทนไม่เปลี่ยน แถวในหน้ารายการไม่เสนอปุ่มที่กดแล้วจะถูกปฏิเสธ: ถ้าขาดที่อยู่ผู้รับเงิน ปุ่มของแถวคือ "เพิ่มที่อยู่"
28. **สามจุดในการบันทึกรายจ่าย (D24)**: (ก) การแนบหรือลบไฟล์ทำให้หน้าอ่านรายจ่ายใหม่และเคยล้างค่าที่ผู้ใช้เพิ่งเลือกในขั้นตรวจ ตอนนี้ขั้นตรวจคงค่าที่ผู้ใช้แก้ไว้ และยังรับค่าที่เซิร์ฟเวอร์เปลี่ยนในช่องที่ผู้ใช้ไม่ได้แตะ (ข) ปุ่มในหน้ารายการค่าใช้จ่ายใช้ชื่อ "บันทึกด้วยมือ" เหมือนเมนู สวิตช์ และคู่มือ (ค) คำถามเป็น "รายการนี้หักภาษี ณ ที่จ่ายไหม" และสี่ช่อง (หักหรือไม่ ประเภทผู้รับเงิน ประเภทเงินได้ สถานะหลักฐานภาษี) มีคำอธิบายหนึ่งบรรทัดใต้ช่อง อ่านพร้อมช่องโดยโปรแกรมอ่านจอ ชื่อช่องไม่เปลี่ยน เพราะรายงาน ตัวกรอง ข้อความปฏิเสธ และ LINE ใช้ชื่อเดียวกัน หน้ารายจ่ายที่ถูกตรึงด้วยชุดทดสอบไม่ถูกแก้ (ส่วนของขั้นตรวจอยู่ในไฟล์ส่วนประกอบร่วม)
29. **จากการเดินตามขั้นตอนทดลองของเจ้าของ (12 ต.ค.)**: ที่อยู่ผู้รับเงินที่พิมพ์บนการ์ดอยู่ต่อหลัง "แก้ไขเอกสาร" และยืนยันอีกครั้ง เมื่อผู้รับเงินยังเป็นรายเดิม (เลขผู้เสียภาษีตรงกัน หรือชื่อตรงกันเมื่อไม่มีเลขทั้งคู่) เว้นแต่รายจ่ายมีที่อยู่ของตัวเองที่ต่างจากเดิม ซึ่งถือว่าผู้ใช้เพิ่งแก้ จึงใช้ที่อยู่ของรายจ่าย; แท็บ "ยกเลิก" ของหน้ารายการบอกวันที่ยกเลิก เหตุ และเหตุผลที่พิมพ์; หน้าต่างที่อยู่ใช้ชื่อ "เพิ่มที่อยู่ผู้รับเงิน" หรือ "แก้ไขที่อยู่ผู้รับเงิน"; ข้อความปฏิเสธสองข้อจบด้วยชื่อปุ่มจริง "พิมพ์เอกสาร 50 ทวิ" ซึ่งอ่านจากที่เดียวกับปุ่ม; บนกระดาษ ที่อยู่เว้นที่ให้สระล่างเหนือเส้นประ
30. **ที่อยู่ของร้านบนเอกสารที่พิมพ์มีคำนำหน้า (D26)**: รูปแบบสำหรับพิมพ์เติม "แขวง" และ "เขต" เมื่อจังหวัดคือกรุงเทพมหานคร และ "ตำบล" "อำเภอ" "จังหวัด" เมื่อเป็นจังหวัดอื่น ส่วนที่มีคำนำหน้าอยู่แล้ว (เต็มหรือย่อ) ไม่ถูกเติมซ้ำ ใช้กับที่อยู่ผู้จ่ายบนหนังสือรับรอง (ทั้งค่าที่จำไว้ตอนยืนยันรายจ่ายและค่าที่เติมจากข้อมูลกิจการตอนออก) ทางออกโดยตรง และใบเตรียมจ่าย/ใบสำคัญจ่าย รูปแบบเดิมที่ไม่มีคำนำหน้ายังใช้กับการเทียบที่อยู่ของร้านกับใบกำกับภาษีที่ร้านได้รับ และแบบ ภ.ง.ด.53 ใช้ช่องแยกของแบบอยู่แล้วจึงไม่เปลี่ยน ที่อยู่ผู้รับเงินพิมพ์ตามที่ผู้ใช้กรอก เหตุผล: ไม่พบแนววินิจฉัยของกรมสรรพากรที่ตอบเรื่องการละคำนำหน้าโดยตรง แต่บรรทัดคำแนะนำของแบบขอ "ตำบล/แขวง อำเภอ/เขต จังหวัด" และที่อยู่แบบไม่มีคำนำหน้ากำกวมเมื่อชื่อตำบลกับอำเภอซ้ำกัน
31. **"แก้ไขหนังสือรับรอง" แก้ได้เฉพาะสิ่งที่ไม่กระทบแบบที่ยื่น (D28 ข้อ 4)**: แก้ได้เฉพาะชื่อ ที่อยู่ รหัสสาขาของผู้รับเงิน และวันที่จ่าย ส่วนจำนวนเงินที่จ่าย ภาษีที่หักไว้ อัตราภาษี แบบที่ยื่น ประเภทเงินได้ และเลขผู้เสียภาษีของผู้รับเงิน ระบบปฏิเสธก่อนเขียนข้อมูลใด ๆ (ค่าที่ส่งมาเท่าเดิมไม่นับเป็นการแก้ เพื่อให้หน้าจอรุ่นเก่ายังทำงาน) หน้าจอแสดงค่าที่ล็อกเป็นข้อความสองบรรทัดใต้ช่องที่แก้ได้ พร้อมปุ่ม "แก้ไขเอกสาร" ของรายจ่าย ปุ่มยืนยันชื่อ "ออกใบใหม่แทนใบเดิม" ข้อนี้แทนข้อความ "ไม่เปลี่ยนพฤติกรรม" ของตารางใน §10.2 สำหรับช่องที่ล็อก
32. **ลบการบันทึกว่าร้านออกเองที่บันทึกผิด (D28 ข้อ 5)**: ผู้มีสิทธิ์บันทึกลบได้โดยต้องใส่เหตุผล รายการกลับไปรอออก (คงที่อยู่ผู้รับเงินและข้อมูลที่จำไว้) ประวัติเก็บเป็นเหตุการณ์ของตัวเองพร้อมผู้ทำ เลขที่ และเหตุผล แยกจากการลบที่เกิดจากการเปิดรายจ่ายกลับมาแก้ ใช้การตรวจขอบเขต สถานะรายจ่าย งวดภาษีที่ยื่นแล้ว และรุ่นข้อมูลชุดเดียวกับคำสั่งข้างเคียง และกันคำสั่งซ้ำด้วยรหัสคำสั่ง
33. **หน้ายืนยันก่อนออกหนังสือรับรอง (D28 ข้อ 1 และ 3)**: ปุ่มชื่อ "ออกหนังสือรับรอง 50 ทวิ" (ชื่อเดียวจากแหล่งเดียว ข้อความปฏิเสธของระบบจึงตามไปด้วย) กดแล้วเปิดหน้าต่างแสดงสิ่งที่จะพิมพ์: ผู้รับเงิน เลขผู้เสียภาษี ที่อยู่ ประเภทเงินได้ จำนวนเงินที่จ่าย ภาษีที่หักไว้ และประโยคเดียว "ออกแล้วได้เลขที่ทันที ถ้าผิดต้องยกเลิกแล้วออกใหม่" ปุ่มยืนยันไม่รับการกดใน 600 มิลลิวินาทีแรก เมื่อรายจ่ายยังไม่บันทึกว่าจ่ายครบ มีป้าย "ยังไม่ได้บันทึกว่าจ่าย" (เฉพาะเมื่อกดจากหน้ารายจ่าย ซึ่งรู้สถานะการจ่าย) ระบบไม่ห้ามออก และวันที่จ่ายบนหนังสือรับรองยังเป็นไปตาม D5
34. **การ์ดหนังสือรับรองและหน้าต่างที่เกี่ยวข้องพูดให้น้อย (D29)**: สถานะบนการ์ดเป็นวลีสั้น; "ออกใบแทน" เป็น "พิมพ์ใบแทน (เลขที่เดิม)" และไม่มีบรรทัดอธิบาย; หลังออกแล้วการ์ดบอก "พิมพ์ ตรวจลายเซ็น แล้วส่งให้ผู้รับเงิน"; หน้าต่างแก้ไขและยกเลิกเอกสารที่มีหนังสือรับรองเหลือบรรทัดที่บอกเลขที่ใบที่จะถูกยกเลิก ประโยคเดียวสำหรับใบที่ร้านออกเอง ("ระบบยกเลิกใบที่ร้านออกเองให้ไม่ได้ ร้านต้องยกเลิกเอง") ช่องเหตุผล และตัวเลือกสองข้อเรื่องการยื่นภาษีแทนช่องติ๊กเดียว (ค่าที่ส่งให้ระบบยังเป็นคำรับรองเดิม) สิ่งที่ต้องทำต่อบอกบนหน้าหลังกดแล้ว เหตุผลที่พิมพ์ไว้ไม่หายเมื่อปิดหน้าต่าง และปุ่มที่ยกเลิกหนังสือรับรองใช้สีของการกระทำที่ย้อนไม่ได้ทั้งสองหน้าต่าง
35. **หน้าต่างอ่านหนังสือรับรองฉบับปัจจุบันเสมอ (D27)**: หน้าต่างแก้ไขและยกเลิกเอกสารอ่านเลขที่จากข้อมูลชุดเดียวกับการ์ด จึงไม่แสดงเลขที่ที่เพิ่งถูกแทนไปแล้ว
36. **ยืนยันรายจ่ายจบในรอบเดียว (D27)**: ผู้ที่มีสิทธิ์ยืนยันเห็นปุ่ม "ยืนยันเอกสาร" ที่ขั้นสุดท้ายของรอบแรก (ระบบส่งแล้วยืนยันด้วยการตรวจชุดเดิม ถ้าการยืนยันถูกปฏิเสธ รายจ่ายที่ส่งแล้วยังเปิดอยู่พร้อมปุ่มยืนยันตามเดิม) "ส่งให้คนอื่นตรวจ" เป็นปุ่มรอง ผู้ไม่มีสิทธิ์ยืนยันเห็นเฉพาะปุ่มส่ง กติกาฝั่งระบบไม่เปลี่ยน
37. **ฟอร์มและขั้นตรวจของการบันทึกรายจ่าย (D27, D29)**: ฟอร์มบันทึกด้วยมือใส่สาขาให้ก่อนเมื่อทำได้ และบอก "เลือกสาขาก่อน จึงจะกรอกรายการได้" เมื่อแตะช่องที่ยังล็อก; ช่องที่ยังไม่เคยถามไม่ขึ้นข้อความผิดพลาดจนกว่าจะกดถัดไป และการกดหนึ่งครั้งแจ้งทุกข้อที่ขาด; คำถามเรื่องหัก ณ ที่จ่ายใช้คำของร้าน ("ผู้รับเงินเป็นใคร" "จ่ายค่าอะไร" พร้อมอัตราในตัวเลือก); คำใบ้เหลือบรรทัดเดียว; ชื่อการบันทึกฉบับร่างเหลือชื่อเดียว; ไม่แสดงรหัสเหตุผลของระบบ; รายจ่ายที่บันทึกด้วยมือไม่แสดงกล่องข้อมูลจาก AI ที่ว่าง; ฟอร์มไม่ล้นจอแคบ
38. **หน้ารายจ่ายที่ยืนยันแล้วและที่ยกเลิกแล้ว (D27)**: กล่องบนสุดของรายจ่ายที่ยืนยันแล้วบอกงานถัดไปจากข้อมูลที่หน้ามีอยู่ ("ต้องจ่าย ฿…" พร้อมปุ่มไปที่การชำระเงิน และปุ่มไปที่หนังสือรับรอง 50 ทวิ เมื่อยังรอออก หรือบรรทัดสรุปเมื่อครบแล้ว) แถบทางลัดมี "50 ทวิ" และเลื่อนในแถวเดียว; รายจ่ายที่ยกเลิกแล้วเปิดด้วยกล่องสีแดงบอกวันที่ เหตุผล และหนังสือรับรองที่ถูกยกเลิกด้วย และไม่มีปุ่มที่ใช้ไม่ได้; ปุ่มจ่ายใช้คำว่า "ส่วนที่เหลือ" เฉพาะเมื่อมีการจ่ายที่ยังมีผลอยู่แล้ว
39. **เตือนเลขผู้เสียภาษีที่ไม่ผ่านหลักตรวจสอบ (D28 ข้อ 6)**: เมื่อพิมพ์ครบ 13 หลักและหลักตรวจสอบไม่ผ่าน มีบรรทัดเตือนใต้ช่อง และสรุปการตรวจนับเป็น "ต้องตรวจ" ไม่ห้ามบันทึก ฝั่งระบบยังรับเลขเช่นนี้ ตัวคำนวณย้ายไปอยู่ที่สัญญากลางและหน้าข้อมูลร้านใช้ตัวเดียวกันโดยพฤติกรรมไม่เปลี่ยน
40. **หน้ารายการ 50 ทวิ หาง่ายและทำงานจากหน้านั้นได้ (D27)**: เมนูอยู่ถัดจากรายการค่าใช้จ่ายและสองทางของการบันทึก (ชื่อ สิทธิ์ และการผูกแพ็กเกจเดิม) และหน้า ภ.ง.ด.53 มีลิงก์มา; การค้นที่ไม่พบในแท็บปัจจุบันบอกว่าพบในแท็บใดพร้อมปุ่มไป; การค้นอ่านประวัติหนังสือรับรองด้วย จึงพบเลขที่ที่ถูกแทนหรือถูกยกเลิก แถวอยู่ในแท็บของรายการตามเดิมและบอกเลขที่ที่ตรงกับคำค้นกับใบที่มีผลอยู่ (ตัวเลขบนแท็บนับด้วยกติกาเดียวกัน); แถวบอกรายละเอียดของรายจ่าย (นิยามเดียวกับตัวเลือกรายจ่ายของใบเบิก) และ "จ่าย ฿… · หักไว้ ฿…"; "เพิ่มที่อยู่" เปิดหน้าต่างบนหน้ารายการ; แท็บของรายการที่ถูกยกเลิกชื่อ "ยกเลิกแล้ว"; เลขที่ในแถวไม่ถูกตัดกลางเลข
41. **ที่อยู่ที่ถูกล้างเพราะเลขผู้เสียภาษีเปลี่ยน บอกผู้ใช้ (D27)**: กติกาเดิมคงอยู่ (เลข 13 หลักต่างกันคือผู้รับเงินคนละราย) เมื่อการเปิดรายการกลับมาทำให้ที่อยู่ที่พิมพ์ไว้ถูกทิ้งด้วยเหตุนี้ ประวัติของรายการบันทึกเหตุการณ์ และการ์ดบอก "ที่อยู่ที่เคยเพิ่มไว้ใช้กับเลขผู้เสียภาษีเดิม" จนกว่าจะบันทึกที่อยู่ใหม่

## 11. ข้อมูลและ field

### 11.1 โครงสร้างใหม่ (เพิ่มอย่างเดียว)

| ตาราง | field หลัก |
|---|---|
| `DisbursementVoucher` (เอกสารใบเดียวทั้งก่อนและหลังจ่าย) | `companyId`, `branchId`, `number` (ว่างจนส่งครั้งแรก), `revision`, `status`, ที่มา (จัดทำเป็นใบ / กดออกจากการจ่ายตรง / ออกใหม่แทนใบที่ถูกยกเลิก + ใบที่อ้างถึง), ผู้รับเงิน: snapshot ชื่อ/เลขภาษี/สาขา (ไม่เก็บการผูกคู่ค้า K02), ฐานที่ใช้รวมผู้รับเงิน (รายการเดียว / เลขภาษี / ชื่อตรงกัน / ผู้จัดทำยืนยัน) + ผู้ยืนยัน, `plannedPayDate`, `plannedMethod`, บัญชีผู้รับ: ธนาคาร/ชื่อบัญชี/4 หลักท้าย + เลขเต็มเข้ารหัส, `note`, `totalAmount`, `currency`, ผู้จัดทำ, ผู้อนุมัติที่เลือก, ผู้รับแจ้งเตือนล่าสุด + เวลาและลำดับการเตือน, ผู้อนุมัติจริง + `selfApproved`, เหตุผลตีกลับ/ยกเลิก + เครื่องหมายยกเลิกหลังจ่าย, ผู้จ่าย + `paidAt` + `paidMethod` + `paidFromRef`, snapshot และ hash ตอนจ่าย, `templateVersion`, `pdfAttachmentId?`, `version` สำหรับ CAS |
| `DisbursementVoucherRevision` | `voucherId`, `revision`, `snapshotJson`, `snapshotHash`, ผู้ส่ง/เวลา, ผลตัดสิน |
| `DisbursementVoucherLine` | `voucherId`, `expenseId`, `amount`, `sourceHashAtSubmit`, `expensePaymentId?` (มีค่าเมื่อจ่ายแล้ว; unique แบบมีเงื่อนไข: การจ่ายหนึ่งรายการอยู่ในใบที่ยังไม่ถูกยกเลิกได้ใบเดียว) |
| `WhtCertificateHistory` (เพิ่มอย่างเดียว) | รายจ่ายและรายการรอออกที่เกี่ยวข้อง, ชนิดเหตุการณ์, เลขที่ใบ, เป็นใบในระบบหรือฉบับที่ร้านออกเอง, วันที่ของใบ, ผู้ทำ, เวลา, เหตุผล, ใบที่มาแทน, การรับรองเรื่องการยื่นภาษี |

| `CompanyWebEntrySetting` (เดิม) | เพิ่ม `disbursementVoucherEntryEnabled?` |

- **ไม่แตะตาราง `ExpensePayment`**: ความสัมพันธ์กับใบอยู่ที่ `DisbursementVoucherLine.expensePaymentId`
- ชื่อในโค้ดใช้ disbursement voucher ทุกที่ (K01) ตารางใหม่ลบตามบริษัท (cascade) และห้ามลบรายจ่ายที่ยังถูกอ้าง (restrict) ตามแบบตารางลูกของรายจ่าย enum ใหม่ต้องมีคู่ใน contracts (มี test เทียบ) ช่องใหม่บนรายจ่ายต้องเพิ่มในชนิดข้อมูลของ contracts ด้วยมือ migration เพิ่มอย่างเดียวและตั้งชื่อโฟลเดอร์ตามกติกาที่ตัวตรวจของระบบจริงอ่าน
- ไฟล์แนบสองชนิดใหม่: สลิปของใบ และไฟล์ใบสำคัญจ่าย แต่ละชนิดมีทางอัปโหลด/แนบ/ดาวน์โหลดของตัวเองตามแบบสลิปใบเบิก มีกติกาไม่ให้ไฟล์เดียวถูกใช้ข้ามชนิด และถูกกันไม่ให้ลบขณะยังอ้างถึง สลิปผูกกับใบ ไม่ผูกกับรายจ่ายหลายรายการ
- ชนิดเลขเอกสารหนึ่งชนิดใหม่ใน `DEFAULT_DOCUMENT_SEQUENCE_CONFIGS` (เสนอ `PV-{YYYY}{MM}-{SEQ}` รีเซ็ตรายเดือน; ไม่ใช้ `PAY-` เพราะมีสองชนิดเดิมใช้อยู่) ไม่ต้อง seed รายบริษัท
- ไม่มีตารางรวมการจ่ายแยก ไม่มีตารางภาษีใหม่ ไม่มีชื่อ `ExecutionAttempt` (ถูกใช้แล้วโดย feature-launch) ไม่มี key ใหม่ใน `FEATURE_CATALOG`
- `sourceHashAtSubmit` คำนวณจาก field ที่มีผลต่อการจ่าย (สถานะ ยอดสุทธิ ผู้ขาย สาขา สกุลเงิน) ไม่ใช้ `updatedAt`
- เลขบัญชีผู้รับ: เข้ารหัสด้วยตัวเข้ารหัสเดียวกับบัญชีรับเงินคืน แสดง 4 หลักท้าย เปิดเลขเต็มเฉพาะผู้อนุมัติ ผู้บันทึกจ่าย และผู้ที่แก้ไขใบร่างนั้นได้ (รวมผู้จัดทำที่นำบัญชีจากใบเดิมที่ตนเปิดได้มาใช้) ผ่านคำสั่งที่เขียน audit ก่อนถอดรหัส (โมดูล `data-rights` ไม่มีทะเบียนช่องข้อมูลให้ลงเพิ่ม ดู §14)

| วันที่จ่ายจริง / วิธี / จ่ายจาก | เขียนลง `ExpensePayment.paidAt`, `paymentMethod`, `bankAccountRef` | อยู่ใน fingerprint รุ่น 1 อยู่แล้ว ไม่ต้องขึ้นรุ่น "จ่ายจาก" เป็นข้อความกำกับ และปรากฏบนใบรับรองแทนใบเสร็จ ชุดส่งออกหลักฐาน และหน้าจับคู่ธนาคารด้วย หน้าจอจึงบอกไม่ให้พิมพ์เลขบัญชีเต็ม |
| key กันส่งซ้ำของแต่ละการจ่าย | `dv:<voucherId>:<lineId>` | ไม่เกิน 64 ตัว คงที่เมื่อ retry |

### 11.3 ข้อบังคับของยอด

```text
0 < line.amount ≤ expense.outstandingAmount                 (ตอนส่ง และตรวจซ้ำตอนจ่าย)
sum(line.amount) = voucher.totalAmount
จ่ายแล้ว: ทุก line มี expensePaymentId และ ExpensePayment.amount = line.amount
expense.reservedByDisbursementVoucherId มีค่า ⇔ รายจ่ายอยู่ในใบที่รออนุมัติหรืออนุมัติแล้ว รอจ่าย
```

- ยอดของรายจ่ายเปลี่ยนได้ทางเดียวคือตรรกะของ `recordPaymentAtomic` และการยกเลิกการจ่ายเดิม เอกสารนี้ไม่เขียนยอดของรายจ่าย
- ใช้ Decimal และกติกาทศนิยมเดิม (เก็บ 4 ตำแหน่ง รับ 2 ตำแหน่ง) ไม่ใช้ float
- การลงบัญชีเกิดจากการจ่ายแต่ละรายการตามเดิมเท่านั้น และมีผลเฉพาะร้านที่เปิดบัญชีแยกประเภท ซึ่งไม่อยู่ในแพ็กเกจที่ขาย

## 12. API และ transaction

เส้นทางด้านล่างเป็นข้อเสนอ ใช้ envelope, requestId, validation และรูปแบบ error ของ repo

| กลุ่ม | สัญญา |
|---|---|
| ผู้รับเงินและรายการที่เลือกได้ | ตัวอ่านสองตัวตาม §8.1: กลุ่มผู้รับเงินที่มีรายจ่ายค้าง (ค้นได้ แบ่งหน้า) และรายจ่ายค้างของกลุ่มที่เลือกหรือของคำค้น พร้อมยอดค้างและเหตุผลที่เลือกไม่ได้ ไม่คืนรายการที่ผู้ใช้อ่านไม่ได้ ใช้สิทธิ์จัดทำ ไม่ต้องมีสิทธิ์อ่านคู่ค้า |
| ใบเตรียมจ่าย/ใบสำคัญจ่าย | list (`page`/`pageSize`, กรองสถานะ) / get / create / update / delete ฉบับร่าง + submit / approve / return / cancel / pay / ส่งเตือนอีกครั้ง ทุกคำสั่งรับ `commandId` และ `expectedVersion`; ออกจากการจ่ายตรง; ออกใหม่แทนใบที่ถูกยกเลิก; อัปโหลดสลิป; เปิดเลขบัญชีเต็ม; ดูตัวอย่างและดาวน์โหลดไฟล์ ไม่มี endpoint ที่รับยอดเงินของการจ่ายตรงจาก client |
| 50 ทวิ | endpoint เดิม เพิ่มแบ่งหน้า ขอบเขต และตัวอ่านประวัติตาม §10.5, §10.6 |
| ผู้ดูแลระบบ | คำสั่งตั้งค่าหน้าจอหนึ่งเส้นทาง; รายละเอียดร้านคืนค่า version และรายชื่อตำแหน่งที่มีสิทธิ์ |

ข้อกำหนด:

1. **ส่งอนุมัติ** (transaction เดียว มี timeout ชัดเจน): ล็อกใบ → `lockFundingEvidence` ครั้งเดียวสำหรับรายจ่ายทุกรายการ → `assertFundingMutation('payment')` ต่อรายการ → ล็อกวงจรชีวิตของรายจ่ายทุกรายการตามลำดับ id → ตรวจ §8.1 → เขียนยอดจอง → เขียนรุ่นและ snapshot → ออกเลข (ครั้งแรก) เป็นลำดับสุดท้าย จองทั้งใบหรือไม่จองเลย
2. **บันทึกจ่าย** (transaction เดียว มี timeout ชัดเจน): ล็อกใบก่อน → ล็อก key คำสั่งของทุกรายการตามลำดับ → `lockFundingEvidence` ครั้งเดียว → `assertFundingMutation` ต่อรายการ → ล็อกวงจรชีวิตทุกรายการก่อนเขียนใด ๆ → สร้างการจ่ายทีละรายการด้วยตรรกะเดียวกับ `recordPaymentAtomic` (แยกส่วนในออกมาเป็นฟังก์ชันที่รับ transaction และยอมให้ผ่านยอดจองของใบตัวเอง) → ผูกการจ่ายกับรายการของใบ → ล้างยอดจอง → ใบเป็นจ่ายแล้วพร้อม snapshot ตอนจ่าย → audit และ outbox ห้ามเรียกการจ่ายทีละรายการแยก transaction
3. **ออกจากการจ่ายตรง** (transaction เดียว): ล็อกวงจรชีวิตของรายจ่าย → ตรวจว่าการจ่ายยังมีผลและยังไม่อยู่ในใบที่ไม่ถูกยกเลิก → สร้างใบสถานะจ่ายแล้วพร้อม snapshot → ออกเลขเป็นลำดับสุดท้าย กดซ้ำคืนใบเดิม
4. ทางยกเลิกการจ่ายและยกเลิกรายจ่ายที่ต้องทำให้ใบเป็นยกเลิก **ต้องไม่ขอล็อกของใบ** เพื่อไม่ให้ล็อกวนกับข้อ 2
5. แต่ละการจ่ายส่ง `expense.payment_recorded` เหมือนทางบันทึกด้วยมือ (วันนี้ไม่มีผู้ฟังเฉพาะ มีเพียงตัวระบาย outbox ทั่วไป)
6. `commandId` เดิมกับข้อมูลเดิมคืนผลเดิม ข้อมูลต่างคืน conflict การส่งซ้ำที่บางรายการเคยสำเร็จและบางรายการไม่เคย ถือเป็น conflict
7. สิทธิ์ สาขา และสถานะตรวจที่ server ทุกคำสั่ง ค่าตั้งหน้าจอไม่อยู่ในการตรวจ
8. การสร้างและเก็บไฟล์ PDF และการส่งแจ้งเตือนอยู่นอก transaction ล้มเหลวแล้วไม่ย้อนการจ่าย ผู้ใช้เห็นข้อความแยกว่า "บันทึกจ่ายแล้ว เอกสารกำลังจัดทำ"
9. error code ใหม่ทุกตัวมีข้อความไทย (มี test ตรวจความครบ)
10. เส้นทางอยู่ที่ controller ของเอกสารนี้เอง (`companies/:companyId/disbursement-vouchers`) ไม่วางใต้ `…/expenses/` (K01)
11. กติกาของการจ่ายที่วันนี้อยู่นอกฟังก์ชันจ่าย (ไม่ใช่รายการจากใบเบิก ต้องมีสาขา วันที่จ่ายไม่อยู่ในอนาคตตามเวลาไทย) ย้ายไปอยู่ที่เดียวกับฟังก์ชันจ่ายร่วม ทางจ่ายตรงและทางจ่ายตามใบจึงใช้ชุดเดียวกัน (K08)
12. เวลาของ transaction บันทึกจ่ายตั้งเอง ค่าเริ่มต้นที่เสนอ 20 วินาที และวัดบน PostgreSQL จริงด้วยใบ 20 รายการก่อนตรึงค่า ถ้าเกินครึ่งของเวลาที่ตั้ง ให้ลดจำนวนรายการสูงสุดต่อใบ หมดเวลาแล้วไม่มีการจ่ายเกิดและผู้ใช้ได้ข้อความให้ลองใหม่
13. การส่งคำสั่งบันทึกจ่ายซ้ำคืน **สถานะปัจจุบันของใบ** ถ้าหลังสำเร็จมีการจ่ายถูกยกเลิก ใบเป็น "ยกเลิก" และคำตอบบอกเช่นนั้น ไม่ตอบว่าสำเร็จ
14. คำสั่งใหม่ทุกคำสั่งปฏิเสธ session ที่เข้าระบบด้วย LINE ตามแบบของการจ่ายและการยกเลิกการจ่าย

## 13. ข้อมูลย้อนหลังและความเข้ากันได้

- เพิ่มอย่างเดียว ไม่เปลี่ยนความหมาย field เดิม ไม่เปลี่ยน route ของใบสำคัญรับเงิน (`…/expenses/:expenseId/payment-voucher.pdf`)
- การจ่ายตรงที่มีอยู่ก่อน release กดออกใบสำคัญจ่ายได้ ใบระบุวันที่จ่ายเดิมและวันที่ออกจริง ไม่มี backfill ออกใบให้อัตโนมัติ
- รายจ่ายเก่าที่มียอดจ่ายรวมแต่ไม่มีแถวการจ่าย และรายจ่ายที่จ่ายผ่านใบเบิก ออกใบไม่ได้ และระบบไม่สร้างการจ่ายขึ้นมาแทน
- รายการรอออกหนังสือรับรองเดิมทั้งหมดขึ้นในหน้ารายการโดยไม่ต้องย้ายข้อมูล
- response เดิมของการบันทึกจ่ายตรงไม่เปลี่ยนรูป
- ถอยรุ่น: ช่องใหม่ว่างได้ทั้งหมด API รุ่นเก่าไม่อ่าน เว็บรุ่นเก่าไม่รู้จักค่าใหม่ เมนูใหม่จึงหายไปเฉย ๆ สวิตช์บันทึกด้วยมือไม่ได้รับผล

### 16.2 ช่องว่างอื่นของระบบปัจจุบัน

พบระหว่างตรวจ ไม่อยู่ในงานนี้ และควรสั่งแยก:

- ไฟล์ 50 ทวิไม่ถูกเก็บตรึง การดาวน์โหลดซ้ำสร้างใหม่ด้วยค่าลายเซ็นปัจจุบัน
- ทางออกหนังสือรับรองแบบเก่า (`tax/wht-certificates`) กับทางปัจจุบันไม่กันกันเอง
- การ sync ภาษีและการสร้างไฟล์ยังถอยไปใช้ ภ.ง.ด.53 เมื่อไม่ทราบประเภทผู้รับ
- รายการภาษีอ่านหมวดจาก `taxCategory` ขณะที่รายการรอออกอ่านจาก `whtCategoryCode`
- ตำแหน่งที่สร้างจากการติ๊กชุดไม่มีสิทธิ์หน้า "AI แนะนำ" และมุมมองรายงานที่ตำแหน่งพนักงานมาตรฐานมี
- การผูกคู่ค้าของรายจ่ายค้างของเดิมเมื่อผู้ใช้แก้ชื่อร้าน หน้าคู่ค้าจึงอาจแสดงรายจ่ายใต้ร้านผิด (K02)
- หน้า "ยังไม่จ่าย" ของรายจ่ายโหลดได้สูงสุด 200 แถวแล้วกรองในเบราว์เซอร์ ร้านที่มีรายจ่ายยืนยันแล้วมากกว่านั้นเห็นไม่ครบ (K03)
- การจ่ายที่เกิดจากการอนุมัติใบรับรองแทนใบเสร็จไม่ผ่านฟังก์ชันจ่ายกลาง จึงไม่มี audit ของการจ่ายและไม่ส่ง event
- ทางปิดรายการเงาของใบเบิกที่ยังไม่ยืนยันทำให้แถวเป็นยกเลิกโดยไม่ล้างยอดค้าง

การตรวจรุ่น 2.1: เขียนจากผลตรวจอิสระและการอ่านโค้ดเพิ่มสี่ส่วนที่ `origin/main` `9b94ce059` (สวิตช์บันทึกด้วยมือ, โครงสิทธิ์และหน้าติ๊กตำแหน่ง, จุดเชื่อมการจ่ายของรายจ่าย, โครงหน้าเว็บ การแจ้งเตือน และรายการรอออกหนังสือรับรอง) ไม่ได้รัน test และไม่ได้เดินหน้าจอจริง เพราะฟีเจอร์ยังไม่มีโค้ด รุ่น 2.2 อ่านเพิ่ม: ทางแก้ไขหนังสือรับรอง ตัวกันของการเปิดกลับมาแก้และการยกเลิกรายจ่าย และ spec การแก้ไขหนังสือรับรอง รุ่น 2.3 อ่านเพิ่ม: ทางออกใบจากรายการรอออก ทางเปิดรายจ่ายกลับมาแก้ และโครงตารางของหนังสือรับรอง รุ่น 2.4 ดูหน้าจอจริงของ FlowAccount และตรวจความเข้ากับโค้ดจริงอีกรอบ (D18) รุ่น 2.5 ปรับตามผลตรวจนั้น: ผู้ช่วยอ่านโค้ดสามด้าน (หน้าจอ, ข้อมูลและโมดูลข้างเคียง, บั๊กในโค้ดเดิม) และผู้เขียนเปิดโค้ดยืนยันข้อที่มีผลต่อแบบเอง เกณฑ์ยอมรับ 83 ข้อใน §15 เป็นข้อกำหนด ไม่ใช่ผลทดสอบ
