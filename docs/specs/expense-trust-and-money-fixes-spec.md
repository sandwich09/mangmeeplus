**Failures today:** (a) `%PDF-... /J#61vaScript` with an escaped `/OpenAction`/`/JS` spelling is not matched by the literal-name regex; `(>> stream)` in a dictionary can cause the payload-stripping regex to hide later structural actions. Scanner rules, reproduced here so implementation does not need the feature spec:

1. Preserve MIME magic, EICAR and existing active-content detection. Remove regex stream stripping. Tokenize PDF names, numbers/references, comments, literal strings with balanced parentheses/backslash/octal escapes, hex strings, arrays and dictionaries. Include NUL in whitespace. Strings and comments do not delimit streams. A `stream` payload is skipped only using a structurally parsed dictionary and direct/resolved indirect `/Length`. If length/endstream disagree or cannot be resolved, both the declared-length interpretation and EOL-delimited endstream interpretation must inspect safely; any ambiguous/unparseable branch rejects. Never regex-delete bytes to obtain a trustworthy structure.
2. Decode name `#xx` in either hex case. As the source design specifies, an escape yielding an ASCII letter/digit rejects as `PDF could not be inspected.`; necessary escapes such as `/text#2Fxml` and `/Arial#20Bold` are decoded and checked. Compare forbidden names case-insensitively: JavaScript, JS, OpenAction, Launch, RichMedia, XFA and (unless the narrow receipt exception passes) EmbeddedFile. Escaped ObjStm names cannot hide compressed objects.
3. Expand ObjStm with built-in `node:zlib.inflateSync` and `maxOutputLength`. Allow only the supported single Flate filter, not unsupported/multiple filters. Limits: 8 MiB per object stream, 32 MiB expanded total, 2,000 object streams, 100,000 objects, combined array/dictionary depth 64, 2 seconds elapsed per file. Re-tokenize expanded objects with the same budget; nested `stream` inside ObjStm rejects. Parse/inflate failure, encryption/uninspectable structure or a limit breach rejects; it never means clean. No pdf-lib/pdfjs load in this security scanner.
4. Check structural text and decoded PDF string values for `<script`, `<svg`, `javascript:`, `vbscript:`, `data:text/html`, with ASCII whitespace/control removal for scheme checks. Keep normal compressed image/font/content streams opaque. Do not regress ordinary scanned receipts by matching random compressed bytes. EICAR still checks the complete original bytes.
5. Receipt policy alone may accept **1–2 distinct XML embedded streams**, each expanded to at most 3 MiB and sharing the total budget. Resolve Filespecs referenced from Names/EmbeddedFiles, Catalog/AF and FileAttachment annotations. Deduplicate Filespecs by object number/generation (direct dictionaries by position), streams by their `/EF /F` or `/UF` object identity; Names and AF may reference the same Filespec. Every EmbeddedFile stream must be referenced by an inspected Filespec; orphan, hidden, unresolved, conflicting F/UF, extra or unsupported-filter content rejects. Require XML MIME (`text/xml` or `application/xml`) or `.xml`, **and** actual XML root namespace validation, never extension alone. No DTD, ENTITY or external entity resolution. Allowed namespace is exactly `urn:etda:uncefact:data:standard:<Name>_CrossIndustryInvoice:2`, where Name is TaxInvoice, Receipt, DebitCreditNote, AbbreviatedTaxInvoice, Invoice or CancellationNote (source spec §5.2 R3). No C2PA, ZIP, executable, generic attachment or arbitrary XML exception in this round.
6. No new XML dependency: this step only recognizes bounded XML structure/root identity; it does not extract tax fields, validate XSDs or verify signatures. Implement the small bounded recognizer alongside the scanner: strict text decoding, balanced tags, quoted attributes, namespace binding of the root, comments/CDATA/processing instructions handled as data, no duplicate attributes or trailing second root; reject encodings/constructs it cannot inspect. Test declarations/comments/CDATA containing fake roots, namespace rebinding, DTD/ENTITY, malformed/truncated markup and binary payloads. Do not use a permissive regex root match or import the lockfile's transitive `sax`. Full e-Tax parsing remains later work; unlike source plan P2.1's dependency addition, this round adds none.
7. A matching XML attachment is only a **file-safety exception**. It does not prove PDF/A compliance, signature authenticity, issuer eligibility or tax eligibility. Preserve uploaded bytes and their checksum; never reprint/flatten them automatically.
