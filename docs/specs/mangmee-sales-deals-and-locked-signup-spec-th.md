## 2. Goal

1. ตั้งแต่นี้ **ไม่มีทดลองใช้ฟรี**: ร้านที่สมัครใหม่คุยกับ AI ไม่ได้ และบนเว็บเห็นแค่ "ตั้งค่า (ข้อมูลร้านและบัญชีของฉัน)" กับ "แพ็กเกจ" จนกว่าจะชำระเงิน; ร้านที่กำลังทดลองอยู่ใช้จนครบวันเดิม (มติ Owner)
2. ทีมขายของมั่งมีมี **Sales console** เป็น role แยก: หัวหน้าเซลล์สร้างบัญชีเซลล์ในทีม ดูยอดขาย/ยอดเปิดบริษัทของทุกทีม อนุมัติดีล; เซลล์สร้างดีลพิเศษให้ร้านที่มีบัญชีอยู่แล้วด้วย **ราคาใดก็ได้ จำนวนเดือน โควตา สาขา ผู้ใช้ เมนู งบ AI** แล้วส่งหัวหน้าอนุมัติ
3. เมื่ออนุมัติ ระบบสร้างการ์ด **"ข้อเสนอพิเศษสำหรับร้านคุณ"** บนหน้าแพ็กเกจของร้านนั้นร้านเดียว ลูกค้ากรอกข้อมูลและชำระเองผ่าน Stripe ด้วยบัตรหรือ PromptPay แล้วระบบเปิดสิทธิ์อัตโนมัติ **ภายใน 3 วัน** ไม่มีการเปิดสิทธิ์ก่อนจ่าย
4. Admin console (Owner) สร้างบัญชีเซลล์พร้อมข้อมูลสำหรับทำใบค่าจ้าง/50 ทวิ (คอมมิชชันคำนวณนอกระบบ)

## 4. Non-goals

- ไม่มีสวิตช์เปิด/ปิด trial (ค่าคงที่ = ไม่มี); ไม่ตัดร้านที่กำลังทดลอง
- ไม่มี coupon บน subscription; Price เฉพาะร้าน/ต่ออายุอัตโนมัติสำหรับดีล = Phase 5 (D7, §17.3); ไม่มี proration ในระบบ (Q7 ค่าเริ่มต้น, §19.5)
- ไม่คำนวณคอมมิชชัน/ไม่ออกใบค่าจ้าง/50 ทวิ จากระบบ (เก็บข้อมูลให้ทำนอกระบบ)
- ไม่มีการเปิดสิทธิ์ล่วงหน้าก่อนชำระ (ทุกช่องทาง); ไม่มี LIFF/หน้าแอปแยกสำหรับเซลล์ (ใช้เว็บเดิม)
- ไม่รองรับการโอนเงินหรือแนบสลิป รวมถึง EasySlip (มติ Owner 2026-09-21: ลูกค้าชำระผ่าน Stripe บัตร/PromptPay เท่านั้น — กันทุจริต)

## 6. Business Journey

**J1 สมัครใหม่ → ล็อก**: LINE/เว็บ signup → provisioning เขียน term 0 วัน + `DISABLED`/`termDisabledAt` (reason `no_package`) ทันที (ไม่รอ sweep) + push "เปิดร้านแล้ว ขั้นต่อไปเลือกแพ็กเกจ" → LINE: ทุกข้อความ/รูปตอบการ์ด "สมัครแพ็กเกจก่อนเริ่มใช้งาน" + ปุ่มเปิดหน้าแพ็กเกจ (ไม่มี OCR/model) ; "ติดต่อเจ้าหน้าที่"/"ติดต่อเรา" ยังทำงาน → เว็บ: locked shell 2 เมนู

**J2 ลูกค้าเลือกแพ็กเกจเอง**: หน้าแพ็กเกจ → การ์ด catalog → quote → Checkout (บัตร/PromptPay; อีเมลและที่อยู่กรอกที่หน้าชำระเงินของ Stripe ไม่ต้องกรอกในแอปก่อน — D-PF-1, purchase-without-setup PR D) → เปิดสิทธิ์อัตโนมัติ (flow P26 เดิม)

**J3 เซลล์ทำดีล**: เซลล์ค้นร้าน → ฟอร์มดีล (tier ฐานเติมค่าเริ่มต้น; แก้ราคา/เดือน/ลิมิต/เมนู/งบ AI ได้หมด; โน้ตถึงลูกค้า) → ส่งอนุมัติ → หัวหน้า/Owner อนุมัติ (หรือปฏิเสธพร้อมเหตุผลถึงเซลล์) → ระบบสร้างการ์ดข้อเสนอบนหน้าแพ็กเกจของร้านนั้น + push LINE ถึง OWNER (ไม่มีตัวเลข) → ลูกค้าเลือก → ชำระด้วยบัตรหรือ PromptPay (อีเมล/ที่อยู่กรอกที่หน้าชำระเงิน — D-PF-1) → เปิดสิทธิ์ตามดีล → ดีล APPLIED; เซลล์และหัวหน้าเห็นสถานะ

**J4 หมดเวลา/ต่ออายุ**: ข้อเสนอไม่ถูกจ่ายใน 3 วัน → EXPIRED การ์ดหาย ร้านยังล็อก เซลล์ออกใหม่ได้; ร้านที่จ่ายดีลแล้ว 14 วันก่อนหมด ระบบสร้างข้อเสนอรอบถัดไปเงื่อนไขเดิม (D3) → จ่ายใหม่แตะเดียว; ไม่จ่าย → P29 ล็อก

**J5 Owner สร้างเซลล์**: admin console → "ทีมขาย" → สร้างผู้ใช้ (username, ชื่อ, เบอร์, อีเมล, role, ข้อมูลภาษี) → รหัสผ่านชั่วคราว (แสดงครั้งเดียว/ส่ง LINE ถ้าผูก) → เซลล์ login ครั้งแรกต้องเปลี่ยนรหัส

## 7. Business Rules

- R1 **ไม่มี trial**: `TRIAL_DAYS = 0` ทุกช่องทางสมัคร; copy "ทดลองฟรี 30 วัน" ทั้ง 6 จุด (LIFF สมัคร, เว็บสมัคร 3 หน้า, การ์ดโปรโมชั่น, catalog `trial`) เปลี่ยนเป็น "เลือกแพ็กเกจเพื่อเริ่มใช้งาน"; `BillingCatalog.trial` = null; ร้านที่มี term ทดลองอยู่ไม่ถูกแตะ
- R2 **สถานะร้าน** ใช้ term เดิม: ยังไม่มีแพ็กเกจ (term 0 วัน + `termDisabledAt`) → ใช้งาน (term เต็ม) → หมดอายุ (P29); `lockReason` derive จาก term (`termEndsAt <= termStartAt && renewCount = 0` ⇒ `no_package`); label กลาง: ยังไม่มีแพ็กเกจ / กำลังทดลองใช้ / ใช้งานได้ / หมดอายุ / พักการใช้งาน (`planTermStateLabel`, purchase-without-setup R-C7) — sales console badge ACTIVE เปลี่ยนจาก "ใช้งานอยู่" เป็น "ใช้งานได้"
- R3 **ดีล** = แถว `PackageChangeRequest` kind `SALES_DEAL`; หนึ่งร้านมีดีลที่ยังไม่จบได้หนึ่งใบ (partial unique OPEN เดิม); เนื้อหาถูก snapshot ใน `offerSnapshotJson` v2: `{ base: tierKey, priceSatang, months, branchLimit, employeeLimit, monthlySlipLimit, features[], aiMonthlyBudgetSatang|null, description, salesUserId, approvedBy, offerExpiresAt }`; ราคา ≥ 1 satang ไม่มีเพดาน/พื้น (เตือนเมื่อสูงกว่า catalog หรือต่ำกว่าพื้นที่ Owner ตั้ง — ไม่ห้าม); เดือน 1–36 · *(Phase 3, D-P3-1: `base` = `STARTER_249` / `BASIC_499` / `PRO_999` เท่านั้น — ตัด `ENTERPRISE_1999` ออกจาก `SALES_DEAL_BASE_TIERS` เพราะไม่มี Stripe Price ให้ `paidVariant` อ่าน product; ขนาดร้านใหญ่กำหนดผ่านลิมิตของดีลเอง)* · *(D-P3-2: `aiMonthlyBudgetSatang` = ว่าง (inherit) หรือ ≥ 1 สตางค์; 0 ถูกปฏิเสธ — ปิด AI = เอาเมนู `ai_line_assistant` ออก)*
- R4 **สถานะดีล**: DRAFT → PENDING_APPROVAL → APPROVED (การ์ดโชว์; `offerExpiresAt = approvedAt + 3 วัน`) → PAID (Stripe ยืนยัน) → APPLIED (เปิดสิทธิ์แล้ว) | EXPIRED (เลย 3 วัน; derive + scan รายวันปิดแถว) | REJECTED (หัวหน้า) | CANCELLED (เซลล์/หัวหน้า ก่อนจ่าย); แก้ไขได้เฉพาะ DRAFT/REJECTED; APPROVED แก้ไม่ได้ (ยกเลิกแล้วออกใหม่)
- R5 **อนุมัติ**: `MANGMEE_SALES_LEAD` หรือ SYSTEM_ADMIN; ผู้สร้างอนุมัติดีลของตัวเองไม่ได้ ยกเว้น SYSTEM_ADMIN (single-admin); ทุกการเปลี่ยนสถานะมีเหตุผล + audit CRITICAL (`sales.deal.*`) · *(Phase 2, 2026-09-21: D2 ให้ lead อนุมัติดีลของตัวเองได้ (audit `selfApproved`); เหตุผลบังคับเฉพาะ ปฏิเสธ/ยกเลิก — อนุมัติไม่บังคับ เพื่อความเร็ว; audit เก็บผู้อนุมัติเสมอ)*
- R6 **ชำระดีลด้วย Stripe แบบครั้งเดียว** *(แก้ไขโดย §19.2 — ใช้เส้นทางครั้งเดียวของ PR #667)*: quote จาก snapshot ดีล (ยอด = `priceSatang`, VAT ตามนโยบาย `quoteTotals`), Checkout `mode: 'payment'` `price_data { product: product ของ tier ฐาน (อ่านจาก Price catalog), unit_amount: priceSatang }`, `payment_method_types: ['card','promptpay']`; หลักฐานผ่าน `paidPackageCheckoutEvidence` (ขยายให้รับ `promptpay`), async events ที่มีอยู่; apply = term `termEndsAt = appendPackageInterval × months` จาก now, ลิมิต/เมนู/งบ AI ตาม snapshot, ใบเสร็จ = ~~โควตาต่อเดือน (LEGACY_MONTH)~~ *(แทนโดย D-P3-4: PAID_GRANTS เหมือนแพ็กเกจจ่ายเงินทุกแบบ — `receiptAllowance = monthlySlipLimit × months` ผ่าน `grantPaidPackageReceipts` หมดอายุพร้อมดีล)*, `billingReceiptAccountId` ~~**ไม่ตั้ง**~~ *(แทนโดย D-P3-4: `grantPaidPackageReceipts` ตั้งให้เสมอ ซึ่งเป็นสิ่งที่ `billingPurchaseSource` ใช้จำแนกสัญญาที่จ่ายแล้ว)* → source แสดงเป็น `DEAL` (D-P3-6: อ่านจาก `quoteSnapshot.deal` ของ attempt ที่เป็นสัญญาปัจจุบัน) ; re-enable บริษัทถ้า `termDisabledAt`
- R7 **ช่องทางชำระเงิน**: ลูกค้าชำระผ่าน Stripe ด้วยบัตรหรือ PromptPay เท่านั้น; ไม่มีการโอนเงินหรือแนบสลิป
- R8 **ไม่มีสิทธิ์ก่อนจ่าย** ทุกช่องทาง; การ์ดข้อเสนอเป็นแค่ข้อมูล; ร้านยังล็อกจน APPLIED
- R9 **ดีลบน subscription เดิม** *(แก้ไขโดย §19.3)*: ร้านที่มี `CARD_AUTO` ปกติรับดีลได้; Checkout ของดีลยังเป็น one-time ของตัวเอง แต่ snapshot ผูก `baseSubscriptionId`/วันสิ้นสุดเดิมไว้เพื่อกันข้อมูลเปลี่ยนระหว่างจ่าย แล้วเมื่อ APPLIED จึงยกเลิก subscription เดิมแบบ `prorate: false` พร้อม journal/observed/retry. `PROMPTPAY_RENEW`, ค้างชำระ, grace, refund/dispute หรือ subscription ที่ถูกสั่งยกเลิกแล้ว → `CONTROL_DEAL_SUBSCRIPTION_REVIEW`
- R10 **หน้าแพ็กเกจ**: การ์ดข้อเสนอเป็นการ์ดแรกก่อน catalog; catalog ยังเลือกได้; "แพ็กเกจปัจจุบัน" ของร้านล็อกแสดง "ยังไม่มีแพ็กเกจ · เลือกแพ็กเกจเพื่อเริ่มใช้งาน" ไม่ใช่ "ไม่จำกัด"; public catalog/BFF/marketing ไม่เปลี่ยน
- R11 **การมองเห็นเซลล์**: เห็นร้านผ่าน endpoint ใหม่ที่คืนแค่ ชื่อ/สถานะ/แพ็กเกจ/จังหวัด/วันที่สมัคร; ไม่ได้ `system.partner_dashboard.read` หรือ billing permission ใด; ดีลของคนอื่นเห็นเฉพาะหัวหน้า/Owner; หัวหน้าเซลล์กรอกข้อมูลภาษี/ที่อยู่/ธนาคารตอนสร้างและเปิดดูข้อมูลเซลล์ในทีมของตนได้ แต่แก้หรือส่งออกไม่ได้; เซลล์และหัวหน้าเปิดดูและแก้ข้อมูลภาษี/ที่อยู่/ธนาคารของตนเองได้ โดยแก้อัตราหัก ณ ที่จ่ายไม่ได้; SYSTEM_ADMIN เปิดดู แก้ และส่งออกได้ทุกบัญชี; ทุกการเปิดดูต้อง audit, การแก้ต้อง audit โดยไม่บันทึก PII; team list ไม่คืน PII
- R12 **ข้อมูลเซลล์สำหรับใบค่าจ้าง/50 ทวิ** (ตาราง `SalesAgentProfile`): ชื่อ-นามสกุลตามบัตร, เลขบัตรประชาชน/เลขผู้เสียภาษี (เข้ารหัสแบบ credential เดิม), ที่อยู่, ธนาคาร/เลขบัญชี, อัตราหัก ณ ที่จ่าย, สถานะ (ACTIVE/SUSPENDED), ทีม/หัวหน้า; ส่งออก CSV ให้บัญชี (SYSTEM_ADMIN)
- ฟอร์มสร้างบัญชีของ SYSTEM_ADMIN และหัวหน้าเซลล์: แสดง "ที่อยู่ (ตามบัตรประชาชนหรือบริษัท)" และใช้รหัสไปรษณีย์ → จังหวัด/อำเภอ/ตำบลแบบเดียวกับหน้าข้อมูลร้าน; เก็บกลับเป็น `SalesAgentProfile.address` ข้อความเดิมเมื่อกรอกครบ; เลขบัตรประชาชนและเลขผู้เสียภาษีรับตัวเลขได้ไม่เกิน 13 หลัก; ชื่อธนาคารเลือกจากรายการพร้อมช่องระบุธนาคารอื่น เพื่อไม่บังคับชื่อผิดเมื่อรายการไม่ครอบคลุม; สร้างสำเร็จคืน temp password ให้ผู้สร้างเห็นครั้งเดียวและบังคับเปลี่ยนเมื่อเข้าใช้ครั้งแรก
- R13 **รายงานหัวหน้า**: ต่อเซลล์/ต่อทีม/ทั้งบริษัท: ดีลตามสถานะ, ยอดชำระที่ APPLIED (รายเดือน จาก BillingInvoice Stripe), จำนวนร้านที่เปิดใช้ (APPLIED ครั้งแรก), conversion (APPROVED→APPLIED), ค้างชำระ; ตัวเลขมาจาก server เท่านั้น
- R14 **LINE**: การ์ดล็อก + reply พนักงาน + ปิดช่องโหว่ 5 นาที ตาม free-usage plan §4.4; push ข้อเสนอถึง OWNER เป็น Flex card พร้อมปุ่มเปิดหน้าแพ็กเกจของร้านนั้นด้วย `openExternalBrowser=1` เพื่อให้เข้าเว็บและล็อกอินในเบราว์เซอร์เดียวกัน ไม่แสดง URL ดิบในข้อความ/พรีวิว; ไม่มีตัวเลขหรือราคาบน LINE; ถ้าสร้างลิงก์ที่ปลอดภัยไม่ได้ให้ส่งข้อความแจ้งอย่างเดียว

## 8. Boundary and Ownership

- **billing**: quote/checkout/evidence/apply ของดีลบนเส้นทางครั้งเดียวของ PR #667 (snapshot `deal`, ไม่มี `DealSource`), label `DEAL` (§19.2)
- **external-signup**: แถว `PackageChangeRequest` + endpoint ลูกค้าสำหรับดูข้อเสนอ — เดิม
- **system-partner-management**: ไม่เปลี่ยน (manual term/ต่ออายุ ยังเป็นเครื่องมือ Owner)
- **module ใหม่ `sales-console`** (apps/api): roles, `SalesAgentProfile`, deals CRUD/approve, company search, reports; ใช้ `create-employee`/`regenerate-employee-credential` ของ employee-access กับ platform tenant
- **auth**: permission ใหม่ + role ใหม่ใน registry; web gate `canOpenSales`
- **web**: พื้นที่ใหม่ `/sales/*` (layout + nav ของตัวเอง), admin console เพิ่ม "ทีมขาย", BillingPage เพิ่มการ์ดข้อเสนอ, locked shell
- **line-ai**: การ์ดล็อก/reply/window (ของเดิมในแผนสวิตช์)
- AI Gateway ไม่เกี่ยว; workers: scan รายวันปิดดีล EXPIRED และออกข้อเสนอต่ออายุ (reuse scan-worker pattern)

### 17.1 D6 ตัดสินแล้ว (Owner 2026-09-20): นับยอดจาก "รู้จักเราทางไหน" ด้วย ทำในรอบแรกพร้อมตัวกันโกง

มติ: ยอดจากดีล = ของเซลล์ผู้สร้างดีล; ยอด subscription ที่ลูกค้าซื้อเอง = นับให้เซลล์ที่ลูกค้าระบุในช่อง "รู้จักเราทางไหน" ตอนสมัคร **ภายใน 14 วันนับจากวันเปิดร้าน (Owner แก้จาก 1 เดือน)**; เซลล์ไม่ทับพื้นที่กัน (ไม่มีกติกา first/last touch); ต้องมีตัวกันโกงตั้งแต่แรก

**กติกา**
- ฟอร์มสมัคร (LIFF + เว็บ) เพิ่ม option `SALES` "เซลล์ของมั่งมี" ใน `SIGNUP_DISCOVERY_SOURCE_OPTIONS` ([external-signup.ts:5-11](../../packages/contracts/src/external-signup.ts)) พร้อมช่อง **รหัสเซลล์แบบง่าย** (ตั้งเองได้ 3–6 ตัว ตัวพิมพ์ใหญ่/ตัวเลข ไม่ซ้ำ เช่น ชื่อเล่น "TON"; ค่าเริ่มต้นระบบสุ่ม 4 ตัวโดยไม่ใช้ตัวที่สับสน 0/O 1/I; ออกให้ทุกบัญชีเซลล์ตอนสร้าง; ลิงก์ `?ref=<รหัส>` เติมให้อัตโนมัติ); server แปลงรหัสเป็น `referralSalesUserId` ตอน submit; รหัสผิด/ไม่ ACTIVE → เก็บข้อความดิบไว้ให้แอดมินดู ไม่นับ
- ตอน provisioning คัดลอกไป `Company.referralSalesUserId` + `referredAt` (= เวลา provision) + `referralSource` ('SIGNUP_CODE'|'SIGNUP_LINK'|'ADMIN'); แก้ได้เฉพาะ SYSTEM_ADMIN พร้อมเหตุผล (audit) ภายใน 14 วันแรก

- "ยอดเปิดบริษัท" = ร้านที่ APPLIED ครั้งแรกภายในหน้าต่างของเซลล์ (ดีลหรือแนะนำ) นับร้านละ 1

**ช่องทาง "สรุปให้ Owner ทุกเช้า" (รอ Owner เลือก):** ระบบมีอยู่แล้ว 3 ช่อง — (ก) การแจ้งเตือนในคอนโซล + badge บนเมนู "ทีมขาย" (แน่นอนที่สุด ใช้กลไก dashboard-notifications ของ SYSTEM_ADMIN แบบเดียวกับคำขอสมัคร) (ข) LINE push ถึงบัญชีของ Owner ที่ผูก LINE กับบัญชี SYSTEM_ADMIN (ต้องผูกก่อน; วันนี้ยังไม่มี SYSTEM_ADMIN ที่ผูก LINE) (ค) อีเมลผ่าน Postmark ถึงกล่องที่กำหนด (ใช้ transport เดิมของอีเมล billing/สมัคร) — ข้อเสนอ: (ก) + (ข) ทุกวัน 07:00 ตามเวลาไทยด้วย cron เดิมของสรุปรายวัน (`daily_owner_summary` 07:00 Asia/Bangkok) โดยเพิ่ม trigger `sales_daily_digest`; (ค) เป็นทางเลือก

#### 17.1.1 ฐานของยอดและการหักยอด — สิ่งที่โค้ดทำ (มติ Owner 2026-10-02, RB-37 / Q36)

มติสี่ข้อ: (1) คืนเงินหักจากยอดเดือนที่คืน ไม่ใช่เดือนที่รับเงิน (2) แพ้ข้อโต้แย้งการชำระหักเหมือนคืนเงิน (3) 60 วันนับถึงเวลาจริงของการคืนเงินหรือข้อโต้แย้งที่ผู้ให้บริการรับชำระ ไม่ใช่เวลาที่ระบบตรวจเจอ (4) ยอดจากดีลและยอดจากการแนะนำใช้ฐานเดียวกัน
ที่ตัดสินไว้แล้วและไม่เปลี่ยน: ผู้แนะนำที่ผู้ดูแลใส่ให้ภายหลังไม่ได้ยอด, รอบต่ออายุไม่นับ, แถวติดธงที่ยังไม่ตรวจนับศูนย์

**ฐานของยอด (`SalesAttribution.amountSatang`)**
- ทั้งสองแบบคือราคาแพ็กเกจที่เรียกเก็บจากร้าน ไม่รวมภาษีที่บวกเพิ่ม
- ดีล: ราคาดีล (`snapshot.quote.offer.priceSatang`) เหมือนเดิม
- การแนะนำ: `recordReferralAttribution` อ่านจากใบแจ้งหนี้ที่ตรวจหลักฐานแล้ว — ตั้งภาษีแบบบวกเพิ่ม (`EXCLUSIVE_VAT_7`) ใช้ `totalSatang − taxSatang`; แบบรวมในหรือไม่จดภาษีมูลค่าเพิ่ม ใช้ `totalSatang` ซึ่งเป็นตัวเลขเดิม
- ร้านที่ใช้ส่วนลดจากงานอีเวนต์: ยอดคือราคาหลังส่วนลดที่เรียกเก็บจริง ก่อนภาษีที่บวกเพิ่ม ไม่ใช่ราคาเต็มของแพ็กเกจ (คงตามสเปกส่วนลดจากงาน §5.5 ที่ให้บันทึกยอดจริง)
  ข้อนี้ controller ตัดสินเมื่อ 2026-10-02 และใช้ไปจนกว่า Owner จะคัดค้าน ไม่ใช่ผลข้างเคียงของโค้ด: ถ้านับราคาเต็ม ยอดจะสูงกว่าเงินที่ร้านจ่าย และยังเหลืออยู่แม้คืนเงินเต็มจำนวน

**อะไรหักยอด และหักเท่าไร**
- หนึ่งแถว `SalesAttributionDeduction` ต่อการคืนเงินที่สำเร็จหนึ่งครั้ง หรือข้อโต้แย้งการชำระที่แพ้หนึ่งรายการ ของการชำระครั้งที่สร้างยอด (`sourceInvoiceId`) การคืนเงินที่ยังไม่สำเร็จหรือล้มเหลว และข้อโต้แย้งที่ชนะหรือยังไม่จบ ไม่หัก
- จำนวนที่หักคือจำนวนที่คืนหรือที่แพ้ แต่ไม่เกินยอดที่ยังเหลือของร้านนั้น รวมทุกรายการจึงไม่เกินยอดของร้าน (คืนเต็มจำนวนหักเท่ายอดพอดี แม้เงินที่คืนจะรวมภาษีที่บวกเพิ่ม)
- 60 วันนับจาก `paidAt` ถึงเวลาของผู้ให้บริการ คือเวลาที่คืนเงิน หรือเวลาที่ลูกค้าเปิดข้อโต้แย้ง (วันที่ 60 พอดียังนับ) คืนวันที่ 59 แต่ระบบเจอวันที่ 61 หัก; คืนวันที่ 61 ไม่หัก
- รหัสรายการของผู้ให้บริการหนึ่งรหัสหักหนึ่งครั้ง (unique ในฐานข้อมูล) ไม่ว่าระบบจะเห็นกี่ครั้ง

**หักเดือนไหน**
- ยอดอยู่ในเดือนที่รับเงิน (เวลาไทย) และไม่ถูกแก้อีก
- รายการหักเป็นบรรทัดของตัวเองในเดือน (เวลาไทย) ที่ระบบบันทึกรายการ ปกติระบบบันทึกภายในไม่กี่นาทีหลังเกิดจริง (แจ้งเตือนจากผู้ให้บริการ หรือรอบตรวจทุก 5 นาที) จึงเป็นเดือนเดียวกับที่คืนเงิน ยอดของเซลล์ในเดือนนั้นติดลบได้
- เดือนที่จบแล้วไม่เปลี่ยน: ถ้าระบบทราบหลังสิ้นเดือน (ระบบหรือผู้ให้บริการขัดข้อง หรือการคืนเงินค้างสถานะ) รายการหักลงเดือนที่ทราบ และบรรทัดยังแสดงวันที่คืนเงินจริง
- ข้อโต้แย้งลงเดือนที่ระบบบันทึกว่าแพ้ เพราะข้อมูลข้อโต้แย้งของผู้ให้บริการมีเวลาเปิดแต่ไม่มีเวลาปิด เวลาเปิดใช้นับ 60 วันและแสดงในบรรทัด
- การลงเดือนตามเวลาที่ระบบบันทึก แทนวันที่ของผู้ให้บริการ controller ตัดสินเมื่อ 2026-10-02 และใช้ไปจนกว่า Owner จะคัดค้าน ไม่ใช่ผลข้างเคียงของโค้ด: เป็นทางเดียวที่ทำให้เดือนที่จบแล้วไม่ขยับในทุกกรณี

**แถวติดธง** — แถวที่ยังมีธงนับศูนย์ กติกาเดียวอยู่ที่ `salesCreditState` และ `salesCountsAsActivation` (`packages/contracts/src/sales.ts`) ใช้ทั้งรายงาน สรุปรายวัน และคิวของเจ้าของ
- **มติ Owner 2026-10-02: ร้านที่ติดธงและยังรอตรวจ ไม่นับเป็นร้านที่เปิดจนกว่าจะตรวจ**
  รอตรวจ (มีธง ยังไม่มีเวลาตรวจ): ไม่มียอดและไม่นับเป็นร้านที่เปิด ในทุกตัวเลข คือรายงานรายเดือน มุมมองรายเซลล์ ยอดรวม และสรุปรายวัน
  รายงานแยกแสดงเป็น “รอตรวจ N ร้าน” ในเดือนที่ร้านชำระเงิน พร้อมชื่อร้านและเหตุผลที่ติดธง ผู้อ่านรายงานจึงเห็นว่าร้านใดยังไม่นับและเพราะอะไร (ก่อนมตินี้ร้านรอตรวจนับเป็นร้านที่เปิดโดยยอดเป็นศูนย์; เซลล์ที่ไม่ใช่หัวหน้ายังเปิดรายงานไม่ได้ ดูหัวข้อ “หน้าจอ” ข้างล่าง)
- เจ้าของเลือก “ตัดออกจากยอด” (ธงยังอยู่และมีเวลาตรวจ): ไม่อยู่ในตัวเลขใดเลยอย่างถาวร ทั้งยอด จำนวนร้านที่เปิด (§17.2 “จำนวนร้านที่นับได้”) และจำนวนรอตรวจ
- รายการหักของแถวทั้งสองแบบนับศูนย์ การคืนเงินของร้านที่ไม่เคยได้ยอดจึงไม่ทำให้เดือนใดติดลบ
- เจ้าของเลือก “ยืนยันว่าไม่ผิดปกติ” (ธงถูกล้าง): นับตั้งแต่นั้นเหมือนร้านที่ไม่เคยติดธง ร้านและยอดอยู่ในเดือนที่รับเงิน และรายการหักอยู่ในเดือนที่บันทึก
  **มติ Owner 2026-10-02 (“นับเดือนที่ลูกค้าจ่ายเงินสิ”): ร้านที่ยืนยันหลังเดือนที่รับเงินจบไปแล้ว นับในเดือนที่ลูกค้าจ่ายเงิน ไม่ใช่เดือนที่ยืนยัน** ตัวเลขของเดือนนั้นจึงเพิ่มขึ้นทั้งจำนวนร้านและยอด ข้อนี้ต่างจากรายการหัก ซึ่งลงเดือนที่ระบบบันทึกและไม่ย้อนแก้เดือนที่จบแล้ว
  ระบบไม่มีค่าคอมมิชชัน เป้า ขั้น หรืออันดับที่คำนวณจากจำนวนร้าน จึงไม่มีตัวเลขอื่นขยับตาม ทางเลือกให้ร้านลงเดือนที่ยืนยัน (เพื่อให้เดือนที่จบแล้วไม่เปลี่ยน) ถูกเสนอและ Owner ไม่เลือก ใครที่อ่านยอดของเดือนที่ผ่านไปแล้วจึงต้องรู้ว่ายอดนั้นเพิ่มได้เมื่อมีร้านรอตรวจของเดือนนั้นถูกยืนยัน รายงานบอกไว้ใต้ตารางว่าร้านรอตรวจจะนับในเดือนที่ร้านชำระเงิน
- ร้านที่ตัดออกแล้วยังยืนยันภายหลังได้ ซึ่งเป็นทางแก้เมื่อตัดผิด ร้านที่ยืนยันแล้วตัดออกไม่ได้ เพราะไม่มีธงเหลือ ระบบปฏิเสธคำสั่งนั้น (`SALES_FLAG_REVIEW_INVALID`) แทนการบันทึกว่าตัดแล้วทั้งที่ยอดยังนับ
- ก่อน 2026-10-02 แถวที่เจ้าของตัดออกถูกนับยอดเต็ม เพราะรายงานถือว่าแถวที่มีเวลาตรวจนับได้ทุกแถว แก้พร้อมงานนี้

**แถวที่มีอยู่ก่อนการเปลี่ยนนี้ (ไม่ back-fill และไม่แก้ตัวเลขเดิม)**
- `refundedSatang` ของแถวเดิมคือยอดคืนสะสมที่ไม่มีวันที่ รายงานยังหักในเดือนที่รับเงินเหมือนเดิม (`max(0, amountSatang − refundedSatang)`) ตัวเลขของเดือนที่อ่านไปแล้วจึงไม่ขยับ โค้ดไม่เขียนคอลัมน์นี้อีก แถวใหม่จึงเป็น 0 เสมอ
- การคืนเงินหรือการแพ้ข้อโต้แย้งครั้งใหม่ของแถวเดิมเป็นรายการหักที่มีวันที่ตามกติกาข้างบน ในรายงานเดียวกัน แถวหนึ่งจึงมีได้ทั้งสองส่วน: ยอดคืนเดิมหักในเดือนรับเงิน และรายการหักใหม่ในเดือนที่บันทึก รวมกันไม่เกินยอดของร้าน
- เมื่ออ่านรายการคืนเงินของผู้ให้บริการสำหรับแถวที่มี `refundedSatang` ระบบถือว่ารายการคืนเงินที่เก่าที่สุดรวมกันเท่ายอดสะสมนั้นถูกหักไปแล้ว และลงวันที่เฉพาะส่วนที่เกิน ข้อโต้แย้งไม่เคยอยู่ในยอดสะสมเดิม
- ข้อโต้แย้งที่แพ้ไปก่อนการเปลี่ยนนี้ (โค้ดเดิมไม่หัก) และเปิดภายใน 60 วัน จะเป็นรายการหักในเดือนที่ระบบอ่านพบครั้งแรกหลังขึ้นระบบ ไม่ย้อนเข้าเดือนเดิม
- ยอดของแถวการแนะนำเดิมไม่ถูกแก้ แถวที่เกิดขณะตั้งภาษีแบบบวกเพิ่มจึงยังรวมภาษี (สูงกว่าฐานใหม่เท่าจำนวนภาษี) คำสั่งอ่านรายการเหล่านี้อยู่ใน `docs/agent-memory/sales-credit-refund-rules-2026-10-02.md`

**ที่มาของข้อมูล**
- จุดเดียวที่ระบบเห็นการคืนเงินหรือข้อโต้แย้งคือ `observeBillingCharges` (`billing-financial.ts`) ซึ่งทำงานเมื่อผู้ให้บริการแจ้งเหตุการณ์ของรายการนั้น และทุกรอบตรวจบัญชี (ประมาณ 5 นาที)
- รายการชำระบอกเพียงยอดคืนสะสมและธงว่ามีข้อโต้แย้ง สำหรับการชำระที่มียอดเซลล์และยอดยังเหลือ ระบบจึงอ่านรายการคืนเงินและรายการข้อโต้แย้งของรายการชำระนั้นจากผู้ให้บริการเพิ่ม (รหัส จำนวน เวลา สถานะ) การชำระอื่นไม่มีการเรียกผู้ให้บริการเพิ่ม
- `recordAttributionDeductions` (`billing-package-request.ts`) เขียนรายการหักใน transaction เดียวกับการบันทึกยอดคืนของใบแจ้งหนี้ กติกาอยู่ใน `creditDeductions` (`sales-attribution.logic.ts`)

**หน้าจอ** (`/sales/reports`): การ์ดของแต่ละเดือนมีหัวข้อ “รายการหักในเดือนนี้” หนึ่งบรรทัดต่อรายการ — “หักจากการคืนเงิน” หรือ “หักจากข้อโต้แย้งการชำระ”, ชื่อร้าน, เดือนของยอดเดิม, วันที่คืนเงินหรือวันที่เปิดข้อโต้แย้ง และจำนวนที่หัก ยอดที่ติดลบแสดงเครื่องหมายลบหน้าจำนวนเงิน
คิวของเจ้าของ (`/system/sales-team` หัวข้อ “รายการที่ถูกธง”) เก็บทุกแถวที่เคยติดธง และบอกสถานะของแต่ละแถว: “รอตรวจ · ยังไม่นับในยอด”, “ตัดออกจากยอดแล้ว · ไม่นับให้เซลล์” หรือ “ยืนยันแล้วว่าไม่ผิดปกติ · นับในยอด” พร้อมวันที่ตรวจและเหตุผลที่เจ้าของพิมพ์ ปุ่มมีเฉพาะการตัดสินใจที่ยังเปลี่ยนผลได้
ร้านรอตรวจ (มติ 2026-10-02) ใช้คำ “รอตรวจ” คำเดียวกันทุกหน้าจอ รายงานมีคอลัมน์ “รอตรวจ”, บรรทัด “รอตรวจ N ร้าน · ยังไม่นับในยอด” ของแต่ละเซลล์ และหัวข้อ “ร้านที่รอตรวจ · ยังไม่นับในยอด” ในการ์ดของเดือนที่ร้านชำระเงิน หนึ่งบรรทัดต่อร้าน — ชื่อร้าน, ชื่อเซลล์เมื่อรายงานมีหลายคน, ดีลพิเศษหรือแนะนำร้าน และเหตุผลที่ติดธงด้วยคำเดียวกับคิวของเจ้าของ
ท้ายรายงานมีข้อความ “มี N ร้านรอตรวจ ยังไม่นับเป็นร้านที่เปิดและยังไม่นับในยอด เมื่อผู้ดูแลระบบยืนยันว่าไม่ผิดปกติ จะนับในเดือนที่ร้านชำระเงิน”
ในคิวของเจ้าของ กล่อง “ยืนยันว่าร้านนี้ไม่ผิดปกติ” บอกเดือนที่ร้านจะถูกนับก่อนกดยืนยัน
สรุปรายวัน (§17.2) นับ “ร้านเปิดใหม่เมื่อวาน” และยอดรวมเฉพาะร้านที่นับได้ และแยก “รอตรวจ N ร้าน (ยังไม่นับในยอด)” ร้านที่ถูกตัดออกแล้วไม่อยู่ในตัวเลขใด
หน้ารายงานเปิดได้เฉพาะหัวหน้าเซลล์และเจ้าของ (`sales.report.read`) เซลล์ที่ไม่ใช่หัวหน้ายังไม่มีหน้าจอที่เห็นยอดของตัวเอง จึงยังไม่เห็นบรรทัดร้านรอตรวจด้วยตัวเอง การให้สิทธิ์นี้แก่เซลล์เป็นการตัดสินใจเรื่องสิทธิ์ที่ยังไม่ได้ทำ

- เวลาปิดข้อโต้แย้งของผู้ให้บริการไม่ถูกเก็บ (มีเฉพาะในเหตุการณ์ที่ผู้ให้บริการส่งมา ซึ่งระบบเก็บโดยไม่มีเวลาของผู้ให้บริการ) เดือนที่หักของข้อโต้แย้งจึงเป็นเดือนที่ระบบบันทึกผล

- **R6 (แก้)** ดีลใช้ **เส้นทางซื้อครั้งเดียวของ #667 ทั้งชุด** ไม่มี `DealSource`/Checkout แยก: quote `{ dealId, purchaseMode ∈ {CARD_ONCE, PROMPTPAY_ONCE} }` → snapshot `{ deal: { requestId, snapshotHash }, quote.purchaseMode, quote.offer = offer ของดีล }` → Checkout / หลักฐาน / reconciler เดิม → apply ครั้งเดียวเดิม + follow-up ของดีล **ในธุรกรรมเดียว** (ลิมิต/เมนู/งบ AI ตาม snapshot, `PackageChangeRequest → APPLIED`, แถว `SalesAttribution`, audit) → `renewalMode` = โหมดที่จ่าย (สถานะ/sweep/แจ้งเตือนของ #667 ใช้คำ "ซื้อใหม่" ได้ทันที)
  - offer ของดีล: `offerKey` = tier ฐาน, `interval: 'month'`, **`intervalCount = months`** (catalog ยังเป็น 1 เสมอ), `priceSatang` = ราคาดีล, ลิมิตตามดีล, `receiptAllowance = monthlySlipLimit × months`; `appendPackageInterval` รับจำนวนรอบ (N เดือน รักษาวัน anchor)
  - `assertStripePrice` (เทียบ Price catalog) ข้ามเมื่อ snapshot มี `deal` แล้วใช้ `assertDealSnapshot` แทน (แถว APPROVED, ยังไม่หมดอายุ, hash ตรง, ราคา/เดือนตรง, ร้านตรง); `productId` ยังอ่านจาก Price catalog ของ tier ฐาน; `unit_amount` มาจาก snapshot เท่านั้น
  - gate: ดีลใช้ gate เดียวกับลูกค้าทั่วไป (`new_sales` + `card_once` / `promptpay_once`) ไม่มี gate แยก; ปิด = `BILLING_MODE_NOT_READY` และการ์ดข้อเสนอแสดงเฉพาะโหมดที่เปิด (ถ้าปิดทั้งคู่ การ์ดบอก "ติดต่อทีมงาน")
  - `restartFits` (ตรวจสาขา/ผู้ใช้ปัจจุบันพอดีกับ offer) ไม่ใช้กับดีล — ลิมิตดีลต่ำกว่าที่ใช้อยู่ = ห้ามสร้างเพิ่ม ของเดิมคงอยู่ (S31/P29 §4D) และ preview ดีลเตือนเซลล์แล้ว
- **R7 (ยืนยัน)** ดีลไม่มีช่องทางโอนหรือแนบสลิป แม้ gate PromptPay ปิด; ลูกค้าชำระได้เฉพาะโหมดบัตร/PromptPay ที่เปิดอยู่
- **R9 / S14 / D5 (แก้)** ร้านที่มีสิทธิ์อยู่แล้วรับดีลได้ตามตาราง 19.3; ไม่มีการปฏิเสธ `CONTROL_DEAL_SUBSCRIPTION_ACTIVE` อีก; ปฏิเสธเฉพาะบัญชีค้างชำระ/grace/invoice ล่าสุด refund-dispute → `CONTROL_DEAL_SUBSCRIPTION_REVIEW`
- **R10 / §11 UI (แก้)** การ์ดข้อเสนอใช้ตัวเลือกโหมดของ #667 จำกัดเฉพาะ `CARD_ONCE` / `PROMPTPAY_ONCE` ∩ gate ที่เปิด (Phase 5 เพิ่ม `CARD_AUTO` / `PROMPTPAY_RENEW` สำหรับดีลต่ออายุอัตโนมัติ); `billingProfileHref` เพิ่ม `deal=<id>` ให้ขั้นกรอกที่อยู่/อีเมล (D4) กลับมาที่การ์ดเดิม; ข้อความยืนยันก่อนจ่ายบอกชัดว่า "จ่ายครั้งเดียว ไม่มีหักอัตโนมัติ" ตาม #667
- **§17.2 การนับยอด (ยืนยัน)** นับครั้งแรกครั้งเดียว: `CARD_ONCE` / `PROMPTPAY_ONCE` = ยอดที่จ่าย; `CARD_AUTO` = invoice `INITIAL`; `PROMPTPAY_RENEW` = การจ่าย QR ครั้งแรกเท่านั้น (บิลงวดถัดไปเป็น `RENEWAL` ไม่นับ); ดีล = ราคาดีล
- **§17.3 / D7 (ขยาย)** ดีลต่ออายุอัตโนมัติ (Phase 5) ยังใช้ Stripe Price เฉพาะร้าน และรองรับ 2 โหมดของ #667: `CARD_AUTO` (ตัดบัตรทุกงวด) และ `PROMPTPAY_RENEW` (ออกบิล QR ทุกงวด ผ่าน `bindPromptPayRenewal` ด้วย Price ของดีล) — Q8; ข้อความเดิม "ลูกค้าต้องมีบัตร" เปลี่ยนเป็น "บัตร หรือ QR แบบสแกนทุกงวด"
- **S11 (ปิด)** เส้นทางครั้งเดียวสำหรับร้านที่ไม่มี subscription และหลักฐาน promptpay มีแล้ว · **S12 (เหลือ)** เปิด PromptPay บนบัญชี Stripe live + เพดานยอดต่อรายการ (S38) · **AC6 (แก้)** `paid-invoice.ts` และ `paid-checkout-invoice.ts` ไม่ต้องแก้เพิ่มสำหรับดีล (พิสูจน์ด้วย diff ว่างเทียบ origin/develop)
- copy Phase 1 "ชำระผ่านบัตรออนไลน์" คงไว้จน Owner เปิด gate PromptPay บน production แล้วจึงเปลี่ยนเป็น "บัตรหรือ PromptPay" (S42)

### 19.3 ดีลบนร้านที่มีสิทธิ์อยู่แล้ว (แทน R9/D5 เดิม)

| สถานะร้านตอนจ่ายดีล | ผล |
|---|---|
| ล็อก / หมดอายุ / ทดลองอยู่ (Q5) | ดีลเริ่มทันทีที่จ่าย: term = วันจ่าย + N เดือน, สิทธิ์ตามดีล |
| ซื้อครั้งเดียวยังไม่หมด (`CARD_ONCE` / `PROMPTPAY_ONCE`) | ต่อท้าย: `termEndsAt = paidThrough + N เดือน` (anchor เดิม) ผ่านกลไก `snapshot.oneTime` ของ #667; **สิทธิ์ของดีล (ลิมิต/เมนู/งบ AI) มีผลทันที** ไม่มีงานรอขอบรอบ |
| QR ต่ออายุ (`PROMPTPAY_RENEW`) | ระบบยกเลิก subscription QR ให้ (system-initiated, journal/observed) + void บิลค้าง แล้วต่อท้ายเหมือนแถวบน |
| บัตรอัตโนมัติ (`CARD_AUTO`) — **Q7** | **ทำแล้ว**: ระบบรับราคา deal ที่อนุมัติไว้เป็นยอดสุดท้าย (**ไม่มี proration/refund/เครดิตส่วนต่างในระบบ**) → Checkout ครั้งเดียว → apply ดีลทันที → คิว operation ยกเลิก subscription เดิมด้วย `prorate: false`; การยกเลิกต้อง observed ก่อนปล่อย reservation และถ้าล้มเหลวเปิด `DEAL_SUBSCRIPTION_CANCEL_PENDING` เพื่อ retry. เหตุการณ์ที่มาช้าของ subscription เดิมเป็น no-op ไม่ hold บัญชี |
| ค้างชำระ / grace / invoice ล่าสุด refund-dispute | ปฏิเสธ `CONTROL_DEAL_SUBSCRIPTION_REVIEW` (ทีมงานเคลียร์ก่อน) |

หลังยกเลิก subscription เดิม (แถว 3–4) เหตุการณ์ของ subscription นั้นต้องถูก **เพิกเฉย** ไม่ใช่ hold บัญชี (S34) — กรณีที่ยกเลิกไม่สำเร็จหลังจ่าย ให้เปิด issue `DEAL_SUBSCRIPTION_CANCEL_PENDING` + retry ตามแบบ refunds

**Update 2026-10-10 — D-P5-6: a price return the provider does not hold ends (`SPECIAL_PRICE_RETURN_NOT_APPLIED`).** Before this, a `SCHEDULE_PRICE_RETURN` refused before any provider write stayed `BLOCKED` for ever, and one sent but not applied stayed `UNKNOWN` after 23 hours; both kept `activeCollectionOperationId`, so the shop could not buy, change or cancel and every reconcile pass of the account stopped at the operation. Rule: never sent → `FAILED` in the same pass; sent → re-sent under its key for one hour, then read only, and from one hour ten a read that still shows the deal price on the same item ends it `FAILED`; a failed read, or any other shape, keeps waiting in review. Ending sends nothing, releases the slot, keeps the `SPECIAL_PRICE_RETURN_REVIEW` case open and writes `billing.price_return.ended`. The bound is safe because the swap is only ever sent under one idempotency key and nothing is sent after the first hour. Left open: the subscription keeps the deal price and nothing queues the return again (the sweep's retry reuses the same operation key), so the open review case is the only signal.

**Update 2026-10-10 (2) — D-P5-6: a failed price return is queued again once a day.** Before this, a return that ended `SPECIAL_PRICE_RETURN_NOT_APPLIED` was never tried again: the sweep skipped only non-failed operations, but a second operation reused the unique key `deal-return:<deal>:<paidThrough>`, so its create failed and was swallowed, and the shop stayed on the deal price for ever. Rule: the 15-minute sales sweep takes each such failed operation whose end is at least 24 hours old and queues a NEW operation for the deal (key `deal-return:<deal>:<paidThrough>:<attempt number>`, a new row and so a new provider idempotency key), marking the failed one `SUPERSEDED`; the new attempt targets the account's current boundary, starts from the provider read as every attempt does, and holds the shop's slot only while in flight (about seventy minutes at most). It records success without sending when the subscription already shows the catalog price. No row is written, and the failed operation is looked at again a day later, when the account is not ready (a purchase attempt or the shop's own command holds the slot, a pending plan change, renewal cancelled, grace, the boundary under two hours away) or the subscription is not the one the failed attempt saw (another subscription or item, a price that is neither the deal's nor the catalog's, a schedule, a cancellation, a pause, a pending update, another collection method or quantity, a discount) — so a return that can never apply does not fail daily. A return the provider itself refused (a 4xx on the swap) ends `SPECIAL_PRICE_RETURN_REJECTED` and is never retried: that one needs staff, and there is no staff action to queue it again yet. A renewal already charged at the deal price before a return applied stays as it is: the swap is `proration_behavior: 'none'` and only changes the next cycle; nothing is back-charged. The `SPECIAL_PRICE_RETURN_REVIEW` cases of the failed attempts stay open until an attempt succeeds, which resolves all of the deal's.

### 19.10 ซื้อดีลต่ออายุอัตโนมัติล่วงหน้าจากแพ็กเกจจ่ายครั้งเดียว (มติ Owner 2026-09-23)

ร้านที่มี `CARD_ONCE` หรือ `PROMPTPAY_ONCE` และยังมีสิทธิ์อยู่ต้องซื้อดีล `autoRenew=true` ที่อนุมัติแล้วได้ก่อนสิทธิ์เดิมหมด โดยจ่ายราคาดีลงวดแรก **ตอนกดซื้อ**; ดีลเริ่มที่ `paidThrough` เดิม และงวดแรกสิ้นสุดหลังจากนั้นหนึ่ง `cadence` (เดือน/ปี). สิทธิ์เดิม (tier, ลิมิต, เมนู, เครดิต AI และใบเสร็จ) ใช้จนถึงวันเริ่มดีล; สิทธิ์ดีลเริ่มในวันนั้น. รอบถัดไปจึงตัดบัตรอัตโนมัติหรือออกบิล QR ตามโหมดที่ลูกค้าเลือก. หน้า quote/ยืนยันต้องแสดงวันเริ่มดีล วันสิ้นงวดแรก และวันเก็บเงินรอบถัดไปให้ชัด.

- ชำระงวดแรกด้วย Checkout แบบครั้งเดียวและหลักฐาน paid invoice เดิม; snapshot ผูก invoice/`paidThrough`/anchor/term ของแพ็กเกจเดิมและ Stripe Price เฉพาะร้าน. ห้ามสร้าง recurring Checkout ที่เริ่มเก็บเงินทันทีซ้อนรอบเดิม.
- หลังจ่าย ดีลเป็น `PAID` พร้อมรายการเปิดใช้ตามวัน (`effectiveAt = paidThrough` เดิม); ออกใบเสร็จ/บันทึกยอดที่จ่ายแล้ว แต่ยังไม่เปลี่ยนสิทธิ์ปัจจุบัน. เมื่องานตามวันทำสำเร็จจึงเป็น `APPLIED`, เปิดสิทธิ์ดีลและเริ่มนับ `cycles` จากวันนั้น. ต้อง retry ได้โดยไม่เปิดสิทธิ์หรือทำ attribution ซ้ำ.
- ผูก subscription ล่วงหน้าแบบไม่เก็บเงินซ้ำในงวดแรก: สำหรับบัตรต้องเก็บ payment method ที่ลูกค้ายินยอมให้ตัดรอบต่อไปและผูกแบบ `charge_automatically`; สำหรับ QR ใช้ `send_invoice`. ทั้งสองแบบเริ่มเรียกเก็บรอบถัดไปที่ **วันสิ้นงวดแรกของดีล**. คำสั่งภายนอกต้อง idempotent, อ่านผลกลับ, ตรวจ invoice ศูนย์บาทและห้ามมีสมาชิกเก็บเงินซ้ำ.
- ก่อนสร้าง Checkout และก่อน apply ตรวจ tenant/OWNER, ดีลยัง APPROVED และไม่หมดอายุ ณ ตอนเริ่ม Checkout, invoice เดิมไม่ refund/dispute, `paidThrough`/term/Price/เมนูไม่เปลี่ยน, ไม่มี attempt/change/collection ค้าง. ถ้าข้อมูลเปลี่ยนหลังเก็บเงินให้ HELD/retry หรือส่งตรวจ ไม่เปิดสิทธิ์ผิดรอบ. หากเงินงวดแรกถูกคืนก่อนเริ่มดีล ต้องหยุดการเปิดสิทธิ์และสมาชิกที่ตั้งไว้ โดยคงสิทธิ์เดิม.
- `status.deal.purchaseModes` และ UI ต้องแสดงเฉพาะทางที่ quote รับจริง; วันที่เริ่มและสถานะ `PAID` ที่รอเปิดใช้ต้องมองเห็นได้. ดีลที่รับก่อน `offerExpiresAt` ยังคงเปิดใช้ตามวันที่กำหนด แม้วันเริ่มจริงอยู่หลังวันหมดอายุข้อเสนอ.
- ระหว่างงวดดีลแรกที่จ่ายแล้ว OWNER หยุดการต่ออายุบัตรที่ปลายงวดได้โดยไม่เสียสิทธิ์งวดนั้น. ถ้าหลังจ่ายแล้วพบข้อมูลต้นทางเปลี่ยนหรือเปิดสิทธิ์ไม่ได้ ระบบต้องหยุด subscription ที่ผูกไว้ก่อนมีการเก็บงวดถัดไป และแสดงรายการ `HELD` ให้ทีมตรวจ. สำหรับแพ็กเดิมที่ซ้อนนานเกินช่วง trial ของ Stripe ให้คงรายการ `PAID` และผูก subscription ภายหลังเมื่อเข้าในช่วงที่ผู้ให้บริการรองรับ โดยไม่เปิดทางซื้อซ้ำระหว่างรอ.

### 20.2 กติการาคา

ราคารายปี = **ราคารายเดือน × 10** ทุก tier (เหมือนเดิม) → ENTERPRISE = 199,900 สตางค์/เดือน,
1,999,000 สตางค์/ปี (19,990 บาท). `offerTerms` ของนโยบายตั้งทับได้ทุก tier รวม ENTERPRISE.

### 20.3 เปิดขาย ENTERPRISE

- `BILLING_PAID_TIERS` มี 4 tier → `paidVariant`, `parseBillingPolicy` (`priceIds`/`zeroPriceIds`/`offerTerms`),
  `validateProvider`, `impact()`, `isUpgrade` และฟอร์มตั้งค่าได้แถว ENTERPRISE มาเอง.
- **fail-closed**: `billingOffer` ตอบ `COMING_SOON` เฉพาะ ENTERPRISE ที่ยัง *ไม่ผูก* Stripe Price ในนโยบายที่ใช้อยู่;
  `catalog()` เปลี่ยนเป็น `AVAILABLE` เมื่อ Price ของ variant นั้นถูกผูกแล้วและ gate `new_sales` เปิด. ก่อนผูก
  quote ตอบ `BILLING_OFFER_UNAVAILABLE` (409) เหมือนเดิม — ไม่มีอะไรพังก่อน Owner ผูกราคา.
- Stripe Product/Price ของ ENTERPRISE สร้างด้วย `apps/api/src/scripts/create-catalog-prices.ts`
  แล้ว Owner ผูกรหัสในหน้าตั้งค่า (ดู [runbook](../runbooks/production-stripe-live-enablement.md)).

### 20.4 ดีลใช้ ENTERPRISE เป็นฐานได้

`SalesDealBaseTier` = ทุก tier ที่จ่ายเงินได้ (ยกเลิก D-P3-1 ที่ตัด ENTERPRISE ออกเพราะไม่มี Price).
ฐานที่ยังไม่ผูก Price ล้มที่ quote ด้วย `BILLING_OFFER_UNAVAILABLE` และ Price ของดีลอัตโนมัติจะค้างที่
`priceState=FAILED` (`catalog_price_missing`) จนกว่าจะผูก — ไม่มีทางเปิด Checkout ที่จ่ายไม่ได้.
ค่าเริ่มต้นของฟอร์มดีลอ่านจาก `TIER_FEATURE_PRESETS[base]` และ offer ของดีล (`dealOffer`) พก
`featureKeys` ของ snapshot ตัวเอง.

#### 20.4.1 เมนูหลักที่ไม่มีเมนูย่อยในรายการเมนูของดีล (แก้ 2026-10-01)

การชำระเงินเขียนทุก key ใน catalog ที่ไม่อยู่ในรายการเมนูของดีลเป็น "ปิด" ดีลที่เลือกเมนูทีละรายการหลังกด
"ล้างทั้งหมด" เคยเก็บเฉพาะ key ของเมนูหลัก (เช่น `expenses`) ร้านจึงจ่ายเงินแล้วเมนูย่อยค่าใช้จ่ายถูกปิดทั้งหมด
กติกาเดียว (`salesDealFeatureKeys` ใน `packages/contracts/src/sales.ts`) ใช้ทั้งสามจุด:

- เมนูหลักที่ไม่มีเมนูย่อยของตัวเองอยู่ในรายการเลย หมายถึงเมนูย่อยทุกตัวของเมนูนั้นที่ดีลขายได้
  (`SALES_DEAL_ALLOWED_FEATURE_KEYS`); เมนูหลักที่มีเมนูย่อยบางตัวอยู่ในรายการ คงไว้เฉพาะตัวที่ระบุ
- หน้าสร้างดีล: เลือกเมนูแล้วได้เมนูย่อยมาด้วย เลิกเลือกแล้วเมนูย่อยออกไปด้วย
- ตอนบันทึกดีล (`buildDealSnapshot`) และตอน billing อ่านดีลที่บันทึกไว้แล้ว (`dealSnapshot`) ใช้กติกาเดียวกัน
  ดีลเก่าที่เก็บเฉพาะเมนูหลักจึงได้ผลเหมือนดีลใหม่เมื่อชำระเงิน รวมถึงรายการ "เมนูที่จะหยุดใช้" ในหน้าชำระเงิน
- ชุดเริ่มต้นครบอยู่แล้ว กติกานี้จึงไม่เปลี่ยนดีลที่เริ่มจากค่าเริ่มต้น (`dashboard_notifications`
  ไม่มีเมนูย่อยที่ดีลขายได้ จึงคงเป็นเมนูหลักอย่างเดียวเหมือนแพ็กเกจเริ่มต้นใน catalog)
- ข้อจำกัด: หน้าชำระเงินที่เปิดค้างไว้ก่อนขึ้นระบบยังใช้แผนสิทธิ์เมนูที่คำนวณไว้ตอนเปิด; ใบเสนอราคาที่ยังไม่เปิดหน้าชำระเงิน
  จะถูกขอให้ตรวจสอบรายการใหม่ (`BILLING_DEAL_SNAPSHOT_MISMATCH`) แล้วได้แผนที่ถูกต้อง

### 20.5 เปลี่ยนแพ็กเกจกลางคันย้ายชุดเมนู (มติ Owner 2026-09-21)

**มติ**: ร้านที่จ่ายเงินแล้วเปลี่ยนแพ็กเกจกลางคัน — ขึ้นหรือลง เส้นทางต่ออายุอัตโนมัติหรือชำระครั้งเดียว —
ชุดเมนูต้องย้ายไปเป็นของ tier ใหม่ **อัตโนมัติ ณ เวลาที่การเปลี่ยนมีผล** และลูกค้าต้องเห็นว่าเมนูอะไรเปิด
อะไรปิด **ก่อนกดยืนยัน**. ลดแพ็กเกจ = ถอดเมนูส่วนเกิน โดยข้อมูลเดิมยังอยู่ (runoff ชุดเดียวกับตอนดีลจบ).

**จุดที่การเปลี่ยนมีผลจริงมี 4 จุด** และทั้งสี่จบด้วยการเขียน `companyPlanTerm.tierKey` เป็น tier ใหม่:

| เส้นทาง | ทิศ | มีผลเมื่อ | ที่เขียน tier ใหม่ |
|---|---|---|---|
| ต่ออายุอัตโนมัติ | ขึ้น | จ่ายส่วนต่างสำเร็จ (ทันที) | `billing-repeat.ts` `apply()` (`snapshot.upgrade`) |
| ต่ออายุอัตโนมัติ | ลง (`SCHEDULE_DOWNGRADE`) | ใบแจ้งหนี้ `RENEWAL` ของรอบถัดไป | `applyInvoice` (`applyingChange`) |
| ชำระครั้งเดียว | ขึ้น | จ่ายส่วนต่างสำเร็จ (ทันที) | `reconcileOneTime` (`snapshot.upgrade`) |
| ชำระครั้งเดียว | ลง / เปลี่ยนรอบ (`CUSTOMER_PREPAID_PLAN_CHANGE`) | วันเริ่มแพ็กเกจรอบถัดไป | `applyDueOneTimePlanChange` |

**ทางแก้ที่ใช้** — operation ที่ขอบรอบชื่อ `APPLY_PLAN_MENUS` ([billing-plan-menus.ts](../../apps/api/src/modules/billing/application/billing-plan-menus.ts))
รูปทรงเดียวกับ `SCHEDULE_PRICE_RETURN` (Phase 5) แต่ไม่มีการคุยกับ Stripe จึงไม่ต้อง fence ด้วย lease:
ทั้งสี่จุดข้างบนเรียก `movePlanMenus` **ทันทีหลัง commit** ที่ย้าย term แล้ว op นั้นจะอ่าน tier ที่ร้าน
จ่ายอยู่จริง สร้าง `billingFeaturePlan(..., TIER_FEATURE_PRESETS[tier])` **ใหม่สด ๆ ในธุรกรรมที่กำลัง apply**
ใต้ entitlement lock เดิม แล้วเขียนด้วย `applyBillingFeaturePlan` ตัวเดิม. `BillingOperation` แถวเดียว
(`idempotencyKey = plan-menus:<invoiceId>`) ทำหน้าที่เป็นทั้งกันซ้ำและสมุดสำหรับ retry — และแถวนั้นถูกเขียน
**ในธุรกรรมเดียวกับที่ย้าย term** (`queuePlanMenuMove`) เพื่อให้ deploy restart หรือ worker ตายคั่นระหว่าง
commit กับการย้ายเมนู ยังเหลือแถวให้ตามต่อเสมอ.

ทำไมไม่ใช้ seam ของใบแจ้งหนี้ (`rewritesFeatures`) ตามที่เคยเสนอ: เพราะสามในสี่ข้อติดอยู่ที่ seam นั้นเอง —
invoice ของ plan change เป็น `RENEWAL`, เส้นทางครั้งเดียวไม่มี invoice ที่ขอบรอบ, และ `featurePlan` ที่ pin
ล่วงหน้าจะถูกตรวจ `sourceHash` อีกทีตอน apply (แอดมินแก้สิทธิ์คั่นครั้งเดียว = invoice ที่จ่ายแล้วกลายเป็น
HELD ด้วย `BILLING_ENTITLEMENT_REVIEW_REQUIRED`). การสร้าง plan สดในธุรกรรมที่ apply ทำให้ช่วง `sourceHash`
เหลือระดับวินาที จึงไม่เหลือช่องให้ drift เลย และไม่ต้องมีกลไกที่สองไว้ freeze snapshot ล่วงหน้า.

- **ไม่ย้ายเมื่อ**: ร้านอยู่ระหว่างดีลที่ยังไม่ถึง `returnAt` (ดีลถือ snapshot ของตัวเองตาม §20.4 — การย้ายกลับ
  เป็นหน้าที่ของ `SCHEDULE_PRICE_RETURN`), term ไม่มี tier ที่ขายได้ (เช่นช่วงทดลอง), หรือชุดเมนูเป้าหมาย
  เท่าเดิมอยู่แล้ว — STARTER/BASIC/PRO ใช้ชุดเดียวกัน (§20.1) จึงเป็น no-op ทั้งคู่.
- **ล้มเหลวแล้วยังไง**: term ลิมิต และเงินเปลี่ยนไปแล้วก่อนหน้า op นี้ การย้ายเมนูที่ล้มจึงกลายเป็นแถว
  `BLOCKED` + issue `PLAN_MENU_MOVE_REVIEW` เท่านั้น ไม่ย้อนเงินและไม่ค้างสิทธิ์ที่ลูกค้าจ่ายแล้ว;
  `scan()` ของ billing worker ลองใหม่ทุกรอบจนสำเร็จหรือหมดอายุ op (30 วัน) — ทั้งแถว `BLOCKED` และแถว
  `QUEUED` ที่ค้างเกิน 2 นาที (ซึ่งแปลว่าการย้ายหลัง commit ไม่เคยได้รัน).
- **ลูกค้าเห็นก่อนยืนยัน**: `quote.featureImpact` คิดจาก preset ของ tier เป้าหมายทุกครั้งที่เป็นการเปลี่ยน
  กลางคัน (ทั้งขึ้นและลง) — แต่ **ไม่ pin** `featurePlan` ลง snapshot เพราะการเปลี่ยนแบบรอขอบรอบต้องไม่ย้าย
  เมนูตอนจ่าย; หน้าจอยืนยันแบบรอขอบรอบเปลี่ยนคำเป็น "ตั้งแต่ <วันเริ่มแพ็กเกจรอบถัดไป>". เส้นทางลดแพ็กเกจ
  ของสมาชิกรายเดือน/รายปีใช้หน้า `collection/preview` ไม่ใช่ quote จึงส่ง `featureImpact` มาบน
  `BillingCollectionOperation` แทน และการ์ดยืนยันแสดงรายการเดียวกัน.

**ร้านที่ term หมดแล้วซื้อใหม่ (`RESTART`) — ปิดช่องว่างแล้ว (มติ Owner 2026-09-21)**: ร้านที่ถูกล็อกเพราะ
term หมด แล้วซื้อแพ็กเกจใหม่ (tier เดิมหรือ tier อื่น, ครั้งเดียวหรือต่ออายุอัตโนมัติ) ต้องได้ชุดเมนูของ
แพ็กเกจที่เพิ่งจ่ายเหมือนซื้อครั้งแรกทุกประการ. ทำด้วยการ pin `featurePlan` ที่ quote เหมือน
`initialPurchaseSource` ไม่ใช่ op ที่ขอบรอบ เพราะการเปลี่ยนมีผล "ตอนจ่าย" อยู่แล้วและช่วง `sourceHash`
เท่ากับหน้าชำระเงิน (ไม่กี่นาที) — และเพราะ seam ปลายทางรองรับอยู่แล้วทั้งสองทาง: ใบแจ้งหนี้ของสมาชิกที่
เริ่มใหม่มี `billing_reason = subscription_create` จึงเป็น `INITIAL` (`rewritesFeatures` เดิมทำงาน) ส่วนเส้นทาง
ครั้งเดียวและงวดแรกของ QR ผ่าน `reconcileOneTime` ซึ่งเขียน `featurePlan` ที่ pin ไว้อยู่แล้ว.

ตัวตัดสินใหม่คือ `packageMenuPurchaseSource` = `initialPurchaseSource` + `PAID_EXPIRED_CURRENT_MODE`
([billing-purchase-source.ts](../../apps/api/src/modules/billing/application/billing-purchase-source.ts)) และ
ใช้ทั้งสี่จุดพร้อมกัน: pin ที่ `quote()`, ตรวจซ้ำสองจุดใน `checkout()`, และ `status()` (ร้านที่จะถูกปฏิเสธ
ตอนชำระต้องเห็นตั้งแต่หน้าแพ็กเกจ). ตัวอย่างที่ต้องผ่าน: ENTERPRISE หมดอายุ → ซื้อ PRO แล้วเมนูเฉพาะ
ENTERPRISE ปิด (ข้อมูลเดิมยังอยู่); PRO หมดอายุ → ซื้อ ENTERPRISE แล้วเมนูครบชุดเปิด.
