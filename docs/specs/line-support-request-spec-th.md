## สัญญาปัจจุบัน v2

ข้อกำหนดส่วนนี้และ spec recovery/resolution มีผลเหนือประวัติ v1 ด้านล่างทั้งหมด:

1. Inbox `/system/support-requests` เป็นจุดรับผิดชอบ ตอบ ส่งต่องาน และปิดเคส ใช้สิทธิ์ `system.partner_company.update` เดิมทั้งอ่านและทำงาน ตอบถึงผู้ขอจาก `supportRequestId` ที่ server ตรวจ ไม่รับ raw LINE ID จากหน้าเว็บ และรองรับผู้ที่ยังไม่มีบริษัท/บัญชี
2. `OPEN`=รอตอบ, `ANSWERED`=ตอบแล้วแต่ยังไม่ถือว่าแก้เสร็จ, `CLOSED` พร้อม `closedReason=resolved` และเหตุผล/ผู้แก้=ปิดงานโดยชัดเจน การกลับไปคุยกับ AI ทั้งจากลูกค้าและแอดมินล้างเพียง pause ไม่ปิดเคส และ pause หมด24ชั่วโมงไม่ปิดงานอัตโนมัติ การลบตามอายุ90วันแตะเฉพาะ CLOSED
3. Claim/release/รับช่วงต่อมีผู้รับผิดชอบ เวลา เหตุผลส่งต่อ และ audit; การรับช่วงตรวจรุ่นการมอบหมายที่เห็นอยู่ ผู้รับผิดชอบลาหรือลบบัญชีแล้วไม่ทำให้เคสติดตาย
4. ตอบข้อความได้จาก inbox ทั้งมีร้านและไม่มีร้าน ใช้การตรวจข้อความ/URL/ขนาดเดิม; ส่งครั้งเดิมซ้ำใช้ operation เดิม มีการป้องกันข้อความเก่ามาถึงช้าและผลตอบกลับหาย สถานะส่งแยกจากการแก้เคส ผลส่งและ audit บันทึกพร้อมกันหลังจบ provider I/O เก็บเพียงข้อความตอบล่าสุดและสถานะที่จำเป็น
5. REQUEST_INFO จากคิวสมัครผูก/สร้างเคสและผู้รับผิดชอบพร้อม decision/outbox ใน transaction เดียวกัน ถ้ามีเคสเดิมรักษาเจ้าของงานเดิม แสดงคำถามของทีมงานจาก signup relation เป็นข้อมูลที่ขอ ไม่แต่งเป็นข้อความของลูกค้า ผู้สมัครที่ยังไม่ผูกบัญชีตอบข้อความทั่วไปแล้วต้องเข้าถึงเคสเดิมได้ โดยคงคำสั่งสมัคร/เมนูที่ชัดเจน
6. คิวใช้ cursor จากลำดับ `lastMessageAt,id` และจำนวนจาก database; ไม่มีเพดาน200ที่ทำให้งานเก่าหาย บนมือถืออ่านข้อความเต็มได้โดยไม่ต้อง hover และปุ่มทำงานแตะได้สะดวก
7. ลูกค้าเห็นภาษาธรรมชาติและสิ่งที่ควรทำต่อ ไม่มีเลขอ้างอิงหรือรหัสภายใน หากบันทึกข้อความไม่ได้หรือเปิดเคสใหม่เกินเพดาน ต้องบอกตามจริงพร้อมช่องติดต่อ ไม่อ้างว่าได้รับเรื่องแล้ว รายละเอียดเทคนิคคงอยู่ฝั่งแอดมิน
8. `requestText` เป็นคำถามแรก, `lastMessageText` เป็นข้อความล่าสุด, `lastMediaAt` เป็นเพียงเครื่องหมายว่าส่งรูป ไม่ใช่การเก็บรูปให้เจ้าหน้าที่ตรวจ การย้ายเจ้าของร้าน/กู้บัญชีจากหลักฐานนอกระบบไม่อยู่ใน endpoint นี้

## สัญญา v3 (Owner 2026-09-20): แชทในเคส และรูปที่ลูกค้าส่ง

สถานะ: implementation ตาม [plan](../plans/line-support-thread-plan-th.md) และ [memory](../agent-memory/line-support-thread-2026-09-20.md); ข้อ 9–12 นี้มีผลเหนือข้อ 8 ของ v2 และ §3 บรรทัด "ไม่เก็บรูป" เฉพาะส่วนที่ขัดกัน ข้ออื่นของ v2 คงเดิมทั้งหมด

9. **หนึ่งเคส = หนึ่งเธรดแชท** เริ่มเมื่อลูกค้ากด "ติดต่อเจ้าหน้าที่" (หรือขอความช่วยเหลือจาก LIFF) และจบเมื่อเคส `CLOSED` ทุกสิ่งที่พูดกันระหว่างนั้นเป็นแถวใน `LineSupportMessage` ผูกกับ `LineSupportRequest` (cascade): ข้อความลูกค้า (`CUSTOMER`/`TEXT` เก็บเต็มประโยค ≤2000 ตัวอักษร ไม่ใช่แค่ 200 ตัวสรุปบนแถวเคส), รูป/ไฟล์ลูกค้า (`CUSTOMER`/`IMAGE`|`FILE`), และคำตอบทีมงาน (`STAFF`/`TEXT` พร้อมชื่อผู้ส่งและสถานะส่ง `PENDING|SENT|FAILED` ที่ผูกกับ `operationId` เดิม ส่งซ้ำ operation เดิมไม่เพิ่มแถว) ข้อความจากหน้า partner ที่ระบุ `supportRequestId` ก็ลงเธรดเดียวกัน คำถามที่ทีมงานขอเพิ่ม (REQUEST_INFO) ยังแสดงจาก signup relation ตามข้อ 5 ไม่แต่งเป็นข้อความในเธรด
10. **รูป/ไฟล์ของลูกค้าเก็บไบต์ไว้ให้เจ้าหน้าที่ดูได้** ดึงจาก LINE content API ตอน webhook มาถึง (LINE เก็บไฟล์ให้ชั่วคราวเท่านั้น) ผ่านการตรวจเดิมทั้งหมดของ media lane (ชนิด/ขนาด/ลายเซ็นไฟล์/malware); ไม่ผ่านหรือดึงไม่ได้ให้เก็บแถวพร้อม `mediaError` แทนไบต์ และเธรดบอกตามจริง ไบต์อยู่ใน `LineSupportMessageBlob` (Postgres เหมือน `AttachmentBlob`) เสิร์ฟผ่าน `GET /v1/system/support-requests/:id/messages/:messageId/content` (same-origin, `Cache-Control: private, no-store`) สิทธิ์เดิม `system.partner_company.update` การเก็บรูปไม่เปลี่ยนกติกา marker ของข้อ 8: รูปยังไม่ reopen, ไม่ขยับ `lastMessageAt`, ไม่ต่อ pause และ media lane ยังประมวลผลรูปเป็นใบเสร็จตามเดิม (Owner 2026-09-06)
11. **Inbox แสดงเคสเป็นแชท** ปุ่ม "เปิดแชท" ทุกแถว (รวม CLOSED ที่ยังไม่ถูกลบ) เปิดหน้าต่างเธรด: หัวเคส (ผู้ขอ/รหัสผู้ขอ/สถานะ/ผู้รับผิดชอบ/คำถามตั้งต้น/ข้อมูลที่ทีมงานขอ), ข้อความเรียงตามเวลา ลูกค้าซ้าย ทีมงานขวา รูปคลิกเปิดเต็ม, ช่องพิมพ์ตอบ (เฉพาะผู้รับผิดชอบบนเคสที่ยังไม่ปิด ใช้กติกา operation/retry เดิมของข้อ 4 ทุกประการ) และปุ่มจัดการเคสชุดเดียวกับแถว หน้าต่างดึงเธรดใหม่ทุก 10 วินาทีขณะเปิดอยู่ (`GET /v1/system/support-requests/:id/thread` คืนทั้งแถวเคสล่าสุดและข้อความ ≤500 แถว) เคสที่เปิดก่อน v3 มีเฉพาะสรุปบนแถวเคส หน้าต่างต้องบอกเช่นนั้น ไม่ประดิษฐ์ประวัติ
12. **PDPA (§3 ปรับ)**: ข้อความเต็มและไบต์ของรูปเป็นข้อมูลของเคส ลบพร้อมเคสตอน sweep 90 วันหลัง `CLOSED` (cascade, ไม่มี sweep ใหม่); ไม่มี LINE id, ชื่อ LINE หรือ lineMessageId ออกทาง contract; audit ยังบันทึกเพียงข้อเท็จจริง (`hasText`) ไม่บันทึกข้อความหรือไบต์

13. **หยุด AI หมายถึงไม่ให้ AI แทรกระหว่างเจ้าหน้าที่ดูแลทุกชนิดข้อความ**: ขณะ `LineCompanyContext.aiPausedUntil > now` ข้อความอิสระ รูป และไฟล์ห้ามเข้าโมเดล/OCR/การสร้างร่างค่าใช้จ่าย ข้อความยังเข้าเธรดเจ้าหน้าที่ตามข้อ 9–10; รูป/ไฟล์ยังดึง ตรวจความปลอดภัย และเก็บไบต์หรือ `mediaError` เพื่อให้เจ้าหน้าที่ดูได้ แล้วตอบเพียงข้อความระบบว่ารับสื่อส่งให้ทีมงานแล้ว ห้ามส่งข้อความ “กำลังอ่านเอกสาร” หรือผลวิเคราะห์ AI
14. **สถานะมีแหล่งเดียว**: เว็บไม่เก็บธง AI ซ้ำ แต่คำนวณจาก `LineCompanyContext.aiPausedUntil` ของ LINE user ทุกครั้งที่อ่านเคส เหตุการณ์ LINE “ติดต่อเจ้าหน้าที่”, “คุยกับน้องมั่งมี”, การกดจากเว็บ หรือ mutation อื่นที่แก้ context เดียวกันจึงให้ผลตรงกัน หน้าต่างแชทยังคง poll ทุก 10 วินาทีและต้องสะท้อนสถานะล่าสุด
15. **ปุ่มเดียวแสดงสถานะและสลับได้** บนเคสที่ยังไม่ปิด มีร้าน มี LINE assistant context ปัจจุบัน และอยู่กับผู้ใช้ปัจจุบัน: `AI กำลังทำงาน` สีเขียวเมื่อไม่มี pause ที่ยังมีผล กดแล้วตั้ง pause 24 ชั่วโมง; `AI ไม่ได้ทำงาน` สีแดงเมื่อ pause ยังมีผล กดแล้วล้าง pause ปุ่มต้องมี accessible label บอกผลของการกดและมี confirm ก่อนเปลี่ยนสถานะ การสลับ AI ไม่เปลี่ยนสถานะ/ผู้รับผิดชอบ/ผลลัพธ์ของเคส และห้ามสร้าง context ใหม่จาก companyId เก่าบนเคส
16. **API เป็น desired action ไม่ใช่ client-only toggle**: `POST .../:id/pause-ai` ตั้ง pause แบบ idempotent และ `POST .../:id/resume-ai` ล้าง pause แบบ idempotent ทั้งคู่ตรวจว่าเคสยังมีชีวิต อยู่กับผู้กด และมีบริษัทก่อนแก้ พร้อม audit; response/read contract คืน `assistantActive` เพื่อให้ UI แสดงผลจริงจาก server

## 1. หลักการ

- คำว่า "รับเรื่องแล้ว" ต้องเป็นจริง: ระบบต้องรู้ว่าส่งถึง **ใคร** และถ้าส่งถึงใครไม่ได้ต้อง **ดัง** (ops alert) ไม่ใช่ PUBLISHED เงียบ ๆ
- ผู้กดเป็นใครตอนนี้ ไม่ใช่ตอนที่เคยผูก: ร้านที่ผูกกับคำขอ = ร้านที่ผู้กดเป็นสมาชิก ACTIVE อยู่จริง ณ ตอนกด (ผ่าน identity ACTIVE) มิฉะนั้น = "ยังไม่มีร้าน" (ถ้ามีคำขอสมัครค้าง ให้ลิงก์ไปคิวสมัคร)
- แอดมินตอบจาก **กล่อง "ส่งข้อความถึงร้าน" ในหน้า partner** (endpoint เดิม `POST /system/partners/:companyId/line-message`) — ไม่เปิด Chat ใน OA
- ลูกค้าไม่ควรติดอยู่กับ AI ที่เงียบ: ปลดเองได้ด้วยคำสั่ง

## 2. สิ่งที่ต้องเปลี่ยน

### 2.1 ตอนกด (`handleStaffContact`)
