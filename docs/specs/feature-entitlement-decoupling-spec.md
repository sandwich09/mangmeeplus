- Implementation amendment 2026-08-01 (safe OFF / runoff lifecycle, normative deltas): (1) **DRAINING writes `enabled=false`.** The entitlement row is set false in the same transaction as the `DISABLE_REQUESTED` transition, because spec:60 requires a disable request to reject new interactive root mutations and external sends *immediately*; leaving the row enabled would let every queued external send complete, which was measured directly (a queued attempt under a "draining but enabled" row is granted `CLAIMED` and dispatches, versus `SUPPRESSED_FEATURE_DISABLED` under this rule). DRAINING therefore remains purely derived — latest transition is `DISABLE_REQUESTED`, tested as `CompanyFeatureEntitlement.lastSeq === thatTransition.seq` — and ordinary runoff on a snapshotted root is an opt-in the owning family grants by consulting the snapshot, exactly like the retained pre-disable authority rows in §6.2. Consequently a re-enable from DRAINING bumps the epoch through the ordinary enable path, satisfying "Returning DRAINING→ON with the pre-disable epoch is forbidden" with no special case. (2) **Finish-draining is a separate SYSTEM command.** `EntitlementTransition` is unique by `(companyId, featureKey, commandId)`, so `DISABLE_REQUESTED` and `OFF` for one feature cannot share the partner command's id; completion uses the derived, cycle-unique id `runoff-complete:<featureKey>:<disableSeq>`, which is itself the idempotency fence. It bumps neither the epoch nor `CompanyEntitlementSet.setVersion` and writes no `EntitlementCommand` row, because it changes no member of the entitlement set — bumping would spuriously invalidate the operator's freshly read `expectedSetVersion` immediately after every disable. ## 4. Normative Operating Principles

1. Passive capture and required system projections continue while a feature is off; interactive root creation and purchased value are gated by their owner.
2. Static dependencies exist only when a child has no standalone journey. Composite actions use the full per-action entitlement set.
3. Enable-later prepares captured history in the background; users never re-key stored data or migrate records themselves.
4. Tax amounts/commercial math are source facts; Ledger resolves accounts at posting time without making Tax depend on Ledger.
5. VAT claimability follows tax facts, not entitlement. Pending VAT uses the reversible Thai-account lifecycle in CC4.
6. 50ทวิ is derived from the actual payment event. Issued legal artifacts and filed returns are immutable; correction is additive and audited.
7. Source voids may perform narrowly scoped system compensation even after Ledger is off; closed/filed history is never silently rewritten.
8. External sends, notifications, AI and workflow actions are gated at final execution and never replay stale work.
9. Privacy/security/purge/self-service and core company/access administration are platform controls, not optional commercial value.
10. Legacy effective access is normalized atomically before fail-open/inheritance is removed.
11. Cross-feature aggregates are labeled; source details and actions require source entitlement and user permission.
12. Every sellable top-level feature/SKU has its own `DEFAULT` launch and rollback row. FIN, CRM, INV, WF and RPT are implementation workstreams/shared evidence groups only; one sibling never waits for or closes because of an unrelated sibling. Platform baseline keys are always on. Effective availability is the intersection of purchased entitlement and every exact per-action `(gateKey, routeKey)` row required by that action, each protected by the fresh execution fence in CC1.
13. Launch gates are an internal-only operational control plane. Customers, partners, tenant users and AI never read or mutate route state; they see only the permitted business action or friendly fallback.
14. The global action hub is a permission-filtered read model over domain truth. It may store only minimal assignment/acknowledgement/snooze collaboration state; every business mutation still uses the owning domain API and invariant.
15. Accountant delegation never creates an anonymous bypass. v5.1 uses an invited, company-scoped member, explicit assignment and authenticated controlled packet download only.

### CC1 — Effective availability, disable lifecycle, generation vector, and runoff

- `CompanyEntitlementSet(companyId, setVersion, lastTransitionAt)` is the canonical batch-CAS row; `setVersion` increments exactly once per successful multi/single-key entitlement command. `EntitlementCommand(companyId, commandId, payloadFingerprint, expectedSetVersion, resultSetVersion, resultJson, createdAt)` is unique by `(companyId, commandId)` and owns whole-set idempotency. Under the company-set lock, same key/fingerprint returns the stored result before CAS, key reuse with another payload rejects, and a distinct stale expected-set version changes nothing. Its append-only child `EntitlementTransition(companyId, featureKey, seq, epoch, commandId, action ∈ {ENABLE, DISABLE_REQUESTED, OFF}, actorUserId|SYSTEM, createdAt, reasonJson)` is unique by `(companyId, featureKey, seq)` and `(companyId, featureKey, commandId)`. The canonical entitlement row stores current epoch/last seq; epoch increments exactly once on every real non-ON→ON transition, including cancellation/resume from DRAINING, not on disable or idempotent retry. Returning DRAINING→ON with the pre-disable epoch is forbidden. Company normalization is tracked separately per CC7.
- A partner command that changes dependencies locks/CASes the complete affected company entitlement set in canonical feature-key order, validates the proposed final set, then writes the command/result and all child transitions atomically. Disabling a parent with active structural children returns one truthful impact preview and a one-click explicit atomic cascade; it never silently strands or disables a child. Concurrent parent-disable/child-enable has one winner and the loser safely refreshes the preview.
- The partner detail and command share one public contract. Detail exposes the same current-normalization predicate used by the command, current `setVersion`, and a friendly per-feature `canDisable`/reason without internal matrix or route keys. A web attempt keeps one `commandId` across lost-response retries, sends the displayed `expectedSetVersion`, and explicitly confirms the exact cascade preview. Empty, non-array, over-catalog and duplicate feature entries are rejected at both transport and application boundaries; validation and writes operate on the same canonical unique feature map.
- A durable `FeatureLaunchGate` stores `(gateKey, routeKey, state ∈ {CLOSED, OPEN}, generation, lastSeq, reason, updatedAt)` for each sellable feature or named operational route. `routeKey=DEFAULT` is used when no staged route exists. Named capabilities may own multiple internal route rows; those rows are rollout controls, never packages, entitlements or customer/partner commercial settings. Its append-only `FeatureLaunchGateTransition(gateKey, routeKey, seq, generation, commandId, action ∈ {OPEN, CLOSE}, actorUserId|SYSTEM, payloadFingerprint, reason, createdAt)` is unique by `(gateKey, routeKey, seq)` and `(gateKey, routeKey, commandId)`. Under locks sorted by `(gateKey, routeKey)`, command lookup happens before expected-generation CAS: same key/fingerprint/action returns the original result, key reuse with another payload/action rejects, and a delayed distinct command with stale expected generation cannot reopen/close the row. Every real OPEN↔CLOSED transition increments only that route row's `generation`; an OPEN sibling never authorizes another route. A purchased feature is executable only when its entitlement lifecycle permits the action **and** every exact launch route required by that action is OPEN. Customer-facing UI shows only the purchased feature, available action and friendly fallback; it never exposes route keys, gate state or generation.
- Every `FeatureLaunchGateTransition` persists an immutable, queryable `controlPlaneSnapshot` rather than relying on free-text `reason`: `targetEnvironment`, `buildReleaseId`, `expectedGeneration`, `routeClass=ORDINARY|SPECIALIST_LEGAL`, `validationEvidenceRef` nullable, `validationEvidenceHash` nullable, `specialistApprovedByUserId` nullable, `releaseApprovedByUserId` nullable, `emergencyClose`, `emergencyAuthorityUserId` nullable and `incidentRef` nullable. Normal CLOSE records environment/build/expected generation and the release authority under the ordinary command policy. Emergency CLOSE requires `emergencyClose=true`, `emergencyAuthorityUserId` and `incidentRef`, forbids OPEN, and may omit release/specialist approval so shutdown is not delayed. No required field may be reconstructed later from logs or `reason`.
- `FeatureLaunchGate` mutation is an internal-only control-plane command unavailable to customer, partner, tenant-user and AI surfaces. Every OPEN carries the target environment, immutable build/release id, expected generation and release-owner approval. An OPEN for a specialist/legal route additionally requires the exact current `FEATURE_LAUNCH_MATRIX` validation-evidence reference/hash and a recorded specialist approval; both approval roles and evidence are audited with the transition. One authorized on-call operator may CLOSE immediately with an incident reference and audit because stopping new work must not wait for a second approval. Workflow cancellation or waiter timeout does not release authority by itself: a reconciler observes the remote task/deployment to terminal and completes verify/retirement or records an actionable failed state. Another mutating operation refuses while the prior lease is nonterminal or its remote state is unknown. UAT accepts only ancestry from `develop`; production accepts only ancestry from `main`; PLAN and APPLY independently enforce the same rule and APPLY proves the referenced PLAN workflow/path/event/conclusion and artifact digest.

Missing coverage remains UNKNOWN even when the provider shows a healthy service, and zero OPEN intents never substitutes for a missing row. Only api-web may carry first-cutover legacy bootstrap provenance. Bounded ORPHAN repair is limited to the amendment above and never broadens ordinary recovery, entitlement or launch authority.
- Enable/disable/finish-draining locks the canonical company-feature state (or uses expected-seq CAS), deduplicates `commandId`, and writes the entitlement row + transition + any runoff snapshot in one transaction. A stale expected state conflicts and is safely retried; it never produces split-brain state.
- A disable request immediately rejects new interactive root mutations and external sends. In that transaction it records a cutoff and a `RunoffSnapshot` of only the pre-cutoff roots allowed by the approved matrix; later work cannot join that snapshot.
- A narrow retained-artifact compensation authority remains after OFF for an exact legal artifact/root created before cutoff when its error is discovered later. Such history is not held open in `RunoffSnapshot` or DRAINING indefinitely: invocation creates a fresh audited compensation attempt whose availability vector records the retained-artifact policy plus every still-applicable `(gateKey, routeKey, generation)` launch entry.
- Every queued/outbound/final-mutation work row created after rollout stores an **availability vector** containing every required entitlement epoch and `(gateKey, routeKey, generation)` launch entry, not only its owning feature. Scanner/outbox paths without a durable queue row create a stamped attempt before acting.
- Final execution is linearized, not protected by a read alone. An `ExecutionAttempt` claims QUEUED→CLAIMED under the same canonical lock protocol used by enable/disable and gate OPEN/CLOSE (tenant-local company entitlement rows sorted by feature key, then global launch-gate rows sorted by `(gateKey,routeKey)`). Gate claims use a concurrency-safe shared lock or equivalent conditional-CAS/serializable guard while OPEN/CLOSE uses the exclusive side, so actions for many tenants do not serialize on one global gate. Under that protocol the claimant performs an uncached read, requires every entitlement epoch to match and every stamped gate to be OPEN at the same generation, and records the claim; a concurrent disable/close therefore either commits first and prevents the claim, or observes the already claimed attempt. Request/job memoization is planning-only. A database final mutation commits with this claim/guard in the same transaction.
- The uncached final guard remains per durable attempt. F0 must record representative volume, p95/p99 claim/lock wait, outbox age, throughput and maximum safe in-flight evidence before any batch claim is implemented. Until that evidence passes, claim one attempt at a time. A later bounded batch may contain only one company and one identical complete availability-vector hash, must persist an individual claim and dispatch token for every item in the same linearized transaction, and must cap batch/in-flight size so CLOSE remains bounded. A guard result may never be reused across a transaction, company, vector, build or generation.
- External I/O uses a durable `DISPATCHING` token/lease as its linearization boundary; never hold database locks across the network. Disable/close prevents any new token. An already committed token is explicitly “in flight”: the close path follows its matrix policy to wait a bounded time or record/handoff it as already dispatched, the worker records the eventual result once, and no retry is permitted under a closed/mismatched generation. Send the durable attempt/token as the provider idempotency key wherever supported. A crash/timeout after dispatch with no authoritative result becomes `UNKNOWN_EXTERNAL_OUTCOME`; poll the provider or require one prefilled manual reconciliation, never blind-retry or claim failure/success. UI/preview reports both in-flight and unknown-outcome counts because an HTTP request already dispatched cannot be unsent.
- At availability-gate enforcement cutover, reconcile every pre-ship NULL-stamped external/legal/final row against a fixed cutoff. Default to terminal/handoff; allow only an enumerated safe internal projection or an explicitly approved Reissue that creates a new current vector. Never back-stamp old work with current epochs/generations, even before the first disable/close.
- Old work ends as `SUPPRESSED_FEATURE_DISABLED`, `SKIPPED_FEATURE_DISABLED`, `SUPPRESSED_LAUNCH_GATE_CLOSED`, `SKIPPED_LAUNCH_GATE_CLOSED`, or an explicit handoff; it never replays automatically. Re-enable/reopen does not revive it: Resume/Reissue creates a new row under the current availability vector.

Gate-close UX says the purchased capability is temporarily unavailable rather than “not purchased.” External/legal mutations never auto-resume after reopen.
