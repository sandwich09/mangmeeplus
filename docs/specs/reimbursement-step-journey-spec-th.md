# Spec: การเบิกจ่ายแบบขั้นตอน (ผู้เบิกกับผู้อนุมัติ รองรับเจ้าของร้านคนเดียว)

วันที่: 19 กันยายน 2569

สถานะ: ออกแบบเสร็จ เจ้าของดูตัวอย่างหน้าจอและยืนยันคำตัดสินกับสมมติฐานทั้งหมดแล้ว 19 กันยายน 2569 พร้อมเริ่ม Phase 1 ของแผน ยังไม่ implement

เอกสารประกอบ: [แผนงาน](../plans/reimbursement-step-journey-plan-th.md), [สถานะงาน](../agent-memory/reimbursement-step-journey.md), [สเปคเบิกจ่ายฉบับหลัก](reimbursement-approval-spec.md), [นโยบายผู้อนุมัติ](reimbursement-approver-routing-policy-spec.md), [journey uplift](reimbursement-journey-uplift-spec.md), [ใบทดแทน บริษัทจ่าย/พนักงานจ่าย](substitute-receipt-company-payer-spec.md), [ตารางสิทธิ์](permission-matrix.md)

## 1. ที่มาและคำตัดสินของเจ้าของ

ผู้ใช้หลักของระบบคือเจ้าของร้านที่ทำทุกอย่างเองบนมือถือ flow เบิกจ่ายเดิมออกแบบสำหรับบริษัทที่มีผู้เบิก ผู้อนุมัติ และฝ่ายการเงินแยกกัน หน้าจอเป็น hub 4 แท็บบวก drawer เจ้าของคนเดียวจึงต้องกดปุ่ม 4 ปุ่มใน 3 แท็บ และลงนามใบเบิก 4 ช่องด้วยชื่อตัวเอง ทั้งที่กฎของระบบอนุญาตให้คนเดียวทำจบอยู่แล้ว

flow ใบรับรองแทนใบเสร็จ (ใบทดแทน) เป็นแบบขั้นตอนบนหน้าเดียว มีโหมด OWNER_SELF ที่ผู้จ่ายกับผู้อนุมัติเป็นคนเดียวกันได้ เจ้าของต้องการให้เบิกจ่ายเป็นแบบเดียวกัน

คำตัดสินของเจ้าของ 19 กันยายน 2569:

| รหัส | คำตัดสิน |
|---|---|
| D1 | ผู้อนุมัติบันทึกจ่ายได้เลย ไม่ต้องส่งต่อให้ฝ่ายการเงิน |
| D2 | ขั้นตรวจการเงินเก็บไว้เป็นสวิตช์ แต่ค่าเริ่มต้นเป็นปิด เพื่อให้คนเดียวทำได้จนจบโดยไม่งง บริษัทที่มีคนเพิ่มค่อยเปิดเอง |
| D3 | ลายเซ็นบนใบเบิกเหลือ 2 ช่อง คือผู้เบิกกับผู้อนุมัติ |
| D4 | ใบทดแทนที่จ่ายด้วยเงินส่วนตัวต้องสร้างคำขอเบิกต่อได้ |
| D5 | LINE อ่านอย่างเดียว และมีลิงก์พาไปกดบนเว็บ |

สมมติฐานที่ผู้ออกแบบเลือก (เจ้าของยืนยันแล้วทุกข้อ 19 กันยายน 2569 มีผลเท่าคำตัดสิน):

| รหัส | สมมติฐาน | เหตุผล |
|---|---|---|
| A1 | นโยบายที่บันทึกไว้แล้วของทุกบริษัทถูกสลับ "ตรวจการเงินก่อนจ่าย" เป็นปิดครั้งเดียวตอน migrate | แถวนโยบายเดิมเกือบทั้งหมดเกิดจากการกดบันทึกหน้าตั้งค่าซึ่งเติมค่าเริ่มต้นเก่า ไม่ใช่การเลือกโดยตั้งใจ ใบที่ค้างอยู่ปลอดภัยเพราะทุกใบ freeze นโยบายไว้ตอนส่ง และบริษัทเปิดกลับได้เองจากสวิตช์ |
| A2 | ผู้อนุมัติได้สิทธิ์ยกเลิกการจ่ายที่ตนบันทึกด้วย ไม่ใช่แค่บันทึก | คนที่บันทึกจ่ายผิดแล้วแก้เองไม่ได้คือทางตัน การยกเลิกยัง audit และยังถูก bank reconciliation/งวดบัญชีบล็อกตามกฎเดิม ถ้าเจ้าของไม่ต้องการให้ผู้จัดการยกเลิกได้ ให้ตัด `reimbursement.payment.void` ออกจาก MANAGER แล้วผู้จัดการที่บันทึกผิดต้องให้เจ้าของยกเลิกให้ |
| A3 | ค่าเริ่มต้น "ส่งใบเบิกให้ใครอนุมัติ" ยังเป็นผู้จัดการ | เมื่อไม่มีผู้จัดการ ระบบตกไปหาเจ้าของกิจการอยู่แล้ว (D8 ของสเปคนโยบาย) ผลลัพธ์สำหรับร้านคนเดียวเท่ากัน จึงไม่แตะ |
| A4 | สำเนาใบเบิกที่เซ็นบนกระดาษครบแล้วซึ่งอัปโหลดเข้าระบบ นับว่าขั้น "เอกสาร" เสร็จ และช่องลงนามทั้งสองแสดงว่า "ลงนามบนกระดาษ" | วันนี้ระบบรับไฟล์แต่ไม่นับว่าลงนาม ช่องยังขึ้น "ยังไม่ลงนาม" ทั้งที่กระดาษเซ็นครบ ใบทดแทนมีเส้นทางเซ็นกระดาษอยู่แล้ว ใบเบิกควรตอบแบบเดียวกันในรูปแบบที่เบากว่า เพราะลายเซ็นไม่เคยเป็นเงื่อนไขของสถานะ (ดู §9) |

A4 เพิ่มจากคำถามของเจ้าของเรื่องอัปโหลดใบที่เซ็นบนกระดาษ ("ระบบยอมรับว่าผ่านไหม") คำตอบของระบบวันนี้คือรับไฟล์แต่ไม่นับว่าลงนาม เจ้าของยืนยันให้เปลี่ยนตาม A4

## 2. เป้าหมาย

- เจ้าของร้านคนเดียวทำคำขอเบิก 1 ใบจบบนหน้าเดียวด้วย 3 ปุ่ม คือ ส่งอนุมัติ → อนุมัติ → บันทึกจ่าย ไม่ต้องสลับแท็บ
- ร้านที่มีลูกน้อง พนักงานเห็นหน้าเดียวกันและรู้ว่าใบอยู่ที่ใคร เจ้าของเปิดจากลิงก์แจ้งเตือนแล้วอนุมัติกับบันทึกจ่ายต่อกันได้
- บริษัทที่มีฝ่ายการเงินเปิดสวิตช์แล้วได้ขั้นตรวจการเงินเพิ่มเข้ามาในหน้าเดิม โดยไม่มีอย่างอื่นเปลี่ยน
- ใบเบิกที่พิมพ์ออกมามีช่องลงนาม 2 ช่อง และบอกข้อเท็จจริงการจ่ายเงินคืนเป็นข้อความ
- ใบทดแทนที่พนักงานจ่ายด้วยเงินส่วนตัว มีปุ่มพาไปสร้างคำขอเบิกโดยยอดและหลักฐานติดไปด้วย

## 3. ขอบเขต

อยู่ในงานนี้:

- หน้า journey ต่อคำขอเบิกหนึ่งใบ แสดงเป็นขั้น พร้อมปุ่มของขั้นปัจจุบันตามสิทธิ์ของผู้ดู
- ค่าเริ่มต้นนโยบายและข้อความหน้าตั้งค่า
- สิทธิ์ผู้อนุมัติบันทึกจ่าย
- ใบเบิกแบบลงนาม 2 ช่อง และการลงนามครั้งเดียวเมื่อผู้เบิกกับผู้อนุมัติเป็นคนเดียวกัน
- จุดเข้าจากใบทดแทนไปสร้างคำขอเบิก
- ลิงก์จากแจ้งเตือน LINE และเมนู LINE ไปหน้า journey และการไม่แจ้งเตือนผู้กระทำเอง
- ปลด drawer รายละเอียดใน hub เมื่อหน้า journey ครอบคลุมทุกการกระทำแล้ว

ไม่อยู่ในงานนี้:

- เปลี่ยน state machine สถานะคำขอ เพิ่มสถานะ หรือเพิ่ม permission key ใหม่
- สร้าง แก้ อนุมัติ หรือบันทึกจ่ายจาก LINE
- รวมปุ่มอนุมัติกับบันทึกจ่ายเป็น endpoint เดียว
- จ่ายบางส่วน ใบสำคัญจ่ายรวมหลายใบ ลงบัญชีอัตโนมัติของใบเบิก
- เปลี่ยนกฎ VAT/WHT ของรายการต้นทาง เลข RB/SRC หรือกฎใบทดแทนที่เซ็นบนกระดาษ
- ตัวเลือกผู้อนุมัติแบบหลายขั้นหรือตามยอด

## 5. โครงขั้นตอน

หน้า journey หนึ่งหน้าต่อคำขอเบิกหนึ่งใบ ขั้นตอนคำนวณจากรายละเอียดใบ (สถานะ, snapshot นโยบาย, step อนุมัติ, การจ่าย, ลายเซ็น) ด้วย pure function ฝั่ง web ไม่มีข้อมูลขั้นตอนเก็บลงฐานข้อมูล

| ลำดับ | ชื่อขั้น | สถานะที่ครอบ | ผู้ทำ | มีเมื่อ |
|---|---|---|---|---|
| 1 | รายการที่จ่ายไป | DRAFT | ผู้เบิก | เสมอ |
| 2 | อนุมัติ | PENDING_APPROVAL, APPROVED ชั่วคราว | ผู้อนุมัติ รวมผู้เบิกเองเมื่อได้รับยกเว้นหรือเปิดสวิตช์ | เสมอ ถ้ายอดต่ำกว่าเกณฑ์ ขั้นนี้แสดงเป็นผ่านอัตโนมัติ "ไม่ต้องอนุมัติตามนโยบาย" |
| 3 | ตรวจการเงิน | FINANCE_REVIEW | ผู้มีสิทธิ์ตรวจการเงิน | เฉพาะเมื่อ snapshot ของใบเปิด `financeReviewRequired` |
| 4 | จ่ายเงินคืน | READY_FOR_PAYMENT, APPROVED ที่รอ projection, PARTIALLY_PAID (legacy) | ผู้มีสิทธิ์บันทึกจ่าย | เสมอ |
| 5 | เอกสาร | PAID | ผู้เบิก ผู้อนุมัติ และผู้มีสิทธิ์แนบสำเนา | เสมอ ไม่เคยเป็นเงื่อนไขของสถานะ |

กติกาของขั้น:

- เลขขั้นนับใหม่ตามจำนวนขั้นที่มีจริง บริษัทที่ปิดตรวจการเงินเห็น 4 ขั้น บริษัทที่เปิดเห็น 5 ขั้น ใบเดิมที่ snapshot เปิดไว้ยังเห็น 5 ขั้นแม้บริษัทปิดสวิตช์ทีหลัง
- ขั้นปัจจุบันคือขั้นที่ `currentDesk()` ชี้ ขั้นก่อนหน้าเป็น "ผ่านแล้ว" ขั้นถัดไปเป็น "ยังไม่ถึง" เหมือน ThemedSteps ของใบทดแทน
- ปฏิเสธ (REJECTED) แสดงขั้น 2 เป็นสถานะต้องแก้ พร้อมเหตุผลและปุ่ม "แก้ไขและส่งใหม่" ซึ่งใช้การเปิดกลับเป็นร่างที่มีอยู่แล้ว ยกเลิก (CANCELLED) และเพิกถอน (VOIDED) จบเส้นทางที่ขั้นที่เกิดเหตุ ไม่มีขั้นถัดไป
- ทุกขั้นแสดงบรรทัด "อยู่ที่ …" ตามกฎ pool กับบุคคลของ Lane G เดิม ไม่แสดงเศษส่วนบนการ์ดรายการ แต่แสดง "ขั้นตอน N จาก M" บนหน้า journey ได้แบบเดียวกับใบทดแทน
- การเปลี่ยนสถานะทุกครั้งยังเดินผ่าน endpoint และ CAS เดิม หน้า journey เพียงโหลดรายละเอียดใหม่แล้วเลื่อนไปขั้นที่เปลี่ยน

ทางเดินของเจ้าของร้านคนเดียวเมื่อใช้ค่าเริ่มต้นใหม่:

```text
ขั้น 1 รายการที่จ่ายไป   → กด "ส่งอนุมัติ"
ขั้น 2 อนุมัติ           → กด "อนุมัติ" (ระบบบันทึกว่าอนุมัติรายการของตนเอง)
ขั้น 4 จ่ายเงินคืน       → กรอกวิธีจ่าย วันที่ อ้างอิง แล้วกด "บันทึกจ่าย"
ขั้น 5 เอกสาร            → ลงนามครั้งเดียว พิมพ์ แนบสำเนาเมื่อต้องการ
```

## 6. ใครเห็นอะไรในแต่ละขั้น

ปุ่มแสดงตามสิทธิ์จริงของผู้ดูและสถานะของใบ เว็บไม่ใช้ชื่อบทบาทตัดสิน API ยังตรวจซ้ำทุกครั้ง

| ขั้น | ผู้เบิก | ผู้อนุมัติ | ผู้ตรวจการเงิน | ผู้มีสิทธิ์บันทึกจ่าย | คนอื่นที่เกี่ยวข้อง |
|---|---|---|---|---|---|
| 1 | แก้ไขรายการ, ส่งอนุมัติ, ยกเลิกคำขอ | อ่าน | อ่าน | อ่าน | อ่าน |
| 2 | เห็น "รอ … อนุมัติ", แก้ไข (เปิดกลับเป็นร่าง), ยกเลิกคำขอ | อนุมัติ, ปฏิเสธพร้อมเหตุผล | อ่าน | อ่าน | อ่าน |
| 3 | เห็น "อยู่ที่ ฝ่ายการเงิน" | อ่าน | อนุมัติจ่าย, ขอข้อมูลเพิ่ม, บล็อกพร้อมเหตุผล | อ่าน | อ่าน |
| 4 | เห็น "รอบันทึกจ่าย" | ถ้าถือสิทธิ์บันทึกจ่ายด้วย เห็นฟอร์มทันทีหลังอนุมัติ | อ่าน | บันทึกจ่าย เต็มจำนวน วิธี วันที่ อ้างอิง | อ่าน |
| 5 | ลงนามช่องผู้เบิก, พิมพ์, แนบสำเนา | ลงนามช่องผู้อนุมัติ, พิมพ์ | พิมพ์, แนบสำเนา | ยกเลิกการจ่าย (ถ้าถือสิทธิ์), พิมพ์, แนบสำเนา | พิมพ์ |

กรณีผู้อนุมัติไม่มีสิทธิ์บันทึกจ่าย (บทบาทกำหนดเองที่ให้เฉพาะ approve) ขั้น 4 แสดง "รอผู้มีสิทธิ์บันทึกจ่าย" และแจ้งเตือน `reimbursement_ready_for_payment` ไปหาผู้ถือสิทธิ์ตามเดิม

กรณีติดรายการซ้ำภายใต้นโยบาย BLOCK_PAYMENT ขั้น 4 แสดงสถานะติดพร้อมเหตุ ผู้บันทึกจ่าย (ซึ่งหลังงานนี้คือผู้อนุมัติ) ปลดได้เองพร้อมเหตุผลและมี audit ผู้ถือ `reimbursement.duplicate.resolve` ยังปลดได้เหมือนเดิม (คำตัดสินเจ้าของ 21 ก.ย. 2569: ใบเบิกมีแค่ผู้เบิกกับผู้อนุมัติ จึงไม่ต้องให้คนที่สามมาปลด) การปลดใช้ endpoint ตรวจการเงินเดิมแบบไม่มีคำตัดสิน ไม่เปลี่ยนสถานะ ส่วนในขั้นตรวจการเงิน (เมื่อบริษัทเปิด) การปลดยังเป็นของผู้ถือ duplicate.resolve ตามเดิม

## 7. นโยบายและค่าเริ่มต้น

- `financeReviewRequired` ค่าเริ่มต้นเป็น false ทั้งใน Prisma, ค่าเริ่มต้นเสมือน (`REIMBURSEMENT_POLICY_DEFAULTS`) และแถวที่บันทึกไว้แล้วตาม A1
- หน้าตั้งค่าใช้ข้อความ:

```text
ตรวจการเงินก่อนจ่าย                                 [ปิด]
เปิดเมื่อมีฝ่ายการเงินแยกจากผู้อนุมัติ ผู้อนุมัติจึงส่งต่อให้การเงินตรวจก่อนจ่าย
```

- ตัวอย่างพฤติกรรม (decision preview) เมื่อปิด:

```text
ยอดตั้งแต่ 1.00 บาท
ผู้จัดการ (ถ้าไม่มี เจ้าของกิจการ) → จ่ายเงินคืน

ยอดต่ำกว่า 1.00 บาท
ไม่ต้องรอผู้อนุมัติ → จ่ายเงินคืน
```

- สวิตช์ "อนุญาตให้อนุมัติใบเบิกของตนเอง" และข้อความกำกับคงเดิม เพิ่มบรรทัดใต้ตัวเลือกผู้อนุมัติ "ถ้ายังไม่มีคนในบทบาทนี้ เจ้าของกิจการเป็นผู้อนุมัติ"
- เกณฑ์ยอด สวิตช์รับใบใหม่ ใบเสร็จ รายการซ้ำ SLA ไม่เปลี่ยน

## 8. สิทธิ์

- ADMIN และ MANAGER ได้ `reimbursement.payment.record` และ `reimbursement.payment.void` เพิ่ม (D1, A2) OWNER มีครบอยู่แล้ว
- `pack.reimbursement.approve` ได้สองคีย์เดียวกันเพิ่ม เพื่อให้บทบาทกำหนดเองที่ประกอบจาก pack นี้จ่ายได้เหมือนบทบาทระบบ
- `reimbursement.finance_review`, `reimbursement.duplicate.resolve`, `reimbursement.policy.manage` ไม่ขยาย (ไม่เพิ่มคีย์ให้บทบาทใด แต่การปลดรายการซ้ำในขั้นจ่ายเงินรับผู้ถือ `reimbursement.payment.record` ด้วย ตาม §6)
- ไม่มี permission key ใหม่ ตารางสิทธิ์อัปเดตบรรทัด ADMIN/MANAGER และบันทึกว่าคำตัดสินเจ้าของ 19 ก.ย. 2569 แทนที่มติทีม 28 ก.ค. 2569 เรื่อง "จ่ายอยู่กับ FINANCE เท่านั้น"
- การยกเว้น self-approval ของ OWNER/ADMIN/MANAGER และ audit "อนุมัติรายการของตนเอง" คงเดิม บทบาทอื่นได้การยกเว้นกรณีเดียวตามคำตัดสินเจ้าของ 21 ก.ย. 2569 ("ผู้ใช้คนเดียวที่กำหนดบทบาทเอง ต้องทำได้นะ"): ตอนส่ง ถ้าไม่มีผู้อนุมัติคนอื่นเลย (ไม่มีผู้ถือบทบาทที่เลือกคนอื่น และไม่มีเจ้าของกิจการที่ดูแลสาขานั้น) และผู้เบิกเองถือบทบาทที่เลือกหรือเป็นผู้อนุมัติที่ระบุชื่อ และดูแลสาขานั้น ใบจะส่งถึงผู้เบิกและผู้เบิกอนุมัติเองได้แม้สวิตช์อนุญาตปิดอยู่ ระบบ freeze ไว้บน step กับ snapshot (`soloSelfApprovalAtSubmission`) และ audit ด้วย `via: 'no_other_approver'` ถ้ามีผู้อนุมัติคนอื่นแม้คนเดียว ใช้กฎเดิม
- หน้า journey เข้าถึงด้วยสิทธิ์อ่านเดิม (`reimbursement.read_related` หรือกว้างกว่า) และเส้นทาง exact-assignment probe ของ D13 ยังใช้กับหน้านี้

## 9. ใบเบิกค่าใช้จ่ายและลายเซ็น

- ใบเบิกพิมพ์ช่องลงนาม 2 ช่อง คือ ผู้เบิก และ ผู้อนุมัติ กว้างช่องละครึ่งหน้า
- ใต้ตารางรายการเพิ่มบรรทัดข้อความ "การจ่ายเงินคืน: จ่ายเมื่อ … วิธี … เลขอ้างอิง … บันทึกโดย …" เมื่อจ่ายแล้ว หรือ "ยังไม่จ่าย" เมื่อยังไม่ถึง ไม่มีช่องลงนามของผู้จ่ายหรือฝ่ายบัญชี
- ใบที่ผ่านอัตโนมัติเพราะยอดต่ำกว่าเกณฑ์ ช่องผู้อนุมัติพิมพ์ "ไม่ต้องอนุมัติตามนโยบาย" ตามเดิม
- ผู้เบิกกับผู้อนุมัติเป็นคนเดียวกัน: ลงนามครั้งเดียวจากหน้า journey ระบบบันทึกลายเซ็นทั้งบทบาท REQUESTER และ APPROVER ด้วยไฟล์เดียวกัน (เว็บอัปโหลดและเรียกลงนามหนึ่งครั้งต่อบทบาทที่ตนมีสิทธิ์ ไม่แก้ endpoint) และใบพิมพ์ข้อความใต้ช่องลงนาม "ผู้เบิกและผู้อนุมัติเป็นบุคคลเดียวกัน อนุมัติรายการของตนเองตามนโยบายบริษัท"
- บทบาทที่เลือกลงนามได้สำหรับใบใหม่มีเฉพาะ REQUESTER และ APPROVER enum 4 ค่าคงไว้เพื่อแถวเก่า
- ความเข้ากันได้: ใบที่มีแถวลายเซ็น FINANCE_REVIEW หรือ PAYER อยู่แล้ว พิมพ์ด้วยผัง 4 ช่องเดิม ใบอื่นทั้งหมดพิมพ์ผัง 2 ช่อง สำเนาที่สแกนกลับยังเป็นบันทึกถาวรตามเดิม
- ลงนามยังต้องรับทราบ hash ปัจจุบันของใบ และยังไม่เป็นเงื่อนไขของสถานะ

เส้นทางเซ็นบนกระดาษ (A4):

- ขั้น "เอกสาร" มีสองทางที่เทียบเท่ากัน: ลงนามในระบบ (2 ช่อง) หรือ พิมพ์ → เซ็นบนกระดาษ → แนบสำเนาที่เซ็นครบ (PDF/JPG/PNG) ทางใดทางหนึ่งทำให้ขั้นเอกสารเสร็จ
- ผู้แนบสำเนาต้องยืนยันคำรับรองหนึ่งข้อก่อนส่ง: "สำเนานี้มีลายเซ็นผู้เบิกและผู้อนุมัติครบ และตรงกับใบเบิกเลขที่ RB-…" ระบบบันทึกผู้แนบ เวลา และ checksum ของไฟล์ลง audit ของการแนบ (การแนบมี audit และเก็บ checksum บน attachment อยู่แล้ว เพิ่มเฉพาะการรับทราบคำรับรอง)
- หลังแนบ หน้า journey แสดงขั้นเอกสารเป็นผ่านพร้อม "ลงนามบนกระดาษ · แนบเมื่อ … โดย …" ช่องผู้เบิกและผู้อนุมัติแสดง "ลงนามบนกระดาษ (ดูสำเนา)" แทน "ยังไม่ลงนาม" และรายละเอียดใบเพิ่ม field เสริม `documentSignedVia: 'DIGITAL' | 'PAPER' | 'BOTH' | null`
- ใบที่พิมพ์จากระบบหลังแนบสำเนายังไม่วาดลายเซ็นจำลอง ช่องลงนามว่างเหมือนเดิม สำเนาที่แนบคือบันทึกฉบับลงนาม (หลักเดียวกับใบทดแทนข้อ R11)
- ระบบไม่พิสูจน์ลายมือชื่อบนกระดาษ ยอมรับตามคำรับรองของผู้แนบและบันทึกว่าใครแนบเมื่อใด ต้นฉบับกระดาษยังต้องเก็บไว้ที่บริษัท ไม่ต้องมีผู้ตรวจรับคนที่สองเหมือนใบทดแทน เพราะการอนุมัติและการจ่ายของใบเบิกถูกบันทึกและ audit ผ่านปุ่มในระบบไปแล้ว สำเนาเป็นหลักฐานเก็บแฟ้ม ไม่ใช่เครื่องมือออกเอกสารหรือสั่งจ่าย
- ผู้แนบได้ตามกฎเดิม: ผู้เบิก หรือผู้ถือ `reimbursement.finance_review` หรือ `reimbursement.payment.record` ซึ่งหลังงานนี้รวมผู้อนุมัติ แนบได้ตั้งแต่ใบมีเลขที่ (หลังส่งอนุมัติ) เพราะร้านส่วนใหญ่เซ็นกระดาษตอนอนุมัติ ไม่ต้องรอจ่ายก่อน
- แนบซ้ำได้ ฉบับล่าสุดคือฉบับที่นับ ฉบับก่อนหน้ายังเปิดดูได้ในประวัติ ไม่มีการลบ

## 10. ใบทดแทนที่พนักงานจ่ายด้วยเงินส่วนตัว → คำขอเบิก

- ขั้น "รับเอกสาร" ของ wizard ใบทดแทน และแถวในหน้ารวมใบทดแทน แสดงปุ่มหลัก "สร้างคำขอเบิกจากใบนี้" เมื่อ status = ISSUED, fundingSource = PERSONAL_ADVANCE, มี `payerUserId` และผู้ดูถือ `reimbursement.create`
- ปุ่มเปิด `/companies/:companyId/reimbursements/new?expenseId=<expenseId>` หน้าสร้างคำขอเลือกรายการต้นทางนั้นเข้าบรรทัดที่ 1 ให้ทันทีโดยใช้ตัวกรอง `expenseId` ของ endpoint ตัวเลือกต้นทางที่มีอยู่ ยอดเป็นยอดสุทธิที่จ่ายจริงและแก้ไม่ได้ตามกฎเดิม
- ถ้ารายการนั้นไม่เข้าเงื่อนไข (ถูกเบิกแล้ว, ผู้จ่ายไม่ตรงผู้เบิก, ต้องตรวจภาษีก่อน ฯลฯ) หน้าสร้างคำขอแสดงเหตุผลจากรหัสเดิมของตัวเลือกต้นทางและยังใช้งานต่อได้ ไม่สร้างร่างเปล่าอัตโนมัติ
- ใบทดแทนที่เซ็นบนกระดาษโดยไม่มีบัญชีผู้สำรองจ่าย ไม่มีปุ่ม และคงข้อความอธิบายเดิม
- ใบทดแทนที่บริษัทจ่ายเต็ม ไม่มีปุ่ม และยังถูกปฏิเสธเป็นต้นทางตามเดิม
- ข้อความขั้น "รับเอกสาร" เปลี่ยนจากบอกว่ายังไม่คืนเงิน เป็นบอกทางไปต่อ: "ใบรับรองระบุว่าคุณจ่ายร้านเต็มจำนวนด้วยเงินส่วนตัว ทำคำขอเบิกต่อได้เลย ยอดและใบรับรองจะติดไปด้วย"
- เมื่อคำขอเบิกจ่ายแล้ว การ project รายจ่ายของบรรทัดและการผูกต้นทางเป็นไปตามกลไกเดิม ไม่เพิ่มการจ่ายซ้ำบนรายจ่ายต้นทาง

## 11. LINE, แจ้งเตือน และลิงก์

- LINE ยังอ่านอย่างเดียว ไม่สร้าง ส่ง อนุมัติ หรือบันทึกจ่ายจากแชต (D5)
- ลิงก์ทุกจุดที่ชี้ไปคำขอเบิกหนึ่งใบ ใช้ `/companies/:companyId/reimbursements/:requestId` ได้แก่ แจ้งเตือนทั้ง 5 แม่แบบ, `WorkflowTask.webDeepLink`, ข้อความท้าย LINE, `sourceWebPath` ของ workflow, และคำตอบของ AI เมื่อถามสถานะใบเบิก
- การ์ดเมนู LINE "รายการรออนุมัติ" ยังเปิดแท็บคิวอนุมัติของ hub (เป็นรายการ) แต่ละแถวพาไปหน้า journey
- ลิงก์เดิม `?tab=…&focus=<id>` และ `?focus=<id>` ยังใช้ได้ โดย hub redirect ไปหน้า journey ของใบนั้น
- ผู้กระทำเหตุการณ์ไม่ได้รับแจ้งเตือนของเหตุการณ์ที่ตนทำ: ผู้ส่งใบไม่ได้รับ "รออนุมัติ" ของใบตัวเอง ผู้บันทึกจ่ายไม่ได้รับ "จ่ายแล้ว" ของใบที่ตนบันทึก เจ้าของร้านคนเดียวยังได้รับแจ้งเตือน SLA และเหตุการณ์ที่คนอื่นทำ
- ข้อยกเว้น "พร้อมจ่าย" (แก้ 1 ต.ค. 2569 แทนกติกาเดิมที่ตัดผู้อนุมัติออก): ผู้อนุมัติที่บันทึกจ่ายได้ต้องได้รับ "พร้อมจ่าย" ของใบที่ตนเพิ่งอนุมัติด้วย เพราะการบันทึกจ่ายเป็นขั้นถัดไปของเขาเอง ข้อความจึงเขียนเป็นงานของผู้อ่าน ("รอคุณบันทึกการจ่ายเงิน") กติกาเดิมทำให้ใบที่อนุมัติแล้วค้างรอจ่ายโดยไม่มีใครได้รับแจ้ง
- ผู้รับแจ้งเตือน "พร้อมจ่าย" คือคนที่ถึงคิวบันทึกจ่าย ไม่ใช่ทุกคนที่ถือสิทธิ์ (คำสั่งเจ้าของ 1 ต.ค. 2569: เจ้าของร้านถือทุกสิทธิ์ จึงถูกแจ้งทุกใบทุกสาขา) เลือกตามลำดับ โดยนับเฉพาะคนที่บันทึกจ่ายใบนั้นได้จริง คือถือ `reimbursement.payment.record` บทบาทยังใช้งาน สาขาของใบอยู่ในขอบเขต และแพ็กเกจยังเปิดสิทธิ์นั้น
  1. ผู้ทำเหตุการณ์ที่ทำให้ใบพร้อมจ่าย เมื่อไม่ใช่ผู้เบิกเอง ได้แก่ผู้อนุมัติ ผู้ตรวจการเงิน หรือคนที่ยื่นใบแทนผู้อื่นสำหรับใบที่ไม่ต้องอนุมัติ
  2. เฉพาะใบที่ไม่ต้องอนุมัติตามนโยบาย: คนที่จะเป็นผู้อนุมัติของใบนั้นตามนโยบาย ยกเว้นผู้เบิก
  3. ถ้าไม่มีใครในสองข้อแรกบันทึกจ่ายได้ แจ้งทุกคนที่บันทึกจ่ายใบนั้นได้ เช่น เจ้าของร้านคนเดียวที่เบิกและอนุมัติเอง ผู้อนุมัติที่ไม่มีสิทธิ์บันทึกจ่าย หรือผู้อนุมัติที่ออกไปแล้ว
- การเตือนเมื่อใบรอจ่ายเกินกำหนดใช้ลำดับเดียวกันจากข้อมูลของใบ: ผู้ตรวจการเงินที่ผ่านใบ ถัดไปคือผู้อนุมัติของรอบล่าสุด ยกเว้นผู้เบิก ถ้าไม่มีใครบันทึกจ่ายได้จึงเตือนทุกคนที่บันทึกจ่ายได้ การเตือนทำงานเฉพาะบริษัทที่ตั้งกำหนดเวลาในนโยบายเบิกจ่าย ไม่มีค่าเริ่มต้น
- กฎแจ้งเตือนอื่นไม่เปลี่ยน

## 12. หน้าจอเว็บ

หน้า journey (`/reimbursements/[requestId]`):

- ส่วนหัว: ลิงก์กลับ, เลขที่ใบ, ป้ายสถานะ, บรรทัด "อยู่ที่ …", ยอดรวม
- แถบขั้นตอน ThemedSteps 4 หรือ 5 ขั้น พร้อม "ขั้นตอน N จาก M"
- การ์ดขั้นปัจจุบัน: คำอธิบายสั้นว่าต้องทำอะไร และปุ่มตามตาราง §6 ปุ่มหลักหนึ่งปุ่ม ปุ่มรองเป็นแบบโปร่ง
- ส่วนถัดลง: ตารางรายการและหลักฐาน, "เส้นทางของใบเบิก" (timeline เดิม), ลายเซ็นและสำเนาที่ลงนาม (เมื่อมีเลขที่ใบ ใช้ได้ตั้งแต่ขั้น 2 ไม่ต้องรอถึงขั้นเอกสาร), ประวัติการจ่าย
- หลังทุกการกระทำ โหลดรายละเอียดใหม่และเลื่อนโฟกัสไปการ์ดขั้นที่เปลี่ยน ปุ่มแสดงสถานะกำลังทำงาน และ toast ตามระบบเดิม
- ออกแบบที่ 390 px ก่อน ปุ่มสูงอย่างน้อย 44 px ฟอร์มบันทึกจ่ายอยู่ในการ์ดขั้น ไม่ใช่ modal บนมือถือ
- สถานะที่ต้องมี: กำลังโหลด, โหลดผิดพลาดพร้อมลองใหม่, ไม่มีสิทธิ์ (ใช้หน้าห้ามเข้าเดิม), ใบไม่พบ, ใบถูกแก้หลังส่ง (stale snapshot) แสดงข้อความเดิม, ใบถูกยกเลิก/เพิกถอนแบบอ่านอย่างเดียว

hub (`/reimbursements`):

- แท็บและรายการคงเดิม แถวรายการเป็นลิงก์ไปหน้า journey ปุ่มด่วนบนแถว (อนุมัติ/ปฏิเสธ) คงไว้ได้สำหรับเดสก์ท็อป
- `?focus=` และ `?tab=…&focus=` redirect ไปหน้า journey
- drawer รายละเอียดถูกปลดเมื่อหน้า journey มีการกระทำครบตาม checklist ในแผน ไม่มีสองหน้ารายละเอียดพร้อมกันหลังจากนั้น

หน้าสร้าง/แก้ไขคำขอ:

- คงฟอร์มตารางบรรทัดเดิม รับ `?expenseId=` เพื่อเลือกต้นทางล่วงหน้า หลังบันทึกร่างพาไปหน้า journey ขั้น 1

หน้าตั้งค่านโยบาย: ตาม §7

คู่มือผู้ใช้: ปรับ "เส้นทางของคำขอ 1 ใบ" เป็น 4 ขั้นบวกขั้นตรวจการเงินแบบมีเงื่อนไข และปรับคำอธิบายบทบาทว่าผู้อนุมัติบันทึกจ่ายได้

## 13. สัญญา API

ไม่มี endpoint ใหม่ การเปลี่ยนแปลงฝั่ง API:

- ค่าเริ่มต้นนโยบาย (§7) และ migration (§14)
- permission registry และ capability pack (§8) ซิงก์ผ่าน release task เดิม
- renderer ใบเบิกและตัวเลือกบทบาทลงนาม (§9) รายละเอียดใบเพิ่ม `claimFormLayout: 'TWO_SIGNERS' | 'LEGACY_FOUR_SIGNERS'` เป็น field เสริมเพื่อให้เว็บแสดงช่องให้ตรงกับใบพิมพ์
- แม่แบบแจ้งเตือนและ runner: path ลิงก์ใหม่ และการตัดผู้กระทำออกจากผู้รับ (§11)
- คำตอบ AI เรื่องสถานะใบเบิก: ลิงก์ใหม่ เนื้อหาอื่นคงเดิม
- error code เดิมทั้งหมดคงความหมาย ไม่เพิ่ม code ใหม่ นอกจากไม่จำเป็นจริง
- ที่เพิ่มระหว่าง implement (21 ก.ย. 2569) ทุกตัวเป็น field เสริม: รายละเอียดใบมี `claimFormLayout`, `documentSignedVia`, `financeReviewRequired` (จาก snapshot ของใบ หรือนโยบายปัจจุบันเมื่อยังเป็นร่าง), `duplicateBlocksPayment`; `approvalActions.selfApprovalBlocked`; สำเนาที่ลงนามมี `acknowledgedAt`, `acknowledgedByName`
- endpoint ตรวจการเงินเดิมรับการเรียกแบบไม่มีคำตัดสินเพื่อปลดรายการซ้ำในขั้นจ่ายเงิน; endpoint เปิดกลับเป็นร่างเดิมรับการดึงกลับของผู้เบิกเมื่อใบรออนุมัติและยังไม่มีใครตัดสิน (state machine อนุญาต PENDING_APPROVAL → DRAFT อยู่แล้ว) ไม่มี endpoint ใหม่
- คำรับรองสำเนากระดาษเก็บใน metadata ของไฟล์แนบที่มีอยู่แล้ว ไม่มีคอลัมน์ใหม่; hash ที่ลงนามรับทราบคำนวณจากข้อเท็จจริงของใบ ไม่รวมผัง การเปลี่ยนเป็นผัง 2 ช่องจึงไม่ทำให้ลายเซ็นเดิมหลุด

## 14. ข้อมูล

- `ReimbursementPolicy.financeReviewRequired` เปลี่ยน default เป็น false และ migration ตั้งแถวเดิมทั้งหมดเป็น false (A1) แบบ idempotent
- ไม่มีตาราง คอลัมน์ enum หรือ index ใหม่
- snapshot ของใบเดิมไม่ถูกแก้

## 15. กรณีขอบ

| กรณี | พฤติกรรม |
|---|---|
| เจ้าของคนเดียวแต่ถือเฉพาะบทบาทกำหนดเองที่ไม่ใช่ OWNER/ADMIN/MANAGER | (คำตัดสินเจ้าของ 21 ก.ย. 2569) บทบาทนั้นเป็นบทบาทผู้อนุมัติที่เลือกไว้ และไม่มีผู้อนุมัติคนอื่น: ใบส่งถึงตัวเองและอนุมัติเองได้โดยไม่ต้องเปิดสวิตช์ (§8) บทบาทนั้นไม่ใช่บทบาทผู้อนุมัติและไม่มีใครอนุมัติได้: ระบบไม่รับส่ง แต่บอกทางไปต่อตรงจุดที่กดส่ง ผู้มีสิทธิ์ตั้งค่านโยบายเห็นลิงก์ไปเลือกผู้อนุมัติ คนอื่นให้ขอเจ้าของกิจการเลือกผู้อนุมัติหรือเพิ่มสิทธิ์อนุมัติให้บทบาท มีผู้อนุมัติคนอื่น: กฎเดิม อนุมัติเองไม่ได้จนกว่าจะเปิดสวิตช์ หน้า journey บอกเหตุและลิงก์ไปหน้าตั้งค่า |
| ผู้อนุมัติกดอนุมัติแล้วยังไม่ได้โอนเงิน | ใบหยุดที่ขั้นจ่ายเงินคืน ปิดหน้าได้ กลับมาบันทึกทีหลัง ไม่มีการจ่ายอัตโนมัติ |
| บริษัทปิดตรวจการเงินหลังมีใบค้างอยู่ที่ขั้นตรวจการเงิน | ใบนั้นยังต้องผ่านขั้นตรวจการเงินตาม snapshot ใบใหม่ไม่มีขั้นนี้ |
| ใบเก่าที่ลงนามครบ 4 ช่องแล้วถูกพิมพ์ใหม่ | พิมพ์ผัง 4 ช่องเดิม |
| ผู้เบิกกับผู้อนุมัติคนเดียวกัน แต่ลงนามไว้ก่อนอนุมัติ | ตอนลงนามมีสิทธิ์เฉพาะผู้เบิก จึงบันทึกช่องเดียว หลังอนุมัติปุ่ม "ลงนามใหม่" เติมช่องผู้อนุมัติได้ด้วยไฟล์ใหม่ |
| ใบทดแทน PERSONAL_ADVANCE ถูกเบิกไปแล้วในใบที่ยังไม่ถูกปฏิเสธ/ยกเลิก | ปุ่มยังแสดง แต่หน้าสร้างคำขอบอก "รายการนี้ถูกเบิกแล้ว" จากรหัส `expense_already_claimed` |
| ใบทดแทนแก้ไขเป็นเวอร์ชันใหม่หลังถูกเบิก | กฎ supersede เดิมปฏิเสธการเปลี่ยนข้อเท็จจริงการเงินเมื่อมีคำขอเบิกใช้งานอยู่ |
| ผู้จัดการอนุมัติของลูกน้อง แต่บริษัทตั้งเส้นทางเป็นเจ้าของ | เส้นทางตัดสินตอนส่ง ผู้จัดการไม่เห็นปุ่มอนุมัติ หน้าบอกว่าอยู่ที่เจ้าของ |
| ยอดต่ำกว่าเกณฑ์อนุมัติ | ขั้น 2 ผ่านอัตโนมัติโดย SYSTEM ตามเดิม ข้ามไปขั้นจ่ายเงินคืน (หรือตรวจการเงินถ้าเปิด) |
| ลิงก์แจ้งเตือนเก่าในกล่องข้อความ LINE | `?focus=` ยัง redirect ไปหน้า journey |
| แนบสำเนากระดาษที่ยังไม่มีลายเซ็นโดยพลาด | คำรับรองก่อนส่งคือด่านของมนุษย์ ระบบไม่ตรวจภาพ แก้ได้ด้วยการแนบฉบับใหม่ ฉบับล่าสุดคือฉบับที่นับ |
| ลงนามในระบบไปแล้วบางช่อง แล้วแนบสำเนากระดาษที่เซ็นครบ | ขั้นเอกสารเสร็จ `documentSignedVia = 'BOTH'` แสดงทั้งสองอย่างในประวัติ ไม่ลบลายเซ็นดิจิทัล |
| แนบสำเนาก่อนจ่ายเงินคืน | อนุญาต ขั้นเอกสารแสดงว่าลงนามแล้วแต่ยังไม่ใช่ขั้นปัจจุบัน เส้นทางยังหยุดที่จ่ายเงินคืนจนกว่าจะบันทึกจ่าย |

| AC13 | ปฏิเสธ ยกเลิก เพิกถอน stale snapshot รายการซ้ำ และไม่มีสิทธิ์ แสดงสถานะที่ถูกต้องบนหน้า journey |
| AC14 | หน้า journey ใช้งานได้ที่ 390 px ปุ่มสูงอย่างน้อย 44 px ไม่มี scroll แนวนอน |
| AC15 | หลังปลด drawer ทุกการกระทำที่ drawer เคยมี ทำได้จากหน้า journey (checklist ในแผน) |
| AC16 | ไม่มี permission key ใหม่ ไม่มีสถานะใหม่ ไม่มีตารางใหม่ และ LINE ไม่มีการเขียนใด ๆ |
| AC17 | แนบสำเนาใบเบิกที่เซ็นบนกระดาษครบพร้อมคำรับรอง ทำให้ขั้นเอกสารเสร็จ ช่องลงนามทั้งสองแสดง "ลงนามบนกระดาษ" audit มี checksum และผู้แนบ ใบที่พิมพ์ใหม่ไม่วาดลายเซ็นจำลอง และการแนบไม่เปลี่ยนสถานะคำขอ |

## 17. การทดสอบ

- Unit API: renderer ใบเบิก (2 ช่อง, บรรทัดจ่ายเงินคืน, คนเดียวกัน, ผ่านอัตโนมัติ, legacy 4 ช่อง), `eligibleClaimSignatureRoles` ให้เฉพาะ 2 บทบาทสำหรับใบใหม่, permission-registry (ADMIN/MANAGER มี payment.record/void), ค่าเริ่มต้นนโยบาย, การตัดผู้กระทำออกจากผู้รับแจ้งเตือน, path ลิงก์ของแม่แบบ
- Unit web: pure function สร้างขั้นตอนจากรายละเอียดใบ (4/5 ขั้น, ขั้นปัจจุบัน, ปฏิเสธ, ยกเลิก, auto-approve), การเลือกต้นทางจาก `?expenseId`, การเลือกบทบาทลงนาม
- Unit API/web: `documentSignedVia` จากลายเซ็นดิจิทัลและสำเนาที่แนบ, คำรับรองบังคับก่อนแนบ, audit metadata มี checksum, renderer ไม่วาดลายเซ็นเมื่อมีเพียงสำเนากระดาษ
- Integration: migration ตั้งค่าแถวเดิม, ส่ง → อนุมัติ → บันทึกจ่ายโดยผู้ใช้เดียวที่เป็น OWNER และที่เป็น MANAGER, ใบทดแทน PERSONAL_ADVANCE → คำขอเบิก → จ่าย ไม่เพิ่ม ExpensePayment ต้นทาง
- E2E: ปรับ `e2e/reimbursements.spec.ts` ให้เดินบนหน้า journey, เพิ่มเส้นทางจากใบทดแทน, ลิงก์ `?focus=` redirect
- Permission: บทบาทกำหนดเองที่มี approve อย่างเดียว เห็น "รอผู้มีสิทธิ์บันทึกจ่าย"
- Browser: 390 px ทุกขั้น และหน้าตั้งค่า
