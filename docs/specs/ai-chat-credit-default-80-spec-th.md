# สเปก: เครดิตแชตเริ่มต้น 80 credit ต่อร้านต่อเดือน

สถานะ: Owner ตัดสินใจ 2026-09-23; รอ implementation และ UAT

มติ Owner 2026-11-08: เครดิตแชตพื้นฐานเปลี่ยนจาก 80 เป็น **50 credit** (`DEFAULT_CHAT_CREDIT_SATANG = 5_000`). เลข 80 ด้านล่างอ่านเป็น 50. รอบที่เขียนยอดไว้แล้วไม่เปลี่ยน; รอบใหม่ได้ 50. ลิงก์เดโม่ค่าเริ่มต้นก็เป็น 50.

มติใหม่ 2026-09-28/29: สำหรับร้านที่ย้ายไปกติกา add-on แล้ว เครดิต AI จากแพ็กเกจเติมตาม **รอบของช่วงที่ชำระของแพ็กเกจ** แทนเดือนปฏิทินไทย (ใช้ `appendPackageInterval`/`billingAnchorDay` แบบ UTC ของ billing แล้วแสดงเวลาไทย; แพ็กรายปีแบ่ง 12 รอบ; ระหว่าง grace ของการต่ออายุด้วย QR รอบใหม่ใช้ได้ตั้งแต่วันครบรอบ) และมีเครดิต AI ที่ซื้อหรือทีมงานเพิ่มให้ อายุ 12 เดือน ตัดหลังยอดจากแพ็กเกจ — ดู [สเปกซื้อเครดิต AI และจำนวนอ่านรูปใบเสร็จเพิ่ม](chat-credit-and-receipt-addons-spec-th.md) §5.1 และ §11. ร้านทดลอง ร้านที่ทีมงานตั้งค่าให้ และร้านที่ไม่มีช่วงที่ชำระ ยังใช้เนื้อหาด้านล่าง (เดือนปฏิทิน) ต่อไปใน V1. Override ของแอดมิน/ดีลและเพดานความปลอดภัยยังมีผล; การนับ `monthlyBudgetSatang` ที่ระบุชัดตอนย้ายตัดสินแล้ว (Q5 ของสเปก add-on, Owner รับค่าเริ่มต้น 2026-09-29): เครดิตต่อรอบ = ค่าที่ resolver เดิมให้ร้านนั้น ณ ต้นรอบ (ดีล/override/cap แชตของ SPLIT/80) และเพดานรวมยังเป็นเพดานความปลอดภัย. ข้อความ “ไม่มีการเติม/ซื้อเพิ่ม” และ “ต่อเดือนปฏิทินไทย” ด้านล่างใช้กับร้าน legacy เท่านั้น. Runtime ของรอบและยอดเพิ่มเติมมีแล้ว (add-on PR C, `ai-credit-cycles.ts`/`ai-credit-ledger.ts`) แต่ไม่มีร้านใดเปลี่ยนจนกว่าเครื่องมือย้าย (PR G) ตั้ง `aiCreditCutoverAt`

## เป้าหมายและความหมาย

- (ร้าน legacy) ร้านทุก tier รวมทั้งแพ็กปกติและดีล มี **เครดิตแชตเริ่มต้น 80 credit ต่อเดือนปฏิทินไทย**; 1 credit ใช้แทนต้นทุน AI ที่มิเตอร์บันทึก 1 บาท (80 credit = 8,000 สตางค์) ไม่ใช่เงินสด เงินที่เติมได้ หรือส่วนลดบิล
- เครดิตนี้ครอบ bucket `CHAT` ที่ `classifyAiUsageRequest` จัดประเภท รวมต้นทุนเลือกเส้นทางและตอบจริงทุก call ของข้อความ ไม่ใช้เพียง tag `line-turn`. รูปที่อ่านเป็นเอกสารและ OCR อยู่ bucket `OCR`; จำนวนใบเสร็จที่อ่านสำเร็จและเพดานเงิน OCR ใช้กติกาแยกที่มีอยู่ ห้ามหักต้นทุน OCR จากเครดิตแชต
- เครดิตคือเพดานหยุดการใช้ ไม่ใช่การจ่ายให้ provider 80 บาททุกเดือน; ไม่มีการโอนยอดที่ไม่ได้ใช้เป็นเงิน คืนเงิน หรือทบเดือน
- บริษัทยังต้องผ่านสิทธิ์แพ็ก, การเปิดใช้ AI, เพดาน AI รวมเพื่อความปลอดภัย, และข้อจำกัดอื่นที่มีอยู่. การแยกเครดิตแชตไม่ใช่การยกเลิกเพดาน OCR/รวม

## ลำดับค่าที่มีผล

1. นโยบาย `SPLIT` ที่ System Admin ตั้งและ audit แล้วคง caps ที่ระบุไว้; ไม่เปลี่ยนบริษัทเหล่านี้อัตโนมัติ
2. ค่า AI พิเศษที่ System Admin ตั้งไว้คงเดิมจริง: `monthlyBudgetSatang` ที่ระบุชัดเป็นทั้งเพดานรวมเดิมและเพดานแชตที่มีผลเหนือ 80/ดีลเซลล์ จนแอดมินยกเลิก override; cap แชตของ `SPLIT` ยังมีผลตามเดิม. ช่อง `chatMonthlyBudgetSatang` ของ `SHARED` เดิมเป็นข้อมูลประกอบที่ไม่ได้บังคับใช้ จึงไม่แปลงค่าเก่าให้เป็น cap ใหม่. ระบบเก่าไม่ได้บันทึก provenance ว่า `monthlyBudgetSatang` มาจากแอดมินหรือดีล v2/v3 จึงต้องคงค่าทั้งสองชนิดตามพฤติกรรมเดิม ไม่เดาสุ่มล้างค่า — **แทนที่ 2026-09-29 (มติ Owner, แท็บผู้ดูแล “เครดิต AI และอ่านรูป”):** เครดิตแชตที่แอดมินตั้งเก็บใน `chatMonthlyBudgetSatang` ของ `SHARED` และ `monthlyBudgetSatang` เป็นเพดานความปลอดภัยอย่างเดียว; migration `20260929200000_admin_chat_credit_explicit` ย้ายค่า override เดิมทุกร้านเป็นเครดิตแชตที่ระบุชัด (ค่าเท่าเดิม และยังชนะดีลเหมือนเดิม) และล้างค่าแชตค้างของ `SHARED` ที่ไม่เคยมีผล; ดีล v2/v3 เขียนและคืนทั้งสองช่องคู่กัน — ดู[สเปก add-on §18.8](chat-credit-and-receipt-addons-spec-th.md)
3. ดีลเซลล์ **รุ่นใหม่** ที่ระบุเครดิตแชตพิเศษใช้ค่านั้นตลอดช่วงสิทธิ์ดีล; ช่องว่างหมายถึง 80 credit; เมื่อดีลสิ้นสุดกลับไปข้อ 1/2 หรือ 80 ตามเดิม
4. ร้านอื่นทุกแห่งใช้ 80 credit ไม่ขึ้นกับ tier, รูปแบบซื้อ, หรือราคาดีล

ค่า `CompanyAiConfiguration.monthlyBudgetSatang` ที่แอดมินเคยตั้งเป็นเพดาน **รวม** ต้องคงค่าและความหมายเดิม. ค่า `AI_MONTHLY_BUDGET_SATANG` เป็นเพดานรวม ไม่ใช่เครดิตแชต; ห้ามเปลี่ยนเป็น 8,000 สตางค์ เพราะ OCR จะชนเพดานผิดส่วน. ร้านที่สมัครใหม่ในระบบปัจจุบันถูกล็อกจนซื้อแพ็ก; การมีค่าเริ่มต้นเครดิตแชตไม่เปิดสิทธิ์ทดลองใช้ฟรีเอง

## ดีลและแพ็ก

- ฟอร์มดีลใหม่แสดงค่าเริ่มต้น **80 credit/เดือน** และระบุชัดว่าปรับได้เฉพาะแชต; ใบเสร็จตามจำนวนที่ขาย. ดีลที่ approved แล้วมี snapshot v2/v3 ต้องอ่านและ apply ตามความหมายเดิมของ `aiMonthlyBudgetSatang` ซึ่งเป็นเพดานรวม; ห้ามแปลงความหมายของ JSON เดิมย้อนหลัง
- Snapshot/quote ใหม่ต้อง pin ว่าเครดิตพิเศษเป็น `CHAT`, ไม่ใช่ total. การ apply ที่จ่ายแล้วเปลี่ยนเฉพาะสิทธิ์แชตของดีล; ไม่ล้างเพดานรวม/สิทธิ์พิเศษที่แอดมินตั้งไว้. ดีลจ่ายครั้งเดียวต้องบันทึกวันสิ้นสุดสิทธิ์จากรอบที่จ่ายและกลับไป 80 credit หลังวันนั้น แม้ร้านซื้อแพ็กใหม่ภายหลัง; ดีลต่ออายุอัตโนมัติคืนค่าเมื่อรอบดีลสิ้นสุด
- อัปเกรดที่จ่ายส่วนต่าง, ซื้อแพ็กเต็มซ้อน และซื้อดีลต่ออายุล่วงหน้า ไม่เติมเครดิต 80 ซ้ำในเดือนปฏิทินเดียวกัน. เมื่อสิทธิ์ดีลเริ่มในอนาคต เครดิตของดีลเริ่มพร้อมดีล ไม่ใช่วันที่เก็บเงินงวดแรก
- การแสดงเครดิตในหน้าลูกค้าและทีมขายใช้หน่วย `credit` พร้อมคำอธิบายสั้นว่าเป็นเครดิตแชตต่อเดือน; ดีลใหม่แสดง 80 หรือจำนวนพิเศษ ส่วนดีลเก่าต้องติดป้ายว่าเป็นเพดาน AI รวม

## การบังคับใช้และข้อมูล

- ค่าเริ่มต้นต้องทำงานกับร้านเดิมและร้านใหม่โดยไม่ต้องเขียนแถว config ให้ทุกร้าน. สำหรับนโยบาย `SHARED` เดิม ให้ตรวจการใช้ `CHAT` จาก aggregate bucket ภายใต้ lease เดือนเดียวกับเพดานรวม; ปฏิเสธ CHAT เมื่อใช้ถึงค่า effective แล้วและส่ง `budgetScope: CHAT`. พฤติกรรมนี้มี overshoot จำกัดเท่าหนึ่งงานที่รับเข้าก่อนรู้ต้นทุน เช่นเดียวกับเพดานรวมเดิม; แสดงยอดใช้จริงและยอดคงเหลือที่ไม่ติดลบ
- ไม่บังคับให้ร้าน `SHARED` ทั้งหมดเปลี่ยนเป็น `SPLIT`: engine แบบ `SPLIT` ต้องมี model ID ต่อร้านและ reservation bounds ที่ผ่าน readiness gate. การบังคับย้ายทุกบริษัทโดยไม่มี model จะทำให้ AI ใช้งานไม่ได้. ร้าน `SPLIT` ใช้การจอง/settle แบบเข้มงวดต่อไป
- ค่าเครดิตดีลใหม่ต้องแยกที่มาจากการตั้งค่าแอดมิน เพื่อคืนค่าเริ่มต้นได้เมื่อดีลจบโดยไม่ล้าง admin override. ข้อมูลดีลเก่าคงความหมายเดิม
- การเปิดใช้กลางเดือนที่ bucket usage เก่าครอบคลุมไม่ครบ ต้องแสดงข้อจำกัดของเดือน rollout และยืนยันค่าจากต้นเดือนถัดไป; ห้ามแปลง tag เป็น CHAT/OCR ด้วยชื่อ tag อย่างเดียว
- เมื่อปฏิเสธด้วย `budgetScope: CHAT` ให้ข้อความบอกขอบเขตแชตและเดือนที่เริ่มใหม่; ห้ามชวนเปลี่ยนแพ็กเพื่อให้ใช้แชตต่อในเดือนเดิม เพราะแพ็กมาตรฐานทุกระดับเริ่มที่ 80 credit และการซื้อ/เปลี่ยนแพ็กไม่เติมเครดิตแชตซ้ำ. ให้ใช้ช่องทางติดต่อทีมงานที่มีอยู่เพื่อตรวจสอบสิทธิ์ดีลพิเศษ. การปฏิเสธแบบ `TOTAL` คงข้อความและการกระทำเดิม
- ข้อความ CHAT refusal ต้องคง `budgetScope` ผ่าน LINE ingress และ ledger reclaim, เพื่อให้ข้อความที่ส่งซ้ำใช้เหตุผลเดียวกับการปฏิเสธครั้งแรก

## เกณฑ์ยอมรับ

1. ร้าน `SHARED` ไม่มี config override: ข้อความต้นทุน CHAT ครบเส้นทางสะสมกับเครดิต 80; OCR ไม่หักเครดิตแชต; ยอด CHAT ถึง cap ปฏิเสธ scope CHAT แต่ OCR ยังผ่านหากสิทธิ์/เพดานอื่นผ่าน
2. `SPLIT` และค่าพิเศษของแอดมินยังเหมือนเดิม; default ไม่เขียนทับแถว config. เพดานรวมยังแยกจากเครดิตแชตและบังคับใช้ต่อ
3. ดีลใหม่ว่าง=80, พิเศษ=ค่าดีลเฉพาะ CHAT; ดีลเก่า v2/v3 ยังคงความหมายเพดานรวม. ดีลล่วงหน้าเริ่มเครดิตตามวันเริ่มสิทธิ์; return ไม่ล้างค่าพิเศษแอดมิน
4. Upgrade/repeat/full-pack ในเดือนเดิมไม่เพิ่มเครดิต 80 อีกครั้ง; quote, billing card, sales form และ admin read สื่อความหมายตรง backend
5. ทดสอบการรับงานชน cap, แยก text/image, เดือนใหม่, concurrent turn, denied/unknown provider, ดีลใหม่/เก่า และแพ็กซ้อน. ห้ามเปิด Production โดยไม่มีผล UAT ตาม release runbook
