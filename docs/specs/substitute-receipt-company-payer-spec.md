# ใบรับรองแทนใบเสร็จ: บริษัทจ่ายเต็ม / พนักงานจ่ายเต็ม

สถานะ: Implement แล้วและตรวจ local พร้อมให้ผู้ใช้ตรวจ 2026-09-09; ยังไม่ deploy

## 1. ขอบเขตล่าสุด — ใช้แทนข้อกำหนดฉบับก่อนของงานนี้

ผู้ใช้ยืนยันว่าให้ทำ **ใบรับรองแทนใบเสร็จรับเงิน** เท่านั้น รองรับบริษัทจ่ายเต็มจำนวน หรือพนักงานหนึ่งคนจ่ายเต็มจำนวน ไม่ขยายไปสร้าง ส่งอนุมัติ หรือลงรายการจ่ายใบเบิกคืน ส่วนขยายใบเบิกที่ทำระหว่างตรวจผลกระทบถูกนำออกจาก implementation นี้แล้ว

ปัญหาในภาพ: ชื่อแสดงผลกิจการปนกับชื่อจดทะเบียน, รายชื่อผู้จ่ายไม่แยกแหล่งเงินกับบุคคลที่ลงนาม, ตำแหน่งต้องพิมพ์เอง และข้อความระบุว่าผู้จ่ายต้องลงนามทำให้กรณีบริษัทจ่ายกำกวม

เป้าหมาย: ระบุข้อเท็จจริงว่าเงินมาจากใคร โดยผู้ลงนามยังเป็นบุคคลจริง ชื่อบริษัทในเอกสารตรงข้อมูลจดทะเบียนที่บันทึกไว้ และการออก/แก้ใบรับรองไม่เพิ่มยอดจ่ายซ้ำ

ไม่อยู่ในรุ่นนี้: จ่ายบางส่วน ทยอยจ่าย บริษัทกับพนักงานร่วมจ่าย หลายพนักงานหารจ่าย เงินทดรอง/เคลียร์เงินทดรอง ระบบใบเบิก/การจ่ายคืนใหม่ การเปลี่ยน VAT/WHT engine และ deploy

## 2. พฤติกรรมหลัก

| ประเด็น | บริษัทจ่ายเต็มจำนวน | พนักงานจ่ายเต็มจำนวน |
|---|---|---|
| fundingSource | COMPANY | PERSONAL_ADVANCE |
| เงินที่ใช้ | ของบริษัทปัจจุบัน | เงินส่วนตัวของพนักงานหนึ่งคน |
| ผู้รับรอง | สมาชิกผู้ดำเนินการจ่ายและทราบข้อเท็จจริง | สมาชิกผู้สำรองจ่ายเอง |
| เอกสาร | ชื่อจดทะเบียนบริษัท + แหล่งเงิน + ชื่อ/ตำแหน่งบุคคล | ชื่อจดทะเบียนบริษัท + แหล่งเงิน + ชื่อ/ตำแหน่งบุคคล |
| ผลการออก | คงพฤติกรรมบันทึกบริษัทจ่ายเต็ม โดยเพิ่มได้ครั้งเดียว | ไม่สร้าง ExpensePayment และไม่ทำเครื่องหมายว่าบริษัทจ่ายคืนแล้ว |
| เมื่อออกเสร็จ | เปิดดู/ดาวน์โหลด/ดูรายการต้นทาง | เปิดดู/ดาวน์โหลด/ดูรายการต้นทาง ไม่มีปุ่มพาไปสร้างใบเบิก |

ทั้งสองกรณีต้องเลือกเอง ไม่มี default และยืนยันว่าจ่ายเต็มจากแหล่งเดียวแล้ว ข้อมูลวิธีจ่าย วันที่ ผู้รับเงิน ยอดรวม WHT และยอดสุทธิเป็นข้อเท็จจริงของรายการ ไม่ใช่วันออกเอกสาร

กรณี COMPANY: ถ้าบันทึกจ่ายไว้ 0 และจ่ายจริงเต็มแล้ว ให้ออกใบรับรองพร้อมบันทึกเต็มยอดสุทธิครั้งเดียว ถ้าบันทึกเต็มแล้วไม่เพิ่ม ถ้ามี 40/100 ต้องปฏิเสธโดยคงยอด 40 ไม่เติมอีก 60 ผ่านใบรับรอง ใช้ Decimal/ความคลาดเคลื่อนที่ระบบเดิมกำหนดและ fingerprint รูปแบบเดิม

กรณี PERSONAL: ใบรับรองยังไม่ใช่หลักฐานว่าบริษัทคืนเงินแล้ว ห้ามปุ่มบันทึกจ่ายร้านหรือ ordinary confirm ของต้นทางพาไปบันทึกผิดบัญชี การคืนเงินเป็นขั้นตอนการเงินแยกและอยู่นอกงานนี้

## 3. UX และสิทธิ์

- ขั้นข้อมูลมีตัวเลือกแหล่งเงินสองรายการ แสดงชื่อบริษัทจริง และเลือกบุคคลผู้รับรองแยกกัน
- แสดงยอดรวม WHT สุทธิจ่ายร้าน และผลต่อยอดบริษัทก่อนยืนยัน โดยไม่มีช่องแบ่งยอด
- ใช้ชื่อจดทะเบียน `registeredName.trim()` ก่อนชื่อแสดงผล ถ้าไม่มีให้แจ้ง fallback และมีโหลดข้อมูลล่าสุดหลังแก้ข้อมูลบริษัท ไม่ hardcode ชื่อจากภาพ
- ตำแหน่งเป็น optional ทั้งผู้รับรองและผู้อนุมัติ ไม่บล็อกการตรวจเอกสารหรือลงนามเมื่อเว้นว่าง ใช้ ThemedSelect เดิม: jobTitle ของผู้ใช้เอง + ตัวเลือกทั่วไป + ระบุเอง สูงสุด 120 ตัวอักษร ไม่โหลดรายชื่อ HR และไม่เพิ่มสิทธิ์ HR
- ตำแหน่งที่เลือกพิมพ์ตามตัวอักษรใน snapshot schema 2 ไม่ตีความเป็น role code โดยอัตโนมัติ
- เปลี่ยนผู้จ่าย/แหล่งเงิน/ตำแหน่ง/เวอร์ชันต้องทำให้ preview และ acknowledgement เก่าหมดอายุ รวม callback ที่กลับมาช้า
- ใช้ทั้ง wizard และหน้าตรวจค่าใช้จ่ายเดิม หน้า list/history แสดงแหล่งเงินและคนลงนามชัดเจน
- คง tenant/branch/member, ลายเซ็นส่วนตัว, OWNER_SELF และ DESIGNATED_APPROVERS ตามระบบเดิม บริษัทไม่ใช่บัญชีผู้ลงนาม
- LINE ถามแหล่งเงินเมื่อไม่ชัด ข้อความ “ฉันเป็นผู้จ่าย” ไม่เท่ากับจ่ายด้วยเงินส่วนตัว ต้องยืนยันจ่ายเต็มชัดเจน ข้อความแบ่งจ่าย/แหล่งเงินขัดกันทำให้ต้องตรวจใหม่ การลงนามยังอยู่บนเว็บ

### ผู้จัดทำและผู้รับรองการจ่าย (local UX review 2026-09-09)

- ผู้มีสิทธิ์จัดทำเลือกสมาชิกในบริษัท/สาขาเป็นผู้รับรองได้ ไม่จำเป็นต้องเป็นผู้จัดทำเอง ร่างใหม่ไม่เลือกผู้จัดทำหรือสมาชิกคนแรกให้อัตโนมัติ; คงค่าที่ผู้ใช้เคยเลือกหรือยืนยันผ่าน LINE ไว้เมื่อยังมีสิทธิ์
- ใช้ชื่อช่อง “ผู้รับรองการจ่าย” และอธิบายตามแหล่งเงิน: บริษัทจ่าย = ผู้ดำเนินการจ่ายและทราบข้อเท็จจริง; พนักงานจ่าย = ผู้ที่สำรองเงินส่วนตัวเอง ผู้ที่เลือกต้องลงนามด้วยบัญชีของตนเอง
- หน้าลงนาม/รอลงนามแสดงชื่อผู้รับรองและทาง “เปลี่ยนผู้รับรองการจ่าย” สำหรับผู้มีสิทธิ์จัดทำ เมื่อเอกสารยังไม่ออกและสถานะรายการอนุญาต โดยเปิดส่วนยกเลิกเวอร์ชันพร้อมโฟกัสเหตุผล ไม่ยกเลิกเอกสารเพียงเพราะกดทางลัด
- ใช้ API ยกเลิกพร้อมเหตุผล/version check เดิม แล้วจัดทำฉบับแก้ไขและเลือกคนใหม่อย่างชัดเจน คงประวัติเดิมและต้องตรวจ/ลงนามใหม่; ไม่เปิดเปลี่ยนตัวบุคคลผ่านการแก้เฉพาะชื่อบริษัท/ตำแหน่งของเอกสารที่ออกแล้ว
- Snapshot ใหม่ระบุชื่อบทบาท “ผู้รับรองการจ่าย” สำหรับเอกสาร; snapshot เก่าคงป้ายเดิมเพื่อรักษาการแสดงผลย้อนหลัง ไม่แก้ไฟล์เอกสารที่ออกแล้ว

### ลำดับตรวจเอกสารก่อนลงนาม (local UX review 2026-09-09)

ทั้งผู้รับรองและผู้อนุมัติใช้ลำดับ ตำแหน่ง → เตรียมลายเซ็น → ตรวจเอกสาร → คำรับรองและปุ่มยืนยัน โดยวางการตรวจเป็นขั้นสุดท้ายของการเตรียมข้อมูล ให้ปุ่มตรวจเด่นเมื่อยังไม่เปิดตรวจ และเรียงรายการที่ยังขาดตามลำดับหน้าจอ ใช้ลำดับเดียวกันในหน้าตรวจค่าใช้จ่ายเดิมด้วย

คง gate เดิม: preview ต้องโหลดสำเร็จ ผู้ลงนามต้องเตรียมข้อมูล/ลายเซ็น/คำรับรองครบ และ API ตรวจ version/checksum ตามเดิม การโหลดเอกสารไม่ได้พิสูจน์ว่าอ่านครบแล้ว; คำรับรองยังเป็นการยืนยันของบุคคล เปลี่ยนตำแหน่งต้องตรวจใหม่ ไม่ทำ auto-pass หลังย้าย UI

## 4. Snapshot และแก้เอกสาร

Preview ที่ตรวจ checksum แล้วเป็น business snapshot ชุดเดียวกับที่นำไป certify เปลี่ยนได้เฉพาะเวลาลงนาม ห้ามอ่านชื่อบริษัทอีกครั้งแล้วนำข้อมูลคนละชุดมาเก็บภายใต้ checksum เดิม

ตรวจ expense revision/status ใน transaction ตอน certify และ issue ควบคู่กับ evidence revision และไฟล์/ลายเซ็นที่ยัง active การเปลี่ยนชื่อก่อนตรวจใหม่ต้องดู preview ใหม่ แต่การเปลี่ยน profile ภายหลังต้องไม่แก้ signed bytes/history เดิม

คำสั่ง `correct-document` สร้างเวอร์ชันใหม่เพื่อแก้ชื่อบริษัท/ตำแหน่งของตัวตนเดิม โดยรักษา TIN ผู้รับเงิน แหล่งเงิน ผู้จ่าย วันที่ วิธีจ่าย ยอด และหลักฐานเดิม รองรับเอกสารที่ลงบัญชีหรือจ่ายแล้ว ไม่ย้อน payment/JV ไม่เรียก settlement ซ้ำ ผู้จ่าย/ผู้อนุมัติเดิมต้องลงนามภายใต้สิทธิ์ปัจจุบัน

ต้นฉบับยัง ISSUED ระหว่างรอฉบับแก้ ยกเลิกร่างแก้ได้แล้วเริ่มใหม่ได้ retry ต้องได้ pending version เดิม เมื่อออกฉบับใหม่แล้วจึง supersede ฉบับเก่าโดยรักษา bytes/hash เดิม Export มีชื่อบริษัทตาม snapshot แหล่งเงิน ผู้รับรอง และสายเอกสาร/ไฟล์ที่แก้ไข

Supersede เอกสารทั่วไปไม่ void payment และไม่ reset ยอด หากมีคำขอเบิกที่ใช้งานอยู่ ให้ปฏิเสธการเปลี่ยนข้อเท็จจริงการเงินของใบรับรอง คำสั่งแก้เอกสารอย่างเดียวไม่ใช่คำสั่งแก้ยอดหรือคืนเงิน

## 5. ข้อมูลและสัญญา API

- Evidence เพิ่ม nullable enum `fundingSource`; null คือ legacy เท่านั้น ไม่ backfill เดาว่าเป็นเงินส่วนตัว
- เพิ่ม nullable `correctionOfEvidenceId`/`correctionReason` ที่ evidence
- Prepare ใหม่บังคับ `fundingSource` และ `paidInFullAcknowledged: true`; ค่าไม่ครบ/ผิดต้องคืน error ที่แก้ได้
- Runtime policy เพิ่มชื่อบริษัท/name source และ jobTitle ของผู้เรียกเอง
- เพิ่ม POST `expenses/:expenseId/substitute-receipt/:evidenceId/correct-document` ใช้ permission expense.review และ expectedEvidenceUpdatedAt
- ใช้ locks ของใบรับรอง/หลักฐานที่มีอยู่ในลำดับคงที่; duplicate payment key อยู่ใน namespace ใบรับรอง
- ไม่เพิ่ม column, API, หน้าจอ หรือ workflow ของ Reimbursement ในงานนี้

### เลขที่อ้างอิงเดือนที่จ่ายเงิน (2026-09-10)

เลขที่จองใหม่ใช้ปี ค.ศ. และเดือนจากวันที่จ่ายเงินตามวันปฏิทินกรุงเทพฯ ในรูปแบบเดิม `SRC-{YYYY}{MM}-{SEQ}` เช่น จ่าย 22 ส.ค. 2569 แต่จัดทำเดือนกันยายน ต้องได้ `SRC-202608-…` ใช้ตัวรันเลขกลางเดิมของบริษัทและเดือนนั้น ครอบคลุมเว็บ/LINE ออนไลน์/กระดาษ บริษัทจ่าย/พนักงานจ่าย รวมฉบับแก้ไขที่คงวันที่จ่ายเดิม การ retry คืนเลขเดิม ไม่จองซ้ำ ไม่มีวันที่จ่ายที่ถูกต้องให้ปฏิเสธก่อนจองเลขใหม่ ไม่เปลี่ยนเลขที่เคยจองหรือออกแล้ว ไม่แก้เอกสารลงนามย้อนหลัง และไม่เปลี่ยนวันที่รายจ่าย วันสร้าง วันลงนาม หรือยอดเงินจริง

## 6. บัญชี ภาษี และขอบเขตผลกระทบ

ใบรับรองเป็นหลักฐานประกอบรายจ่าย ไม่ใช่ใบกำกับภาษี ไม่ทำให้ VAT ซื้อใช้สิทธิได้ หรือ CIT/WHT ผ่านโดยอัตโนมัติ คง SUPPORTING_ONLY/NON_CLAIMABLE ตาม flow ใบรับรองเดิม และคงการตรวจเอกสาร/ยอด/วัน/สิทธิ์ตามเดิม

สิ่งที่ตรวจพบรอบระบบใบเบิก เช่น paid source ถูกใช้ซ้ำ, การสูญเสีย seller/version/hash และ generic VAT mapper เป็นข้อค้นพบที่บันทึกไว้สำหรับงานแยก ไม่ถือว่าแก้แล้วในงานนี้ และไม่ใช้เป็นเหตุขยายใบรับรองไปสร้างหรือจ่ายใบเบิก

เอกสารภาพจริงยังไม่ได้ตรวจข้อมูล live หรือ serving build จึงไม่สรุปว่าชื่อผิดในภาพเกิดจากสาเหตุใดโดยแน่ชัด การแก้นี้อ้างอิง bug snapshot ที่ทำซ้ำได้และชื่อจาก profile ที่บันทึกจริง
