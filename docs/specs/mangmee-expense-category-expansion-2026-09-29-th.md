## 0. คำตอบสั้น

**เสียคุณค่าไปบางส่วน:**

- **ช่องว่างใหญ่ที่สุดคือไม่มีหมวด "วัตถุดิบและสินค้าเพื่อขาย"** ซึ่งเป็นรายจ่ายก้อนใหญ่ที่สุดของคาเฟ่ ร้านอาหาร ซาลอน และร้านค้าปลีก
  - ตั้งแต่ #911 และ #914 (ขึ้น production แล้วใน release 2026-09-30) AI ใส่หมวดให้รายการจาก LINE และ PDF เองเมื่อมั่นใจ แต่ไม่เลือกหมวดเบ็ดเตล็ด
  - ใบเสร็จวัตถุดิบจึงไม่มีหมวดและรอคนเลือก หรืออาจไปอยู่หมวดที่ใกล้แต่ผิด เช่น ค่าอาหารและเครื่องดื่ม ถ้าคนเลือกเองก็มักไปรวมที่ "ค่าใช้จ่ายเบ็ดเตล็ด" (ชุดทดสอบในแผน §5 วัดสัดส่วนนี้)
  - การแยกยอด การเทียบเดือน และคำแนะนำของน้องมั่งมีจึงไม่เห็นก้อนนี้
- **รองลงมาคือหมวดที่รวมกันเกินไป:** น้ำมันรวมอยู่ในค่าเดินทาง ส่วนไฟฟ้า ประปา และโทรศัพท์รวมอยู่ในสาธารณูปโภค

**แต่ชุดเดิมไม่ได้น้อยโดยบังเอิญ:**

- ชุด V1 ตัดตาม **พฤติกรรมภาษี** (ภาษีซื้อเคลมได้หรือไม่ และอัตราหัก ณ ที่จ่าย) เพื่อไม่ให้ร้านเคลมภาษีผิด
- การเพิ่มหมวดมีต้นทุนสามข้อ:
  - AI เลือกยากขึ้น
  - ผู้ใช้ต้องเลือกจากรายการยาวขึ้น
  - หนึ่งหมวดผูกได้แค่หนึ่งบัญชี
- ข้อเสนอนี้จึงเพิ่มหมวดเฉพาะเมื่อ **บันทึกบัญชีหรือภาษีต่างจากหมวดเดิม** หรือ **ให้ข้อมูลเชิงลึกคุ้มพอ** ตามกติกาเดิมของ template และแยกชุดตามประเภทธุรกิจเป็นตัวเลือก

**มติ Owner 2026-09-30 (§9):**

- **เพิ่มชุด ก 6 หมวดให้ทุกร้านอัตโนมัติ** (ข้อ 1, 3): น้ำมัน ไฟฟ้า ประปา โทรศัพท์และอินเทอร์เน็ต อุปกรณ์ราคาต่ำ และค่าปรับ
  - ทั้ง 6 หมวดไม่ตั้งภาษีใหม่ คือใช้ Tax Code เริ่มต้นแบบเดียวกับหมวด V1 ที่ใช้อยู่แล้ว หรือเว้นว่าง และผูกบัญชีค่าใช้จ่ายที่มีในผัง จึงไม่ต้องรอนักบัญชี
  - ร้านเดิมได้หมวดผ่าน migration ใน release ซึ่งข้ามร้านรุ่นก่อน bootstrap และหมวดที่ชื่อหรือความหมายซ้ำกับของร้าน
- **วัตถุดิบ (B1) เลื่อนออกไปก่อน** หลัง Owner อ่านความเสี่ยงเรื่องบัญชีต้นทุน (ข้อ 4, เหตุผลใน §3)
- **หมวดที่ต้องรอนักบัญชีไม่เพิ่มเข้าระบบ** (ข้อ 1, 2, 5, 8): ชุด ข และชุดตามประเภทธุรกิจ
  - เตรียมข้อมูลไว้ในตารางสำหรับนักบัญชี (แผน ภาคผนวก ข) และยังไม่ระบุตัวนักบัญชี
  - ร้านเพิ่มหมวดเหล่านี้เองได้บนเว็บ หมวดที่ร้านตั้งเองไม่ผูกบัญชี ซึ่ง Owner รับได้ และ AI เลือกหมวดของร้านได้ตามชื่อ
- **หัก ณ ที่จ่ายไม่ผูกกับหมวด** (ข้อ 6): ตัดสินรายใบและแก้ได้เหมือนเดิม
- **ต้องแก้จุดเหล่านี้ก่อนหรือพร้อมการเพิ่มหมวด** ไม่อย่างนั้น AI จะเลือกพลาดมากขึ้นเมื่อรายการยาวขึ้น (§1.5, §6):
  - ตัวอ่านรูปและตัวจัดเส้นทางต้องเห็นหมวดเป็นรหัสสั้น แบบที่ PDF ใช้แล้ว
  - ส่งคำใบ้สั้นของแต่ละหมวดให้ AI
  - เครื่องมืออ่านรายจ่ายต้องบอกชื่อหมวดครบเมื่อหาหมวดจากคำที่ผู้ใช้พิมพ์ไม่เจอ
  - ระบบเลิกเสนอหมวดเบ็ดเตล็ดให้ AI ที่อ่านรูปบนเว็บ เหมือน LINE และ PDF (ข้อ 10)
- **ขนาดของขอบเขตตอนนี้ประมาณ 3–4.5 วันทำงาน** + ค่าทดสอบกับโมเดลจริงประมาณ 420 บาท ภายในเพดาน 600 บาทที่ Owner อนุมัติ (ข้อ 12, แผน §13)
- **ไม่ตั้งเกณฑ์ราคาสินทรัพย์และไม่มีคำเตือน** (ข้อ 7): คนตัดสินเองว่าของชิ้นไหนเป็นสินทรัพย์
- **ไม่จัดหมวดย้อนหลังให้รายการเก่า** (ข้อ 11)
- **ทุกข้อใน §9 ตัดสินแล้ว**

### 1.3 ข้อเท็จจริงอื่นที่กำหนดขอบเขตข้อเสนอ

- **ร้านเพิ่มหมวดเองได้บนเว็บ** ที่หน้า "หมวดหมู่ค่าใช้จ่าย" (`CategoryManagePanel`, `ExpensesWorkspacePanels.tsx:92`, เมนูย่อย `expenses.categories`)
  - ต้องมีสิทธิ์ `expense.category.manage` ซึ่ง OWNER, ADMIN และ FINANCE ถือ (route `expense.controller.ts:619-652`)
  - ระบบสร้าง `accountHintKey` ให้เป็น `expense.custom.<เวลา>` (`ExpensesWorkspacePanels.tsx:154`) และให้เลือก Tax Code เริ่มต้นได้
  - หมวดที่ร้านสร้างเองได้ `sortOrder` 0 (`prisma-expense.repository.ts:3294-3297`) จึงขึ้นก่อนหมวดจาก template ในทุกรายการ
  - API แก้ชื่อและ `accountHintKey` ได้ (`packages/contracts/src/expenses.ts:1060-1073`) แต่หน้าเว็บส่งแค่ชื่อ Tax Code และสถานะ
  - **หมวดที่ร้านสร้างเองไม่มีการผูกบัญชี** จึงลงบัญชีเป็น `expense_account_unmapped` (`expense-account-binding.logic.ts:46-54`) จนกว่าจะมีผู้ถือ `ledger.posting-rule.manage` มาผูกผ่าน API ซึ่งไม่มีหน้าจอ (มติปิดหน้าบัญชีต่อผู้ใช้ 2026-08-09)
- **การผูกบัญชีรับเฉพาะบัญชีของบริษัทที่ active ลงรายการได้ และไม่ใช่บัญชีคุม ไม่ได้จำกัดชนิดบัญชี** — **ตรวจแล้ว** (`expense-account-binding.use-case.ts:58`, `resolveExpenseDebits` `expense-account-binding.logic.ts:39-76`)
  - แต่ spec ของ template เองบังคับทุกแถวให้เป็นบัญชีชนิด EXPENSE (`expense-category-bootstrap.service.spec.ts:33-42`) หมวดวัตถุดิบที่ผูก 5130-01 (COST) จึงต้องแก้ spec นี้อย่างตั้งใจ (§3, แผน C2)
  - การลงบัญชีแยกตามหมวดของแต่ละบรรทัด บรรทัดที่ไม่มีหมวดใช้หมวดที่หัวรายการ (`journal.use-case.ts:185`)
- **การลงบัญชีอัตโนมัติปิดเป็นค่าเริ่มต้น** — **ตรวจแล้ว**
  - `expense_auto_post` ไม่อยู่ในฟีเจอร์ที่เปิดตอนสร้างร้าน (`feature-registry.ts:21-27`) รายจ่ายที่ยืนยันแล้วจึงค้าง `pending`
  - เมื่อเปิด worker (`expense-auto-post.use-case.ts`) จะลงบัญชีตามการผูกบัญชีของหมวด ณ ตอนลง ไม่ใช่ ณ ตอนบันทึก
  - ร้านบน production เปิดข้อนี้หรือไม่ — **ต้องตรวจสอบ** ก่อนเพิ่ม B1 ภายหลัง (แผน ภาคผนวก ก.1) ส่วนรายงานกำไรขั้นต้นที่อ่านบัญชี COST — **ต้องตรวจสอบ** (โมดูลรายงานไม่อยู่ในแพ็กเกจที่ขาย)

### 1.5 ข้อจำกัดที่พบตอนตรวจ (มีผลกับการเพิ่มหมวด)

1. **รายการหมวดเกิน 100 หมวด → gateway ไม่ส่งหมวดให้โมเดลเลย** ไม่ใช่ตัดบางส่วน (`MAX_RECEIPT_CATEGORY_CATALOGUE`, `line-ai-internal.controller.ts:57`, `:1292-1303`) และชื่อที่ยาวเกิน 120 ตัวอักษรถูกตัด
2. **เครื่องมืออ่านรายจ่ายบอกได้แค่ 10 ชื่อแรกเมื่อหาหมวดจาก `categoryName` ไม่เจอ** (`NAME_MATCH_DISPLAY_LIMIT`, `business-read-source.logic.ts:112`)
   - ลูกค้าเห็นรายการนี้ตรง ๆ ในคำตอบ "ไม่พบหมวด … หมวดที่มี เช่น …" (`business-read-result-semantics.ts:140-142`)

   - ชื่อที่ซ้อนกันทำให้กำกวม เช่น "ค่าน้ำ" อยู่ทั้งใน "ค่าน้ำมันเชื้อเพลิง" และ "ค่าน้ำประปา" ระบบจะถามกลับ ซึ่งยอมรับได้
   - คำถาม "ค่าวัตถุดิบเดือนนี้" หาหมวดชื่อ "วัตถุดิบและสินค้าเพื่อขาย" ไม่เจอ เพราะชื่อไม่ขึ้นต้นด้วย "ค่า" ชื่อใหม่ใน §3 จึงขึ้นต้นด้วย "ค่า" ทุกหมวด

## 2. หลักการของข้อเสนอ

1. **แยกเมื่อบันทึกต่างกัน รวมเมื่อบันทึกเหมือนกัน** (กติกาของ V1) เว้นแต่การแยกให้ข้อมูลเชิงลึกคุ้มชัดเจน ทุกแถวในตาราง §3–§4 เขียนเหตุผลและสิ่งที่ต้องแลกไว้
2. **หนึ่งหมวดผูกหนึ่งบัญชี:** ถ้าผังไม่มีบัญชีที่ตรง ให้เขียนตรง ๆ ว่า **ต้องตรวจสอบ** และเสนอทางเลือก ไม่เดาบัญชี
3. **Tax Code เริ่มต้นเป็นแค่คำแนะนำ:** ถ้าภาษีขึ้นกับรายละเอียดที่หมวดรู้ไม่ได้ (เช่น ชนิดรถ) ให้เว้นว่างเพื่อให้คนเลือก ตามแบบของ V1
4. **ไม่ลบหรือเปลี่ยนชื่อหมวด V1** เพราะประวัติรายการและรายงานเดิมอ้างชื่อเหล่านี้
5. **ไม่มีสวิตช์:** ชุดใหม่เป็นข้อมูลที่เปิดเสมอ ชุดตามประเภทธุรกิจเป็นการเลือกข้อมูล ไม่ใช่ feature flag
6. **นักบัญชีไทยตรวจตารางภาษี:** ค่าเริ่มต้นมีผลกับการยื่นภาษีของร้าน ข้อกฎหมายที่อ้างเป็น "ตามที่ทราบ"
   - มติ Owner 2026-09-30: หมวดที่ต้องรอนักบัญชี (B1, ชุด ข และชุดตามประเภทธุรกิจ) **ไม่เพิ่มเข้าระบบ** เตรียมข้อมูลไว้ให้นักบัญชีเท่านั้น (แผน ภาคผนวก ข) และร้านเพิ่มเองได้
   - ชุด ก ไม่ต้องรอนักบัญชีตามหลักข้อ 7 (Owner อนุมัติ §9 ข้อ 1) ถ้านักบัญชีแก้ภายหลัง ให้แก้ด้วย migration (แผน ภาคผนวก ก.4)
   - ข้อนี้เปลี่ยนจากฉบับแรกที่ให้ตรวจทั้งตารางก่อนเปิดใช้
7. **แบ่งหมวดใหม่ตามความชัดของภาษี:**
   - **ชุด ก:** Tax Code เริ่มต้นเหมือนหมวด V1 ที่ใช้อยู่แล้วหรือเว้นว่าง ไม่มีภาษีใหม่ที่ต้องตัดสิน และบัญชีมีชื่อตรงในผังหรือเป็นบัญชีเดียวกับหมวด V1 (6 หมวดที่ Owner อนุมัติ)
   - **ชุด ข:** ภาษีหรือบัญชีขึ้นกับรายละเอียดที่หมวดรู้ไม่ได้
   - **B1** ผูกบัญชีต้นทุนซึ่งต่างจากทุกหมวด จึงเลื่อนออกไปตามมติ §9 ข้อ 4

  - การถามตอนสมัครแตะ flow สมัครผ่าน LINE ที่เพิ่งเปิดขาย และร้านตอบได้แม่นขึ้นหลังใช้งานไปแล้ว
- **ไม่ผูกกับ `Company.businessCategory`:** field นั้นเป็นตัวเตือน PDPA ของธุรกิจเกี่ยวกับสุขภาพ (RETAIL, TRADING, SERVICE, CLINIC, WELLNESS_SPA, MEDICAL_RETAIL, OTHER) และไม่มีค่าของร้านอาหาร การแก้ field นั้นเพื่อเลือกหมวดเสี่ยงไปกระทบการเตือน
- **ไม่เก็บว่าร้านเลือกชุดไหน:** หมวดที่เพิ่มแล้วคือสถานะเดียวที่ต้องมี (YAGNI) ตัดสินใน §9 ข้อ 2

## 5. ร้านที่มีอยู่แล้ว

### 5.1 ทางเลือก

- เป็นการเพิ่มอย่างเดียว ไม่ลบหรือย้ายของเดิม และตรงกับที่ Owner อยากให้ AI เลือกเอง

### 5.2 กลไก

- **ร้านใหม่:** เพิ่ม `TH_SME_EXPENSE_CATEGORIES_V2` ประกอบด้วยแถว V1 เดิมทั้งหมดในลำดับเดิมบวกชุด ก 6 หมวด และเปลี่ยน `EXPENSE_CATEGORY_TEMPLATE_KEY` เป็น `TH_SME_EXPENSE_CATEGORIES_V2` เพื่อให้ audit ของการเปิดร้านบอกชุดที่ได้จริง
  - `bootstrapCompanyExpenseCategories` เดิมใช้ V2 โดยไม่ต้องแก้ onboarding
- **ร้านที่มีอยู่แล้ว** (SQL migration ใน release ตามมติ §9 ข้อ 3 แทนสคริปต์ครั้งเดียวที่ฉบับแรกเสนอ):
  - เพิ่มเฉพาะบริษัทที่มีหมวดประทับ sentinel ของ bootstrap อย่างน้อยหนึ่งหมวด เพื่อไม่ให้บริษัทรุ่นก่อน bootstrap เปลี่ยนไปใช้กติกาเห็นเฉพาะหมวดของตัวเอง (§1.1)
  - เพิ่มเฉพาะเมื่อผังของบริษัทมีบัญชีนั้นแบบ active ลงรายการได้ และไม่ใช่บัญชีคุม (กติกาเดียวกับ bootstrap)
  - ข้ามหมวดที่บริษัทมีชื่อเดียวกันหรือ `accountHintKey` เดียวกันอยู่แล้ว ทั้งที่เปิดและเก็บถาวร การเก็บถาวรของร้านจึงยังมีผล
  - ข้ามหมวดที่ชื่อใกล้กับหมวดที่ร้านตั้งเอง ด้วยคำตรวจต่อแถวที่เขียนไว้ใน template (เช่น ร้านมี "ค่าน้ำมันรถ" อยู่แล้ว จะไม่ได้ "ค่าน้ำมันเชื้อเพลิง") แล้วรายงานรายการที่ข้าม
  - id คงที่ต่อบริษัทและหมวด และใช้ `ON CONFLICT DO NOTHING` รันซ้ำจึงไม่เพิ่มแถว
  - ไม่แก้หรือลบแถวเดิมเลย หมวดที่ร้านสร้างเองจึงไม่ถูกแตะ
  - เหตุผลที่ใช้ migration: รันใน release ที่มีหลักฐานใน ledger ของ runbook ทดสอบบน UAT ก่อน production ด้วยขั้นตอนเดียวกัน และไม่ต้องเปิด session ฐานข้อมูล production เอง
  - ต้นทุน: แถวใน SQL ซ้ำกับแถวใน TypeScript จึงต้องมี PG spec ตรวจว่าตรงกัน (แผน §4.2)
- **ชุดตามประเภทธุรกิจ (ภายหลัง — มติ §9 ข้อ 2 ยังไม่ทำ):** ฟังก์ชันเพิ่มหมวดที่รันซ้ำได้ `ensureCompanyExpenseCategories(tx, { companyId, rows })` ใช้กติกาข้ามแบบเดียวกับ migration เรียกจาก endpoint ใหม่ (แผน ภาคผนวก ก.3)
  - `createMany` ของ V1 วันนี้ไม่มี `skipDuplicates` (§1.5 ข้อ 5) จึงใช้กับงานนี้ไม่ได้
- **`accountHintKey` ของหมวดใหม่คงที่:**
  - ชุด ก: `expense.fuel`, `expense.electricity`, `expense.water`, `expense.telecom`, `expense.small_equipment`, `expense.penalties`
  - สงวนไว้สำหรับหมวดที่ยังไม่เพิ่ม: `expense.cost_of_goods` (B1), `expense.software` (ตรงกับหมวดกลางเดิม `ค่าซอฟต์แวร์/บริการ` ใน `seed.ts:3223`), `expense.insurance`, `expense.government_fees`
  - คำใบ้ของ AI ผูกกับ key นี้ (§6)
- **ผู้ตรวจของหมวดใหม่:** เป็นค่า sentinel `system:expense-category-bootstrap` เหมือน V1 นักบัญชีจึงยังเห็นว่าเป็นค่าที่ template เลือก
- **`sortOrder` และ `createdAt`:** `sortOrder` ต่อท้ายหมวดเดิม (13–18) ส่วน `createdAt` เป็นเวลาที่ migration รัน ซึ่งเครื่องมือรายจ่ายผิดปกติของที่ปรึกษาใช้ข้ามหมวดที่เพิ่งสร้าง (§7)
- **บริษัทรุ่นก่อน bootstrap:** อยู่นอกข้อเสนอนี้ ต้องนับก่อนว่ามีร้านจริงหรือไม่ ถ้ามีต้อง bootstrap ผังบัญชีก่อน
- **production:** migration รันเมื่อ Owner สั่งขึ้น production ตาม runbook เท่านั้น การนับแบบอ่านอย่างเดียวบน production ต้องเปิด session ฐานข้อมูลซึ่งส่งอีเมลเตือนความปลอดภัยถึง Owner จึงต้องแจ้งก่อน

### 5.3 ผลกระทบ

- **การลงบัญชี** (มีผลเฉพาะร้านที่เปิด `expense_auto_post` ซึ่งปิดเป็นค่าเริ่มต้น §1.3):
  - หมวดใหม่ผูกบัญชีที่มีอยู่แล้ว จึงพร้อมลงบัญชีได้ รายการเก่าไม่เปลี่ยนหมวดและไม่ย้อนแก้บัญชีที่ลงแล้ว
  - รายการใหม่ที่เข้าหมวดใหม่จะลงบัญชีต่างจากเดิม:
    - น้ำมันยังอยู่ 5200-09 เหมือนเดิม
    - ไฟฟ้า ประปา และโทรศัพท์ย้ายจาก 5330-05 ไปบัญชีของตัวเอง
    - วัตถุดิบยังไม่ย้าย เพราะ B1 เลื่อนออกไป (§3)
  - ควรแจ้งนักบัญชีของร้าน เพราะไฟล์ส่งนักบัญชีแสดงหมวดใหม่ตั้งแต่วันที่เพิ่ม
- **รายงานและที่ปรึกษา:**
  - การแยกยอดตามหมวดมีกลุ่มใหม่ตั้งแต่วันที่เพิ่ม การเทียบข้ามวันนั้นจึงไม่ใช่ของชนิดเดียวกัน
  - ที่ปรึกษาต้องบอกเรื่องนี้ และเครื่องมือรายจ่ายผิดปกติต้องข้าม "หมวดพุ่ง" ของหมวดที่เพิ่งสร้าง (แผนที่ปรึกษา S4a)
  - ไฟล์ส่งนักบัญชีแสดงชื่อหมวดใหม่
- **ภาษี:** Tax Code เริ่มต้นเป็นคำแนะนำ ผู้ตรวจยังยืนยันเอง ส่วนหัก ณ ที่จ่ายยังตัดสินรายรายการเหมือนเดิม
- **LINE:** รายการหมวดแบบมีเลขใน flow ใบรับรองยาวขึ้นจาก 12 เป็น 18 บรรทัด
  - เลขยังตอบได้ (รับ 1–2 หลัก) และรายการที่เปลี่ยนระหว่างถามกับตอบถูกกันไว้แล้ว (§1.3)
  - ฉบับแรกเสนอให้แสดง 5 อันดับแรก แต่ต้องมีตัวจัดอันดับเพิ่ม จึงแนะนำให้คงรายการเต็มไว้ก่อน และให้ Owner ลองบนโทรศัพท์ใน UAT
- **หมวดที่ร้านสร้างเอง:** ยังลงบัญชีไม่ได้จนกว่าจะผูกบัญชี (ปัญหาเดิม)
  - หมวดที่เพิ่มผ่าน migration ผูกบัญชีมาแล้ว
  - หมวดที่ร้านตั้งชื่อเองไม่ผูกบัญชี ซึ่ง Owner รับได้ และทีมงานผูกให้เมื่อร้านขอ (§9 ข้อ 9)

## 6. ให้ AI เลือกถูกเมื่อหมวดมากขึ้น

1. **รหัสสั้นทุกเส้นทาง:** ตัวอ่านรูป (เว็บและ LINE) และตัวจัดเส้นทางเห็นหมวดเป็น `c1..cN` แบบที่ PDF ใช้ตั้งแต่ #914 แล้ว gateway แปลงกลับเป็น id ที่ API ส่งมา (แผน C1)
   - ทำใน `line-ai-internal.controller.ts` ทั้งหมด รวมถึงการห่อ `router.routeIntake(body)` (`:562`) จึงไม่ต้องแก้ `intent-router.agent.ts`
   - รหัสสั้นยังประหยัด token ของ id ยาวที่ส่งทุกเทิร์น ซึ่งชดเชยคำใบ้ในข้อ 3 ได้บางส่วน
2. **ไม่เสนอหมวดเบ็ดเตล็ดทุกช่องทาง:** เว็บใช้ `aiSelectableExpenseCategories` แบบเดียวกับ LINE และ PDF (แผน C1, มติ §9 ข้อ 10)
3. **คำใบ้สั้นต่อหมวด:** รายการหมวดเปลี่ยนเป็น `activeCategories: {id, name, hint?}` (แผน C2)
   - หมวดจาก template ส่งคำใบ้ที่จับคู่ด้วย `accountHintKey` กับแถวใน template จึงไม่ต้องเพิ่มคอลัมน์ในฐานข้อมูล และ template เป็นแหล่งเดียวของคำใบ้
   - หมวดที่ร้านสร้างเองส่งแค่ชื่อ ส่วนหมวดจาก template ที่ร้านเปลี่ยนชื่อยังได้คำใบ้ตาม key

## 7. ความสัมพันธ์กับที่ปรึกษา

- **การแยกยอด** (`expense.get_breakdown`) และ **รายการผิดปกติ** (S4a) คมขึ้นเพราะน้ำมันและค่าไฟไม่ถูกกลืนในก้อนใหญ่ และเพราะรายการที่ไม่มีหมวดลดลง (S4a ไม่นับกลุ่มไม่มีหมวดเป็นหมวดพุ่ง)

- **"ค่าน้ำมันเดือนนี้"** ใช้การกรองหมวดตรง ๆ (`categoryName`) ได้เมื่อชื่อหมวดมีคำที่คนพิมพ์ (§2 ข้อ 8)
  - "ค่าน้ำ" กำกวมระหว่างน้ำมันกับประปา ระบบจะถามกลับ (`business-read-result-semantics.ts:121-125`)

- **ความพร้อมภาษี** (S4b) ได้ประโยชน์จาก B10 (ค่าปรับที่ต้องบวกกลับ) ส่วน B8 และ B9 ไม่เพิ่มตอนนี้

- **ถ้างานหมวด merge ก่อน S4a** (น่าจะเป็นเช่นนั้น เพราะ S4a อยู่ R4): PG spec ของ S4a มีเคสหมวดที่เพิ่งสร้างอยู่แล้ว ส่วน harness ของที่ปรึกษาที่ seed 5 หมวดเอง (`scripts/line-ai-expense-advisor/seed.ts:43`) ไม่ได้รับผลจากงานนี้
