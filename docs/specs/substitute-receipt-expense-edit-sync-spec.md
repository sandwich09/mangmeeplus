# Substitute receipt synchronization after expense edits

Owner decision: 2026-09-10. A reviewer can edit the source expense and return to step 3; no manual cancellation or document recreation is required. Both online and paper signing use the latest reviewed data.

## Journey and acceptance

- Before any signature or paper submission, saving the expense refreshes the prepared evidence and invalidates the previous printable form/preview. Keep its number within the payment period and its signing method.
- After a signature, paper submission, or issuance, saving a permitted expense edit supersedes the old evidence and prepares the next internal revision automatically with the same number within the payment period. Keep the old snapshots, signatures, scans, artifacts and audit trail. The current revision contains no signatures/scan/review acknowledgements and must be signed and approved again.
- Existing links to superseded evidence lead the wizard to the current revision. Old artifacts remain identifiable as superseded.
- Step 3 allows back navigation to source data/evidence and back to signing. Editing source data opens the existing expense review page. Signing-method changes still use the existing explicit cancellation workflow.
- Step 3 also offers **แก้ไขข้อมูลใบแทน** for a reviewer while the expense is editable and the certificate is PREPARED/PAYER_CERTIFIED (excluding issued-document corrections). Reuse the details/evidence screens to edit payee, reason, purpose, payment date/method and selected supporting/payment files. Save atomically via PATCH on the existing certificate, with source and certificate revision checks. No manual cancellation or recreation. Funding source, signing method and account signer remain unchanged in this flow.
- Keep the assigned number for edits within its actual payment month. Changing that month selects the number previously reserved for this logical certificate and target month, or reserves one using the canonical allocator. September → August → September restores the original September number; it is never released to another certificate. A number change creates an internal revision even when unsigned, preserving the prior form and linking its successor. Same-month unsigned edits keep their ID; signed/submitted edits require new signatures. Expense date alone does not change the number. Saving unchanged details does not invalidate signatures.
- Back/cancel from editing does not save certificate fields or advance signing. An uploaded supporting file remains attached to the source, but is not selected in the certificate until save. Background refresh must not silently replace the revision being edited; stale edits must ask for reload. Issued/cancelled documents retain existing correction rules.
- Downloading an unsigned form and online preview render latest expense dates, item details, amounts and current seller data. Explicit substitute-only fields (reason, business purpose, payment date/method, funding source and signer) retain their values unless the corresponding expense field was actually changed.
- A stale preview cannot be signed. A paper upload is bound to the form revision present when upload was initialized; expense edits invalidate that revision. The UI asks the user to print and sign the latest form. The system does not infer handwritten document contents automatically.
- Paid/posted source amounts are not rewritten by document refresh, and re-issuance must not create another payment, tax event or journal entry. Existing source-edit permission and status restrictions remain authoritative. Financial changes to already paid records require their existing correction/reversal flow.

## Related-field consistency follow-up

- Receipt→certificate and certificate→receipt are both supported review journeys. The receipt screen always exposes its linked certificate, including on mobile and with attachments. In the data step the return action saves current edits before navigating; a failed save keeps the user on the source with its error. Existing revision links resolve to the latest linked revision, including after a month change.
- Prefill shared purpose and reason for existing web/manual receipts as well as LINE drafts. A known blank source purpose must remain blank. Source and certificate purpose fields accept the same 500-character reviewed value. Editing unrelated fields must preserve an unchanged purpose/note, including legacy notes. A new certificate copies known vendor name/TIN; an explicit reuse action can retrieve these again. No source address is currently stored in the expense contract, so never invent one or copy a buyer address. Existing distinct payees retain their own identity.
- A different payee accepted from a LINE continuation must not inherit the source vendor's TIN. Purpose stored in the source note is removed from the certificate's separate note field during source synchronization: print the purpose once in its full-width field, preserving unrelated notes. This also avoids exceeding the certificate note limit after a valid 500-character purpose edit.

- Source expense owns expense date, vendor identity, items, totals, tax and recorded company payments. The certificate owns the actual payee (which may differ from the vendor), payee address, selected evidence and signing facts. Show vendor and actual payee separately with a source-edit link. A source vendor edit follows through to the certificate only when the previous payee identity matched that vendor; never overwrite a separately entered recipient. Clearing a matched source identity clears the corresponding certificate values, which can be completed from step 3.
- Business purpose and missing-receipt reason describe the same expense in both screens. Preparing/amending the certificate writes those source facts atomically with the certificate, with the updated source revision bound to it. Store purpose in the existing structured note segment, preserving unrelated notes/provenance. Source note edits support legacy plain purpose, structured purpose changes, and removal of the purpose segment. Null/blank clears cannot silently retain an old reason/purpose in a new form. Source draft projection continues to refresh from the updated source revision.
- Expense date and actual payment date remain separate. COMPANY records with a nonzero paid amount use the recorded payment date/method: show the recorded values in the wizard and offer an explicit action to use them when repairing old inconsistent certificates. Do not silently rewrite payment history. Reject conflicting prepare/amend requests before invalidating any signatures, and recheck at signing/issuance for races. Compare payment calendar days, not time-of-day. PERSONAL_ADVANCE dates refer to the employee's payment and are not overwritten by company settlement fields.
- Missing required facts on a legacy/refreshed certificate are editable in step 3; expose an actionable warning and do not certify/download an apparently complete form with missing facts. Unrelated edits remain possible. Existing financial correction restrictions remain intact; this scope adds no payment reversal or accounting mutation endpoint.
- Verification includes source↔certificate purpose/reason, blank values, distinct payee preservation, same-day payment timestamps, paid-date/method conflicts and recovery, no-op signatures, stale revisions, latest snapshots and both paper/digital flows. One additive constraint migration permits blank reason/purpose only in PREPARED/SUPERSEDED; PAYER_CERTIFIED/ISSUED still require both. The nullable revision link is additive; deploy migrations before API code. No deployment is included in this merge request.

## Monthly number reuse (approved 2026-09-10)

- Preserve committed reservations permanently. Reuse is restricted to the same tenant, source expense and automatic revision lineage. Manual cancellation/recreation is a different logical document. Existing same-number revisions are supported for backward compatibility.
- Period is derived from actual payment date using the existing civil-date/Bangkok helper. Respect branch scope in configured branch-specific templates; company-wide templates can retain their number on a branch edit. A missing payment date can remain in a prepared draft but cannot allocate or sign; completing it reconciles the number. Issued financial corrections retain their existing restrictions and original number.
- Source review and in-wizard amendment call one shared revision/numbering helper inside the funding/substitute locked transaction. Stale/concurrent/invalid edits roll back both document changes and allocations. No-op and repeated saves consume no additional number.
- Preserve old signed/paper snapshots, invalidate current preview/signing acknowledgements, and require the current evidence revision for download/sign/submit. Follow the explicit revision chain for old links; do not redirect to an unrelated newer certificate. Show the actual returned number in success text and PDF.
- Regression coverage: same-month date edits, month toggling and other documents in the same month, year/Bangkok boundary, branch changes, both signature modes, stale concurrent saves, transaction rollback, source payment versus expense date, tenant/owner checks, PDF and old-link navigation.

- Corrupt or imported legacy evidence without a committed number registry keeps ordinary same-month edits available. Cross-period/branch changes report an explicit registry-repair error rather than guessing ownership or assigning another document’s number. No bulk migration or live customer data rewrite is included.
