# ผลตรวจความเข้ากับโค้ดจริง: ใบเตรียมจ่าย/ใบสำคัญจ่าย และ 50 ทวิ

วันที่: 2026-10-11 · ตรวจกับ `origin/main` `9b94ce059` · ที่มา: คำสั่งเจ้าของ "ตรวจ impact dependency gap bug module ข้างเคียง apply ui กับ code จริงด้วย" (spec D18)

เอกสารที่เกี่ยว: [Spec v2.5](../specs/expense-payment-preparation-voucher-spec-th.md) · [แผน](../plans/expense-payment-preparation-voucher-plan-th.md) · [ผลกระทบและช่องว่างรอบก่อน](expense-payment-preparation-voucher-impact-gap-2026-10-11-th.md) · [ผลศึกษาหน้าจอ FlowAccount](flowaccount-expense-payment-ux-study-2026-10-11-th.md)

สถานะ: **อ่านโค้ดอย่างเดียว ไม่ได้แก้โค้ด ไม่ได้รัน test ไม่ได้แตะระบบจริง**

## 0. สรุปสำหรับเจ้าของ

1. **แบบที่ออกไว้ทำได้จริงบนโค้ดปัจจุบัน** ไม่มีข้อใดต้องกลับไปขอคำตัดสินใหม่ แต่มี 8 จุดที่แบบเขียนไว้ไม่ตรงกับโค้ด จึงปรับ spec เป็นรุ่น 2.5 (§2)
2. **หน้าจอ**: หน้ารายการ หน้าเอกสารแบบขั้นตอน แถวบนหน้าผู้ดูแล และหน้ารายการ 50 ทวิ ประกอบจากชิ้นส่วนที่มีอยู่ได้ งานใหม่ก้อนใหญ่สุดคือหน้าสร้างใบ (เลือกผู้รับเงินแล้วติ๊กรายจ่าย) ซึ่งระบบยังไม่มีทั้งหน้าจอแบบนี้และข้อมูลที่หน้านี้ต้องใช้ (§4)
3. **หน้ารายละเอียดรายจ่ายเป็นจุดเปราะ**: มี test ล็อกข้อความและลำดับในไฟล์นี้หลายชุด ของใหม่ทุกชิ้นต้องเป็นชิ้นส่วนแยก และหน้าต่างยืนยันจะเปลี่ยนเฉพาะกรณีที่รายจ่ายมีหนังสือรับรอง (§4.3)
4. **พบบั๊กของเดิม 14 จุด** ในโค้ดรอบข้าง 5 จุดกระทบร้านที่ใช้แพ็กเกจที่ขายอยู่วันนี้ เสนอให้แก้ไปพร้อมงานนี้ **รอคำยืนยันหนึ่งข้อ** (§5.1) อีก 6 จุดเป็นสิ่งที่งานนี้ต้องแก้อยู่แล้วมิฉะนั้นของใหม่จะพัง จึงใส่ในแผนแล้ว (§5.2)
5. **เงินและยอด** ของระบบจ่ายเดิมผ่านการตรวจ: จ่ายพร้อมกัน จ่ายแล้วยกเลิกแล้วจ่ายใหม่ และการกันจ่ายเกิน ทำงานถูก (§6)

## 1. วิธีตรวจ

อ่านโค้ดสามด้านพร้อมกัน แล้วผู้เขียนเปิดโค้ดยืนยันข้อที่มีผลต่อแบบด้วยตัวเอง

| ด้าน | ขอบเขต |
|---|---|
| หน้าจอ | ชิ้นส่วนกลางของเว็บ หน้าใบเบิก หน้าใบรับรองแทนใบเสร็จ หน้ารายละเอียดรายจ่าย หน้าผู้ดูแล และ test ที่ล็อกหน้าเหล่านี้ |
| ข้อมูลและโมดูลข้างเคียง | รายการรายจ่าย การผูกคู่ค้า เลขเอกสาร การจ่าย สมุดรายรับรายจ่าย การแจ้งเตือน ผู้ช่วยใน LINE ไฟล์แนบ การส่งออกหลักฐาน migration |
| บั๊กในโค้ดเดิม | ทางจ่าย ยกเลิกการจ่าย เปิดกลับมาแก้ ยกเลิกรายจ่าย ใบรับรองแทนใบเสร็จ การออกและแก้ไขหนังสือรับรอง |

สิ่งที่ตรวจแล้ว **ไม่ต้องปรับ** เพราะ spec เขียนไว้ถูกอยู่แล้ว: ไฟล์ใบสำคัญจ่ายสร้างและเก็บนอก transaction; ยอดจองไม่เปลี่ยน `updatedAt`; แถวตั้งค่าที่สร้างใหม่ต้องใส่ค่าของสวิตช์บันทึกด้วยมือ (ช่องนั้นห้ามว่างและไม่มีค่าเริ่มต้น); สลิปผูกกับใบ ไม่ผูกกับรายจ่ายหลายรายการ; ไม่แตะไฟล์ที่ผู้ช่วยใน LINE ตรึง hash

ข้อเสนอของผู้ช่วยที่ **ไม่รับ** พร้อมเหตุผล:

- เติมสิทธิ์ใหม่ให้ตำแหน่งที่ร้านสร้างเองโดยอัตโนมัติ: ขัดคำตัดสิน D12 และ test ของ registry
- เพิ่มสิทธิ์ดูใบเข้าในรายการที่ทำให้กลุ่มเมนูรายจ่ายปรากฏ: ต้องแก้ไฟล์ที่ผู้ช่วยใน LINE ตรึง hash และไม่จำเป็น เพราะสิทธิ์ดูใบให้เห็นเฉพาะใบของรายจ่ายที่ผู้นั้นอ่านได้อยู่แล้ว ตำแหน่งที่ไม่มีสิทธิ์รายจ่ายเลยจึงไม่มีอะไรให้ดู แก้ด้วยบรรทัดแนะนำในหน้าสร้างตำแหน่งแทน

### 4.2 ชิ้นส่วนที่ไม่มี ต้องสร้าง (เรียงจากใหญ่ไปเล็ก)

1. **ตัวเลือกผู้รับเงินที่ค้นจาก server** และรายการรายจ่ายค้างของผู้รับเงินนั้น ช่องเลือกแบบค้นหาที่มีอยู่กรองได้เฉพาะตัวเลือกที่โหลดมาแล้ว
2. **รายการติ๊กที่มียอดรวมขยับตาม** พร้อมแก้ยอดรายบรรทัดและแถบยอดรวมที่ติดขอบล่าง

4. **เลขที่และประวัติของหนังสือรับรองบนหน้ารายจ่าย** ข้อมูลยังไม่มี
5. **ประวัติจัดกลุ่มตามวัน** ระบบยังไม่มีที่ใดทำ
6. **ตัวเลือกผู้รับของ "ส่งเตือนอีกครั้ง"**
7. **เมนูเพิ่มเติมแบบกลาง** แยกจาก `ReceiptActions` ของหน้าใบรับรองแทนใบเสร็จ
8. **ปุ่มรวม "ส่งและอนุมัติ"**
9. **หน้าต่างยืนยันการยกเลิกรายจ่าย** วันนี้เป็นกล่องเหตุผลในแถบล่าง ไม่ใช่หน้าต่าง

| 15 | ก | หน้า "ยังไม่จ่าย" ของรายจ่ายโหลดได้สูงสุด 200 แถวแล้วกรองในเบราว์เซอร์ ร้านที่มีรายจ่ายยืนยันแล้วมากกว่านั้นเห็นไม่ครบ |
| 16 | ค | การจ่ายที่ลงบัญชีแยกประเภทอัตโนมัติแล้วยกเลิกการจ่ายไม่ได้ เหลือแค่ยกเลิกรายจ่าย (บัญชีแยกประเภทยังไม่ขาย) |
| 17 | ค | การโอนครั้งเดียวที่จ่ายหลายรายจ่ายจะเป็นหลายรายการในหน้าจับคู่ธนาคาร (ยังไม่ขาย) |
| 18 | — | ช่องการผูกคู่ค้าของรายจ่ายรับค่าจาก API โดยไม่ตรวจ หน้าเว็บไม่เคยส่ง |

## 6. สิ่งที่ตรวจแล้วและทำงานถูก

- จ่ายรายจ่ายเดียวกันพร้อมกันสองคำสั่ง: ล็อกและการอ่านซ้ำกันจ่ายเกินได้
- จ่าย → ยกเลิกการจ่าย → จ่ายใหม่: ยอดรวมถูก ยอดจ่ายเก่าที่ไม่มีแถวการจ่ายถูกเก็บไว้
- ใช้ key เดิมกับรายจ่ายอื่นหรือข้อมูลต่าง: ถูกปฏิเสธ
- เปิดกลับมาแก้รายจ่ายที่มีการจ่าย: จ่ายเพิ่มไม่ได้ ยกเลิกการจ่ายได้ ยืนยันใหม่ด้วยยอดต่ำกว่าที่จ่ายแล้วถูกปฏิเสธพร้อมวิธีแก้
- เปิดกลับมาแก้ → เปลี่ยนผู้ขาย → ยืนยันใหม่ (ไม่มีหนังสือรับรอง): รายการรอออกแถวเดิมถูกปรับ ไม่เกิดแถวซ้ำ
- ทุกทางที่ตรวจกรองตามบริษัท
- วันที่จ่ายเก็บเป็นวันตามเวลาไทย และการกันวันที่ในอนาคตใช้เวลาไทย
- รายจ่ายที่ถูกจองไม่ถูกนำไปตั้งเบิกได้ key ของการจ่ายตามใบปลอมจากฝั่งผู้ใช้ไม่ได้ (key ของผู้ใช้ถูกเติมคำนำหน้า)

## 7. สิ่งที่ยังไม่ได้ทำในการตรวจนี้

- ไม่ได้รัน test และไม่ได้เดินหน้าจอ เพราะฟีเจอร์ยังไม่มีโค้ด ความเสี่ยงบนจอใน §4.4 มาจากการอ่านโค้ด ต้องยืนยันบนเครื่องจริงตอนทำ
- ข้อที่ระบุว่า "ผู้ช่วยอ่าน" ยังไม่ได้เปิดโค้ดยืนยันซ้ำ ให้ตรวจซ้ำในรอบ 0 ของแผน
- ยังไม่ได้นับข้อมูลบนระบบจริง (ใบ 50 ทวิและรายการรอออกที่ค้างบนรายจ่ายที่ถูกยกเลิก) อยู่ในรอบ 0 ของแผน และต้องแจ้งเจ้าของก่อนเปิดการเชื่อมต่อ
