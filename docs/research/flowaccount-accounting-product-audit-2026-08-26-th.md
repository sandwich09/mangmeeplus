## 1. คำตอบสรุป

FlowAccount ที่เห็นจากบัญชีทดสอบไม่ใช่แค่โปรแกรมออกบิล แต่เป็นระบบที่เชื่อม 7 ชั้นเข้าหากัน:

1. เอกสารทางธุรกิจ เช่น ใบเสนอราคา ใบวางบิล ใบกำกับภาษี ใบสั่งซื้อ และค่าใช้จ่าย
2. การรับ–จ่ายเงินจริง เช่น เงินสด ธนาคาร บัตร EDC POS และช่องทางออนไลน์
3. เอกสารภาษี เช่น ภาษีซื้อ ภาษีขาย ภ.พ.30 ภ.พ.36 และภาษีหัก ณ ที่จ่าย
4. รายการบัญชี เช่น สมุดรายวันซื้อ ขาย รับ จ่าย และทั่วไป
5. บัญชีแยกประเภท งบทดลอง งบกำไรขาดทุน และงบฐานะการเงิน
6. สินค้าคงเหลือ คลัง การโอนสินค้า และสินทรัพย์ถาวร
7. การตั้งค่าและสิทธิ์ที่ควบคุมผลทั้งหมด เช่น วิธีคำนวณ VAT/WHT เลขเอกสาร ผังบัญชี งวดบัญชี และการล็อกงวด

จุดแข็งที่สุดไม่ใช่จำนวนฟีเจอร์ แต่คือ “สร้างครั้งเดียวแล้วไหลต่อ” เช่น ใบเสนอราคาไปใบวางบิล ไปใบกำกับภาษี ไปการรับชำระ โดยไม่คีย์ข้อมูลเดิมใหม่ และรายการค่าใช้จ่ายที่อนุมัติ/จ่ายแล้วไหลไปสมุดรายวันที่เกี่ยวข้อง

สำหรับมั่งมี ข้อสรุปหลักคือ:

- ต้องออกแบบเป็น “ระบบงานบัญชีที่มีเอกสารต้นทางเดียว” ไม่ใช่สร้างหน้ารายรับ รายจ่าย ภาษี และบัญชีแยกกันจนตัวเลขไม่ตรง
- ผู้ใช้ 40+ และไม่ถนัดเทคโนโลยีควรเห็น “งานที่ต้องทำวันนี้” ก่อนเมนูบัญชีทั้งหมด
- นักบัญชีต้องตรวจรายละเอียดและแก้ exception ได้ แต่เจ้าของร้านไม่ควรถูกบังคับให้เข้าใจเดบิต/เครดิต
- สมองมั่งมีต้องอธิบายและพาไปทำงานได้ แต่ตัวเลขบริษัทต้องมาจาก API ที่ตรวจสิทธิ์ และกฎภาษีเสี่ยงสูงต้องมาจากคลังความรู้ที่ผู้เชี่ยวชาญอนุมัติ
- FlowAccount เป็นหลักฐานด้าน product/UX ไม่ใช่แหล่งตัดสินกฎหมายภาษี แหล่งตัดสินกฎหมายต้องเป็นกรมสรรพากรและผู้เชี่ยวชาญที่ระบุชื่อ

## 2. วิธีสำรวจและระดับหลักฐาน

### 2.1 วิธีสำรวจ

- ใช้บัญชีทดสอบจริงที่ผู้ใช้เปิดไว้ใน Chrome
- สำรวจเมนู รายการ ฟอร์มสร้างเอกสาร ตัวกรอง สถานะ การตั้งค่า และหน้ารายงาน
- เปิดเฉพาะหน้าหรือกล่องข้อความเพื่ออ่านโครงสร้าง ไม่กดบันทึก ไม่อนุมัติ ไม่ยื่นภาษี ไม่อัปโหลด Statement และไม่ดาวน์โหลดข้อมูล
- ตรวจคู่มือสาธารณะของ FlowAccount เพื่อยืนยัน flow ที่บัญชีว่างไม่สามารถแสดงได้
- ตรวจแหล่งทางการของกรมสรรพากรสำหรับขอบเขตภาษี
- เทียบกับ spec/plan/readiness assessment ที่มีอยู่ใน repository ของมั่งมี

### 2.2 ป้ายกำกับหลักฐาน

| ป้าย | ความหมาย | ใช้ตัดสินอะไรได้ |
|---|---|---|
| OBSERVED_UI | เห็นจากหน้าเว็บในบัญชีทดสอบ | ยืนยันว่ามีเมนู ฟิลด์ ปุ่ม หรือตัวเลือกนั้นใน UI ที่สำรวจ |
| OBSERVED_HELP_TITLE | เห็นชื่อวิดีโอหรือคู่มือในหน้าระบบ | ยืนยันว่าผลิตภัณฑ์สื่อว่ารองรับเรื่องนั้น แต่ยังไม่ยืนยัน end-to-end |
| OFFICIAL_PUBLIC_DOC | คู่มือสาธารณะของ FlowAccount | ยืนยัน workflow ที่อธิบายในคู่มือ ณ วันที่เข้าถึง |
| OFFICIAL_LAW_SOURCE | กรมสรรพากรหรือหน่วยงานกำกับ | ใช้เป็นฐานกฎหมาย โดยยังต้องตรวจ effective date และกรณีเฉพาะ |
| REPOSITORY_BASELINE | เอกสาร/โค้ด/ผลตรวจใน repository มั่งมี | ใช้เป็นสถานะตั้งต้น แต่ finding เก่าต้อง revalidate ก่อนลงมือ |
| INFERENCE | ข้อสรุปจากหลายหลักฐาน | ใช้ออกแบบได้ แต่ต้องทดสอบกับผู้ใช้หรือผู้เชี่ยวชาญก่อนเปิดจริง |
| NOT_VERIFIED | ไม่ได้ทำธุรกรรมจริงในรอบนี้ | ห้ามกล่าวอ้างว่าใช้งานจริงครบแล้ว |

### 2.3 การคุ้มครองข้อมูล

เอกสารนี้ไม่บันทึกรหัสบัญชีผู้ใช้ เลขบัญชีธนาคาร เลขประจำตัวผู้เสียภาษี ที่อยู่ ชื่อลูกค้า/โครงการ หรือข้อมูลติดต่อที่ปรากฏในบัญชีทดสอบ แม้ข้อมูลบางส่วนจะเห็นได้ในหน้าเว็บก็ตาม

## 4. โครงสร้าง UX ที่ทำให้ใช้ง่าย

### 4.1 ฟอร์มเอกสารใช้โครงเดียวกัน

ใบเสนอราคา ใบวางบิล ใบกำกับภาษี ใบสั่งซื้อ ใบรับสินค้า และค่าใช้จ่ายใช้โครงสร้างใกล้กัน:

- คู่ค้าและข้อมูลภาษี
- วันที่เอกสาร วันครบกำหนด เครดิต ผู้รับผิดชอบ โครงการ และเอกสารอ้างอิง
- สกุลเงินและคลังสินค้า
- รายการสินค้า/บริการ จำนวน หน่วย ราคา ส่วนลด VAT และ WHT
- หมายเหตุภายนอก โน้ตภายใน ลายเซ็น/ตรายาง และไฟล์แนบ
- สรุปฐานภาษี มูลค่า VAT, WHT และยอดสุทธิ
- การกระทำหลัก เช่น บันทึก ดาวน์โหลด พิมพ์ แชร์ หรือส่งอีเมล

ผลคือผู้ใช้เรียนรู้ฟอร์มหลักครั้งเดียวแล้วใช้เอกสารชนิดอื่นได้ และการแปลงเอกสารสามารถนำข้อมูลเดิมไปต่อได้โดยไม่คีย์ซ้ำ

### 4.2 แยกภาษาธุรกิจกับภาษานักบัญชี

หน้าตั้งค่าส่วนตัวมีตัวเลือกแสดงหมวดหมู่แบบ “สำหรับธุรกิจ” หรือ “สำหรับนักบัญชี” เจ้าของร้านเลือกหมวดงานที่เข้าใจง่าย ส่วนนักบัญชีเลือกผังบัญชีและรายการคู่บัญชีละเอียดได้ นี่เป็น pattern สำคัญสำหรับผู้ใช้ 40+:

- Beginner mode: ถามว่า “จ่ายค่าอะไร” และแสดงผลกระทบแบบภาษาคน
- Accountant mode: แสดง account code, debit/credit, tax code และ posting evidence
- ข้อมูลต้นทางเดียวกัน ห้ามสร้างสองชุดข้อมูลแยกกัน

### 4.3 สถานะบอก “ต้องทำอะไรต่อ”

รายการเอกสารทุกกลุ่มแสดงสถานะและตัวกรอง ตัวอย่างเช่น รออนุมัติ อนุมัติแล้ว รอวางบิล วางบิลแล้ว รอรับเงิน ชำระแล้ว ยกเลิก หรือออกเอกสารต่อแล้ว สถานะจึงเป็นทั้ง audit trail และ next action

### 4.4 Default ก่อน Advanced

ค่าที่ใช้บ่อยตั้งเป็นค่าเริ่มต้นระดับบริษัท เช่น ราคาแบบรวม/ไม่รวม VAT, วิธีแสดง VAT/WHT/ส่วนลด, คลังหลัก, สกุลเงินหลัก และเลขรันเอกสาร แต่ยังแก้เป็นรายเอกสารได้ การตั้งค่าใหม่ไม่มีผลย้อนหลังกับเอกสารเดิมตามคู่มือสาธารณะ

### 4.5 รายงานมี pattern เดียวกัน

หน้ารายงานส่วนใหญ่ใช้:

- ช่วงเวลา/วันที่อ้างอิง
- ตัวกรองสถานะ คู่ค้า โครงการ หรือคลัง
- ปุ่มแสดงผลก่อนสร้างรายงาน
- ดาวน์โหลด Excel และ/หรือพิมพ์
- แยกเอกสารธุรกิจกับรายการบัญชีที่ลงเองเมื่อเกี่ยวข้อง

ผู้ใช้จึงไม่ต้องเรียนรู้วิธีใช้รายงานใหม่ทุกหน้า

## 5. ภาพรวมและรายงานบริหาร

### 5.1 Dashboard ที่เห็น

Dashboard รวมยอดขาย การเก็บเงิน ค่าใช้จ่าย การชำระเงิน ลูกหนี้ เจ้าหนี้ สินค้า และโครงการ พร้อม CTA สร้างเอกสารขาย/ค่าใช้จ่าย การประกาศฟีเจอร์ในหน้าเดียวกันกล่าวถึง e-Tax, QR Payment, Online Card, POS, Marketplace, Payroll, OCR และ Multi-unit stock แต่ประกาศเหล่านี้นับเป็น OBSERVED_HELP_TITLE/announcement ไม่ใช่หลักฐานว่า flow จริงทุกตัวผ่านในบัญชีทดสอบ

### 5.2 รายงานธุรกิจที่พบ

| กลุ่ม | รายงานหลัก | มิติสำคัญ |
|---|---|---|
| ขาย | สรุปยอดขาย, ตามสินค้า, พนักงาน, ลูกค้า, ใบวางบิล, การเก็บเงิน | วันที่ เอกสาร ลูกค้า/โครงการ ยอดก่อนภาษี VAT สุทธิ สถานะ ช่องทางรับเงิน |
| ซื้อ | ใบสั่งซื้อ, ใบรับสินค้า, ใบรับสินค้าตามสินค้า | ผู้จำหน่าย โครงการ จำนวน ราคา VAT สถานะ |
| ค่าใช้จ่าย | สรุปค่าใช้จ่าย, การชำระเงิน | หมวด ผู้จำหน่าย วันที่ชำระ รายละเอียดการจ่าย ยอดค้าง/จ่ายแล้ว |
| โครงการ | รายได้ ค่าใช้จ่าย กำไร/ขาดทุน | ลูกค้า/ผู้จำหน่ายและผลประกอบการต่อโครงการ |
| สินค้า | สรุปสินค้าคงเหลือ | รหัส ชื่อ จำนวน หน่วย ราคาเฉลี่ย มูลค่าคงเหลือ และคลัง |
| ภาษี | ภาษีขายตามเอกสาร, ภาษีซื้อตามเอกสาร, WHT | คู่ค้า เลขภาษี เอกสาร ฐานภาษี VAT/WHT และสถานะ |
| ลูกหนี้/เจ้าหนี้ | Aging ตามเอกสาร | วันที่ครบกำหนด คู่ค้า และเอกสารเปิด |

ข้อสังเกต: รายงานแยก “เอกสารทางธุรกิจ” กับ “เอกสารทางบัญชี” ช่วยให้ตรวจได้ว่ายอดมาจากระบบงานหรือรายการที่นักบัญชีลงเพิ่มเอง

## 6. Sell-to-Cash: เอกสารขาย รายรับ และลูกหนี้

### 6.1 ชนิดเอกสารที่พบ

- ใบเสนอราคา
- ใบวางบิล/ใบแจ้งหนี้ และใบวางบิลรวม
- ใบส่งสินค้า/ใบแจ้งหนี้/ใบกำกับภาษี
- ใบเสร็จรับเงิน และใบเสร็จรวม
- ขายเงินสด หรือใบกำกับภาษี/ใบเสร็จรับเงินในใบเดียว
- ใบลดหนี้/ใบกำกับภาษี
- ใบเพิ่มหนี้/ใบกำกับภาษี
- ใบส่งของที่ต่อท้ายเอกสารขายบางประเภท
- เอกสารมัดจำ แบ่งจ่าย แบ่งรับชำระ เงินประกันผลงาน และสกุลเงินต่างประเทศจากคู่มือ

  → อนุมัติ / ไม่อนุมัติ
  → ใบวางบิล/ใบแจ้งหนี้ หรือเอกสารขายถัดไป
  → ใบกำกับภาษีเมื่อถึง tax/document boundary ที่กำหนด
  → บันทึกรับชำระ (เต็มจำนวน/บางส่วน/ผลต่าง/WHT รับ)
  → ใบเสร็จรับเงิน
  → กระทบยอดกับเงินเข้าธนาคาร
  → สมุดรายวันขาย/รับ และ AR ถูกเคลียร์
~~~

สำหรับขายสดสามารถข้ามลูกหนี้และบันทึกการขายกับการรับเงินใน transaction เดียว แต่ยังต้องสร้างภาษีและตัดสต็อกตามกฎของเอกสาร

### 6.3 กฎผลิตภัณฑ์ที่สำคัญ

- ใบเสนอราคาไม่ควรลงบัญชีหรือเกิดภาษีเพียงเพราะสร้างเอกสาร
- การแปลงเอกสารต้องรักษา source lineage และยอดที่แปลงแล้ว เพื่อกันออกซ้ำหรือเกินยอด
- รองรับ partial document, partial payment, deposit และ retention โดยแสดงยอดต้นทาง ยอดที่ใช้แล้ว และยอดคงเหลือ
- การรับเงินจาก invoice ที่รับรู้รายได้แล้วต้องเคลียร์ลูกหนี้ ไม่ลงรายได้/VAT ซ้ำ
- ใบลดหนี้/เพิ่มหนี้ควรอ้างอิงเอกสารเดิม เหตุผล มูลค่าเดิม มูลค่าถูกต้อง ส่วนต่าง และผลต่อ VAT/stock/payment
- เอกสารยกเลิกต้องคงเลขและประวัติ ไม่ใช้ hard delete กับเอกสารที่ออกแล้ว
- ช่องทางรับชำระควรตั้งไว้ระดับบริษัทและเลือกใช้ในเอกสาร/ลิงก์รับเงินได้

### 6.4 รายรับอัตโนมัติที่อนุมานได้

FlowAccount แสดงแนวคิด Bank Reconcile ที่จับ Statement กับรายได้ ค่าใช้จ่าย หรือสมุดรายวันที่มีอยู่ และสร้างรายการใหม่จาก Statement เมื่อไม่มีคู่ได้ สำหรับมั่งมีควรต่อยอดเป็น Revenue Inbox แต่ต้องแยก:

- Invoice payment
- Revenue ที่ยังไม่มี invoice
- Transfer ระหว่างบัญชี
- เงินทุน/เงินกู้
- เงินมัดจำหรือหนี้สิน
- Refund
- Marketplace settlement หลังหักค่าธรรมเนียม
- Unidentified cash-in

หลักคิดสำคัญ: เงินเข้าธนาคารไม่เท่ากับรายได้เสมอไป และการ match เงินต้องไม่กลายเป็นการรับรู้รายได้หรือ VAT ซ้ำ

## 7. Procure-to-Pay: จัดซื้อ รับสินค้า ค่าใช้จ่าย และเจ้าหนี้

### 7.1 ใบสั่งซื้อ

ฟอร์มใบสั่งซื้อมีผู้จำหน่าย วันที่เครดิต/ครบกำหนด ผู้ซื้อ สกุลเงิน โครงการ อ้างอิง คลัง รายการสินค้า ส่วนลด VAT WHT และไฟล์แนบ สถานะในคู่มือครอบคลุมรอดำเนินการ อนุมัติ สร้างใบรับสินค้า สร้างค่าใช้จ่าย และยกเลิก

ข้อดีของ flow นี้คือการอนุมัติเกิดก่อนบริษัทผูกพันเงิน และ PO สามารถแปลงต่อโดยไม่คีย์ซ้ำ

### 7.2 ใบรับสินค้า

ใบรับสินค้าสร้างใหม่ได้หรือแปลงจาก PO ได้ เมื่อยืนยันจะเพิ่มจำนวนสินค้าในคลังและเกิดยอดเจ้าหนี้หากยังไม่จ่าย รองรับรับบางส่วนตามจำนวน หรือแบ่งชำระตามยอด/เปอร์เซ็นต์จากคู่มือ

กฎที่ควรใช้กับมั่งมี:

- ของซื้อเพื่อขาย → รับเข้าคลังและสร้าง inventory/AP effect
- ของใช้หรือบริการที่ไม่นับ stock → ไป expense/vendor bill
- รับสินค้า การรับใบกำกับภาษี และการจ่ายเงินเป็นคนละ event และอาจเกิดคนละวัน
- ต้องรองรับ 2-way/3-way match: PO ↔ Receipt ↔ Vendor tax invoice/bill

### 7.3 ค่าใช้จ่ายและ OCR

ค่าใช้จ่ายสร้างด้วยมือหรือสแกนบิล/ใบเสร็จได้ ฟอร์มมีหมวดธุรกิจและหมวดนักบัญชี ไฟล์แนบ การชำระเงิน และข้อมูลใบกำกับภาษีที่ได้รับ คู่มือระบุว่าเมื่อบันทึก/อนุมัติจะไปสมุดรายวันซื้อ และเมื่อเปลี่ยนเป็นชำระเงินแล้วจะไปสมุดรายวันจ่าย

นี่เป็น pattern ที่เหมาะกับมั่งมีมากที่สุด:

~~~text
ถ่าย/อัปโหลด
  → AI อ่านเป็น Draft
  → ผู้ใช้ตรวจเฉพาะช่องที่ไม่มั่นใจ
  → เลือกหมวดภาษาคน
  → ส่งตรวจ/อนุมัติ
  → บันทึกเจ้าหนี้หรือจ่ายทันที
  → นักบัญชีแก้ account/tax mapping เฉพาะ exception
~~~

ข้อควรระวังจากปัญหาจริงของมั่งมี:

- หลัง “ส่งตรวจเรียบร้อย” ต้องกลับหน้ารายการอัตโนมัติ แสดงสถานะและเน้นแถวล่าสุด ห้ามค้างหน้าเดิมจนผู้ใช้ไม่แน่ใจว่าบันทึกแล้วหรือยัง
- ใบเดียวต้องรองรับสินค้า VAT 7%, VAT 0%, ยกเว้น VAT, ไม่มี VAT/อยู่นอกขอบเขต และการปัดเศษในระดับบรรทัด
- VAT ที่ OCR อ่านจากเอกสารกับ VAT ที่คำนวณต้องเก็บทั้งสองค่าและอธิบายผลต่าง ห้ามบังคับให้ระบบเขียนทับเอกสารจริงหรือ block แบบไม่มีทางแก้
- การแก้ยอดเอกสารที่อนุมัติ/จ่ายแล้วต้องใช้ reset/correction/reversal ที่มี audit ไม่แก้ทับเงียบ ๆ

### 7.4 ใบเตรียมจ่าย/ใบสำคัญจ่าย

หน้าที่พบรองรับเลือกผู้จำหน่ายและเอกสารหลายใบ ผู้จัดทำ ผู้ขออนุมัติ ผู้อนุมัติ เหตุผล วันครบกำหนด รายละเอียดจ่าย WHT และไฟล์แนบ เป็น control point ก่อนเงินออก เหมาะกับการทำ segregation of duties และจ่ายเฉพาะรายการที่อนุมัติ

## 9. VAT และเอกสารภาษีซื้อ

### 9.1 การคำนวณในเอกสาร

หน้าตั้งค่ารองรับราคาแบบรวม/ไม่รวม VAT และคำนวณ VAT, ส่วนลด และ WHT แบบแยกรายการหรือท้ายเอกสาร คู่มือระบุว่า VAT ต่อรายการสามารถเลือก 7%, 0% และยกเว้นภาษีได้

ข้อสรุปสำหรับมั่งมี:

- tax treatment ต้องอยู่ระดับ line item
- document summary เป็นผลรวม ไม่ใช่ source ที่เขียนทับ line
- เก็บ source amount, calculated amount, difference, rounding policy และ reviewer resolution
- อย่าใช้ค่า 0 ค่าเดียวแทน zero-rated, exempt และ out-of-scope เพราะผลรายงาน/สิทธิภาษีต่างกัน

### 9.2 ภาษีซื้อ

หน้าจัดการเอกสารภาษีซื้อมีวันที่ เอกสาร ผู้จำหน่าย มูลค่า VAT และสถานะใบกำกับภาษี พร้อมตัวกรองสถานะ อัตรา VAT และ “รอใช้สิทธิ์” คู่มือสาธารณะอธิบาย flow ว่า:

1. ค่าใช้จ่าย/ใบรับสินค้าอาจลง “ภาษีซื้อยังไม่ถึงกำหนด” ก่อน เมื่อยังไม่มีรายละเอียดใบกำกับภาษี
2. เมื่อได้รับใบกำกับภาษี บันทึกเลขที่ วันที่ และแบบที่เกี่ยวข้อง
3. เลือกเอกสารภาษีซื้อที่จะใช้สิทธิ์ในงวด ภ.พ.30
4. ถ้าไม่ใช้สิทธิ์ ระบบกลับรายการไปภาษีซื้อไม่ขอคืนและไม่รวมในแบบ
5. เมื่อเตรียมแบบ ระบบปิด/โอนบัญชีภาษีซื้อ–ขาย และเมื่อชำระจึงบันทึกช่องทางจ่ายภาษี

นี่แสดงว่าต้องแยก “VAT อยู่บนเอกสาร” ออกจาก “VAT มีสิทธิ์ขอคืนในงวดใด”

### 9.3 ภ.พ.30

หน้าระบบมีรายงานภาษีซื้อ ภ.พ.30 รายงานภาษีขาย ภ.พ.30 และหน้าเตรียมแบบรายเดือน คู่มือระบุว่า output VAT ถูกดึงจากเอกสารขาย ส่วน input VAT ให้ผู้ใช้เลือกสิทธิ์ ระบบคำนวณยอดขาย ภาษีขาย ยอดซื้อ ภาษีซื้อ เครดิตยกมา และยอดชำระ/ขอคืน

ตามคำแนะนำแบบ ภ.พ.30 ของกรมสรรพากร ภ.พ.30 เป็นแบบรายเดือนสำหรับผู้ประกอบการจด VAT และคำนวณจากภาษีขายหักภาษีซื้อ ระบบมั่งมีต้องเก็บ snapshot ของ scope, rule version และ source lines ที่ใช้สร้างแต่ละแบบ ไม่คำนวณใหม่เงียบ ๆ หลังยื่นแล้ว

### 9.4 ภ.พ.36

คู่มือ FlowAccount แสดง state ที่ละเอียด:

~~~text
ค่าใช้จ่ายต่างประเทศ
  → ระบุคู่ค้า/บริการต่างประเทศและเอกสาร
  → รอยื่น ภ.พ.36
  → สร้างแบบ → รอชำระภาษี
  → ชำระแล้ว → รอใบเสร็จสรรพากร
  → บันทึกหลักฐาน
  → เลือกใช้สิทธิ์ภาษีซื้อใน ภ.พ.30 เมื่อเข้าเงื่อนไข
~~~

ระบบมั่งมีต้องไม่ตีความว่ารายการต่างประเทศทุกอันเป็น ภ.พ.36 อัตโนมัติ ต้องใช้ rule/evidence และ expert review สำหรับกรณีเฉพาะ

### 9.5 แหล่งกฎหมาย

กรมสรรพากรเผยแพร่แบบ ภ.พ.30 และ ภ.พ.36 และประมวลรัษฎากรแยกความรับผิด VAT ของขายสินค้า บริการ และนำเข้า การออกแบบจึงต้องเก็บ event date หลายชนิด เช่น document date, supply/service date, payment date, tax invoice date และ filing period แทนการใช้วันที่เดียวทุกกรณี

## 10. ภาษีหัก ณ ที่จ่าย

หน้าสร้าง WHT มีผู้ถูกหัก วันที่ แบบฟอร์ม ประเภทเงินได้ อัตรา จำนวนเงิน VAT included/excluded ฐาน และยอดภาษีที่หัก หน้า report มี action ยื่นออนไลน์และเลือก ภ.ง.ด.3/53 คู่มือในระบบกล่าวถึง RD Prep, 50 ทวิ, ภ.ง.ด.1 และ ภ.พ.36

กฎที่มั่งมีต้องมี:

- แยกผู้รับเงินบุคคลธรรมดากับนิติบุคคลเพื่อเลือกแบบที่เป็นไปได้ แต่ยังต้องตรวจประเภทเงินได้และข้อยกเว้น
- WHT เกิดตาม payment event ไม่ใช่แค่มี vendor bill
- รองรับ WHT แยกบรรทัดและท้ายเอกสารโดยไม่ double count
- สร้างหนังสือรับรอง 50 ทวิและ package ยื่นจาก immutable payment/tax snapshot
- รายรับที่ถูกลูกค้าหัก WHT ต้องรองรับ Bank net + WHT receivable = Invoice total
- แบบ/อัตรา/กำหนดเวลาทั้งหมดต้อง versioned และผู้เชี่ยวชาญอนุมัติ ห้ามให้โมเดลภาษาเลือกแล้ว post เอง

## 11. สมุดรายวัน ผังบัญชี และงบการเงิน

### 11.1 สมุดรายวันที่พบ

- สมุดรายวันทั่วไป (JV)
- สมุดรายวันซื้อ (UV)
- สมุดรายวันขาย (SV)
- สมุดรายวันจ่าย (PV)
- สมุดรายวันรับ (RV)

รายการทุกสมุดใช้หน้า list รูปแบบเดียวกัน: วันที่ เลขเอกสาร คำอธิบาย ยอดสุทธิ และสถานะ

### 11.2 ฟอร์ม Journal

ฟอร์มสร้างรายการมีวันที่ ผู้ติดต่อ เลขอ้างอิง คำอธิบาย แถวรหัส/ชื่อบัญชี เดบิต เครดิต คำอธิบายย่อย หมายเหตุ โน้ตภายใน และไฟล์แนบ มี:

- บันทึกร่าง
- อนุมัติแล้วสร้างใหม่
- ใช้คำอธิบายเดียวกัน
- เติมผลต่างอัตโนมัติในแถวใหม่
- ช่องจำนวนรองรับสูตร

นี่ช่วยให้คีย์เร็วสำหรับนักบัญชี แต่มั่งมีควรบังคับ invariant ว่า debit = credit, period เปิด, account active, company/branch ถูกต้อง และ posted entry แก้ไม่ได้โดยตรง

### 11.3 ผังบัญชีและบัญชีแยกประเภท

หน้าบัญชีแยกประเภทแสดงรหัส ชื่อ กลุ่ม หมวด ยอดคงเหลือ และ drill-down พร้อมบริหารผังบัญชี ผู้ใช้ธุรกิจไม่ควรต้องเลือก account code ทุกครั้ง; mapping จากหมวดภาษาคนไป account/tax code ต้องเป็น rule data ที่นักบัญชีตรวจได้

### 11.4 รายงานบัญชี

- งบทดลอง: เลือกช่วงเวลา แสดง draft/ยอดศูนย์ และมุมมองตามสมุดรายวันหรือตามเอกสาร
- งบกำไรขาดทุน: เปรียบเทียบงวดก่อน แสดงยอดศูนย์/ก่อนปิด
- งบฐานะการเงิน: เปรียบเทียบงวดก่อน
- รายการเคลื่อนไหว: วันที่ ลำดับ เอกสาร คำอธิบาย และยอดสุทธิ
- รายได้และค่าใช้จ่าย: สร้างรายการปิดบัญชี แสดงรอบปิด รายได้ ค่าใช้จ่าย และสถานะ

### 11.5 งวดบัญชี ล็อกงวด และยอดเริ่มต้น

- ตั้งเดือนสิ้นปีบัญชีและวันที่เริ่มบริษัท
- ล็อกงวดถึงวันที่กำหนด พร้อมเหตุผลการแก้ไข/ปลดล็อก
- ตั้งยอดเริ่มต้นด้วยบัญชี เดบิต เครดิต และอนุมัติ
- คู่มือปิดบัญชีระบุว่า draft ยังไม่กระทบรายงาน การอนุมัติสร้างรายการปิดใน JV และการเปิดรายการใหม่หลังปิดแต่ไม่ล็อกสามารถทำให้ต้องปิดผลต่างซ้ำ

มั่งมีควรใช้ hard gate: ยื่นภาษี/ปิดงบแล้วต้องล็อก scope ที่เกี่ยวข้อง การปลดล็อกต้องมีสิทธิ์สูง เหตุผล และ audit event

## 12. สินค้า คลัง และต้นทุน

### 12.1 Product master

สินค้าแบ่งเป็นบริการ สินค้าไม่นับสต็อก และสินค้านับสต็อก มีชื่อ SKU หมวด หน่วย Barcode รูป ราคา VAT คำอธิบาย และบัญชีรายได้ คู่มือ/announcement รองรับหลายหน่วยและ conversion

### 12.2 คลังสินค้า

- สร้างได้หลายคลัง; UI ระบุสูงสุด 50 คลัง
- มีคลังหลักและคำเตือนว่า Marketplace/OpenAPI/POS/Import บางเส้นทางตัดคลังหลัก
- คลังเก็บรหัส ที่อยู่ และผู้ดูแลได้
- เอกสารขาย/ซื้อบางชนิดเลือกคลังและตัด/เพิ่ม stock จากคลังนั้น

### 12.3 Movement

- ใบรับสินค้าเพิ่ม stock
- ใบขายที่เกี่ยวข้องลด stock
- ใบลด/เพิ่มหนี้อาจคืนหรือปรับ stock ตามตัวเลือก
- ใบโอนย้ายมีต้นทาง ปลายทาง จำนวน หน่วย ต้นทุน และสถานะ
- ปรับยอดรองรับเพิ่ม/ลดพร้อมเหตุผล จำนวน และต้นทุน
- Low-stock เทียบ on-hand กับ minimum quantity

ข้อสรุปทางสถาปัตยกรรม: StockMovement ต้อง immutable และเป็น source of truth; StockBalance เป็น projection ที่สร้างซ้ำได้ เอกสารธุรกิจส่ง movement command แบบ idempotent ห้ามแก้จำนวนคงเหลือตรง ๆ

### 12.4 Costing

รายงานสินค้าคงเหลือแสดงราคาเฉลี่ยและมูลค่าคงเหลือ แต่คู่มือปิดงบสาธารณะกล่าวถึง FIFO แบบ periodic จึงไม่ควรสรุป algorithm จาก UI เพียงอย่างเดียว สำหรับมั่งมีต้องเลือกและประกาศ costing policy ต่อบริษัท/สินค้าอย่างชัดเจน พร้อม golden cases สำหรับ purchase, sale, return, transfer, adjustment, negative stock และ cutover

## 13. สินทรัพย์ถาวร

ระบบมี:

- ทะเบียนสินทรัพย์ แยกใช้งานอยู่ ไม่ใช้งาน และจำหน่าย
- รหัส ชื่อ หมวด วันที่เริ่มใช้ ราคาซื้อ มูลค่าตามบัญชี และสถานะ
- หมวดสินทรัพย์ที่ map บัญชีสินทรัพย์ ค่าเสื่อมราคา และค่าเสื่อมราคาสะสม
- คำนวณค่าเสื่อมรายงวด และมี action แยกเพื่อบันทึกเข้า GL

สำหรับมั่งมีต้องแยก asset acquisition, capitalization approval, depreciation run, transfer, impairment/adjustment, disposal/write-off และ gain/loss พร้อม evidence และ reversal

## 14. การตั้งค่าที่เป็นตัวควบคุมความถูกต้อง

| Setting | ผลกระทบ |
|---|---|
| ราคา VAT/Discount/WHT ต่อบรรทัดหรือท้ายเอกสาร | เปลี่ยนวิธีคำนวณและหน้าตาฟอร์ม ต้อง version ต่อเอกสาร |
| เลขรันเอกสารและการ reset | กระทบ audit/กฎหมาย ต้อง unique ตาม company/branch/type/series |
| การรับรู้รายได้ที่ใบวางบิล/ใบแจ้งหนี้ | กระทบ journal และรายงาน ต้องให้ Accountant อนุมัติ policy |
| ข้อมูลรับชำระ | ใช้ในเอกสารและ payment link ต้องปกปิดข้อมูลตามสิทธิ์ |
| สกุลเงิน | ต้องเก็บ currency, rate source, rate time, base amount และ realized/unrealized FX |
| คลังหลัก/negative stock | กระทบ stock และ COGS ต้องมี policy/audit |
| งวดบัญชี/ล็อกงวด/ยอดเริ่มต้น | คุม cutover, posting และงบทั้งหมด |
| โหมดธุรกิจ/นักบัญชี | เปลี่ยนคำศัพท์และระดับรายละเอียด แต่ห้ามเปลี่ยนข้อมูลจริง |

หลักสำคัญ: ค่า setting ที่กระทบเอกสาร/ภาษี/บัญชีต้องถูก snapshot ตอนสร้างหรือ finalize เอกสาร การเปลี่ยนค่าใหม่ห้ามแก้ผลย้อนหลังอย่างเงียบ ๆ

## 15. จุดที่อาจทำให้ผู้ใช้ 40+ สับสน

รายการนี้เป็น INFERENCE จากโครงสร้างหน้าจอและต้อง usability test เพิ่ม:

| จุดเสี่ยง | เหตุผล | แนวทางของมั่งมี |
|---|---|---|
| เมนูด้านข้างยาวและแบ่งตามศัพท์บัญชี | ผู้ใช้ไม่รู้ว่าจะเริ่มที่ “ขาย”, “รับเงิน” หรือ “บัญชี” | หน้าแรกเป็น Inbox งานวันนี้ 4–6 งาน พร้อมค้นหาเมนู |
| ฟอร์มเดียวมี field สูงมาก | มือใหม่กลัวกรอกผิดและไม่รู้ช่องบังคับ | Progressive disclosure; เริ่ม 5–7 ช่องสำคัญ แล้วเปิด “รายละเอียดสำหรับนักบัญชี” |
| VAT/WHT/ส่วนลดหลายโหมด | เลือกผิดแล้วผลรวมต่าง | แสดงตัวอย่างยอดทันทีและคำว่า “มี VAT/ไม่มี VAT” ต่อรายการ |
| สถานะเอกสารหลายชุด | ธุรกิจ ภาษี จ่ายเงิน และบัญชีอาจไม่ตรงกัน | แสดง progress เดียว แต่เปิดรายละเอียด 4 สถานะแยกเมื่อกดดู |
| การย้อน/รีเซ็ตเอกสาร | ผู้ใช้อาจคิดว่าเป็น Undo ธรรมดา | บอกผลกระทบก่อนยืนยันและสร้าง reversal/audit |
| รายงานต้องเลือกช่วงแล้วกดแสดงผล | ผู้ใช้อาจเห็นหน้าว่างและคิดว่าไม่มีข้อมูล | ใช้ค่าเริ่มต้นเดือนนี้และ empty state ที่บอกวิธีแก้ |
| ตั้งค่าบัญชีมีผลกว้าง | เจ้าของอาจเปิด/ปิดโดยไม่เข้าใจผล | จำกัดสิทธิ์, preview ผลกระทบ และให้ Accountant approve |

## 16. สิ่งที่มั่งมีควรทำให้ดีกว่า

### 16.1 Task-first Accounting Home

หน้าแรกไม่เริ่มจากเมนู แต่เริ่มจากคำถาม:

- วันนี้มีอะไรต้องตรวจ
- เงินเข้าไหนยังไม่รู้ที่มา
- ใบเสร็จไหน AI ไม่มั่นใจ
- ใบกำกับภาษีซื้อไหนยังขาด
- ลูกหนี้ไหนเกินกำหนด
- ธนาคารเดือนไหนยังกระทบยอดไม่ครบ
- งวดนี้ปิดไม่ได้เพราะอะไร

### 16.2 One Source, Four Views

รายการเดียวแสดงได้ 4 มุมโดยไม่ทำข้อมูลซ้ำ:

1. มุมเจ้าของ: ขายอะไร/จ่ายอะไร/รับเงินหรือยัง
2. มุม Admin: เอกสารครบหรือไม่ ต้องตามใคร
3. มุมนักบัญชี: tax code, account mapping, posting และ reconciliation
4. มุมผู้สอบทาน: source, version, actor, time, reason และ evidence

### 16.3 Exception-first Automation

AI อ่านและระบบจับคู่ให้อัตโนมัติ แต่คนทำเฉพาะ exception:

- ช่องที่ความมั่นใจต่ำ
- ยอดไม่ตรงเอกสาร
- mixed VAT
- ไม่พบ invoice/order
- transfer/capital/loan/deposit ที่แยกไม่ออก
- period locked หรือ rule version ไม่พร้อม

### 16.4 Mangmee Brain เป็นทางเข้า ไม่ใช่ฐานข้อมูลใหม่

ผู้ใช้ถามภาษาคน เช่น “เดือนนี้ต้องจ่ายภาษีอะไร”, “ลูกค้าคนไหนค้างจ่าย”, “ใบนี้ VAT ทำไมไม่ตรง” สมองมั่งมีต้อง:

- อ่านข้อมูลบริษัทผ่าน permission-checked tools
- อธิบายจาก deterministic result พร้อมช่วงเวลาและ source
- ใช้ approved knowledge สำหรับหลักบัญชี/ภาษี
- เปิดหน้าแก้ exception ที่ถูกต้อง
- ไม่คำนวณตัวเลขใหม่จากความจำของโมเดล
- ไม่อนุมัติ ยื่นภาษี หรือ post รายการเสี่ยงสูงแทนคนโดยไม่มี explicit confirmation และสิทธิ์

## 17. Gap baseline ของมั่งมี

จาก REPOSITORY_BASELINE โดยเฉพาะผลตรวจ 2026-08-03 ระบบมั่งมีมีฐานเอกสาร ค่าใช้จ่าย OCR, VAT/WHT data, bank reconciliation draft, ผังบัญชี และ ledger บางส่วน แต่ในวันตรวจยังมี blocker สำคัญ:

- posting rule และ account mapping ไม่พร้อมสำหรับบริษัทจริง
- เอกสารขายบางเส้นทางไม่มีทาง post จาก UI
- JV ไม่มี UI
- งบยังขาด opening/YTD/roll-forward และ balance assertion
- ปิดปี/ยอดยกมายังไม่ครบ
- tax report/package/PDF/e-filing ยังไม่พร้อม
- bank adjustment ยังไม่เข้าบัญชีครบ
- inventory ยังขาด costing/COGS สำหรับงานบัญชีเต็มรูปแบบ
- fixed assets และ depreciation เดิมยังไม่พร้อม
- สิทธิ์ผู้ใช้บัญชี/การเงินมี gap

Finding เหล่านี้เป็น baseline เก่าและต้อง revalidate บน current SHA ก่อนใช้เป็นคำตัดสิน release แต่ห้ามโฆษณาว่า “ทำบัญชี/ยื่นภาษีครบ” จนมี evidence ใหม่ปิดทุก gate

## 18. ข้อจำกัดของผลสำรวจ

- บริษัททดสอบมีข้อมูลธุรกรรมน้อยหรือว่างหลายหน้า จึงไม่เห็นรายการจริงครบทุกสถานะ
- ไม่ได้สร้างเอกสาร ไม่เปลี่ยนสถานะ ไม่อนุมัติ ไม่รับ/จ่ายเงินจริง และไม่ยื่นแบบภาษี
- ไม่ได้เชื่อมธนาคารหรือ Marketplace จริง และไม่ได้ทดสอบ duplicate/retry/failure
- ไม่ได้ตรวจ package entitlement และสิทธิ์ทุก role
- ไม่ได้ตรวจ Mobile App, POS, Payroll, AutoKey แยกเป็นระบบเต็ม
- ไม่ได้ยืนยัน algorithm ต้นทุนจาก transaction จริง
- ฟังก์ชันที่เห็นจากชื่อวิดีโอ/announcement ยังเป็น NOT_VERIFIED จนกว่าจะมี workflow evidence
