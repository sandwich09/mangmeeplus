## 1. ข้อสรุปหลัก (TL;DR)

1. **สรรพากรไม่รับ "ไฟล์ ภ.พ.30"** — ภ.พ.30/ภ.พ.36/ภ.ง.ด.51 เป็นการคีย์ฟอร์มบน e-Filing เท่านั้น สิ่งที่ระบบต้องผลิตคือ **หน้าจอสรุปเลขให้ผู้ใช้คีย์ตาม** (แบบเดียวกับ FlowAccount/PEAK)
2. **ไฟล์ที่ยื่นได้จริงมีที่เดียว: ใบแนบ ภ.ง.ด.1/1ก/2/2ก/3/3ก/53** — ระบบ export `.txt/.csv` → ผู้ใช้ import เข้าโปรแกรม **RD Prep** ของสรรพากร (map คอลัมน์ได้ ไม่บังคับ layout ตายตัว) → ได้ `.rdx` → อัปโหลดบน e-Filing นี่คือฟีเจอร์ "ยื่นออนไลน์" ที่ FlowAccount/PEAK โฆษณา
3. **รายงานภาษีขาย/ภาษีซื้อ/สินค้าและวัตถุดิบ ไม่ต้องส่ง** — เป็นสมุดตามแบบท้ายประกาศฯ ฉบับที่ 89 เก็บที่สถานประกอบการ ≥5 ปี ให้เจ้าหน้าที่ตรวจ; ระบบต้องพิมพ์ได้ตรงแบบ + ลงรายการใน 3 วันทำการ + แก้ไขแบบไร้ร่องรอยไม่ได้
4. **เส้นทางอัตโนมัติจริงในปี 2569 มี 2 เส้น**: (ก) **e-Tax Invoice & e-Receipt ผ่าน Service Provider API** (XML ขมธอ.3-2560 + digital signature — SaaS เรียก REST ของ SP เช่น Leceipt/INET) และ (ข) **e-WHT ผ่านธนาคาร** (ธนาคารหัก-นำส่ง-รายงานแทน → **ไม่ต้องออก 50 ทวิ และไม่ต้องยื่น ภ.ง.ด.3/53** สำหรับรายการนั้น + อัตราลดเหลือ 1% ถึง 31 ธ.ค. 2570)
5. **RD e-Filing Open API มีจริง** (ยื่น ภ.พ.30/ภ.พ.36/ภ.ง.ด.54/90/91/94 ทาง REST) แต่จำกัด 3 บทบาท: ผู้ให้บริการตัวแทนที่ได้รับอนุมัติ / ผู้ให้บริการจัดเตรียมข้อมูล (บุคคลธรรมดาเท่านั้น) / นิติบุคคลยื่นของตัวเอง — ไม่ใช่ API เปิดให้ software ยื่นแทนลูกค้าได้ทันที
6. **ลำดับการกรอกข้อมูลที่ตลาดพิสูจน์แล้ว**: FlowAccount = "ตัวตนภาษีขั้นต่ำก่อนออกใบกำกับ ที่เหลือ lazy สร้างตอนออกเอกสาร แล้วตรวจความครบย้อนหลังตอน export"; PEAK = "ยืนยันตัวตนจากทะเบียนราชการ + นโยบายก่อน + ยอดยกมา 8 ขั้นสำหรับบริษัทย้ายระบบ" — ระบบเราควรอยู่กึ่งกลาง (ดู §5)
7. ช่องว่างของ WatchDog-BMS ที่ขวางทางทั้งหมดนี้ตรงกับ RA ที่ประเมินไว้แล้ว: **RA-23** (กรอกตัวตนภาษีไม่ได้) ขวาง Step 0, **RA-13** (ไม่มีเอกสาร/PDF ไทย) ขวางทุก output, **RA-18/19/20** ขวางใบแนบ ภ.ง.ด., **RA-08** ขวางยอดยกมา

## 3. FlowAccount vs PEAK: ลำดับการกรอกที่ใช้จริง (สรุปจาก help center ทั้งสองค่าย)

**FlowAccount — document-first, เกือบทุกอย่าง lazy:**
1. สมัคร → ได้บริษัทเปล่าทันที (ถามแค่ชื่อ/อีเมล)
2. **ตัวตนภาษี = เงื่อนไขเดียวก่อนออกใบกำกับภาษี**: ชื่อ TH/EN, ที่อยู่, เลขผู้เสียภาษี, สนญ./รหัสสาขา (+ ต้องเป็นแพ็กเกจเสียเงิน)
3. หัวเอกสารเป็นสวิตช์ VAT: ค่า default คือเอกสารรวม "ใบกำกับภาษี/ใบเสร็จรับเงิน"; ธุรกิจไม่จด VAT เปลี่ยนหัวเป็น "ใบแจ้งหนี้" ทั้ง chain
4. ผู้ติดต่อ/สินค้า **สร้าง inline ตอนออกเอกสาร** — บังคับครบ (เลขภาษี+สาขา+ที่อยู่) เฉพาะเมื่อออกใบกำกับเต็มรูป และถูกตรวจย้อนหลังอีกครั้งตอน export ใบแนบ ภ.ง.ด.
5. ค่าใช้จ่าย: หมวดหมู่ = mapping GL เพียงจุดเดียวที่ผู้ใช้เห็น; WHT แนะนำอัตราตามลักษณะจ่าย (ขนส่ง 1, โฆษณา 2, บริการ/ฟรีแลนซ์ 3, เช่า 5); ออก 50 ทวิ ได้; AutoKey OCR
6. รายเดือน: รายงานภาษีขาย/ซื้อ (PDF/Excel) → สร้าง "แบบยื่นภาษีรายเดือน" ภ.พ.30 (สรุปให้คีย์ + สถานะยื่นแล้ว + ลงบัญชีปิดยอดอัตโนมัติ) → **ดาวน์โหลด .txt ภ.ง.ด.3/53 เข้า RD Prep**
7. บัญชีลึก (ผัง, ยอดเริ่มต้น, ล็อกงวด, งบ) → ปล่อยให้นักบัญชีทำทีหลัง; double-entry ทำงานเบื้องหลังอัตโนมัติ (สมุดรายวัน 5 เล่ม)

**PEAK — identity-first + ยอดยกมาเป็นระบบ:**
1. ตอนสร้างกิจการบังคับ: **เลขทะเบียน 13 หลัก (auto-fill ชื่อ+ที่อยู่จากทะเบียนราชการ) + สถานะจด VAT**
2. นโยบายก่อนใช้: เลขรันเอกสาร, ตั้งค่าใบกำกับภาษี, ราคารวม/แยก VAT default, ล็อกงวด, แบบฟอร์มรองรับ e-Tax
3. **ยอดยกมา 8 ขั้น (แนวทางที่ควรลอก)**: เตรียม TB ณ วันก่อนเริ่ม → ผู้ติดต่อ (ค้นทะเบียน) → สินค้า+สต๊อกยกมา → ช่องทางการเงิน → ลูกหนี้ยกมา (invoice ย้อนหลัง เพื่อให้ aging ทำงาน) → เจ้าหนี้ยกมา (expense ค้างจ่าย) → สินทรัพย์ยกมา → JV ปรับให้ TB ตรงกับระบบเดิม
4. เอกสารแยกตาม tax point ตามกฎหมาย: ใบแจ้งหนี้/ใบกำกับภาษี (ส่งมอบของ ม.78), ใบเสร็จ/ใบกำกับภาษี (รับเงิน ม.78/1 บริการ), ใบกำกับภาษีแยก; อนุมัติแล้วลง GL อัตโนมัติ เห็นบัญชีระดับบรรทัด
5. ภาษีเป็นเอกสารชั้นหนึ่ง: แบบ ภ.พ.30 มี Smart Validation + ยื่นปกติ/เพิ่มเติม/ล่าช้า + ลงบัญชีปิดยอด; **Text File ภ.ง.ด.2/3/53**; ทะเบียน "ถูกหัก ณ ที่จ่าย" ไว้เครดิต CIT (ฝั่งที่เราไม่มี — RA-22)
6. e-Tax: ทั้ง by Time Stamp (ผูก Gmail ที่ลงทะเบียน ก.อ.01) และ **ผ่าน SP (INET) แบบ XML** + export PDF/A-3

## 4. Template ข้อมูลที่ต้องเก็บให้ครบ (ย้อนจากปลายทาง §2)

**ก. บริษัท (Step 0 — ก่อนออกเอกสารใบแรก):** เลขผู้เสียภาษี 13 หลัก · ชื่อนิติบุคคล TH/EN · ที่อยู่จดทะเบียน · สถานประกอบการ: สนญ./สาขา + รหัส 5 หลัก ต่อแห่ง · สถานะจด VAT + วันมีผล · เดือนเริ่มปีบัญชี · เลขรันเอกสารต่อชนิด · (ถ้าใช้ e-Tax: ใบรับรองอิเล็กทรอนิกส์ + ทะเบียน บ.อ.01) → ปัจจุบันติด **RA-23** (CompanyTaxProfile อ่านอย่างเดียว) + **RA-12/17** (สาขาไม่ไหลเข้า tax event)

**ข. คู่ค้า (ผู้ติดต่อ):** ประเภท **นิติบุคคล/บุคคลธรรมดา** (ตัวกำหนด ภ.ง.ด.53/3 — แก้ RA-18 ต้องมี field นี้) · เลขภาษี 13 หลัก · สนญ./สาขา · **ที่อยู่เต็ม** (ใบแนบ ภ.ง.ด. + ใบกำกับเต็มรูปต้องใช้) · validate กับ **RD TIN/VAT web service ฟรี** (rdws.rd.go.th — PEAK ใช้ auto-fill ชื่อ+ที่อยู่; ควรทำเหมือนกัน) · เงื่อนไขเครดิต

**ค. สินค้า/บริการ:** ชื่อ · หน่วย · ราคา · ประเภท VAT ต่อรายการ (7/0/ยกเว้น) · นับสต๊อก/ไม่นับ (+ ต้นทุน เมื่อทำ RA-31)

**ง. เอกสารขาย:** ชนิดตาม tax point (T02 ใบแจ้งหนี้/ใบกำกับ, T03 ใบเสร็จ/ใบกำกับ, ใบกำกับแยก, ใบลดหนี้/เพิ่มหนี้อ้างต้นฉบับ) · snapshot ผู้ซื้อครบ ม.86/4: ชื่อ+เลขภาษี+**ที่อยู่+สนญ./สาขา** (แก้ RA-13 snapshot) · ต้นฉบับ/สำเนา

**จ. จ่ายเงิน/หัก ณ ที่จ่าย:** วันที่จ่าย (พ.ศ.) · ประเภทเงินได้ (ม.40) · อัตรา (ตาราง 1/2/3/5% เก็บเป็น config — RA-24) · เงื่อนไขการหัก (หักฯ/ออกให้ตลอดไป/ออกให้ครั้งเดียว) · จำนวนจ่าย/ภาษีหัก → ต่อแถวใบแนบ 1 แถว (แก้ RA-19: ห้าม drop rate; RA-20: AP ต้องเข้า)

**ฉ. ยอดยกมา (บริษัทย้ายระบบ):** TB ณ วันก่อนเริ่ม · ลูกหนี้/เจ้าหนี้รายใบ · สต๊อกจำนวน+ต้นทุน · ทะเบียนสินทรัพย์ · (RA-08/04)

**ช. ปฏิทิน/อัตราเป็น config ไม่ใช่โค้ด:** อัตรา VAT/WHT · กำหนดยื่นต่อแบบ · วันสิ้นสุดโครงการ +8 วัน (31 ม.ค. 2570) · โครงการ สปส. +7 วันทำการ (ธ.ค. 2572) · e-WHT 1% (31 ธ.ค. 2570) → ตาราง `TaxRateConfig`/`TaxCalendarRule` ที่มีอยู่แต่เป็น dead code (RA-24) คือที่ลงของข้อมูลชุดนี้พอดี

## 6. เส้นทางส่งอัตโนมัติ จัดลำดับ ง่าย → ยาก

| # | เส้นทาง | ความพยายาม | เงื่อนไข | หมายเหตุ |
|---|---|---|---|---|
| 1 | **สร้างไฟล์ให้ผู้ใช้อัปโหลดเอง** (.txt ใบแนบ ภ.ง.ด.1/3/53 → RD Prep) | วัน–สัปดาห์ | ไม่ต้องขออนุมัติใคร | เท่ากับที่ FlowAccount/PEAK ทำ; RD Prep map คอลัมน์ได้ → เลียน layout ของ vendor (pipe + header + วันที่ พ.ศ.) แล้วทดสอบกับ RD Prep รุ่น ≥ 24 ก.ค. 2569 |

## 7. สิ่งที่งานวิจัยนี้เปลี่ยนจาก readiness assessment

- **RA-15 แคบลง**: ไม่ต้องทำ "ไฟล์ยื่น ภ.พ.30" (ไม่มีอยู่จริง) — เป้าคือ .txt ใบแนบ ภ.ง.ด. + หน้าสรุป ภ.พ.30 เท่านั้น
- **RA-21 (50 ทวิ) ได้ spec ชัด**: 2 ฉบับ + คู่ฉบับ + เลขลำดับ/เล่ม + เงื่อนไขการหัก + ลายเซ็นสแกนได้ (ประกาศฯ ฉบับที่ 62); การส่ง PDF ทางอีเมลอย่างเดียว **ยังไม่มีฐานกฎหมายรองรับชัด** — ทางไร้กระดาษที่สะอาดคือ e-WHT
- **RA-14 ได้ spec ชัด**: คอลัมน์รายงานภาษีขาย/ซื้อตามประกาศ 89+197 (มีเลขภาษี+สนญ./สาขาคู่ค้า) + กติกา 3 วันทำการ + ห้ามแก้ไร้ร่องรอย → การออกแบบ period-lock/reversal ที่มีอยู่รองรับข้อกำหนด software class ก–ง ได้พอดี
- **RA-24 ได้รายการ config ที่ต้องเก็บ**: วันสิ้นสุด +8 วัน (31 ม.ค. 2570), สปส. +7 วันทำการ (ธ.ค. 2572), e-WHT 1% (31 ธ.ค. 2570) — ยืนยันหลักการ "ห้าม hardcode"
- **ภ.ง.ด.50 มีข่าวดี**: ยื่นงบผ่าน DBD e-Filing แล้วไม่ต้องแนบงบซ้ำที่ RD (ประกาศ 318) — แต่ต้องมีปิดปี (GAP-05/RA-09) ก่อนเสมอ

## 8. ประเด็นที่ยังยืนยันไม่ได้ (ต้องตามต่อก่อนเขียน spec)

1. ประกาศกระทรวงการคลัง (ฉบับที่ 9) ลง 18 พ.ย. 2568 — อาจแก้วันสิ้นสุดโครงการ +8 วัน (หน้า archive ของ RD โหลดไม่ได้)
2. Layout ไฟล์ สปส.1-10 (.txt/.dat) — spec ไม่เผยแพร่สาธารณะ ต้องขอจาก สปส. หรือเทียบ export ของ payroll vendor
3. Layout .txt ที่ RD Prep รับ — กลไกปัจจุบันคือ map คอลัมน์เอง ไม่มี layout บังคับ; ต้อง fix layout ของเราแล้วทดสอบจริงกับ RD Prep (encoding แนะนำ UTF-8 BOM)
4. รายชื่อ/จำนวน Service Provider ปัจจุบัน + ราคา cert TDID/INET ปัจจุบัน (หน้าเป็น JS SPA) — ตรวจใน browser
5. เงื่อนไขรับเข้าเป็น "ผู้ให้บริการตัวแทน" ของ e-Filing Open API — ต้องติดต่อ helpdesk
6. รายชื่อธนาคาร e-WHT ปัจจุบัน (list 11 แห่งเป็นข้อมูลปี 2563) + spec ไฟล์/API ของแต่ละธนาคาร (อยู่หลัง onboarding)
7. พ.ร.ฎ./กฎกระทรวง e-WHT 1% ปี 2569–2570 อยู่ขั้น ครม. อนุมัติร่าง (16 มิ.ย. 2569) — ยังไม่ยืนยันประกาศราชกิจจาฯ
