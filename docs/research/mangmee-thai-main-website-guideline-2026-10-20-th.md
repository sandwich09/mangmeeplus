## 1. ทิศทางที่บันทึกไว้

ใช้ **mangmeeplus.com เป็นเว็บหลักสาธารณะ** ให้คนที่ยังไม่รู้จักเข้าใจผลิตภัณฑ์ เห็นวิธีใช้ ราคา และทางเริ่มต้น พร้อมลิงก์ **เข้าสู่ระบบ** ไป `/login` สำหรับลูกค้าเดิม คงเส้นทาง ERP/API/auth เดิม ส่วน `official.mangmeeplus.com` เตรียมย้ายและ redirect เมื่อปลายทางพร้อมตาม spec การย้าย URL

ยังใช้หน้าแรกหน้าเดียวเป็นจุดขายหลัก เมนูเลื่อนไปยังส่วนต่าง ๆ ในหน้าได้ การเปลี่ยนโดเมนหลักไม่ได้อนุมัติให้เพิ่มหลาย landing pages หรือย้ายแอปไป subdomain ใหม่โดยอัตโนมัติ

คำอธิบายทิศทางภาพ: **“ผู้ช่วยงานรายจ่ายที่ใช้เป็น เห็นของจริง และตรวจสอบได้”** ใช้ภาษาไทยธรรมดา ภาพใบเสร็จและ LINE ที่คุ้นตา บุคลิกเขียวสะอาด อ่านง่าย มีความเป็นคน

เป้าหมายของหน้าคือให้ผู้ชมตอบได้ว่า “ช่วยงานอะไร เหมาะกับฉันไหม ใช้อย่างไร และเริ่มตรงไหน” การหยุดดูต้องนำไปสู่ความเข้าใจและการใช้งาน ไม่วัดความสำเร็จจาก animation หรือเวลาค้างหน้าอย่างเดียว

## 2. กลุ่มเป้าหมายและปัญหาที่ใช้ตั้งต้น

กลุ่มต่อไปนี้เป็น working segments จากขอบเขตผลิตภัณฑ์และเอกสารภายใน ยังไม่ใช่ผลสำรวจตลาดหรือหลักฐานว่ากลุ่มใดมีความต้องการซื้อมากที่สุด

| ลำดับ | คนที่ต้องสื่อสารด้วย | สิ่งที่ควรเข้าใจ | ภาพ/ตัวอย่างที่เหมาะ |
|---|---|---|---|
| หลัก | เจ้าของกิจการไทยที่ดูแลรายจ่ายเองหรือมีทีมเล็ก | ส่งใบเสร็จให้ AI ช่วยเตรียมข้อมูลได้ และยังตรวจควบคุมงานได้ | ซื้อของเข้าร้าน → ส่งใบเสร็จ → ตรวจข้อมูล |
| รอง | พนักงานหรือแอดมินที่ส่งเอกสาร | เริ่มส่งจากที่ไหน ข้อมูลใดต้องตรวจ และใครทำต่อ | หน้าส่งเอกสารและสถานะรอตรวจที่มีจริง |
| ผู้ร่วมตัดสินใจ | ผู้ดูแลบัญชี/ผู้ตรวจรายจ่าย | เห็นต้นฉบับ แก้ข้อมูล และทำงานตามสิทธิ์ได้อย่างไร | ต้นฉบับเทียบข้อมูลก่อนยืนยัน |

ตัวอย่างร้านอาหาร ร้านค้า และธุรกิจบริการใช้เพื่ออธิบายสถานการณ์เท่านั้น ไม่อ้างว่ารองรับ POS สต็อก หรือบัญชีครบวงจรของทุกธุรกิจ ไม่กำหนดว่าคนไทยทุกคนชอบสี มุก หรือรูปแบบเดียวกัน

ฐานขอบเขต: [feature readback 6 ตุลาคม](../agent-memory/mangmee-ai-live-feature-structure-2026-10-06.md) เป็นประวัติ ต้องตรวจ current release ก่อนเผยแพร่ claim; [strategy assessment](mangmee-strategy-handoff-assessment-2026-10-03-th.md) แยกผลิตภัณฑ์รายจ่ายปัจจุบันจากข้อเสนอ Financial Intelligence ในอนาคต

## 4. ตัวอย่างเว็บไทยที่ตรวจวันที่ 20 ตุลาคม 2026

ตรวจเนื้อหาสาธารณะที่เว็บแสดงผ่าน web reader ไม่ได้เข้าระบบซื้อบริการหรือทดสอบ conversion ของคู่เทียบ การมีองค์ประกอบเหล่านี้บนเว็บพิสูจน์ได้เพียงว่าเขาใช้ ไม่ได้พิสูจน์ว่าองค์ประกอบนั้นทำให้คนชอบ

| เว็บ | รูปแบบที่พบ | สิ่งที่นำมาเป็นแนวทาง |
|---|---|---|
| [FlowAccount](https://flowaccount.com/) | แยกเข้าสู่ระบบ/สมัคร/สาธิต มีราคา ชื่อฟังก์ชันตามงาน และกลุ่มผู้ใช้งาน | แยกทางลูกค้าเดิมออกจากคนใหม่ และใช้ภาษางานของผู้ใช้ |
| [PEAK](https://www.peakaccount.com/) | เรียกประเภทซอฟต์แวร์ชัด แบ่งเจ้าของกิจการ/นักบัญชี มีตัวอย่าง วิดีโอผู้ใช้ การช่วยเหลือ และ FAQ | ให้ผู้ชมเห็นว่ามีคนดูแลและมีคำตอบก่อนตัดสินใจ |
| [Paypers](https://paypers.ai/) | สื่อสารงานเอกสารผ่าน LINE ใกล้หัวเรื่อง มีภาพงาน ลำดับวิธีใช้ และคำถามเรื่องข้อมูล/ราคา | แสดง input → output และทางเริ่มโดยไม่ต้องรู้ศัพท์เทคนิค |

ไม่ยืมตัวเลขผลลัพธ์ รีวิว โลโก้ลูกค้า หรือข้อเสนอทดลองใช้ฟรีของเว็บอื่นมาใช้กับมั่งมี ไม่รับรองคำอ้างประสิทธิภาพของคู่เทียบโดยไม่มีวิธีทดสอบของเขา เว็บ reader บางส่วนแสดงตัวนับ Paypers เป็น 0+ และราคากำลังโหลด จึงไม่ใช้เป็นข้อมูลจำนวนผู้ใช้หรือราคาปัจจุบัน

## 6. ข้อความหน้าแรกและทางเริ่มต้น

**ชุด A ที่เสนอให้ทำต้นแบบก่อน**

- ชื่อเหนือหัวเรื่อง: `มั่งมีพลัส (MangmeePlus) · ตัวช่วยจัดการใบเสร็จและรายจ่าย`
- H1: `ส่งใบเสร็จผ่าน LINE ให้ AI ช่วยอ่านข้อมูล`
- คำอธิบาย: `ถ่ายรูปใบเสร็จส่งผ่าน LINE ให้มั่งมีพลัสช่วยเตรียมรายการค่าใช้จ่าย คุณหรือผู้มีสิทธิ์ตรวจและแก้ไขก่อนยืนยัน`
- ปุ่มหลัก: `เริ่มใช้งานผ่าน LINE`
- ปุ่มรอง: `ดูตัวอย่างการใช้งาน` → ไปส่วน demo ในหน้า
- หัวเว็บ: `เข้าสู่ระบบ` → `/login`
- ข้อความใกล้ CTA: `ดูแพ็กเกจและเงื่อนไขก่อนเริ่มใช้งาน` → ไปส่วนราคา

ชุด B สำหรับเทียบความเข้าใจ: H1 `ใบเสร็จเข้าทาง LINE รายจ่ายเป็นรายการให้ตรวจ` พร้อมคำอธิบายและ CTA เดียวกับชุด A เปลี่ยนเฉพาะหัวเรื่องในการทดลอง ไม่เลือกจากความชอบของทีมอย่างเดียว

CTA หลักต้องต่อกับเส้นทางเริ่มใช้งานจริงของ system OA ไม่ใช้คำว่า “คุยทีมงาน” หากปลายทางเป็นบอต ไม่สัญญาว่า “ใช้ได้เลยโดยไม่สมัคร” หากยังต้องตั้งบริษัท/เลือกแพ็กเกจ ที่มาของเส้นทางและการปิด trial อยู่ใน [marketing README](../../../mangmee_web/README.md)

**กติกาภาษา**

| ใช้ภาษาแบบนี้ | ลด/แทนคำแบบนี้ |
|---|---|
| ส่งใบเสร็จ, ตรวจข้อมูล, แก้ไข, ยืนยันรายการ | OCR pipeline, ERP workflow, Agentic platform |
| AI ช่วยอ่านและเตรียมข้อมูล | AI ทำบัญชีจบทุกอย่าง |
| ดูต้นฉบับประกอบการตรวจ | แม่นยำ 100%, ถูกต้องทุกใบ |
| รอตรวจ / ยืนยันแล้ว ตามสถานะจริง | เสร็จแล้ว ทั้งที่ยังมีขั้นยืนยัน |
| ราคาและขอบเขตที่ประกาศตรงกับแพ็กเกจ | ยอดนิยม/ขายดี/คุ้มที่สุด ที่ไม่มีข้อมูลรองรับ |

ใช้ประโยคสั้นหนึ่งใจความต่อช่วง คำศัพท์บัญชีที่จำเป็นอธิบายด้วยตัวอย่าง ไม่ใส่ภาษาอังกฤษทุกหัวข้อ ไม่ทำภาพที่มีข้อความเป็นช่องทางอ่านเพียงอย่างเดียว

## 7. ลำดับหน้าและหลักฐานที่ต้องเตรียม

| ลำดับ | คำถามของผู้ชม | สิ่งที่หน้าเว็บต้องแสดง |
|---|---|---|
| 1. ช่วงแรก | “ช่วยฉันทำอะไร?” | ชื่อสินค้า หัวเรื่อง คำอธิบายสั้น ภาพงานเดียว CTA หลัก/ดูตัวอย่าง และเข้าสู่ระบบ |
| 2. Demo | “ใช้อย่างไร?” | ส่งใบเสร็จ → AI อ่าน/เตรียมรายการ → คนตรวจแก้และยืนยัน; แสดงสถานะและผู้มีสิทธิ์ตาม flow จริง |
| 3. สถานการณ์ | “ใช้กับงานฉันได้ไหม?” | 2–3 กรณีที่เปิดใช้จริง เช่นเจ้าของรวบรวมรายจ่ายเองและพนักงานส่งใบเสร็จ |
| 4. สิ่งที่ได้/ขอบเขต | “ได้อะไร และยังต้องทำอะไรเอง?” | ความสามารถที่ขายจริง พร้อมตัวอย่างและข้อจำกัดใกล้ claim |
| 5. หลักฐาน | “เชื่อได้แค่ไหน?” | demo จากระบบจริง วันที่/รุ่น และผล pilot ตามนิยาม; รีวิวลูกค้าเฉพาะที่มีจริงและได้รับอนุญาต |
| 6. ราคา | “จ่ายเท่าไร เหมาะกับงานแค่ไหน?” | ราคา รอบจ่าย โควตา ข้อจำกัด และสถานะขายจาก catalog เดิม เลือกแพ็กเกจตาม flow เดิม |
| 7. FAQ/ช่วยเหลือ | “ถ้าอ่านผิดหรือมีปัญหาทำอย่างไร?” | ตรวจแก้ได้อย่างไร, ต้องสมัครอะไร, ใช้ผ่าน LINE/เว็บตรงไหน, ข้อมูล/สิทธิ์, เกินโควตา, ติดต่อใคร; ตอบเฉพาะนโยบายที่ตรวจแล้ว |
| 8. ปิดหน้า | “เริ่มที่ไหน และใครเป็นเจ้าของบริการ?” | CTA เดิม ชื่อบริษัท ช่องทางจริง เงื่อนไข และนโยบายความเป็นส่วนตัว |

เมนูตั้งต้น: `วิธีใช้ / ใช้กับงานอะไร / ราคา / คำถามที่พบบ่อย` กับ `เข้าสู่ระบบ` ไม่ต้องเพิ่มทุก section ลงเมนู มือถือยังเข้าระบบได้ง่าย

**ชิ้นงานภาพหลัก:** ใช้เอกสารตัวอย่างที่ปลอดภัยหนึ่งใบ สลับภาพ LINE → ข้อมูลรอตรวจ → ยืนยัน การย่อเป็นสามช่วงมีไว้เล่าเรื่อง ไม่ได้ลดขั้นอนุมัติจริง ห้ามตัดต่อข้ามความผิดพลาดให้ดูแม่นทุกใบ หรือทำเวลาเร่งแล้วอ้างเป็นความเร็วจริง

**คลิปตั้งต้น:** ทดลองความยาวประมาณ 30–45 วินาที มีคำบรรยายไทย ปุ่มเล่น และภาพนิ่งที่อ่านแทนได้ ระยะเวลานี้เป็นขอบเขตต้นแบบ ไม่ใช่ความยาวที่งานวิจัยพิสูจน์ว่าดีที่สุด เสียงไม่เล่นเอง ตัวอย่างที่ยังเป็น mockup ต้องติดป้าย “ภาพจำลอง”

ถ้ายังไม่มีรีวิวลูกค้า ให้ใช้หลักฐานการสาธิตจริง ไม่ใส่ testimonial สมมติ ไม่ใช้ตรารับรอง ความปลอดภัยระดับธนาคาร หรือโลโก้หน่วยงานแทนหลักฐานที่ไม่ได้รับ

## 8. Guideline ภาพและการอ่านภาษาไทย

สีและฟอนต์ด้านล่างเป็นจุดเริ่มจาก source marketing ที่ตรวจ ไม่ใช่ผลโหวตความชอบผู้ใช้หรือการเปลี่ยน CI ของทั้งระบบ

| เรื่อง | แนวทางเริ่มต้น |
|---|---|
| สี | ใช้เขียวหลักเดิม `#046B29`, สีข้อความ `#0F1714`, เขียวเข้ม `#0B3D26`, พื้นขาว/เขียวอ่อน `#E9F2EC`; ใช้สีเน้นกับปุ่มและจุดสำคัญ |
| ภาพหลัก | ใบเสร็จและหน้าจอจริงที่อ่านรายละเอียดสำคัญได้ ภาพคน/มือใช้ผลิตภัณฑ์เมื่อมีสิทธิ์ใช้ภาพ |
| ตัวอักษร | เริ่มจาก Anuphan/Inter ที่มีอยู่ใน marketing source; ทดสอบอักษรไทยและตัวเลขจริงก่อนเพิ่มฟอนต์อื่น |
| ขนาดตั้งต้น | มือถือ H1 ประมาณ 32–40px, เนื้อหา 17–18px, line-height 1.6–1.75; เป็นค่าออกแบบทดลอง ต้องย่อขยายตามจอและข้อความ |
| การแบ่งบรรทัด | แบ่งเป็นหน่วยความหมาย ให้สระ/วรรณยุกต์ไม่ถูกตัด ไม่ยืดช่องไฟอักษรไทยแบบหัวข้ออังกฤษ ไม่ย่อเป็นภาพตัวหนังสือ |
| โครงหน้า | หนึ่งส่วนตอบหนึ่งคำถาม Desktop ให้ข้อความคู่ภาพงาน มือถือเรียงเรื่องตามลำดับ ไม่ย่อ dashboard ทั้งจอจนอ่านไม่ได้ |
| ปุ่ม | เป้าหมายภายในสูงประมาณ 48px และเว้นระยะกด; ไม่อ้างว่า 48px คือข้อกำหนด WCAG AA |
| Motion | ใช้แสดงการส่ง/อ่าน/ตรวจเมื่อช่วยอธิบาย หัวเรื่องอ่านได้ทันที รองรับ reduced motion และปุ่มหยุดเมื่อเข้าข่าย; งด scroll hijack และเสียงอัตโนมัติ |

W3C อธิบายว่ามีอักษรไทยทั้งแบบมีหัวและไม่มีหัว แต่ไม่ได้ยืนยันว่าฟอนต์รูปแบบหนึ่งเหมาะกับทุกกลุ่ม จึงทดสอบกับเจ้าของกิจการจริง ([Thai type styles](https://www.w3.org/International/articles/typography/fontstyles.en.html#thai))

เกณฑ์มาตรฐานที่ต้องตรวจแยกจากรสนิยม: ข้อความทั่วไป contrast อย่างน้อย 4.5:1; ข้อความใหญ่ตามนิยาม WCAG อย่างน้อย 3:1 ([Contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)); WCAG 2.2 AA กำหนดเป้าหมายกดขั้นต่ำ 24×24 CSS px โดยมีข้อยกเว้น ([Target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)); เนื้อหาเคลื่อนไหวอัตโนมัติบางกรณีต้องหยุด/ซ่อนได้ ([Pause, Stop, Hide](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html))

เทรนด์ที่เลือกใช้: ภาพจริง บุคลิกแบรนด์ชัด ข้อความกระชับ และ motion ที่อธิบายงาน เทรนด์ที่ไม่เลือกเป็นแกน: ตัวอักษรวิ่งจนอ่านยาก 3D หนักเต็มจอ สีหลายชุดแข่งกัน เคอร์เซอร์พิเศษ และกล่องแชทที่บังเนื้อหา ไม่มีหลักฐานจากงานนี้ว่าลูกค้าไทยต้องการสิ่งเหล่านั้น

| Personalization แบบผู้ใช้เลือกเอง — ทดลองเมื่อมีเหตุผล | กลุ่มงานต่างกันใน product docs; F3 ชี้ความสำคัญของความเกี่ยวข้อง | หากหน้าเดียวตอบไม่พอ ให้ผู้ชมเลือก “เจ้าของ / ผู้ส่งเอกสาร / ผู้ดูแลบัญชี” เพื่อดูตัวอย่างที่ตรงงาน | เป็นสมมติฐานผลิตภัณฑ์ ไม่ใช่ trend ที่พิสูจน์ในไทย; ยังไม่ต้องทำระบบคาดเดาตัวตน |

**ทิศทางที่ควรยืนระยะถึง 2028:** ทำให้เว็บอ่านเข้าใจได้ทั้งคนและเครื่องมือค้นหา ใช้ LINE ตามงานจริง และให้เจ้าของกิจการมองเห็นการควบคุมข้อมูลของตน บุคลิกภาพเปลี่ยนตามผลทดสอบได้โดยไม่ต้องเปลี่ยนคำสัญญาของผลิตภัณฑ์

ไม่ใช้คำทำนาย “SEO จะตาย”, “ทุกคนจะซื้อผ่าน agent”, “เว็บต้องเป็น chatbot ทั้งหน้า” หรือสถิติ forecast มาเขียนเสมือนเป็นพฤติกรรมที่เกิดแล้วในไทย

## 10. วิธีพิสูจน์กับกลุ่มเป้าหมายของเรา

ยังไม่มีผู้ร่วมทดสอบและยังไม่ได้ติดต่อบุคคลภายนอก แผนต่อไปนี้คือเกณฑ์สำหรับต้นแบบ ไม่ใช่ผลสำเร็จที่วัดแล้ว

1. **ทดสอบความเข้าใจรอบเล็ก:** เริ่ม 8 คน เช่นเจ้าของกิจการ 4 คน แอดมิน/ผู้ส่งเอกสาร 2 คน และผู้ดูแลบัญชี 2 คน ใช้มือถือและระดับความคุ้นเคยเทคโนโลยีที่ต่างกัน จำนวนนี้ใช้ค้นปัญหา ไม่ได้แทนประชากรไทย
2. **ดูหน้าแรก 5 วินาทีแล้วซ่อน:** ถามปลายเปิดว่า “เว็บนี้ช่วยเรื่องอะไร” และ “เหมาะกับใคร” ไม่บอกคำตอบก่อน ห้ามนับคำตอบที่ทีมช่วยใบ้
3. **เปิดให้ดูต่อ 10–20 วินาที:** ถามว่าเริ่มอย่างไรและใครตรวจยืนยันข้อมูล บันทึกคำตอบจริง แยกความเข้าใจผิดว่า AI ทำบัญชี/ยื่นภาษีให้ทั้งหมด
4. **ลองทำ 3 งาน:** หาตัวอย่างการใช้ หาราคา/เงื่อนไข และหาทางเข้าสู่ระบบ จบก่อนสมัคร จ่ายเงิน หรือส่งเอกสารจริง
5. **เปรียบเทียบชุด A/B:** สลับลำดับเพื่อลดอคติจากการเห็นก่อน บันทึกแยกแต่ละกลุ่ม ไม่สรุปจากคำถาม “อันไหนสวยกว่า” เพียงคำถามเดียว
6. **เกณฑ์ผ่านภายในที่เสนอ:** อย่างน้อย 7/8 คนอธิบายงานหลักและทางเริ่มได้; ทุกคนแยกคนตรวจยืนยันออกจาก AI ได้หลังดู demo หากมีความเข้าใจผิดสำคัญแก้แล้วทดสอบใหม่ เกณฑ์นี้ตั้งเพื่อควบคุมงาน ไม่ใช่มาตรฐานจากงานวิจัยหรือผลที่เกิดแล้ว

หลังเผยแพร่ค่อยแยกวัด: การเห็น/เล่น demo, คลิกเริ่ม LINE, สมัครสำเร็จ, เริ่มใช้งานจริง และจ่ายเงิน ห้ามนับคลิก LINE เป็นยอดสมัคร การเชื่อม event ต้องอยู่ใน contract และสิทธิ์เดิม ไม่ส่งใบเสร็จหรือข้อมูลส่วนบุคคลไป analytics

ข้อมูล GSC ที่เก็บครั้งก่อนมีเพียง 29 clicks/100 impressions ในช่วง 28 วันตาม filters ที่บันทึก จึงยังไม่มีเหตุผลใช้ traffic นี้รับรองผล A/B ทางสถิติ เริ่มจากความเข้าใจและ journey ก่อน แล้วประเมิน sample size จาก baseline conversion เมื่อวัดได้

สำหรับ AI Search ให้ตรวจ report ที่บัญชีรองรับจริง: Google มีเอกสาร [Generative AI performance report](https://support.google.com/webmasters/answer/16984139) แล้ว แต่รอบนี้ยังไม่ได้ตรวจว่ามีข้อมูลของ property เราหรือไม่ ไม่แยกยอด AI ออกจาก baseline เก่าโดยคาดเดา

## 11. ลำดับนำไปใช้และเกณฑ์ตรวจรับ

| ช่วง | งานที่เตรียม | หลักฐานก่อนเดินต่อ |
|---|---|---|
| ก่อน implementation | claim audit, hero และ demo หนึ่ง flow, ตรวจ catalog/เส้นทาง CTA, ทำต้นแบบมือถือ | ข้อความทุกความสามารถผูกกับ release ที่ใช้ได้จริง; ไม่มี free-trial/ตัวเลขผลลัพธ์สมมติ |
| ทดสอบต้นแบบ | ความเข้าใจและ 3 งานจากข้อ 10 | บันทึกคำตอบ/ปัญหาและการแก้ ไม่ใช่คะแนนความชอบอย่างเดียว |
| ย้าย root | เขียน routing/migration spec; คง auth/API/deep links; ตรวจ canonical/redirect/assets/cache | target พร้อม 200, mapping ไม่วน, regression flow เดิมผ่าน; ทำตาม deployment runbook |
| ปรับเนื้อหา/ดีไซน์ | นำ guideline ไปใช้เป็นชุดที่ตรวจสอบผลได้ | แยกช่วงจาก URL move ตามคำแนะนำ Google; ไม่ต้องคงคำอ้างที่ผิดไว้เพื่อรอทดลอง |
| 3–12 เดือน | เพิ่ม demo/กรณีจริงตามคำถามและการใช้งานที่เก็บได้ | มีหลักฐานว่าปัญหาที่จะตอบเกิดจริง และประเมินผลต่อ activation |
| 12–24 เดือน | ทบทวน AI discovery/agent/แชทจากข้อมูลเรา | เพิ่มความสามารถเมื่อมี demand และ contract พร้อม ไม่ตั้งโครงการใหม่จากข่าวอย่างเดียว |

เกณฑ์ส่งต่องาน:

- [ ] ระบุสินค้า กลุ่มหลัก และบทบาท AI/คนชัด ไม่มี claim เกิน readiness
- [ ] ภาพและข้อมูลตัวอย่างมีที่มา/สิทธิ์ใช้ อ่านได้บนมือถือ และไม่เผยข้อมูลลูกค้า
