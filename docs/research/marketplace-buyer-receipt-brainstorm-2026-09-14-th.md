## 1. ทิศทางที่แนะนำ

เริ่มจาก “ชุดหลักฐานการซื้อ” ที่รวมภาพคำสั่งซื้อหลายหน้า หลักฐานชำระเงิน และเอกสารจากร้านค้า แล้วให้ผู้ใช้ตรวจรายการแยกร้านและยอดขอเบิก ก่อนส่งเข้าสู่ expense workflow เดิม

อย่ากำหนดว่า 1 รูป = 1 ร้าน = 1 ออเดอร์ = 1 ค่าใช้จ่าย = 1 การจ่ายเงิน เอกสารหนึ่งภาพอาจมีหลายร้าน และธุรกรรมเดียวอาจมีหลายภาพ หลายพัสดุ หลายการจ่าย หรือใบกำกับภาษีตามมาทีหลัง

ให้ AI อ่านความหมายและตำแหน่งหลักฐาน ส่วน ERP ตรวจตัวเลข ความครบถ้วน การซ้ำ สิทธิ และการเปลี่ยนสถานะ ใช้ค่าที่เอกสารแสดงจริง ไม่จำลองระบบโปรโมชั่นทั้งหมดของแต่ละแพลตฟอร์ม

การรวมเอกสารเป็นชุดเป็นข้อเสนอในระบบเรา ไม่ใช่การรับรองว่าแพลตฟอร์มมี checkout ID หรือความสัมพันธ์แบบเดียวกันทั้งหมด ต้องเก็บความสัมพันธ์ที่พิสูจน์ได้และความสัมพันธ์ที่ผู้ใช้จัดกลุ่มแยกกัน

## 3. ต้องแยกยอดและเจ้าของข้อมูล

| ยอดตามเอกสารร้านค้า | มูลค่า/ภาษีที่ผู้ออกเอกสารระบุ เก็บตามต้นฉบับ |
| ยอดต้องชำระตาม order | ราคาที่ผู้ซื้อถูกเรียกเก็บหลังส่วนลดที่มีผลจริง |
| การจ่ายจริงแต่ละครั้ง | เงินสด บัตร เงินใน wallet; มีวัน เวลา ผู้จ่าย และ transaction reference |
| ยอดพนักงานออกเอง | เงินบริษัทจ่ายตรงไม่กลายเป็นสิทธิเบิกของพนักงาน |
| ยอดที่ขอเบิก/อนุมัติ | เฉพาะส่วนที่ใช้เพื่อธุรกิจ ตามนโยบายและหลักฐาน |
| ยอดคืนเงิน | เป็นเหตุการณ์ภายหลัง อาจคืนหลายครั้งและต่างช่องทาง |
| สิทธิภาษีซื้อ | พิจารณาจากเอกสารและเงื่อนไขภาษี ไม่คำนวณจากยอดเงินออกอย่างเดียว |

ยอดเอกสารร้านค้าอาจไม่ตรงยอดที่ตัดบัตรเพราะมีส่วนลดที่บุคคลอื่นสนับสนุน หรือมีการชำระด้วยหลายแหล่งเงิน ให้เก็บตัวเลขเดิมและเหตุผลการเชื่อมยอด ไม่ลดฐานภาษีบนใบกำกับเพื่อบังคับให้เท่าเงินจ่าย ความหมายทางบัญชีต้องให้ผู้รับผิดชอบบัญชีกำหนดก่อน posting

แยก platform, storefront, legal issuer, payment recipient และ actual payer; ห้ามตั้ง Shopee/Lazada/TikTok เป็น vendor ของสินค้าทุกร้านเพียงเพราะชื่อแพลตฟอร์มปรากฏใหญ่ที่สุดบนภาพ

## 4. โครงสร้างข้อมูลเชิงแนวคิด

ชื่อด้านล่างเป็นข้อเสนอเชิง domain ยังไม่ใช่การตัดสินใจสร้างตารางหรือ migration:

- Purchase evidence group: กลุ่มเอกสารในบริษัท/สาขาเดียวกัน มีเจ้าของ ผู้ขอเบิก และการเชื่อมรายการ ไม่ลงบัญชีซ้ำกับรายการลูก
- Source documents: ภาพ/PDF ต้นฉบับ hash ชนิดเอกสาร ลำดับหน้า เวลาจับภาพ ความครบถ้วน/ส่วนที่ถูกตัด และข้อมูลอ้างอิง
- Seller orders: platform, market, store identity, order ID ที่พบ, วันที่สั่ง, สถานะการจ่าย/คืน, รายการสินค้า; ไม่มี ID ให้ใช้ temporary ID ภายใน ห้ามแต่งเลข order
- Items: source row ID, order item ID ถ้ามี, ชื่อ ตัวเลือก จำนวน หน่วย ราคาเดิม ราคาขายต่อหน่วย/ต่อแถวที่เห็น และสิทธิใช้เพื่อธุรกิจ
- Monetary components: ค่าส่ง ส่วนลด ค่าธรรมเนียม ภาษี และยอดควบคุม พร้อมหลักฐานและขอบเขตที่ใช้
- Payments/refunds: หลักฐานการเคลื่อนไหวเงินจริงและยอดที่เชื่อมกับ order; รองรับหลายต่อหลายเมื่อมีหลักฐาน ไม่อนุมานว่าหนึ่งกลุ่มมีหนึ่ง payment เสมอ
- Supplier documents: ใบเสร็จ/ใบกำกับ/ใบลดหนี้ เชื่อมกับร้านและรายการที่ครอบคลุม เป็นหลักฐานเพิ่มไม่สร้างค่าใช้จ่ายซ้ำ
- Expense/reimbursement drafts: ใช้ expense model และ permission workflow เดิม เมื่อข้อมูลพร้อม; แยกตามผู้ออกเอกสารและขอบเขตบัญชีจริง UI อาจแสดงเป็นกลุ่มร้าน แต่หนึ่งร้านไม่จำเป็นต้องมีเพียงหนึ่ง expense

ฟิลด์ขั้นต่ำตอน capture คือ source attachment, tenant/owner และสถานะรอตรวจ; ฟิลด์ที่อ่านไม่ออกยังรับเข้าระบบได้ แต่ก่อนยืนยันต้องมีข้อมูลร้าน/รายการ ยอดที่อธิบายได้ หลักฐานสถานะจ่าย ผู้จ่าย และนโยบายที่เกี่ยวข้องครบ ทั้งนี้คำอธิบาย “ซื้อไปใช้ทำอะไร” ยังคงเป็น optional metadata ตาม spec เดิม ไม่เพิ่มเป็นช่องบังคับ การระบุรายการบริษัท/ส่วนตัวในเคสขอเบิกเป็นอีกการตัดสินใจหนึ่ง

## 5. แทนฟิลด์โปรโมชั่นจำนวนมากด้วยรายการองค์ประกอบเงิน

แต่ละ component ควรตอบคำถามได้ว่า:

| มิติ | ค่า/ตัวอย่าง |
|---|---|
| คืออะไร | สินค้า, ส่วนลดสินค้า, ค่าส่ง, ส่วนลดค่าส่ง, ค่าบริการ, ภาษี, ปัดเศษ, ยอดรวม, อื่น ๆ ที่ยังไม่ทราบ |
| เป็นเงิน/รางวัลแบบไหน | ส่วนลดที่ใช้แล้ว, วิธีชำระ, รางวัลที่จะได้รับ, ข้อความโปรโมชั่นที่ยังไม่ได้ใช้ |
| ใช้กับอะไร | item, seller order, shipment, group หรือยังไม่ทราบ; มี target references |
| ใครสนับสนุน | seller, platform, payment provider, co-funded, unknown; ไม่เดาจากโลโก้ และไม่จำเป็นต้องบล็อก capture ถ้ายังไม่รู้ |
| จำนวนและหน่วย | decimal string หรือ integer satang, currency; จำนวนเหรียญแยกจากมูลค่าเงิน |
| เป็นยอดชนิดใด | gross/net, unit/extended, component/control total; ยอดนี้รวมส่วนลดอื่นอยู่แล้วหรือไม่ |
| มีความสัมพันธ์กับยอดใด | ยอดแม่/รายการแจกแจง, ราคาที่รวมส่วนลดไว้แล้ว, allocation จาก component เดียวกัน |
| มาจากไหน | attachment/page/ตำแหน่งหรือข้อความอ้างอิงเฉพาะ, raw label, raw value |
| ได้ค่าอย่างไร | อ่านตรงจากเอกสาร, คำนวณจากหลักฐาน, ปันส่วนตามนโยบาย, ผู้ใช้แก้ พร้อมผู้แก้และเหตุผล |
| ขอบเขตเวลา | วันเอกสาร/การจ่าย/การคืน/การจับภาพ ไม่ใช้วันที่ upload แทนโดยไม่ระบุ |

coupon code เป็นตัวระบุโปรโมชั่น ไม่ใช่ตัวเลขที่ต้องหักเพิ่ม คูปองหนึ่งใบอาจให้ทั้งส่วนลดสินค้าและส่ง แต่ต้องมี applied component ที่อธิบายเงินแต่ละส่วนได้

ไม่ต้องเพิ่มคอลัมน์ shopeeVoucher1/lazadaBonus2 หรือเขียนรายการ keyword ทุกโค้ด ให้ AI จำแนกบริบทและเก็บป้ายเดิม แล้วใช้ enum/เงิน/ขอบเขต/หลักฐานที่ตรวจสอบได้เป็น guard

## 6. กฎการอ่านและกระทบยอด

1. จำแนกหน้า cart/ก่อนจ่าย, order ที่ชำระแล้ว, รอ COD, หลักฐาน payment, ใบเสร็จ, ใบกำกับ, refund ก่อน ไม่ถือคำว่า “ยอดรวม” เป็นหลักฐานว่าจ่ายแล้ว
2. จัดกลุ่มหน้าโดยหลักฐาน order/payment/store และให้ผู้ใช้แก้กลุ่มได้ ถ้าข้อมูลขัดกันเก็บ conflict ไม่เลือกค่าที่ลงตัวกับสมการเอง
3. ระบุขอบเขตร้าน สินค้า การจัดส่ง และยอดรวมก่อนเชื่อมตัวเลข; จำนวนเดียวกันที่อยู่หลายตำแหน่งไม่ใช่หลักฐานว่าเป็น field เดียวกัน
4. แยกราคาขีดฆ่ากับราคาขายจริง หน่วยกับยอดทั้งแถว และส่วนลดที่รวมในราคาขายแล้ว ห้ามหักซ้ำ
5. ยอด “ประหยัดทั้งหมด” เป็น control total หากมีรายการแจกแจงอยู่แล้ว ไม่หักทั้งยอดแม่และยอดลูก
6. ค่าส่ง 50 ลด 50 สุทธิ 0 เลือกใช้ gross-minus-discount หรือ net เพียงเส้นทางเดียว ไม่ใช้ 0-minus-50
7. เหรียญที่ใช้ลดเงินจริง เงินใน wallet ที่ใช้ชำระ และ cashback ที่จะได้ภายหลังเป็นคนละประเภท เก็บความไม่แน่ใจแทนการใส่ 0
8. ตรวจ subtotal ระดับสินค้า/ร้าน/group เฉพาะเมื่อรู้ว่าตัวเลขอยู่บนฐานเดียวกัน ยอดครบทั้งกลุ่มต้องเท่าร้านลูกที่นับครั้งเดียวบวกองค์ประกอบระดับกลุ่มที่ยังไม่ถูกแจก
9. กระทบยอดการชำระกับยอดเรียกเก็บแยกจากเลขใบกำกับภาษี การตัดบัตรเพียงช่องทางเดียวอาจไม่เท่าทั้ง order หากมี wallet/เครดิตอื่นร่วม
10. ใช้ decimal/integer satang ตรวจสมการแน่นอน ข้อมูลที่ครบเป็นสตางค์ควรเท่ากันถึงสตางค์; การอ่านยอดที่ปัดมาแล้วต้องติด review reason ไม่สร้างส่วนลดหรือ rounding เพื่ออุดช่องว่าง
11. เมื่อข้อมูลไม่พอ เก็บ draft พร้อม missing evidence/unallocated amount การพับยอดรวมตาม fallback เดิมไม่ใช่หลักฐานว่ารู้ vendor หรือแบ่งร้านสำเร็จ
12. เก็บ snapshot ที่ review แล้ว การอ่านใหม่เสนอ diff ไม่เขียนทับค่าที่คนยืนยัน และไม่แก้ record ที่ลงบัญชีแล้วเงียบ ๆ

ความเชื่อมั่นของ AI และผลตรวจเลขเป็นคนละเรื่อง: ตัวเลขผิดความหมายก็อาจบวกลบลงตัวได้ ต้องมีทั้งหลักฐาน field, ความครบถ้วน และ arithmetic proof

## 7. การแบ่งส่วนลดร่วม

ลำดับที่เสนอ:

1. ใช้ยอดแบ่งจริงจากหลักฐานของแพลตฟอร์ม/รายร้าน/ราย item ก่อน
2. ถ้าคำนวณส่วนที่ขาดได้อย่างเอกเทศจากหลักฐานที่ครบและขอบเขตเดียวกัน ให้บันทึกว่า derived พร้อมสมการ ไม่เรียกว่าอ่านจากเอกสาร
3. ถ้าไม่มีการแบ่งจริง แต่ทราบรายการที่มีสิทธิและบริษัทอนุมัตินโยบายแล้ว จึงเสนอปันส่วนตามมูลค่าสินค้าที่มีสิทธิหลังส่วนลดร้าน แสดงว่าเป็น allocation สำหรับเบิกเงินของบริษัท
4. ถ้าไม่รู้รายการที่มีสิทธิหรือฐานที่ถูกต้อง ให้ยังไม่แบ่งและรอตรวจ ไม่เฉลี่ยข้ามร้านทั้งหมดอัตโนมัติ

ค่าส่งให้ยึดร้าน/พัสดุจริง ไม่ใช้สัดส่วนราคาสินค้าปันส่วนข้ามร้านโดยไม่มีนโยบาย สินค้าส่วนตัวต้องอยู่ในฐานการแบ่งส่วนลดเมื่อมีสิทธิเข้าร่วมจริง แล้วค่อยตัดสิทธิเบิก เพื่อไม่ย้ายประโยชน์จากส่วนลดของสินค้าส่วนตัวไปบริษัท

ปัดเศษการแบ่งด้วย largest remainder ที่สตางค์และ stable tie-break เช่น internal item ID ให้ผลรวม allocation เท่า component ต้นทางเสมอ และไม่ให้ส่วนลดเกินฐานที่มีสิทธิ เศษนี้อยู่ใน allocation metadata ไม่สร้างรายการ rounding บนเอกสารต้นฉบับ

### ตัวอย่างจำลอง — ไม่ใช่สูตร official ของแพลตฟอร์ม

สมมติสองร้านมีข้อมูลครบ ไม่มีภาษีที่ต้องบวกเพิ่ม ไม่มี coins/wallet/ค่าบริการอื่น และบริษัทอนุมัติการแบ่งคูปองร่วมตามยอดหลังส่วนลดร้าน:

| องค์ประกอบ (บาท) | ร้าน A | ร้าน B | รวม |
|---|---:|---:|---:|
| สินค้า | 1,000.00 (600 + 400) | 500.00 | 1,500.00 |
| ส่วนลดร้าน | -100.00 | 0.00 | -100.00 |
| ฐานแบ่งคูปองร่วม | 900.00 | 500.00 | 1,400.00 |
| คูปองร่วม 140 ตามฐานข้างต้น | -90.00 | -50.00 | -140.00 |
| ค่าส่งก่อนส่วนลด | 40.00 | 60.00 | 100.00 |
| ส่วนลดค่าส่งที่แสดงแยกร้าน | -40.00 | -30.00 | -70.00 |
| ยอดสุทธิที่จัดสรร | 810.00 | 480.00 | 1,290.00 |

ตรวจ: 1,500 - 100 - 140 + 100 - 70 = 1,290 บาท

ถ้าหน้าจอระบุ “จะได้รับ cashback 50” ยอดจ่ายครั้งนี้ยังเป็น 1,290 บาท ถ้าร้าน B เป็นของส่วนตัวทั้งร้านและ A เป็นของบริษัททั้งหมด ภายใต้สมมติฐานนี้ยอดเสนอเบิกคือ 810 บาท ไม่ใช่ 1,290 บาท ไม่เอาคูปองของ B อีก 50 บาทมาลดให้ A แทน

ถ้าหลักฐานจากแพลตฟอร์มแสดงการแบ่งจริงต่างจากตัวอย่าง ต้องใช้หลักฐานนั้นเป็นต้นทางการกระทบยอดและแสดงผลต่างจาก allocation ภายใน ไม่เขียนทับเอกสารภาษี

## 8. หน้าจอและ journey ที่เสนอ

1. ผู้ใช้อัปโหลดหลายภาพ/PDF เป็นชุด เก็บต้นฉบับทุกหน้า ใช้บริบทที่ตรวจสอบได้และถามผู้จ่ายเฉพาะเมื่อยังไม่ทราบ วัตถุประสงค์เป็นข้อมูลเสริม ไม่บังคับเพื่อเก็บร่าง
2. ระบบแสดงจำนวนร้าน/รายการที่พบ ยอดตามหลักฐาน ยอดคำนวณ และผลต่าง พร้อมบอกหน้าที่ขาดหรืออาจซ้ำ
3. ผู้ใช้เปิดดูรายร้าน ตรวจสินค้า ตัวเลือก จำนวน ส่วนลด และค่าจัดส่ง คลิก field แล้วเห็นหลักฐานที่อ่านมาได้
4. ระบุรายการใช้เพื่อธุรกิจ/ส่วนตัว หมวดค่าใช้จ่าย โครงการ และจำนวนหรือสัดส่วนที่ขอเบิก
5. ข้อสงสัยถามเฉพาะจุด เช่น ไม่เห็น breakdown คูปอง หรือยังไม่เห็นสถานะจ่าย; draft ต้องไม่หายเมื่ออ่านไม่สำเร็จ ไม่มีสิทธิ หรือแก้แล้วกลับมาใหม่
6. แสดงสถานะแยก: อ่านครบหรือไม่ / ยอดตรงหรือไม่ / มีหลักฐานชำระหรือไม่ / นโยบายเบิกครบหรือไม่ / เอกสารภาษีพร้อมหรือไม่
7. ผู้มีสิทธิตรวจและยืนยันใน web ตาม workflow เดิม; LINE/AI ช่วย capture และตอบข้อสงสัย ไม่ยืนยันหรือจ่ายเงินแทน
8. ใบกำกับหรือหลักฐานคืนเงินที่ตามมา ให้เสนอเชื่อมกับรายการเดิม ไม่สร้าง expense ใหม่เพียงเพราะเป็นไฟล์ใหม่

กรณีรอใบกำกับภาษีอาจยังเข้าสู่ review ค่าใช้จ่ายได้ตามนโยบายบริษัท แต่การอนุญาตเบิกและการใช้ภาษีซื้อต้องแยกกัน ไม่ตั้งสถานะเดียวว่า “ถูกต้องทั้งหมด” จากการที่ยอดเงินตรง

## 9. นโยบายที่ต้องรู้ก่อน implement

| เรื่องที่ยังต้องตกลง | ข้อเสนอเริ่มต้นเพื่อหารือ |
|---|---|
| จะยอมรับหลักฐานขั้นต่ำแบบไหน | ภาพรายละเอียด order/ร้าน/รายการ/ยอด พร้อมสถานะชำระหรือหลักฐานที่เชื่อมการจ่ายได้ และการระบุส่วนที่ขอเบิกตามนโยบาย; ไม่บังคับกรอกข้อความวัตถุประสงค์ธุรกิจ |
| จุดที่มีสิทธิเบิก | แยกชำระแล้วกับได้รับสินค้าแล้ว บริษัทต้องกำหนดเงื่อนไข; unpaid/COD pending เก็บ draft ได้แต่ไม่ถือว่าพนักงานจ่ายแล้ว |
| ใครออกเงิน | บันทึก employee/company/advance และ source ของ wallet เพื่อไม่เบิกซ้ำกับเงินบริษัท |
| Coins/สิทธิส่วนตัว | เริ่มเสนอเบิกจากเงินที่พนักงานจ่ายจริงที่เข้าเงื่อนไข; มูลค่า coins ส่วนตัวต้องมีนโยบายต่างหาก ไม่ถือว่าเบิกได้อัตโนมัติ |
| การปันส่วน | official breakdown ก่อน; internal proportional allocation ใช้ได้เมื่อรู้ eligible base และอนุมัตินโยบายแล้ว |
| สินค้าส่วนตัว/ใช้ร่วม | ระดับ item/quantity พร้อมเหตุผล; ค่าส่งและส่วนลดต้องแบ่งอย่างสอดคล้อง |
| คืนหลังเบิก/ยกเลิกบางชิ้น | บันทึก refund/adjustment ที่ผูกกับต้นทางและให้ reviewer จัดการการเรียกคืนหรือหักรอบถัดไป ไม่แก้ประวัติเดิม |
| ใบกำกับไม่ตรงยอดจ่าย | รักษายอดเดิมทั้งคู่และให้บัญชีกำหนด bridge ของเงินสนับสนุน/วิธีจ่าย ห้ามเดาฐาน VAT |
| ผ่อน/BNPL, wallet หลายแหล่ง | capture หลักฐานได้ แต่การเบิกและ posting ต้องมีนโยบายเฉพาะ; ไม่สร้างค่าใช้จ่ายซื้อสินค้าซ้ำทุกงวด |
| สินทรัพย์/สต็อก/ซื้อแทนลูกค้า | ส่งต่อเส้นทางเดิมของระบบตามหมวดและวัตถุประสงค์ ไม่สรุปว่าทุกสิ่งเป็นค่าใช้จ่ายดำเนินงาน |

ทั้งหมดเป็นคำถามออกแบบ ไม่ใช่ blocker ของการ brainstorm รอบนี้ และยังไม่ถือว่าผู้ใช้อนุมัตินโยบายเหล่านี้แล้ว

## 10. แผนที่เล็กที่สุดที่น่าทดลอง

### A. ชุดตัวอย่างและเกณฑ์ก่อนเขียน logic ใหม่

- เก็บ 30 ชุดการซื้อจริงที่ปิดข้อมูลส่วนตัวที่ไม่เกี่ยวกับการอ่านแล้ว เป็นจุดเริ่มต้นแพลตฟอร์มละ 10 ชุด ไม่ใช่จำนวนที่รับรองความแม่นยำ production
- หนึ่งชุดอาจมีภาพหลายหน้า + หลักฐานชำระ + ใบเสร็จ/ใบกำกับ + refund ให้คนตรวจทำ expected output
- ครอบคลุมหลายร้าน หลายสินค้า โค้ดร่วม ค่าส่งฟรีบางส่วน เหรียญ สินค้าส่วนตัว ภาพซ้ำ และข้อมูลที่ตั้งใจเว้นให้ขาด
- แยกชุดปรับ prompt กับ held-out ตามธุรกรรมต้นฉบับ ไม่แยกภาพคนละหน้าของออเดอร์เดียวกันไปคนละชุด

### B. Prototype แบบ draft-only

- ใช้ intake, attachment, OCR/AI และ expense review เดิม เพิ่มการเสนอแยกร้าน/แสดง source components ใน draft
- เริ่มรองรับ THB ที่อ่านสกุลได้ หลักฐานชำระครบ และรายละเอียดส่วนลดแยกร้านชัดเจน; รับเคสอื่นเข้าคิว review
- ให้ arithmetic/checks เป็น pure deterministic logic; เก็บทั้งผลอ่านและการคำนวณ ไม่อาศัย self-reported confidence เป็นคะแนนความถูกต้อง
- ไม่เปิด marketplace import backlog #19 ทั้งชุด และไม่เพิ่ม seller API เป็น dependency ของ buyer workflow

### C. Spec/plan สำหรับส่วนที่พิสูจน์ว่าจำเป็น

- เขียน buyer multi-document/multi-seller spec และ plan ที่มี contract, document grouping, review journey, dedup, policy boundaries, idempotency และ failure handling
- เลือก storage ที่เล็กที่สุดตามรูปแบบการค้น/แก้/ตรวจ ไม่ยืนยันว่าจะใส่ทุกอย่างใน JSON หรือต้องสร้างตารางชุดใหม่ก่อนเห็นข้อจำกัดจริง
- ทดสอบ frontend → API → OCR apply → review save → confirm ด้วย acceptance examples และเส้นทาง browser/LINE ที่มีอยู่
- เพิ่ม shared allocation, split tender และ refund linking ทีละ slice หลังนโยบายและข้อมูลรองรับ ห้ามเปิด auto-posting จากการอ่านรูป

### เกณฑ์ตรวจและเคสที่ต้องอยู่ใน evaluation

- ความถูกต้องเป็นระดับกลุ่มเอกสาร ร้าน รายการ จำนวน และองค์ประกอบเงิน ไม่วัดเพียง OCR อ่านตัวอักษรหรือยอดสุดท้ายตรง
- แยก exact-match accuracy, false confident acceptance, human-review rate, เวลาแก้ต่อชุด, latency และต้นทุนต่อชุด
- Golden cases ที่จะยอมรับเป็น draft ที่ยอดครบต้องมีหลักฐานและเลขตรงทุกระดับที่เกี่ยวข้อง; เคสไม่ครบต้องแสดงเหตุผล review ที่ถูก ไม่เดาให้ผ่าน
- ยอดรวม discount แม่/ลูกไม่หักซ้ำ; net shipping ไม่หัก shipping discount ซ้ำ; cashback ไม่ลดเงินจ่ายปัจจุบัน
- แถวสินค้า 2 ชิ้นราคา extended ต้องไม่คูณซ้ำ; ชื่อ/SKU ซ้ำแต่ order item ID ต่างกันต้องไม่หาย; ของแถม 0 บาทคงอยู่ได้
- screenshot หลายหน้าที่ซ้อนกันไม่เพิ่มสินค้า; เอกสารใหม่ของออเดอร์เดิมไม่สร้าง expense ซ้ำ
- การแบ่งสตางค์รวมเท่าต้นทางเสมอ ไม่เกิน eligible base และแก้กลุ่มแล้ว recalculation ไม่สะสมการหักซ้ำ
- pending COD/unpaid ไม่กลายเป็นจ่ายแล้ว; ยกเลิกบาง item/refund แยกสถานะจาก item ที่ยังคงอยู่
- worker retry/re-OCR ไม่สร้างกลุ่ม/expense/payment ซ้ำและไม่ overwrite review ที่ใหม่กว่า
- cross-tenant attachment/group linkage ปฏิเสธ; ทุกร้านลูกใช้สิทธิบริษัท/สาขาถูกต้อง; child creation ไม่เกิดชุดค้างครึ่งหนึ่ง
- ภาพที่มีข้อความสั่ง AI ให้เปลี่ยนยอดถือเป็นข้อมูลในเอกสาร ไม่ใช่คำสั่ง ระบบไม่ส่ง raw เอกสารหรือข้อมูลส่วนตัวลง audit logs
- foreign currency ถูกส่ง review ตามขอบเขต MVP ไม่ตีความตัวเลขเป็น THB อัตโนมัติ

## 13. UX สำหรับผู้ใช้ 40+ และหลัก “มีทางออกเสมอ”

### 13.1 ข้อปรับจาก brainstorm รอบแรก

ผู้ใช้ยืนยันว่าหลักมั่งมีคือใช้งานง่ายที่สุดและมีทางออกเสมอ ข้อ 8 เดิมยังให้ผู้ส่งเอกสารตรวจยอดและสถานะหลายมิติมากเกินไป จึงปรับเป็น: ระบบจัดรายละเอียดให้ คนตอบเฉพาะเรื่องที่ระบบรู้แทนไม่ได้ เช่น สินค้าใช้ส่วนตัวหรือใช้กับบริษัท และใครออกเงิน

อายุ 40+ ไม่ได้แปลว่าความสามารถดิจิทัลเหมือนกัน ควรออกแบบรองรับการมองเห็น ความคุ้นเคยศัพท์ การใช้มือเดียว และการถูกขัดจังหวะ แล้วทดสอบกับผู้ใช้จริงหลายช่วงอายุและความคล่อง ไม่อ้างผลใช้ง่ายจากอายุหรือ guideline อย่างเดียว

นี่เป็นข้อเสนอ UX ยังไม่ใช่หน้าจอที่ implement แล้ว และไม่เปลี่ยน stable financial review form หรือ LINE summary เดิมโดยอัตโนมัติ ถ้าจะลด/จัดใหม่ต้องแก้ spec และทดสอบเส้นทางจริงก่อน

### 13.2 งานหลักของผู้ใช้เหลือสามเรื่อง

1. ส่งรูปที่มี: ปุ่มหลัก “เพิ่มรูปหรือไฟล์” พร้อมตัวอย่างสั้น ๆ ว่าใช้ภาพคำสั่งซื้อได้ เลือกหลายรูปได้ ระบบช่วยแยกร้าน ไม่บังคับจัดไฟล์ แยกร้าน เลือกชนิดเอกสาร หรือกรอกข้อมูลบัญชีก่อน
2. ดูภาพรวม: ยอดจ่ายตามหลักฐาน ชื่อร้าน และรายการที่รู้จัก กด “ดูสินค้าและส่วนลด” เมื่อต้องการดูเพิ่ม ยอดที่ยังไม่ชัดต้องระบุว่า “ยอดที่อ่านได้ รอตรวจ” ไม่แสดงเป็นยอดจริงที่ยืนยันแล้ว
3. ระบุสิ่งที่จะเบิก: เมื่อยังไม่ทราบ ให้เลือก “ใช้สำหรับบริษัททั้งหมด” หรือ “มีของส่วนตัวด้วย” และถามผู้จ่ายเฉพาะข้อมูลที่ยังไม่ทราบ จากนั้นแสดงยอดขอเบิกและ action ตามสิทธิ/สถานะ

จัดสามเรื่องนี้ในหน้าสรุปเดียวได้ ไม่ต้องเป็น wizard สามหน้าหรือบังคับตรวจสินค้าทีละช่อง การเลือกใช้สำหรับบริษัททั้งหมดต้องมาจากผู้ใช้ ไม่ตั้งค่าให้โดยอัตโนมัติจากการที่อัปโหลดในบริษัท

ผู้ใช้ที่มีสินค้าส่วนตัวเลือกยกเว้นได้เป็นรายสินค้า/จำนวน โดยเห็นชื่อ ตัวเลือก และยอดสุทธิ การยกเว้นจากสิทธิเบิกยังรักษารายการต้นฉบับและฐานปันส่วนที่เกี่ยวข้องครบ จึงไม่ต้องให้ผู้ใช้แบ่งคูปองเอง

คำว่า “ซื้อไปใช้ทำอะไร” ยังคง optional ตาม [receipt single-form spec](../specs/receipt-single-form-preview-spec.md) ข้อมูลที่ระบบมีอยู่แล้วไม่ถามซ้ำ; บริษัท/สาขาปัจจุบันแสดงให้เห็นและถามเฉพาะเมื่อมีความกำกวมจริง

### 13.3 หน้าหลักกับรายละเอียด

- แสดงยอดที่ตรงกับงานขณะนั้นให้เด่น เช่น “ยอดที่คุณขอเบิก 810 บาท” พร้อม “จากยอดจ่ายรวม 1,290 บาท” เมื่อรู้ทั้งสองจริง
- ใช้ข้อความสถานะที่นำไปสู่การกระทำหนึ่งเรื่อง เช่น “เติมยอดจ่ายอีก 1 ช่อง” แทนการแสดงห้าสถานะทางเทคนิคเรียงกัน ข้อมูลตรวจเงิน/จ่าย/ภาษียังอยู่ในรายละเอียดและยังมีผลกับ guard ตามเดิม
- ใช้คำว่า “รายการนี้”, “รูปที่ส่ง”, “ยอดจ่าย”, “ส่วนลด”, “เก็บไว้ก่อน”, “กลับมาทำต่อ” แทน evidence group, reconciliation, allocation, draft ID หรือ confidence score
- รายละเอียดคูปองและเหตุผลการแบ่งเปิดดูได้ แต่ไม่เป็นข้อสอบที่ผู้ส่งเอกสารต้องผ่าน ข้อผิดปกติทางตัวเงินที่ยังไม่คลี่คลายต้องแสดงก่อน action ที่ได้รับผลกระทบ ไม่ซ่อนใต้รายละเอียด
- หนึ่ง action หลักต่อสถานะ พร้อมทางรองที่เกี่ยวข้องเท่านั้น ไม่โชว์ทุกทางออกพร้อมกันทั้งหน้า
- ผู้ส่งเอกสารเห็น “ส่งให้ตรวจ” เมื่อมีผู้ตรวจและมีสิทธิส่งจริง ผู้ตรวจ/เจ้าของใช้ action ตาม workflow ของตน ไม่บังคับเพิ่มนักบัญชีหรือคนอื่นเพื่อใช้ฟีเจอร์
- ยึดฟอร์มเดียวที่ผู้ใช้กำลังแก้และรูปต้นฉบับเดิม ตาม spec stable review; ไม่เพิ่มฟอร์มกรอกข้อมูลซ้ำหรือ dashboard missing-fields อีกชุด

### 13.4 ทางออกต้องทำงานจริงในทุกกรณี

| สถานการณ์ | ข้อความตัวอย่าง | ทางออกที่ต้องทำได้จริง |
|---|---|---|
| เก็บภาพแล้ว กำลังอ่าน | “เก็บรูปแล้ว กำลังอ่านรายละเอียด” | ไปทำงานอื่นแล้วกลับมารายการเดิมได้ |
| อ่านไม่สำเร็จหลัง retry แบบจำกัด | “เก็บรูปไว้แล้ว ยังอ่านยอดไม่ได้” | ใส่ยอดเอง / เก็บไว้ก่อน; เสนอรูปใหม่เฉพาะกรณีที่ช่วยได้จริง |
| รูปถูกตัด ขาดยอดหรือหน้าร้าน | “รูปนี้ยังไม่เห็นยอดจ่าย” | เพิ่มรูปในรายการเดิม พร้อมตัวอย่างตำแหน่งที่ต้องการ / เติมเอง / เก็บไว้ก่อน |
| อ่านคูปองไม่ชัดหรือยอดต่าง | “รายละเอียดรวมได้ 1,310 บาท แต่ยอดจ่ายในรูปคือ 1,290 บาท” | เปิดรูปตรงจุด / แก้ข้อมูล / เก็บรอผู้มีหน้าที่ตรวจ; ไม่ให้คนเดาคูปองมาอุด 20 บาท |
| ไม่รู้คำตอบ | “ข้อนี้เก็บไว้เติมภายหลังได้” | รับคำตอบบางส่วนและคงค่าที่ไม่ทราบ; ถ้ามีผู้ดูแลที่รับงานได้จริงจึงเสนอส่งให้ช่วยตรวจ |
| ไม่เห็นใบกำกับภาษี | “เก็บรายการได้แล้ว ใบกำกับภาษีแนบเพิ่มภายหลังได้” | เก็บ draft ต่อ และให้คำแนะนำขอเอกสารจากร้าน; การส่งตรวจ/เบิกขึ้นกับนโยบาย ไม่เปิดสิทธิภาษีซื้อเอง |
| ภาพซ้ำแน่นอน/ภาพคล้าย | “พบรูปนี้ในรายการเดิม” / “รูปนี้อาจเป็นรายการเดียวกัน” | เปิดของเดิม; กรณีคล้ายให้เทียบแล้วเลือก “เป็นคนละรายการ” ได้ ไม่รวมบิลยอดเท่ากันเอง |
| ผู้ใช้รีบ ปิดหน้า หรือเปลี่ยนเรื่อง | “เก็บไว้แล้ว ยังไม่ได้ส่งให้ตรวจ” เมื่อบันทึกสำเร็จจริง | กลับจาก “รายการของฉัน” หรือ LINE link ไปจุดเดิม; ไม่ทวงหรือยืนยันเอง |
| อัปโหลดไม่ถึงระบบ | “รูปยังส่งไม่สำเร็จ” | ลองส่งต่อจากข้อมูลที่ยังอยู่ได้ พร้อมระบุว่าอะไรยังไม่ถูกเก็บ; ห้ามบอกเก็บแล้ว |
| บันทึกสำเร็จ แต่ refresh/แจ้งผลล้มเหลว | “บันทึกแล้ว แต่ยังโหลดหน้าล่าสุดไม่ได้” | เปิดรายการเดิม/ลองโหลดใหม่ ไม่ replay การสร้างรายการ |
| สิทธิ์เปลี่ยน ลิงก์เก่า หรือ session หมดอายุ | บอกสิ่งที่ต้องทำด้วยภาษาธรรมดา | เข้าสู่ระบบแล้วกลับรายการเดิมเมื่อยังมีสิทธิ หรือกลับรายการที่เข้าถึงได้; ขอสิทธิได้เฉพาะช่องทางที่มีจริง โดยไม่เปิดเผยข้อมูลข้ามสิทธิ |
| ใช้สิทธิ์อ่านอัตโนมัติหมด | “ตอนนี้อ่านอัตโนมัติไม่ได้ แต่กรอกเองต่อได้” | เก็บหลักฐาน/กรอกมือภายใต้สิทธิ์และโควตาเก็บข้อมูลที่มี; ไม่บังคับซื้อแพ็กเกจเพื่อกู้งานที่บันทึกแล้ว |

ตารางนี้เป็น acceptance ที่เสนอ ต้องตรวจ endpoint/สิทธิ/สถานะจริงของทางออกทุกช่อง ห้ามสร้างปุ่ม “ให้คนช่วย” ที่ไม่มีผู้รับงาน หรือ “บันทึกไว้ก่อน” ที่ validator บังคับข้อมูลครบทั้งหมด

หลัก “มีทางออกเสมอ” หมายถึงข้อมูลที่เก็บแล้วคงอยู่ ผู้ใช้รู้สถานะ และมีทางทำต่อ/แก้/พัก/ขอความช่วยเหลือที่เข้าถึงได้ การพักงานไม่ข้ามกฎการยืนยัน การจ่าย หรือภาษี

### 13.5 การถามและการบันทึก

- รวบรวมเฉพาะข้อมูลที่ต้องให้คนตอบทั้งหมด ณ ขณะนั้นไว้ด้วยกัน ตอบบางข้อได้ ไม่ถามทีละ field จนกลายเป็นแชตยาว และไม่ถามเรื่องที่อ่านได้แล้ว
- บนเว็บใช้ label และคำอธิบายใกล้ช่องเดิม ไม่สร้างฟอร์ม/รายการเตือนซ้ำ ตามกติกา stable review ปัจจุบัน
- เมื่อข้อมูลใหม่ทำให้ต้องถามเพิ่มจริง ให้บอกสาเหตุ ไม่ทำให้ผู้ใช้รู้สึกว่าตอบอย่างไรก็ไม่จบ
- เก็บ draft ที่ยังไม่ครบโดยไม่ต้องให้ผู้ใช้จำกดบันทึกทุกครั้งเป็นเป้าหมาย UX; แต่ข้อความ “เก็บแล้ว” แสดงหลัง server ยืนยัน write เท่านั้น ต้องแสดงกรณี save pending/failure ตามจริง และกำหนด persistence ใน spec ก่อนลงมือ
- “เก็บไว้ก่อน” หมายถึงพักการไล่ถามและกลับงานหลักได้ พร้อมบอกว่าเก็บอะไรแล้ว/ยังไม่ส่งตรวจ ไม่ตีความว่าลบ ยืนยัน หรืออนุมัติ
- แก้จำนวน/รายการบริษัทแล้วคำนวณใหม่พร้อมบอกผลของยอด ไม่ overwrite ข้อมูลที่ผู้ใช้แก้ด้วย OCR ที่กลับมาช้า มีทางย้อนการแก้ใน draft; หลัง finalization ใช้กระบวนการแก้ไขที่อนุญาตพร้อมอธิบายผล
- เสนอขอคนช่วยเฉพาะเมื่อมีผู้รับและผู้ใช้มีสิทธิ; การส่งจริงต้องเกิดจากการเลือกของผู้ใช้ ไม่แชร์เอกสารให้บุคคลอื่นเอง

แนวทางนี้ต่อยอด [LINE receipt reliability UX research](line-receipt-reliability-ux-review-2026-09-07-th.md) ที่กำหนดให้ถามข้อมูลที่ขาดร่วมกัน รับคำตอบบางส่วน เก็บร่าง และเปิดแก้รายการเดิมได้ แต่เอกสารเก่าไม่ใช่หลักฐานว่าทุกเส้นทางปัจจุบันทำงานครบ ต้องตรวจ implementation และ browser อีกครั้งก่อน acceptance

### 13.6 ขนาดและการอ่าน

- เสนอ baseline ตัวอักษรไทยเนื้อหา 18 CSS px แล้วทดสอบกับฟอนต์และโทรศัพท์จริง ใช้ label คงอยู่เหนือช่อง ไม่พึ่ง placeholder ขนาดเล็กหรือสีจาง
- ตั้งเป้าปุ่มหลัก/ตัวเลือกที่ใช้บ่อยมีพื้นที่แตะอย่างน้อย 48 × 48 CSS px และระยะห่างพอ ปุ่มย้อนกลับ/แก้ไขหาเจอ ไม่ใช้ไอคอนเดี่ยวเมื่อความหมายไม่ชัด
- รองรับการขยายข้อความ 200% และ reflow หน้าจอเล็ก โดยไม่ทำให้ยอด/ปุ่ม/ข้อความผิดพลาดถูกตัด
- ใช้ contrast เนื้อหาปกติอย่างน้อย 4.5:1 และสื่อสถานะด้วยข้อความ/สัญลักษณ์ประกอบ ไม่ใช้สีอย่างเดียว
- ใช้แป้นตัวเลขให้เหมาะกับจำนวนเงิน แต่รองรับ paste และไม่บังคับ format จุกจิกเมื่อ normalize ได้อย่างปลอดภัย
- ไม่ใช้ countdown ที่ทำให้ต้องรีบอ่านหรือแก้ข้อมูล; session/security timeout ที่จำเป็นต้องมีทางกลับและอธิบายสิ่งที่ถูกเก็บไว้

18 px และ 48 px เป็น design target ที่เสนอของมั่งมี ไม่ใช่ข้อบังคับเฉพาะคนอายุ 40+ ส่วน [W3C Target Size Enhanced](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html) ระดับ AAA ระบุ 44 × 44 CSS px พร้อมข้อยกเว้น; [Resize Text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html) อธิบายการขยาย 200%; [Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) ระบุเกณฑ์ contrast และข้อยกเว้นตามประเภทข้อความ

ใช้ภาษาง่าย label ที่มองเห็น และ error ที่บอกวิธีแก้ตาม [W3C Forms Tutorial](https://www.w3.org/WAI/tutorials/forms/) และ [Clear Visible Labels](https://www.w3.org/WAI/WCAG2/supplemental/patterns/o4p06-clear-labels/) โดยไม่ถือว่าการผ่าน guideline เท่ากับผ่าน usability test ของผู้ใช้มั่งมี

### 13.7 จะพิสูจน์ว่าใช้ง่ายอย่างไร

ทดลองกับผู้ใช้ 40–49, 50–59 และ 60+ ที่มีความคุ้นเคยโทรศัพท์/LINE ต่างกัน เริ่มรอบเล็ก 6–8 คนเพื่อหาปัญหา แล้วปรับและทดสอบต่อ จำนวนนี้ไม่ใช้รับรองประชากรทั้งหมด และไม่ทดแทน accessibility testing

ให้ลองบนโทรศัพท์ของตัวเอง โดยผู้ทดสอบไม่สอนวิธีกดระหว่างทำ:

1. ส่งภาพซื้อสองร้าน แล้วอธิบายว่าระบบเก็บไว้หรือยัง
2. มีของส่วนตัวหนึ่งชิ้น เลือกออกจากยอดเบิกและบอกยอดที่ตนขอเบิกได้
3. ระบบอ่านผิดหนึ่งยอด ค้นต้นฉบับและแก้ได้
4. อ่านไม่ครบและไม่รู้คำตอบ เก็บไว้ก่อน ปิดหน้า แล้วกลับมารายการเดิมได้
5. พบภาพซ้ำ เลือกเปิดเดิมหรือระบุคนละรายการได้อย่างถูกต้อง
6. แยกได้ว่ารายการ “เก็บไว้แล้ว”, “ส่งให้ตรวจแล้ว”, “อนุมัติแล้ว” และ “ได้เงินแล้ว” อยู่ขั้นไหน โดยไม่อนุมานจากคำว่าเรียบร้อย
7. ถ้าไม่มีนักบัญชีหรือผู้ดูแลอีกคน ยังมีทางเก็บ/แก้/ทำต่อได้ตามสิทธิ์

วัด task completion โดยไม่ช่วย จำนวนจุดที่ขอความช่วยเหลือ เวลา active ที่ผู้ใช้ต้องทำ การย้อนกลับ/ส่งซ้ำ ความถูกต้องของยอดเบิก และความเข้าใจสถานะ บันทึกเวลาระบบอ่านแยกจากเวลาที่คนต้องใช้ ไม่ใช้เพียงจำนวนคลิกหรือความเร็วเฉลี่ยตัดสิน

เกณฑ์ที่ควรยึดใน acceptance: ทุก failure fixture มีทางออกที่ใช้งานได้จริง; ไม่มี false-success message; งานที่บันทึกแล้วกลับมาทำต่อได้; ส่วนตัว/บริษัทไม่เปลี่ยนเงียบ ๆ; คนทดสอบไม่เข้าใจการเก็บ draft ว่าได้รับอนุมัติหรือจ่ายแล้ว หากพบความเข้าใจผิดเรื่องยอด/สถานะ ต้องแก้ก่อนรับ flow แม้จำนวนคลิกต่ำ

Verification รอบ UX: ทบทวนเอกสาร UX/receipt form เดิมและแนวทาง W3C; ตรวจเอกสารและ local links เท่านั้น ยังไม่มี prototype, user session, browser test หรือ application changes ในรอบนี้

## 14. ใช้ flow อัปโหลดค่าใช้จ่ายเดิมเป็นทางเข้า

คำตอบต่อคำถามผู้ใช้: ใช้ flow เดิมเป็นฐานได้และเป็นแนวทางที่แนะนำ ผู้ใช้เข้าจากเพิ่มค่าใช้จ่าย/อัปโหลดเดิม หรือส่งหลักฐานผ่าน LINE เดิม ระบบจึงค่อยตรวจว่าเป็นเอกสารร้านเดียวหรือหลายร้าน ไม่เพิ่มเมนู marketplace หรือบังคับให้ผู้ใช้เลือก flow เอง

ตรวจ code read-only พบว่า:

- [ExpensesPages](../../apps/web/src/features/expenses/ExpensesPages.tsx) อัปโหลดผ่าน init → upload → complete → extraction อยู่แล้ว จุดเริ่มที่ตรวจรับ selectedFile ทีละไฟล์ ยังไม่ใช่ multi-file grouping ที่เสนอ
- [Expense upload use case](../../apps/api/src/modules/expenses/application/use-cases/expense-upload.use-case.ts) สร้าง ExpenseRecord draft และ attachment intent แล้วคืน expenseId เดียว พร้อมตรวจ company/branch/permission และ reuse LINE capture identity
- [Expenses API client](../../apps/web/src/features/expenses/expenses.api.ts) มี uploadExpenseEvidenceFile เพื่อแนบหลักฐาน primary/supporting/payment เพิ่มเข้า expenseId เดิม จึงใช้โครงสร้าง attachment เดิมต่อได้

สิ่งที่ต้องต่อยอดคือการรับหลายภาพที่เกี่ยวกัน การอ่านเป็นหลายร้าน/หลาย order การอธิบายส่วนลดร่วม และการเสนอรายการแยกร้านในหน้าตรวจเดิม ก่อนสร้าง/เชื่อม expense ตามผู้ออกเอกสารที่ถูกต้อง ต้องออกแบบการจัดการร่างเริ่มต้นเพื่อไม่ให้ยอดชุดรวมกับ expense ที่แยกแล้วลงบัญชีซ้ำ ไม่ใช่แก้ prompt อย่างเดียว

LINE ใช้ทางเข้าเดิม แต่ spec ปัจจุบันไม่ auto-create expense จากภาพหลายเอกสาร/กำกวม จึงต้องกำหนดและตรวจกรณี marketplace หลายร้านที่รู้ขอบเขตได้ให้ชัดก่อนอ้างว่ารองรับ ไม่ปิด classification/permission guards แบบกว้าง

พฤติกรรมที่ผู้ใช้ควรได้รับหลังพัฒนา: เอกสารปกติไปต่อใน flow เดิม; เมื่ออ่านพบหลายร้าน ระบบจัดรายละเอียดให้ในงานเดิม; ถ้าข้อมูลยังไม่ครบเก็บร่างและเพิ่มรูป/แก้ต่อได้ตามสิทธิ์ ทั้งหมดนี้ยังเป็นข้อเสนอ ไม่ใช่คำยืนยันว่าฟีเจอร์หลายร้านทำงานครบในปัจจุบัน

Verification: อ่าน upload UI, upload use case และ evidence attachment client โดยไม่แก้ code หรือเรียก runtime; ไม่มี application tests ในรอบตอบคำถามนี้

## 15. วิเคราะห์ BA, SA, AI Engineer, ผู้ประกอบการ และบัญชี

วันที่: 2026-09-14 — การวิเคราะห์ตามมุมที่ผู้ใช้ขอ ไม่ใช่การผ่าน implementation/release gate และไม่มีการมอบหมาย role subagents

### 15.1 ผลลัพธ์ร่วมและขอบเขต

ผู้ใช้ส่งหลักฐานผ่านค่าใช้จ่าย/LINE เดิม ระบบช่วยอ่านและจัดข้อมูล แล้วพาไปสู่รายการบริษัทหรือใบเบิกที่ตรงกับผู้จ่ายจริงได้ โดยไม่กรอกซ้ำ ไม่ทำยอด/รายการหาย และไม่บันทึกเงินหรือภาษีซ้ำ

แยกความสำเร็จสี่ระดับ: เก็บหลักฐานสำเร็จ → จัดข้อมูลพร้อมตรวจ → ผ่านกฎเส้นทางค่าใช้จ่ายหรือใบเบิก → ลงบัญชี/ชำระตามสิทธิและสถานะจริง การผ่านระดับหนึ่งไม่แปลว่าผ่านระดับถัดไปทั้งหมด

### 15.2 มุม BA: กฎที่ต้องเปลี่ยนเป็นพฤติกรรมและ acceptance

| เรื่อง | ข้อเสนอและผลที่ผู้ใช้ต้องได้ |
|---|---|
| ใครจ่าย | แยกเงินบริษัท พนักงานสำรองจ่าย เงินทดรอง และกรณีหลายแหล่ง; การส่งรูปไม่ยืนยันว่า uploader เป็นผู้มีสิทธิรับเงินคืน |
| ใช้เพื่ออะไร | ผู้ใช้ระบุของบริษัท/ส่วนตัวในระดับสินค้า/จำนวนเมื่อยังไม่ทราบ ระบบคำนวณตามนโยบาย; คำบรรยายวัตถุประสงค์ยัง optional ตามกติกาเดิม |
| หลักฐานแสดงอะไร | cart, order paid, COD pending, slip, invoice, refund แสดงข้อเท็จจริงต่างกัน เก็บได้แต่ความพร้อมของ action ต่างกัน |
| ส่วนลดและค่าส่ง | ใช้การแบ่งจริงก่อน internal allocation; ถ้าไม่รู้ eligibility ไม่เฉลี่ยให้ดูครบ; นโยบายอนุมัติครั้งเดียวระดับบริษัทไม่ถามสูตรทุกบิล |
| วันและช่วงเวลา | วันที่สั่ง วันที่ร้านออกเอกสาร วันที่ผู้ซื้อจ่าย วันที่บริษัทคืนเงิน และวันที่คืนสินค้าเป็นคนละวัน ไม่ใช้วัน upload แทนทั้งหมด |
| เอกสารใหม่ตามมา | เสนอแนบกับรายการเดิม ต้องพิสูจน์ความสัมพันธ์และไม่เกิดค่าใช้จ่ายใหม่ซ้ำ |
| พักและแก้ | รับข้อมูลบางส่วน เก็บสถานะไม่ทราบ และมี action ที่ทำได้จริงในสิทธิ์ปัจจุบัน; ไม่ปล่อยให้ปุ่มถัดไปปิดโดยไม่บอกเหตุผล |
| อนุมัติแล้วมีการเปลี่ยน | ยอด/หลักฐานที่เปลี่ยนต้องกลับตรวจหรือเข้า adjustment ที่เหมาะสม ไม่เก็บ approval เดิมไว้บนข้อมูลใหม่ |

BA ต้องส่งมอบ decision table, ตัวอย่าง expected amounts, ผู้รับผิดชอบนโยบาย และ acceptance ทั้งเส้นทางสำเร็จ/ผิดพลาด ตัวอย่างแกนกลางคือซื้อ 1,290 บาทแล้วเบิกเฉพาะส่วนบริษัท 810 บาทได้ด้วยหลักฐานการแบ่งที่ตรวจได้ ซึ่งยังเป็นความสามารถใหม่ ไม่ใช่การแก้ยอดใบเบิกเองตามใจ

กรณี “ไม่รู้ใครจ่าย/ไม่รู้เงินบริษัทหรือส่วนตัว/ไม่รู้สัดส่วนสิทธิ” เป็นข้อมูลให้คนตอบหรือกำหนดนโยบาย กรณี “ข้อความส่วนลดอยู่ใต้ร้านไหน/เลขซ้ำจากภาพซ้อน” เป็นงานของระบบอ่านและตรวจหลักฐาน ไม่โยนให้ผู้ใช้กรอกใหม่ทั้งหมด

### 15.3 มุม SA: ต่อของเดิมโดยรักษาเจ้าของข้อมูล

ใช้ entry, storage/attachment, OCR request, draft review, permission และ audit เดิม เพิ่มความสัมพันธ์และ snapshot เฉพาะที่จำเป็นก่อนเปลี่ยนสถานะการเงิน ไม่แยกฐานข้อมูล/บริการ marketplace ใหม่จากความต้องการนี้เพียงอย่างเดียว

| เจ้าของ | หน้าที่ |
|---|---|
| Intake/attachments | รับไฟล์ ตรวจสิทธิ/ขนาด/บริษัท/สาขา เก็บต้นฉบับ และผูกงานเดิม |
| AI Gateway | คืนการอ่านที่มี schema และหลักฐาน รวม group/store/item suggestions ผ่าน API; ไม่อ่านหรือเขียน ERP repository โดยตรง |
| Expense core | source facts ที่ตรวจแล้ว ตัวเลข การจัดกลุ่ม/แบ่งส่วน สถานะร่างและ revision |
| Reimbursements | ผู้ขอเบิก/ผู้รับคืน source eligibility การอนุมัติ การจ่าย และกันการเบิกซ้ำ |
| Ledger/tax | journal identity, account/tax mapping, งวดบัญชี, reversal และสิทธิภาษีจาก facts ที่ผ่านการตรวจ |

ข้อจำกัดที่พบจาก docs และ code จริง ซึ่งเปลี่ยนขอบเขตการพัฒนา:

1. [Reimbursement source consistency spec](../specs/reimbursement-source-consistency-spec.md) และ [source resolver](../../apps/api/src/modules/reimbursements/infrastructure/reimbursement-source.ts) รับยอดเต็มของ source expense: line.amount ต้องเท่ากับ source netPayableAmount การเลือกบริษัทเฉพาะบางสินค้าใน expense เดียวจึงยังส่งเข้าใบเบิกเดิมโดยลด line.amount ไม่ได้
2. ตัว resolver ไม่รับ source ที่ CONFIRMED/VOIDED/REJECTED, posted, มี paidAmount หรือเป็น claim-born projection ดังนั้นต้องเลือกเส้นทางเบิกก่อนยืนยันต้นทางเป็นค่าใช้จ่ายบริษัท ไม่ auto-confirm แล้วค่อยพยายามสร้างใบเบิก
3. การเลือกไฟล์ที่เชื่อมกับหลาย source expense ถูกกันด้วย reimbursement_source_ambiguous การแยกสองร้านแล้วแนบไฟล์ชุดเดียวทุก expense ต้องออกแบบ source scope ให้ชัด ห้ามปิด ambiguity guard เพื่อให้ผ่าน
4. source ที่มี WHT หรือ input VAT เป็น CLAIMABLE/NEEDS_REVIEW หรือสถานะภาษีที่ยังไม่พร้อมถูกกันใน source resolver ส่วน [claim materializer](../../apps/api/src/modules/reimbursements/application/services/materialize-claim-expenses.service.ts) ทำ projection แบบ gross/non-claimable อยู่ นี่เป็นข้อจำกัด implementation ของเส้นทางนี้ ไม่ใช่ข้อสรุปว่าพนักงานสำรองจ่ายแล้วบริษัทใช้ภาษีซื้อไม่ได้ตามกฎหมาย
5. [Reimbursement journey](../specs/reimbursement-journey-uplift-spec.md) มีใบเบิกหลายรายการอยู่แล้ว จึงใช้รูปแบบเดิมเมื่อ source แต่ละรายการผ่านกฎ แต่เอกสารเก่าบางส่วนมี scope payment ที่เปลี่ยนต่อมาแล้ว ห้ามนำข้อความเก่ามาสรุปสถานะ runtime โดยไม่ตรวจ code ปัจจุบัน

ทางออกที่เสนอสำหรับ mixed personal/business คือเก็บ original purchase facts ครบ แล้วสร้าง reviewed eligible portion ที่ระบุ source items/quantity, adjustments และ allocated amount ก่อนเชื่อมใบเบิก ต้องเลือก representation ที่เล็กที่สุดใน spec หลังตรวจ model เดิม จะเป็น scope ของต้นทางหรือ eligible child draft ก็ต้องมี lineage และกฎกันใช้สิทธิซ้ำ ไม่ใช้ manual unlink/re-upload เป็นทางเลี่ยง guard

ข้อคงจริงที่ต้องตรวจทุกครั้ง:

- ค่าใช้จ่ายเดิมที่เป็นหลักฐานและรายการที่เกิดจากใบเบิกไม่รับรู้ต้นทุนซ้ำกัน; กลุ่มรวมไม่มี accounting effect ซ้ำกับลูก
- จำนวน/มูลค่าที่ถูกจองหรือใช้เบิกต้องไม่เกิน eligible portion ของ source เดียวกัน แม้หลายไฟล์ หลายรายการ หรือ concurrent requests
- แก้/แบ่งกลุ่ม/เปลี่ยนรายการส่วนตัวแล้ว invalidate calculation และ review ที่ขึ้นกับข้อมูลนั้น; re-OCR ไม่ทับ revision ของคน
- ใช้ idempotency แยก capture, extraction, split/materialization, claim submission และ payment ตาม side effect จริง; retry ไม่สร้างธุรกรรมซ้ำ
- การเชื่อม evidence ต้องตรวจ tenant/branch/owner/role ทุกครั้ง เอกสารชุดเดียวไม่เปิดสิทธิถึงร้านลูกหรือบริษัทอื่นโดยอัตโนมัติ
- หาก source child creation ล้มเหลว ต้องไม่แสดง success ครบชุดทั้งที่สร้างได้บางส่วน ใช้ transaction หรือ resumable operation ที่เหมาะกับขอบเขตเดิม

### 15.4 มุม AI Engineer: อ่านให้ครบ ตอบเฉพาะที่หลักฐานรองรับ

Pipeline ที่เสนอ: อ่านภาพ/หน้าและโครงสร้าง → เสนอ document/store/item relationships → คืน facts และ monetary components ตาม schema → ERP ตรวจตัวเลขและความครบถ้วน → retry เฉพาะปัญหาที่แก้ได้ภายใน budget → human-review เฉพาะส่วนที่ยังไม่ทราบ

- Reuse reader/extractor ที่มีอยู่ แยก transcription ออกจาก interpretation อย่างชัดเจน ไม่เริ่มจากหลายโมเดลหรือหลาย agent โดยไม่มีผล benchmark รองรับ
- รองรับหลายภาพโดยรู้ page order/overlap และขอบเขตร้าน ไม่ส่ง text ยาวรวมจนทำชื่อร้านหลุดจากสินค้า; เกินขอบเขตให้แบ่งงานอย่างมีหลักฐานหรือแสดง incomplete ไม่ตัดแถวท้ายเงียบ ๆ
- เก็บ exact raw label/value และ source location ที่ตรวจย้อนกลับได้ การพบเลขเดียวกันใน OCR text ไม่เพียงพอ เพราะค่าส่ง/ส่วนลด/ยอดรวมอาจเป็นจำนวนเดียวกัน
- แยก read, derived, allocated และ user-reviewed values; ไม่เสนอผู้ให้ส่วนลดหรือ eligible items ที่มองไม่เห็นเป็นข้อเท็จจริง
- มี bounded schema ของ groups/items/components และ UNKNOWN; model output ที่ครบรูปแบบแต่ขาดรายการยังไม่ถือว่าผ่าน
- ถ้า item count หรือ subtotal ไม่ครบ ให้ re-read ส่วนที่เกี่ยวข้องหรือพักรอตรวจ ไม่ใช้ราคา/ส่วนลดปลอมทำยอดให้ตรง
- เคสหลายร้านที่ระบบใหม่ตีความได้ต้องมีเกณฑ์ต่างจากภาพหลายเอกสารกำกวมที่ classifier เดิมปฏิเสธ ห้ามเปลี่ยน classifier ให้รับภาพทุกแบบเพื่อกู้ field
- เอกสารเป็น untrusted input ข้อความสั่ง AI ในรูปไม่มี authority; field/context จากผู้ใช้ไม่ยกระดับ permission หรือเปลี่ยน company context
- เก็บ prompt/model/schema version, failure stage, counts, timing และ cost แบบไม่บันทึก raw PII ลง logs ข้อมูลจริงสำหรับ evaluation ต้องอยู่ภายใต้สิทธิและการเก็บรักษาที่เหมาะสม

เกณฑ์วัดหลัก: grouping precision/recall, seller/item/quantity correctness, ความหมายและscopeของ monetary components, exact amount match, false confident acceptance, manual correction time, review rate, latency และต้นทุนต่อชุด

ต้องแยก held-out ตามธุรกรรม/ชุดหลักฐาน ไม่เอาภาพหน้าอื่นของออเดอร์เดียวกันไปอยู่คนละชุด; มี ambiguous/unreadable/refund/personal items และ template ที่ไม่เคยเห็น ไม่วัดเพียงอ่านยอดรวมตรงกับตัวอย่างที่ใช้ปรับ prompt

confidence ที่โมเดลรายงานยังไม่ใช่ probability ที่ calibrate แล้ว การอ่านเป็น draft ได้ไม่เท่ากับผ่านเงื่อนไขการส่งเบิก และความถูกต้องของตัวเลขไม่แทนการยืนยันผู้จ่าย/สิทธิภาษี

### 15.5 มุมผู้ประกอบการ: งานต้องจบและต้นทุนการใช้งานต้องคุ้ม

- หน้าแรกบอกสิ่งที่ซื้อ ยอดที่เกี่ยวกับตน และ action ถัดไปที่ทำได้จริง ไม่ต้องเปิดสามแอปเพื่อรวมส่วนลดด้วยมือ
- ระบบถามเฉพาะ facts ที่คนรู้ เช่น ใครจ่ายและรายการส่วนตัว โดยใช้ข้อมูลสมาชิก/บริษัท/สาขาที่มีแล้ว ไม่ให้กรอกชื่อร้าน/ยอดซ้ำเมื่ออ่านได้
- ความสำเร็จต้องดูจากเวลาที่เจ้าของ/พนักงานและบัญชีใช้รวมกัน การย้ายงานแก้ไปให้บัญชีจำนวนมากยังไม่ถือว่าประหยัดเวลา
- มีทางใช้ได้ทั้งเจ้าของทำเองและบริษัทมีบัญชีช่วย ตาม role/approval policy เดิม; ไม่บังคับมีพนักงานเพิ่มเพื่อผ่านขั้นตอน
- เก็บไว้ก่อนแล้วกลับได้จริง รวมถึงการกลับจาก LINE ไปเว็บ; อ่านอัตโนมัติไม่พร้อมยังใช้ manual path ได้ภายใต้สิทธิ์
- ต้นทุนต่อชุดและวิธีนับสิทธิ์อ่านสำหรับหลายภาพต้องชัดก่อนกำหนดราคา ไม่ให้ภาพซ้ำ/system retry ทำให้ลูกค้าเกิดความสับสนเรื่องสิทธิ์หรือต้องเริ่มงานใหม่
- ตัวเลขวัดธุรกิจคือ captured-to-completed rate, user active time, การส่งภาพซ้ำ, งานค้างเพราะไม่รู้คำตอบ, งานบัญชีที่ต้องแก้ และการเบิก/ลงบัญชีซ้ำที่หลุด ไม่ถือจำนวนไฟล์ที่ OCR สำเร็จเป็นผลลัพธ์ทั้งหมด

### 15.6 มุมบัญชี: เอกสาร เงินจ่าย และภาษีมีเจ้าของคนละส่วน

ต้องเห็นและตรวจย้อนกลับได้จากชุดเดียวกัน: เอกสารร้านค้า → รายการสินค้า/บริการ → ส่วนลดที่มีผลจริง → แหล่งเงินที่ชำระ → ส่วนที่เป็นของบริษัท → หนี้ต่อผู้ขายหรือพนักงาน → การจ่าย/คืนเงิน → รายการบัญชี

| หัวข้อ | ผลที่ระบบต้องรักษา |
|---|---|
| คู่ค้า/ผู้รับเงิน | ชื่อร้านบนแพลตฟอร์ม ผู้ออกใบกำกับ ผู้รับชำระ และผู้รับเงินคืนพนักงานแยกกันได้ |
| การจำแนกซื้อ | ค่าใช้จ่าย สินค้าคงเหลือ สินทรัพย์ เงินล่วงหน้า หรือรายการเพื่อบุคคลอื่นต้องเข้าบัญชีตามข้อเท็จจริง ไม่โยนทุก SKU เป็นค่าใช้จ่ายทั่วไป |
| ส่วนลด | ส่วนลดร้านที่อยู่บนใบกำกับ ส่วนลดแพลตฟอร์ม เงินสนับสนุน และ reward มีผลต่างกันตามหลักฐาน; ไม่ลดยอด VAT หรือรับรู้รายได้อื่นอัตโนมัติจากชื่อ coupon |
| ค่าขนส่ง/ค่าบริการ | ต้องทราบผู้ออกเอกสารและบริบทการให้บริการก่อน tax mapping ไม่กำหนด VAT/WHT ด้วยคำว่า “ค่าขนส่ง” อย่างเดียว |
| เบิกบางส่วน | ยอดบริษัท/ส่วนตัวต้องมีฐานแบ่งที่ตรวจได้ พร้อมเก็บต้นฉบับครบและกันใช้ source ส่วนเดียวกันซ้ำ |
| จ่ายแล้วหรือยัง | หลักฐานการที่พนักงานจ่ายร้านค้าไม่ใช่การที่บริษัทจ่ายคืนพนักงาน; ไม่เติม ExpensePayment ของบริษัทจากสลิปส่วนตัวโดยอัตโนมัติ |
| Refund/credit note | แยกเงินคืนจริงกับเอกสารปรับยอด ผูก source เดิม รักษา approval/period/reversal ตามเดิม ไม่แก้ยอดย้อนหลังเงียบ ๆ |
| Audit/export | เห็นยอดเดิม ยอดที่ยอมรับ วิธีแบ่ง ผู้แก้ เหตุผล และลิงก์หลักฐานที่ยังอยู่ในสิทธิ ไม่ต้องเปิด raw JSON เพื่อทำงานบัญชี |

[มาตรา 82/5](https://www.rd.go.th/5206.html) กำหนดข้อจำกัดภาษีซื้อเรื่องหลักฐานและความเกี่ยวข้องกับกิจการ จึงแยกความพร้อมเบิกออกจากสิทธิใช้ภาษีซื้อ [ข้อหารือส่วนลดในกิจการโทรศัพท์](https://www.rd.go.th/24410.html) และ [ข้อหารือบริการออกของพร้อมขนส่ง](https://www.rd.go.th/24178.html) แสดงการพิจารณาตามข้อเท็จจริงเฉพาะกรณี ใช้เตือนการออกแบบไม่ให้เหมารวมเท่านั้น ไม่ใช่กฎตัดสิน marketplace vouchers/ค่าขนส่งทั้งหมด การบัญชีเงินสนับสนุนและนโยบายต้นทุนต้องตกลงจากเอกสารจริงก่อน final posting

ไม่เสนอ journal entries ตายตัวในรอบนี้ เพราะยังไม่มีเอกสารจริงที่ระบุผู้ออกใบกำกับ แหล่งเงิน และฐานภาษีครบ การใช้ gross/non-claimable ของ claim projection ปัจจุบันเป็นขอบเขตซอฟต์แวร์ที่ต้องรักษาหรือแก้ด้วย spec ไม่ใช่ฐานกฎหมายให้ตัด VAT ที่พิสูจน์ได้ทิ้ง

### 15.7 จุดที่ทั้งห้ามุมต้องตกลงร่วมกัน

| การตัดสินใจ | ข้อเสนอ |
|---|---|
| ทางเข้าผู้ใช้ | ใช้ค่าใช้จ่าย/LINE เดิม ระบบตรวจประเภทและแสดงรายละเอียดตามที่พบ |
| ใครเป็นคนคำนวณ | AI อ่าน facts; ERP คำนวณ/ตรวจขอบเขต; ผู้ใช้ยืนยันเรื่องส่วนตัว/บริษัทและผู้จ่าย; policy/accountant ตัดสินภาษีและข้อยกเว้น |
| หน่วยข้อมูล | ชุดหลักฐานสำหรับการใช้งาน + source scope ที่พิสูจน์ได้สำหรับ expense/claim; หนึ่งชุดไม่จำเป็นต้องมีหนึ่ง expense หรือหนึ่ง payment |
| การจัดการต้นทางใบเบิก | เลือกเส้นทางก่อน finalizing source; reuse reimbursement workflow และ projection เดิมเท่าที่ eligibility รองรับ |
| ของส่วนตัวปน | ต้องออกแบบ eligibility/allocated source และกันซ้ำก่อนส่งเบิกบางส่วน; เก็บ/อ่าน/แสดง draft ได้โดยไม่อ้างว่าส่งใบเบิกสำเร็จแล้ว |
| เอกสารภาษี/เงินจ่ายซับซ้อน | เก็บข้อมูลเดิมครบและให้ทาง review ที่มีผู้รับผิดชอบ; ไม่ลดสิทธิภาษีหรือปลด guard เพื่อให้ผ่าน pipeline |
| ข้อมูลไม่ครบ | เก็บไว้ แสดงสิ่งที่ขาดและ action ที่เข้าถึงได้ ไม่ fabricate ยอดหรือบังคับเริ่มใหม่ |
| Scope การพัฒนา | spec/plan สำหรับการอ่านหลายร้าน + จุดเชื่อม expense/reimbursement + UX recovery ก่อน code; ไม่เปิด marketplace seller import ทั้งชุด |

### 15.8 ลำดับพิสูจน์และเกณฑ์รับงาน

1. ทำ expected-output bundles จากเอกสารจริงและ policy examples รวมอย่างน้อย: บริษัทจ่ายตรง, พนักงานจ่ายเต็ม, ส่วนตัวปน, shared voucher, ภาพซ้ำ, invoice ตามมา, refund และ tax review
2. ตรวจช่องว่าง contract/reimbursement ที่พบข้างต้น แล้วกำหนด representation ของ eligible source ที่ตรวจ lineage และกันซ้ำได้ โดยยังรักษาหน้าหลักง่าย
3. ทดลอง draft-only ผ่านทางอัปโหลดเดิมก่อน: หลายร้าน/หลายภาพ/รายละเอียดครบ/unknown พร้อม manual recovery โดยยังไม่อ้างว่า partial claim หรือ VAT handoff สำเร็จ
4. เชื่อมเส้นทางธุรกรรมที่กำหนดไว้ใน spec ทีละกรณี: source eligibility → claim → review/approval → accounting/payment; ใช้ existing permissions และ idempotency
5. รับงานด้วย user test 40+ และ focused integration/browser tests สำหรับตัวเลข/ข้อมูลที่แก้/ภาพแนบ/สิทธิ/งานค้าง/การ retry รวมถึง regression ของบิลร้านเดียวเดิม

Pilot ที่เริ่มจาก THB, ข้อมูลครบ, บริษัทใช้ทั้งหมด, พนักงานจ่ายเต็ม และภาษีอยู่ในขอบเขตเดิมช่วยพิสูจน์จุดเชื่อมได้ แต่ยังไม่ถือว่าบรรลุ feature ทั้งหมดซึ่งรวมหลายร้านและของส่วนตัวปน เกณฑ์เปิดใช้งานและ coverage ต้องแสดงตรงกับสิ่งที่ผ่านจริง

Verification รอบห้ามุม: อ่าน spec ค่าใช้จ่าย/ภาษี/ledger/reimbursement และ code source resolver/materializer; ตรวจ official Revenue Department pages เพื่อแยกหลักภาษีกับข้อจำกัดซอฟต์แวร์ เป็นการวิเคราะห์แบบ read-only ไม่มี application tests, live environment access, implementation หรือ approval to implement

## 16. Solution baseline หลังรวมทั้งหกมุมและใบรับรองแทนใบเสร็จ

ข้อเสนอที่เลือกถูกสรุปเป็น [solution spec](../specs/marketplace-buyer-expense-capture-spec-th.md) และ [phased plan](../plans/marketplace-buyer-expense-capture-plan-th.md) เพื่อใช้ตั้งต้นก่อน implementation โดยให้สองเอกสารนี้เป็นแหล่งอ้างอิงของข้อเลือกที่ล่าสุด ส่วน research นี้รักษาที่มาและข้อจำกัดจากการค้นคว้า

ทิศทาง: โฟลว์อัปโหลดเดิม → เก็บ source facts ครบ → ตรวจและจัดส่วนบริษัท → ใช้ใบเสร็จเดิม/จัดทำใบรับรองเมื่อเข้าเงื่อนไข → expense หรือใบเบิกเดิมตามผู้จ่ายและสิทธิ

เลือกสร้าง eligible source จากส่วนบริษัทที่ตรวจแล้วเพื่อคง full-source claim semantics ไม่เปิดให้แก้ partial claim amount ตามใจ; ต้องเพิ่ม canonical lineage, actual payer binding, group locks/unique handoff และ capture-only guards ให้ทำงานจริง

ผู้ใช้ย้ำให้รวมใบรับรองแทนใบเสร็จ: baseline รวม wizard เดิม DIGITAL/PAPER, actual certifier, COMPANY issuance payment idempotency, PERSONAL no-company-repayment, source review/correction และทางกลับงานเดิมแล้ว การไม่มี VAT invoice อย่างเดียวไม่เท่ากับต้องออกใบรับรอง และกระดาษที่ไม่มี verified payer account ยังส่งเบิกคืนในระบบไม่ได้ตามขอบเขตเดิม

สถานะ: proposed solution/spec/plan เท่านั้น ไม่มี application changes หรือการออกเอกสาร/ลงนาม/จ่าย/ลงบัญชีจริง
