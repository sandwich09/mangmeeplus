# ตรวจ UX/UI มั่งมีสำหรับผู้ประกอบการ — 16 กันยายน 2569

**ข้อสรุป: มีธีมหลักร่วมกันแล้ว แต่ยังไม่สม่ำเสมอทั้งระบบ และยังมีหน้าที่ทำให้ผู้ใช้ต้องเดาว่าควรทำอะไรต่อ** ปัญหาหลักคือการจัดลำดับงาน ความเด่นของปุ่ม ข้อมูลที่มาก่อนผลลัพธ์สำคัญ และความไม่ตรงกันระหว่างช่องทาง มากกว่าการขาดสีหรือการ์ดที่สวยงาม

นี่เป็นการประเมินโดยผู้ตรวจจากหน้าจอ โค้ด และเอกสาร ไม่ใช่ผลทดลองกับลูกค้าจริง อายุ40+ไม่ได้แปลว่าใช้เทคโนโลยีไม่เป็น สมมติฐานที่ใช้คือเจ้าของร้านมีเวลาจำกัด ถูกขัดจังหวะบ่อย ใช้มือถือ และบางคนต้องการตัวอักษร/พื้นที่กดที่อ่านและแตะง่ายขึ้น

## ขอบเขตและหลักฐาน

- ตรวจโครงสร้าง `page.tsx`158รายการ รวมฝั่งระบบ51รายการ และ feature TSX141ไฟล์ บันทึกเส้นทางครบใน [source-inventory.json](../evidence/mangmee-ux-audit-2026-09-16/source-inventory.json) จำนวนนี้ไม่ใช่จำนวนหน้าที่เปิดทดสอบครบทุกสถานะ
- เปิดหน้าจริง UAT9หน้า: Dashboard, รายการใบเสร็จรอตรวจ, ตรวจใบเสร็จ, อัปโหลด, แพ็กเกจ, เบิกจ่าย, ตั้งค่าบริษัท, AIแนะนำ, เข้าใช้งานด้วยอีเมล และเปิดเว็บทางการส่วนแรก/ราคา
- ตรวจที่1512×745 และบางหน้าที่390×844 โดยไม่ได้ส่งข้อมูลธุรกิจ บันทึกใบเสร็จ จ่ายเงิน หรือเปลี่ยนค่าในรอบตรวจนี้
- แอดมิน: ตรวจ source ปัจจุบันและภาพ local browser ของ releaseเดียวกันที่มีอยู่แล้ว ไม่ใช่การเปิด sessionแอดมินใหม่ในรอบนี้
- LINE: ตรวจรูป rich menu, manifest, handlerและcard ไม่ใช่การทดสอบบนแอป LINE/iOS/Androidจริง
- Source base2221b24d; UATให้บริการ7ccff811; copy fixจากรอบก่อนยัง local. `mangmee_web`ที่เผยแพร่กับไฟล์ในเครื่องต่างกัน จึงระบุแยกชัดเจน

## สิ่งที่ทำดีอยู่แล้วและควรรักษา

1. Workspaceมีสีเขียว พื้นสว่าง ฟอนต์ร่วม เมนูตามสิทธิ์ และปุ่มหลัก/รองในหลายหน้าที่สม่ำเสมอ
2. ตรวจใบเสร็จมี3ขั้น: ตรวจข้อมูล → ภาษีและเอกสาร → ตรวจก่อนส่ง พร้อมคำอธิบายขั้นปัจจุบันและปุ่มถัดไป
3. หน้าสมัครอีเมลเริ่มจากช่องเดียวและปุ่มรับรหัสเดียว มี loading/error/focus/retry stateในโค้ด
4. หน้าตั้งค่าบริษัทแสดงการ์ดตามสิทธิ์ พร้อมคำอธิบายผลของแต่ละเรื่อง อ่านได้ง่ายกว่าหน้ารวมปุ่ม
5. Uploadเลือกสาขาให้เมื่อมีตัวเลือกเดียว อธิบายว่า AIสร้างฉบับร่าง และแยกปุ่มถ่ายรูป/เลือกไฟล์
6. Billingมีสถานะรอผลที่ตรงความจริง ล็อกการกดซ้ำ และแยกการจ่ายจากการเปิดสิทธิ์; แอดมินมีร่าง ตรวจผลกระทบ ยืนยันตัวตนและประวัติ
7. ข้อมูล JSON ในหน้ารายละเอียด AIถูกเก็บในส่วนพับ “รายละเอียดสำหรับฝ่ายสนับสนุน” แล้ว ไม่ใช่สิ่งที่ผู้ใช้ต้องอ่านเป็นอันดับแรก

## ลำดับที่เสนอให้ใช้ร่วมกันทั้งระบบ

แต่ละหน้าควรตอบได้ทันทีว่า **อยู่ร้านไหน → ตอนนี้เกิดอะไรขึ้น → ต้องทำอะไรต่อ → กดแล้วจะเกิดอะไร → สำเร็จแล้วไปไหน**

| งาน | ลำดับที่ผู้ใช้เห็น | ปุ่มหลักตามจังหวะ |
| --- | --- | --- |
| เริ่มใช้งาน | เลือกLINE/อีเมล → ยืนยันตัวตน → ข้อมูลร้านที่จำเป็น → พร้อมใช้งาน → ใบเสร็จแรก | เริ่มด้วยLINE / รับรหัส → ยืนยัน → เริ่มใช้ร้าน → ถ่ายใบเสร็จ |
| ตรวจใบเสร็จ | ตรวจผู้ขาย/วัน/ยอด → แสดงเรื่องภาษีที่ต้องตัดสินใจ → สรุปก่อนบันทึก → ผลสำเร็จ | ถัดไป → ตรวจสรุป → ยืนยันข้อมูล → ตรวจใบถัดไป |
| ซื้อแพ็กเกจ | สิทธิ์ปัจจุบัน → เลือกแพ็กเกจ → สรุปยอด/วัน/โควตา/ต่ออายุ → Stripe → ผลเปิดสิทธิ์ | ดูแพ็กเกจ → ตรวจสรุป → ไปชำระ249บาท → กลับไปใช้งาน |
| เจ้าของอนุมัติ | งานรอฉัน → รายการและหลักฐาน → ผลกระทบ/ผู้รับเงิน → ยืนยัน → คิวถัดไป | ตรวจรายการ → อนุมัติรายการนี้ → รายการถัดไป |
| แอดมินแก้สิทธิ์/ค่า | ค้นหาลูกค้า → เลือกงาน → กรอกค่าและเหตุผล → ดูก่อน/หลัง → ยืนยันตัวตนและการเปลี่ยน → ประวัติผล | เลือกลูกค้า → ตรวจผลก่อนบันทึก → ยืนยันการเปลี่ยน → ดูผล |
| LINE | เลือกร้านเมื่อจำเป็น → ส่งรูป/ถามเรื่องงาน → ผลอ่านหรือคำตอบสั้น → งานถัดไปหนึ่งเรื่อง | ตรวจใบเสร็จ / เปิดรายจ่าย / ไปจัดการแพ็กเกจ ตามstateและสิทธิ์ |

ปุ่มรองและย้อนกลับต้องยังเข้าถึงได้ ผู้ใช้ที่ทำงานคล่องไม่ควรถูกบังคับผ่านหน้าที่ไม่เกี่ยวข้อง การยกเลิกต่ออายุ/ขอความช่วยเหลือต้องหาเจอง่าย คำสั่งที่เกี่ยวกับเงิน สิทธิ์ หรือลบข้อมูลยังคงขั้นตรวจและยืนยันตามความเสี่ยง

## เกณฑ์สำหรับรอบแก้

1. **ลำดับปุ่ม:** หนึ่งงานถัดไปที่เด่นในบริเวณตัดสินใจ ป้ายใช้กริยาและผลลัพธ์ ปุ่มนำทางไม่ดูเหมือนคำสั่งบันทึก
2. **ผลลัพธ์ก่อนรายละเอียด:** หน้าหลังจ่าย/หลังบันทึกเห็นผลสำเร็จหรือรอผล พร้อมสิ่งที่ทำต่อได้ในจอแรกที่390×844 ไม่ต้องเลื่อนผ่านการตั้งค่าที่สำเร็จแล้ว
3. **อ่านง่าย:** คงเป้าหมายP24เนื้อหาหลัก16pxขึ้นไป,ระยะบรรทัดไทยอ่านง่าย; captionเล็กได้เฉพาะข้อมูลรองที่ไม่จำเป็นต่อการตัดสินใจ ปุ่มสำคัญใช้ข้อความอ่านได้ชัด
4. **พื้นที่กด:** ตั้งเป้าหมายผลิตภัณฑ์44×44pxขึ้นไปสำหรับcontrolsสำคัญตามP24; อย่าอ้างว่าWCAG AAบังคับ44pxทุกกรณี เพราะ2.5.8ขั้นต่ำ24×24และมีข้อยกเว้น
5. **สี/โฟกัส:** ข้อความปกติcontrastอย่างน้อย4.5:1,ข้อความใหญ่3:1; ตรวจfocus/keyboard/200%zoom/reflowและhighcontrastตามตัวจริง
6. **กดซ้ำ/หลงหน้า:** busyชัดเจน ปุ่มไม่ย้ายตำแหน่งเพราะข้อความloading รักษาร่าง/บริษัท/สาขาเมื่อย้อนกลับ มีเหตุผลใกล้ปุ่มที่ใช้ไม่ได้และทางแก้ที่ตรงปัญหา
7. **ข้อมูลสำคัญไม่หาย:** จำนวนเงิน บริษัท วันหมดอายุ ภาษี ผู้รับ และผลจากการยกเลิกต้องเห็นก่อนยืนยัน ไม่พับข้อมูลที่ทำให้ตัดสินใจผิด
8. **ไม่เปลี่ยนbusiness/securityด้วยการจัดUI:** คงpermission/tenant/source-version/idempotency/preview/confirmation/auditทุกจุด รวมexitของร่างที่invalidและเส้นทางเลิกต่ออายุ

แนวทางนี้สอดคล้องกับ [W3Cสำหรับผู้ใช้สูงวัย](https://www.w3.org/WAI/older-users/), [หลักลำดับปุ่มของGOV.UK](https://design-system.service.gov.uk/components/button/), [WCAGcontrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) และ [WCAGtarget size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html). ขนาด16px/44pxในที่นี้เป็นเป้าหมายของผลิตภัณฑ์ตามP24 ไม่ใช่การเหมารวมข้อกำหนดWCAGทั้งหมด
