## 1. สิ่งที่คุ้มทำก่อน และสิ่งที่ยังไม่ควรลงทุน

| ลำดับ | ชุดงานที่เสนอ | คุณค่าฝั่งลูกค้า/เรา | ขนาดงานสัมพัทธ์และข้อแลกเปลี่ยน |
|---|---|---|---|
| A | ทางเข้าร้านเดิมเด่นกว่าเปิดร้านใหม่สำหรับบัญชีที่รู้จัก; ปุ่มแอดมินระบุผลชัด; คู่มือตรงรุ่น | ลดร้านซ้ำและแนะนำผิด ลดเวลาสอนลูกค้า | ต่ำถึงกลาง ใช้สิ่งที่มี; ยังไม่ทำให้กู้บัญชีที่ไม่มีหลักฐานเป็นอัตโนมัติ |
| B | หน้าเคสเดียวเชื่อมคำขอสมัคร บัญชี/ร้านที่มีสิทธิ์ดู เหตุผลที่ค้าง ข้อมูลที่ขาด และทางแก้ | ส่งต่อง่าย ขอข้อมูลครั้งเดียว ไม่เปิดหลายหน้าเพื่อเดาว่าเกิดอะไร | กลาง มี inbox/รหัสคำขอเดิมให้ต่อ; ต้องเพิ่มเจ้าของเคส/ผลแก้จริงเท่าที่ขาด |
| C | ทำเองสำหรับเข้า LINE/บัญชีเดิมได้: กลับร้าน เพิ่มร้าน หรือผูกหลังพิสูจน์ | คนทั่วไปไม่รอ ลดภาระแอดมิน | กลางถึงสูงตามการเชื่อม journey และพิสูจน์สิทธิ์; ใช้ auth/link/merge ที่มี |
| D | กู้แบบไม่มีช่องทางเดิม และการรวมบัญชีหลายรูปแบบอัตโนมัติ | อาจลดเคสยากเมื่อปริมาณมาก | สูงและเสี่ยง ยังคงให้ผู้มีอำนาจตรวจรายกรณีจนข้อมูลต้นทุน/ความถี่พิสูจน์ว่าคุ้ม |

ขนาดงานเป็นการประเมินจาก code paths ที่มี ไม่ใช่เวลาประเมินงานหรือราคาที่ตกลงแล้ว ไม่เสนอซื้อระบบ ticket, SMS, eKYC, identity provider หรือใช้ AI ตัดสินแทนเป็นจุดเริ่มต้น

## 2. กฎที่เสนอ โดยมีลำดับก่อนหลัง

ตรวจคำขอเดิมและสถานะจริงก่อนสร้างอะไรใหม่ จากนั้นตรวจข้อห้าม/สิทธิ์ ตัวตน เจตนา และสิทธิ์ทดลองตามลำดับ การเข้าบัญชีได้ไม่ใช่สิทธิ์ OWNER ของทุกร้านในบัญชีนั้น

| รหัส | เงื่อนไข | ผลที่เสนอ | ร้าน/สิทธิ์ทดลอง |
|---|---|---|---|
| R01 | request เดิมยังค้าง หรือสร้างร้านแล้วแต่ตอบกลับไม่สำเร็จ | กลับสถานะ/ทำงานเดิมให้จบด้วย request เดิม | ไม่สร้างซ้ำ ไม่หัก/แจกสิทธิ์ซ้ำ |
| R02 | LINE/บัญชีถูกระงับ หรือมีข้อห้ามที่ยืนยันแล้ว | ส่งเจ้าหน้าที่ที่มีอำนาจดูสาเหตุ แยกการระงับจากหมดแพ็กเกจ | สมัครใหม่/กู้บัญชีไม่ข้ามข้อห้าม |
| R03 | เข้า LINE/บัญชีเดิมได้ และมีสิทธิ์ในร้านที่เลือก | กลับร้านเดิม; พนักงานคงสิทธิ์พนักงาน | ข้อมูล/แพ็กเกจ/ยอดใช้เดิม |
| R04 | บัญชีที่พิสูจน์แล้วต้องการเพิ่มสาขา | เพิ่มสาขาภายใต้ร้านและแพ็กเกจเดิมเมื่อมีสิทธิ์ | ไม่สร้างบริษัทหรือ trial ใหม่ |
| R05 | บัญชีที่พิสูจน์แล้วต้องการร้านใหม่จริง | ยืนยันว่าเปิดร้านใหม่ เพิ่มให้บัญชีเดิม ใช้สิทธิ์แพ็กเกจที่อนุมัติ | การให้ทดลองเพิ่มเป็นการตัดสินใจแยก |
| R06 | เจ้าของรายแรกตามตัวตนที่ระบบยืนยันได้ ข้อมูลถูกต้อง ไม่มีความขัดแย้ง/ข้อห้าม และยังมี cap/ระบบพร้อม | เปิดร้านอัตโนมัติตามกฎเดิม ไม่ต้องตั้ง password หรือรอส่งเมล | ใช้ preset15 เดิม ไม่ hardcode อีกชุด |
| R07 | อีเมลตรงบัญชีเดิมของตนเอง และพิสูจน์การเข้าถึงบัญชีนั้นได้ | ใช้บัญชีเดิม; เลือกกลับร้านหรือเพิ่มร้าน | ไม่ให้ email ของตัวเองเป็นเหตุ manual ซ้ำโดยลำพัง |
| R08 | อีเมลตรงบัญชีอื่น แต่ยังพิสูจน์การเข้าถึงไม่ได้ | เก็บคำขอ ให้แก้เมล/เข้าบัญชีเดิม/ขอช่วย; ไม่รวม ไม่ย้ายอีเมล | ไม่เปิดร้านหรือแจก trial ระหว่างข้อขัดแย้งยังไม่คลี่คลาย |
| R09 | อีเมลติดต่อร้านใช้ร่วมกัน แต่เป็นคนละคนจริง | เจ้าหน้าที่บันทึกว่าเป็น shared contact; แยกบัญชีและสิทธิ์; หากเข้าร้านเดียวกันใช้การเชิญตามบทบาท | contact ซ้ำไม่เท่ากับบัญชีเดียว; อีเมลล็อกอินชนต้องแก้/พิสูจน์บัญชี ไม่ปล่อยให้เข้าใจผิด |
| R10 | ซ้ำแค่คำขอเก่าที่จบ/หมดอายุ ไม่มีร้านเกิด ไม่มีการระงับ/ข้อห้ามที่ยืนยัน | ประวัตินี้เพียงอย่างเดียวไม่เป็นการจองอีเมลถาวร; พิจารณา auto ตาม R06 | ไม่ลบ audit; ถ้าร้านเกิดแล้วแม้เปิดค้าง ต้องใช้ R01 |
| R11 | อีเมลเดียวกันชนคำขอที่กำลังทำจาก LINE อื่น | รอคลี่คลาย/แก้ข้อมูล ไม่ auto ทั้งคู่ | ใช้หลักฐานคำขอ committed กัน race; ฝั่งที่มีสิทธิ์เดิมไม่ถูกยึดเพราะคนอื่นกรอกเมล |
| R12 | ร้านเดิมหมดทดลอง/แพ็กเกจ | กลับร้านเดิมและเสนอการต่ออายุที่ตรงสภาพจริง | ไม่ reset trial ด้วย recovery หรือเปลี่ยน LINE |
| R13 | ลูกค้าหายไป/ไปทำเรื่องอื่น | เก็บคำขอและข้อมูลที่กรอกให้กลับมาทำต่อ; ขอใหม่เฉพาะหลักฐานที่หมดอายุ | ไม่ auto approve เพราะเงียบ และไม่หยุดงานอื่นที่ลูกค้ามีสิทธิ์ทำ |
| R14 | ร้านซ้ำมีรายการจริงทั้งสองแห่ง | ส่งเคสตรวจข้อมูล ห้ามใช้ account merge เป็นการรวมบัญชีทางธุรกิจ/บิลโดยอัตโนมัติ | ไม่ลบร้าน/รายการเพื่อทำให้เลขสวย; ร้านเปล่าจะเก็บถาวร/ปิดต้องยืนยันผลและมี audit |

R07/R10 และการแยกผลแอดมินเป็นข้อเสนอเปลี่ยนจากกฎใน PR #475/#476 ยังไม่ใช่พฤติกรรมที่ deploy แล้ว คำขอ REJECTED เพราะทุจริต/ระงับต้องเข้า R02 ถ้ามีข้อห้ามที่บันทึกชัด ไม่เหมารวมกับพิมพ์ผิดหรือเลิกทำเอง

ผลตรวจต่อจากคำถาม Owner ว่ามี code/ทาง support ครบหรือไม่: [audit โค้ดและทาง recovery R01–R14](line-signup-rules-code-coverage-and-recovery-audit-2026-09-07-th.md) พบช่องว่าง intake ค้างและสถานะ LIFF ที่ reproduce ได้ รวมถึง workflow ใหม่ที่ยังไม่ implement ห้ามใช้ตารางกฎนี้เป็นหลักฐานว่าระบบปัจจุบันรองรับครบแล้ว

อีเมลถูกตรวจแค่รูปแบบไม่ได้พิสูจน์ว่าถือกล่องเมล แม้พิสูจน์ถือกล่องเมล ก็ไม่ได้ให้สิทธิ์ทุกร้านที่เคยใส่อีเมลนั้นเป็น contact ชื่อร้าน/เบอร์/คำตอบเกี่ยวกับรายการย้อนหลังเป็นข้อมูลช่วยตรวจ ไม่เพียงพอให้ย้าย OWNER ด้วยตัวมันเอง

## 3. กฎ trial และอีเมลที่แนะนำให้เริ่มต้น

- ทดลองอัตโนมัติครั้งแรกตามบัญชีเจ้าของที่พิสูจน์ได้; บัญชีพนักงานที่ไม่เคยเป็นเจ้าของไม่ถูกตัดสิทธิ์เพียงเพราะเคยทำงานร้านอื่น
- กลับร้านเดิม/กู้บัญชี/สมัครซ้ำ/เปลี่ยน LINE ไม่เริ่ม trial ใหม่ การเปิดร้านเพิ่มจริงให้เลือกแพ็กเกจหรือให้ผู้มีอำนาจอนุมัติสิทธิ์ทดลองเพิ่ม พร้อมเหตุผลและงบ
- นาฬิกาทดลองเริ่มตอนร้านเปิดสำเร็จตามทางเดิม ไม่เริ่มตอนยื่นคำขอ ถ้าระบบล่มทำให้ใช้ไม่ได้ให้พิจารณาชดเชยตามช่วงที่พิสูจน์ได้ ไม่ reset รอบใหม่ทั้งหมด
- รุ่นปัจจุบัน preset FREE_TRIAL_15 ใช้ monthlySlipLimit15 และกรอบเดือนเดิม เอกสารนี้ไม่เปลี่ยนให้เป็น lifetime15 หรือเปลี่ยนการนับรอบโดยเงียบ ๆ
- การอ่านล้มเหลวไม่กินโควตาลูกค้า แต่ต้นทุนโมเดลที่เกิดจริงยังเป็นต้นทุนเรา จึงต้องกู้ผลสำเร็จเดิมก่อนเรียกใหม่
- ไม่อ้างว่ากันคนเดียวเปลี่ยนทั้ง LINE และอีเมลได้100%; คง cap และงบรวมเดิม การบังคับเก็บข้อมูลมากขึ้นต้องพิสูจน์ความคุ้มค่าก่อน
- คงข้อกำหนดกรอกอีเมลปัจจุบันไว้ในระหว่างออกแบบ วัดว่าคนหลุดที่ช่องนี้หรือไม่ ก่อนทดลองเลื่อนการเก็บไปหลังบิลแรก ไม่เปลี่ยนหลายปัจจัยพร้อมกัน
- หากอีเมลใช้ได้แค่ติดต่อร้าน ต้องบอกว่าเข้าใช้ด้วย LINE และเสนอแก้อีเมลบัญชีภายหลังอย่างตรงไปตรงมา ไม่อ้างว่าอีเมลนั้นล็อกอินได้แล้ว

## 4. วิธีทำให้ support เร็วโดยไม่ข้ามหลักฐาน

### หน้าเคสเดียว

ต่อจาก inbox เดิม ไม่สร้าง ticket system ใหม่ แสดงเจตนา รหัสคำขอเดิม ผู้รับผิดชอบ เวลาเริ่มรอ/ตอบล่าสุด สถานะจริง สิ่งที่พิสูจน์แล้ว เหตุผลที่ติด ข้อมูลที่ยังขาด และผลก่อนกดทำรายการ

แสดงเฉพาะร้าน/ข้อมูลที่เจ้าหน้าที่มีสิทธิ์ดู หลักฐานที่ใช้ยืนยันตัวตนต้องมีแหล่งที่มาและขอบเขต ข้อความที่ลูกค้าบอกหรือ AI สรุปไม่เลื่อนเป็น verified โดยอัตโนมัติ ไม่เก็บ OTP/token/password ในข้อความเคส

### ปุ่มตามผล

- เข้าร้านเดิม: เปิดทางเข้าให้ตัวตนที่พิสูจน์และมีสิทธิ์แล้ว
- กู้การเข้าบัญชี: ใช้ขั้นตอนหลักฐานของ recovery ไม่เรียก provisioning ร้านใหม่
- เพิ่มร้านในบัญชีเดิม: ยืนยันบัญชีปลายทาง จำนวนร้าน และแพ็กเกจ
- เปิดร้านใหม่ให้คนละบัญชี: แสดงว่าไม่เข้าร้านเก่า แสดงผลต่อ email login และ trial ก่อนยืนยัน
- ขอข้อมูลเพิ่ม: ระบบจัดสิ่งที่ขาดให้ครบในข้อความเดียว เจ้าหน้าที่ตัดสิ่งที่ไม่จำเป็นออกได้

แยกการให้สิทธิ์ทดลองเพิ่มออกจากปุ่มแก้การเข้าใช้งาน ทุก mutation ตรวจบัญชี/ร้าน/บทบาทและ source-state อีกครั้งตอน commit; กดซ้ำ/เจ้าหน้าที่สองคนพร้อมกันต้องได้ผลเดียวและ audit เดียวตาม operation เดิม

### หลักฐานคืนบัญชี

1. เข้า LINE/บัญชีเดิมได้: ให้ผู้ใช้ยืนยันเองผ่าน flow ที่มี session และหลักฐาน LINE; ไม่ขอ password/OTP ให้เจ้าหน้าที่
2. มีวิธีกู้ที่เคยผูกและพิสูจน์ไว้จริง: ใช้ตัวนั้นตามข้อกำหนดการกู้ที่รองรับ อย่านับเบอร์หรือเมลที่กรอกไว้เฉย ๆ ว่า verified; ตอนนี้ไม่พึ่ง SES/SMS ที่ยังไม่ได้ตรวจว่าพร้อม
3. ไม่มีทั้งสองอย่าง: ส่งผู้มีอำนาจกู้บัญชี พร้อมหลักฐานความเป็นเจ้าของ/อำนาจในธุรกิจจากแหล่งที่ตรวจอิสระได้และบันทึกเดิมที่เกี่ยวข้อง ชื่อร้าน เมลตรง และรายการย้อนหลังสองรายการอย่างเดียวไม่พอ คืนสิทธิ์ได้เฉพาะเมื่อเกณฑ์กู้บัญชีที่เขียนไว้ครบ; ถ้ายังไม่ครบให้บอกสิ่งที่ขาดและเวลานัดอัปเดต ห้ามผู้รับเคสทั่วไปเดาย้ายสิทธิ์

รายละเอียดประเภทเอกสารที่ยอมรับสำหรับกรณี3 และผู้มีอำนาจต้องเขียนเป็น recovery spec ก่อนทำส่วนนี้ ไม่แปลงการ brainstorm นี้เป็นทางลัดมอบ OWNER ปัจจุบันมีเครื่องมือ reissue/unlink แต่เครื่องมือไม่ได้ทำ identity proof แทนเจ้าหน้าที่

### ขอข้อมูลครั้งเดียว และปิดเมื่อแก้ได้จริง

- รอบแรกขอเพียงเรื่องที่ต้องการทำ ชื่อร้านที่ลูกค้าจำได้ เข้า LINE/บัญชีเดิมได้หรือไม่ และช่องทางนัดติดต่อ; ใช้ข้อมูลที่มีแล้ว ไม่ให้กรอกซ้ำ
- หลัง triage ให้รายการหลักฐานที่ขาดของทางนั้นทั้งหมดในครั้งเดียว หากภายหลังพบข้อขัดแย้งใหม่ต้องบอกเหตุผลที่ขอเพิ่ม
- พักเคสเมื่อรอลูกค้าได้ แต่แยกเวลาที่ทีมรอข้อมูลออกจากเวลาที่คิวดอง และเก็บเวลารวมจริง ไม่ลดตัวเลข SLA ด้วยการกดรอข้อมูลทั้งที่ยังไม่ได้ขอ
- ตอบแล้วไม่เท่ากับแก้แล้ว ส่งลิงก์สำเร็จไม่เท่ากับเข้าใช้ได้ ต้องมีหลักฐานการเข้าร้านถูกแห่ง/รายการสำเร็จหรือการยืนยันของลูกค้า; หากยังไม่ทราบให้เป็นรอยืนยัน ไม่อ้างว่าจบ
- ลิงก์หมดอายุออกใหม่ให้เคสเดิมหลังตรวจสิทธิ์อีกครั้ง ไม่สร้างคำขอสมัครใหม่; ผู้ใช้กลับมาสามารถต่อเคสเดิมได้ตามสิทธิ์และ retention เดิม
- รูปหรือเรื่องใหม่ที่ไม่เกี่ยวกับการกู้ไม่ควรถูกตีความเป็นคำยืนยันย้ายสิทธิ์ ให้เมนู/งานที่ยังทำได้ดำเนินต่อ
- AI ช่วยสรุป/ร่างคำตอบได้โดยให้เจ้าหน้าที่ตรวจ; ใช้ข้อความสำเร็จรูปและกฎตายตัวก่อนหากเพียงพอ ไม่ให้ AI อนุมัติ รวมบัญชี กู้ OWNER หรือเพิ่มโควตา

## 5. เป้าหมายความเร็วสำหรับทดลองภายใน

เป็นเป้าหมายเสนอ ไม่ใช่ SLA ที่โฆษณา และไม่ใช่ความสามารถที่วัดแล้ว ต้องตรวจจำนวนคนเข้าเวร/อัตราเคสก่อนประกาศ

| เคส | เป้าหมายเสนอในเวลาทำการที่ตั้งจริง | หลักการ |
|---|---|---|
| ลูกค้าเดิมเข้าใช้ทำงานไม่ได้/เสี่ยงสิทธิ์ผิด | คนรับเคสภายใน15นาที | ห้ามเร่งคืนสิทธิ์โดยลดหลักฐาน; ส่งคนมีอำนาจทันทีเมื่อจำเป็น |
| สมัครใหม่/อีเมลชนที่ไม่กระทบร้านเดิม | คนรับภายใน1ชั่วโมง | แจ้งทางไปต่อและขอสิ่งที่ขาดครบ |
| เคสง่ายหลังหลักฐานครบและระบบปกติ | ลองตั้งเป้าจบภายใน30นาที | วัด median และ P90 ไม่ดูค่าเฉลี่ยอย่างเดียว |
| เคสยากรอการตัดสิน/พิสูจน์เพิ่ม | นัดอัปเดตอย่างช้าภายในวันทำการถัดไป | เป็นคำมั่นอัปเดต ไม่ใช่รับประกันกู้สำเร็จ |

นอกเวลาให้ระบบรับเรื่องทันทีและแจ้งเวลาที่จะมีคนดูจริง ไม่อ้างว่าเจ้าหน้าที่รับแล้ว คิวเรียงตามผลกระทบและอายุการรอ ไม่ให้เคสเงียบเก่าถูกข้อความใหม่กลบ ผู้รับผิดชอบหนึ่งคนต่อเคสและผู้สำรองหนึ่งช่องทางเป็นเป้าหมายปฏิบัติงาน ไม่ต้องสร้างระบบเวรใหม่หากตารางทีมเดิมพอ

## 6. ความคุ้มค่าและเกณฑ์ลงทุน

ยังไม่มีข้อมูลปริมาณสมัคร อัตราเคส เวลาเฉลี่ย ต้นทุนพัฒนา หรือต้นทุน support จริงที่ตรวจในรอบนี้ ไม่ได้อ่าน AWS cost จึงไม่ระบุ ROI เป็นข้อเท็จจริง

สูตรภาระงาน/เดือน = จำนวนคำขอ × สัดส่วนที่ต้องให้คนช่วย × นาทีต่อเคส ÷ 60

ตัวอย่างสมมติทั้งหมดเพื่อดูขนาด: 300คำขอ/เดือน ก่อนแก้40%ต้องช่วยครั้งละ10นาที =20ชั่วโมง หลังแก้15%ครั้งละ6นาที =4.5ชั่วโมง คืนเวลา15.5ชั่วโมง/เดือน หากคิดค่าเวลา120บาท/ชั่วโมง มีมูลค่าความจุงาน1,860บาท/เดือน หากค่าพัฒนา30,000บาท การคิดคืนทุนด้วยมูลค่าเวลาล้วนใช้ประมาณ16.1เดือนก่อนค่าดูแล ตัวเลขนี้ไม่ใช่ประมาณการโครงการ

เงินเดือนเท่าเดิมไม่ได้ทำให้เงินสดลด1,860บาททันที ประโยชน์คือทีมรับลูกค้าเพิ่มหรือทำงานอื่นได้ เงินสดที่ประหยัดต้องเป็นค่า overtime/outsourcing/การจ้างเพิ่มที่หลีกเลี่ยงได้จริง

การตัดสินลงทุนควรแยก: ค่าใช้จ่ายเงินสดที่ลดจริง + กำไรส่วนเพิ่มจากร้านจ่ายเงินที่เพิ่มสุทธิ/รักษาไว้ได้ (หักค่า AI, payment และ support เพิ่มที่เกี่ยวข้อง) − ค่าดูแลรายเดือน ห้ามนับรายได้ทั้งหมดเป็นกำไร หรือคิด conversion และ retention ซ้ำในลูกค้าคนเดียว

ทำ A/B/C เท่าที่มี evidence รองรับก่อน D หากผลตอบแทนรายเดือนที่ตรวจได้ไม่เป็นบวกอย่าอ้างว่ามีจุดคืนทุน ถ้าจะซื้อบริการใหม่หรือทำ automation เพิ่ม ให้เทียบราคาค่าพัฒนา/ดูแลจริงกับเวลาที่ลดและลูกค้าที่รักษาได้ก่อน

## 7. การวัดและการยอมรับ

- วัดสมัครถึงบิลแรกสำเร็จ โดยแยกลูกค้าใหม่/กลับมา/เพิ่มร้าน/กู้บัญชี ไม่เอาจำนวนบริษัทที่สร้างมาแทนจำนวนลูกค้าจริง
- วัดอัตราเข้าร้านเดิมได้เอง ร้านซ้ำที่ยืนยันแล้ว เคสต่อ100คำขอ จำนวนรอบถามข้อมูล และเวลาจบ median/P90
- ติดตามยอดทดลองที่ให้เพิ่มพร้อมเหตุผลและต้นทุน AI ไม่ให้ตัวเลขคืนโควตาลูกค้าซ่อน provider spending
- ทดลองต้นแบบกับเจ้าของร้านที่คล่อง/ไม่คล่องรวมผู้สูงอายุ แยกเวลาที่รอระบบออกจากเวลาที่หลงทาง
- ทดลองภายใน/กลุ่มเล็กอย่างน้อย2สัปดาห์เพื่อเริ่มเก็บ baseline; ถ้าปริมาณน้อยยังไม่สรุปผลเชิงสถิติและไม่อ้าง uplift ตัวเลขเป้าหมายด้านเวลาเป็นสมมติฐานทดสอบ
- การยอมรับที่ไม่ผ่อน: ไม่ให้สิทธิ์ผิดบัญชี ไม่เปลี่ยนพนักงานเป็น OWNER ไม่สร้างร้าน/สิทธิ์ซ้ำจากกดซ้ำ ไม่เริ่ม trial ขณะรออนุมัติ ไม่เปลี่ยนข้อมูลเดิมจากการกู้ ไม่หยิบ proof ของอีกคำขอ/อีกบริษัทมาใช้ และไม่พาผู้ใช้ไปตั้ง password เพื่อผ่านการสมัครครั้งแรก

## 8. หลักฐานปัจจุบันและช่องว่างก่อนทำ

- [ปุ่ม approve ปัจจุบัน](../../apps/web/src/features/system-signup-requests/SignupQueuePage.tsx): handleApprove ส่ง action APPROVE และตอบว่าเปิดร้านแล้ว จึงต้องปรับทั้ง backend decision และคำบนปุ่ม ไม่ใช่เปลี่ยนข้อความอย่างเดียว
- [provision](../../apps/api/src/modules/external-signup/application/provision-signup.use-case.ts), [account merge](../../apps/api/src/modules/auth/application/use-cases/account-merge.use-case.ts), [owner link reissue](../../apps/api/src/modules/system-onboarding/application/use-cases/reissue-owner-line-link.use-case.ts): มีชิ้นส่วนให้ใช้ แต่ไม่มี approval outcome ใหม่ตามร่างนี้
- [schema](../../apps/api/prisma/schema.prisma) LineSupportRequest มี signupRequestId, คำถามแรก/ข้อความล่าสุด, สถานะ OPEN/ANSWERED/CLOSED และ reopenedCount; ไม่ใช่ประวัติสนทนาครบทุกข้อความหรือ workflow พิสูจน์ตัวตนครบ ต้องไม่อ้างว่าใช้ได้ทั้งหมดแล้ว
- [support queue](../../apps/api/src/modules/external-signup/application/support-request-admin.use-case.ts): มีคิวและ counts เดิม แต่เรียง lastMessageAt ใหม่ก่อนและจำกัด200แถว การทำเร็วต้องมองเคสเก่าด้วยและไม่ซ่อนส่วนที่เกินจำนวนที่แสดง
- [support playbook](../runbooks/line-first-signup-support-playbook.md): ยังมีข้อความไม่มีอีเมล/ปลดโควตาอุ่นเครื่องสัปดาห์แรก ไม่ตรงกับ owner-email/trial15 ล่าสุด ต้องปรับคู่มือตาม release ก่อนให้ทีมใช้ ไม่ถือว่าคู่มือเก่ามีอำนาจอนุมัติ recovery ใหม่
- [trial preset](../../packages/contracts/src/plan-term.ts): FREE_TRIAL_15 และ SIGNUP_TRIAL_WARMUP_SLIPS ใช้ค่าร่วม15 งานใหม่นี้ต้องไม่สร้าง policy limit อีกชุด
- [Auth0 account linking](https://auth0.com/docs/manage-users/user-accounts/user-account-linking): หลักฐานบัญชีทั้งสองฝั่งก่อนเชื่อม
- [OWASP recovery](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html): token ใช้ครั้งเดียว/หมดอายุ ไม่แก้บัญชีก่อนมีหลักฐานที่ถูกต้อง และมี support fallback; เป็นหลักอ้างอิงด้าน recovery ไม่ใช่การอ้างว่า password-reset flow เท่ากับการย้ายความเป็นเจ้าของร้าน

## 9. สถานะก่อน coding

ทิศทางได้รับความเห็นด้วยแล้ว ร่างนี้เสนอการตัดสินใจที่ชัดขึ้น โดยยังต้องกำหนดใน spec/plan: proof ที่ยอมรับและผู้มีสิทธิ์กู้, การให้ trial เพิ่ม, การแยก historical-email signals, ผลการตัดสินใจใหม่และการยกเลิกคำขอสมัครที่ถูกเปลี่ยนไปเป็น recovery, เป้าหมายเวลาตามทีมจริง และการจัดการลิงก์หมดอายุ/คำขอที่กลับมาหลัง retention ไม่เปลี่ยนสิทธิ์หรือนโยบายปัจจุบันจากเอกสารนี้โดยอัตโนมัติ
