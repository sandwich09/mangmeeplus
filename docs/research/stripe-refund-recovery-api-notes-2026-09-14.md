# Stripe refund and invoice-adjustment research

Status: developer research for the unfinished C08 controls; no refund implementation, provider mutation or financial policy approval in this note. Read official documentation on2026-09-14. Existing manual-review policy remains authoritative.

Read-only implementation detail: Refund objects expose pending/requires_action/succeeded/failed/canceled; nullable status remains unknown. Follow the original Charge and keep instructions email, metadata and payment details out of general responses. Credit notes bind Invoice/customer/mode, have issued/void status and a separately requested PDF. Listing credit notes can filter the original Invoice; refund lists can filter Charge. Pages are bounded and cursors are verified against those original bindings. Stripe documents charge.amount_refunded as an aggregate, without specifying pending-status semantics here; do not claim that aggregate proves bank receipt. [Refund object](https://docs.stripe.com/api/refunds/object), [Credit-note object](https://docs.stripe.com/api/credit_notes/object), [Credit-note list](https://docs.stripe.com/api/credit_notes/list), [Charge object](https://docs.stripe.com/api/charges/object).

Stripe can refund part or all of an original payment, with aggregate refunds bounded by the original charge. Refunds return to the original payment method. An accepted card refund can remain pending when the Stripe balance is insufficient; refunds can also fail. Original processing fees are not returned. Therefore a submitted request must not be presented as money received by the customer. Stripe refund email delivery depends on customer/email configuration. [Refund lifecycle](https://docs.stripe.com/refunds).

The create API targets the original Charge or PaymentIntent and can specify an amount in the currency's smallest unit. Original provider identity must be resolved from verified local invoice/payment evidence, not supplied as arbitrary Admin input. Listing refunds provides a read path to reconcile original requests; metadata, pagination and current API-version fields still need a detailed implementation review. [Create refund](https://docs.stripe.com/api/refunds/create), [List refunds](https://docs.stripe.com/api/refunds/list), [Refund object](https://docs.stripe.com/api/refunds/object).

A credit note adjusts a finalized invoice while preserving the original invoice. Stripe recommends associating credit with original invoice line items. Credit amounts and invoice limits constrain subsequent adjustments. This document is distinct from the card refund's banking outcome. [Invoice credit notes](https://docs.stripe.com/invoicing/dashboard/credit-notes).

The credit-note API can create a refund through `refund_amount` or associate existing refunds through `refunds`; it can also credit customer balance or record an outside payment. Those components must match the post-payment adjustment. These alternatives must not become independent retry actions for the same intended refund. [Create credit note](https://docs.stripe.com/api/credit_notes/create).

Implementation implications to resolve in spec/plan before code:

- Prefer one original invoice/command identity with separate money, document and entitlement observations. Never implement “refund” as reversing an APPLIED flag or deleting receipt grants.
- Decide and document whether the approved command issues a credit note with its refund, or links an existing observed refund. Preserve original invoice lines/tax treatment; reject unsupported credit-balance/outside-payment paths rather than inventing evidence.
- Retain PREVIEW/approval/source/permission/lease boundaries, original command lookup, bounded provider reconciliation and ambiguous-response recovery. A lost response must not mint another refund or credit note.
- Surface pending/failed/canceled/refund-review states, dispute conflicts and accounting-document gaps with original case links. Failed financial execution and support contact are distinct outcomes.
- Existing commercial refund eligibility remains manual review. Monetary thresholds or automatic entitlement revocation are not selected by this research. No Thai tax-law compliance conclusion is made here.

## Monetary execution follow-up (not implemented)

The read-only preview API accepts the intended amount and refund component without creating a credit note. Creation accepts `amount` (or line/shipping detail) and `refund_amount`, so a single original command can request the adjustment and its associated refund. The default credit-note email is enabled; an implementation must deliberately choose and disclose that behavior rather than copying an internal operator reason into customer-facing memo/email. Provider preview line/tax amounts and the final response must be checked against the original invoice; a preview is not authorization or proof of a settled refund. [Preview credit note](https://docs.stripe.com/api/credit_notes/preview), [Create credit note](https://docs.stripe.com/api/credit_notes/create).

Before the next monetary slice, resolve these implementation contracts in the controls spec and shared DTOs:

- Reuse BillingOperation for one immutable command bound to original company/account/mode/Invoice/Charge/case and amount; keep independent initiator/approver and current password/session proof. Scoped Finance needs its own current-scope reauthentication path; existing configuration reauthentication is platform-only. Do not bypass that with copied system permissions.
- Keep refund admission closed until the versioned Admin policy has an approved monetary bound. Always require independent manual approval initially; do not infer a commercial refund window, threshold or automatic loss of paid rights from this research.
- Include current refundable evidence, existing credit notes/refunds, pending or disputed amounts, current paid usage and no automatic entitlement change in preview. Refuse changed source/permission/mode/policy before dispatch; serialize against original account and operation leases.
- Use the original provider idempotency key. After ambiguous transport, discover the original credit note and linked refunds before any new write. Old or incomplete discovery must remain UNKNOWN with exact references; never mint a replacement financial command merely to clear a status.
- Record credit-note issuance, refund lifecycle and any later operator entitlement decision separately. Failed refunds on already-issued credit notes need a specifically designed compensation path; a second credit note/refund is not an assumed valid repair. No implementation of this compensation has been claimed.


## API constraint checked2026-09-15

The update-credit-note endpoint only exposes memo and metadata changes; it is not an API to replace a linked refund. Stripe documents voiding only for credit notes on an open invoice. Therefore an already-issued paid-invoice credit note must not offer an assumed void-and-reissue repair when its refund fails. The create/preview API supports amount plus refund_amount, but execution still requires the separate original-command discovery, current approved bounds and independent approval described above. A compensation needing a new transfer or different payment method must remain an explicit reviewed financial workflow, not automatic replay. [Update credit note](https://docs.stripe.com/api/credit_notes/update), [Voiding credit notes](https://docs.stripe.com/invoicing/dashboard/credit-notes#voiding-credit-notes), [Create credit note](https://docs.stripe.com/api/credit_notes/create), [Preview credit note](https://docs.stripe.com/api/credit_notes/preview). No monetary implementation or native provider mutation was performed by this research.
