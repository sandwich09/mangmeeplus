## 1. ข้อสรุป

ทิศทางเดิมถูก: บริษัทเป็นเจ้าของเงินได้ คนเป็นผู้รับรอง ตำแหน่งเป็นข้อมูลตามจริง และชื่อเอกสารต้องใช้ข้อมูลบริษัทที่บันทึกแล้ว แต่ฉบับก่อนทบทวนยังไม่ครบพอที่จะบอกว่าการจ่าย เบิกคืน บัญชี และภาษีปลายทางถูกต้อง จึงปรับสเปกและเพิ่ม AC19–28 ในรอบนี้ โดยยังไม่ถือว่า implementation ผ่าน

สิ่งที่เห็นในภาพไม่เพียงพอจะวินิจฉัยว่ารายการร้านอาหารเป็นรายจ่ายทางภาษีได้หรือไม่ หรือชื่อผิดเพราะ field ใดใน live data ส่วน snapshot race เป็นบั๊กที่ทำซ้ำใน local ได้จริงตาม audit เดิม

## 4. หลักภาษีที่ใช้กำหนดพฤติกรรม

ตรวจแหล่งทางการวันที่ 2026-09-09 เนื้อหาต่อไปนี้เป็นหลักทั่วไปและการแปลงเป็นข้อกำหนดผลิตภัณฑ์ ไม่กำหนดอัตราหรือเกณฑ์จำนวนเงินเหมารวมจากตัวอย่าง

| เรื่อง | หลักที่ตรวจพบ | ผลต่อผลิตภัณฑ์ |
|---|---|---|
| บริษัทและผู้รับรอง | กรมสรรพากรยกตัวอย่างบริษัทจัดทำใบรับรองแทนใบเสร็จ โดยให้พนักงานรับรองการจ่าย เมื่อเรียกใบเสร็จไม่ได้ | แยกบริษัทเจ้าของรายจ่ายจากบุคคลผู้ดำเนินการและรับรอง ไม่สร้างลายเซ็นของบริษัทขึ้นแทนคน |
| WHT | การทำใบรับรองไม่ได้ลบหน้าที่หรือความรับผิดเรื่องหัก ณ ที่จ่าย | ห้ามล้าง WHT ตอนออกใบ/เบิกคืน และไม่ใช้ตัวเลือก funding เป็น tax rule |

สองข้อข้างต้นอ้าง [กรมสรรพากร: คำถาม–คำตอบ Cluster หน้าที่พิมพ์ 17](https://www.rd.go.th/fileadmin/download/QA_Cluster.pdf) เอกสารเองระบุว่าตัวอย่างไม่ครอบคลุมทุกกรณี จึงไม่ถือว่าเอกสารที่ผู้ใช้กรอกเองทุกรายการผ่านภาษีอัตโนมัติ

- **ภาษีเงินได้นิติบุคคล:** รายจ่ายทางบัญชีกับรายจ่ายที่ใช้คำนวณกำไรสุทธิทางภาษีอาจต่างกัน ต้องตรวจเงื่อนไขของรายจ่ายต้องห้าม วัตถุประสงค์ และผู้รับเงิน ไม่สรุปจากการมีลายเซ็นครบเพียงอย่างเดียว; รายจ่ายลงทุนและค่ารับรองมีข้อพิจารณาเฉพาะ [กรมสรรพากร: รายจ่ายต้องห้าม มาตรา 65 ตรี](https://www.rd.go.th/827.html)
- **VAT:** มาตรา 82/5 มีข้อจำกัดเรื่องไม่มีหรือแสดงใบกำกับภาษีไม่ได้และสาระสำคัญของใบกำกับภาษี จึงไม่ให้ใบรับรองภายในสร้างสิทธิภาษีซื้อโดยลำพัง; การมีใบกำกับภาษีที่เกี่ยวข้องภายหลังต้องส่งตรวจตามหลักเกณฑ์จริง [กรมสรรพากร: มาตรา 82/5](https://www.rd.go.th/5206.html)
- **งวดรายจ่าย:** มาตรา 65 วางเกณฑ์สิทธิในการคำนวณรายได้และรายจ่าย จึงไม่ควรแทนวันเกิดรายจ่ายด้วยวันออกใบหรือวันจ่ายคืนเพื่อให้ workflow ผ่าน การรับรู้/แก้ไขข้ามงวดต้องเข้าการตรวจของบัญชีตามจริง [กรมสรรพากร: มาตรา 65](https://www.rd.go.th/5939.html)

ข้อกำหนดซอฟต์แวร์ที่อนุมานจากหลักเหล่านี้คือเก็บข้อเท็จจริงและหลักฐานแยกจากผลตรวจภาษี ไม่สร้างสถานะ “ผ่านภาษี” จาก funding/signature และไม่ทำลายข้อมูลระหว่าง handoff ส่วนการใช้ OWNER_SELF/ตำแหน่งที่เสนอในระบบเป็นนโยบายภายในที่มีอยู่ ไม่ใช่สิทธิรับรองทางภาษีที่แหล่งอ้างอิงนี้ให้ทุกคนตาม role

## 6. ความพร้อมและขอบเขตส่งมอบ

- ส่งแก้ชื่อ/snapshot/ตำแหน่งก่อนแหล่งเงินได้ตาม plan โดยต้องผ่าน regression ของส่วนที่แก้
- Funding ใหม่ต้องมี final guards และ explicit money effect พร้อมกัน; PERSONAL integration เพิ่มเงื่อนไข §7.4/CC2 ไม่ใช้ generic mapper เดิมเป็นหลักฐานว่าภาษีถูกแล้ว
- แก้ชื่อหลัง posted/paid ต้องมี document-only command ตาม §8.1 ก่อนถือว่ารองรับครบ ไม่ใช้ existing void เป็นทางลัดแก้คำผิด
- จ่ายบางส่วน/ทยอยจ่าย/top-up หลายคนหารจ่าย เงินผสม เงินทดรองบริษัท ข้ามบริษัท และเจ้าของไม่ขอคืนอยู่นอก scope รอบแรก; เคส WHT/VAT ที่ integration ยังไม่รองรับต้องมีข้อความและงานค้างที่ติดตามได้ ไม่รายงานว่าสำเร็จ
- ไม่มีการขยายไปสร้างทะเบียนตำแหน่ง ระบบอนุมัติ ภาษี หรือ reversal engine ใหม่
