# Use case เอกสารค่าน้ำและค่าไฟไทยสำหรับ OCR

Status: สำรวจแหล่งสาธารณะ 25 กันยายน 2569 (Asia/Bangkok); **ยังไม่ใช่ผลรับรองความแม่นยำของ OCR หรือความพร้อม Production**
Scope: เอกสารค่าใช้บริการน้ำ/ไฟของ กปน. (MWA), กปภ. (PWA), กฟน. (MEA), กฟภ. (PEA) ที่ผู้ใช้ส่งผ่าน LINE หรือ Web เพื่อบันทึกค่าใช้จ่าย/หลักฐาน; ไม่รวมการชำระเงินอัตโนมัติหรือการยืนยันสถานะหนี้จากระบบของผู้ให้บริการ
Related: [incident ลองจ่าย](../agent-memory/prod-longchai-utility-bill-ocr-2026-09-25.md), [image intake spec](../specs/business-document-image-intake-spec.md), [expense capture spec](../specs/marketplace-buyer-expense-capture-spec-th.md)

## วิธีสำรวจและขอบเขตหลักฐาน

- ใช้แหล่งของหน่วยงานผู้ออกเอกสารและสำนักงาน กกพ. เป็นหลัก: หน้าเว็บ กปน./กปภ./กฟน./กฟภ./กกพ., คู่มือลูกค้า และตัวอย่าง PDF ที่หน่วยงานเผยแพร่; ไม่ใช้โฆษณาหรือบล็อกภายนอกยืนยันรูปแบบใบจริง
- ตัวอย่าง กปภ. ในคู่มือลูกค้าเป็น **specimen**; PDF ใบแจ้งค่าไฟ กฟน./กฟภ. ที่ search index พบเป็นเอกสารสาธารณะซึ่งอาจมีข้อมูลบุคคล จึงบันทึกเฉพาะโครงสร้างและ URL ไม่คัดลอกชื่อ ที่อยู่ เลขมิเตอร์ เลขบัญชี หรือไฟล์ลง repo. บาง PDF ของ กฟภ. เปิดโดยตรงไม่ได้จากเครื่องมือเว็บ จึงใช้เพียงเป็น lead ไม่ใช่ fixture ที่ตรวจครบ
- แยก `S` = รูปแบบ/กฎที่มีหลักฐานจากแหล่งทางการ, `D` = เคสทดสอบที่อนุมานจากความเสี่ยงของ OCR และ incident. กรณี `S` เป็น **candidate acceptance** ไม่ใช่สิ่งที่ระบบผ่านแล้ว. จำนวนมากไม่ได้แปลว่าทุกแบบของทุกหน่วยงานมี specimen ปัจจุบันครบ
- อัตรา, ส่วนลด, ระยะผ่อนผัน และรูปแบบเอกสารเปลี่ยนตามงวด/ช่องทางได้. อ่าน **ยอดที่พิมพ์บนใบ** และแยกงวดก่อนเสมอ; ไม่คำนวณย้อนหลังด้วยอัตรา ณ วันที่ค้นเว็บเพื่อแทนยอดเอกสาร

## ข้อกำหนดร่วมที่ได้จาก use case

1. ขั้นอ่านควรคืน `documentGroups[]` ที่มี `issuer`, `role` (`INVOICE`, `RECEIPT`, `REMINDER`, `PAYMENT_INSTRUCTION`, `OTHER`), `billPeriod`, `documentId`, `invoiceDate`, `dueDate`, `paymentDate`, `currentCharge`, `priorBalance`, `discountOrCredit`, `payableTotal`, `paidAmount`, `meterRefs`, `fieldProvenance` และ `ambiguities` เท่าที่อ่านได้. Group ไม่ได้แปลว่าจะสร้าง expense หนึ่งรายการทันที
2. `total` ต้องติดป้ายว่าเป็น **ยอดงวดนี้**, **ยอดค้างเดิม**, **ยอดรวมที่ต้องจ่าย**, **ยอดจ่ายจริง**, หรือ **ตัวเลขประวัติ**. ห้ามแปลงทุกจำนวนเงินเป็น expense total เดียว
3. PDF/ภาพที่มีหลายส่วนต้องแยก **หลายเอกสารอิสระ** ออกจาก **หลายส่วนของใบเดียว** (coupon, หน้าหลัง, meter rows, usage history). ปัญหา Production ของ กปน. อยู่ตรงนี้: OCR เห็นยอด แต่ `MULTI_DOCUMENT` แบบ single-expense ตัด fields ทั้งหมด
4. การอ่านใบแจ้งให้ `DUE`/unknown payment ได้ตามหลักฐานที่พิมพ์ แต่การเปลี่ยนเป็น `PAID`, บันทึก payment, ใช้ VAT หรือยืนยันความแท้ต้องผ่านหลักฐานและ permission ของ workflow เดิม; ชื่อผู้รับบิลกับผู้มีสิทธิลงบัญชีอาจต่างกัน
5. `docs/specs/business-document-image-intake-spec.md` §5.7 คง guard ภาพหลายเอกสาร; §5.8 เพิ่มผลอ่านแบบ read-only สำหรับใบแจ้ง/ใบเสร็จค่าสาธารณูปโภคในภาพเดียว. ยังไม่สร้างหลาย expense อัตโนมัติ และ **เอกสารสำรวจนี้ไม่ได้ประกาศว่า Production รองรับแล้ว**

## ช่องว่างหลักฐานและลำดับตรวจรับ

- มีตัวอย่าง กปภ. ที่เป็น specimen ชัด, ตัวอย่าง MEA/PEA ที่ index พบ, และ incident กปน. ที่ตรวจไฟล์ตามสิทธิ. ยังไม่มี corpus ที่ได้รับอนุญาตของปี 2569 ครบ **4 หน่วยงาน × ใบแจ้ง/ใบเสร็จ/เตือน × paper/electronic × บ้าน/ธุรกิจ**; ห้ามอ้าง “อ่านได้ทุกบิล” จากรายการ use case นี้
- ตรวจรับก่อน: S01 ภาพ incident เดิม, S18 coupon ซ้ำ, S24 usage history, S10–S12 หนี้หลายงวด, S30–S32 ส่วนลด/เครดิต, S35 QR ปลอม, D08–D10 ภาพยาก/ยอดขัดกัน. ต้องวัด document-role, period, amount provenance และ false expense/paid ไม่ใช่เพียง OCR character accuracy
- ใช้ไฟล์ที่ได้รับอนุญาตและ redacted สำหรับ fixture; เก็บ source URL/วันตรวจ/ชนิด specimen/ปีเอกสาร/ผลการอ่านจริง. ไม่คัดลอกบิลบุคคลที่ index พบหรือ customer Production ลง repo
