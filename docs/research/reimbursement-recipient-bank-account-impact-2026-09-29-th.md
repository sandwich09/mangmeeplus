# ผลกระทบ: เพิ่มบัญชีรับเงินคืนในใบเบิก

วันที่: 2026-09-29
สถานะ: วิเคราะห์จาก docs และ source code ใน workspace; ผู้ใช้ยืนยันให้ตรวจบัญชีด้วยคนแล้ว ส่วนรายละเอียด implementation ยังเป็นข้อเสนอและยังไม่ได้ implement

## เป้าหมายและข้อเสนอ

พนักงานระบุบัญชีรับเงินคืน ผู้ตรวจเทียบชื่อผู้เบิกกับชื่อเจ้าของบัญชี และผู้จ่ายใช้บัญชีชุดเดียวกับที่ผ่านการตรวจ โดยย้อนหลังได้ว่าใครตรวจบัญชีใด เมื่อไร

ควรเพิ่มเป็นส่วน **“การรับเงินคืน” ของใบเบิก** ประกอบด้วยวิธีรับเงิน ธนาคาร ชื่อบัญชี และเลขบัญชี พร้อมการรับรองโดยผู้ตรวจและการแสดงผลก่อนจ่าย การเพิ่ม textbox เลขบัญชีอย่างเดียวไม่ครอบคลุมเป้าหมายนี้

ขอบเขตเล็กสุดที่ครบงานคือเก็บบัญชีต่อใบเบิกก่อน ส่วน “บัญชีรับเงินประจำของพนักงาน” เป็นงานถัดไปที่ช่วยเติมข้อมูลอัตโนมัติ ไม่ควรบังคับให้สร้างระบบ HR/payroll ก่อนใช้งานใบเบิก

คำตัดสินผู้ใช้ 2026-09-29: “ไม่เป็นไร ใช้การตรวจสอบด้วยคน” — ให้ผู้ตรวจพิจารณาชื่อบัญชี เลขบัญชี และข้อมูลประกอบใน flow เดิม ระบบตรวจความครบถ้วน/รูปแบบและบันทึกผู้ตรวจ เวลา และบัญชีฉบับที่ตรวจ ไม่เพิ่มการจับคู่ชื่อเจ้าของบัญชีหรือยืนยันบัญชีผ่านธนาคารอัตโนมัติ

คำว่า “ตรวจแล้ว” หมายถึงมนุษย์ตรวจข้อมูล/หลักฐาน ไม่ใช่ธนาคารยืนยันว่าบัญชีมีอยู่หรือเป็นของบุคคลนั้น และไม่ใช่หลักฐานว่าโอนเงินสำเร็จ

## Flow ที่เสนอหลังยืนยันให้ตรวจด้วยคน

ใช้ขั้นตอนใบเบิกเดิม: **สร้างใบเบิก → ส่งตรวจ/อนุมัติ → ตรวจการเงิน (ถ้าเปิดใช้) → จ่ายเงินคืน → เอกสาร/ประวัติ** การตรวจบัญชีเป็นส่วนหนึ่งของงานตรวจเดิม ไม่เพิ่มขั้นอนุมัติแยกอีกสาย

| ลำดับ | ผู้ทำ | การทำงาน |
|---|---|---|
| 1. สร้างใบเบิก | พนักงาน หรือผู้มีสิทธิ์จัดทำแทน | ใส่รายการค่าใช้จ่ายและหลักฐาน เลือกวิธีรับเงิน ถ้าโอน ให้กรอกธนาคาร ชื่อบัญชี เลขบัญชีของผู้รับเงินที่ระบุในใบ ตรวจความครบถ้วนก่อนกดส่ง |
| 2. ตรวจและอนุมัติ | ผู้อนุมัติที่รับผิดชอบ | เห็นค่าใช้จ่าย หลักฐาน ชื่อผู้เบิก และบัญชีรับเงิน ตรวจด้วยคนแล้วรับรอง “ตรวจสอบบัญชีรับเงินแล้ว” ประกอบการอนุมัติ ระบบบันทึกผู้ตรวจ เวลา และบัญชีฉบับที่ตรวจ; ถ้าพบข้อมูลผิด ให้ปฏิเสธพร้อมเหตุผลเพื่อแก้ร่างและส่งใหม่ |
| 3. ตรวจการเงิน (ถ้าเปิดใช้) | ผู้มีสิทธิ์ตรวจการเงิน | ตรวจตามนโยบายเดิมโดยเห็นบัญชีและผลตรวจประกอบ หากบัญชียังไม่ถูกตรวจ ให้ตรวจและรับรองในขั้นนี้; NEEDS_INFO ใช้ส่งกลับได้ตาม guard เดิม |
| 4. โอนและบันทึกจ่าย | ผู้มีสิทธิ์จ่าย | เปิดบัญชีชุดที่ผ่านการตรวจและคัดลอกเลขไปโอนผ่านธนาคาร ตรวจข้อมูลผู้รับที่ธนาคารแสดงกับใบเบิกก่อนยืนยันโอน ถ้านโยบายข้ามขั้นตรวจทั้งหมด ผู้จ่ายต้องตรวจและรับรองบัญชีก่อนโอน เมื่อยืนยันได้ว่าโอนสำเร็จแล้วจึงบันทึกยอด วันที่ เลขอ้างอิง และยืนยันบัญชีที่ใช้จ่าย ระบบเก็บปลายทางที่ใช้จริงกับ payment |
| 5. เอกสารและประวัติ | ผู้เกี่ยวข้องตามสิทธิ์ | ใบเป็น PAID หลังบันทึกจ่าย ดูบัญชีที่ใช้จริง ผู้ตรวจ และผู้จ่ายย้อนหลังได้ ใบพิมพ์ใช้บัญชีจากใบฉบับที่ตรวจ; การลงนาม/แนบสำเนาใช้กฎเอกสารเดิม |

การพิมพ์/ลงนามยังทำได้ตั้งแต่หลังส่งใบตามสิทธิ์และกฎเดิม ไม่ต้องรอ PAID และไม่เพิ่มให้เป็นเงื่อนไขก่อนจ่ายจากงานนี้

ทางแก้ไข: ข้อมูลผิดก่อนอนุมัติ → ปฏิเสธพร้อมเหตุผล → แก้ร่าง → ส่งตรวจใหม่ การแก้บัญชียกเลิกผลตรวจเดิม ส่วนใบอนุมัติแล้วที่มี projection ให้กำหนด cancel/reissue หรือ controlled return ใน spec ก่อน implement ไม่อ้างว่า endpoint ส่งกลับเดิมรองรับทุกสถานะ หลังจ่ายแล้วห้ามแก้บัญชีทับประวัติ

## ตรวจความครบถ้วนของ flow

ผลทบทวนตามคำถามผู้ใช้: ทางปกติครบ แต่ยังไม่ใช่ spec พร้อม implement จนกว่าจะกำหนดทางแยกและ recovery ต่อไปนี้ โดยคง 5 ขั้นหลักเดิม ไม่เพิ่มขั้นอนุมัติทั่วไป

| กรณี | พฤติกรรมที่ต้องกำหนด |
|---|---|
| ข้อมูลไม่ครบ/ผู้ตรวจพบบัญชีผิด | ร่างยังบันทึกได้ แต่ใบขอโอนที่ข้อมูลไม่ครบส่งไม่ได้; ก่อนอนุมัติ ปฏิเสธพร้อมเหตุผลแล้วแก้และส่งใหม่ตาม flow เดิม |
| พบบัญชีผิดหลังอนุมัติหรือขณะรอจ่าย | หยุดการจ่าย ห้ามผู้จ่ายแก้เลขทับข้อมูลที่ตรวจแล้ว; ต้องเลือกเส้นทาง cancel/reissue ตาม guard เดิม หรือเพิ่ม controlled return/reapproval ให้รองรับ projection ก่อนเรียก flow นี้ว่าครบ |
| ธนาคารแสดงผู้รับไม่สอดคล้องกับบัญชีในใบ | ผู้จ่ายหยุดก่อนยืนยันโอน และให้ผู้ตรวจทบทวน ไม่ปล่อยให้ช่องชื่อบัญชีที่กรอกเองเป็นหลักฐานยืนยันตัวตนเพียงอย่างเดียว |
| โอนไม่สำเร็จ หรือยังไม่แน่ใจผล | ยังไม่บันทึก PAID; ตรวจผลกับธนาคารก่อนโอนซ้ำ ระบบบันทึกใบเบิกไม่ได้ทราบผลการโอนภายนอกอัตโนมัติ |
| โอนสำเร็จแล้ว แต่บันทึกจ่ายล้มเหลว/หน้าเว็บหมดเวลา | อ่านสถานะ payment กลับ แล้ว retry การบันทึกรายการเดิมด้วยข้อมูล/ตัวระบุเดิม ถ้ายังไม่บันทึก ห้ามแนะนำให้โอนเงินจริงใหม่; คงข้อมูลที่ผู้ใช้กรอกและแสดงข้อความแยก “โอนแล้ว” จาก “บันทึกสำเร็จ” ให้ชัด |
| ผู้จ่ายหลายคนเปิดใบเดียวกัน | กำหนดผู้รับผิดชอบการโอนและการตรวจประวัติก่อนโอนให้ชัด ระบบกันบันทึก payment ซ้ำไม่ได้กันคนสองคนโอนผ่านธนาคารคนละเครื่อง; ต้องเลือกการประสานงาน/การรับงานจ่ายที่เหมาะสมใน spec ไม่กล่าวอ้างว่ามีอยู่แล้ว |
| ใบเก่าค้างจ่ายไม่มีบัญชี หรือมีการเปลี่ยนบัญชีหลังตรวจ | ห้ามเดาหรือเติมข้อมูลย้อนหลังเข้าเอกสารที่ลงนามแล้ว; ต้องมีทางตรวจ/อนุมัติฉบับใหม่ตาม rollout และ correction policy |
| โอนไปบัญชีผิดแล้ว หรือธนาคารคืนเงินภายหลัง | เก็บข้อเท็จจริงของการโอนเดิมและส่งให้การเงินจัดการแก้ไข/คืนเงินตามกระบวนการ; การ void ในระบบไม่ใช่การดึงเงินจริงกลับ ห้ามแก้เลขบัญชีเก่าให้ดูเหมือนโอนถูกตั้งแต่แรก |

ความพร้อมที่ยืนยันได้ตอนนี้คือ flow หลักและแนวทางตรวจด้วยคน ส่วน correction หลังอนุมัติ, การจัดการใบเก่าค้างจ่าย และการประสานงานผู้จ่ายต้องลงรายละเอียดใน spec/plan ก่อน implementation หลักฐานบัญชีหรือสลิปแนบยังเป็นข้อเสนอแยก ไม่เพิ่มเป็นข้อบังคับจากการทบทวนนี้

## สิ่งที่พบในระบบปัจจุบัน

| ส่วน | สิ่งที่พบ | ผลต่อการเพิ่มฟีเจอร์ |
|---|---|---|
| ข้อมูลพนักงาน | `EmployeeAccessProfile` และ employee contracts ไม่มีบัญชีรับเงิน; contract ระบุด้วยว่า owner บางรายไม่มี employee profile | ถ้าจะมีบัญชีประจำ ต้องรองรับ company member ที่เบิกได้ทุกบทบาท ไม่ผูกความสามารถนี้กับ employee profile อย่างเดียว |
| ผู้รับเงินคืน | `requesterUserId` คือผู้รับเงินคืน; finance ทำใบแทน active scoped member ได้; เปลี่ยน requester หลังสร้างร่างไม่ได้ | ต้องใช้บัญชีของผู้เบิกที่เลือก ไม่ดึงบัญชีของคนล็อกอิน/ผู้จัดทำแทนโดยอัตโนมัติ |
| ใบเบิก | ไม่มีวิธีรับเงิน/ธนาคาร/ชื่อบัญชี/เลขบัญชีใน request schema, create/update input หรือ detail | ต้องเพิ่มทั้งฐานข้อมูล API validation mapping และหน้าเว็บ |
| การจ่าย | Payment มี `paymentMethod`, `paymentReference`, optional `bankAccountId`; หน้าเว็บรับยอด วิธี วันที่ และเลขอ้างอิง โดยเริ่มที่ CASH | ยังไม่มีบัญชีปลายทางให้ตรวจหรือคัดลอก และไม่ควรใช้ค่าเริ่ม CASH กลบวิธีรับเงินที่ระบุในใบ |
| บัญชีธนาคาร | `BankAccount` ผูก company/branch, ledger, statement และ reconciliation; optional `bankAccountId` บน payment ไม่ได้เก็บชื่อ/เลขบัญชีผู้รับ | บัญชีเงินของบริษัทกับบัญชีรับเงินของพนักงานต้องแยกความหมาย ห้ามนำเลขบัญชีพนักงานไปใส่ `bankAccountId` |
| ขั้นตรวจ | ขั้น finance review เปิด/ปิดได้ตาม policy snapshot; บางใบไม่ต้องผ่าน approval ตาม threshold; มีกฎ self-approval ที่อนุญาตบางกรณี | ห้ามฝากการตรวจบัญชีไว้เฉพาะ finance review หรือบังคับผู้ตรวจคนที่สองโดยไม่ตกลงกฎใหม่ |
| อนุมัติ/ลายเซ็น | มี approval hash และ signature acknowledgement hash แยกกัน; ทั้งสองยังไม่มีบัญชีรับเงิน | ต้องผูกบัญชีฉบับเดียวกับที่ตรวจ/ลงนาม และรักษาความเข้ากันได้ของใบเก่า |
| ใบพิมพ์ | สร้าง SVG preview ตามสถานะปัจจุบัน มีรายละเอียดการจ่าย แต่ไม่มีบัญชีรับเงิน | หน้าพิมพ์ต้องใช้ข้อมูลจากใบ ไม่อ่านบัญชีปัจจุบันของพนักงานทุกครั้ง |
| การแก้ไข | เปิดกลับจาก REJECTED/PENDING_APPROVAL และ finance NEEDS_INFO ได้ตามเงื่อนไข; NEEDS_INFO ปฏิเสธกรณีมี payment/live projection | ไม่สามารถสมมติว่าใบ READY_FOR_PAYMENT ทุกใบเปิดกลับแก้บัญชีได้ด้วย endpoint เดิม |
| สิทธิ์ | การอ่านใบมี own/related/broad read และ branch scope; related read กว้างกว่าผู้ต้องใช้เลขบัญชีเต็ม | ต้องกำหนดสิทธิ์ข้อมูลบัญชีแยกจากการเห็นใบเบิกทั่วไป รวมไฟล์แนบ/พิมพ์/export |
| LINE/AI | Spec กำหนดเป็นแจ้งเตือน/อ่านสรุป/ลิงก์เข้าเว็บ; การอนุมัติและบันทึกจ่ายอยู่บนเว็บ/API | ข้อความแจ้งเตือนไม่ควรมีเลขบัญชีเต็ม และไม่เพิ่มการเปลี่ยนบัญชีผ่าน AI ในงานนี้ |

## ฟีเจอร์ที่ควรทำรอบแรก

1. **ช่องรับเงินคืนในหน้าสร้างและแก้ร่าง**: เลือกวิธีรับเงิน โดยใช้ประเภทการจ่ายเดิม เมื่อเลือกโอนต้องมีธนาคาร ชื่อบัญชี เลขบัญชี; ร่างบันทึกข้อมูลที่ยังไม่ครบได้ แต่ก่อนส่งใบที่ขอโอนต้องครบ แสดงข้างชื่อผู้เบิกและรองรับ finance ทำแทน
2. **ตรวจรูปแบบโดยไม่อ้างว่าเป็นการยืนยันบัญชี**: เก็บเลขเป็น string รักษาเลขศูนย์นำหน้า แยกตัวคั่นที่อนุญาตออกตามกฎเดียวกันฝั่ง API/เว็บ ห้าม fix ทุกธนาคารเป็น 10 หลักโดยไม่มีข้อมูลรองรับ ชื่อบัญชีเป็นชื่อเต็มตามบัญชี แสดงคู่ชื่อผู้เบิก; การสะกดไม่ตรงต้องให้มนุษย์ตรวจ ไม่ตัดสินตัวบุคคลจาก nickname หรือ fuzzy match
3. **ส่วนตรวจบัญชีใน flow เดิม**: แสดงชื่อผู้เบิก ธนาคาร ชื่อบัญชี และเลขบัญชีให้ผู้มีสิทธิ์ตรวจ; บันทึกผู้ตรวจ เวลา และ version ของบัญชีที่รับรอง ใช้ label “ผู้ตรวจยืนยันข้อมูลบัญชีแล้ว” แยกจากสถานะอนุมัติค่าใช้จ่าย ผู้ไม่มีข้อมูลพอต้องส่งกลับพร้อมเหตุผลได้
4. **ครอบคลุมกรณีข้ามขั้น**: การรับรองทำร่วมกับขั้นอนุมัติ/ตรวจการเงินที่มีอยู่ได้ ถ้าไม่มีขั้นดังกล่าว ต้องตรวจในขั้นจ่ายก่อนบันทึก BANK_TRANSFER; ห้ามใช้ปุ่มตรวจบัญชีเป็นการข้าม approval หรือ payment permission และรักษากฎ self-approval เดิมจนกว่าจะมีคำตัดสินใหม่
5. **แสดงบัญชีที่ผ่านการตรวจในหน้าจ่าย**: คัดลอกเลขบัญชีได้ ไม่ต้องกรอกซ้ำ; ผู้จ่ายรับรองว่าโอนไปยังบัญชีชุดนี้ก่อนบันทึก พร้อมเลขอ้างอิงเดิม บันทึกบัญชี/เวอร์ชันที่ใช้จริงกับ payment; API และ transaction ต้องปฏิเสธบัญชีที่ถูกแก้หรือไม่ผ่านเกณฑ์ แม้ client ส่งคำขอโดยตรง
6. **ใบพิมพ์และประวัติ**: เพิ่มส่วนรับเงินคืนที่อ่านได้ชัด และประวัติเปลี่ยน/ตรวจบัญชี เลือกการแสดงเลขเต็มตามสิทธิ์; ตัวเลขบนกระดาษ หน้าอนุมัติ และหน้าจ่ายต้องมาจาก snapshot เดียวกัน

หลักฐานชื่อบัญชี เช่น หน้าบัญชีหรือภาพจากแอปธนาคาร เป็นตัวช่วยที่มีประโยชน์ ควรรองรับเมื่อผู้ตรวจต้องใช้ โดย reuse attachment storage เดิม แต่ต้องแยก purpose และสิทธิ์จากใบเสร็จค่าใช้จ่าย การแนบหลักฐานบัญชีห้ามทำให้สถานะ receipt ของค่าใช้จ่ายกลายเป็น “มีหลักฐานครบ” โดยอัตโนมัติ นโยบายบังคับแนบทุกครั้งยังต้องตกลง ไม่ควรเพิ่มเป็นข้อบังคับโดยเงียบ ๆ

## ข้อมูลและกฎที่ต้องออกแบบให้ครบ

- **บัญชีต่อใบ**: proposed request fields คือวิธีรับเงินและ destination ที่มีธนาคาร/ชื่อบัญชี/เลขบัญชีเข้ารหัส/เลขท้ายสำหรับแสดงผล/เวอร์ชัน ข้อมูลนี้เป็น header ของทั้งใบ หนึ่งใบโอนไปหนึ่งบัญชีตาม full-payment model เดิม ไม่เพิ่มการแบ่งจ่ายหลายบัญชี
- **บัญชีประจำในอนาคต**: เป็นแหล่งเติมร่าง ไม่ใช่ source ที่ใบอนุมัติแล้วอ่านสด; scope ตามบริษัทและผู้รับเงิน ไม่ใช้บัญชีระดับ global user ร่วมข้ามบริษัทโดยอัตโนมัติ ต้องมีทางใช้สำหรับสมาชิกที่ไม่มี EmployeeAccessProfile
- **การตรวจ**: สถานะยังไม่ตรวจ/ตรวจแล้ว/ต้องแก้ไข เก็บ actor/time/reason และ destination version ที่ตรวจ ใช้ transaction ของ decision เดิมเมื่อเป็นไปได้ ไม่ต้องสร้าง workflow engine ใหม่
- **การตรึงข้อมูล**: การเปลี่ยนธนาคาร ชื่อบัญชี เลขบัญชี หรือวิธีรับเงินถือเป็นการเปลี่ยนข้อเท็จจริงที่ผู้ตรวจรับรอง ต้องยกเลิกผลตรวจเดิม และเข้า approval/signature binding ด้วยค่าที่คงที่ฝั่ง server ไม่ใช้ randomized ciphertext เป็น hash โดยตรง และไม่ให้การกดตรวจเปลี่ยนตัวเนื้อหาที่ลงนามวนไปมา
- **แก้หลังส่ง**: ห้ามแก้ปลายทางเงียบ ๆ ในหน้าจ่าย เมื่อสถานะเดิมรองรับส่งกลับ/ถอนใบ ให้แก้และส่งตรวจใหม่; เมื่ออนุมัติแล้วมี projection ต้องกำหนด recovery ให้ชัด ทางเล็กสุดคือใช้ cancel/reissue ตาม guard เดิม ถ้าต้องการแก้เลขในใบเดิมขณะ READY_FOR_PAYMENT ต้องออกแบบ controlled return/reapproval เพิ่มโดยรักษา projection/signature consistency
- **หลังจ่าย**: เก็บข้อมูลที่จ่ายจริงอย่างถาวร การเปลี่ยนบัญชีประจำไม่แก้ประวัติ ใบ PAID ห้ามแก้ย้อนหลัง; payment void/reversal และ reconciliation lock ใช้กฎเดิม
- **วิธีจ่ายไม่ตรงใบ**: ต้องตกลงว่าจะให้กลับแก้/ตรวจใหม่อย่างไร ห้ามเปลี่ยนจากโอนเป็นเงินสดเพื่อหลบ account validation ที่ payment endpoint
- **การส่งซ้ำ/แข่งกัน**: payment idempotency comparison ต้องรวม destination version/snapshot; การบันทึกจ่ายแข่งกับการแก้/ส่งกลับต้องตรวจภายใต้ request lock เดิม รวมทั้งเส้นทาง replay ห้ามคืน payment คนละบัญชีเป็น success
- **ความเป็นส่วนตัว**: reuse encryption helper ที่ employee identity / sales profile ใช้อยู่หลังตรวจ config; mask รายการรวมและข้อมูลที่ไม่จำเป็น เลขเต็มให้เฉพาะผู้เบิก/ผู้จัดทำแทนที่ได้รับสิทธิ์/ผู้ตรวจที่รับผิดชอบ/ผู้จ่ายตาม scope ไม่ปล่อยเลขเต็มเพียงเพราะมี `read_related`; API projection, print, attachment download และ export ต้องใช้กฎเดียวกัน
- **Audit/LINE/AI**: audit เก็บ actor/time/เหตุผล/เวอร์ชัน/เลขท้าย ไม่เก็บเลขเต็มใน metadata หรือ notification; AI Gateway ใช้ API ที่ตรวจสิทธิ์ต่อไป และไม่มี plaintext ใน tool summaries โดยอัตโนมัติ

## ขอบเขตผลกระทบด้านระบบ

| พื้นที่ | งานจำเป็น | ขนาดสัมพัทธ์ |
|---|---|---|
| Prisma / migration | เพิ่มข้อมูล destination และผลตรวจแบบ nullable พร้อม version; payment snapshot/reference | กลาง |
| Contracts / DTO / mapper | create/edit/read, validation, masking, decision/payment binding และ error codes | กลาง |
| Request / approval / finance / payment | submit gate, verification, stale checks, correction, atomic payment/replay | สูงที่สุด |
| Web | create/edit, review, journey/queue, payment, readonly และ loading/error/permission states | กลาง |
| เอกสาร | claim renderer, acknowledgement hash, signed copy binding, masked export | กลาง |
| Employee settings | บัญชีประจำ + self service / ผู้จัดทำแทน / company scope | แยกเป็นรอบถัดไปได้ |
| Banking / ledger / tax | รักษา source-payment identity, ยอดเงิน, posting/reversal และ reconciliation เดิม; ตรวจ regression | ไม่ต้องเพิ่มกฎบัญชีหรือภาษีจากการมีเลขบัญชีอย่างเดียว |

ระบบมี encrypted bank field ใน SalesAgentProfile แต่เป็นคนละโดเมนกับพนักงานของบริษัทลูกค้า และ SupplierBankAccount เก็บเพียงเลขท้าย จึง reuse ได้ในระดับ pattern/helper ไม่ควรผูกใบเบิกเข้ากับข้อมูลสองชุดนั้น

## ใบเก่าและการทยอยเปิดใช้

เพิ่มคอลัมน์แบบ nullable ก่อน โดยไม่เดาบัญชีหรือ mark verified จาก profile ปัจจุบันย้อนหลัง ใบ PAID เดิมแสดงว่าไม่มีข้อมูลบัญชีที่บันทึกในระบบ และต้องพิมพ์/เปิดประวัติได้เหมือนเดิม

ก่อน implementation ต้องตกลงจุดเริ่มบังคับสำหรับใบค้าง: ข้อเสนอคือบังคับเมื่อส่งใบโอนใหม่/ส่งใหม่ ส่วนใบที่อนุมัติก่อนเปิดฟีเจอร์แต่ยังไม่จ่าย ให้แสดงสถานะ legacy ชัดเจนและกำหนดการทบทวนบัญชีผ่านเส้นทางที่อนุมัติไว้ ไม่ backfill เข้า signed snapshot เงียบ ๆ ไม่ทำให้เอกสารเก่าทั้งหมด stale เพราะเปลี่ยน hash algorithm

ถ้าจะบังคับข้อมูลบัญชีก่อนโอนสำหรับใบค้างทุกใบ ต้องส่งมอบเส้นทาง correction/reapproval ที่ครอบคลุม READY_FOR_PAYMENT ด้วย ไม่ใช่แค่เพิ่ม NOT NULL หรือ payment guard แล้วปล่อยให้ผู้ใช้ติดทางตัน

## ลำดับงานที่เสนอ

1. เขียน spec + plan ตามคำตัดสินตรวจด้วยคน พร้อมระบุสิทธิ์ผู้ตรวจและขอบเขต legacy/correction
2. ทำบัญชีต่อใบให้ครบ create → submit → review → pay → print/audit พร้อม validation/security/concurrency และ compatibility
3. เพิ่มบัญชีประจำของสมาชิกเพื่อเติมข้อมูลครั้งต่อไป เมื่อจะลดการกรอกซ้ำ; การเปลี่ยนบัญชีต้องใช้ใหม่เฉพาะร่างที่ผู้ใช้ยืนยัน
4. พิจารณาหลักฐานการโอน, หลายบัญชี/บัญชีหลัก, OCR เอกสารบัญชี, ตรวจสลิปอัตโนมัติ หรือ bank verification integration ภายหลังตามความจำเป็น ระบบโอนเงินจริง/bulk payment/PromptPay ไม่อยู่ในขอบเขตเพิ่มช่องครั้งนี้

## เกณฑ์ตรวจรับสำหรับ implementation

- เลขนำหน้า 0 ไม่หาย ข้อมูลโอนไม่ครบส่งไม่ได้ เงินสดไม่ถูกบังคับบัญชี และเปลี่ยนวิธีจ่ายข้ามกฎไม่ได้
- Finance ทำใบให้ B ต้องได้ข้อมูลบัญชีของ B; A อ่าน/แก้เลขเต็มของ B โดยไม่มีสิทธิ์ไม่ได้ รวม cross-company/branch และผู้อนุมัติตาม assignment
- เปิดและปิด finance review, ไม่ต้องอนุมัติตาม threshold, และ self-approval ที่อนุญาตเดิม ล้วนมีทางตรวจบัญชีก่อนจ่ายโดยไม่เพิ่มสิทธิ์อนุมัติเอง
- เปลี่ยนบัญชีหลังตรวจทำให้ผลตรวจเก่าใช้ไม่ได้; stale browser/API approve/pay/sign ถูกปฏิเสธ และมีทางแก้ตามแต่ละสถานะ
- เปลี่ยนบัญชีประจำแล้วใบอนุมัติ/ใบจ่าย/ใบพิมพ์เดิมไม่เปลี่ยน
- การ retry payment และ concurrent edit/pay ไม่สร้าง payment record ซ้ำหรือบันทึกคนละบัญชี; void/reversal/reconciliation เดิมยังถูกต้อง การกันโอนเงินจริงซ้ำผ่านธนาคารภายนอกต้องมีการประสานงานผู้จ่ายแยกจาก idempotency ของการบันทึก
- เลขเต็มไม่หลุด list/export/audit/notification/AI หรือ URL ไฟล์แนบที่ผู้ใช้ไม่มีสิทธิ์
- หลักฐานบัญชีไม่นับแทนใบเสร็จ; signed scan ของ version ก่อนเปลี่ยนบัญชีไม่รับรอง version ใหม่
- ใบเก่าไม่มีข้อมูลยังอ่าน/พิมพ์ได้; ใบเก่าค้างจ่ายมีทางดำเนินการตาม rollout policy; ไม่มี synthetic verification ย้อนหลัง
- Browser journey ทั้ง desktop/mobile รวม loading, missing account, invalid input, access denied, stale version และ read-only paid; ใช้ `e2e/reimbursements.spec.ts` และ `e2e/reimbursement-receipt.spec.ts` เป็นจุดต่อ regression

## คำตัดสินและรายละเอียดสำหรับ spec

ผู้ใช้ให้ใช้การตรวจสอบด้วยคน จึงไม่เพิ่มเงื่อนไขระบบว่าชื่อบัญชีต้องตรงกับชื่อพนักงานอัตโนมัติ ให้แสดงทั้งสองชื่อเพื่อให้ผู้ตรวจตัดสินตามนโยบายบริษัท ไม่ตีความคำตอบนี้เป็นการอนุญาตบัญชีบุคคลอื่นทุกกรณี

ก่อน implement ให้ระบุเพิ่มใน spec: ใครตรวจ/เห็นเลขเต็ม, ใช้หลักฐานบัญชีแบบบังคับหรือเลือกแนบ, วิธีแก้บัญชีเมื่ออนุมัติแล้ว, วิธีจัดการใบค้างก่อนเปิดฟีเจอร์ และต้องมีบัญชีประจำในรอบแรกหรือไม่ ประเด็นเหล่านี้ไม่ขวางการสรุป impact แต่ห้ามเดากฎไป implement
