## Incident (UAT, 2026-08-03, uat-mangmeeplus OA)

1. User sent handwritten cash bill photo → draft expense created correctly (59.00, doc date 17 มิ.ย. 2569).
2. User: "วันที่ออกสารผิดนะ ต้องเป็นวันที่20" → bot asked CLARIFY (which month/year).
3. User: "20 กรกฎาคม 2569" → bot **created a second, mostly-empty EXPENSE_NOTE_TEXT draft** instead of updating the first record. Original record keeps the wrong date.

## Root cause (layered)

1. **No "correct existing record" capability anywhere in the chain.**
   - `LineIntakeRouteIntent` (packages/contracts/src/line-ai.ts:295) has 7 intents, no EDIT/CORRECTION.
   - `LINE_ALLOWED_TOOL_CATEGORIES` (packages/contracts/src/ai-tools.ts:8) = read/report/suggestion/evidence_capture; **no `draft_update` category exists even in the type union**.
   - Dispatcher branch for `EXPENSE_DOCUMENT_CAPTURE` text (apps/api/src/modules/line-ai/application/use-cases/process-line-webhook.use-case.ts:745) always calls `CaptureLineExpenseNoteUseCase` → `createDraft.execute` (apps/api/src/modules/expenses/application/use-cases/expense-document.use-case.ts:66). Always creates.
2. **Router prompt funnels corrections into capture.** MUTATION_REQUEST_REFUSAL definition lists only final mutations (approve/pay/post/file tax/...), not draft edits; openClarifications rule ("classify for the ORIGINAL request with the answer applied", intent-router.agent.ts:164) pushed the clarified date answer into EXPENSE_DOCUMENT_CAPTURE.
3. **Conversation memory cannot identify the created record.** `replyPreview` truncated to 240 chars (PREVIEW_MAX_CHARS) cuts off the expense URL/id; no structured recent-artifact refs in `LineIntakeRouteRequest`.
4. **Amplifier:** intake branches (capture/signature/clarify) return before step 10.5 and never `ack` consumed `waiting_user` ledger entries — only the business-QA path does (process-line-webhook.use-case.ts:944). Stale clarifications can re-trigger phantom captures within the 15-min window (`LINE_AI_CONTEXT_WINDOW_MINUTES`).
5. Spec permits the missing half: docs/specs/line-ai-read-only-assistant-spec.md:25,135 says capture "may update draft… records"; only the create half was built. No RECEIPT-0x gap item covers post-capture corrections. No router/dispatch spec test exercises a correction message.

## Other AI surfaces (survey verdicts)

- **CRM autonomous booking, post-commit — same bug, worse impact**: reschedule request in chat → second real `CrmBooking`; committed booking is terminal (`ACTIVE_STATUSES` excludes BOOKED for proposal resolution), chat CANCEL only hits pending proposals. Reminder text even invites "เลื่อน/ยกเลิก แจ้งได้ในแชทนี้" (crm-booking.logic.ts:144). Pre-commit is SAFE via `createSuperseding` slot-fingerprint supersede (prisma-crm-booking-proposal.repository.ts:109).
- **LINE receipt image re-send — NOT a gap (corrected 2026-08-03 after owner pushback)**: already handled by the shipped duplicate lifecycle (`5c700860` cross-channel detection, `c028b12f` perceptual-hash for LINE-recompressed images; checksum + field scoring 180d → POSSIBLE_DUPLICATE flag → web confirm/override, confirmed duplicates never post). Create-then-human-resolve is intended design.
- **CRM booking contact fill — inverse gap**: corrections to an already-set phone are silently ignored (fill-only-if-empty, prisma-crm.repository.ts:441).
- Safe/N-A: signature tickets (approval-queue supersede), ai-draft (`editedPayloadJson` — reference pattern, LINE hard-refused), bank statement (preview→commit), CRM profile extract (human form), read-only CRM agents, workers (note: outbox event `expense.line_receipt_uploaded` has no subscriber).
