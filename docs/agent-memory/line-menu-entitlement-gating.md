# Agent Memory: LINE staff menu feature-entitlement gating

Status: Implemented and unit-verified 2026-08-15; not yet exercised on a live LINE OA
Owner: develop
Scope: Make the LINE staff quick-reply menu honor company feature entitlements, the same way the web sidebar and dashboard tiles already do. Sibling of [[agent-memory/feature-entitlement-dashboard-gating|Feature-entitlement dashboard/nav gating]].

Decisions:
- UAT 2026-08-15: owner reported `ยอดขายวันนี้` appearing in the LINE menu on a company that never switched the sales feature on. Rule stated by owner: a feature that is off in the system must not appear in LINE at all.
- `buildStaffCompletionQuickReply` / `buildStaffMainMenu` / `buildStaffQueryMenu` / `buildPendingApprovalCard` filtered on **permissions only**. Permission grants are role-shaped and say nothing about what the company purchased, so any role holding `dashboard.read` saw a sales button whose only possible answer was an empty one.
- `StaffMenuContext` now carries `entitledFeatureKeys: ReadonlySet<string> | null`, loaded through the existing `loadEntitledFeatureKeys`. `null` is that loader's legacy fail-open sentinel (company with no entitlement rows) and preserves today's behavior exactly — no company loses a menu because it was never configured.
- Each menu action names the feature that OWNS the data its answer reads, not the feature its permission happens to live under: `ยอดขายวันนี้`→`sales_documents`, `คิว/นัดวันนี้`→`crm.bookings`, `แชทค้างตอบ`→`crm.inbox`, `ค่าใช้จ่ายเดือนนี้`→`expenses`, `รายงานการเงิน`→`reports`/`double_entry_ledger`, `ใบสั่งซื้อ (PO)`→`procurement.purchase_orders`, `📷 ถ่ายใบเสร็จ`→`expenses.upload`. Submenu keys are checked directly because `evaluateEntitledFeatureKeys` already expands a parent's submenus, so this is the precise gate rather than a stricter one.
- `📊 ถามข้อมูล` and `🏢 บริษัทของฉัน` stay ungated: the first is the generic AI query surface, the second is company switching. Neither reads a gated module.
- `✅ รายการรออนุมัติ` is now derived from `availableApprovalSurfaces`, the same helper `buildPendingApprovalCard` uses, so the button and the card behind it can never disagree about which queues this company runs. Previously the button had its own permission list and could open a card with zero buttons.
- Menu copy changed from "แสดงเฉพาะสิ่งที่ตำแหน่งคุณมีสิทธิ์เข้าถึง" to "...ที่บริษัทเปิดใช้และตำแหน่งคุณมีสิทธิ์เข้าถึง", because the filter is now two-dimensional and the old line would misdescribe a hidden menu as a permission problem.

Resolved owner decisions 2026-08-15:
- `sales.order.read` was listed as a gate permission for `ยอดขายวันนี้` since the menu was written but exists nowhere else in the repo — not in `permission-registry.ts`, not in any role grant, not in `ai-tools.ts` — so it never gated anything and the button ran on `dashboard.read` alone. Owner ruled the sales button waits for the sales feature and its number is read off the dashboard, so the permission stays `dashboard.read` (NOT the `crm.report.read` that `sales.get_sales_summary` checks) and the wait is expressed by the `sales_documents` entitlement. The dead key was removed; no behavior changed, because `hasAny` over a key no role can hold was already a no-op.
- AI tools themselves are not entitlement-gated — `erp-tools.use-case.ts` checks permissions only — so a user who types "ยอดขายวันนี้" as free text still reaches the tool even while the menu hides it. Owner ruled this is its own slice, treated as a feature that is not open yet. Spawned as separate work; deliberately NOT folded into this change.

ERP tool entitlement gate 2026-08-15 (the separate slice, delivered):
- Measured before building, and the measurement changed the plan. With each tool's owning feature switched off (parent off ⇒ submenus off, as `evaluateEntitledFeatureKeys` produces), **47 of 59 tools were already blocked** — `filterPermissionsByEntitlement` strips their permission via `PREFIX_FEATURE_RULES` or capability-pack membership, so the free-text bypass was far narrower than assumed. 5 more are ungated by design (`data-model-core` tenant context, `employee-access`, `hr` — no sellable feature owns them).
- Exactly **one genuine bypass**: `sales.get_sales_summary`. It requires `crm.report.read` (gated by `crm`) but reads customer receipts owned by `sales_documents`, so a company with sales off and CRM on still answered "ยอดขายวันนี้" typed as free text. That is precisely the reported case, and the new tool-level feature key is what closes it.
- Two mappings were corrected BY the measurement rather than shipped wrong. `inventory.search_products` / `inventory.get_product_detail` are `product_catalog`, not `inventory` — `PREFIX_FEATURE_RULES` already states the product/service catalog is sold independently of Inventory + CRM, and mapping them to `inventory` would have contradicted it. And the whole `reimbursements` module is deliberately absent from the map: owner decision 2026-08-10 (launch matrix §6.3 r5) keeps reads/approve/reject/finance-review alive after the feature is disabled so in-flight claims still clear, which is why `RETAINED_REIMBURSEMENT_PERMISSIONS` survives stripping. Gating those three read tools would have silently reversed that decision and stranded an approver.
- Mechanism: `ToolMeta.featureKeys` (optional per-tool override) + `TOOL_MODULE_FEATURE_KEYS` (sourceModule default) + `toolFeatureKeys` / `hasToolFeature` in `packages/contracts/src/ai-tools.ts`. Submenu-precise overrides mirror the menu exactly: `crm.inbox` for the three inbox tools, `crm.bookings` for the two booking tools, `expenses.upload` for receipt capture.
- Enforced in `internal-tools.controller.ts` as a new step 4 of the L-08 deny chain, AFTER permissions and BEFORE wiring. After, deliberately: only a caller who could otherwise read the data learns which features this company runs.
- Second, larger fix found on the way: the 47 already-blocked tools were reporting `ERP_PERMISSION_DENIED` → "🔒 คุณไม่มีสิทธิ์เข้าถึงข้อมูลนี้ค่ะ", which sends the user to an admin for a grant their role already holds. The permission branch now puts `access.entitlementDeniedPermissions` back and re-tests: if the tool would then pass, the feature switch is the cause and it returns `FEATURE_NOT_ENABLED`. This affects far more real traffic than the single bypass did.
- User-facing decision: a blocked tool returns `status: 'unsupported_module'` with `errorCode: 'FEATURE_NOT_ENABLED'`, and the gateway answers `🚧 ฟีเจอร์นี้ยังไม่ได้เปิดใช้งานสำหรับบริษัทของคุณค่ะ / หากต้องการเปิดใช้งาน กรุณาติดต่อผู้ดูแลระบบของบริษัทนะคะ`. Checked BEFORE the all-forbidden branch. Without it the turn fell through to `NO_DATA_REPLY` ("📭 ไม่พบข้อมูลที่ตรงกันค่ะ"), which reads as "your business has no data". The reply names no feature key, no other feature, and no other company; a test asserts no internal key leaks into it.
- `status: 'forbidden'` was rejected for this case: it is a lie about the cause, and the gateway maps it to the permission refusal. `unsupported_module` already means "this module is not available here" and its existing plumbing (`enforceSourceHonesty` preserves `errorCode` across the boundary) needed no contract change.
