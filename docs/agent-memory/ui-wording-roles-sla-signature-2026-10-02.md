## 4. "เกิน 30 นาที" (second round, a finding of the pass above)

The inbox (chip, button) and the CRM report (a card and the pill under the average reply time) named 30 minutes. The time a shop allows is its own setting, "กำหนดเวลาตอบลูกค้า": 1 to 1440 minutes, counted inside business hours when that box is ticked (no saved setting = 30 minutes inside 09:00-18:00). Only `crm.inbox.policy_manage` reads it, so neither page holds the number.

- The figure is right and was not touched. A chat is given its deadline once, when it starts or restarts (`resolveConversation` -> `computeFirstResponseDueAt`, from the setting of that moment), and every count compares that stored time with now (`overdueWhere` in `prisma-crm-inbox.repository.ts`: inbox chip, CRM report card, the scan behind the dashboard card and the notice). Nothing counts with a fixed 30. On a local stack, changing the setting to 1 and to 1440 minutes left the late count as it was: the setting reaches new chats only, as its page says.
- Texts now, with no number: chip "⏱ รอตอบเกินกำหนด", button "ดู N แชทด่วนที่รอตอบเกินกำหนด", report card "ลูกค้ารอตอบเกินกำหนด", pill "ไม่ควรเกินกำหนดเวลาตอบ" (with "ลูกค้า" the pill wrapped at 1280 px, by 2 px). The English side of the same four keys carries no number either. The live inbox words its chip and button itself (`inbox-prototype.model.ts`, `InboxPrototypePage.tsx`); the two `inbox.*` keys serve the unrouted `InboxPage.tsx`, the two `crm_reports.*` keys the live report.
- Also reworded, though no route shows them: two lines of the module mock and one sample summary in `mangmee-crm-data.ts`.
- Left: comments in the API and contracts that still call the chip "เกิน 30 นาที"; the mock's "รออนุมัติ ... เกิน 30 นาที" (approvals, not replies); the unused `CRM_OVERDUE_MIN = 30`.

## 5. Six example roles were never offered (second round, a finding of the pass above)

- Cause: the role builder (`RoleBuilder` in `EmployeeAccessPages.tsx`) offered an example only when every choice it names has a tick box. On 2026-08-27 "ขอเบิกของฉัน" (`pack.reimbursement.self`) became a choice every role holds automatically, which has no tick box, and the six examples that name it went missing: ร้านค้าปลีก พนักงานขาย and พนักงานคลัง, ธุรกิจค้าส่ง ฝ่ายขาย and คลังสินค้า, ธุรกิจบริการ หน้าร้าน/ต้อนรับ and ฝ่ายขาย/ดูแลลูกค้า. 15 of the 21 examples were offered.
- Fix, in the rule: an automatic choice neither rules an example out nor is ticked (`roleTemplateChoices` in `role-picker.logic.ts`). An example is still left out when another of its choices is locked for the company or beyond what the user may give. The registry and the API are unchanged: the API gives the automatic choices to every role whatever is sent.
- On a local stack: 21 of 21 offered at 390 and 1280 px. A role made on the screen from each of the six saved and holds exactly the rights of its example (75, 54, 75, 54, 73 and 71 rights): none missing and none extra against the API's own expansion of the example (`roles/preview` with the example's key) and against the union of the served choices, own-claim rights included.
- Noticed, not changed: the line under the choices says what every employee can do already (use the system, the home page, notices) and does not name own claims, so an example that says "เบิกของตัวเอง" ticks no box for it.

## 6. A company's sixth role with a Thai name was refused (third round, listed under the open questions before)

- Cause: a name with no Latin letter or digit gives the key `ROLE` (or the key of the example sent with it), and `CreateRoleUseCase` tried five keys only: `ROLE`, `ROLE_1` to `ROLE_4`. The sixth role was refused with a 409 that had no code, which the role form reads by its status as "ข้อมูลซ้ำกับที่มีอยู่ในระบบ". Nothing was duplicated, and trying again never helped. The role form fills in an example's Thai name and does not send the example's key, so a shop that keeps the names of the 21 examples (all 21 give `ROLE`) reached the cap at its sixth role. Sent with its key, an example gives its own base (`MANAGER`, `SALES`, `FINANCE`, …), and the same cap applied to several roles of one base.
- Fix, in the API (`create-role.use-case.ts`): the keys the company uses with that base are read once, inside the transaction that creates the role, and the role takes the first free of `KEY`, `KEY_1`, `KEY_2`, … with no cap. The seventh role with a Thai name gets `ROLE_6`, the twentieth `ROLE_19`. Two roles created at the same moment read the same free key; the unique index on (scopeKey, key) refuses one, its transaction is rolled back whole and run again (five rounds at most), and it takes the next number.
- Not changed: which key a name or an example gives (`roleKeyFromName`, `reservedRoleKey`), the key of the first role of a base and of the next four, the refusal of a reserved name, the keys of existing roles. No migration.
- The one refusal left is five rounds lost in a row: six roles of one base saved in one company in the same instant. It answers 409 `role_key_allocation_failed`, nothing is written, and saving again works. The role form and the toast say "ยังไม่ได้สร้างบทบาทนี้ เพราะมีการบันทึกบทบาทอื่นในเวลาเดียวกัน กรุณากดบันทึกอีกครั้ง" (`CODE_LABELS` in `api-error-message.ts`; the form already words a refusal that carries a code through `apiErrorMessage`, and only a refusal with no code by its status).
- Neighbours read for the same five-attempt pattern, none has it, none changed: editing a standard role (`update-role.use-case.ts`) copies it under the standard role's own key, found or created once under the company lock, with no numbering; no route duplicates a role; the loop in `create-employee.use-case.ts` runs once (a user name is typed, never numbered, and its conflict has a code).
- Tests: four in `role-management.use-case.spec.ts` (twenty Thai names in one company; seven roles from the manager example around a key the company already uses; three created at the same moment; every round lost), whose fake now enforces the index with the driver's own error. Two in `create-employee-username.pg.spec.ts`, the module's registered real-PostgreSQL spec (run by `extended-tests.yml`, skipped without `EMPLOYEE_ACCESS_TEST_DATABASE_URL`): four roles created at the same moment, and the numbering past five. It fits by module, harness and subject (a unique index and the driver's error shape), not by its file name. One web test in `api-error-coverage.spec.ts`.
- Noticed, not changed: a Thai name with a digit takes the digit as its key ("พนักงาน 2" gives the key `2`), so two such names share a base and are numbered `2`, `2_1`. The keys taken are read with Prisma's `startsWith`, a LIKE that does not escape `_`: it reads more keys than the base's own (`STOREXMANAGER` with `STORE_MANAGER`), which the exact lookup ignores.

Decisions: recorded above. No role-name unification, no hiding of `SYSTEM_ADMIN` / `COMPANY_VIEW` from a shop's role list (the API lists them; only the sales roles are platform-only).
