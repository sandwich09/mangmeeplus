# Agent Memory: employee-access-role-management-10c

Status: IMPLEMENTED AND VERIFIED. Master checklist item 10C checked.
Owner: Product / Customer Owner/Admin.
Scope: Customer owner/admin creates employee access users, temporary passwords, role assignments, and LINE account-link QR packages from Settings.

Decisions:
- Added as master checklist item 10C, not 23B, because it is foundational access provisioning for web and LINE AI permissions.
- Kept separate from Payroll and HR Compliance item 20; item 10C stores only access/contact identity fields needed for provisioning.
- QR is for short-lived LINE account linking only. It never contains a password or a static permission snapshot.
- Role and permission management is web/API only. LINE and AI refuse user, credential, role, permission, and employee-status mutations (no new LINE/AI tool was added, so the existing item 07 read-only allowlist boundary is untouched).
- Reused `credential-cipher.logic.ts` (AES-256-GCM, `AppConfigService.credentialEncryptionKey`) from `system-partner-management` for Thai ID/passport encryption instead of inventing a second vault primitive.
- New permission keys (`access.employee.*`, `access.role.*`, `access.permission.*`) follow `docs/specs/permission-matrix.md` §5.0 literally, kept distinct from the older, coarser item-02 `admin.user.*`/`admin.role.*` keys (which stay unused/unremoved — low risk, out of scope to clean up).
- `EmployeeAccessProfile.status` reuses the existing `MembershipStatus` enum (ACTIVE/INVITED/SUSPENDED/DISABLED) instead of a new enum; `CompanyMembership.status` remains the actual access-enforcement source of truth, kept in sync in the same transaction.
- OWNER and SYSTEM_ADMIN role keys are blocked from assignment via this flow (`NON_ASSIGNABLE_ROLE_KEYS` in `employee-access.logic.ts`) both in the API (`CreateEmployeeUseCase`/`UpdateEmployeeUseCase`) and in the web role picker. Settings > Employees can therefore never reach the owner's own membership (no `EmployeeAccessProfile` row is ever created for it), which is why there is no separate "last active owner" runtime check in the employee use-cases — protection is structural. The OWNER *role definition* itself is still protected via the generic `isSystem` guard in `UpdateRoleUseCase`/`DisableRoleUseCase`.
- Feature-entitlement filtering for role permission grants (plan Phase 3) is deferred: no other module in the repo enforces `CompanyFeatureEntitlement` on permission mutation yet, so building it only here would be a speculative, unproven abstraction. `CreateRoleUseCase`/`UpdateRoleUseCase` validate against `COMPANY_PERMISSION_KEYS` only.
- LINE account-link token is a new `EmployeeLineLinkToken` model (short-lived, single-use, hashed with SHA-256 — raw token never persisted), consumed by a new `CompleteEmployeeLineLinkUseCase` inside the **auth** module (not employee-access) so it can directly reuse `LinkLineIdentityUseCase`/`LineLoginVerifierAdapter` without a cross-module export change beyond what already existed.

Bugs found and fixed while testing (pre-existing, not introduced by 10C, but surfaced by exercising its audit/DI paths):
1. **Auth audit silently broken**: `@Optional() private readonly audit: AuditService | null = null` (and the equivalent for `PermissionResolverService`) across 7 files in `apps/api/src/modules/auth/application/use-cases/` (`logout`, `issue-token`, `unlink-line-identity`, `link-line-identity`, `exchange-line-token`, `refresh-session`, plus the new `complete-employee-line-link`) loses TypeScript's `design:paramtypes` reflection because the parameter type is a union (`X | null`). Nest's DI resolved this to `undefined`/`null` every time, silently, with no error. Fixed by adding an explicit `@Inject(AuditService)` / `@Inject(PermissionResolverService)` next to `@Optional()` in all 7 files. Verified live: `access.employee.line_link.failure` and `auth.login.exchange` audit rows now actually appear in `AuditLog` where they did not before the fix.
2. **`pnpm dev` (tsx watch) cannot run this API at all**: esbuild (which powers `tsx`) does not emit `design:paramtypes` decorator metadata, so *every* Nest constructor-injected class — not just union-typed ones — is instantiated with zero arguments. `AuthGuard.canActivate` crashes on `this.reflector.getAllAndOverride(...)` (`reflector` is `undefined`) on literally every request, including `@Public()` ones, so `pnpm --filter api dev` 500s on everything. Confirmed by running the identical code as a `tsc` build (`node dist/apps/api/src/main.js`), which works correctly. This is a repo-wide, pre-existing local-dev blocker, unrelated to 10C's own code, and out of scope to fix here (needs a decision on replacing the dev runner, e.g. `ts-node`, or a `tsc --watch` + `node --watch` pipeline). **Anyone doing local API dev right now must build (`pnpm --filter api build`) and run the compiled `dist/apps/api/src/main.js` instead of `pnpm --filter api dev` until this is fixed.**
3. **Role edit/disable 404'd instead of 403'ing on system roles**: `UpdateRoleUseCase`/`DisableRoleUseCase` originally scoped their `role.findFirst` lookup to `scopeKey: companyId` only, so system-scoped roles (OWNER, ADMIN, ...) were never found and returned `404 Role not found` instead of the intended `403 Protected system roles cannot be edited/disabled`. Fixed by matching the same `OR: [{scopeKey:'system'}, {scopeKey: companyId}]` pattern already used by `list`/`get`. Caught via live browser testing, not by the original unit tests (whose hand-rolled Prisma fake didn't simulate the real scope filter) — the fake was strengthened afterward to actually filter by `scopeKey` so this class of regression is now caught by `pnpm test` too.
4. **Role picker allowed granting platform-level `SYSTEM_ADMIN`**: initial code only blocked the `OWNER` role key, not `SYSTEM_ADMIN` (a platform-only role from item 10A, also `scopeKey: 'system'`), so a company admin could have granted a company employee platform onboarding/partner-management permissions. Fixed with a shared `NON_ASSIGNABLE_ROLE_KEYS = ['OWNER', 'SYSTEM_ADMIN']` list, applied in both `CreateEmployeeUseCase`/`UpdateEmployeeUseCase` and the web role picker (`assignableRoles()` in `EmployeeAccessPages.tsx`).
