## Bugs found and fixed during this session (not caused by item 16 work)

1. **Procurement/AP module (item 12) permissions were never registered** — `apps/api/src/modules/auth/permission-registry.ts` had zero `procurement.*` entries in `PERMISSIONS`/`ROLE_GRANTS`, even though every procurement controller enforces `@RequirePermissions('procurement.xxx')`. `seed.ts` had a dead block writing to a non-existent `permissionDefinition` Prisma model (silently no-op via optional chaining). Net effect: **no role, not even OWNER, could ever call any procurement/AP API** — item 12 was checked off "complete" in the master checklist but was 100% inaccessible in practice. Fixed: added all 27 real `procurement.*` keys used by controllers to `PERMISSIONS`, granted to OWNER (automatic)/ADMIN/MANAGER/FINANCE/ACCOUNTANT/INVENTORY/AUDITOR_READONLY per `docs/specs/procurement-supplier-ap-spec.md` section 4 role descriptions. Removed the two dead no-op seed blocks (procurement + reimbursement — reimbursement's real keys were already correctly registered, its dead block was pure clutter). Verified in a live DB: OWNER/FINANCE now actually hold these permissions via `RolePermission`.
2. **`pnpm dev` (previously `tsx watch src/main.ts`) could not boot the app with working dependency injection at all** — confirmed via `git stash` bisection that this was 100% pre-existing, not introduced by item 16. Root cause: `tsx` is esbuild-based; esbuild does not implement TypeScript's `emitDecoratorMetadata`, so `Reflect.getMetadata('design:paramtypes', AnyInjectable)` returned `undefined` for **every** class in the codebase under `tsx` (re-confirmed empirically this session). NestJS's constructor-based DI relies on this metadata for any parameter without an explicit `@Inject()` token — the pattern used almost everywhere in this codebase. First observed failure: `IssueTokenUseCase` (auth module), but the defect was universal, not specific to that class. **FIXED (this session):** changed `apps/api`'s `dev` script off `tsx` to a zero-new-dependency `tsc`-based runner that emits decorator metadata correctly:

   ```json
   "dev": "tsc -p tsconfig.json && { tsc -p tsconfig.json -w --preserveWatchOutput & T=$!; node --watch --enable-source-maps dist/apps/api/src/main.js & N=$!; trap \"kill $T $N 2>/dev/null\" EXIT INT TERM; wait; }"
   ```

   Chose `tsc --watch` + `node --watch` (both already required — no SWC/ts-node added, per the AGENTS.md "no new dependency" rule) over adding SWC. If the team later wants faster incremental reloads, `@swc/core` + `@swc-node/register` (or the Nest CLI's SWC builder) is the standard upgrade — a deliberate, separate decision. The explicit-PID `trap ... EXIT INT TERM; wait` shape reaps the background `tsc --watch` on shutdown and, unlike a `kill 0` process-group blast, cannot terminate sibling tasks (`web`/`workers`) when run under `turbo run dev`. Verified: reaps both children on a direct signal to the dev shell and spares siblings; a terminal Ctrl-C (group SIGINT) tears down the whole dev tree with zero orphans. `apps/workers` and `apps/web` were left on their existing `dev` scripts — `apps/workers` uses plain BullMQ workers with **no** Nest decorators (grep-confirmed) so `tsx watch` is unaffected there, and `apps/web` is Next.js. Production path was always unaffected: `pnpm build` (real `tsc`) emits `__metadata("design:paramtypes", [...])` and `node dist/apps/api/src/main.js` boots all 23 modules; that remains the `api-built` launch config.
3. **`apps/workers`' `start` script pointed at a stale, dead build artifact** — `package.json` had `"start": "node dist/main.js"`, but `dist/main.js` was a 374-byte placeholder last built 2026-06-24 (before the item-06 notification worker even existed), because the monorepo's `tsconfig.base.json` sets `baseUrl` at the repo root and the workers package pulls in `packages/config`/`packages/contracts` source via path-mapping, so `tsc`'s real output actually lands at `dist/apps/workers/src/main.js` (mirroring the monorepo path, exactly like `apps/api` does). Net effect: **running `pnpm start` (i.e. whatever runs workers in production) has silently executed dead code with zero workers since June 24** — no notification delivery worker, and it would have silently swallowed the new workflow worker too. No launch.json entry existed for `workers` and no CI ever booted it, which is why nobody caught it. Fixed: corrected the `start` script to `node dist/apps/workers/src/main.js` and deleted the stale `dist/main.js`/`.map`. Verified: `pnpm build && pnpm start` now logs `notification_worker_started` and `workflow_worker_started`, and all 5 BullMQ repeatable jobs (outbox drain/30s, 3 scans/15min, retry sweep/60s) actually fire on schedule against a real Redis.
