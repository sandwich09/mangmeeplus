## 3. Release tasks and one-time steps

The actual normal Kamal release sequence is: verify migration catalog with pending allowed → `prisma migrate deploy` → verify catalog → `sync-permissions.ts` → `sync-feature-launch-gates.ts --verify-specialist-closed` → `sync-workflow-templates.ts` → `sync-thai-address-master.ts` → `normalize-entitlements.ts --dry-run --allow-exceptions` → verify feature-launch build authority (`infra/kamal/release.py:migrations`). The legacy release-task script has the corresponding guarded sequence, but is not authority to use the retired route.

`apps/api/start-production.sh` repeats migrations, permission sync, feature gates, Thai-address sync and entitlement **dry-run**; local-only seed and optional bootstrap-admin reset are also present. It **does not run workflow template sync**. The comment in `sync-workflow-templates.ts` describing production boot is not implemented by that shell entry point. Use the release task; boot alone is insufficient. Never use `seed.ts` to prepare production: it contains local/demo data and explicitly enables manual entry on two seed companies. Executive label back-fill is in the standalone permission script's `main()`, not the exported function that seed calls.
