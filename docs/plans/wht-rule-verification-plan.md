## 1. คำตอบสั้น: ยืนยันด้วย 3 ชั้น ไม่ใช่ชั้นเดียว

การ "ยืนยัน" กฎภาษีไม่ใช่แค่เขียนเทสต์ ต้องครบ 3 ชั้นนี้:

| ชั้น | ยืนยันอะไร | ใครทำ | ผลลัพธ์ที่จับต้องได้ |
|---|---|---|---|
| **1. Golden fixture** | ระบบคำนวณตรงกับตัวอย่างที่มีคำตอบถูกอยู่แล้ว | dev | test suite ที่ล้มเมื่อกฎเพี้ยน |
| **2. รีวิวโดยผู้เชี่ยวชาญ** | กฎที่เราตีความ ตรงกับกฎหมายจริง | ผู้สอบบัญชีภาษีอากร (TA) / นักบัญชี | เอกสารลงนามว่าตรวจแล้ว + `reviewedBy` ในระบบ |
| **3. Review-gate ในระบบ** | กฎที่ยังไม่ผ่านชั้น 2 **ใช้จริงไม่ได้** | ระบบ | `status: DRAFT` เป็น default, activate ต้องมี audit |

**ข่าวดี: ชั้น 3 ระบบทำถูกแล้ว** — `WhtIncomeCategory` ship มาเป็น `DRAFT` ทั้ง 15 แถว พร้อม `conditionNote: 'Accountant verification required before activation.'` และรายการ ACTIVE เท่านั้นที่โผล่ให้เลือก (`procurement/.../wht-income-category.use-case.ts:24-28`) — นี่คือ pattern ที่ถูกต้องและควรขยายไปใช้กับ posting rule (แผน G2 §5.4)

**ข่าวที่ต้องรู้: ชั้น 1 มีบางส่วน ชั้น 2 ยังไม่เกิด และมีข้อบกพร่องเชิงโครงสร้างที่ต้องแก้ก่อน**

## 2. สิ่งที่พบและต้องแก้ก่อนยืนยันอะไรก็ตาม

### 2.1 ⚠️ Catalog WHT เป็น global — ผู้เช่าหนึ่งเปิดใช้ มีผลกับทุกผู้เช่า (P1)

**หลักฐาน:**
- `WhtIncomeCategory` (`schema.prisma:3571-3588`) **ไม่มีคอลัมน์ `companyId`** และมี `@@unique([code])`
- `SetWhtIncomeCategoryStatusUseCase` (`tax/application/use-cases/wht-income-category.use-case.ts:32-35`) เรียก `update({ where: { code } })` — **ไม่มี company scope**
- แต่ audit บันทึกใต้ `ctx.companyId` (`:40`) → ดูเหมือนเป็นการกระทำระดับบริษัท ทั้งที่ผลกระทบเป็นระดับแพลตฟอร์ม

**ผลกระทบจริง:** ผู้ใช้ที่ถือ `tax.config.manage` ในบริษัท A กด activate `WHT_SERVICE_3` → บริษัท B, C, D ทุกบริษัททั่วระบบเห็นและใช้หมวดนั้นได้ทันที และถ้ากด DRAFT กลับ ก็ปิดให้ทุกบริษัทเช่นกัน

นี่ขัดกับหลัก tenant isolation ที่ระบบบังคับเข้มทุกที่ (`company-scope.policy.ts`, deny-by-default guard)

**ทางเลือกแก้ (ต้องเคาะ):**

| ทาง | วิธี | ข้อดี | ข้อเสีย |
|---|---|---|---|
| **A** | catalog เป็น **platform-managed read-only** — ถอด `SetWhtIncomeCategoryStatusUseCase` ออกจาก tenant, ให้ system admin จัดการที่ `app/system/*` เท่านั้น | ตรงความจริงว่ามันเป็นข้อมูลกฎหมายกลาง; ทีม compliance คุมจุดเดียว | tenant ที่อยากใช้หมวดหนึ่งต้องรอส่วนกลาง |
| **B** | เพิ่ม `CompanyWhtCategoryActivation (companyId, code, status, reviewedBy, reviewedAt)` — catalog กลางคงเดิม แต่การ "เปิดใช้" เป็นของแต่ละบริษัท | ตรงเจตนาเดิม (นักบัญชีของบริษัทเป็นผู้ vouch); audit ถูกต้องตามบริษัท | ตารางเพิ่ม |
| C | เพิ่ม `companyId` ลง `WhtIncomeCategory` แล้ว copy 15 แถวต่อบริษัท | ง่าย | ข้อมูลกฎหมายเดียวกันซ้ำ N ชุด อัปเดตกฎยาก |

**แนะนำ B** — เพราะ comment ในโค้ด (`:12-15`) บอกเจตนาชัดว่าต้องการให้ "นักบัญชีเป็นผู้ยืนยันอัตรา" ซึ่งเป็นเรื่องต่อบริษัท ส่วนตัวอัตรา/กฎหมายเป็นของกลาง — ทาง B แยกสองเรื่องนี้ออกจากกันได้พอดี และสอดคล้องกับสิ่งที่แผนนี้ต้องการ (§1 ชั้น 2 ต้องบันทึกว่า *ใคร* ตรวจ)

### 2.2 อัตราที่ใช้จริง ไม่เคยถูกตรวจกับ catalog

| จุด | อัตรามาจาก | ตรวจกับ catalog ไหม |
|---|---|---|
| Supplier payment | `dto.whtRate` ที่ผู้เรียกส่งมา (`supplier-payment.use-case.ts:75-95`) | ❌ ตรวจแค่ `0 < rate ≤ 100` และหมวดต้อง ACTIVE — **ไม่เคยเทียบกับ `defaultRate`** |
| Vendor bill | `raw.whtRate` ต่อบรรทัด (`vendor-bill.use-case.ts:687`) | ❌ ไม่ตรวจเลย |
| Expense | `whtRate` กรอกอิสระ (เก็บเป็นเศษส่วน) (`expense-draft.use-case.ts:45-47`) | ❌ ไม่ตรวจ; `taxCategory` เป็น string อิสระที่ถูกนำไปใช้เป็น `incomeCategoryCode` ภายหลัง (`expense-source.adapter.ts:79`) |
| Web UI | prefill จาก `defaultRate` แต่แก้ได้ (`AccountsPayablePages.tsx:634-652`) | — |

**ผลที่ตามมา:** การ activate หมวดด้วยอัตราที่ผ่านการตรวจสอบแล้ว ไม่ได้รับประกันว่าเอกสารจะใช้อัตรานั้นจริง

**ข้อเสนอ:** ไม่ต้องล็อกให้แก้ไม่ได้ (มีเคสที่ต้องแก้จริง) แต่ต้อง **บันทึกว่าเบี่ยงจาก default** และติดธงให้นักบัญชีตรวจ — pattern เดียวกับ `TaxReviewIssue` ที่มีอยู่

### 2.3 ผู้รับต่างประเทศตกไป ภ.ง.ด.53 แบบเงียบ ๆ

- `TaxFormType` มี `PND3, PND53` เท่านั้น ไม่มี `PND54` (`schema.prisma:2982-2990`)
- supplier ที่เป็น `FOREIGN` → fallback เป็น PND53 (`sync-tax-events.use-case.ts:305-310`) และ **ไม่มี review issue ถูกสร้าง** (มีเฉพาะเคส `MISSING_TAX_ID` ที่ `:326-331`)
- เทสต์ปัจจุบันยืนยัน fallback นี้ว่าเป็นพฤติกรรมที่ตั้งใจ (`sync-tax-events-supplier-payment-wht.use-case.spec.ts:89-98`)

**ปัญหา:** "เงียบ" คือส่วนที่อันตราย — ผู้ใช้ไม่รู้ว่าระบบเอาไปใส่แบบผิด

**ข้อเสนอขั้นต่ำ (ไม่ต้องทำ PND54 เต็ม):** เมื่อผู้รับเป็น `FOREIGN` → สร้าง `TaxReviewIssue` เตือนว่าอาจต้องยื่น ภ.ง.ด.54 + ภ.พ.36 และให้จัดการนอกระบบ พร้อมข้อความชัดว่าระบบไม่รองรับ

### 2.4 บิลปนสินค้า+บริการ — รองรับไม่เท่ากันในแต่ละเส้นทาง

| เส้นทาง | ระดับ | สถานะ |
|---|---|---|
| Vendor bill | **บรรทัด** | ✅ ใส่ `whtRate` เฉพาะบรรทัดบริการได้ |
| Expense | **บรรทัด** | ✅ และฐานคิดจากเฉพาะบรรทัดที่มี WHT (`expense-source.adapter.ts:6-21`); บิลที่มีหลายอัตราคืน `whtRate: null` ให้คนตรวจแทนที่จะเดา — **ดีไซน์นี้ถูกต้อง** |
| **Supplier payment** | **เอกสาร** | ⚠️ มี `whtAmount`/`whtRate`/`whtCategoryCode` ตัวเดียวต่อ payment |

**อันตรายที่ต้องแก้:** UI แนะนำยอด `bill.taxableAmount × rate` ซึ่งเป็นฐาน **ทั้งบิลรวมสินค้า** (`AccountsPayablePages.tsx:580-584`) → บิลปนจะ **หักเกิน** ถ้าผู้ใช้ไม่แก้เอง (ช่องแก้ได้ และ helper บอก "ปรับได้" ที่ `:655` แต่ไม่ได้เตือนว่าทำไมต้องปรับ)

**ข้อเสนอ:** ให้ค่าที่แนะนำคำนวณจาก **เฉพาะบรรทัดที่เข้าข่ายหัก** และถ้าบิลมีทั้งสินค้าและบริการ ให้แสดงคำเตือนว่า "บิลนี้มีทั้งสินค้าและบริการ — หักเฉพาะส่วนบริการ ถ้าแยกยอดไม่ได้ต้องหักทั้งจำนวน"

### 2.5 ไม่มีเกณฑ์ 1,000 บาท และไม่มี gross-up

ทั้งสองเรื่อง **ไม่มีโค้ดใด ๆ ในระบบ** (ค้นทั่ว `apps/api/src`, `apps/web/src`, `packages`)

- **เกณฑ์ 1,000:** ต้องตัดสินใจว่าจะทำหรือไม่ และถ้าทำ ต้องนับ **สะสมต่อสัญญา** ไม่ใช่ต่อบิล — ซึ่งต้องมีแนวคิด "สัญญา" ที่ระบบยังไม่มี → **งานใหญ่กว่าที่ดูเหมือน**
- **gross-up (ออกภาษีแทน):** `WhtCertificate` (`schema.prisma:3791-3821`) ยังไม่มีคอลัมน์ "เงื่อนไขการหัก" ที่แบบ 50 ทวิ ต้องระบุ (หักฯ / ออกให้ตลอดไป / ออกให้ครั้งเดียว) — บันทึกไว้แล้วใน `docs/research/rd-filing-and-data-intake-research.md:65`

**ข้อเสนอลำดับ:** ทำ gross-up ก่อน (เล็กกว่า และ 50 ทวิ ต้องมี field นี้อยู่แล้วตามแบบราชการ) ส่วนเกณฑ์ 1,000 ต่อสัญญา เลื่อนไปพร้อมกับตอนที่ระบบมีแนวคิดสัญญา/PO ผูกกัน

### 2.6 catalog ไม่มี effective date และไม่มีอ้างอิงกฎหมาย

- `WhtIncomeCategory` มี `taxRateConfigId` ที่ชี้ไป `TaxRateConfig` (ซึ่งมี effective date ผ่าน `TaxYearConfig`) — **แต่ไม่มีโค้ดใดเขียนค่านี้เลย** (ค้นทั่ว `apps/api/src` และ `seed.ts`: ไม่มี writer)
- ไม่มี field `lawRef`

ทำให้ข้อ "รายการเก่าใช้กฎ ณ วันนั้น" ยังทำไม่ได้สำหรับ WHT และ verdict ของ G1 จะไม่มีกฎหมายมาอ้าง

ไฟล์ข้อมูลแยกจากโค้ดเทสต์ เพื่อให้ **นักบัญชีอ่านและรีวิวได้โดยไม่ต้องอ่าน TypeScript**:

```jsonc

    "given": {
      "payerType": "JURISTIC", "payeeType": "JURISTIC",
      "lines": [{ "description": "ค่าจ้างทำเว็บไซต์", "amountBeforeVat": "10000", "vatRate": "0.07" }]
    },
    "expect": {
      "incomeCategoryCode": "WHT_SERVICE_5", "rate": "3", "base": "10000",

    "lawRef": "ทป.4/2528 ข้อ 8",
    "reviewedBy": null, "reviewedAt": null
  }

```

**ทำไมต้องแยกเป็น JSON:** ชั้นที่ 2 (รีวิวโดย TA) ต้องการเอกสารที่ผู้เชี่ยวชาญอ่านรู้เรื่อง — ถ้าซ่อนใน `.spec.ts` จะรีวิวไม่ได้จริง และ field `reviewedBy`/`reviewedAt` ทำให้ track ได้ว่าเคสไหนผ่านตาผู้เชี่ยวชาญแล้ว

**ชุดเคสขั้นต่ำที่ควรมี (ประมาณ 25-30 เคส):**
- อัตราหลักครบทุกหมวดในตาราง × ผู้รับบุคคล/นิติบุคคล
- ฐานก่อน VAT (มี VAT / ไม่มี VAT / VAT รวมในราคา)
- ปัดสตางค์
- บิลปนสินค้า+บริการ (แยกยอดได้ / แยกไม่ได้)
- ยกเว้นไม่หัก (ขนส่งสาธารณะ, ดอกเบี้ยธนาคาร, โรงแรม/ร้านอาหาร)
- ผู้รับต่างประเทศ (คาดหวัง = ติดธงให้คนตรวจ ไม่ใช่คำนวณเอง)
- gross-up (หลังทำฟีเจอร์)

## 4. ชั้นที่ 2 — รีวิวโดยผู้เชี่ยวชาญ

**สิ่งที่ต้องส่งให้ผู้สอบบัญชีภาษีอากร (TA) ตรวจ:**
1. `wht-golden-cases.json` แปลงเป็นตารางอ่านง่าย (ควรมี script แปลงเป็น markdown/xlsx)
2. ตาราง 15 หมวดใน seed พร้อม `defaultRate` และ `formType`
3. รายการสิ่งที่ระบบ **ไม่ทำ** อย่างซื่อสัตย์ (ไม่มีเกณฑ์ 1,000, ไม่มี gross-up, ไม่มี ภ.ง.ด.54)

**บันทึกผลอย่างไร:**
- ในระบบ: `reviewedByUserId` + `reviewedAt` บนตัว activation (ทาง B ของ §2.1)
- ในเอกสาร: `docs/legal-review/` (โฟลเดอร์นี้มีอยู่แล้ว) — บันทึกวันที่ ผู้ตรวจ ขอบเขต และข้อสงวน

**ข้อสังเกตสำคัญ:** `tax-thailand-2026-spec.md` ระบุแล้วว่า *"WHT categories/rates should be seeded as a full configurable catalog and remain review-gated until accountant verification"* — แผนนี้คือการทำให้ข้อนั้นเกิดขึ้นจริง ไม่ใช่ของใหม่

## 6. Acceptance criteria

1. บริษัท A เปลี่ยนสถานะหมวด WHT → บริษัท B ไม่ได้รับผลกระทบ (test ยืนยัน)
2. golden fixture ทุกเคสรันผ่าน และเมื่อแก้อัตราในโค้ดผิด ต้องมีเคสล้ม
3. เอกสาร golden case อ่านได้โดยผู้ไม่ใช่ developer และมีช่อง `reviewedBy` ที่กรอกจริงหลังรีวิว
4. กรอกอัตราต่างจาก `defaultRate` → เกิด review issue ไม่ใช่ผ่านเงียบ
5. ผู้รับต่างประเทศ → เกิด review issue ระบุว่าอาจต้อง ภ.ง.ด.54/ภ.พ.36 และระบบไม่รองรับ
6. บิลที่มีทั้งสินค้าและบริการ → ค่าที่แนะนำคิดจากส่วนบริการ และมีคำเตือน
7. หมวดที่ยังไม่ผ่านรีวิว ยังคง DRAFT และเลือกใช้ไม่ได้
8. เทสต์ WHT เดิมทั้งหมด (§3.1) ผ่าน

## 7. ความเสี่ยง

| ความเสี่ยง | ระดับ | การรับมือ |
|---|---|---|
| catalog global ถูกใช้งานจริงแล้วก่อนแก้ | **สูง** | ตรวจ audit log ว่ามี activation เกิดขึ้นแล้วกี่รายการ ก่อนเลือกวิธี migrate |
