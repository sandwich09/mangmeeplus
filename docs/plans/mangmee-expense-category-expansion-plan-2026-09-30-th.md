### 2.4 กติกาคำใบ้ (spec ของ template ตรวจทุกข้อที่ตรวจด้วยเครื่องได้)

1. **สั้น:** ไม่เกิน 80 ตัวอักษร 3–8 คำหรือวลีคั่นด้วยเว้นวรรค
2. **เป็นคำบนเอกสารหรือคำที่คนพิมพ์:** ประเภทร้าน ชื่อสินค้า หน่วย ชื่อหน่วยงานที่ออกบิล ไม่ใช่คำอธิบายบัญชี
3. **ไม่มีชื่อหมวดอื่นทั้งชื่อ และไม่มีคำที่ชวนตัดสินภาษี** ("VAT", "ภาษีซื้อ", "เคลม", "หัก ณ ที่จ่าย") คำอย่าง "ภาษีป้าย" หรือ "เงินเพิ่มภาษี" เป็นชื่อสิ่งที่จ่าย จึงใช้ได้
4. **เขียนเป็นรายการของสิ่งที่อยู่ในหมวด:** ไม่เขียน "ไม่รวม X ซึ่งอยู่หมวด Y" เพราะร้านอาจเก็บถาวรหมวด Y ไว้
   - คำปฏิเสธที่ไม่ชี้ไปหมวดอื่นใช้ได้ เช่น "ไม่ใช่น้ำดื่ม"
   - ถ้าร้านไม่มีหมวดเฉพาะ ชื่อหมวดกว้างของ V1 ยังรับรายการนั้นได้ เช่น ร้านที่เก็บถาวรค่าไฟฟ้า บิลไฟจะไปค่าสาธารณูปโภคตามชื่อ (เคส K-E)
5. **ไม่มีคำเดียวกันในคำใบ้สองหมวด** (คำที่คั่นด้วยเว้นวรรคต้องไม่ซ้ำกันข้ามหมวด) เช่น แก๊สรถ (B2) แยกจาก แก๊สหุงต้ม (สาธารณูปโภค) เพราะถังแก๊สหุงต้มก็เป็น LPG
6. **คู่ที่สับสนง่ายต้องมีคำแยกทั้งสองฝั่ง:**

   | คู่ | คำฝั่งหนึ่ง | คำอีกฝั่ง |
   |---|---|---|
   | น้ำมัน / ค่าเดินทาง | ปั๊มน้ำมัน ลิตร แก๊สรถ | แท็กซี่ ทางด่วน ที่จอดรถ |
   | ไฟฟ้า ประปา โทรศัพท์ / สาธารณูปโภค | บิลค่าไฟ การประปา ค่ามือถือรายเดือน | แก๊สหุงต้ม ค่าเก็บขยะ |
   | วัตถุดิบ / ค่าอาหาร | ของสด วัตถุดิบทำของขาย | อาหารพร้อมทาน เลี้ยงพนักงาน |
   | อุปกรณ์ราคาต่ำ / เครื่องเขียน | ใช้ได้นาน พัดลม เก้าอี้ | หมึกพิมพ์ ทิชชู่ ถุงขยะ |
   | ค่าปรับ / ค่าซ่อมแซม | ใบสั่งจราจร เบี้ยปรับ | ปรับปรุงร้านเล็กน้อย ช่างซ่อม |
   | ค่าอาหาร / ค่ารับรอง | เลี้ยงพนักงาน | เลี้ยงรับรองลูกค้า ของขวัญลูกค้า |

7. **หมวดที่ร้านตั้งเองส่งเฉพาะชื่อ** ส่วนหมวดจาก template ที่ร้านเปลี่ยนชื่อยังได้คำใบ้ตาม `accountHintKey`
8. **คำใบ้เป็นข้อความที่ระบบเขียน** และอยู่ในกล่องข้อมูลรายการหมวดที่ prompt ระบุว่าเป็นข้อมูล ไม่ใช่คำสั่ง (`line-ai-internal.controller.ts:1218`, `expense-capture-read.logic.ts:159`)
9. **ชื่อหมวด:** ขึ้นต้นด้วย "ค่า" และไม่มีชื่อใดเป็นส่วนหนึ่งของชื่ออื่น (สเปก §2 ข้อ 8)
   - คำที่คนพิมพ์ต้องหาได้หมวดเดียวด้วย `resolveNameCandidate`: "ค่าน้ำมัน", "ค่าไฟ", "ประปา", "ค่าวัตถุดิบ", "วัตถุดิบ", "ค่าโทรศัพท์", "ค่าปรับ"
   - "ค่าน้ำ" ต้องได้ผลกำกวมสองหมวด (น้ำมันและประปา) ให้ระบบถามกลับ
10. **จำนวน:** V2 รวมชุดธุรกิจหนึ่งชุดไม่เกิน 25 หมวด (เพดานของ gateway คือ 100 หมวด ซึ่งถ้าเกินจะไม่ส่งหมวดเลย สเปก §1.5 ข้อ 1)

### 2.5 การผูกบัญชี

- **ทุกบัญชีของชุด ก มีใน `TH_SME_COA_V1` เป็นบัญชีลงรายการได้และไม่ใช่บัญชีคุม** (`th-sme-chart-of-accounts-v1.ts:124-201`, `:226-227`)
- **ข้อยกเว้นชนิดบัญชี:** spec ของ template เปลี่ยนจาก "ทุกแถวเป็น EXPENSE" (`expense-category-bootstrap.service.spec.ts:33-42`) เป็น "EXPENSE หรือ COST เฉพาะ key ที่อยู่ในรายการอนุญาต"
  - รายการอนุญาตมีแค่ `expense.cost_of_goods` ใน C2 และแถว 5130-xx ของชุดธุรกิจใน C4
  - การพิมพ์ผิดที่ผูกแถวอื่นกับบัญชี COST จึงยังถูกจับตอน build
- **ไม่ออกผังรุ่นใหม่:** ผังมี checksum ตายตัว (`th-sme-chart-of-accounts-v1.ts:277`) หมวดที่ไม่มีบัญชีตรงใช้บัญชีที่ใกล้ที่สุดที่นักบัญชีเลือก (สเปก §9 ข้อ 5)
- **แก้การผูกหลังนักบัญชีตรวจ:** แก้ template สำหรับร้านใหม่ และเขียน migration ที่ `UPDATE` เฉพาะแถวที่ยังประทับ sentinel และยังผูกบัญชีเดิม (§4.4) แถวที่คนผูกใหม่แล้วไม่ถูกแตะ
- **ผลต่อการลงบัญชี:** เกิดเฉพาะร้านที่เปิด `expense_auto_post` ซึ่งปิดเป็นค่าเริ่มต้น (สเปก §1.3) และ worker ลงบัญชีตามการผูก ณ ตอนลง

### 4.2 ร้านที่มีอยู่แล้ว (data migration)

โครงของ SQL (ตรวจชื่อคอลัมน์และ enum ตอนลงมือ):

```sql
-- ชุด ก ของ TH_SME_EXPENSE_CATEGORIES_V2 สำหรับบริษัทที่ bootstrap แล้ว (แผน §4.2)
INSERT INTO "ExpenseCategory" ("id", "companyId", "name", "accountHintKey", "ledgerAccountCode",
  "ledgerAccountReviewedByUserId", "ledgerAccountReviewedAt", "defaultInputTaxCode",
  "status", "sortOrder", "createdAt", "updatedAt")
SELECT 'ecat_v2_' || md5(c."id" || ':' || t.hint), c."id", t.name, t.hint, t.code,
       'system:expense-category-bootstrap', NOW(), t.tax,
       'ACTIVE'::"ExpenseCategoryStatus", t.sort, NOW(), NOW()
FROM (VALUES
  ('ค่าวัตถุดิบและสินค้าเพื่อขาย', 'expense.cost_of_goods', '5130-01', 'V7', 13, 'วัตถุดิบ|สินค้าเพื่อขาย|ต้นทุนสินค้า')
  -- … แถวอื่นของชุด ก ตาม §2.1
) AS t(name, hint, code, tax, sort, near)
JOIN "Company" c ON EXISTS (
  SELECT 1 FROM "ExpenseCategory" b
  WHERE b."companyId" = c."id" AND b."ledgerAccountReviewedByUserId" = 'system:expense-category-bootstrap')
WHERE EXISTS (
    SELECT 1 FROM "ChartOfAccount" a
    WHERE a."companyId" = c."id" AND a."code" = t.code
      AND a."status"::text = 'ACTIVE' AND a."isPosting" AND NOT a."isControlled")
  AND NOT EXISTS (
    SELECT 1 FROM "ExpenseCategory" e
    WHERE e."companyId" = c."id"
      AND (e."accountHintKey" = t.hint OR btrim(e."name") = t.name OR e."name" ~ t.near))
ON CONFLICT DO NOTHING;
```

- **เงื่อนไขและเหตุผล:**
  - เฉพาะบริษัทที่มีหมวดประทับ sentinel ของ bootstrap: บริษัทรุ่นก่อน bootstrap ถูกข้าม เพราะถ้าได้แถวที่ประทับ sentinel หมวดกลางของบริษัทนั้นจะหายทันที (`prisma-expense.repository.ts:462-479`)
  - เฉพาะเมื่อผังของบริษัทมีบัญชีนั้นแบบ active ลงรายการได้และไม่ใช่บัญชีคุม (กติกาเดียวกับ bootstrap)
  - ข้ามเมื่อบริษัทมี key เดียวกัน ชื่อเดียวกัน หรือชื่อที่ตรงคำตรวจ ทั้งแถวที่เปิดและเก็บถาวร การเก็บถาวรของร้านจึงยังมีผล
  - ไม่มี `UPDATE` หรือ `DELETE` หมวดที่ร้านสร้างเองและหมวดเดิมทุกแถวจึงไม่ถูกแตะ
  - id คงที่ต่อบริษัทและ key พร้อม `ON CONFLICT DO NOTHING` การรันซ้ำจึงไม่เพิ่มแถว
  - `sortOrder` 13–19 ต่อท้าย V1 และ `createdAt` เป็นเวลาที่รันจริง ซึ่ง S4a ใช้ข้ามหมวดที่เพิ่งสร้าง
- **PG spec** (`expense-categories-v2-backfill.pg.spec.ts` รันไฟล์ SQL สองครั้งบนฐานข้อมูลทดสอบในเครื่อง ใช้ env และการกันเฉพาะ localhost แบบ PG spec เดิม):
  - บริษัท V1 ปกติได้ครบ 7 หมวด ประทับ sentinel ผูกบัญชีและ Tax Code ตรง template
  - บริษัทรุ่นก่อน bootstrap (ไม่มี sentinel) ไม่ได้แถวใดเลย และรายการหมวดที่ `listCategories` คืนเท่าเดิม
  - บริษัทที่มีหมวดตั้งเอง "ค่าน้ำมันรถ" ไม่ได้ B2 แต่ได้หมวดอื่นครบ
  - บริษัทที่เก็บถาวร "ค่าสาธารณูปโภค" ยังเก็บถาวรอยู่
  - บริษัทที่ไม่มีบัญชี 5330-02 ในผังไม่ได้ B3
  - รอบที่สองเพิ่มศูนย์แถว
  - ผลของร้านที่ได้ V2 ผ่าน migration เท่ากับร้านใหม่ที่ได้ V2 ผ่าน `bootstrapCompanyExpenseCategories` (ชื่อ key บัญชี Tax Code ลำดับ)
- **ก่อนและหลังรันบน UAT และ production:**
  - ก่อน: คำสั่งนับแบบอ่านอย่างเดียวด้วยเงื่อนไขเดียวกัน ได้จำนวนแถวที่จะเพิ่มต่อบริษัท รายชื่อหมวดที่จะถูกข้ามเพราะชื่อใกล้กัน จำนวนบริษัทรุ่นก่อน bootstrap จำนวนหมวดที่ใช้งานต่อบริษัทสูงสุด และจำนวนบริษัทที่เปิด `expense_auto_post` (ตาราง `CompanyFeatureEntitlement`)
  - หลัง: นับซ้ำให้ตรงกับที่คาด แล้วรายงาน Owner เป็นภาษาไทยธรรมดาว่ากี่ร้านได้หมวดใหม่และกี่ร้านถูกข้ามเพราะอะไร
  - บน production การนับต้องเปิด session ฐานข้อมูลซึ่งส่งอีเมลเตือนความปลอดภัยถึง Owner ต้องแจ้งก่อนทุกครั้ง
- **ถอยกลับ:** migration ใหม่ที่เปลี่ยนแถว id ขึ้นต้น `ecat_v2_` เป็น `ARCHIVED` ไม่ลบ เพราะรายการที่บันทึกแล้วอาจอ้างหมวดนั้น

### 5.2 เกณฑ์ผ่าน (ทุกข้อ ทั้งสองรอบบน commit เดียวกัน)

1. **ความแม่นของหมวดที่ AI เขียนให้** (รูปและ PDF ที่ความมั่นใจถึง 0.85, ข้อความที่ตัวจัดเส้นทางระบุ): ถูกอย่างน้อย 95% หรือผิดไม่เกิน 1 ใน 20
2. **ความครอบคลุม:** เคสที่คาดว่ามีหมวดได้หมวดอัตโนมัติอย่างน้อย 70% และบนเคสที่ V1 มีหมวดรองรับ ไม่ต่ำกว่ารอบที่ผ่านของ C1
3. **เคสที่ไม่มีหมวดที่ใช่:** เว้นว่างทุกเคส ห้ามเบ็ดเตล็ดเสมอ และห้ามหมวดนอกรายการ
4. **คู่ที่สับสน:** ผิดไม่เกิน 1 ครั้งต่อคู่ต่อรอบ
5. **K-R:** ตัวเลขตรง oracle ทุกข้อ และ "ค่าน้ำ" ได้คำถามกลับที่มีทั้งสองหมวด
   - เคส "ค่าไฟสิงหาเท่าไหร่" ไม่นับเป็นเกณฑ์ผ่าน เพราะขึ้นกับตัวอ่านวันที่ ถ้าไม่ผ่านให้รายงานผู้คุมเป็นงานแยก
6. **ต้นทุน:** input token ของตัวจัดเส้นทางเพิ่มไม่เกิน 400 token ต่อเทิร์นเทียบกับรอบของ C1 และค่าต่อใบของรูปและ PDF เพิ่มไม่เกิน 10%
7. **C1 เพิ่มเติม:** ไม่แย่กว่ารอบ baseline บน develop ในข้อ 1 และข้อ 2

   2. ส่งรูปใบเสร็จปั๊มน้ำมัน → ค่าน้ำมันเชื้อเพลิง
   3. ส่งรูปบิลค่าไฟ และบิลค่าน้ำประปา → หมวดของตัวเอง
   4. พิมพ์ "ค่าเน็ตร้าน 599" → ค่าโทรศัพท์และอินเทอร์เน็ต
   5. พิมพ์ "ซื้อพัดลมเข้าร้าน 890" → ค่าอุปกรณ์และเครื่องใช้ราคาต่ำ
   6. พิมพ์ "โดนใบสั่ง 500" → ค่าปรับ เบี้ยปรับ และเงินเพิ่ม
   7. ส่งรูปใบเสร็จแท็กซี่หรือทางด่วน → ค่าเดินทางและยานพาหนะ ไม่ใช่น้ำมัน
   8. พิมพ์ "ซื้อของ 500" → ไม่มีหมวดและระบบถามหมวด
   9. ถาม "ค่าน้ำมันเดือนนี้เท่าไหร่" และ "ต้นทุนวัตถุดิบเดือนนี้" → ตัวเลขถูก

   - เปิด customer gate เป็น `OPEN` แล้วตรวจรับหลัง logout
   - จด run หรือ operation ID ทั้งหมดใน ledger ของ runbook

## 11. สิ่งที่ไม่ทำในแผนนี้

- **ให้ AI เลือกหมวดต่อบรรทัดของรูปหรือ PDF** (ข้อความใน LINE ทำได้อยู่แล้วตั้งแต่ #911)
- **จัดหมวดย้อนหลังให้รายการเก่า** (สเปก §9 ข้อ 11)
- **อัตราหัก ณ ที่จ่ายเริ่มต้นต่อหมวด** และ **คำเตือนสินทรัพย์** (สเปก §9 ข้อ 6–7)
- **หน้าผูกบัญชีของหมวดที่ร้านตั้งเอง** (สเปก §9 ข้อ 9)
- **ผังบัญชีรุ่นใหม่** (สเปก §9 ข้อ 5)
- **ถามประเภทธุรกิจตอนสมัคร** และ **เก็บว่าร้านเลือกชุดไหน** (สเปก §4, §9 ข้อ 2)
- **เปลี่ยนตารางหน้าหมวดเป็นการ์ดบนมือถือ** (§7)
- **แก้ `intent-router.agent.ts`, `semantic-turn-v2.ts` และไฟล์อื่นของ lane ที่ปรึกษาใน C1–C2** เว้นแต่ข้อที่ระบุว่าทำหลัง R1 merge
- **ใช้ใบเสร็จของลูกค้าจริงในการทดสอบ**
- **แก้ `seed.ts`, หมวดกลาง หรือบริษัทรุ่นก่อน bootstrap**
