# Plan: G3 — เชื่อมระบบตรวจสอบผู้เสียภาษีของกรมสรรพากร

- สถานะ: **DRAFT — ต้องทำ spike ยืนยัน service จริงก่อนวางแผนละเอียด (§4)**
- วันที่: 2026-08-14
- โจทย์จากเจ้าของผลิตภัณฑ์: *"ต้องทำอย่างไรถึงจะไปต่อกับระบบสรรพากรได้"*
- คำเตือน: ข้อมูล endpoint ด้านล่างมาจากเอกสารสาธารณะของกรมสรรพากร ณ 2026-08-14 **ต้องยืนยันด้วยการเรียกจริงก่อนออกแบบละเอียด** และต้องให้นักบัญชี/ที่ปรึกษาภาษีตรวจก่อนใช้ผลตัดสินทางภาษี

## 1. คำตอบสั้น: ไปต่อได้ และมีช่องทางที่เปิดอยู่แล้ว

กรมสรรพากรเปิด **web service สาธารณะ** สำหรับตรวจข้อมูลผู้ประกอบการจดทะเบียน VAT — ไม่ต้องขอสิทธิ์ ไม่ต้องทำสัญญา ใช้ credential `anonymous`

| บริการ | Endpoint | ใช้ทำอะไร |
|---|---|---|
| **VAT Service** | `https://rdws.rd.go.th/serviceRD3/vatserviceRD3.asmx` | ตรวจเลข 13 หลัก → คืนชื่อ/ที่อยู่/สาขา/**วันที่อนุมัติจดทะเบียน VAT** |
| Common Service | `https://rdws.rd.go.th/serviceRD3/commonserviceRD3.asmx?wsdl` | รหัสจังหวัด/อำเภอ (ใช้ประกอบ query) |
| JSON variant | `https://rdws.rd.go.th/jsonRD/...` | ทางเลือก — **ยังเป็น SOAP ต้องยืนยัน** |

- โปรโตคอล: SOAP (`application/soap+xml; charset=utf-8`)
- Auth: `username: anonymous` / `password: anonymous`
- Input: เลขผู้เสียภาษี 13 หลัก (+ ชื่อ/จังหวัด/สาขา/อำเภอ เป็นตัวเลือก ใส่ `0` ถ้าไม่ทราบ)
- Output: ~17 field รวมเลขผู้เสียภาษี, เลขสาขา, ชื่อกิจการ, ที่อยู่เต็ม, **วันที่อนุมัติ VAT**
- ติดต่อ: `webservice@rd.go.th`
- **ไม่มีการประกาศ rate limit หรือ SLA** ← ข้อนี้สำคัญมากต่อการออกแบบ (§5)

**แหล่งอ้างอิง:** [VAT Service — กรมสรรพากร](https://www.rd.go.th/42535.html) · [Common Service — กรมสรรพากร](https://www.rd.go.th/42539.html) · [ตัวอย่าง SOAP Request (PDF)](https://www.rd.go.th/fileadmin/webservice/Sample_SOAP_Request_V5.pdf)

### 1.1 ช่องทางเสริมที่ควรรู้ (ไม่ใช่ขอบเขตรอบนี้)

- **DBD DataWarehouse** (กรมพัฒนาธุรกิจการค้า) — ข้อมูลนิติบุคคล สถานะ ทุนจดทะเบียน งบการเงิน ใช้ยืนยัน "บริษัทนี้ยังดำเนินกิจการอยู่ไหม" คนละเรื่องกับ VAT — [datawarehouse.dbd.go.th](https://datawarehouse.dbd.go.th/)
- **RD e-Filing / Open API** — สำหรับ **ยื่นแบบ** ไม่ใช่ตรวจสอบ และ `tax-thailand-2026-spec` ระบุไว้ชัดว่า auto-filing เป็น non-goal และทุก route ยัง CLOSED จนกว่าจะ contract-test ราย tuple — **แผนนี้ไม่แตะ**

## 2. ใช้ผลลัพธ์ทำอะไรได้ (ตรงกับที่ระบบต้องการอยู่แล้ว)

| ผลจาก RD | เอาไปใช้ที่ |
|---|---|
| เลขนี้จดทะเบียน VAT จริงหรือไม่ | **ด่านที่ 3 ของ VAT engine** (แผน G1 §4.2) — "ใบกำกับจากผู้ไม่มีสิทธิออก" ตาม ม.82/5 |
| ชื่อกิจการตรงกับที่ OCR อ่านได้ไหม | ตรวจความถูกต้องของ `vendorNameSnapshot` — ปัจจุบัน `deriveExpenseAuditChecks` เช็คแค่ว่ามีค่า |
| ที่อยู่/สาขา (สำนักงานใหญ่/สาขาที่) | องค์ประกอบตาม **ม.86/4** ที่ต้องระบุสำนักงานใหญ่/สาขา |
| **วันที่อนุมัติจดทะเบียน VAT** | ตรวจว่าวันที่ในใบกำกับ **หลัง** วันที่ผู้ขายได้รับอนุมัติ — จับใบกำกับที่ออกก่อนมีสิทธิ์ |

**จุดที่มีอยู่แล้วในระบบและรอเสียบพอดี:**
- OCR อ่านเลขผู้เสียภาษีอยู่แล้ว → `vendorTaxIdSnapshot` (`schema.prisma:2124`)
- มี `AccountingCounterparty` เก็บคู่ค้า → เป็นที่เก็บผลตรวจที่เหมาะสม
- `expense-status.logic.ts:174` ตรวจว่ามีเลขผู้เสียภาษีอยู่แล้ว แต่ตรวจแค่ "มี/ไม่มี" และ 13 หลัก

## 3. หลักการออกแบบ (สำคัญกว่า endpoint)

### 3.1 ต้อง fail-open เสมอ — ห้ามบล็อกงานผู้ใช้

บริการนี้เป็นของหน่วยงานภายนอก **ไม่มี SLA ประกาศ** และ credential เป็น `anonymous` แปลว่าอาจถูกจำกัด/ปิด/ช้าเมื่อไหร่ก็ได้

**กฎ:**
- ตรวจไม่ได้ = `UNKNOWN` **ไม่ใช่** `INVALID`
- `UNKNOWN` ต้องไม่บล็อกการบันทึก/confirm รายจ่าย — แค่ติดธงให้นักบัญชีดู
- pattern นี้มีในระบบแล้ว: `receipt-ocr.client.ts` คืน `{status:'failed', errorCode}` **ไม่ throw** — เดินตามนี้

### 3.2 ต้อง cache — เพราะไม่มี rate limit ประกาศ = ต้องประหยัดเอง

- ผลตรวจต่อ `(taxId, branchNo)` เก็บไว้ พร้อม `verifiedAt`
- TTL ข้อเสนอ: 90 วัน (สถานะ VAT ไม่เปลี่ยนบ่อย) — ต้องเคาะ
- ตรวจซ้ำเมื่อ: ผู้ใช้กดตรวจเอง / ผลเดิมเป็น `UNKNOWN` / เกิน TTL
- **ห้ามยิงต่อ 1 ใบเสร็จ** — ยิงต่อ **คู่ค้า** และ reuse

### 3.3 ต้อง throttle + circuit breaker ฝั่งเรา

ใช้ Redis rate limit ที่มีอยู่แล้ว (pattern เดียวกับ `receipt-ocr.client.ts:23-28`) และตัดวงจรเมื่อ error ติดกัน N ครั้ง เพื่อไม่ยิงซ้ำใส่ระบบราชการ

### 3.4 PDPA — ระวังเลข 13 หลักของบุคคลธรรมดา

เลข 13 หลักของ **นิติบุคคล** = ข้อมูลธุรกิจ ตรวจได้ตามปกติ
เลข 13 หลักของ **บุคคลธรรมดา** = เลขบัตรประชาชน = **ข้อมูลส่วนบุคคล**

**ข้อเสนอ:** ยิงตรวจเฉพาะเมื่อคู่ค้าเป็นนิติบุคคล หรือเมื่อเอกสารเป็นใบกำกับภาษี (ซึ่งผู้ออกต้องจด VAT อยู่แล้ว) — ต้องให้ทีม legal/PDPA ยืนยัน (repo มี `pdpa-notice-and-ai-opt-out-spec` + `docs/legal-review/` อยู่แล้ว)

### 3.5 ไม่ใช่คำวินิจฉัยทางกฎหมาย

ผลจาก RD เป็น **หลักฐานสนับสนุน** — ต้องแสดงว่า "ตรวจกับกรมสรรพากรเมื่อ [วันที่]" และให้นักบัญชี override ได้ พร้อม audit (สอดคล้องหลัก human-in-the-loop ของ G1)

## 4. Phase 0 — Spike ยืนยันก่อน (ต้องทำก่อนวางแผนละเอียด)

**ห้ามข้ามขั้นนี้** ข้อมูล endpoint มาจากเอกสารและบทความ ยังไม่ได้เรียกจริงจากโปรเจกต์นี้

สิ่งที่ต้องพิสูจน์และบันทึกผล:

1. เรียก `vatserviceRD3.asmx` ด้วยเลขจริงของบริษัททดสอบ → ได้ response ไหม, field ชื่ออะไรจริง ๆ, encoding อะไร (ภาษาไทยเพี้ยนไหม)
2. เลขที่ **ไม่มีอยู่** คืนอะไร (empty / error / fault)
3. เลขที่มีอยู่แต่ **ยกเลิกจดทะเบียน VAT แล้ว** คืนอะไร — ต้องแยกออกจาก "ไม่เคยจด"
4. กิจการที่มี **หลายสาขา** — ระบุ branch อย่างไร, สำนักงานใหญ่คือ `0` หรือ `00000`
5. ยิงติด ๆ กัน 20 ครั้ง → ถูก throttle ไหม ตอบช้าแค่ไหน (วัด p50/p95)
6. TLS/cert ของ `rdws.rd.go.th` ใช้ได้จาก ECS Fargate ap-southeast-1 ไหม (บาง service ราชการใช้ cert chain ที่ต้อง config)
7. เรียกจาก **นอกประเทศไทย** ได้ไหม — ถ้าไม่ได้ กระทบสถาปัตยกรรม (hosting อยู่สิงคโปร์ตาม `sme-business-os-overview.md:175`) ← **ข้อนี้เสี่ยงสุด ต้องทดสอบก่อน**

**Deliverable ของ Phase 0:** เอกสารสั้น ๆ ใน `docs/research/` บันทึก request/response จริง + ผลวัด + ข้อจำกัดที่พบ

> ถ้าข้อ 7 ล้มเหลว ทางเลือกคือ: proxy ใน region ไทย, หรือ worker ที่รันในไทย, หรือใช้ผู้ให้บริการตัวกลาง — ต้องกลับมาเคาะใหม่

## 5. สถาปัตยกรรมที่เสนอ (หลัง Phase 0 ผ่าน)

```
apps/api/src/modules/tax/infrastructure/rd-vat-registrant.client.ts   ← SOAP client + throttle + circuit breaker
apps/api/src/modules/tax/domain/logic/vendor-verification.logic.ts    ← pure: เทียบผล RD กับข้อมูลในใบเสร็จ
apps/workers/  (หรือ queue)                                            ← ตรวจแบบ async ไม่บล็อก request
```

**ทำไมต้อง async:** การตรวจไม่ควรอยู่ใน request path ของการอัปโหลดใบเสร็จ — ให้ enqueue หลัง OCR เสร็จ แล้วอัปเดตผลเข้ามาทีหลัง (pattern เดียวกับที่ OCR ทำอยู่)

**ตารางใหม่ (ข้อเสนอ):** `VendorTaxVerification`
`(id, companyId?, taxId, branchNo, status: VERIFIED|NOT_REGISTERED|UNKNOWN, registeredName, registeredAddress, vatApprovedDate, checkedAt, source: 'RD_VAT_SERVICE', rawResponseJson)`

- `companyId` เป็น nullable เพราะผลตรวจของเลขผู้เสียภาษีหนึ่งใช้ร่วมกันได้ทุก tenant (เป็นข้อมูลสาธารณะ)
- ⚠️ **แต่ต้องระวังบทเรียนจาก `WhtIncomeCategory`** ที่เป็น global แล้วเกิดปัญหาข้ามผู้เช่า (ดูแผน G5 §2.1) — ถ้าเก็บ global ต้องเป็น **read-only cache ที่ไม่มีใครแก้ได้** เท่านั้น ห้ามมี mutation จาก tenant

## 7. Acceptance criteria

1. อัปโหลดใบกำกับที่มีเลขผู้เสียภาษี → ระบบตรวจกับ RD แบบ async และแสดงผลในหน้า review พร้อมวันที่ตรวจ
2. เลขที่ไม่ได้จด VAT → ติดธงในด่าน 3 ของ VAT verdict พร้อมเหตุผลอ้าง ม.82/5 — **แต่ยังบันทึกรายจ่ายได้**
3. ชื่อผู้ขายไม่ตรงกับที่จดทะเบียน → เตือน (WARNING ไม่ใช่ BLOCKING)
4. วันที่ใบกำกับก่อนวันอนุมัติจด VAT ของผู้ขาย → เตือน
5. RD ล่ม/ช้า/ตอบไม่ได้ → `UNKNOWN` ไม่บล็อกอะไร ไม่มี error หลุดถึงผู้ใช้ และมี log/metric
6. ตรวจเลขเดิมซ้ำภายใน TTL → ใช้ cache ไม่ยิงซ้ำ
7. นักบัญชี override ผลได้ และมี audit ว่าใครแก้ ตอนไหน เพราะอะไร
8. ไม่มีเลข 13 หลักของบุคคลธรรมดาถูกส่งออกไปนอกระบบโดยไม่ผ่านเงื่อนไข §3.4
