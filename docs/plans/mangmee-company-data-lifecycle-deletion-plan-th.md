## เป้าหมายและเส้นแบ่ง

ทำให้ MangmeePlus **ถือข้อมูลร้านที่เลิกใช้ได้อย่างปลอดภัย** และ **ลบได้จริงเมื่อถึงเวลา**
โดยไม่ผิดทั้ง PDPA และ พ.ร.บ.การบัญชี

**ลำดับความสำคัญกลับด้านจากที่คิดตอนแรก:** เพราะมติ D2 (ไม่มีคำร้อง = เก็บจนครบอายุกฎหมาย)
แปลว่าเราจะถือข้อมูลร้านที่ตายแล้วไว้นานมาก คำถามหลักจึงเปลี่ยนจาก "ลบยังไง"
เป็น **"ถือไว้แล้วปลอดภัยจริงหรือเปล่า"** → งานล็อกประตูมาก่อนงานสร้างเครื่องมือลบ

**ไม่อยู่ในแผนนี้:** ปุ่มลบ self-service, cron ลบอัตโนมัติ, backup tombstone/replay,
การแก้กติกากู้คืนของ `DISABLED`, CRM end-customer erasure ที่มีอยู่แล้ว

## D1 — ล็อกประตูร้านที่ปิด

**ทำไมมาก่อน:** วันนี้ร้านที่ `ARCHIVED` แล้ว session เดิมยังใช้ได้ LINE ยังตอบ
และ **บัตรเครดิตยังถูกตัดเงินอยู่** (spec §1.3, §1.6) การถือข้อมูล 5 ปีโดยประตูยังไม่ล็อก
คือส่วนผสมที่แย่ที่สุดของทั้งสองทาง

### ขอบเขต

ต่อยอด `PartnerLifecycleTransitionUseCase` ที่มีอยู่ — ไม่สร้าง use-case ใหม่

- **D1.1** ยกเลิก Stripe subscription ให้สำเร็จ **ก่อน** เปลี่ยนสถานะ (A3, fail-closed)
  ถ้าไม่สำเร็จ → สถานะไม่เปลี่ยน + แจ้ง operator
- **D1.2** เพิกถอน `AuthSession` ทุกใบของทุก membership ในร้าน (A1)
- **D1.3** ปิด `LineChannelBinding` + หยุดตอบ LINE (A2)
- **D1.4** หยุด `OutboxEvent` / worker ของร้าน (A4)
- **D1.5** ปิดเส้นทางกู้คืนสำหรับ `ARCHIVED` — แก้ทั้ง 8 จุดใน spec §1.7
  ให้ `DISABLED + termDisabledAt` ยังผ่านเหมือนเดิม แต่ `ARCHIVED` ไม่ผ่าน
- **D1.6** AuditLog CRITICAL บันทึกผล D1.1–D1.5 รายข้อ
- **D1.7** worklist `DISABLED → ARCHIVED` เมื่อครบ xx วันนับจาก `Company.disabledAt`
  **ขึ้นรายการให้แอดมินเห็น ไม่ใช่ย้ายสถานะเอง** (D2)

### จุดที่ต้องระวัง

- D1.5 แตะ auth path หลายจุด — ต้องพิสูจน์ว่า `DISABLED` ยังกู้คืนได้ครบทั้ง 8 จุด
  ไม่ใช่แค่ทดสอบว่า `ARCHIVED` เข้าไม่ได้
- `SUSPENDED` เป็นสถานะความปลอดภัยแยก ห้ามเอามารวม
- การสั่ง `ARCHIVED → ACTIVE` กลับ ต้องไม่ฟื้น Stripe subscription เอง

### Gate

- [ ] `ARCHIVED` แล้ว session เดิมใช้ไม่ได้ทันที / LINE ไม่ตอบ / outbox หยุด
- [ ] Stripe ยกเลิกสำเร็จก่อนสถานะเปลี่ยน; ยกเลิกไม่สำเร็จ = สถานะไม่เปลี่ยน
- [ ] ทั้ง 8 จุดของ spec §1.7 ยังกู้คืน `DISABLED` ได้ครบ
- [ ] AuditLog CRITICAL ครบทุกข้อ
- [ ] focused test ครอบคลุม `ARCHIVED` เข้าไม่ได้ **และ** `DISABLED` ยังเข้าได้

## D2 — เครื่องมือนับของ

**ทำไมมาคู่กับ D1:** ตอบคำถาม "เราถืออะไรไว้เท่าไร" (spec §5) และเป็นวัตถุดิบของ
ด่าน E1 และหลักฐาน `OBJECT_STORAGE_INVENTORY` ใน D5

### ขอบเขต

สคริปต์อ่านอย่างเดียว รับ `companyId` คืน JSON ที่ hash ด้วย SHA-256 ได้

- **D2.1** นับแถวต่อตารางทั้ง 194 ตารางที่ถือ `companyId`
  รวม 20 ตาราง orphan ที่ต้องนับด้วย `companyId` ตรง ๆ เพราะไม่มี FK
- **D2.2** นับ object + version จริงใน storage — ต่อยอด `getExactObjectVersionInventory` /
  `object-version-inventory.logic.ts` ที่มีอยู่ ไม่เขียนใหม่
- **D2.3** สถานะ Stripe: `subscriptionState`, `cancelAtPeriodEnd`, `paidThrough`, `baseSubscriptionId`
- **D2.4** จำนวน `AuthSession` ที่ยัง active + `LineChannelBinding` ที่ยังผูก
- **D2.5** รายการ FK ที่จะบล็อกการลบ (ก่อน D4 เสร็จจะมี 3 รายการตาม spec §1.1)
- **D2.6** เขียนผลเป็นไฟล์ + พิมพ์ SHA-256 ไม่ใช่ข้อความบนหน้าจอ

### จุดที่ต้องระวัง

- รายการตารางต้อง**สร้างจากสคีมา ไม่ใช่รายการที่พิมพ์มือ** ไม่งั้นตารางใหม่ในอนาคตจะหลุด
- ต้องรันบน production ผ่าน SSM port-forward ได้ และ**ประกาศให้ Owner ทราบก่อน**
  เพราะทุก session ยิงเมลแจ้งเตือนความปลอดภัย

### Gate

- [ ] ไม่มี write ใด ๆ (พิสูจน์ด้วย read-only DB user หรือ transaction rollback)
- [ ] นับครบทั้ง 194 ตาราง รวม 20 orphan
- [ ] นับ object/version จริงใน storage ไม่ใช่แค่แถว DB
- [ ] รันบน production ได้จริงหนึ่งครั้ง พร้อมเก็บผล + hash เป็นหลักฐาน

## D3 — นาฬิกาเก็บรักษาสองชั้น

**บล็อกโดย Q2 (แยกสองนาฬิกาไหม) และ Q3 (เอกสารบัญชีหลัง 5 ปีเก็บหรือส่งคืน)**

### ขอบเขต

- **D3.1** กำหนดสคีมาของ `CompanyBusinessPolicy.retentionPolicyJson` ที่วันนี้เป็น `{}` เปล่า
  (spec §1.11) — ต้องเก็บวันครบกำหนดรายหมวด + เหตุผล + ผู้แก้ + เวลาแก้
- **D3.2** คำนวณวันครบกำหนดจาก `AccountingPeriod.endDate` / `closedAt` และ `TaxPeriod`
  ตาม spec §6.3 — **รายเอกสาร ไม่ใช่รายร้าน**
- **D3.3** จัดหมวดทุกตารางลงนาฬิกา A หรือ B ตาม spec §6.2 เป็นตารางที่ตรวจทานได้
- **D3.4** guard: ปฏิเสธการลบหมวดนาฬิกา B ก่อนครบกำหนด (D2 fail-closed)
- **D3.5** แสดงวันครบกำหนดในหน้า partner detail ให้แอดมินเห็น

### จุดที่ต้องระวัง

- ม.14 เปิดช่องให้สั่งขยายถึง 7 ปี และกรณีเลิกกิจการ VAT มีกฎแยก
  → ค่าต้อง**แก้ได้** ห้ามเป็น constant ในโค้ด (spec §6.4)
- D3.3 ต้องตรวจทีละตาราง ห้ามจัดยกแผง

### Gate

- [ ] คำนวณวันครบกำหนดถูกต้องกับร้านที่มีงวดปิดหลายงวดต่างปี
- [ ] แก้วันครบกำหนดได้พร้อมเหตุผล และมี audit
- [ ] พยายามลบหมวด B ก่อนครบกำหนด → ถูกปฏิเสธ
- [ ] ลบหมวด A ไม่กระทบหมวด B

## D4 — ปิดรู FK

**ทำตอนสคีมายังเล็ก** — อีก 5 ปีจะแก้ยากกว่านี้มาก ถึงแม้ยังไม่มีใครลบอะไรเร็ว ๆ นี้

### ขอบเขต

- **D4.1** แก้ 3 ตัวบล็อกตาม spec §7.1
  (`CompanyOnboardingRun`, `ExpenseSubstituteReceiptEvidence`, `CrmDataSubjectRequest`)
- **D4.2** ผูก FK ให้ 20 ตาราง orphan ตาม spec §7.2 พร้อม `onDelete` ที่ตรงกับหมวดนาฬิกา
- **D4.3** `DataRightsCase` / `LegalDocumentActionRecord` ต้อง**ไม่** Cascade — เป็นหลักฐานที่ต้องอยู่ต่อ
- **D4.4** `AuditLog` / `OutboxEvent` คง SetNull แต่เพิ่ม tombstone ที่ยังชี้ร้านเดิมได้ (spec §7.3)

### จุดที่ต้องระวัง

- **D4.1 ขึ้นกับ D3:** `ExpenseSubstituteReceiptEvidence` เป็น `Restrict` โดยตั้งใจเพื่อกันลบ
  หลักฐานใบแทนใบเสร็จ ห้ามเปลี่ยนเป็น Cascade ก่อนมีนาฬิกา B คุม (spec §7.1)
- **D4.2 ต้องตรวจทีละตาราง** ว่าเป็นข้อมูลของร้านจริงหรือเป็นข้อมูลกลางที่บังเอิญมี `companyId`
  (`PlatformAiBudgetConfig`, `RemoteReleaseMutationIntent`, `Role` น่าสงสัยเป็นพิเศษ)
- migration ต้อง additive และไม่ล็อกตารางใหญ่นาน

### Gate

- [ ] `prisma.company.delete()` บนร้านทดสอบที่มีข้อมูลครบทุกโมดูล **ไม่ error**
- [ ] หลังลบ ไม่มีแถวค้างใน 20 ตาราง orphan
- [ ] `DataRightsCase` / `LegalDocumentActionRecord` ยังอยู่
- [ ] `AuditLog` ยังอยู่และยังสืบย้อนร้านเดิมได้
- [ ] smoke script ที่เคยต้อง `deleteMany` มือก่อน (`signup-journey-smoke.ts:189` ฯลฯ)
      ลบบรรทัดนั้นออกได้แล้วยังผ่าน

## D5 — single-admin mode + executor

**บล็อกโดย Q4 (user ที่เหลือ 0 ร้าน)** — เฉพาะส่วนที่แตะ membership

### D5.1 single-admin mode

ตามแบบ `selfApprovalPermitted` / `selfApproved` ใน `substitute-receipt.use-case.ts:43-47`
(spec §8.3) — **ห้ามคิดแบบใหม่**

- ผ่อน 4 กฎใน `data-rights.service.ts` (552/570/584/612) เมื่อเปิด single-admin mode
- ติดธง `selfExecuted` ลงในเคสและใน `DataRightsCaseActionRecord`
- ต้องเป็นการตั้งค่าที่ประกาศชัด ไม่ใช่ผลข้างเคียงจากการบังเอิญมีแอดมินคนเดียว (spec §8.6)

### D5.2 ด่านที่เครื่องตรวจ

| # | ด่าน | ข้ามได้ |
|---|---|---|
| E1 | รายงาน D2 ที่ hash แล้วและสร้างไม่เกิน 1 ชม. | ไม่ |
| E2 | พิมพ์ชื่อร้านให้ตรง | ไม่ |
| E3 | หลักฐานมาจากเครื่อง ไม่ใช่พิมพ์มือ | ไม่ |
| E4 | รอ 1 วันหลังอนุมัติ (ค่าตั้งต้น) | ได้ — ต้องพิมพ์เหตุผล |

E4' ปุ่มลบทันที: **ต้องพิมพ์เหตุผล ไม่ใช่ดับเบิลคลิก** แล้วบันทึก
`cooldownWaivedAt` + เหตุผล + ผู้กด (spec §8.4)

### D5.3 executor

ลำดับตาม spec §9.2 — **ลบไฟล์ก่อนลบแถวเสมอ**

- ห้ามใช้ `prisma.company.delete()` เป็นกลไก (spec §9.3)
- purge job ต้อง idempotent + resumable + นับจำนวนต่อตาราง
- ผลิตหลักฐานครบ 6 ชิ้นพร้อม SHA-256 จริง

### D5.4 จดหมายแจ้งผล

- ธง `selfExecuted` และ `cooldownWaived` + เหตุผล ต้องปรากฏ
- ข้อจำกัดตาม spec §10 (backup / processor / นาฬิกา B) ต้องเขียนตามจริง
- ห้ามใช้คำว่า "ลบถาวรทั้งหมด" เว้นแต่หลักฐานรองรับขอบเขตนั้นจริง

### จุดที่ต้องระวัง

- ห้ามลด `system.data_rights.manage` จาก CRITICAL
- ห้ามปิด `assertExecutionEvidence()` หรือ `assertRetentionDatesCurrent()`
- เคสแรกจะจบที่ `COMPLETED_WITH_EXCEPTION` เพราะ `PROCESSOR_CONFIRMATION` ยังไม่ครบ (spec §9.4)
  — ไม่ใช่บั๊ก ต้องเขียนจดหมายตามนั้น

### Gate

- [ ] แอดมินคนเดียวพาเคสจาก `RECEIVED` ถึง `COMPLETED_WITH_EXCEPTION` ได้จบ
- [ ] E1/E2/E4/E4' ปฏิเสธถูกต้องทุกกรณี (ทดสอบทั้งทางผ่านและทางไม่ผ่าน)
- [ ] ธง `selfExecuted` / `cooldownWaived` ปรากฏถึงจดหมาย
- [ ] purge job รันซ้ำได้ผลเดิม และขาดกลางคันแล้วรันต่อได้
- [ ] รายงาน "หลัง" เทียบ "ก่อน" แล้วชี้ได้ว่าอะไรถูกลบ อะไรเก็บต่อและเพราะอะไร
- [ ] `assertExecutionEvidence` ยังปฏิเสธ sha256 ปลอม

## ลำดับที่แนะนำ

```
D1 ─┬─→ D3 ──→ D4 ──→ D5
D2 ─┘
```

- D1 และ D2 ขนานกันได้ ไม่ชนกัน
- D3 ต้องมาก่อน D4 เพราะ `ExpenseSubstituteReceiptEvidence` ต้องมีนาฬิกาคุมก่อนเปลี่ยนเป็น Cascade
- D4 ต้องมาก่อน D5 เพราะ executor ลบไม่สำเร็จถ้า FK ยังบล็อก
- D5 ทำท้ายสุด และไม่ด่วน — ไม่มีเคสค้าง และเส้นทาง "ไม่มีคำร้อง" เลื่อนไปอีกหลายปี

**แต่ต้องตัดสิน Q1–Q4 ก่อนอีเมลคำร้องฉบับแรกเข้ามา ไม่ใช่หลัง** เพราะนาฬิกา 90 วัน
เริ่มเดินตั้งแต่วินาทีที่ลูกค้ากดส่ง ไม่ใช่ตอนที่เราเปิดเคส
