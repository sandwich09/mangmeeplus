## ลำดับงาน

### รอบ 1 — โครงข้อมูล สัญญา และรายการบัญชีที่บันทึกไว้ (API)

- [ ] Migration และ Prisma schema: `MemberSavedPayoutAccount`, `holderType`/`holderNote` บน `ReimbursementPayoutDestination`, CHECK และ trigger ตรึงแถว (spec §7)
- [ ] สัญญาใน `packages/contracts`: ชนิดข้อมูลของทั้งงาน (รายการที่บันทึกไว้ รูปแบบ payout ใหม่ ช่องเจ้าของบัญชีบนสรุปทุกแบบ การยอมรับของผู้อนุมัติ) ตัวตรวจรูปแบบ และถ้อยคำกลาง (spec §6)
- [ ] กติกา fingerprint ของบัญชีบุคคลอื่น (spec §5.1)
- [ ] คำสั่งรายการที่บันทึกไว้: ดู เพิ่ม ลบ เปิดดูเลขเต็ม ตั้งเป็นบัญชีประจำ พร้อม audit (spec §4, §8)
- [ ] test: กติกา (unit) คำสั่ง (use case) รูปแบบ DTO และ real-PostgreSQL สำหรับ unique, CHECK, trigger และการสลับบัญชีประจำ

ตรวจรับ: AC1, AC2, AC3, AC6 (ส่วนรายการ)

### รอบ 2 — ใบเบิก การอนุมัติ การจ่าย และรอบแก้บัญชี (API)

- [ ] ร่าง: `SAVED`, ช่องเจ้าของบัญชีของ `SPECIFIED`, `saveForLater`, กติกาผู้จัดทำแทน และข้อความแจ้งผู้เบิก (spec §5.2)
- [ ] ส่ง: ต้องมีผู้อนุมัติเสมอสำหรับบัญชีบุคคลอื่น ตรึงเหตุผลใน policy snapshot ยืนยันใต้ล็อก (spec §5.3)
- [ ] อนุมัติ: การยอมรับบัญชีบุคคลอื่น และ audit (spec §5.4)
- [ ] รอบแก้บัญชี: `SAVED`, ช่องเจ้าของบัญชี, ข้อห้ามของใบที่ไม่มีขั้นอนุมัติ (spec §5.6)
- [ ] รายละเอียดใบ ประวัติบัญชี บัญชีของรายการจ่าย ใบพิมพ์ แจ้งเตือน และคำตอบ LINE แสดงบัญชีบุคคลอื่น (spec §6)
- [ ] ข้อป้องกันของคำสั่งบันทึกจ่าย: สกุลเงิน และรหัสบัญชีบริษัท (spec §9) และรายงานผลตรวจ F08
- [ ] test รวม real-PostgreSQL ของการส่งและการอนุมัติ

ตรวจรับ: AC4, AC5, AC7–AC12, AC14–AC16

## สิ่งที่ต้องระวัง

- ห้ามให้เส้นทางใดอ่านบัญชีที่บันทึกไว้แทนบัญชีประจำโดยไม่ตั้งใจ: บัญชีที่บันทึกไว้เข้าใบได้ทางเดียวคือผู้เบิกเลือกเอง
- เลขบัญชีเต็มและคำอธิบายของบัญชีบุคคลอื่นไม่เข้า audit metadata, log, แจ้งเตือน, LINE หรือผลลัพธ์เครื่องมือ AI
- hash ของใบเดิมต้องไม่เปลี่ยน: แถว `SELF` ใช้ fingerprint สูตรเดิม และ policy snapshot ของใบเดิมไม่ถูกแตะ
- trigger ตรึงแถวต้องคลุมช่องใหม่ มิฉะนั้นคำอธิบายแก้ได้หลังอนุมัติ
