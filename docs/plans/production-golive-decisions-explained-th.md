## D1 — `db.t4g.micro` คืออะไร และ upgrade แล้วได้อะไร

### ชื่อนี้อ่านยังไง

`db.t4g.micro` แยกเป็น 4 ส่วน:

| ส่วน | ความหมาย |
| --- | --- |
| `db` | เป็นเครื่องของ RDS (บริการฐานข้อมูลที่ AWS ดูแลให้) ไม่ใช่ EC2 ธรรมดา |
| `t` | ตระกูล **burstable** — จุดสำคัญที่สุด อธิบายข้างล่าง |
| `4g` | รุ่นที่ 4, `g` = ชิป Graviton (ARM ของ AWS) ถูกกว่าและประหยัดไฟกว่า Intel |
| `micro` | ขนาดเล็กสุดในตระกูล |

### "Burstable" คืออะไร และทำไมมันอันตรายกับ production

เครื่องตระกูล `t` **ไม่ได้ให้ CPU เต็มที่ตลอดเวลา** มันทำงานแบบระบบแต้ม:

- เครื่องได้ **CPU พื้นฐาน (baseline) แค่ 10%** ของกำลังจริง
- ถ้าใช้ต่ำกว่า baseline → **สะสมแต้ม (CPU credit)** ได้ 12 แต้ม/ชั่วโมง เก็บได้สูงสุด 288 แต้ม
- ถ้าต้องใช้เกิน baseline → **จ่ายแต้มที่สะสมไว้** เพื่อวิ่งเร็วขึ้นชั่วคราว
- **ถ้าแต้มหมด → ถูกบีบลงเหลือ 10% ทันที**

ปัญหาคือ **แต้มจะหมดตอนที่คุณต้องการมันที่สุด** — ตอนที่ traffic เยอะผิดปกติ หรือตอนสิ้นเดือน
ที่ทุกบริษัทปิดบัญชีพร้อมกัน พอแต้มหมดปุ๊บ database ช้าลง 10 เท่าทันที ทุก request ช้าตาม
ทุก worker ค้าง ทุก user เห็นหน้าหมุน **พร้อมกันหมด** ไม่ใช่แค่คนที่ใช้หนัก

มีข้อควรระวังเพิ่ม: **CPU credit ของ t4g ไม่ถูกส่งเข้า CloudWatch** (bug ที่ AWS รับทราบแล้ว)
แปลว่าคุณอาจ **มองไม่เห็นด้วยซ้ำว่าแต้มกำลังจะหมด** จนกว่าจะช้าไปแล้ว

### `micro` ให้อะไรบ้าง และข้อจำกัดที่จะเจอจริง

| สเปก | `t4g.micro` | ผลกระทบจริง |
| --- | --- | --- |
| RAM | **1 GiB** | นี่คือตัวคุมทุกอย่าง |
| `max_connections` | **≈ 112** (สูตร RDS: `RAM / 9,531,392`) | เพดานจำนวนการเชื่อมต่อพร้อมกัน |
| Cache ในหน่วยความจำ | เล็กมาก | ข้อมูลไม่ค่อยอยู่ใน RAM → ต้องอ่านจากดิสก์บ่อย → ช้า |
| CPU baseline | 10% | ตามที่อธิบายข้างบน |

**ทำไม 112 connection ถึงน้อย** — ไม่ใช่ "รับ 112 คนพร้อมกัน" แต่เป็น "รับ 112 ท่อพร้อมกัน"
และแต่ละ service เปิดท่อค้างไว้เป็นชุด (connection pool) ไม่ได้เปิด-ปิดตามคน งบของเราจะเป็นแบบนี้:

```
api-web        2 task × pool     = ?
ai-gateway     1 task × pool     = ?
workers        1 task × pool     = ?
release task   ตอน deploy         = ~5
A5 evidence    ตอนรัน            = 8   (ตั้งไว้ตายตัวในโค้ด)
support view                      = 4
support execute                   = 2
```

**ปัญหาคือเครื่องหมาย `?`** — ตอนนี้ `DATABASE_URL` ไม่ได้ตั้ง `connection_limit` เลย
Prisma จึงคำนวณเอง (`จำนวน CPU × 2 + 1`) และ **บน Fargate มันอ่านจำนวน CPU ของเครื่องแม่
ไม่ใช่ของ container เรา** ซึ่งอาจเป็น 8, 16 หรือมากกว่า → pool ใหญ่กว่าที่คิดหลายเท่า

อาการเวลาชนเพดานคือ **error ที่ดูไม่เกี่ยวกันเลย** — บาง request 500, บาง worker ค้าง,
login บ้างไม่ได้บ้าง — เพราะแต่ละตัวแย่ง connection กัน ไม่ใช่ error เดียวชัด ๆ ที่ไล่ตามได้ง่าย

### ทางเลือกในการ upgrade

| รุ่น | RAM | `max_connections` โดยประมาณ | ราคาโดยประมาณ/เดือน | หมายเหตุ |
| --- | --- | --- | --- | --- |
| `db.t4g.micro` (ปัจจุบัน) | 1 GiB | ~112 | ~$12 | เสี่ยงตามที่อธิบาย |
| `db.t4g.small` | 2 GiB | ~225 | ~$23 | **ขั้นต่ำที่ผมแนะนำ** |
| `db.t4g.medium` | 4 GiB | ~450 | ~$47 | สบายใจได้จริง |
| `db.m7g.large` | 8 GiB | ~900 | ~$120+ | ไม่ใช่ burstable — CPU เต็มตลอด ไม่มีเรื่องแต้ม |

**หมายเหตุ:** ราคาข้างบนยัง **ไม่รวม Multi-AZ ซึ่งคูณสอง** (ดู D3)

### เรื่องที่ประหยัดกว่าและได้ผลมากกว่าการ upgrade เครื่อง

**เปลี่ยน storage จาก gp2 เป็น gp3** — นี่คือของฟรีที่ควรทำไม่ว่าจะตัดสินใจ D1 ยังไง:

| | gp2 (ปัจจุบัน) | gp3 |
| --- | --- | --- |
| IOPS ที่ 20 GB | 3 IOPS ต่อ GB ขั้นต่ำ **100 IOPS** | **3,000 IOPS** คงที่ ไม่ขึ้นกับขนาด |
| Throughput | ผูกกับขนาด | 125 MiB/s |
| ราคา | แพงกว่า | **ถูกกว่าราว 20%** |

**100 → 3,000 IOPS คือ 30 เท่า และจ่ายน้อยลง** IOPS คือจำนวนครั้งที่อ่าน/เขียนดิสก์ได้ต่อวินาที
ที่ 100 IOPS ระบบบัญชีที่ต้องอ่านหลายตารางต่อหนึ่งหน้าจอจะติดคอขวดที่ดิสก์ตั้งแต่มี user ไม่กี่คน

### สรุปข้อเสนอสำหรับ D1

1. **เปลี่ยน gp2 → gp3 แน่นอน** (เร็ว ถูกลง ได้ 30 เท่า ไม่มีข้อเสีย)
2. **Upgrade เป็น `db.t4g.small` เป็นอย่างน้อย** ถ้ารับ `medium` ได้จะสบายใจกว่ามาก
3. **ตั้ง `connection_limit` ให้ทุก service อย่างชัดเจน** — ข้อนี้ **สำคัญกว่าการ upgrade เครื่องอีก**
   เพราะ upgrade แล้วแต่ pool ยังคำนวณเองผิด ๆ ก็ชนเพดานอยู่ดี
4. ทำทั้งหมดใน W1 ตอนที่ยังไม่มี user เพราะการเปลี่ยน instance class ต้อง restart/failover

## D2 — `SECURITY_ALERT_TOPIC_ARN` ต้องใช้อะไรบ้าง

> คุณตอบว่า: **คนจริงคือคุณเอง**

### SNS Topic คืออะไร

คิดว่าเป็น **"กลุ่มไลน์สำหรับเครื่องจักร"** — ระบบเฝ้าระวัง (CloudWatch Alarm) จะโยนข้อความ
เข้ากลุ่มนี้ แล้วทุกคนที่ subscribe กลุ่มไว้จะได้รับ `ARN` คือเลขที่อยู่ของกลุ่มนั้น หน้าตาแบบ:

```
arn:aws:sns:ap-southeast-1:311414082667:watchdog-bms-production-security-alerts
```

`deploy.sh` ต้องได้ค่านี้ ไม่งั้น **มันจะหยุดก่อนจะเริ่ม deploy เลย** — ไม่ใช่เตือน แต่หยุด
เพราะระบบตั้งใจไม่ให้มี production ที่ไม่มีใครเฝ้า

### ต้องทำอะไรบ้าง

**1. สร้าง topic**
```bash
aws sns create-topic --name watchdog-bms-production-security-alerts --region ap-southeast-1
```

**2. Subscribe อีเมลของคุณ**
```bash
aws sns subscribe --topic-arn <arn ที่ได้จากข้อ 1> \
  --protocol email --notification-endpoint thawatchai.phuchana@gmail.com
```
AWS จะส่งเมล **ยืนยัน** มา ต้องกดลิงก์ในเมลนั้นก่อน ไม่งั้น subscription จะค้างที่
`PendingConfirmation` และ **จะไม่ได้รับ alert เลยทั้งที่ดูเหมือนตั้งค่าแล้ว** — จุดพลาดที่เจอบ่อยที่สุด

**3. เช็ค spam folder** — เมลจาก SNS โดน Gmail จัดเข้า spam ได้ ให้ mark ว่าไม่ใช่ spam
และเพิ่ม `no-reply@sns.amazonaws.com` เข้า contact

### ทำไมอีเมลอย่างเดียวไม่พอ

ปัญหาที่จะเกิดจริงคือ: alarm ดังตอนตีสอง คุณหลับ เห็นเมลตอนเก้าโมงเช้า ระบบล่มไปแล้ว 7 ชั่วโมง
อีเมลเป็น "ช่องบันทึก" ที่ดี แต่เป็น "ช่องปลุก" ที่แย่

ผมแนะนำ **สองชั้น**:

| ชั้น | ช่องทาง | ใช้กับ |
| --- | --- | --- |
| ปลุก | **SMS** (SNS protocol `sms`) หรือแอปที่เด้ง notification | CRITICAL เท่านั้น — เรื่องที่ต้องลุกจากเตียง |
| บันทึก | อีเมล | ทุกอย่าง รวม HIGH ที่รอเช้าได้ |

**อย่าเอา LINE เป็นช่องทางหลัก** ถึงแม้ระบบนี้จะต่อ LINE OA อยู่แล้ว เพราะถ้าระบบล่ม
ช่องทางแจ้งเตือนที่พึ่งระบบตัวเองจะล่มไปด้วย ต้องใช้ช่องทางที่ **ไม่ขึ้นกับระบบที่กำลังเฝ้า**

### เรื่องที่คนมองข้าม — alert fatigue

ถ้าทุกอย่างส่งหาคุณ ภายในสองสัปดาห์คุณจะเลิกอ่าน แล้วตอนที่มีเรื่องจริงคุณจะพลาด
ตั้งแต่วันแรกให้แยก **CRITICAL** (ปลุก) กับ **HIGH** (รอเช้าได้) ให้ชัด และถ้ามี alert
ตัวไหนดังบ่อยจนน่ารำคาญ ให้ **แก้ต้นเหตุหรือปรับ threshold** อย่าปิดมันทิ้ง

### M-16 ไม่ได้ขอแค่ ARN

ข้อนี้ปิดไม่ได้ด้วยการตั้งค่าอย่างเดียว runbook ระบุว่าต้องพิสูจน์ **ทั้งสาย**:

```
ยิง synthetic event  →  เข้า CloudWatch log  →  alarm เปลี่ยนสถานะ
                     →  SNS ส่งออก           →  คุณได้รับจริง
                     →  คุณตอบรับและบันทึกว่าได้รับ (acknowledgement)
```

ขั้นสุดท้ายสำคัญ: ต้องมี **บันทึกว่าคนชื่อนี้ได้รับตอนกี่โมง** ไม่ใช่แค่ "ส่งออกจาก AWS แล้ว"
เพราะเป้าหมายคือพิสูจน์ว่าถ้าเกิดเรื่องจริง **มีคนรู้** ไม่ใช่ว่ามีท่อ

## D3 — Redis two-node + RDS Multi-AZ + backup 35 วัน

### สามอย่างนี้แต่ละอย่างคืออะไร

#### 1. Redis two-node replication group

**Redis คืออะไรในระบบนี้:** เป็นหน่วยความจำร่วมที่เก็บของที่ต้องเร็วและใช้ร่วมกันหลาย service:
- **คิวงาน (BullMQ)** — งานที่รอประมวลผล เช่น อ่าน OCR ใบเสร็จ, ส่ง notification
- **ตัวนับ rate limit** — กันคนยิง API รัว ๆ
- **replay store ของ M-01** — กันการใช้ token ซ้ำในระบบ AI

**"two-node replication group" คือ:** มีเครื่องหลัก (primary) + เครื่องสำรอง (replica)
ที่คนละ Availability Zone (คนละอาคาร data center) ข้อมูลถูกคัดลอกไปเครื่องสำรองตลอดเวลา
ถ้าเครื่องหลักตาย ระบบสลับไปใช้เครื่องสำรองเองอัตโนมัติภายในไม่กี่นาที

**ถ้าไม่มี (เครื่องเดียว) แล้วเครื่องตาย:**
- งานในคิวที่ยังไม่เสร็จ **หายหมด** — ใบเสร็จที่ user อัปโหลดแล้วรอ OCR จะไม่มีวันได้ผล
- rate limit หยุดทำงาน
- M-01 replay store หาย → ระบบ **fail closed** (ออกแบบมาดี) แปลว่าฟีเจอร์ AI หยุดทำงาน
  ไม่ใช่เปิดช่องโหว่ — แต่ user จะใช้ AI ไม่ได้เลยจนกว่าจะกู้เสร็จ

**ราคา:** cache.t4g.micro สองเครื่อง ≈ $26/เดือน (จากเดิม $0 เพราะตอนนี้ไม่มีเลย)

#### 2. RDS Multi-AZ

**คือ:** มี database สำรองอีกตัวที่คนละอาคาร data center ข้อมูลถูกเขียนลงทั้งสองที่
**พร้อมกันแบบ synchronous** (ไม่ใช่ตามหลัง) ถ้าตัวหลักตาย AWS สลับให้เองใน ~60–120 วินาที
โดยที่ endpoint (ที่อยู่ที่แอปเชื่อมต่อ) **ไม่เปลี่ยน**

**ถ้าไม่มี แล้วเครื่องตาย:** ต้อง restore จาก backup ซึ่งใช้เวลา **หลายชั่วโมง** และ
**ข้อมูลตั้งแต่ backup ล่าสุดถึงตอนตายหายไป** — สำหรับระบบบัญชีคือรายการที่ลูกค้าคีย์ไปแล้ว
หายจริง ๆ และไม่มีใครจำได้ว่าคีย์อะไรไปบ้าง

**ราคา:** **คูณสองที่ค่าเครื่อง + คูณสองที่ค่า storage** ถ้าอยู่ที่ `t4g.small` = จาก ~$23 เป็น ~$46

#### 3. Backup 35 วัน

**คือ:** RDS เก็บ snapshot อัตโนมัติ + transaction log ทำให้ย้อนกลับไป **จุดเวลาใดก็ได้**
ในช่วง 35 วันที่ผ่านมา (เรียกว่า Point-in-Time Recovery)

**ทำไมต้อง 35 วัน ไม่ใช่ 7 วันแบบตอนนี้:** ความเสียหายบางแบบ **ไม่ถูกค้นพบทันที** เช่น
bug ที่คำนวณ VAT ผิดตั้งแต่ต้นเดือน อาจถูกพบตอนปิดงบสิ้นเดือน ถ้า backup มีแค่ 7 วัน
ตอนที่รู้ตัวคือ **ย้อนกลับไม่ได้แล้ว** 35 วันครอบคลุมหนึ่งรอบบัญชีเต็ม ๆ ซึ่งเป็นจังหวะที่
ระบบบัญชีมักเจอความผิดพลาด

**ราคา:** ถูกที่สุดในสามข้อ — AWS ให้ backup ฟรีเท่าขนาด database ส่วนเกินคิดตาม GB
database 20 GB จ่ายเพิ่มไม่กี่ดอลลาร์

### ทำไมเลือกทำแค่บางข้อไม่ได้

`infra/security/verify-production-security-baseline.sh` เป็น **fail-closed** — มันตรวจครบทุกข้อ
ขาดข้อเดียวก็ไม่ผ่าน ไม่มีโหมด "ผ่านบางส่วน" เพราะฉะนั้นมีแค่สองทาง:

| ทาง | ทำอะไร | ผลที่ตามมา |
| --- | --- | --- |
| **(A)** ทำครบทั้งสาม | จ่ายเพิ่มตามข้างบน | ผ่าน baseline, M-17 ปิดได้ |
| **(B)** แก้ normative baseline | เขียนเอกสารยอมรับความเสี่ยงอย่างเป็นทางการ + แก้ verifier | ประหยัดเงิน แต่ต้องมีลายลักษณ์อักษรว่าใครยอมรับความเสี่ยงอะไร |

**ห้ามทางที่สาม** คือปิด verifier ทิ้งหรือแก้ให้ผ่านโดยไม่บันทึก — เพราะจากนั้นไปคุณจะไม่รู้อีกเลย
ว่าอะไรคือมาตรฐานจริงของระบบ และ evidence chain ทั้งหมดจะไร้ความหมาย

### ข้อเสนอของผม

**เลือกทาง (A) ทำครบทั้งสาม** ด้วยเหตุผลที่ไม่ใช่เรื่องเทคนิค:

ระบบนี้เก็บ **ข้อมูลบัญชีและภาษีของธุรกิจจริง** ถ้าข้อมูลหายหนึ่งวัน ลูกค้า **คีย์กลับไม่ได้**
เพราะเขาไม่ได้เก็บกระดาษไว้ทุกใบ และบางรายการมาจาก LINE/OCR ที่ต้นทางก็ไม่มีแล้ว
นี่ต่างจากเว็บทั่วไปที่ข้อมูลหายแล้วให้ user กรอกใหม่ได้

**ค่าใช้จ่ายเพิ่มรวมโดยประมาณ ~$50–70/เดือน** (Redis ~$26 + Multi-AZ ~$23 + backup ไม่กี่ดอลลาร์)
เทียบกับความเสียหายจากการสูญเสียข้อมูลบัญชีลูกค้าหนึ่งครั้ง — ไม่ต้องคำนวณก็ตอบได้

**ถ้างบตึงจริง ๆ** ลำดับความสำคัญคือ:
1. **Backup 35 วัน** — ถูกที่สุด คุ้มที่สุด ทำก่อนเลย
2. **RDS Multi-AZ** — ข้อมูลบัญชีอยู่ที่นี่
3. **Redis two-node** — งานในคิวหายเจ็บ แต่กู้ได้ด้วยการให้ user ทำซ้ำ

แต่ย้ำว่าเลือกไม่ครบ = ต้องไปทาง (B) ซึ่งต้องเขียนเอกสารยอมรับความเสี่ยง

### H-14 — ทำ internal service ให้เป็น private และห้ามปลอมสิทธิ์ OWNER

**ปัญหาเดิม:** `api-web`, `ai-gateway`, `workers` ทั้งสามตัวอยู่บน **public subnet** และเปิด
public endpoint ส่วน internal route ระหว่าง service ป้องกันด้วย **รหัสลับตายตัวหนึ่งตัว**
(`WORKER_INTERNAL_TOKEN`) ที่แย่กว่านั้นคือ worker เคย **สร้าง context ว่าเป็น OWNER**
จาก `companyId` ที่ผู้เรียกส่งมาเอง

**อันตรายยังไง:** ถ้ารหัสลับหลุด คนที่ได้ไปสามารถเรียก internal route จากอินเทอร์เน็ตได้
แล้วบอกว่า "ฉันคือ OWNER ของบริษัท X" → อ่านข้อมูลบริษัทไหนก็ได้

**สถานะจริง:** ✅ **ครึ่งที่อันตรายที่สุดปิดแล้ว 2026-07-19**
- worker เลิกสร้าง `roles:['OWNER']` เปลี่ยนเป็น `systemWorkerContext()` ที่ `roles:[]`
- ทุก internal route ตรวจ token แบบ constant-time และ fail-closed
- `companyId` ถูก validate ผ่าน `assertActiveCompany()` ก่อนแตะ DB
- ทดสอบผ่านหมด: full API suite 2166/2166

**ที่ค้าง:** ย้าย workers + ai-gateway ไป private subnet, ปิด public endpoint เดิม,
หมุนรหัสลับใหม่, ตั้ง egress allowlist

**Impact ถ้ายังไม่ทำ:** endpoint ยังโผล่บนอินเทอร์เน็ต แต่คนที่ได้รหัสลับไปทำได้แค่
เรียก route ที่ตรวจสิทธิ์แล้ว **ทำไม่ได้แล้วคือปลอมเป็น OWNER** ความรุนแรงลดจาก
"อ่านข้อมูลทุกบริษัทได้" เหลือ "เรียก internal API ที่ตรวจสิทธิ์แล้วได้"

**หมายเหตุสำคัญ:** การย้ายไป private subnet **ต้องมี NAT gateway ก่อน** ซึ่งเพิ่งถูกลบไป
(ประหยัด $47.55/เดือน) → ข้อนี้ผูกกับ D5 โดยตรง

**ข้อเสนอ:** 🟡 **ไม่บล็อก launch** ถ้าทำสามอย่างนี้ก่อน — หมุน token ใหม่ให้ยาวและสุ่มจริง,
ตั้ง alarm บน 401 ของ internal route, และกำหนดวันทำ cutover ให้ชัด (ไม่ใช่ "ไว้ก่อน")

### M-01 — ผูกการเรียก AI กับสิทธิ์ของผู้ใช้จริง

**ปัญหาเดิม:** เวลา AI Gateway เรียก API ของ ERP มันบอกเองว่า "ทำแทน user คนนี้ บริษัทนี้"
โดยมีแค่รหัสลับร่วมยืนยันว่า *เป็น service ที่ถูกต้อง* แต่ **ไม่มีอะไรพิสูจน์ว่าได้รับ
มอบอำนาจจาก user คนนั้นจริง**

**อันตรายยังไง:** ถ้า AI Gateway ถูกยึด หรือมี bug ที่ทำให้เลือก user ผิด มันขอข้อมูลของ
user ไหนก็ได้ในบริษัทไหนก็ได้ — เป็นการข้ามระบบสิทธิ์ทั้งชุด

**สถานะจริง:** ✅ **โค้ดเสร็จและทดสอบครบ 2026-07-25**
- API ออก **token มอบอำนาจ** (HMAC-SHA256) อายุ **120 วินาที ใช้ได้ครั้งเดียว**
  ผูกกับ user/company/membership/request/tool เฉพาะเจาะจง
- ERP ตรวจ token + กันใช้ซ้ำผ่าน Redis + **ตรวจสิทธิ์ปัจจุบันใหม่อีกรอบ** ไม่เชื่อ token อย่างเดียว
- กุญแจเซ็นอยู่แค่ใน API **ไม่ถูกส่งเข้า AI Gateway/AgentCore เลย**
- ทดสอบผ่าน: focused API 13/13, AI boundary 53/53, full API 2172/2172, AI Gateway 417/417

**ที่ค้าง:** deploy แล้วรันเทสเชิงลบ (substitution, replay, cross-company, Redis ล่ม) บนของจริง

**Impact ถ้ายังไม่ทำ:** โค้ดที่ปลอดภัยจะถูก deploy ไปพร้อม release อยู่แล้ว — **การ deploy
คือการปิดช่องโหว่ไปแล้ว 90%** ที่ขาดคือ *หลักฐาน* ว่ามันทำงานบน production จริง

**ข้อเสนอ:** 🟡 **ไม่บล็อก launch แต่มีเงื่อนไข** — ถ้าเปิดฟีเจอร์ LINE AI ให้ลูกค้าตั้งแต่วันแรก
ควรเก็บหลักฐานให้ครบก่อน ทางที่ปลอดภัยและง่ายกว่าคือ **launch โดยปิด AI tool ไว้ก่อน**
ผ่าน feature launch gate แล้วค่อยเก็บหลักฐาน M-01 แล้วค่อยเปิด — ระบบรองรับการเปิดทีละแถวอยู่แล้ว

### M-16 — log retention, alert และเจ้าของ

**ปัญหาเดิม:** log group ทั้ง 7 ตัว **ไม่มีการตั้งอายุ** (เก็บตลอดกาล = จ่ายตลอดกาล)
alarm ที่มี 3 ตัวเป็น rollback alarm ของ deploy ล้วน ๆ และ **ไม่มี alarm ตัวไหนส่งแจ้งเตือนใครเลย**

**อันตรายยังไง:** ไม่ใช่ช่องโหว่ แต่คือ **การบินโดยไม่มีเครื่องวัด** เกิดอะไรขึ้นก็ไม่มีใครรู้
จนกว่าลูกค้าจะโทรมา และเมื่อรู้แล้วก็สืบสวนย้อนหลังไม่ได้ถ้า log ถูกลบไปแล้ว

**สถานะจริง:** ✅ โค้ดเสร็จ 2026-07-28 — deploy บังคับ retention 90 วัน + KMS + alert topic,
สร้าง metric filter/alarm สำหรับ HIGH/CRITICAL, และเหตุการณ์สำคัญ (auth abuse, AI failure,
erasure failure, malware quarantine) ยิง structured event แล้ว

**ที่ค้าง:** สร้าง KMS key + SNS topic จริงบน AWS แล้วพิสูจน์ทั้งสาย (ดู D2)

**Impact ถ้ายังไม่ทำ:** 🔴 **deploy ไม่ได้เลย** — `deploy.sh` ตรวจ `LOG_KMS_KEY_ID` และ
`SECURITY_ALERT_TOPIC_ARN` **ก่อนเริ่ม rollout** ไม่มีค่า = หยุดทันที ไม่ใช่คำเตือน

**ข้อเสนอ:** 🔴 **บล็อก launch แน่นอน** และไม่ใช่เพราะนโยบาย แต่เพราะกลไก
อีกอย่าง — คุณ *อยาก* ให้มันบล็อก การเปิดระบบให้ลูกค้าใช้โดยไม่มีใครเฝ้าคือความเสี่ยงจริง

### M-17 — Redis/RDS recovery และการหมุน secret

**ปัญหาเดิม:** Redis หนึ่งเครื่อง ไม่มี TLS ไม่เข้ารหัส ไม่มีรหัสผ่าน ไม่มี snapshot ไม่มีตัวสำรอง;
RDS single-AZ, deletion protection ปิด, backup 7 วัน; secret ทั้ง 7 ตัวไม่มีการหมุนอัตโนมัติ

**อันตรายยังไง:** สองชั้น
1. **ความลับ** — Redis ที่ไม่เข้ารหัสและไม่มีรหัสผ่าน ใครเข้าถึง network ได้ก็อ่านได้หมด
   ซึ่งข้างในมี token, rate-limit state, และข้อมูลของ job
2. **ความอยู่รอด** — ตามที่อธิบายใน D3

**สถานะจริง:** ✅ verifier + runbook + post-restore re-erasure path เสร็จ 2026-07-28
❌ ของจริงบน AWS ยังไม่ทำ และ **Redis production ถูกลบไปแล้วเมื่อ 2026-08-07**

**ที่ค้าง:** สร้าง Redis ใหม่ให้ถูกสเปก, hardening RDS, **ซ้อม restore จริง**, หมุน secret

**Impact ถ้ายังไม่ทำ:**
- 🔴 **Redis: บล็อกแน่นอน** — ไม่มี Redis แอปขึ้นไม่ได้ ไม่ใช่เรื่องความปลอดภัย แต่มันจะพังเฉย ๆ
- 🔴 **RDS config: บล็อกแน่นอน** — verifier fail-closed
- 🟡 **Restore drill: ควรทำใน W4** — ไม่ได้บล็อกทางกลไก แต่ "ไม่เคยลอง restore มาก่อน" ในวันแรก
  ที่ถือข้อมูลบัญชีลูกค้าเป็นความเสี่ยงที่ไม่จำเป็น และตอน W4 คุณ**ยังไม่มี user** จึงเป็นจังหวะที่ดีที่สุด
- 🟢 **Secret rotation: ตามหลังได้**

**ข้อเสนอ:** 🔴 **บล็อกบางส่วน** — แยกเป็นสามชิ้นตามข้างบน

## D5 — Bastion: ทาง (ก) vs (ข)

### Bastion คืออะไร ทำไมต้องมี

Database production **จงใจไม่ให้เชื่อมต่อจากอินเทอร์เน็ต** (`PubliclyAccessible: false`)
ซึ่งถูกต้อง แต่แปลว่า **คุณเองก็เชื่อมต่อไม่ได้เหมือนกัน**

Bastion (บางทีเรียก jump host) คือ **เครื่องเล็ก ๆ ที่อยู่ข้างใน network เดียวกับ database**
คุณเข้าเครื่องนี้ก่อน แล้วจากเครื่องนี้ค่อยต่อไป database เปรียบเหมือน **ห้องรับรองหน้าตึก**
คนนอกเข้าตึกไม่ได้ แต่เข้าห้องรับรองได้ถ้ามีสิทธิ์ แล้วจากห้องรับรองค่อยเข้าตึกได้

**สำคัญ:** เราเข้า bastion ผ่าน **AWS SSM Session Manager** ไม่ใช่ SSH
ต่างกันตรงที่ SSM **ไม่ต้องเปิดพอร์ตรับ connection เลยแม้แต่พอร์ตเดียว** — agent บนเครื่อง
เป็นฝ่าย **โทรออก** ไปหา AWS แล้ว AWS ส่งคำสั่งกลับมาตามสายที่เครื่องเปิดไว้เอง
ผลคือ **ไม่มีอะไรจากอินเทอร์เน็ตเชื่อมเข้าเครื่องได้** และทุก session ถูกบันทึกใน CloudTrail

### เปรียบเทียบสองทาง

| | **(ก) public subnet + public IP** | **(ข) private subnet + VPC endpoint** |
| --- | --- | --- |
| เครื่องมี public IP ไหม | **มี** | **ไม่มี** |
| เปิดพอร์ตรับ connection ไหม | ไม่เปิด (SG ไม่มี inbound rule) | ไม่เปิด |
| agent ออกเน็ตยังไง | ผ่าน Internet Gateway | ผ่าน VPC endpoint (ไม่ออกเน็ตเลย) |
| ราคา/เดือน | **~$7.43** (แค่ค่าเครื่อง) | **~$7.43 + ~$44** = ~$51 |
| ถ้ามีคนเผลอเพิ่ม inbound rule | **โดนทันที** — เครื่องเข้าถึงได้จากทั้งโลก | **ไม่มีอะไรเกิดขึ้น** — ไม่มีเส้นทางจากอินเทอร์เน็ตอยู่แล้ว |
| โผล่ใน internet-wide scan ไหม | **โผล่** (Shodan/Censys เห็น IP) | ไม่โผล่ |

### ประเด็นสำคัญที่ทำให้ตัดสินง่ายขึ้น

**(ก) ปลอดภัยพอในทางทฤษฎี** — SG ที่ไม่มี inbound rule เลยคือกำแพงที่แข็งจริง ไม่ใช่แค่ดูดี

**แต่ (ข) ปลอดภัยกว่าในทางปฏิบัติ** เพราะมันกันความผิดพลาดของคน:
- ทาง (ก) ความปลอดภัยขึ้นกับ "ต้องไม่มีใครเพิ่ม inbound rule" ซึ่งเป็นสัญญาที่ต้องรักษาตลอดไป
  และวันหนึ่งจะมีคน (อาจเป็นคุณเองตอนดึก ๆ) เพิ่มเข้าไป "ชั่วคราว" แล้วลืมลบ
- ทาง (ข) ต่อให้เพิ่ม rule ก็ไม่มีผล เพราะ **ไม่มีเส้นทางจากอินเทอร์เน็ตมาถึงตั้งแต่แรก**

หลักการนี้เรียกว่า **ทำให้สถานะที่ผิดเป็นไปไม่ได้** ดีกว่าทำให้สถานะที่ผิดถูกห้าม

### จุดที่ทำให้เรื่องนี้ผูกกับ D4/H-14

**H-14 ต้องการให้ workers + ai-gateway ย้ายไป private subnet** ซึ่งจะทำให้
**ต้องมี NAT gateway หรือ VPC endpoint อยู่ดี** (~$47.55/เดือนสำหรับ NAT)

แปลว่า:
- **ถ้าตัดสินใจทำ H-14** → คุณจะจ่ายค่าทางออกจาก private subnet อยู่แล้ว
  → bastion ย้ายเข้า private subnet ได้ **แทบฟรี** → ทาง (ข) กลายเป็นตัวเลือกที่ถูกกว่า
- **ถ้ายังไม่ทำ H-14** → ทาง (ข) คือจ่าย $44 เพิ่มเพื่อ bastion ตัวเดียว ซึ่งแพงเมื่อเทียบสัดส่วน

### ข้อเสนอของผม

**เริ่มด้วยทาง (ก) แต่ทำให้เข้มจริง** แล้วย้ายไป (ข) พร้อมกับตอนทำ H-14:

เงื่อนไขของทาง (ก) ที่ต้องทำครบ ไม่ใช่เลือกทำ:
1. Security Group **ไม่มี inbound rule แม้แต่ข้อเดียว** — ตรวจซ้ำหลังตั้งค่า
2. บังคับ **IMDSv2** (กัน SSRF ขโมย credential ของเครื่อง)
3. เปิด **SSM session logging** ไป S3 + CloudWatch (เข้ารหัสด้วย KMS)
4. ตั้ง **alarm เมื่อมีใครเปิด session** — session ที่ไม่ได้นัดหมายต้องมีคนรู้ภายในนาที
5. ตั้ง **AWS Config rule หรือ alarm บน `AuthorizeSecurityGroupIngress`** ของ SG นี้ —
   ถ้ามีใครเพิ่ม inbound rule ต้องดังทันที **ข้อนี้ปิดช่องว่างหลักของทาง (ก)**

ทำครบ 5 ข้อแล้ว ทาง (ก) จะปลอดภัยใกล้เคียง (ข) ที่ราคา 1/7

## D6 — Bastion เปิดค้างหรือดับไว้

### เอาไว้ทำอะไรจริง ๆ

Bastion **ไม่ได้รันอะไรเลย** ไม่เสิร์ฟ traffic ไม่ประมวลผลอะไร มันมีหน้าที่เดียวคือ
**เป็นประตูให้คนเข้าไปคุยกับ database** ใช้ตอน:

1. **T1 VIEW** — ลูกค้าแจ้งว่า "รายการหาย" คุณต้องเข้าไปดูว่าข้อมูลจริงเป็นยังไง
2. **T2 EXECUTE** — เจอแล้วว่าข้อมูลผิดเพราะ bug ต้องแก้ให้ลูกค้าใช้งานต่อได้ก่อนแก้โค้ด
3. **ตรวจก่อน/หลัง deploy** — ดูว่า migration ลงจริงไหม, จำนวนแถวถูกไหม

นอกจากนี้ไม่มีอะไรอีก **ถ้าคุณไม่ได้กำลังแก้ปัญหาอยู่ bastion ก็ไม่มีประโยชน์**

### เปรียบเทียบ

| | ดับไว้ (start เมื่อใช้) | เปิดค้าง |
| --- | --- | --- |
| เวลาก่อนใช้งานได้ | **~90 วินาที** (boot ~50s + SSM agent ลงทะเบียน ~30s) | **~5 วินาที** |
| ราคา/เดือน | ~$0.50 (ค่า EBS อย่างเดียว) | ~$7.43 |
| ประหยัดต่อปี | ~$83 | — |
| เครื่องถูกโจมตีได้ไหมตอนไม่ใช้ | **ไม่ได้** เครื่องดับอยู่ | ได้ในทางทฤษฎี (แต่ต้องผ่าน IAM ก่อน) |
| ขั้นตอนตอนเกิดเหตุ | ต้อง `start-instances` แล้วรอ | ต่อได้เลย |

### ข้อเสนอของผม — **เปิดค้าง**

เหตุผล:

**1. $7.43/เดือนไม่ใช่จำนวนที่ควรเสียเวลาคิด** เทียบกับ 90 วินาทีตอนที่ระบบล่ม
และมีลูกค้ารอ — 90 วินาทีนั้นรู้สึกเหมือน 10 นาที

**2. "ดับไว้แล้วปลอดภัยกว่า" จริงน้อยกว่าที่คิด** ตัวคุมการเข้าถึงจริง ๆ คือ **IAM ไม่ใช่สถานะเปิด/ปิด**
คนที่มีสิทธิ์ `ssm:StartSession` ก็มีสิทธิ์ `ec2:StartInstances` ได้ง่าย ๆ ในทางปฏิบัติ
ดังนั้นเครื่องที่ดับอยู่ไม่ได้กันคนที่มีสิทธิ์แล้ว มันกันแค่คนที่ไม่มีสิทธิ์ซึ่งเข้าไม่ได้อยู่แล้ว

**3. อันตรายจริงคือลืมว่ามันมีอยู่** เครื่องที่เปิดค้างและไม่มีใครดูแลจะกลายเป็นเครื่องที่
patch ไม่ทัน ทางแก้ไม่ใช่การดับมัน แต่คือ **เปิด SSM Patch Manager** ให้ AWS อัปเดตให้เอง

**สิ่งที่ควรทำแทนการดับเครื่อง:**
- เปิด **SSM Patch Manager** ตั้งตารางอัปเดตอัตโนมัติ
- ตั้ง **alarm เมื่อมีใครเปิด session** (ตามที่บอกใน D5)
- **ทบทวนทุกไตรมาส** ว่ายังจำเป็นอยู่ไหม
- ถ้ามีช่วงหยุดยาว (ปีใหม่ สงกรานต์) จะดับด้วยมือก็ได้ ไม่ต้องทำ automation

## D7 — ใครมีสิทธิ์ arm `watchdog_support_rw`

> คุณบอกว่า: **เดี๋ยวน่าจะต้องสร้าง user support**

### ก่อนอื่น — "user" ในเรื่องนี้มีสามแบบ ที่คนสับสนกันบ่อยมาก

| แบบ | คืออะไร | ตัวอย่าง | ใช้ทำอะไร |
| --- | --- | --- | --- |
| **1. AWS IAM identity** | ตัวตนสำหรับเข้า AWS | IAM user / IAM Identity Center | เปิด SSM session, สร้าง token ต่อ RDS |
| **2. PostgreSQL role** | ตัวตน **ข้างในฐานข้อมูล** | `watchdog_support_ro`, `watchdog_support_rw` | กำหนดว่า SQL ที่รันได้ทำอะไรได้บ้าง |
| **3. Application user** | login ในตัวโปรแกรม ERP | user ที่ล็อกอินหน้าเว็บ | ใช้งานระบบตามปกติ |

**สำหรับ support คุณต้องการแบบ 1 และ 2 เท่านั้น**

**⚠️ อย่าสร้างแบบ 3 เป็น "support account" ที่เห็นข้ามบริษัทได้** — ระบบนี้ออกแบบให้ RBAC
ผูกกับบริษัท (company-scoped) การสร้าง user พิเศษที่มองข้ามบริษัทได้จะเป็น
**ปัญหา PDPA ที่ใหญ่กว่าการอ่าน database ตรง ๆ มาก** เพราะมันกลายเป็นสิทธิ์ถาวรที่อยู่ในระบบ
ตลอดเวลา แทนที่จะเป็นการเข้าถึงชั่วคราวที่มีบันทึก และถ้า account นั้นหลุด = ทุกบริษัทหลุด

ถ้าอนาคตจำเป็นต้องมี "support ดูหน้าจอแทนลูกค้าได้" ทางที่ถูกคือ
**impersonation ที่ลูกค้าอนุญาตและมีเวลาจำกัด + audit** ไม่ใช่ account ที่เห็นทุกอย่างตลอดเวลา
(และนั่นเป็นงานคนละก้อน ต้องมี spec แยก)

### เรื่อง "คนที่สอง" — พูดกันตรง ๆ

หลักการ two-person rule มีเหตุผลชัดเจน: **ไม่ให้ใครคนเดียวเขียนทับข้อมูล production
ได้เงียบ ๆ** ไม่ใช่เพราะไม่ไว้ใจ แต่เพราะ (ก) คนเหนื่อยตอนตีสามตัดสินใจพลาดได้
(ข) ถ้ามีข้อพิพาทกับลูกค้าภายหลัง คุณอยากมีหลักฐานว่ามีคนที่สองเห็นด้วย

**แต่ถ้าตอนนี้ทีมมีคนเดียว การบังคับ two-person rule คือละครที่ไม่มีคนดู**
มันจะจบลงที่คุณข้ามขั้นตอนเอง ซึ่งแย่กว่าการไม่มีขั้นตอนเลย เพราะเอกสารจะโกหก

### ทางเลือกจริงสามแบบ

**(a) Two-person เต็มรูปแบบ** — ต้องมีคนที่สองที่ไว้ใจได้และตื่นได้ตอนตีสาม
ควบคุมดีที่สุด แต่ถ้ายังไม่มีคน ก็ยังทำไม่ได้

**(b) คนเดียว + มาตรการชดเชย** — arm เองได้ แต่:
- การ arm **ยิง alarm ทันที** ไปช่องทางที่คุณลบเองไม่ได้ (SNS → email + CloudWatch Logs ที่มี retention)
- **auto-disarm ภายใน 60 นาที** ด้วย EventBridge → Lambda ไม่พึ่งความจำ
- ต้องระบุ `incident_ref` ตอน arm
- **ต้องเขียนสรุปภายใน 24 ชั่วโมง** ลง `docs/agent-memory/<incident>.md`
- ทบทวนทุกครั้ง ไม่มีข้อยกเว้น

**(c) ผ่าน GitHub workflow ที่ต้องอนุมัติ** — repo นี้ **ใช้ pattern นี้อยู่แล้ว**
(`u5-owner-approval.yml`, `production-a5.yml` ที่ใช้ `environment: production`)
ถึงแม้จะกดอนุมัติเอง มันก็สร้าง **หลักฐานถาวร + จังหวะหยุดคิด** ซึ่งมีค่าจริง

### ข้อเสนอของผม — **แบ่งเป็นสองเลน (b) + (c)**

| เลน | ใช้เมื่อ | ทำยังไง | เวลา |
| --- | --- | --- | --- |
| **เลนปกติ** (90% ของเคส) | แก้ข้อมูลที่รอได้ 30 นาที | เขียน SQL เป็นไฟล์ → PR เข้า `main` → GitHub workflow รันเป็น one-off task | ~15–30 นาที |

## D8 — Port-forward vs Shell: ข้อดีข้อเสียเต็ม ๆ

### สองวิธีนี้ต่างกันยังไง

**Port-forward** — SSM สร้าง "อุโมงค์" ให้ `localhost:15432` บนเครื่องคุณ
**กลายเป็น database production จริง ๆ** จากนั้นเปิด DBeaver / TablePlus / pgAdmin
ชี้ไปที่ `localhost:15432` แล้วใช้งานเหมือน database อยู่ในเครื่องตัวเอง

**Shell on bastion** — SSM ให้ **หน้าจอ terminal บน bastion** คุณพิมพ์ `psql` ที่นั่น
แล้วพิมพ์ SQL ในเทอร์มินัล ทุกตัวอักษรที่พิมพ์และทุกบรรทัดที่แสดงผลวิ่งผ่าน SSM

### ตารางเปรียบเทียบเต็ม

| | **Port-forward** | **Shell on bastion** |
| --- | --- | --- |
| ใช้ GUI (DBeaver/TablePlus) | ✅ ได้ | ❌ ไม่ได้ |
| ดูตารางกว้าง ๆ 30 คอลัมน์ | ✅ อ่านง่าย เลื่อนได้ | ⚠️ ต้องใช้ `\x` แสดงแนวตั้ง |
| export ผลเป็น CSV/Excel | ✅ กดปุ่มเดียว | ⚠️ ต้อง `\copy` แล้วดึงไฟล์ออกอีกที |
| autocomplete ชื่อตาราง | ✅ มี | ⚠️ มีบ้าง (psql มี tab completion) |
| เขียน query ยาว ๆ แก้ไปมา | ✅ สบาย | ❌ ลำบาก |
| **บันทึกว่าพิมพ์ SQL อะไร** | ❌ **ไม่มีเลย** | ✅ **ครบทุกตัวอักษร** |
| CloudTrail รู้ว่าใครเปิด session | ✅ รู้ | ✅ รู้ |
| CloudTrail รู้ว่าทำอะไร | ❌ **ไม่รู้** | ✅ รู้ผ่าน transcript ใน S3 |
| ตอบได้ไหมว่า "เคยดูข้อมูลลูกค้า X ไหม" | ❌ **ตอบไม่ได้** | ✅ ตอบได้ |
| ต้องติดตั้งอะไรบนเครื่องตัวเอง | AWS CLI + Session Manager plugin + DB client | AWS CLI + Session Manager plugin |

### ทำไม port-forward ถึงไม่มี transcript

เพราะ SSM มองอุโมงค์เป็น **ท่อส่ง byte ดิบ** มันไม่รู้ว่าข้างในเป็น PostgreSQL protocol
และไม่พยายามตีความ สิ่งที่มันบันทึกคือ "session `xxx` โดย IAM user `yyy`
เปิด 14:32 ปิด 14:48 ไปยัง port 5432 ของ host `zzz`" — **จบแค่นั้น**

ต่างจาก shell session ที่ SSM มองเห็นเป็น **stream ของตัวอักษร** จึงบันทึกลง S3/CloudWatch ได้ทั้งหมด

### แล้ว pgaudit ช่วยได้ไหม

ในทางทฤษฎีได้ แต่มีกับดัก:

- ตั้ง `pgaudit.log = 'read'` ที่ระดับ parameter group → **จะ log ทุก SELECT ของแอปด้วย**
  ซึ่งเป็นหลักหมื่น query ต่อนาที → **ค่า CloudWatch ระเบิด** (ระบบนี้เพิ่งโดน $179
  จาก log ingest เมื่อต้นเดือน — เป็นบทเรียนที่จ่ายไปแล้ว)
- ตั้งเฉพาะ role ด้วย `ALTER ROLE ... SET pgaudit.log` → **ต้องเป็น superuser**
  ซึ่ง RDS ไม่ให้ master user เป็น superuser จริง **ต้องทดสอบว่า `rds_superuser` ทำได้ไหม
  ยังยืนยันไม่ได้** ถ้าทำได้นี่คือทางออกที่ดีที่สุด

**สรุป:** pgaudit เป็นทางเลือกที่ *อาจ* ใช้ได้ แต่ต้องพิสูจน์บน UAT ก่อน อย่าวางแผนโดยสมมติว่าได้

### มุม PDPA — เรื่องนี้ไม่ใช่แค่ "ดีถ้ามี"

PDPA กำหนดให้ data controller มี **มาตรการควบคุมการเข้าถึงข้อมูลส่วนบุคคล** และ
**บันทึกกิจกรรมการประมวลผล** ถ้าวันหนึ่งลูกค้าถามว่า *"มีใครเข้าถึงข้อมูลบริษัทผมบ้าง"*
หรือมีข้อพิพาทว่าข้อมูลถูกแก้โดยใคร:

- **มี transcript** → ตอบได้ตรง ๆ ว่าเข้าถึงอะไร เมื่อไหร่ ด้วยเหตุผลอะไร
- **ไม่มี transcript** → ตอบได้แค่ "มีคนต่อ database ตอน 14:32 นาน 16 นาที"
  ซึ่งในสายตาผู้ตรวจสอบ **ไม่ต่างจากไม่มีอะไรเลย** และจะทำให้ทุกการเข้าถึงในอดีต
  ถูกตั้งคำถามพร้อมกันหมด

โทษปรับตาม PDPA สูงสุด 5 ล้านบาท

### ข้อเสนอของผม — **เริ่มด้วย shell อย่างเดียวทั้ง T1 และ T2**

เหตุผลเชิงกลยุทธ์: **ผ่อนคลายกฎทีหลังทำได้ง่าย บีบกฎทีหลังทำได้ยาก**

ถ้าเริ่มด้วยการอนุญาต port-forward แล้วทุกคนติด DBeaver การกลับมาบอกว่า
"ต่อไปนี้ต้องพิมพ์ในเทอร์มินัล" จะเจอแรงต้านและจะถูกข้ามในที่สุด
แต่ถ้าเริ่มด้วย shell แล้วพบว่าลำบากจริง การอนุญาตเพิ่มเป็นข่าวดีที่ไม่มีใครค้าน

**ทางประนีประนอมถ้า shell ลำบากเกินไปจริง ๆ:**

อนุญาต port-forward **เฉพาะ T1 VIEW** (อ่านอย่างเดียว ไม่มีทางเขียน) โดยต้องเปิดผ่าน
script ที่:
1. บังคับใส่ `incident_ref`
2. เขียน log เข้า CloudWatch ว่า "ใคร เปิดเมื่อไหร่ ทำไม"
3. ตั้งเวลาปิดอัตโนมัติที่ 30 นาที
4. บังคับ `application_name=support:<incident>:<ชื่อ>` ในทุก connection

คุณยังไม่ได้ตัว SQL แต่ได้ **เจตนา + ช่วงเวลา + คนรับผิดชอบ** ซึ่งพอสำหรับ PDPA
ในระดับที่ตอบคำถามได้ว่า "การเข้าถึงครั้งนี้มีเหตุผลอะไรและใครรับผิดชอบ"

**แต่ T2 EXECUTE ต้องเป็น shell เท่านั้น ไม่มีข้อยกเว้น** — การเขียนทับข้อมูล production
โดยไม่มีบันทึกว่าเขียนอะไรเป็นความเสี่ยงที่ไม่ควรยอมรับในระบบที่เก็บข้อมูลบัญชี

## D9 — UAT นับเป็น staging ไหม

> คุณตอบว่า: **มีแค่ 3 env คือ local, UAT, prod**

### คำตอบ: **ใช่ UAT คือ staging rung — และในทางกลไก repo นี้บังคับแบบนั้นอยู่แล้ว**

Spec เขียนว่า `dev/test → staging → production` ซึ่งเป็น 3 ขั้น เรามี `local → UAT → prod`
ซึ่งก็ 3 ขั้นเหมือนกัน — **ตรงกันอยู่แล้ว** ไม่ต้องสร้าง environment ที่สี่

และไม่ใช่แค่ตรงกันบนกระดาษ **`deploy-production.yml` บังคับจริง** — มีขั้นตอน
"Verify signed UAT production acceptance" ที่ดาวน์โหลด artifact `uat-accepted-release-<sha>`
และตรวจลายเซ็น แปลว่า **build เดียวกันเป๊ะต้องผ่าน UAT มาก่อนถึงจะขึ้น production ได้**
นี่คือนิยามของ staging rung ทางเทคนิค

**ข้อเสนอ: บันทึก OPEN-3 เป็น RESOLVED** ว่า UAT คือ staging rung โดยมีเงื่อนไขข้างล่าง

### เงื่อนไขที่ทำให้ UAT "นับเป็น staging ได้จริง"

การมี 3 env ไม่ได้แปลว่ามันทำหน้าที่ staging ได้เอง staging ที่ดีคือ
**การซ้อมใหญ่ที่เหมือนของจริง** ต้องทำ 3 อย่าง:

**1. Config ต้องเหมือนกันในเชิงรูปร่าง**
env key ชุดเดียวกันต้องถูกตั้งครบทั้งสองที่ ถ้าต่างต้องมีรายการที่ตั้งใจให้ต่างและอธิบายได้
กับดักคลาสสิก: prod มี key ตัวหนึ่งที่ UAT ไม่มี → พังเฉพาะบน prod ตอน deploy จริง

**2. Feature launch gate ต้องเปิดชุดเดียวกัน**
ถ้า UAT เปิดทุก gate แต่ prod เปิดครึ่งเดียว การทดสอบบน UAT ไม่ได้พิสูจน์อะไรเกี่ยวกับ prod

**3. อย่าใช้ UAT เป็นถังขยะ**
UAT ที่เต็มไปด้วยบริษัททดสอบชื่อ "aaa" "test123" ยังใช้ทดสอบ *ความถูกต้อง* ได้
แต่ใช้ทดสอบ *สภาพจริง* ไม่ได้ — เพราะ data shape ไม่เหมือน

### สิ่งที่ UAT บอกคุณไม่ได้ (จุดที่ต้องระวังที่สุด)

**UAT พิสูจน์ "ทำงานถูกไหม" แต่พิสูจน์ "ทนได้ไหม" ไม่ได้** เพราะ database ของ UAT เล็ก

สิ่งที่ต้องพิสูจน์จากที่อื่น:

| เรื่อง | UAT บอกได้ไหม | ต้องพิสูจน์จากไหน |
| --- | --- | --- |
| Migration ทำงานถูกไหม | ✅ ได้ | UAT |
| **Migration ใช้เวลานานแค่ไหน** | ❌ **ไม่ได้** | restore clone ที่มีข้อมูลเท่าจริง |
| Query ให้ผลถูกไหม | ✅ ได้ | UAT |
| **Query จะช้าไหมเมื่อมีข้อมูลเยอะ** | ❌ **ไม่ได้** | clone หรือ load test |
| Connection pool พอไหม | ❌ **ไม่ได้** (traffic ต่างกัน) | คำนวณ + เฝ้าดูจริง (ดู D1) |
| **ระบบทน traffic จริงไหม** | ❌ **ไม่ได้** | เปิดให้ user ทีละกลุ่ม |

ตัวอย่างที่เจ็บจริง: migration ที่ใช้ 2 วินาทีบน UAT (100 แถว) อาจใช้ 20 นาทีบน prod
(1 ล้านแถว) และระหว่างนั้น **ตารางถูกล็อกทั้งใบ** ระบบล่มโดยที่ทุกอย่าง "ผ่าน UAT แล้ว"

**ทางแก้:** ใน W4 restore snapshot ของ production มาเป็น clone แยกใน subnet ที่ตัดขาด
แล้วรัน migration ที่นั่นเพื่อจับเวลา — ทำก่อนรันบน production จริง
(ตอนนี้ prod ยังไม่มีข้อมูล ครั้งแรกจึงเร็วแน่ ๆ แต่ **ตั้งเป็นนิสัยตั้งแต่ครั้งแรก**
เพราะ migration ครั้งที่ 130 ตอนมีลูกค้า 500 บริษัทคือครั้งที่คุณจะต้องการมัน)
