## 7. สิ่งที่ต้องระวัง

**ชื่อ**

- "payment voucher" ในโค้ดคือใบสำคัญรับเงิน: ตัวทำ PDF, use case, ฟังก์ชันเว็บ และ route `…/expenses/:expenseId/payment-voucher.pdf` ของใหม่ใช้ disbursement voucher และ controller ของตัวเอง
- route ใหม่ใต้ `…/expenses/` จะถูก `:expenseId` รับไป

**การจ่ายและล็อก**

- การยกเลิกรายจ่ายทำงานแบบ Serializable และอ่านก่อนได้ล็อก สิ่งที่มันต้องเห็นต้องอยู่บนแถวรายจ่ายหรือเขียนแถวรายจ่าย และการชนต้องได้ข้อความให้ลองใหม่ วันนี้กลุ่มรายจ่ายยังไม่มีการแปลงข้อผิดพลาดชนิดนี้
- `recordPaymentAtomic` เปิด transaction ของตัวเอง ไม่ตั้งเวลา และใช้ราว 20 คำสั่งฐานข้อมูลต่อรายการ transaction ทั้งใบต้องตั้งเวลาเองและวัดจริง
- กติกาสามข้อของการจ่าย (ไม่ใช่รายการจากใบเบิก, ต้องมีสาขา, วันที่ไม่อยู่ในอนาคต) อยู่ที่ use case ไม่อยู่ในฟังก์ชันที่จะแยก
- เรียก `lockFundingEvidence` ครั้งเดียวสำหรับทุกรายจ่าย แล้วล็อกรายจ่ายตามลำดับ id ก่อนเขียน การเรียกทีละรายการล็อกวนกับใบอื่นและกับการจ่ายตรงของรายจ่ายที่ใช้ไฟล์ใบเสร็จร่วมกัน
- การอนุมัติใบรับรองแทนใบเสร็จเทียบ `updatedAt` ของรายจ่าย การเขียนยอดจองจึงต้องไม่เปลี่ยน `updatedAt` และทางนี้สร้างการจ่ายเองโดยไม่ผ่านฟังก์ชันจ่ายกลาง
- การส่งซ้ำของการจ่ายคืนผลก่อนตรวจสถานะ ทางจ่ายทั้งใบต้องคืนสถานะปัจจุบันของใบ
- ข้อผิดพลาด unique ของ Prisma รุ่นนี้ไม่ให้ชื่อช่องใน `meta.target` ให้อ่านจาก `meta.driverAdapterError.cause.constraint.fields`
- แยกส่วนในของการจ่ายแล้ว ทางจ่ายตรงเดิมต้องตอบและทำงานเหมือนเดิมทุกประการ (F15)

**ผู้รับเงิน**

- การผูกคู่ค้าบนรายจ่ายค้างของเดิมได้ ห้ามใช้เป็นฐานรวมหรือจัดกลุ่ม
- เลขภาษีเก็บตามที่พิมพ์ ไม่ปรับรูปแบบ ไม่มี index การเทียบต้องตัดอักขระที่ไม่ใช่ตัวเลขก่อน
- รายการรายจ่ายเดิมตัดที่ 200 แถว ห้ามใช้เป็นข้อมูลของหน้าสร้าง

**หนังสือรับรอง (ส่งมอบ ก)**

- key กันส่งซ้ำและ key ออกเลขของการออกใบผูกกับรายการรอออก ถ้าไม่ใส่เลขรอบ การออกใหม่หลังยกเลิกได้เลขของรอบเก่ากลับมา หรือชนเมื่อข้ามเดือน
- ตอนยืนยันรายจ่ายใหม่ ระบบนำแถวรายการรอออกกลับมาใช้เฉพาะแถวสถานะยกเลิก มิฉะนั้นสร้างใหม่และชน unique ต้องทำแถวเป็นยกเลิกและล้างตัวชี้ตอนยกเลิกใบ โดยเขียนประวัติก่อน
- ตัวกัน `certificate_issued` ค้นใบจากรายการภาษีโดยไม่ดูสถานะของใบ ต้องเพิ่มเงื่อนไข
- การยกเลิกรายจ่ายที่ยืนยันแล้วไม่แตะรายการรอออกและรายการภาษี (ปล่อยให้การ sync ภาษีจัดการ) งานนี้เปลี่ยนเฉพาะรายการรอออก
- สายอ้างถึงใบเดิมรองรับหนึ่งต่อหนึ่ง ใบที่แก้หลายรอบต้องต่อเป็นสายยาว ไม่ชี้ซ้ำ
- การยกเลิกใบต้องอยู่ใน transaction เดียวกับการยกเลิกรายจ่ายและไม่เรียกบริการภายนอก
- ไม่เปลี่ยนสิ่งที่ผู้ใช้ทำได้ใน "แก้ไขหนังสือรับรอง" และการออกใบแทน เพิ่มแค่การป้องกันและข้อความบนฟอร์ม (E2 เปลี่ยนการเติมค่าเมื่อเจ้าของยืนยัน)

**สิทธิ์**

- เพิ่มสิทธิ์เข้าไปในชุดเดิมจะทำให้ชุดนั้นหลุดติ๊กในตำแหน่งเก่าทุกตำแหน่ง ห้ามทำ
- สิทธิ์ที่ไม่อยู่ในชุดใดเลยจะไม่ถูกตัดเมื่อปิดรายจ่าย และไม่มี test เดิมจับ ข1 ต้องเพิ่ม test นี้
- ตรวจสิทธิ์ด้วย permission เสมอ ไม่ตรวจด้วยชื่อตำแหน่ง ตำแหน่งที่ร้านสร้างเองมี key เป็นรหัสทั่วไป
- สิทธิ์ใหม่ไม่ทำให้กลุ่มเมนูรายจ่ายปรากฏเอง และไม่เพิ่มเข้ารายการนั้น (อยู่ในไฟล์ที่ถูกตรึง hash)

**สวิตช์**

- ข้อความเรียก `buildNavItems` ถูกล็อกด้วย regex ใน test ของบันทึกด้วยมือ และ test ของสวิตช์ตัดช่วงซอร์สของหน้าผู้ดูแลไปตรวจ
- รายชื่อไฟล์ที่อ่านตารางค่าตั้งถูกล็อกเป็นรายการตายตัวใน pg spec
- ช่องของสวิตช์บันทึกด้วยมือห้ามว่างและไม่มีค่าเริ่มต้นในฐานข้อมูล แถวที่สร้างเพราะค่าตั้งใหม่ต้องใส่ค่าเอง
- ไฟล์ session ฝั่ง server ถูกตรึง hash ไม่ต้องแก้ ค่าใหม่ผ่านเป็น JSON ได้เอง
- การบันทึกสวิตช์ต้องไม่โหลดรายละเอียดร้านใหม่ มิฉะนั้นการแก้แพ็กเกจที่ยังไม่บันทึกจะหาย
- `seed.ts` อยู่นอก typecheck ของ API

**ไฟล์แนบ**

- ทางแนบไฟล์ทั่วไปรู้จักปลายทางสองชนิด เพิ่มแค่ในรายการอนุญาตไม่พอ ต้องมีทางของตัวเอง
- ทางดาวน์โหลดและทางลบทั่วไปตรวจแค่สิทธิ์ไฟล์แนบและสาขา ต้องปฏิเสธไฟล์ใหม่ให้ชัด

**หน้าจอ**

- `ExpenseReviewPage.tsx` ถูกล็อกด้วย test ที่ตรวจข้อความในซอร์สและนับลำดับของ state ของใหม่ต้องเป็น component ลูกที่ถือ state เอง ห้ามเพิ่ม hook ที่ถือ state ในระดับหน้า ห้ามใช้ชื่อ `whtIssuePrompt` และแถบล่างรับปุ่มเดียว
- ชื่อปุ่มจริงคือ "แก้ไขเอกสาร" ไม่ใช่ "เปิดกลับมาแก้" ช่องติ๊กบังคับเฉพาะเมื่อมีหนังสือรับรอง เพราะ test ส่งคำสั่งนี้ด้วยเหตุผลอย่างเดียว
- `Modal` กลางปิดเมื่อแตะพื้นหลังเป็นค่าเริ่มต้น และไม่มีระยะเผื่อแถบล่างของเครื่อง
- ช่องเลือกแบบค้นหากรองได้เฉพาะตัวเลือกที่โหลดแล้ว และรายการแบบหล่นลงอาจอยู่ใต้แป้นพิมพ์
- ไม่ส่งรหัสคำขอให้หน้าข้อผิดพลาด (จะพิมพ์รหัสให้ผู้ใช้เห็น)
- คำภาษาไทยใต้ `expenses.*` ห้ามมีอักษรละติน ยกเว้นคำที่อนุญาต; ห้ามใช้ prefix `expenses.v_`; ห้ามคำว่า "ทวิ 50"
- ห้าม `h-screen`/`100vh` และห้ามทำ toast เอง
- error code ใหม่ทุกตัวต้องมีข้อความไทย มี test ตรวจความครบ
- ข้อความต้องจริงในทุกกรณี: ร้านที่ซ่อนเมนู, ร้านที่เปิด, ผู้ที่ไม่มีสิทธิ์, ใบที่ถูกยกเลิก

**การแจ้งเตือน**

- เหตุการณ์ซ้ำของเอกสารเดิมที่ไม่มีตัวบอกรอบใหม่จะถูกรวมกับเหตุการณ์เก่าและไม่ส่งอะไร ไม่มีข้อผิดพลาดให้เห็น
- ชนิดที่ไม่อยู่ในรายการส่ง LINE เสมอ จะไม่ถึง LINE ของสมาชิกที่เคยบันทึกการตั้งค่า
- ชนิดที่ลงทะเบียนในตัวอ่านสถานะเอกสารโดยไม่เพิ่มกิ่งของเอกสารชนิดใหม่ จะถูกอ่านว่างานเสร็จแล้วทันที

**ฐานข้อมูล**

- migration เพิ่มอย่างเดียว ชื่อโฟลเดอร์ตามกติกาที่ตัวตรวจของระบบจริงอ่าน
- enum ใหม่ต้องมีคู่ใน contracts
- ช่องตัวชี้บนตารางรายจ่ายเป็นช่องธรรมดา ไม่มี foreign key

**CI**

- branch ที่เก่ากว่า script ใหม่ของ CI จะล้มจนกว่าจะ merge develop เข้ามา
- งานทดสอบระบบชำระเงินใน CI ล้มแบบสุ่มได้ ให้รันซ้ำเฉพาะงานที่ล้ม ไม่ push commit เปล่า

## 8. ขึ้นระบบและถอยกลับ

1. แต่ละส่งมอบ: merge เข้า develop → ขึ้น UAT ตาม `docs/runbooks/uat-production-v2-deployment.md` บันทึก run id → ผู้ดูแลเปิดเมนูให้ร้านทดสอบบน UAT → เดินบนมือถือ → แจ้งผล
2. **ขึ้น Production เมื่อเจ้าของสั่งเท่านั้น** หลังขึ้นแล้วส่งมอบ ข ยังไม่มีผลกับร้านใดจนกว่าจะเปิดเมนูให้ร้านแรก
3. เปิดให้ร้านจริงทีละร้านจากหน้าผู้ดูแล เริ่มจากร้านของเราเอง ก่อนเปิดให้ร้านลูกค้าร้านแรกต้องมี: ชุดคำตอบของผู้ช่วยใน LINE ที่รู้จักฟีเจอร์นี้ (G22) และคู่มือตอบคำถามหนึ่งหน้าสำหรับซัพพอร์ต (G30)
4. ถอยกลับ: ซ่อนเมนูของร้านนั้นได้ทันทีจากหน้าผู้ดูแล ใบที่ค้างยังทำต่อจนจบได้ ถ้าต้องถอย image ช่องใหม่ว่างได้ทั้งหมดและเว็บรุ่นเก่าไม่รู้จักค่าใหม่ จึงไม่ต้องแก้ข้อมูล
5. ส่งมอบ ก และ ค มีผลทันทีที่ขึ้น Production ต้องแจ้งให้ทราบในบันทึกการขึ้นระบบ ส่งมอบ ก เปลี่ยนสิ่งที่ร้านทำได้กับรายจ่ายที่ออก 50 ทวิแล้ว จึงต้องเดินกรณีจริงบน UAT ครบก่อน
6. ไม่มีขั้นตอน sync แม่แบบการแจ้งเตือนในงานนี้

## 10. สถานะเอกสารและสถานะงาน (12 ต.ค. 2569)

| ส่งมอบ | รอบตามแผน | สถานะ |
|---|---|---|
| ก | ก1–ก5 รวม ก4ข รอบแก้จากการตรวจและการเดินหน้าจอ และรอบ R1 (สามจุดในการบันทึกรายจ่าย D24) | เขียนครบ · PostgreSQL จริงผ่านบนฐานที่สร้างใหม่ · ชุดทดสอบ API เว็บ และ contracts ทั้งชุดผ่าน · เดินหน้าจอจริง 390px สองรอบ · รอเจ้าของลอง |
| ข | ข1–ข11 และรอบแก้จากการเดินหน้าจอ | เขียนครบ · PostgreSQL จริงผ่านบนฐานที่สร้างใหม่ · ชุดทดสอบ API เว็บ และ contracts ทั้งชุดผ่าน · เดินหน้าจอจริง 390px และตรวจซ้ำ · รอเจ้าของลอง |
| ค | ค1–ค4 รอบแก้จากการเดินหน้าจอ รอบ ค7 (ที่อยู่ผู้รับเงิน D22) ค9 (ข้อมูลของร้านเอง D23) และ ค10 | เขียนครบ · PostgreSQL จริงผ่าน · ชุดทดสอบทั้งชุดผ่าน · เดินหน้าจอจริง 390px และตรวจซ้ำ · รอเจ้าของลอง |

- สิ่งที่ต่างจากแผน: รอบ ข4 แยกเป็นสองสายทำพร้อมกัน (คำสั่งของใบ และการกันทางเข้าสี่ทาง); รอบ ข5 แยกเป็นบันทึกจ่ายกับออกจากการจ่ายตรง; รอบ ข6 แยกเป็นไฟล์กับสลิป; เพิ่มรอบแก้จากการเดินหน้าจอของส่งมอบ ก สามรอบ ซึ่งพบบั๊กเลขหนังสือรับรองซ้ำข้ามเดือนของเดิม (spec §10.7 ข้อ 12)
- การตรวจ: ชุด PostgreSQL จริงของรายจ่ายไม่ถูกรันโดยระบบตรวจอัตโนมัติตอนเปิดคำขอรวมโค้ด (รันได้เฉพาะเมื่อสั่งด้วยมือ) หลักฐานเรื่องการชนกันและยอดจองจึงมาจากการรันในเครื่อง ชุดการชนกันต้องรันทีละไฟล์ การรันหลายไฟล์พร้อมกันบนฐานเดียวทำให้ล้มจากภาระของฐานข้อมูล
- ลำดับส่งงาน (D22): เจ้าของลองบนเครื่องเองก่อน แล้วจึงส่งสามชิ้นเข้าสายพัฒนาตามลำดับ ก ค ข
- ส่งมอบ ก ควรขึ้นพร้อม ค: ร้านที่ออกใบเองถูกบอกให้ "บันทึกใบใหม่" และที่บันทึกอยู่ในการ์ดของ ค
